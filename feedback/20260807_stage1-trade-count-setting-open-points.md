# フィードバック: Stage 1 最小取引件数の設定化で計画が触れていない 3 点

## 種別

要求の不足（裁定が定めた範囲の**周辺**に、実装が判断せざるを得なかった点が残った）。
**裁定そのものへの異議ではない。** 実装は裁定どおり行い、判断した箇所を根拠つきで返す。

## 起点となる計画書

- ユースケース（UC）: **UC-06**
- 画面（SC）: **SC-01**（§2 廃止）・**SC-02**（変動閾値・クールダウン・最小取引件数）・**SC-03**（警告表示）

## 問題 1: 値域「1〜1000」のうち**下限 1 の根拠**が述べられていない

### 現状（計画書の記述 / As-Is）

06_daytrading-review §4.1 の追記は「**値域は 1〜1000 件**とする」とだけ述べ、上限 1000 についても
下限 1 についても理由を述べていない。一方、**100 件という既定値については §4.3 が出典つきで詳細に論じている**。

### 何が問題か

**下限を 1 にした場合、条件 3 は「1 件でも約定すれば充足」になる。** これは
「期間（60 営業日）だけで昇格できる」ことと実質的に同じである。§4.1 が条件 3 を置いた目的
（運用に足るかを統計的に判断できる）は、1 件では完全に失われる。

**警告（100 件未満）は表示するが妨げないという裁定と組み合わせると、
「1 件へ下げて 60 営業日で昇格する」経路が正規の操作として存在することになる。**
これは裁定の意図どおりかもしれないが、計画に明記が無いため実装からは判断できない。

### 実装での扱い

**裁定どおり 1〜1000 を実装した**（`Stage1TradeCountBounds`）。0 以下は「条件 3 が無条件に成立する」ため
拒否し、その理由をコードのコメントへ残した。上限 1000 は計画の値をそのまま採った。

### 提案

- **下限 1 の根拠を §4.1 の追記へ 1 文で足す**（例:「1 件は『件数条件を事実上外す』設定であり、
  警告を伴う利用者の明示的な選択として認める」）。**または** 下限を統計的に意味のある値
  （例: §4.3 が「床」と呼ぶ 30 件）へ引き上げる。
- どちらでもよいが、**明記が無いままだと次の実装者が「0 を許してよいのでは」と判断し得る。**

## 問題 2: 「**昇格承認**に警告を常時表示する」の**承認経路**が特定されていない

### 現状（計画書の記述 / As-Is）

§4.1 の追記は「**画面と昇格承認の双方**に……警告を常時表示する」と定める。
一方、昇格承認の窓口は **Discord Bot** である（05_screens「破壊的な統制操作は Discord Bot へ一元化する」）。

### 何が問題か

Discord の段階ゲートには **2 つのコマンド**がある。

| コマンド | 応答が運ぶもの | 警告を出せるか |
| --- | --- | --- |
| `/stage status` | 段階ゲートの現況（`StageGateStatus`。**合格条件を含む**） | **出せる** |
| `/stage promote` | 遷移結果（`StageTransitionResult`。**合格条件を含まない**） | **出せない** |

**「昇格承認」という語が指すのが後者（承認操作そのもの）であれば、現在の契約では警告を出せない。**
遷移応答へ合格条件を載せる（Risk 側の契約変更）か、Bot 側が承認前に status を照会する必要がある。

### 実装での扱い

**`/stage status` の応答へ警告行を足した**（合格条件を運ぶ唯一の経路であるため）。
`/stage promote` には出していない。**承認前に `/stage status` を読む運用**を前提としており、
この前提を `docs/blocked-tasks.md` へ残件として登録した。

### 提案

- **「昇格承認」が指す面を明確にする。** `/stage status` で足りるなら現状のままでよい。
  **承認操作そのものに出す必要があるなら、遷移応答に合格条件を載せる要求として起票が要る。**
- 併せて、**警告を無視して承認した事実を記録に残すか**（承認時の監査エントリへ「100 件未満の設定で承認した」旨を
  含めるか）も定めてほしい。裁定は「下げた事実が記録に残ることを担保する」と述べており、
  **設定変更の履歴には残る**が、**その設定で昇格した事実**は現在どこにも残らない。

## 問題 3: 変動閾値の「理由必須・監査ログ」が**全置換 API には及んでいなかった**

### 現状（計画書の記述 / As-Is）

05_screens SC-02 は変動閾値・クールダウンについて「他のリスク設定と同様に**変更理由を必須**とし、
**監査ログに記録**し、**版（楽観排他）の対象**に含める」と定める。**画面の要件として書かれている。**

### 何が問題か

実装には**画面が使わない全置換エンドポイント** `PUT /monitor/settings` が存在し、
**理由も履歴も持たず、値域も「比率が正・クールダウンが非負」だけ**であった（上限が無かった）。
つまり **API を直接叩けば、理由なしで変動閾値 0.6（60%）を保存できた。**

**要件が「画面の要件」として書かれると、実装は画面にだけ関門を置きがちである。**
統制は「画面が親切であること」に依存してはならない。

### 実装での扱い

**全置換 PUT を部分更新と同じ規律（値域・理由必須・履歴記録）へ揃えた**（IADR-0164 決定3）。
これは以前から [IADR-0155] 残余リスク 4 として記録していた欠陥であり、本裁定を機に解消した。

### 提案

- **設定変更の要件は「画面の要件」ではなく「設定変更の要件」として書く**ことを一般則にしてほしい。
  例: 「本項目の変更は**経路を問わず**理由必須・監査ログ・版の対象とする」。
- 同型の穴が他にも残っていないかは、実装側で棚卸しする（本 PR の範囲外）。

## 参考: 実装が確認した「既に正しかったこと」

**条件 3 の計上単位（「約定が成立した新規建て注文 1 件」）は既に正しく実装されていた**
（#386 / [IADR-0149] 決定2。`DecisionId` を主キーとする観測ログが分割約定・イベント再送を 1 件に畳む）。
2026-08-07 の裁定は**実装が計画の他の記述から読み取っていた前提を追認した**形であり、
本 PR では重複実装をせず、**設定値を 1〜1000 のどこに置いても単位が変わらないこと**をテストで固定した。

同様に、**収集間隔に変更経路が無いことも既に事実であった**。本 PR が足したのは
「無いこと」を**構造テストで固定する**仕掛けである（「実装していない」と「実装してはならない」は別であり、
前者のままだと次の実装者が善意で実装してしまう）。
