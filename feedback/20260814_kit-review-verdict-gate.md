# フィードバック: AI レビューが判定なしで success 終了する穴（kit 共通）

## 種別

**キット内部の欠陥**（計画書の誤りではない）。**配布先の全リポジトリが同じ穴を踏む。**

## 対象

`tools/impl-handoff-kit/repo-template/` の

- `.github/workflows/claude-code-review.example.yml`（プロンプトと後段の検査）
- `scripts/`（**検査器が 1 本足りない**）

## 事象（実測 2026-08-14・ai-stock-trading PR #489）

**同一 PR で 3 回連続、AI レビューが判定（🔴 重大 / 🟡 推奨 / 🟢 軽微）を投稿しなかった。**

| 試行 | 実行時間 | 結論 | 判定 | 形 |
| ---: | --- | --- | --- | --- |
| 1 | 3m55s | **`success`** | **無し** | **A: 待たずにターンを終える** |
| 2 | **20m16s** | `cancelled`（job timeout） | 無し | B: 待って timeout |
| 3 | 11m16s | **`success`** | **無し** | **A** |

3 回とも PR に残ったのは進行中のプレースホルダだけで、1・3 回目には
**「`dotnet test` をバックグラウンドで実行中です。完了後にサマリを投稿します」**と書かれたまま
終わっていた。`timeout-minutes: 20` に対し 2 回目は 20 分 16 秒である。

## 🔴 なぜ実害があるか

| 形 | 結論 | 実害 |
| --- | --- | --- |
| **A: 待たずに終える** | **`success`** | 🔴 **「レビュー済み・指摘なし」と読まれるが何も判定されていない。マージも止まらない** |
| B: 待って timeout | `cancelled` | マージは止まる（gate としては正しい）が、レビューが完了しない |

**A は「緑だが検査されていない」そのものである。**

**既存の `check-permission-denials.js` では捕まらない。** あちらは「AI がツールを 1 つも実行
できなかった」形を見る。本件は**ツールは正常に動いており、最後の投稿だけが無い**——**別の穴**である。

> **実際に、この形 A の green のまま PR がマージされた。** 自前の検証があったため内容の risk は
> 低かったが、**レビュー gate は何の signal も出していなかった。**

## 🔴 引き金は「コード差分ゼロの PR で全テストスイートを回したこと」である

**問題の PR は `backend/` の差分が空**の docs のみの変更であった。それでもレビューは
全スイートを実走しようとし、その待ちで詰まった。

キットのプロンプトは「PR 本文が『テストが通る』と主張しているなら**可能な限り自分で実走して確認**」と
求めているが、**変更範囲を見て絞る指示が無い。**

## 提案（実装側で採った形。3 点セット）

### 1. 検査器 `check-review-verdict.js` を配る（`check-permission-denials.js` の隣）

実行ログ（`steps.claude.outputs.execution_file`）を読み、**AI の出力に判定セクションが
無ければジョブを落とす**。`if: always()` で後段へ配線する。

- **入力は `check-permission-denials.js` と同じ実行ログ**であり、`parseEvents` を借りる（2 本セット）。
- **実行ログを読めないときは warn ＋ exit 0**（fail-open）。**その形は既存の検査器が捕まえる**ため、
  二重に落とす必要は無い。

### 2. 検出は**見出しの構造**で行う（語の一致に頼らない）

**本文の語を素で探すと、レビューが本文中でその語を使った瞬間に誤検出する。**
これは **planning#319 知見3 で実証済みの同型のアンチパターン**である
（検査器について書いた記録が、語の一致だけで自己発火した）。

`### 🔴 重大` / `### 🟡 推奨` / `### 🟢 軽微` の**3 種そろい**を条件とし、
**絵文字と語の両方**を要求する（「重大な問題は無い」という散文で緑にしない）。

### 3. プロンプトへ 2 点を足す

- **バックグラウンド実行の禁止。** 既存の「実行制約・最重要」節は**サブエージェントの spawn 待ち**での
  停止を禁じているが、**バックグラウンドプロセスの待ちは書かれていない**。同じ形の停止である。
  **サマリの投稿はどの検証よりも優先**し、時間が足りなければ「未検証（理由）」と書いて投稿する。
- **変更範囲に応じた絞り込み。** `backend/`（各スタックの実装ディレクトリ）の差分が空なら
  ビルド・テストを実行しない。**実行しなかったことは「実行できなかったこと」節へ理由付きで書く**。

## 🔴 追記（2026-08-14）: 初版は実 CI の初回実行で偽陽性を出した

**提案 1 の検査器の初版は、実データで動かした初回に誤ってジョブを落とした。**

- レビューは**判定を正しく投稿していた**（🔴 0 / 🟡 1 / 🟢 0）。
- それでも検査器は **「見つかった見出し: （無し）」** と報告して落ちた ——
  **判定が無かったのではなく、実行ログから AI の出力を 1 文字も取り出せていなかった。**
- 初版は `assistant` メッセージの `text` ブロックしか読んでおらず、**配送経路を取り違えていた。**

**是正（キットへ配るならこの形で）:**

1. **配送経路を 3 つ見る** —— `assistant` の `text` ／ `result` イベントの `result` ／
   **`input.body` を持つツール呼び出し全般**。
   **🔴 ツール名で絞ってはならない。** 実測では、このワークフローが実際に判定を投稿する経路は
   **`mcp__github_comment__update_claude_comment`** であり、`--allowedTools` から拾って列挙した
   コメント投稿ツール（`add_issue_comment` 等）の**どれにも当たらなかった**。
   **絞るのはツール名ではなくフィールド名（`input.body`）である。**
2. **取り出せなかったときは落とさない**（判定不能として warn ＋ exit 0）。
   **イベント種別の内訳を診断として出す。**

> 🔴 **全文走査で解決してはならない。** 実行ログには**プロンプト自身**が含まれ、その中に
> 判定フォーマットの雛形（`### 🔴 重大` 等）が書かれている。**全文検索にすると常に一致して
> 緑になり、ゲートが無意味になる。** 同じ理由で `tool_use` は **`input.body` に限定する**。

**この 2 点は、キットへ取り込む際に必ず含めること。** 初版のままだと配布先で偽陽性が出る。

## 実装側の実測

- **実 CI で 2 回動かした。** 初版は**偽陽性で failure**（判定は投稿されていたのに抽出できなかった）、
  **是正後は success**（判定あり → 抽出成功。🔴 0 / 🟡 1 / 🟢 1・2m29s・CI 24/24 緑）。
  **🟡 確認できたのは「判定があれば緑になる」ことまでで、「判定が無ければ実データで落ちる」ことは未観測である**
  （自己試験・対照実験でのみ再現）。**キットへ取り込む側も、この限界を承知の上で配ること。**
- **決定 3 点セットの 3（絞り込み）は実データで効いた** —— レビューは `backend/`/`frontend/` の差分が
  空であることを確認し、**ビルド・テストを対象外と判断**した（問題の PR では 3 回とも 4〜20 分かけて
  判定を出せなかったのに対し、2m29s〜3m14s で完了している）。
- 検査器の**自己試験 16 件 all passed**（配送経路 3 種・判定不能の fail-open を含む）。
- **対照実験 4 通りとも予測と一致**——判定 3 種を含む → exit 0／**判定を欠く（形 A の再現）→ exit 1**／
  1 つだけ欠ける → exit 1／**本文に語だけ → exit 1**。

## 影響範囲

- **キットを使う実装リポジトリはすべて同じ穴を持つ。** レビューが判定を出さなくても緑になる。
- 検査器は**外部依存ゼロ**（Node 標準のみ）で、既存の `check-permission-denials.js` と同じ配線に載る。

## 残る弱点（実装側で受け入れた分）

- **プロンプトの遵守は機械では守れない。** 提案 3 が破られても、**判定さえ投稿されれば緑になる。**
- **見出しの書式が変わると偽陽性になる**（検査器の定数とレビューのフォーマットが離れている）。
  **偽陰性より偽陽性へ倒した** —— 落ちれば人が気付くが、緑の素通りは誰も気付かない。
- **判定の「中身」は見ない**（空の判定でも緑）。守るのは「判定が在るか」だけである。
