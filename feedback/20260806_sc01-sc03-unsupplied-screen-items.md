# フィードバック: 画面が表示を求める値に供給元が無い（SC-01 §2 収集間隔・SC-03 空売り現況）

## 種別

要求の不足（画面設計が**供給元の存在を前提にしているが、その供給が計画のどこにも定義されていない**）。
あわせて **由来サービスの誤記**（SC-01 §2）と **値域の未定義**（同）を含む。

## 起点となる計画書

- 機能要求（FR）: **FR-13**（監視銘柄・変動閾値・**収集間隔**・リスク上限などを画面から変更できる）・
  **FR-10**（空売り専用統制）・**FR-11**（監査ログ）・**FR-03**（価格変動検知）
- ユースケース（UC）: **UC-06**（設定変更／代替フロー「現在状態の参照」）
- 画面（SC）: **SC-01 §2**（収集パラメータ）・**SC-03**（統制状態参照の空売り関連の現況・自動縮小の現況）
- 関連 ADR: **ADR-0016** 決定 3・決定 7・決定 9・決定 15 ／ **ADR-0019**（PoC 項目 3）
- 計画書リンク: `projects/ai-stock-trading/05_screens/01_screens.md`（SC-01 §2・SC-03）／
  `projects/ai-stock-trading/02_requirements/01_requirements.md` FR-13

## 問題点 / あるべき姿（To-Be）

### 問題 1: SC-01 §2 の「収集間隔」に供給元が存在しない —— **実装できない**

実装（`develop` 9b0f96f）の実測:

| 値 | 実体 | 読み書きの経路 |
| --- | --- | --- |
| 収集間隔（情報収集） | `CollectionOptions.PollIntervalSeconds`（既定 1800 秒） | **起動時構成のみ**。エンドポイントも設定ストアも無い |
| 収集間隔（市場監視） | `MonitorOptions.PollIntervalSeconds`（既定 60 秒） | 同上 |

**#19（ConfigurationService の設定ストア拡張）はクローズ済みだが、そこで拡張されたのは
`/assumptions`（全体前提条件）であって収集間隔ではない。** SC-01 §2 の備考「#19 完了後に実装する」は
満たされているように見えるが、**収集間隔の供給は #19 の成果物に含まれていない**。

さらに、収集間隔を画面から変えるには「値の永続化」「エンドポイント」に加えて
**稼働中の `BackgroundService`（`CollectionPollingService` / `MonitorPollingService`）が値の変更を
読み直す機構**が要る。これは巡回中のタイミングと絡む挙動変更であり、画面の実装の範囲を超える。

**あるべき姿**: 収集間隔を「画面から変更できる設定」とするなら、計画に
(a) どのサービスの設定ストアに置くか、(b) **稼働中の巡回への反映タイミング**（次回巡回から／即時中断して再開）、
(c) 値域を定める必要がある。定めないなら、SC-01 §2 の対象から外して「起動時構成」と明記すべきである。

### 問題 2: SC-01 §2 の「ConfigurationService 由来」は実装と食い違う

**変動閾値の権威は MarketMonitorService** である（`MarketMonitorSettings.MovementThresholdRatio`・
`GET/PUT /monitor/settings`・OwnerOnly・EF の単一行 JSON ＋ Version 楽観排他）。
ConfigurationService が持つのは `/assumptions` だけである。

計画は SC-01 の責務分界を「**ConfigurationService 由来の収集系パラメータに限る**」と定めているが、
実際にはその値は別サービスにある。**SC-01 は 2 つのサービスを消費する画面になる**（実装では独立縮退で
対処した）。SC-02 が「別サービス由来だから別画面」とされた根拠（planning#33 / IADR-0084）と照らすと、
同じ基準を適用するなら変動閾値は SC-02（監視銘柄と同じ MarketMonitorService 由来）へ移る余地がある。

**あるべき姿**: 由来サービスの記述を実装に合わせて是正するか、責務分界の基準を明示的に再裁定する。

### 問題 3: SC-01 §2 の値域（下限・上限）の具体値が計画に無い

計画は「正値・下限/上限の範囲内」とだけ書き、具体値を与えていない。**検証そのものは要求されている**ため、
実装が値を決めた（IADR-0155 決定3）。

| 項目 | 実装が定めた値域 | 根拠 |
| --- | --- | --- |
| 変動閾値 | **0 超 0.50 以下**（比率） | 0 以下ではあらゆる変動が閾値超過となり、イベント駆動サイクルが常時発火して LLM 費用が暴走する。50% 超では 1 日で半値になる変動でしか発火せず FR-03 が事実上無効になる |
| クールダウン | **0 以上 24 時間以下** | 24 時間超では同一銘柄が 1 営業日に 1 度も再判定されない |

**あるべき姿**: 計画（05_trading-assumptions §5 か SC-01 §2）に値域を明記し、実装はそれを転記する。

### 問題 4: SC-03 が表示を求める値の多くに供給元が無い —— **画面は「未供給」としか書けない**

| 項目 | 供給の実測 | 供給が無い理由 |
| --- | --- | --- |
| **維持率** | **無い** | `UnavailableMaintenanceMarginSnapshotSource` が常に `null`。**PoC 項目 3 で「実弾口座でのみ照会でき SIMULATE では照会 API 自体が失敗」と実測**（ADR-0019 決定1 / `docs/blocked-tasks.md` A-2） |
| **借株料の累計** | **無い** | 累計を保持する型・ストア・イベントがコード全体に存在しない。`ShortSellOrderContext.BorrowRateAnnual` は 1 注文の事前照会入力であり累計ではない |
| **自動縮小の発動履歴** | **無い** | 発火元（維持率）が無く、Risk 側に履歴ストアも照会 API も無い |
| **空売り比率** | **条件付き** | 分母（建玉総額）は**時価**であり、現在値の供給（`MarketData:EnableMarkToMarket`）は既定 false |

**計画は「表示する」と定めたが、「どこから取るか」を定めていない。**
とくに維持率は計画自身が「本画面の最上位に置く。マージンコールは口座を失う唯一の経路である」と
書いた指標であり、**表示できないことの重大さが計画側に見えていない**。

**あるべき姿**: 計画に次を明記する。

1. **維持率の供給元と鮮度**（実弾ヘッダでの照会が要ることは PoC で判明済み。ADR-0016 決定 14 の表に
   「SIMULATE では値そのものが取れない」を追記する裁定は `blocked-tasks` B-4 に登録済み）。
2. **借株料の累計を記録するか**。FR-18 が Won't であっても「経費の記録は不要にならない」と ADR-0016 決定 15 が
   定めており、記録の粒度は FR-11 が担保するとされている。**しかし累計を集計・保持する経路は定義されていない。**
3. **自動縮小の発動履歴の保持先**（日報・監査ログのほかに、SC-03 が参照できる照会 API が要る）。
4. **空売り比率の分母に用いる時価の供給**（現在値の source と、供給が無いときの扱い）。

### 問題 5: 「表示できない」ことをどう見せるかが計画に無い

計画は表示項目を列挙するが、**供給が無いときの表示規約を持たない**。素朴に実装すると 0 や「—」になり、
**統制が正常に働いているように見える**（[#403] の `ControlViolationCount` 既定 0 が「違反なし」に見えた
fail-open と同型）。

実装は供給可否をサーバが宣言する形（`MetricAvailability`・IADR-0154）で対処したが、
**これは画面表示の規約であり、本来は計画（05_screens の表示規約）に属する**。

**あるべき姿**: 05_screens の「表示規約（共通）」へ次を追加する。

> **供給が無い値は「0」「—」で表示しない。** 「取得できていません（供給元がありません）」と明示し、
> 「概念が成立しない（対象なし）」と区別する。とくに統制の現況を表す値は、供給が無いこと自体が
> 「統制が働いていない」という運用上の事実であり、正常値と同じ見た目にしてはならない。

  `docs/adr/IADR-0155_sc01-collection-parameters-supply.md`（収集パラメータ）
- SC-03 の空売り表示項目を実装しようとして、**表示すべき値の大半に供給元が無い**ことが判明した。
  0 で埋めれば画面は作れるが、それは #403 と同型の fail-open を統制の中核指標に作ることになる。
- SC-01 §2 は「#19 完了後に実装する」という備考の前提が満たされていたが、**#19 の成果物に収集間隔は
  含まれていなかった**。変動閾値だけは別サービスに供給があった。

## 提案（計画への反映案）

- 反映先候補: **要求更新（FR-13）** ／ **画面更新（05_screens SC-01 §2・SC-03・表示規約）** ／
  **ADR-0016 決定 14・決定 15 の追補** ／ **ADR-0019 の PoC 項目**
- 提案内容:
  1. **05_screens の表示規約（共通）へ「供給が無い値の表示規約」を追加する**（問題 5）。
     これが最も広く効く。SC-03 以外の画面にも同じ状況が発生し得る。
  2. **SC-01 §2 の「収集間隔」を、供給を定義するか対象から外すかで裁定する**（問題 1）。
     供給を定義するなら「稼働中の巡回への反映タイミング」まで含める。
  3. **SC-01 §2 の由来サービスを MarketMonitorService へ是正する**か、責務分界を再裁定する（問題 2）。
  4. **変動閾値・クールダウンの値域を計画に明記する**（問題 3。実装値を採るなら 0 超 50%／0〜24 時間）。
  5. **SC-03 の各表示項目に「供給元」の列を足す**（問題 4）。表示要求と供給要求を 1 つの表で対応づければ、
     「表示すると決めたが取れない」状態が計画の段階で見える。
  6. **借株料の累計の記録要件を明記する**（ADR-0016 決定 15 の追補）。

## 影響範囲

- **FR-13**: 「収集間隔を画面から変更できる」は現状**充足していない**。裁定次第で要求の表現が変わる。
- **SC-01**: 由来サービスの是正は画面の責務分界（planning#33 / IADR-0084）に触れる。
- **SC-03**: 供給元が入るまで、維持率・借株料の累計・自動縮小の発動履歴は「取得できていません」と
  表示され続ける。**これは実装の不具合ではなく、供給が無いという事実の正しい表現である。**
- **ADR-0016 決定 14** の「Stage 1 で検証できない統制」の範囲は、既に `blocked-tasks` B-4 で
  「当初想定より広い」ことが登録済みであり、本フィードバックはその追認でもある。
- **ADR-0019**: 維持率の照会が実弾ヘッダを要することは PoC で確定済み。供給の実装（#331 / #342）が
  入るまで SC-03 の最上位指標は表示できない。
