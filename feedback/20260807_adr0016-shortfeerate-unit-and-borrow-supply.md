## 1. `ShortFeeRate` の単位が未確定であり、確定の経路も定まっていない

### 現状（計画書の記述 / As-Is）

決定3 の改訂は「**`ShortFeeRate` の値 `1.5` の単位は未確定である**（年率 1.5% か否か）。**確定するまで
FR-17 の費用計算へ流し込まない。** 単位を取り違えると費用モデルが 100 倍ずれる」と定めた。

**「確定するまで流し込まない」とは書かれているが、「どうすれば確定するのか」は定められていない。**
ADR-0019 の PoC 項目にも単位の確認は含まれていない（項目3 は「維持率・借株料・借株可否を取得できるか」であり、
取得できたことは確認したが、単位の解釈は対象外である）。

### 問題点 / あるべき姿（To-Be）

単位が確定しない限り、次の 3 つが同時に止まる。

| 止まるもの | 理由 |
| --- | --- |
| FR-17 の費用計算（採算評価） | 決定3 改訂が明示的に禁じている |
| **ADR-0016 決定14 のバックテスト費用モデル**（借株料を織り込む） | 同じ値を用いる。**決定14 は借株料の織り込みを Stage 3 解禁の前提としている** |
| **決定3 の 20% 閾値判定への料率供給**（後述 2・3） | 供給する値が作れない |

**提案**: 単位の確定手段を計画側で定める。実装側が考え得る経路は次の 3 つである（いずれも実装側だけでは
決められない——実弾口座の操作または moomoo への問い合わせを伴うため）。

1. **既知の値との突合**: SIMULATE の借株料は「年率 6% 固定」とされている（決定14）。同じ API で
   SIMULATE の値が取れれば、`6` と返るか `0.06` と返るかで単位が定まる。**ただし PoC の実測では
   SIMULATE では照会 API 自体が失敗する**ため、この経路は使えない可能性が高い。
2. **moomoo のドキュメント / サポートへの照会**（`TrdGetMarginRatio.ShortFeeRate` のフィールド定義）。
3. **実弾での実費との突合**（実際に空売りを 1 件建てて請求額と照合する）。**Stage 3 の解禁後でなければ
   実行できず、順序が逆転する**（費用モデルの検証は解禁の前提であるため）。

**1 と 3 が使えないなら 2 しか残らない。** ADR-0019 の PoC 項目へ「借株料の単位の確定」を追加するか、
別途の確認事項として計画へ記録することを提案する。

## 2. 「一律料率なら 20% の閾値は永久に超えない」は、単位が「%」であるという読みを前提としている

### 現状（計画書の記述 / As-Is）

決定3 の改訂は「**一律料率であれば 20% の閾値は永久に超えず、本統制は何も弾かない**」と述べ、これを
一次ゲートを移す理由の 1 つとしている。

### 問題点 / あるべき姿（To-Be）

**この記述は `1.5` を「1.5%」と読んだ場合にのみ成立する。** `1.5` が比率（＝150%）であれば、
上限 `0.20`（年率 20%）を **7.5 倍超過**し、**閾値は全銘柄で発火して空売りが 1 件も通らなくなる**。
すなわち「何も弾かない」の正反対である。

| `1.5` の読み | 年率（比率） | 20% 閾値の挙動 |
| --- | --- | --- |
| 1.5%（＝ 0.015） | 0.015 | **発火しない**（改訂の記述どおり） |
| 比率 1.5（＝ 150%） | 1.5 | **全銘柄で発火**（記述と正反対） |

**同じ実測値が、単位の読み方ひとつで統制の帰結を反転させる。** 改訂は「単位は未確定である」と
正しく認識しているが、**同じ文書の中で「永久に超えない」と断じており、両者は整合していない。**

**提案**: 決定3 の改訂に「**この記述は `ShortFeeRate` が百分率であるという読みを前提とする。単位が
比率であった場合、閾値は逆に全銘柄で発火する**」という但し書きを加える。単位の確定（問題 1）で
自動的に解消するが、確定までの間、この文言だけを読んだ者が「閾値は安全に残置できる」と誤読し得る。

> 実装側は**この反転そのものをテストで固定した**（`実測の借株料をそのまま年率として写像すると全件拒否になる`。
> `docs/tests/FR-10_risk-controls-tests.md` T-10-213）。文章ではなく実行可能な形で残してある。

## 3. 単位が確定しない限り、一次ゲートを実地で観測できない（決定3 の 2 つの規則が互いを塞ぐ）

### 現状（計画書の記述 / As-Is）

決定3 は改訂後も次の 2 つを**同時に**要求している。

- **（未改訂）** 発注前に借株料を照会できない場合、**空売り自体を行わない**（フェイルクローズ）。
- **（改訂）** 一次ゲートは `IsShortPermit=False` の拒否である。

### 問題点 / あるべき姿（To-Be）

実装は両方を満たしている（料率 `null` → `BorrowUnavailable`／`IsShortPermit=False` → `BorrowUnavailable`）。
しかし**単位が未確定である間は料率を安全に供給できない**ため、`BorrowRateAnnual` は `null` のままとなり、
**借株が許可された銘柄（`IsShortPermit=True`）であっても空売りは拒否され続ける。**

**すなわち、一次ゲートを可否へ移した効果を実地で観測できない。** Stage 1（SIMULATE）で
「借株できる銘柄は通り、できない銘柄は弾かれる」ことを確認しようとしても、**すべてが弾かれる**。

| 決定14 の記述 | 実装から見た現況 |
| --- | --- |
| 決定3 の実弾解禁前の確認方法＝「一次ゲート `IsShortPermit` が実弾で機能することを確認」 | **単位が確定し料率を供給できるようになるまで、この確認は「一次ゲート**だけ**が働いている」状態を作れない**（料率の欠落で先に落ちる） |

**提案（2 案。裁定を求める）**:

- **案 A（推奨・現状維持）**: 料率の欠落によるフェイルクローズを維持する。**安全側であり、決定3 の
  未改訂部分に忠実**である。代わりに、単位の確定（問題 1）を Stage 1 の空売り検証の**前提条件**として
  決定14 の表へ明記する。
- **案 B**: 一次ゲートを移したことに合わせ、「**料率を取得できないことは、可否が取得できている限り
  拒否理由としない**」と決定3 を further 改訂する。20% 閾値は料率が供給されたときにのみ評価する。
  **統制が緩む向きの変更であり、実装側からは推奨しない**——「照会できないなら通す」は決定3 が
  最初に明示的に棄却した縮退そのものである。

**実装は案 A のままとし、裁定があるまで変更しない。**

## 影響範囲

- **FR-10**: 空売りの一次ゲートは実装済み（#417）だが、**供給が無いため一度も発火しない**。
  `docs/blocked-tasks.md`「実装済みだが発動しない機能」に登録した。
- **FR-15 / ADR-0016 決定14**: バックテストへの借株料の織り込みは**単位の確定まで着手できない**。
  Stage 3 の空売り実弾解禁の前提条件に関わる。
- **FR-17**: 概算費用への借株料の算入は同じ理由で着手できない。実装側は**接続を構造テストで塞いだ**
  （公開面に `Borrow` / `ShortFee` を含む名前が生えたら赤くなる）。
- **ADR-0019**: PoC 項目3 は「取得できるか」を確認したが「単位は何か」は対象外であった。
  項目の追加または別途の確認事項としての記録を提案する。
