# feedback — 計画へのフィードバック記録

実装中に判明した**計画書（`project-planning`）の誤り・不足・新たな制約**を計画側へ環流（フィードバック）するための記録置き場である。

## いつ使うか

- 計画書（要求・UC・画面）の記述が実態と異なる、または不足している。
- 実装で新たな技術・設計上の制約が判明し、ADR を起こすべき。
- 計画書に未登録の用語が頻出する。

## 手順

1. `/plan-feedback <FR-xx|topic>` を実行する（`plan-feedbacker` エージェントが起票を補助）。
2. `feedback/TEMPLATE.md` を雛形に、`feedback/<YYYYMMDD>_<概要>.md` に記録が作成される。
3. 計画リポジトリへ伝達する（両経路に対応）。
   - **記録ファイル経路**: 作成した記録を計画リポジトリの `draft/feedback/` にコピー（submodule/隣接クローン経由）。
     計画側で `/triage-feedback` がトリアージする。
   - **GitHub Issue 経路**: `/plan-feedback` が生成した Issue 本文を、`endazon/project-planning` の
     「計画へのフィードバック」Issue テンプレートに貼り付けて起票する（GitHub MCP / `gh` でも可）。
4. 計画側でトリアージされ、要求更新 / 新 ADR / 用語追加などに反映される。

## `status` の語彙（4 値）

**`status` は「計画側の裁定がどこまで進んだか」を表す。「伝達したか」は表さない**（それは `dispatched:` / `planning_issue:` が担う。後述）。雛形は `status: open` を既定値として配る。

| 値 | 意味 | 誰が書き換えるか |
| --- | --- | --- |
| `open` | 記録を作った。**計画側の裁定はまだ下りていない**（雛形の既定値） | —— |
| `awaiting-decision` | 計画側が受け止めて**反映まで進んだが、裁定待ちの論点が残っている** | **計画側**（`/triage-feedback`） |
| `accepted` | 計画側が**受け入れた**（計画書・ADR へ反映された） | **計画側**の裁定を実装側が転記する |
| `rejected` | **採らないと決まった** | 同上 |

**遷移は `open` → `awaiting-decision` → `accepted` / `rejected` の一方向とする。** `awaiting-decision` は飛ばしてよい（裁定待ちが残らなければ `open` → `accepted`）。

> **`status` と「伝達したか」を混ぜない。** 実測では、実装リポジトリが `triaged`（旧称）を「**実装側が伝達した**」の意味で 7 件に付け、計画側は同じ語を「**計画側が反映した**」の意味で使っていた。**1 つの語が両側で正反対の主体を指していた**（裁定 2026-08-13。planning#323）。伝達の記録は `dispatched:` / `planning_issue:` に書くこと —— **鍵が分かれていれば、どちらの意味かを読み手が推測せずに済む。**
>
> **旧称 `triaged` は使わない。** 「計画側がトリアージに載せた」とも「実装側がトリアージへ回した」とも読めたため `awaiting-decision` へ改めた。既存記録に `triaged` が残っていれば、意味を確かめてから移行する —— **「伝達した」の意味で付けていたなら `open` ＋ `dispatched: true` が正しく、`awaiting-decision` ではない。**
>
> **`resolved` のような語彙外の値を作らない。** 実測では 1 リポジトリが `resolved` を 6 件に使っており、**同じキットを配った 2 リポジトリで語彙が割れていた**。値域を増やすときは本節を直してから使うこと。
>
> **この語彙を検査する機械は無い。** 値の誤りは沈黙する。**`check-feedback-dispatched.js` が見るのは伝達の証拠だけ**であり、`status` は `open` かどうかしか読まない。

## 【最重要】記録を作るだけでは計画へ届かない

**手順 2（記録の作成）と手順 3（計画リポジトリへの伝達）は別の作業であり、3 が漏れる事故が繰り返し起きている。**

2026-08-06 の棚卸しでは、**6 件の記録が「未送付」のまま最長 1 か月近く実装リポに滞留していた**（うち 1 件は実装コードのコメントが「計画へ環流済み」と述べていたのに該当ファイルすら無かった）。**いずれも PR はマージ済みであり、記録には `status: open` と「未送付。計画リポジトリへ issue として起票する」と書かれたままだった。** PR がマージされても検出されない点で、通常の未反映よりも見つけにくい。

**手順 3 まで完了させて初めて `/plan-feedback` は終わる。** 伝達したら**記録に計画リポジトリの issue / PR の URL を残す**こと（後から到達を確認できるようにするため）。**どちらの経路を採ったかで残る証拠が違う**（後述の表）。

### CI による検出（警告のみ）

`scripts/check-feedback-dispatched.js` が CI（`doc-links` ジョブ）で次を警告する。**ジョブは落とさない。**

- `status: open` で、**計画リポジトリの issue / PR への参照が無い**記録
- フロントマターが **`dispatched: false`** で、**かつ他に伝達の証拠も無い**記録（`status` を問わない。記録自身の自己申告）
- **`dispatched:` の値が `true` / `false` のどちらでもない**記録（**YAML 1.1 では `no` / `off` も偽**であり、書くと黙って警告が消えるため）

**警告に留めるのは、起票が人手の判断を伴うためである。** ブロックにすると「記録を作らない」という回避策を誘発し、統制の目的（環流の取りこぼしを無くす）と逆の結果になる。厳格化したい場合は `STRICT_FEEDBACK_DISPATCH=1` を設定する。

> **自リポジトリの issue / PR URL は伝達の証拠にならない。** 計画リポジトリ（別リポジトリ）へのリンク、またはフロントマターの `planning_issue:` / `dispatched: true` が要る。**証拠はこの 3 つだけである**（いずれも構造化された記述である）。
>
> **証拠として認める URL の宛先は 1 つに限られている**（`scripts/check-feedback-dispatched.js` の 置換点 `PLANNING_REPO`）。**警告が出たのに URL を残した覚えがあるなら、まずこの置換点を疑うこと** —— 配布時に自組織の計画リポジトリへ書き換えていないと、正しい URL でも証拠と認められない。無関係な第三者リポの URL を証拠にしないための制限である。
>
> **本文の「起票済み」は証拠にしない。** 素の部分一致であり**文意と無関係に一致する** —— 実測では「他件は**起票済み**だが本件は未対応である」「本件は未**起票済み**である」のいずれもが証拠と判定された。撤廃した「未送付」と同じアンチパターンである。
>
> **鍵が「見えない」形は検出できない** —— **鍵名の誤記**（`dispatchd:`）・**全角コロン**（`dispatched： false`）・**字下げされた鍵**。いずれも鍵が無いのと区別がつかない。`status: open` 側の条件が拾うが、**`status` がそれ以外なら素通りする**。
>
> **`planning_issue: #319` は値として読む。これは YAML 仕様からの意図的な逸脱である。** YAML では空白直後の `#` はコメントであり値は null になるが、**人が issue 番号をこの形で書く**ため、`planning_issue:` に限り `#` ＋数字を値として残す。**他の YAML 読取（`/triage-feedback` 等）とは解釈が割れる**ので、確実を期すなら `319` か URL で書くこと。`status:` / `dispatched:` にこの例外は効かない（閉じた語彙と突き合わせる鍵で効かせると、沈黙と偽陽性の両方を招く）。

#### 経路ごとの証拠（両経路とも機械検査の対象である）

**手順 3 の 2 経路は、残る証拠が違う。** 検査器は**どちらの経路でも緑になる**（確定・2026-08-11。planning#319）。

| 経路 | 残す証拠 |
| --- | --- |
| **GitHub Issue 経路** | フロントマター `planning_issue:`、または計画リポジトリの **issue URL** |
| **記録ファイル経路** | コピーを載せた計画リポジトリの **PR URL** |

**`dispatched: true` はどちらの経路でも使える**（検査器は両経路を等価に扱う）。URL の走査は**ファイル全体**が対象で、フロントマターの `source_ref:` に書いた URL も証拠になる。

> **記録ファイル経路は issue を作らないため、証拠になり得るのは PR しかない。** 検査器が issue 経路しか読まなかった頃は、**この経路を採った記録に恒久的な偽陽性が残っていた**（実測 1 件）。**検査器を満たすためだけに別途 issue を立てるのは、「いずれか一方で足りる」という手順自体に反する。**
>
> **自己申告は本文の語ではなくフロントマターの鍵で書く。** 以前は本文の「未送付」の語で警告していたが、**素の部分一致であるため、この検査器そのものを論じた記録が語を含むだけで自己発火した**（実測。見出しに 1 回使っただけで警告が 1 → 2 件に増えた）。環流の運用を論じる記録ほどこの語を使うため、**鍵へ移して構造的に断ち切った**。
>
> **`dispatched: false` は「他に証拠が無い」ときだけ警告する。** 雛形は `dispatched: false` を**既定値として配る**ため、無条件に警告すると**雛形どおりに書いた記録が必ず赤くなる**（`planning_issue:` を埋めても消えない）。**鍵の更新漏れは伝達そのものの欠落ではない。**

#### 既存記録の移行

**本文に「未送付」とだけ書いて `status: accepted` の記録は、新しい判定では警告されない**（語による判定を撤廃したため）。**該当する記録には `dispatched: false` を明記すること。** 移行しない間は、この検査器の目的（起票漏れの検出）がその記録に対して働かない。

## 注意

- 記録は事実と提案を分けて書く。確定は計画側（人間 + `/triage-feedback`）が判断する。
- この `feedback/` ディレクトリは実装リポジトリ側の控えである。原典の反映先は計画リポジトリ。
