# フィードバック: ADR-0016 決定4 改訂（強制買戻しの事後推定）の実装で判明した 4 点

## 種別

**前提の不足**（4 件）。いずれも [ADR-0016](https://github.com/endazon/project-planning/blob/main/projects/ai-stock-trading/07_adr/ADR-0016_short-selling-staged-release.md)
決定4 の 2026-08-06 改訂および決定15 の 2026-08-06 追記を実装
（[#419](https://github.com/endazon/ai-stock-trading/issues/419)）する過程で判明した。
**改訂・追記の内容そのものに異議はなく、実装は文面どおりに行った。** 本記録が求めるのは、
実装が文面から一意に読めず**裁量で決めた 2 点の追認**と、**実装側では解けない 2 点の扱い**である。

## 問題 1（裁量の追認を求める）: 「自らの決済指示」に**承認済み・未約定**の決済を含めた

決定4 の改訂は「**自らの決済指示に対応しない建玉の消失**を強制買戻しとみなす」と定めている。
文面の「決済指示」を**約定履歴だけ**と読むと、**通常運行のたびに誤検知が出る**。

- 決済注文が**ブローカで約定してから、その約定が取引台帳へ届くまで**の間、台帳とブローカは**正当にズレる**
  （既存の建玉突合〔#292〕が連続観測条件を置いたのと同じ事象）。
- この区間で建玉照会が走ると、「台帳にはある・ブローカには無い」＝**自らの手仕舞いが強制買戻しに見える**。

実装は**承認済みだが未約定の決済数量**（既存の `GetInFlightCloseQuantity`・遡り窓 30 分）も
「自らの決済指示」に含めて差し引いた。**注文の承認は決済指示そのもの**であり、文面と矛盾しないと判断した。

```
未説明の消失 = max(0, 台帳の空売り数量 − ブローカの空売り数量 − 処理中の決済数量)
```

**依頼**: この読み方でよいかを追認いただきたい。もし「約定履歴のみで突合する」が意図であれば、
**正常な手仕舞いのたびに強制買戻しと推定され 30 日禁止が積み上がる**ため、改訂の目的（同じ銘柄で繰り返さない）
とは別の副作用が出る。

## 問題 2（裁量の追認を求める）: 部分約定の扱いを「数量差」に決めた（**消失＝ゼロ**を待たない）

改訂は「**建玉の消失**を約定履歴と突合し」と述べるが、**部分的な消失**をどう扱うかは書かれていない。
実装は**数量差**で突合し、前回までに推定済みの数量を超えた**増分だけ**を新たな推定とした。

- 「建玉が 0 になった時点」を待つ案は採らなかった——**ブローカが分割して買い戻すと永久に発火しない**（過少推定）。
- 逆に、同じ乖離を毎巡回で推定すると **30 日の禁止が事実上の恒久禁止**になる（台帳は自動で是正されないため
  乖離は解消しない）。したがって帰属数量を持ち、**同じ乖離につき推定は 1 回**とした。

**依頼**: 「数量差で推定し、増分ごとに禁止期限を更新する」でよいかを追認いただきたい。

## 問題 3（実装側では解けない）: **報告書へ発生有無・発生回数を供給する経路が無い**

決定15 の追記は「集計元は事後突合が推定した件数である」「**供給が無い間は 0 件と表示してはならない**」と定めた。
**実装は推定の件数を集計元とし、`BuyInBanned` の拒否件数を用いていない**（構造テストで固定した）。

しかし、**推定はリスク管理サービスで動き、報告書は報告サービスが作る**。両者を結ぶ照会 API が無いため、
報告書の記録源は既定で **`null`（未供給）** を返し、日報・月報は
「**照会できませんでした（供給元がありません）**」と表示する。**0 件とは書かない**（決定15 の明文どおり）。

**依頼**: 本状態が決定15 の意図と一致することの確認（＝「推定経路は入ったが報告書には出ない」という
中間状態を許容してよいか）。許容されるなら実装側で照会 API を起票する。

## 問題 4（実装側では解けない）: **推定経路は Stage 1 で一度も発火しない見込みである**

決定14 の表は「決定4（強制買戻しの検知）」の Stage 1 での確認事項を
「**建玉消失と約定履歴の突合による事後推定が動くことを確認**」と改めた。しかし実装の観点では、
Stage 1 でこれを観測できる見込みが立たない。

| 前提 | 現況 |
| --- | --- |
| 突合の入力（`BrokerPositionsObserved`）が届くこと | **OpenD の常駐が要る**（ADR-0019 決定2 の工程 ①・Hetzner ToS が未着手） |
| 空売り建玉が存在すること | **借株照会の供給元が無く、すべての新規売り建てが `BorrowUnavailable` で拒否される**（決定3 改訂・IADR-0158）。加えて `ShortFeeRate` の単位が未確定であり、照会を実装しても料率を供給できない（環流 `20260807_adr0016-shortfeerate-unit-and-borrow-supply.md`） |

**空売り建玉が 1 件も無ければ、突合すべき消失も存在しない。** すなわち、決定14 が求める
「事後推定が動くことの確認」は、**借株照会の供給が成立するまで実行できない**。

あわせて、**推定が動かない間の安全性は別の統制に依存している**——空売り自体が全件拒否であるため
「同じ銘柄で繰り返す」経路が存在しない。**この依存は借株照会が実装された日に消える**ため、
そのとき推定側の縮退（照会失敗時は推定しない）を再評価する必要がある（IADR-0159 決定4 に記録した）。

**依頼**: 決定14 の Stage 1 確認事項について、(a) 借株照会の供給成立を前提条件として明記するか、
(b) 確認自体を実弾解禁前の別工程へ移すか、の裁定。

## 参考: 実装が採った向き（記録）

- **過剰推定（fail-closed）へ倒した。** 決定4 の目的が「同じ銘柄で繰り返さない」ことであり、
  過剰推定の代価（不要な 30 日禁止＝機会損失）と過少推定の代価（損失に上限の無い取引での強制決済の反復）は
  同じ重さではないためである。**手動売買・外部要因による建玉消失を強制買戻しと取り違え得る**ことは
  既知の代価として受け入れ、根拠（消失した建玉・突合した決済約定・処理中の決済・推定日時）を監査ログへ残した。
- **ただし「照会不能＝建玉ゼロ」とは読まない。** それは最も過剰な推定だが、OpenD の 1 回の切断で
  全監視銘柄が 30 日禁止になり、**統制ではなく事故**になるためである。
