## 問題点 / あるべき姿（To-Be）

### 1. 系列 ID は `FM08'FXERD04` である（確定）

日本銀行 時系列統計データ検索サイトの統計別検索（外国為替市況 [FM08] → 外国為替相場状況(日次)）で、ドル・円スポットの日次系列は次のとおりである（2026-08-05 実測・全 22 系列）。

| データコード | 系列名称 |
| --- | --- |
| `FM08'FXERD01` | 東京市場 ドル・円 スポット 9時時点 |
| `FM08'FXERD02` | 東京市場 ドル・円 スポット 最高値 |
| `FM08'FXERD03` | 東京市場 ドル・円 スポット 最安値 |
| **`FM08'FXERD04`** | **東京市場 ドル・円 スポット 17時時点** |
| `FM08'FXERD05` | 東京市場 ドル・円 スポット 中心相場 |
| `FM08'FXERD06` | 東京市場 ドル・円 スポット出来高 |
| `FM08'FXERD07` | 東京市場 ドル・円 スワップ出来高 |

単位は `￥／＄`、期種は `DAILY`、収録開始は 1998/01/05（`FXERD04`）／1999/01/01（`FXERD05`）。

### 2. 「17 時時点」と「中心相場」は定義が異なる。仲値なのは 17 時時点だけである

一次情報の原文は次のとおりで、**ADR-0022 決定 1 の表（仲値）と一致するのは `FXERD04` であり、注記が挙げた「中心相場」（`FXERD05`）ではない。**

- 外国為替市況（日次）ページ:「ドル／円およびユーロ／ドルの9:00時点および17:00時点のスポット・レートは、時系列統計データ検索サイトでは、**オファーとビッドの中間値**を掲載しております。」
- 「外国為替市況」の解説:「**中心相場** — 取引金額で測ったその日の代表的なスポット相場です。ブローカーに、当該日に**最も取引の多かった出来値**を聴取し、その結果を公表しています。」

すなわち **中心相場は仲値ではなく、最も取引の多かった出来値**である。両者を取り違えると、統制判定に入る換算レートの定義が計画の意図とずれる。

**あるべき姿**: 決定 1 の注記の「中心相場」は誤りとして訂正し、採用系列を `FM08'FXERD04` と明記する。

### 3. 「HTTP 403」は本環境では再現しない。公式 API がある

2026-08-05 に、ブラウザ経由・非ブラウザの HTTP クライアント（curl）経由の**双方**で取得に成功した。403 は返らなかった。したがって「自動取得を拒否されているため人手で確認するほかない」という前提は成立しない。**機械的な定期取得は可能である。**

日銀は**公式 API を提供している**（「API 機能利用マニュアル」2026-02-18 版）。要点は次のとおり。

| 項目 | 内容 |
| --- | --- |
| 利用登録 | **不要**。「API機能はどなたでもご利用いただけます」。API キーの概念が無い |
| エンドポイント | `https://www.stat-search.boj.or.jp/api/v1/getDataCode`（ほかに `getDataLayer` / `getMetadata`）。**大文字小文字を区別する** |
| パラメータ | `format`（json/csv）・`lang`（jp/en）・`db`（必須）・`code`（必須）・`startDate`・`endDate`・`startPosition` |
| **落とし穴** | `code` には **系列コード**（`FXERD04`）を指定する。**画面で使う「データコード」（`FM08'FXERD04`）を指定するとエラーになる**。DB 名は `db=fm08` として別に渡す |
| 日次の期間指定 | 週次・日次も**月次形式 `YYYYMM`** で指定する |
| 制限値 | 1 リクエストあたり系列 250 件／データ 60,000 件（系列数 × 期数）。超過分は `NEXTPOSITION` でページングする |
| 圧縮 | `Accept-Encoding: gzip` に対応 |
| アクセス頻度 | **具体的な数値上限は示されていない**。「短時間における高頻度のアクセス」を禁止行為とし、負荷状況に応じて制限をかけることがある、と定める |

実際に成功したリクエスト:

```text
https://www.stat-search.boj.or.jp/api/v1/getDataCode?format=csv&lang=jp&db=fm08&code=FXERD04,FXERD05&startDate=202607&endDate=202608
```

応答（CSV・CP932）はヘッダに `STATUS,200` / `MESSAGE,正常に終了しました。` / `DATE,2026-08-05T21:08:47.734+09:00` を持ち、データ行は `系列コード,系列名称,単位,期種,統計名,最終更新日,日付,値` の並びである。**該当日にデータが無い場合は値が `null` になる**（欠測と休場の区別は付かない）。

### 4. 検索サイトへの収録は「翌々営業日 8:50 頃」である — 決定 4 の前提が崩れる

**これは推測ではない。日本銀行が公表している掲載予定表（`https://www.boj.or.jp/statistics/outline/tkohyos.xlsx`）に明記されている。**

| 対象 | 公表・掲載 | 頻度 |
| --- | --- | --- |
| 外国為替市況（日次）＝**本体の公表**（PDF） | **17:50 頃** | 毎営業日 |
| 外国為替相場状況（インターバンク相場・東京市場、円インデックス：日次）＝**時系列統計データ検索サイトへの収録** | **翌々営業日 8:50 頃** | 毎営業日 |

すなわち、**営業日 D のレートが機械可読な経路に載るのは D の 2 営業日後の朝**である。決定 1 の表が公表頻度を「毎営業日」と書いているのは本体 PDF の話であり、**実装が読む経路の鮮度ではない**。

実測もこれと一致した。2026-08-05（水）21:08:47 JST 時点で、API・主要時系列統計データ表の**いずれも**次の状態だった。

| 日付 | `FXERD04` | 備考 |
| --- | --- | --- |
| 2026/07/31（金） | 160.21 | |
| 2026/08/01（土）・08/02（日） | null | 休場 |
| 2026/08/03（月） | 156.77 | **これが最新** |
| **2026/08/04（火）** | **null** | 営業日。本体 PDF は 08/04 17:50 に公表済み |
| 2026/08/05（水） | null | 本体 PDF は本日 17:50 に公表済み |

コールレート（`FM01`）でも収録終了期が同じく 2026/08/03 であり、統計固有ではない。

#### 追試手順（本記録の主張を第三者が再確認するための手順）

**本記録の根拠はいずれも外部サイトの実測であり、記録を読むだけでは真偽を確かめられない。** 追試は次の 3 つで足りる。いずれも認証不要・副作用なしである。

1. **系列 ID と値**（§1・§4 の実測値）

   ```bash
   curl --compressed "https://www.stat-search.boj.or.jp/api/v1/getDataCode?format=csv&lang=jp&db=fm08&code=FXERD04,FXERD05&startDate=202608&endDate=202608"
   ```

   応答は CP932。先頭に `STATUS,200` / `MESSAGE,正常に終了しました。` / `DATE,<応答時刻>` が入り、データ行は `系列コード,系列名称,単位,期種,統計名,最終更新日,日付,値` の並びになる。**`FXERD04` の系列名称が「東京市場　ドル・円　スポット　17時時点」であること**と、**実行時点から 2 営業日以内の日付が `null` であること**を見る。

2. **収録スケジュール**（§4 の「翌々営業日 8:50 頃」）

   ```bash
   curl -sL "https://www.boj.or.jp/statistics/outline/tkohyos.xlsx" -o tkohyos.xlsx
   ```

   シート 2 の「２．各種マーケット関連統計」に 2 行ある。**外国為替市況＝「17:50頃・毎営業日」**、**外国為替相場状況（インターバンク相場・東京市場、円インデックス：日次）＝「時系列」「翌々営業日 8:50頃・毎営業日」**。前者が本体公表、後者が検索サイトへの収録である。xlsx は zip + XML であり、`xl/sharedStrings.xml` と `xl/worksheets/sheet2.xml` を標準ライブラリだけで読める（追加パッケージ不要）。

3. **仲値の定義**（§2）

   - <https://www.boj.or.jp/statistics/market/forex/fxdaily/index.htm> — 「9:00時点および17:00時点のスポット・レートは、時系列統計データ検索サイトでは、オファーとビッドの中間値を掲載しております」
   - <https://www.boj.or.jp/statistics/outline/exp/exrateyen.htm> — 中心相場の定義（「最も取引の多かった出来値」）

> **`null` の解釈に注意**: API は該当日にデータが無い場合も、まだ収録されていない場合も同じく `null` を返す。**欠測・休場・未収録を区別しない。** 実装で「最新のレート」を求めるときは、`null` を遡ってスキップしたうえで、得られた日付の古さを別途評価する必要がある。
>
> **「統計別検索の方が新しい」は成り立たない。** 検索サイトは「お急ぎの方は、統計別検索をご利用ください」と案内しているが、公式 API（＝統計別検索と同じデータ）を実際に叩いた結果は主要時系列統計データ表と**完全に同一**だった。経路を変えても鮮度は改善しない。

**この収録スケジュールから、曜日ごとの「最新データの古さ」は次のように決まる**（平常時・8:50 以降）。

| 取得曜日 | 最新データ | 古さ |
| --- | --- | --- |
| 水・木・金 | 2 営業日前 | 2 日 |
| **月** | **前週木** | **4 日** |
| **火** | **前週金** | **4 日** |

つまり **平常時であっても週 2 日（月・火）は必ず 3 日を超える。** 祝日を挟むとさらに延び、3 連休明けの火曜は 5 日になる。8:50 の収録前に取得した場合はさらに 1 営業日分古い。

**決定 4 の「日銀と FRED の二段構成であれば、平常時に 3 日を超えることはまずない。3 日を超えたら『両方の源が取れていない』という異常であり、警告として意味のある値になる」という前提は成立しない。** 正常な運用でも週 2 日発火するため、警告としての意味を失い、**本当の異常が埋もれる**。これは決定 4 が 7 日・14 日を却下した理由（異常の検知が遅れる）と同種の失敗を、逆方向で招く。

なお **FRED フォールバックはこれを救わない**。`DEXJPUS` は公表が週次であり、月曜・火曜に日銀側が 4 日前のデータしか持たない局面で、FRED 側がそれより新しい値を持っている保証がない。決定 3 が期待した「日本の連休中も FRED 側は動いている」という冗長化は、**日本の平日にも収録遅れが出る**という本件には効かない。

### 5. 著作権・利用条件 — 商用利用しないため事前相談は不要（2026-08-05 利用者裁定）

「サイトのご利用上の留意点等」の原文は、転載・複製について「**出所を明記してください**」とし、「i) 商用目的で転載・複製を行う場合」は事前相談を求めている。**利用者裁定により本システムは商用利用しない**（2026-08-05）ため、事前相談は不要である。

API 側の「API 機能利用時の留意点について」が課す義務は、いずれも「**本機能を使用したサービスを公開した場合**」という条件付きである。

- 利用時の連絡: 公開した場合に日本銀行調査統計局へ連絡する
- クレジット表示: 公開する場合、指定文言を表示する — 「このサービスは、日本銀行時系列統計データ検索サイトの API 機能を使用しています。サービスの内容は日本銀行によって保証されたものではありません。」

本システムは利用者本人が Discord で受け取る私的な運用であり、文言上はいずれの義務も発生しない。ただし **ADR-0022 が定めた「報告書の為替欄に出典を明記する」方針は維持する**（義務ではなく、値の出所を追えるようにするため）。将来 API を使ったサービスを公開する場合は、上記のクレジット文言と連絡が必要になる。

## 実装で判明した経緯

実機確認セッション（2026-08-05）。`blockedtasks.md` A-4「日銀 時系列統計API の系列 ID の確定」の実施として、ブラウザで日銀の一次情報にあたった。

1. 統計別検索で FM08 の系列一覧を取得し、「17 時時点」と「中心相場」が別系列であることに気づいた。
2. 定義を解説ページで確認し、中心相場が仲値ではないことを確認した。
3. 系列の実データを見た際に `収録終了期` が当日より 2 日前で止まっていたため、別統計（コールレート）と突き合わせ、さらに公式 API を実際に叩いて同じ結果を得た。
4. 一時的な遅延か設計かを確定するため、日銀の公表・掲載予定表（xlsx）を取得し、「翌々営業日 8:50 頃」の記載を確認した。

コードの変更は行っていない。

## 提案（計画への反映案）

- 反映先候補: **新 ADR**（ADR-0022 は Proposed だが、決定 4 の前提が事実で崩れるため部分改定が要る）
- 提案内容:
  1. **系列 ID を `FM08'FXERD04`（東京市場 ドル・円 スポット 17 時時点）と確定する。** 決定 1 の注記にある「中心相場」は別系列（`FM08'FXERD05`・仲値ではない）であり、訂正する。
  2. **「HTTP 403 で一次確認できない」という記述を訂正する。** 公式 API があり、登録不要で取得できる。
  3. **決定 1 の表の「公表頻度: 毎営業日」に、実装が読む経路の収録は翌々営業日 8:50 頃であることを併記する。** 本体公表の頻度と、機械可読経路の鮮度は別物である。
  4. **決定 4（警告しきい値 3 日）を改める。** 平常時に週 2 日発火するため、警告として機能しない。取り得る案は次の 3 つで、いずれも決定 5 の絶対上限 30 日には影響しない。

     | 案 | 内容 | 代償 |
     | --- | --- | --- |
     | A | しきい値を **5 日**へ緩める | 異常検知が 2 日遅れる。決定 4 が 7 日・14 日を却下した理由が部分的に当てはまる |
     | B | しきい値を**営業日ベース**（例: 3 営業日）で定義する | 決定 3 が「保守対象になり誤りが統制の誤判定に直結する」として明確に却下した営業日カレンダーを持ち込むことになる |
     | C | **本体の日次公表（毎営業日 17:50・PDF）を一次取得元にする** | 鮮度は当日になるが、PDF の解析が要る。表形式の安定性・訂正の反映は未調査 |

     **A が最も小さい変更である。** C は鮮度の問題を根本から解くが、PDF 解析という新たな脆さを持ち込むため、採否は計画側の判断が要る。
  5. 商用利用しない旨（2026-08-05 裁定）を記録し、クレジットは報告書の出典表記として維持する。
