# フィードバック: moomoo OpenD の無人運用は条件付き成立（安定 egress IP で無人再起動可）

## 種別

新たな制約(ADR要)。ADR-0002 の未決事項「**OpenD 無人運用の成立性**」に、実バイナリ PoC で得た回答を環流する。

## 現状（計画書の記述 / As-Is）

ADR-0002 は Accepted の条件に「デモ取引（SIMULATE）での PoC」を挙げ、未決事項として
「**OpenD 無人運用の成立性**（長期常駐の安定性・取引パスワードのアンロック自動化・強制アップデート頻度）」
「海外 IP（Hetzner）からの接続・利用規約」を掲げている。03_moomoo-integration も
「無人運用での安全なアンロック手順は PoC で検証する」と記す。

## 問題点 / あるべき姿（To-Be）

**PoC の結果、OpenD は「完全無人（自動再起動）」では運用できないことが判明した。** 計画側の
「無人運用の成立性」の前提を、**「限定的成立（起動時のみ有人・以降常駐）」**へ明確化すべき。

## 実装で判明した経緯

実バイナリ `moomoo_OpenD_10.8.6818`（コマンドライン版）を Docker/k8s 化（#124・IADR-0053）し、実口座で検証:

1. ✅ コンテナで OpenD は起動・moomoo にログイン・API 稼働（権限取得）まで到達。
2. 🔴 **ログイン時に対話デバイス検証（画像 CAPTCHA / SMS）が毎回必要**。デバイス状態を
   home（`/root/.com.moomoo.OpenD`）＋install（`AppData.dat` 等）の**両方を永続化しても、
   新コンテナ（＝新 IP）は再び検証を要求**した。検証は **IP/セッション依存**で永続化では回避不可。
3. 追加制約: 初回に **API 利用規制アンケート**（`api.moomoo.com/v2`）の完了が口座単位で必須。

→ k8s で Pod を再起動するたびに人手の検証が要るため、**自動再起動・自動スケールを前提にした無人運用は不可**
（…と初回 PoC では結論した。**この結論は後日の追検証で修正された。次節を参照**）。

## 追検証（2026-07-15 後日・#13 結合時）— 前提の修正

初回 PoC の「永続化しても再起動のたびに再検証が必要（完全無人不可）」は、**追検証で反証された**。

**観測（再現可能）**: resident Deployment を **3 リビジョン**ロールアウト（`Recreate`＝毎回新 Pod・Pod IP は毎回変化）。
**3 回とも対話検証を一切せず `Login successful`・API 稼働**に到達し、#13 の実 SIMULATE 発注→照会→取消が成功した
（PR #130・本セッションで `kubectl attach` は未実行）。

**成立条件**:
1. **デバイス信頼が一度確立・永続化済み**（先行の対話検証＋規制アンケート完了が PVC `/root/.com.moomoo.OpenD` に永続）。
2. **egress IP が安定**（単一ノード）。moomoo の検証対象は **NAT 後の egress IP** であり、これはノード不変なら変わらない。
   Pod IP（内部）は無関係。→ 初回 PoC の「新 Pod＝新 IP だから再検証」は **Pod IP と egress IP を混同**していた
   （または初回 PoC 時点でデバイス信頼が未確立だった）可能性が高い。

**修正後の結論**: 「完全無人不可」は過度に絶対的だった。**初回のみ有人でデバイス信頼を確立・永続化すれば、
以降の再起動/Pod 再作成は無人再ログインが成立する（安定 egress IP 環境）**。ローカル単一ノードでは実質無人運用が成立。
残る有人条件は **egress IP 変動（マルチノード再スケジュール・クラウド/別リージョン・NAT 変更）と moomoo 側の
セッション失効・再チャレンジ**。egress IP 変更時の切り分けは未検証（要追検証）。

## 提案（計画への反映案）

- 反映先候補: **ADR-0002 の更新**（未決事項→確定事項へ）／必要なら 03_moomoo-integration の追記
- 提案内容（**追検証を反映した最新版**）:
  - ADR-0002 の「無人運用の成立性」を **「条件付き成立：初回のみ有人でデバイス信頼を確立・永続化（PVC）すれば、
    egress IP が安定な環境（例: 単一ノード・固定 NAT）では再起動/Pod 再作成をまたいで無人再ログインが成立する。
    egress IP が変動する構成（マルチノード再スケジュール・クラウド/別リージョン）では再起動時に有人デバイス検証を要する」**
    と明文化。運用は「デバイス信頼の永続化＋安定 egress IP の確保＋再起動最小化」を推奨。
  - 前提条件に「**初回に API 規制アンケートの完了が口座単位で必須**」「**初回デバイス信頼確立は有人**」を追加。
  - 通信は **cross-network（別 Pod 間）trade は RSA 暗号化必須**（#13 で確定・#124 で配備）。
  - Hetzner（海外 IP）接続可否・ToS、取引パスワードアンロックの自動化可否、egress IP 変更時の再検証は引き続き未検証。
  - 可用性設計への含意: 安定 egress IP を保てば OpenD の自動復旧余地がある（従来「再起動＝必ず有人」より緩和）。
    冗長化は `IBrokerAdapter` 差し替え（立花証券 e支店 等）を将来の代替として ADR-0002 の既述どおり保持。

## 影響範囲

- FR-05（発注執行・#13）: moomoo アダプタは**稼働中の常駐 OpenD（`opend:11111`）へ SIMULATE 接続**する前提で実装する。
- 運用（NFR 可用性）: OpenD 再起動時の一時的な発注不可を許容/監視する設計が要る。
- インフラ（#24・Hetzner）: 自動デプロイ/自動復旧の対象から OpenD 認証を除外（有人手順として分離）。
