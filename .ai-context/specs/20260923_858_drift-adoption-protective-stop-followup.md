# 仕様書: 取り込みに保護記録とブローカー側保護注文を追随させる（#858）

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: FR-10（保護逆指値）、FR-05（建玉の突合）、FR-11（監査）
- ユースケース（UC）: UC-02、UC-06
- 画面（SC）: なし
- 関連 ADR: ADR-0003（利用者の承認なしに台帳を書き換えない）、ADR-0040 決定 1
- 関連 IADR: IADR-0350 決定 5（本件の分離元・設計の入口）、IADR-0210（保護レグ）、
  IADR-0344 追記(4)〜(7)（持ち分の割り当て規則）、IADR-0357 / IADR-0117 改定 1・4（取消は**確認できたときだけ**確定）、
  IADR-0118（観測を権威にしない）、IADR-0129（購読の作法）。本作業の決定は IADR-0370
- 計画書リンク: 上記 plan_refs

## 目的・背景

#849（IADR-0350）は**リスク管理側の取引台帳だけ**を観測値へ合わせる。取り込みで台帳の建玉が減る（または消える）とき、
**発注執行側の保護記録（`protective_stop_orders`）は何も知らされないまま残る**。

- 記録が `Active` のまま残ると、ガードは実在しない建玉の保護レグを巡回し続ける。
- 🔴 より重いのはブローカー側である。利用者がシステム外で全株を売却した後も**売りの逆指値が残っていれば、
  発火したとき意図しないショートが建つ**（#853 の「孤立した逆指値」と同じ帰結・原因は別）。

### 既存のガードとの重なり（正直に書く）

**S0（ブローカー側逆指値）については、ガードが動いていれば既に収束する** ——
ガードは毎巡回ブローカーの建玉を照会し、建玉残が 0 になった行の逆指値を取り消して記録を終端化する
（外部要因の未確定分があれば 2 巡回待つ）。したがって本作業が新たに閉じるのは次の 4 点である。

1. **即時性**（30〜60 秒待たず、取り込みの瞬間に取り消す）。
2. **取消の確認**（ガードは `CancelOrderAsync` を投げっぱなしで、取り消せたかを確認せず記録を閉じる。
   本作業は IADR-0357 の確認つき取消を使い、確認できたときだけ終端化する）。
3. **在庫の押さえの解放**（確認できた取消は `OrderCancelled` を発行する。ガードの経路は 1 通も出さないため、
   保護レグの承認行が台帳に押さえられたまま残る）。
4. **取消できないときに Critical を出す**（ガードは無音）。

**ガードが動いていない構成（建玉照会を持たない発注先）では本作業が唯一の追随経路になる。**

## 対象範囲

- 対象: 発注執行が `PositionDriftAdopted` を購読し、当該銘柄・方向の保護記録を追随させる（取消・終端化・通知）
- 対象外:
  - 取り込みそのもの（リスク管理側・#849 で完了済み）
  - 保護レグの**数量の縮小・張り直し**（後述「設計」決定 4 で採らない理由を述べる）
  - 保護レグの状態が不明なときの一般的な扱い（#853）
  - 確認できた拒否の扱い（#857）—— 本作業と**同じファイル群を触らない**ため PR を分ける

### 是正の母集合（自分で引いた結果と除外理由）

「取り込みで建玉が減ったときに追随が要る記録」を、**保護記録を書いている全経路**から引いた
（`grep -rn "stops.Save\|protectiveStops?.Save" backend --include=*.cs`。テストを除く）。

| 記録を書く経路 | 追随の要否 |
| --- | --- |
| `OrderExecutionAppService`（エントリー同時の S0 / S1 の作成） | 作成のみ。取り込み時点では既存行として本作業の対象に入る |
| `ProtectiveStopGuard`（再発注・完了） | 巡回で収束する。本作業と**同じ規則**（下の割り当て）を使うため二重に減らない |
| `SoftwareStopExecutor`（S1 の決済・完了） | 同上 |
| `ProtectiveStopNetting`（外部要因の観測・確定） | 🔴 **本作業と同じ問題を解く既存の規則**。割り当ての規則はここから**再利用**する（2 つ持たない） |

`PositionDriftAdopted` の既存購読者は監査・通知のみ（`grep -rln PositionDriftAdopted backend`）。
発注執行に購読は無い（本作業で追加する 1 つ目）。

## 設計

### 決定 1: 発注執行が `PositionDriftAdopted` を購読する（サービス間の直接参照はしない）

`PositionDriftAdoptedHandler`（`Infrastructure/Steps`）が受け、業務は `ProtectiveStopDriftAdopter`
（`Features/OrderExecution/AdoptPositionDrift`）が行う。**発行はハンドラ**（既存の作法。Features 層は
メッセージ基盤を参照しない）。キューは規約発見で自動生成される（IADR-0129。明示のルーティング宣言は無い）。

### 決定 2: 目標は**絶対値**で、割り当ては既存の規則を再利用する

- 群 = その銘柄・市場・**方向**（取り込み前の数量の符号）の `Active` な保護記録。
- 目標 = `|LedgerQuantityAfter|`（＝観測されたブローカーの数量）。**差分ではなく絶対値**で扱う
  （IADR-0350 決定 2 と同じ理由。**再送で二重に減らない**＝受け入れ基準の否定形がこれで機械的に成り立つ）。
- 減らす量 = `群の主張の合計 − 目標`。**割り当ては `ProtectiveStopNetting` の既存規則**
  （帳簿だけの行〔S1〕を先に使い切り、実注文を持つ行〔S0〕は最後・**全部か 0 か**。
  それぞれ作成時刻 → `EntryDecisionId` の順）を `AllocateReduction` として公開して呼ぶ。
  🔴 **同じ問いに 2 つの答えを持たない**（issue が問うている「どの保護レグから減らすか」への回答がこれである）。

### 決定 3: 取り消す前に**新しい建玉照会**で裏を取る。取れなければ取り込みの観測に従う

取り込みが許す観測の古さは最大 60 分である（IADR-0350 決定 1）。その間に利用者がシステム外で買い戻していれば、
**実在する建玉の保護を消してしまう**。よって建玉照会（`IBrokerPositionSource`。持たない構成では null）が使えるなら
**その巡回の純額と取り込みの目標の大きい方**を目標に採る ——「保護を消しすぎない側」へ倒す。
照会が `null`（不明）なら**取り込みの観測に従う**（何もしないと、本 issue が閉じようとしている
**孤立した逆指値**が残る。取り込みは利用者が承認した操作であり、処理中の決済が無いことも確認済みである）。
いずれの場合も**建玉を売る操作は 1 つも行わない**（取消と帳簿だけ）。

### 決定 4: 数量の縮小・張り直しはしない（部分的な取り込み）

issue の問い「縮小するのか、張り直すのか」への回答:

- **縮小は構造的にできない。** 実 OpenD への `TrdModifyOrder` は配線されておらず、`IOrderAmendmentBroker`
  （訂正の口）は moomoo 構成では登録されない（IADR-0067 / #847）。
- **張り直し（取消 → 小さい数量で再発注）は採らない。** 生きている保護を**確実に消して**、再発注が通る保証のない
  窓を作る取引である（拒否されれば無保護。#857 で実測された拒否の経路がそのまま当たる）。
  IADR-0344 が繰り返し引いた赤線（**生きた S0 の逆指値を取り消さない**）と同じ判断である。
- したがって S0 は既存規則どおり**全部か 0 か**でしか動かさない。部分的な取り込みでは
  **帳簿だけの行（S1）が先に吸収**し、S0 の実注文はそのまま残る（建玉より大きい逆指値が残り得る点は
  IADR-0344 追記(4) が既に受容している性質であり、本作業で新たに生じるものではない）。

### 決定 5: 取消は**確認できたときだけ**終端化する。できなければ Critical を出して `Active` のまま残す

`OrderAmendmentService.CancelAsync`（IADR-0357）を使う。確認できた（`AbandonsUnfilledRemainder`）ときだけ
`OrderCancelled` が返るので、それを発行して記録を終端化する。確認できない・例外のときは:

- 記録を**終端化しない**（`Active` のまま＝ガードが巡回を続ける・無音にしない）
- `SoftwareStopExecuted(Outcome=StopCancelUnconfirmed)`（Critical）を発行する
- **ハンドラは例外を投げない**（他の銘柄・他のレグの進捗を捨てて再配送させない。
  `PositionCloseCancellationHandler` は投げる作法だが、あちらは失敗を記録する経路が他に無い。
  こちらは「記録が `Active` のまま」「Critical」「ガードの巡回」の 3 つが残る）

### 決定 6: 減らした行の未確定の観測は捨てる

取り込みで確定した減少は、ガードが観測していた**同じ外部要因**である。減らした行の
`PendingExternalReduction` / `ExternalReductionObservations` / `ExternalReductionAbsences` を 0 に戻す
（残すと同じ減少を二度数え、次の巡回でさらに削る）。

## 受け入れ基準

- [ ] 取り込みで建玉が消えた銘柄について、発注執行が保護レグを取り消し、記録を終端化する。監査に残る
- [ ] 🔴 「二重決済でショート化しない」を壊さない（T-10-402 / T-10-403 / T-10-406〜408 が緑のまま）
- [ ] 取消できなかった場合は Critical で通知し、黙って `Active` のまま残さない
- [ ] 否定形: 取り込みと無関係な銘柄・方向の保護レグに触らない
- [ ] 否定形: イベントの再送で二重に取り消さない
- [ ] 否定形: 新しい建玉照会が建玉の存在を示すなら、生きている保護を消さない

## 計画書との差異

- 差異: なし。FR-10 の「建玉なき逆指値を残さない」（業務フロー 02 補足の二重決済問題）を、
  計画外の経路（利用者のシステム外売買 → 取り込み）にも届かせる追随である。

## 未決事項

- **部分的な取り込みで S0 の逆指値が建玉を上回る状態**は残る（決定 4）。訂正の口（`TrdModifyOrder`）が
  配線されれば縮小が選べるようになる。現状は IADR-0344 追記(4) の受容範囲と同じ。
- 建玉照会を持たない構成では、取り込みの観測（最大 60 分前）だけを根拠に取り消す（決定 3）。
