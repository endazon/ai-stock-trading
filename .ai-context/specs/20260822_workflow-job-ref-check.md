# 作業仕様書 — 逆転監視の母集合を正し、docs のジョブ名参照を機械で突き合わせる

## 起点となる計画書（トレーサビリティ）

計画 ID（FR/UC/SC）を持たない**工程の改善**である。計画側の非機能要件表は稼働する製品の要件を
持ち、CI の所要時間・文書統制に当たる番号が無いため**無採番の `NFR`** とする。

## 背景 1 —— 🔴 決定 11（skip）が決定 9（定常性の門）を無力化していた

逆転監視は「`build-and-test` の中央値 > `claude-review` の最小値」で判定し、
**中央値が最小の 2 倍以上なら判定を skip** する（決定 9 の定常性の門。CI を作り変えた直後に
狼少年にならないため）。

決定 11 で **backend 非変更 PR は `build-and-test` が 24 秒で終わる**ようになった結果、
母集合が**恒久的に二峰性**になった。

| PR の種類 | `build-and-test` の完了オフセット | 実測 |
| --- | --- | --- |
| docs PR（実測 34%） | 約 **24 秒** | #545 = 24 秒 |
| backend PR | 約 **130 秒** | #544 = 130 秒 |

`中央値 ÷ 最小` は窓が入れ替わっても **5 倍前後**にとどまり、**門が永久に発火する**。
実測でも既に skip している（`最小 24 秒 / 中央値 205 秒 = 8.5 倍`）。

🔴 **「緑だが判定していない」状態で固定される。** 本作業が一貫して潰してきた
「監視が黙って壊れる」形そのものであり、**この状態で issue #543 を閉じると、
逆転が再発しても誰も気付かない。**

## 背景 2 —— 同型の文書乖離が 2 回起きた

| # | いつ | 何が |
| --- | --- | --- |
| 1 | 第 1 弾 | 基盤リポの `scripts/README.md` が、統合で消えたジョブ名を挙げたまま |
| 2 | 今回 | `docs/ai-workflow.md` が `doc-links` / `pipeline-config` / `ai-workflow-config`（`static-checks` へ統合済みで**存在しない**）を挙げたまま |

規約「**同型の事故が 2 回起きたら検査器を足してよい**」の条件を満たす。
🔴 **この乖離は「実在しないチェックを必須にして develop が恒久的にマージ不能」という形で効く。**
同じ文書がその失敗形を警告しているのに、文書自身が破っていた。

## 変更内容

### 1. 監視の母集合から「backend を skip した PR」を除く

**監視が答えたい問いは「CI が仕事をしたとき、レビューより長くかかるか」**である。
docs PR は構造上速いので、**そもそも母集合に入れてはならない。**

- `collect()` で各 PR の変更ファイル（`GET /repos/{repo}/pulls/{n}/files`）を引き、
  **`detect-changed-areas.js` の `decide()` をそのまま使って** `backend=false` の PR を外す。
  🔴 **判定ロジックを 2 つ持たない**（CI 側と監視側で食い違うと、どちらが正かが分からなくなる）。
- 🔴 **`detect-changed-areas.js` が無いリポジトリでも壊れないこと。** 基盤リポには決定 11 が無く
  同ファイルも無い。`require` を try/catch で包み、**読めなければ従来どおり全 PR を母集合にする**
  （機能が減るだけで壊れない）。**同じファイルを両リポジトリへ複写しているため必須の条件である。**
- **除外した本数を必ず出力する**（黙って母集合を狭めない）。
- 権限の追加は不要（`pull-requests: read` が既にある）。

### 2. 新規 `scripts/check-workflow-job-refs.js`

**外部依存ゼロ**（`package.json` も `node_modules` も無い）。YAML パーサは使わず、
既存の `check-action-versions.js` と同じく正規表現で読む
（ジョブ ID は 2 スペース字下げ、`name:` は 4 スペース字下げで直後にある）。

検査するのは **`docs/ai-workflow.md` の 2 つの表の、機械的に真偽が決まる主張だけ**である。

| 表 | 行の形 | 検査 |
| --- | --- | --- |
| 必須チェック表 | `` \| `check名` \| `X.yml` の `jobid` \| … \| `` | `X.yml` が実在し、`jobid` がそのファイルのジョブであること |
| report 名の表 | `` \| `名前`（`X.yml`） \| `a` / `b` / … \| `` | 各 `a` / `b` が `X.yml` の report する名前（ジョブ `name:` があればその値、無ければジョブ ID）であること |

- **正規化**: 打ち消し線 `~~`、matrix の記法 `(1..7)`、`等` を落としてから突き合わせる。
- 🔴 **表が見つからなければ例外で落とす**（`readPlanIds()` と同じ fail-loud。
  **黙って 0 件検査で緑を返さない**）。
- `--self-test` を持つ。配線先は **`static-checks`**（`paths:` を持たず常に走る）。

🔴 **検査しないもの（意図的）**: 表の 3 列目の散文、必須にすべきか否かの判断。
**曖昧なものを検査器に入れると偽陽性を出し、検査器ごと外される。**

## 受け入れ基準

1. 監視が**判定を再開する**（skip のままでない）。除外本数が出力される。
2. `detect-changed-areas.js` を読めない状況でも監視が動く（自己試験で固定）。
3. 検査器が**現状の `docs/ai-workflow.md` で緑**になる。
4. 🔴 検査器が**実在しない名前を実際に検出して落ちる**（差し込んで実測する）。
5. 表が見つからない場合に**例外で落ちる**（0 件検査で緑を返さない）。
6. 必須チェック名が 1 つも変わっていない。
7. シャーディングの実測（130 秒前後）が維持されている。

## 検証（実測でしか確かめない）

- 🔴 **検査器は「落ちること」を先に実測する。** 検出できると確かめないまま
  「検査器を入れた」と言わない。実在しない名前を差し込んで赤くなることを見てから戻す。
- 🔴 **監視は両方向を見る** —— 除外後に判定が走ること、および
  `detect-changed-areas.js` が無い状況で従来どおり動くこと。
- 本 PR は `.github/workflows/**` を変更するので **backend は skip されない**。
  シャーディングの実測もこの PR の CI でそのまま取れる。
- **issue #543 のクローズは 1・2 が緑になってから**行う。順序が逆だと
  「鳴らなくなったから閉じた」と「判定していないから鳴らない」が区別できない。

## 母集合の取り方（規則 6: 引いた結果と除外の理由を残す）

- **文書側の母集合**は `docs/ai-workflow.md` の 2 つの表に限る。
  同ファイルの散文中にもジョブ名は現れるが、**真偽が機械的に決まらない**ため対象外とする。
  他の `docs/**` は今回対象にしない（乖離が実際に起きたのは同ファイルであり、
  検査器の適用範囲を実績のある所から広げる）。
- **ワークフロー側の母集合**は `.github/workflows/*.yml` の全ファイル。

## 未決事項

- **キットへ配布するか。** 本検査器は `docs/ai-workflow.md` の**表の書式に密結合**している。
  配布するなら書式ごと配る必要があり、別途の判断が要る（キットは bootstrap 専用で
  追随義務も無い）。今回は配布しない。
- **基盤リポ（MSP）へ横展開するか。** 同リポの乖離は `scripts/README.md` で書式が異なる。
  必要になったら別途。

## 実施結果（2026-08-22）

### 変更 1: 監視の母集合

`decide()` を `try`/`catch` 付きの `require` で読み込み、`/pulls/{n}/files` の結果へ適用して
`backend=false` の PR を除外した。自己試験 39 → **44 件**。実データで判定が再開したことを確認:

```
マージ済み PR 10 本を走査: build-and-test 5 件 / claude-review 4 件（うち 5 本は backend を skip した PR なので母集合から外した）
build-and-test の中央値 223 秒  vs  claude-review の最小 146 秒（余裕 -77 秒）
```

**除外前は定常性の門で skip していた**（最小 24 秒 / 中央値 205 秒 ＝ 8.5 倍）。
除外により門が発火しなくなり、**判定が再開した**。

🔴 **判定は再開したが、まだ「逆転」と言っている。** 母集合に残った backend PR 5 本のうち
**4 本が最適化前**だからである（窓は直近 10 本のマージ済み PR で、最適化後の backend PR は
まだ 1 本しか入っていない）。**これは監視の欠陥ではなく、窓が入れ替わっていないだけである。**

### 変更 2: 検査器

`scripts/check-workflow-job-refs.js`（自己試験 **28 件**）。`static-checks` へ本走と自己試験を配線した。

**検出できることを実測した**（実データの表へ 1 件ずつ注入 → 3 件とも赤 → 戻した）:

| 注入した誤り | 検出 |
| --- | --- |
| 表A へ統合で消えたジョブ名（`doc-links`） | `ci.yml` にジョブ `doc-links` が無い（実在ジョブを列挙） |
| 表A へジョブ ID を check 名として記載（2026-08-21 の訂正と同型） | 表は `secret-scan` だが report するのは `Secret scan (gitleaks)` |
| 表B へ存在しない report 名（`pipeline-config`） | `pr-title.yml` が `pipeline-config` を report しない |

表の見出しを消した状態でも**例外で落ちる**ことを実データで確認した（exit 1・0 件検査で緑にならない）。

### 検査器が初回本走で見つけた乖離（3 件目の同型事故）

1. `docs/ai-workflow.md` の report 名の表が `frontend.yml` / `frontend-tests.yml` を挙げていたが、
   **本リポジトリに両ファイルは無い**（基盤リポジトリ由来のキット雛形の残り。本リポのフロントは
   `ci.yml` の `frontend` / `frontend-e2e` で、同じ表の別行に正しく載っていた）。→ 2 行を削除。
2. 走査の過程で `scripts/README.md` の検査一覧の列見出しが「ジョブ」のままであることに気付いた。
   決定 6 の統合後、**独立ジョブは 4 つ（＋ `pr-title`）だけで残りは `static-checks` の step** である。
   **1 件目の事故（基盤リポの `scripts/README.md`）と同型がこのリポジトリでも生きていた。**
   → 見出しを是正し、step 名をブランチ保護へ指定すると恒久 pending になる旨と正本の所在を明記。

**母集合の引き直し**（規則 2・規則 9）: `frontend.yml` / `frontend-tests.yml` /
`Frontend CI` / `Frontend Tests` / `build-test` の 5 語で追跡下の全ファイルを走査し、
該当は `docs/ai-workflow.md` の当該 2 行のみ（`.ai-context/specs/` は point-in-time の記録として
対象外だが、実際に該当は 0 件だった）。

### 全体の検証

`scripts.test.js` 267 件・全検査器の自己試験・本走とも緑。**必須チェック名は 1 つも変えていない。**

### AI レビューの指摘への対応（2026-08-22）

🟡 1 件（🔴 は 0 件）。**`/pulls/{n}/files` のページネーション漏れ**を是正した。
変更 100 件超の PR で backend の変更が 101 件目以降にあると、母集合から静かに落ちる経路だった。
全ページを読み、**読み切れなかったときは除外しない**（判断材料が欠けた状態で狭めない）。

🔴 **回帰テストを書く過程で、自己試験ハーネスの欠陥が出た。** `ok()` が `fn()` を await しない
同期実装だったため、**非同期の試験は中で throw してもその行が `ok` と表示され、集計も「N 件 OK」と出た**（実測）。
thenable を待つよう改め、**変異試験で両方向を確認した**（1 ページ目で打ち切る変異に対し、旧ハーネスは `ok`・
新ハーネスは `FAIL`）。自己試験 44 → **50 件**。

なお、レビューが「未検証」と挙げた無採番 `NFR` の妥当性は、計画リポジトリが本セッションから参照できないためで
あり、規約上は「計画側の非機能要件表に当たる番号が無いメタ作業」に該当する（規約整備・検査器の追加が典型例として
明記されている）。この場合は環流もしない。
