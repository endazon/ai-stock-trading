### 🔴 ［2026-09-19 追記 / #875］初版の「偽陽性は 0 件」は撤回する（掃引のモードが間違っていた）

**初版の本節は「残りの 57 ペアは緑であり、偽陽性は 0 件だった」と書いた。この記述は撤回する。**

掃引に使ったのは `--range=<base>..<head>` の **2 ドット**である。`parseRange` は 2 ドットで
`base = theirs = 左辺` を返し、`main` は `theirs = revs.strict ? base : …` とするため、
**規則 2 は規則 1 に潰れて一度も発動しない**。CI が使うのは 3 ドットである。

```
parseRange("A..B")  = {"base":"A","theirs":"A","ours":"B","strict":true}   <- 規則 2 は発動しない
parseRange("A...B") = {"base":"MB","theirs":"A","ours":"B","strict":false} <- CI はこちら
```

**偽陽性はすべて規則 2 側にあり、あの掃引では原理的に検出できない。**「赤 2 件」という数字は
そのモードでは正しいが、**「偽陽性 0 件」の根拠にはなっていなかった。** 実際、CI と同じ 3 ドットで
引き直すと**開いている 10 本のうち 4 本が赤**だった（次節 BLK-1）。

### 🔴 ［2026-09-19 追記 / #875］BLK-1: `touched` 判定が develop の新設行を誤認していた

```js
const touched = !baseRow || !oursRow || oursRow.line !== baseRow.line;  // 初版（誤り）
```

**`!baseRow`（マージベースに当該行が無い）は「我々が足した」だけでなく「統合ブランチ側が
後から足した」場合にも真になる。** ブランチは何も触っていないのに規則 2 が発動し、`theirs` の印を
すべて要求していた。`!oursRow` も同様である。

実測（CI と同じ 3 ドット `origin/develop...<branch>`、開いている 10 本）:

```
fix/FR-04-865-skip-open-when-holdings-unknown  RED  IADR-0352 ［2026-09-19 追記 / #866］
fix/FR-10-864-close-vs-broker-positions        RED  同上
fix/FR-05-852-forgone-ledger-release           RED  同上
feat/FR-10-820-s1-software-stop                RED  同上
（他 6 本は green）
```

**何も失われていない。** マージベース `c53876d4` に IADR-0352 の行はそもそも存在しない:

```
c53876d4        IADR-0352 bytes=0    marks=[]
origin/develop  IADR-0352 bytes=3139 marks=["［…#866］","［…#866］","［…#866］"]
対象ブランチ     IADR-0352 bytes=0    marks=[]
```

`static-checks` は必須チェックであり、**索引行が develop に 1 本増えるたびに在庫の PR 全部が
rebase するまで赤で止まる**。本検査器が繰り返し書いている「偽陽性は検査を外させる」を
自分で作っていた。是正:

```js
const touched = oursRow ? !baseRow || oursRow.line !== baseRow.line : !!baseRow;
```

**`ours` を起点に読む** —— ours に在れば「足した／書き換えた」、ours に無ければ base に在るときだけ
「消した」。**穴を素通りさせたのは固定データである**（base・ours 双方に行が在る形しか踏んでいなかった）。
自己試験と `scripts.repo.test.js` に「**base に行が無い**」形を 3 件足した。

除外理由つきの結論:

- **印の形は `［YYYY-MM-DD 追記 …］` で一定だが、`/ #NNN` は必須ではない**（`［2026-09-03 追記］`・
  `［2026-08-28 追記 / IADR-0259］`・`［2026-09-12 追記 / planning#N］` が実在する）。
  よって検出パターンは **`［<日付> 追記` で始まり `］` で閉じるもの全部**とし、issue 番号を必須にしない。
  **issue 番号を必須にすると、実在する 10 件が検査の外に落ちる**（＝落ちたことに気付けない）。
- **同一の印が複数の行に現れる**（`［2026-09-19 追記 / #866］` が 3 行）。よって
  「ファイル全体で印の集合を比べる」では**行を跨いだ相殺**が起きる。**行（IADR 番号）ごとの多重集合**で持つ。
- 索引行の**外**（README 冒頭の運用ルール等）にも追記ブロックが出得るが、本検査の射程外とする
  （事故が起きたのは索引行であり、射程を広げると #875 の「まずは索引行だけ」に反する）。

## 判定規則

3 つの版を読む。`base`（マージベース）・`theirs`（統合ブランチの先端）・`ours`（HEAD）。

1. **規則 1（削除）**: 印 M が `base` の行 R に在り、`ours` の行 R に無ければ **fail**。
   行 R ごと消えている場合も、その行の印すべてを消失として報告する。
2. **規則 2（衝突解決）**: 我々が行 R を**触った**（`base` と `ours` で行文字列が違う、または `ours` で新規）とき、
   印 M が `theirs` の行 R に在り `ours` の行 R に無ければ **fail**。
   —— **2 件の事故はどちらもこの形である**（develop 側が足した印を、自分側の解決で落とした）。
3. **触っていない行**については `theirs` を要求しない。統合ブランチが先に進んだだけの PR を赤にしないため
   （その行は 3-way マージで統合ブランチ側が採られる。**偽陽性を作ると検査が外される**）。

`--range=A..B`（2 ドット）を渡した場合は `base = theirs = A`・`ours = B` とし、**A の印はすべて要求する**
（事故の再現データを固定するための厳格モード）。`--range=A...B`（3 ドット）は `base = merge-base(A,B)`・
`theirs = A`・`ours = B`。CI の既定は 3 ドット（`origin/<base-ref>...HEAD`）。

**誤検知しない条件**（#875 の受け入れ基準）:

- 印の**追加**は集合が増えるだけなので fail しない。
- 行の**並べ替え**は行を IADR 番号で引くため fail しない。
- 行の**文言の書き換え**は、印が残っている限り fail しない。

## 意図的な撤去を通す手段（allowlist か、コミットの印か）

`scripts/` の既存の作法を読んで決めた。

| 既存の手段 | 使われ方 | 本件に馴染むか |
| --- | --- | --- |
| `scripts/commit-allowlist.json` | `check-commit-messages.js`。**過去のコミット**（force push 禁止で件名を直せない）を SHA で恒久除外する | 馴染まない。本件は**これから行う撤去**であり、SHA は撤去の時点では存在しない |
| コミット本文の印 `[skip-adr-index]` | `check-adr-index-sync.js`。**その PR の作者が意図を宣言する** | 馴染む。同じ検査対象（ADR 索引）・同じ性質（作者の意図） |

→ **コミット本文の印**を採る。ただし `[skip-adr-index]` のような**全体スキップにはしない**。
撤去した印を 1 件ずつ名指しさせる:

```
[remove-adr-addendum] IADR-0118 ［2026-09-19 追記 / #849］
[remove-adr-addendum] IADR-0118 *        ← その行の印をすべて撤去する（行ごと消す場合）
```

- **行として単独**で書かれた場合のみ発動する（`check-adr-index-sync.js` が実測した**自己発火**
  ——「逃げ道について説明した文章そのものが逃げ道を発動させる」——を避ける）。
- 発動したら `notice()` で「どの印を意図的に撤去したか」を CI へ出す。**黙って素通りさせない。**
- **記録は commit に残る**（＝ `git log` と PR に残る）。

## 索引の持ち方を変える案の評価（#875 の「ついでに検討」）

**評価した。結論は「本 PR では変えない。別 issue へ分ける」。**

根本原因は「1 行が数千文字であること」であり、1 IADR = 1 行の短い要約に留めて決定の全文を本体だけが持てば、
衝突解決で行の一部が消える事故は構造的に消える。しかし (a) 現時点で 9 本の PR が並走し、**全部が
`.ai-context/adr/README.md` へ索引行を足す**ため、索引を組み替えると 9 本すべてと衝突する。
(b) 索引行は「本文を開かずに決定の骨子を読む」ために使われており、要約へ削ると
`check-adr-index-sync.js` が守っている「本文と索引の同時更新」の意味も変わる（同検査の射程の再設計が要る）。
(c) 検査器は索引の形に依存しない（印の単位で持つため、1 行が短くなっても効き続ける）。
よって**検査器を先に入れ、索引の持ち方は別 issue で扱う**。詳細は IADR-0363 決定 5。

### 🔴 Windows では本 PR の新規テストがそもそも実行されていなかった（#888 へ起票）

`scripts.repo.test.js` の `setup.sh` 系 4 件は、Windows では `spawnSync bash ENOENT` の
**未捕捉例外**になり、**スイート全体をそこで中断させる**（当該テストが `env.PATH` を
`toolboxPathSs` で上書きするため、呼び出し側が Git Bash を PATH へ足しても解消しない）。
その結果、**それ以降に定義された本 PR の新規 18 件は Windows では一度も走っていなかった。**
例外を捕捉するハーネスで走らせ直して `total=211 / pass=207 / fail=4`（新規 18 件は全て ok）を確認した。
CI は `ubuntu-latest` なので緑であり、**この穴はローカルでしか現れない**。**本 PR では直さず #888 で扱う。**
