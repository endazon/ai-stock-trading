# ci-latency の判定を「監視対象自身の過去の床」へ改める（#1314）

## 起点となる計画書（トレーサビリティ）

- 要求: 無採番の `NFR`（CI の運用性。メタ作業）。製品の FR には当たらない。
- 関連 IADR: IADR-0208 決定 9（逆転の監視）・決定 13（母集合から docs PR を除く）・決定 15（epoch）。
- 利用者裁定（2026-10-12・#1314 のコメント）: 判定方式に (b3) を採る。

## 背景

- 2026-10-10 に AI レビューの既定モデルを sonnet-5-5 へ切り替えた（#1297）。claude-review の所要が大きく縮んだ。
  - AST の中央値は 442 秒から 132 秒へ、最小値は 134 秒から 71 秒へ下がった（#1314 の調査コメント）。
  - レビューの下限は約 70 秒で底を打っている（準備 35〜50 秒＋Claude の処理 16〜60 秒）。
- これとは別に、build-and-test そのものが 6 週間で 125 秒から 237 秒へ伸びていた。この伸びはレビューの陰に隠れて見えていなかった。
- 決定 9 は「必須チェックで最も長いのは当面 claude-review」を前提にしている。この前提はもう成り立たない。
  - 9/28・10/1 の裁定（閾値を緩めない・逆転を受容しない）は「レビューの下限は動かない」を前提にしていたので、そのまま当てはめられない。
- 現行の判定は「build-and-test の中央値 > claude-review の最小値」で赤にする。2026-10-12 の実データでは中央値 225 秒 対 最小 97 秒で赤である（本作業で再現した）。

## 決定（利用者裁定 2026-10-12）

- **(b3)**: 現在の窓の build-and-test の中央値を、過去 K 窓の build-and-test の中央値の**最小値**（自分自身の過去の床）と比べる。R 倍を超えたら赤にする。
- claude-review との比較は**参考値**として出力し続ける（判定には使わない）。
- 次の 2 点の設計原則を保つ。
  - 固定値を持たない（自己校正）。
  - 監視対象は中央値、基準は最小値（この非対称は意図的）。

## 変更内容

### `scripts/check-ci-latency.js`

- **窓の定義**: 監視対象（build-and-test）が測れた backend PR を、マージの新しい順に N 本ずつ区切る。
  - 窓 0 が現在の窓、窓 1〜K が過去の窓である。
  - N は既存の `CI_LATENCY_SAMPLES`（既定 10）を流用する。意味は「1 窓の本数」に改める。
  - 窓は時間ではなく本数で区切る。マージの頻度が変わっても、各窓の中央値が同じ本数から作られるようにするためである。
- **判定**: `現在の窓の中央値 > 過去 K 窓の中央値の最小値 × R` なら exit 1。
  - K は `CI_LATENCY_FLOOR_WINDOWS`（既定 12）、R は `CI_LATENCY_FLOOR_RATIO`（既定 1.2）で与える。
  - 値が数として読めない・範囲外（K < 1、R ≦ 1）のときは設定の誤りとして赤にする。黙って既定値へ戻さない。
- **過去の窓が K 個に満たないときは skip** とし、何個あったかと何個要るかを理由に出す。N 本に満たない最後の窓は数えない。
- **epoch（決定 15）は現在の窓にだけ掛ける。** 過去の窓には掛けない。
  - 過去の窓に epoch を掛けると、`ci.yml` が変わるたびに履歴が消える。8/20 以降の 7.4 週間で `ci.yml` を触った PR は 26 本ある（約 2 日に 1 本）。K 窓の履歴は二度と溜まらず、監視は skip し続ける。
  - 構成変更で速くなった場合、現在の窓は床より下がるので緑になる。床は K 窓が入れ替わるうちに新しい水準へ下がる（自己校正）。
  - 構成変更で遅くなった場合は赤になる。これは待ち時間が実際に伸びたことを示すので、正しい検知である。
- **レビュー側の構成変更は epoch に含めない。** epoch の導出元は従来どおり `CI_LATENCY_CONFIG_PATH`（既定 `.github/workflows/ci.yml`）だけである。判定に claude-review を使わなくなったので、レビュー側の構成変更が判定を動かす経路は無い。
- **定常性の門（決定 9。中央値 ≧ 最小 × 2 なら skip）と最小本数の門（決定 15。3 本）は現在の窓に残す。**
- **docs PR の除外（決定 13）は残す。** 二峰性の母集合では、窓の中央値が docs PR の混ざり方で揺れるためである。
- **参考値**: 現在の窓の claude-review の最小値と、build-and-test の中央値がそれを上回っているか（逆転しているか）を出す。判定には使わない。
- **API の引き方**: PR 一覧を複数ページ引く（最大 10 ページ）。必要な本数 `(K+1)×N` が測れた時点で走査を止める。
  - 既定値では 130 本を測る。docs PR を含めて約 150 本、API 呼び出しは約 300 回である。`GITHUB_TOKEN` の上限（1 時間 1,000 回）に収まる。

## 既定値の根拠（8/20 以降の実測）

### 計測

- 2026-08-20〜10-12 に develop へマージされた AST の PR は 429 本である。build-and-test が測れた backend PR は 367 本である。
- 引き方: 本検査器と同じ尺度（check 群の開始からの完了オフセット）と、同じ backend 判定（`detect-changed-areas.js` の `decide()`）を使った。

### 揺らぎ（R の根拠）

- 9/04 以降の窓（N = 10）の中央値を対数で線形回帰した。残差の標準偏差は 4.2%、最大は 11% である。
- 残差を再標本化し、「定常時に現在の窓 ÷ 過去 K 窓の最小 が R を超える確率」（誤報の率）を求めた。

| K | R = 1.15 | R = 1.2 | R = 1.25 |
| --- | --- | --- | --- |
| 8 | 3.7% | 0.8% | 0.0% |
| 10 | 4.1% | 1.0% | 0.0% |
| 12 | 4.4% | 1.1% | 0.0% |
| 16 | 4.7% | 1.4% | 0.0% |

- **R = 1.2 を採る。** 誤報の率は約 1% で、週次の実行なら年に 1 回程度である。1.15 にすると約 4%（月に 1 回近く）へ上がる。
- 1.25 は誤報を 0 にするが、下の検知力の表で今日の実データ（1.24 倍）を見逃す。

### 伸び（K の根拠）

- 同じ回帰の傾きは **窓 1 つあたり +2.1%** である（N = 10、9/04 以降）。
- 自己校正の床は K 窓ぶんの記憶しか持たない。伸びが `(1 + 傾き)^K ≦ R` なら、床が一緒に上がって永久に鳴らない。
  - K = 8: 1.021^8 = 1.18 < 1.2。**観測した伸びを検知できない。**
  - K = 10: 1.021^10 = 1.23。余裕が 3% しかない。
  - K = 12: 1.021^12 = 1.28。余裕が 8% ある。
- 実データで日ごとに判定を再現した（現在の窓には epoch を掛けた）。R = 1.2 での結果は次のとおりである。

| 時点 | K = 8 | K = 10 | K = 12 | K = 16 |
| --- | --- | --- | --- | --- |
| 09-21 | 1.12 緑 | 1.15 緑 | **1.26 赤** | skip（過去 15 窓） |
| 09-28 | **1.24 赤** | **1.28 赤** | **1.34 赤** | **1.49 赤** |
| 10-05 | **1.25 赤** | **1.30 赤** | **1.40 赤** | **1.45 赤** |
| 10-12 | 1.05 緑 | 1.14 緑 | **1.24 赤** | **1.32 赤** |

- K = 8・10 は 10/10 以降に緑へ戻る。build-and-test は 223 秒のままで、6 週間前の 125 秒から縮んでいない。床が伸びに追いついただけである。
- **K = 12 を採る。** 観測した伸びを余裕をもって検知でき、9/21 の時点（125 秒 → 153 秒）で鳴っていた。
  - K = 16 は検知が早いが、要る履歴が 170 本（約 3.4 週間）になり、API 呼び出しも増える。
- K = 12・N = 10 で要る履歴は 130 本で、現在のマージ頻度（backend PR が週に約 50 本）で約 2.6 週間ぶんである。

## 規則 11（窓を扱う是正）

本件は「現在の窓（後）」と「過去の窓（前）」を突き合わせるので、規則 11 を当てる。

- **増える側のプローブ P1**: 実データ（10/12）。現在の窓 223 秒、過去 12 窓の中央値（新しい順）は 229, 246, 239, 239, 225, 212, 220, 212, 200, 195, 199, 180 秒。6 週間で伸び続けている。**期待は赤。**
- **減る側のプローブ P2**: 過去に速くなり、その新しい水準から伸びた。過去の窓（新しい順）は 170, 165, 160, 150, 140, 135, 130, 220, 225, 230, 235, 240 秒、現在の窓は 175 秒。速くなった後の 130 秒から 1.35 倍に伸びている。**期待は赤。**
- 補助 P3: ちょうど速くなった（シャードの改善直後）。過去は 220〜240 秒、現在は 130 秒。**期待は緑。**
- 補助 P4: 揺らぎだけ。過去は 195〜210 秒、現在は 210 秒。**期待は緑。**

| 床の形 | P1（増える側） | P2（減る側） | P3 | P4 |
| --- | --- | --- | --- | --- |
| 窓の**後**の端だけ（直前の窓） | 0.97 緑 ✗ | 1.03 緑 ✗ | 0.59 緑 | 1.02 緑 |
| 窓の**前**の端だけ（最古の窓） | 1.24 赤 | 0.73 緑 ✗ | 0.59 緑 | 1.03 緑 |
| 両端の突き合わせ `min(前, 後)` | 1.24 赤 | 1.03 緑 ✗ | 0.59 緑 | 1.03 緑 |
| **K 窓すべての最小（採用）** | **1.24 赤** | **1.35 赤** | **0.59 緑** | **1.08 緑** |

- 直前の窓だけを見ると、床が伸びに追いつき、ゆっくりした伸びを永久に見逃す。
- 最古の窓だけを見ると、途中で速くなった後の伸びを、古い遅い値に隠して見逃す。
- 両端の突き合わせは、途中で速くなった水準（窓の中ほどにある）を見ない。
- 期待どおりになるのは、K 窓すべての最小を採る形だけである。P1 と P2 は自己試験で固定する。

- [ ] 現在の窓の中央値が、過去 K 窓の中央値の最小の R 倍を超えたら赤になる（自己試験）。
- [ ] 揺らぎの範囲（R 倍以下）なら緑になる（自己試験）。
- [ ] 過去の窓が K 個に満たなければ skip になり、理由に個数が出る（自己試験）。
- [ ] 床は K 窓すべての最小である（規則 11 の P1・P2 を自己試験で固定する）。
- [ ] 監視対象は中央値で見る（外れ値 1 本で鳴らない）（自己試験）。
- [ ] K・R が不正な値なら赤（設定の誤り）になる（自己試験）。
- [ ] epoch の導出元は `ci.yml` だけである（自己試験）。
- [ ] 既存の罠の回帰テスト（集約ジョブの尺度・permissions・順序・403・404・ページネーション・epoch）が残っている。
- [ ] `GITHUB_REPOSITORY=endazon/ai-stock-trading` の `--report-only` で実データを再現し、結果を PR に書く。
- [ ] CI の node 検査一式が通る。
- [ ] 変異確認: 床を「直前の窓」に変える変異と、比較を中央値から最大値に変える変異で、自己試験が落ちる。確認後は元に戻す。

## 残余リスク

- **床は外れて速い窓 1 つに引きずられる。** 最小を採る以上、過去の窓の 1 つが異常に速いと床が下がり、誤報が出る。窓の中央値の揺らぎは実測で最大 11% であり、R = 1.2 の内側に収まる。異常に速い窓が出たら、その窓が K 窓ぶん流れ去るまで赤が続く。
- **R を超えない速さの伸びは検知できない。** 自己校正の床は K × N 本（既定 120 本）ぶんしか記憶しない。その間に 20% 未満しか伸びない遅い伸びは、床が追いついて検知されない。窓 1 つあたり 1.5% 未満の伸びがこれに当たる。
- **意図して遅くした構成変更（ジョブの追加など）も赤になる。** 床が新しい水準へ追いつくまで（最大 K 窓）赤が続く。待ち時間が実際に伸びたことは事実なので、受容するかどうかは issue で裁定する。
