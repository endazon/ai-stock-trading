## 設計

### 重み（テスト件数）の導き方

- テストプロジェクトの csproj のあるディレクトリ配下の `.cs` を再帰的に読み、
  `[Fact` / `[Theory` の**出現数**を数える（`bin` / `obj` / `node_modules` / `.git` / `.vs` は除く）。
- 素朴な文字列一致であり、コメントアウトされた属性も数える。
  **重みは所要時間の代理変数**であって件数の台帳ではないため、過大評価は分配を僅かに偏らせるだけである。
- **下限は 1**。テストが 0 件でもテストホスト起動の固定費を必ず払う。
- **読めなければ 1（fail-open）**。ここで例外を投げると、走査の失敗が
  「テストが 1 本も走らない」へ化ける。**分配が偏るだけならテストは落ちない。**
- 🔴 **JSON へコミットしない。** コミットした重みはテストが増減するたびに実体とずれ、
  **ずれても誰も気付かない**（分配が静かに偏り、CI が理由もなく遅くなる）。走査は 51 本で 100ms 未満である。

### 分配（LPT 貪欲）

1. 重み降順・同点はパス昇順で全順序を作る。
2. 先頭から、その時点で**最も軽いシャード**へ積む。同点なら**添字の小さいシャード**。
3. 3 つの決定規則がすべて決定的なので、シャード間で分配が食い違わない
   （食い違うと、あるプロジェクトが**どのシャードでも走らない**形で静かに失われる）。

⚠️ **重み未指定（すべて 1）のとき LPT はラウンドロビンに退化する。**
既存の自己試験の期待値はそのまま通り、これ自体が退化の検査になっている。

⚠️ 返す並びは**パス順ではなく積み順（重い順）**である。呼び出し側は行数しか見ない
（`wc -l` と `.slnx` 生成）ため依存しないが、「パス順で出る」と思い込まないこと。

### なぜ 4 か

- makespan の下限は `max(総重み / シャード数, 最大の単一プロジェクトの重み)`。
- **現行 51 プロジェクト構成では最大の単一プロジェクトが全体の 11.4% にすぎず、下限は総重み/N の側で決まる。**
  すなわち N を増やせば理屈上は下がり続ける。
- 一方 `dotnet build backend.slnx` は**脚ごとに丸ごと重複する**（`--no-build` はテスト時のみ）。
  脚を減らした分だけ runner 時間が直接減る。設計書決定 3 の「1 シャード分の余裕を残す」に従い **4** を採る。

## 「Verify report count」の不変条件（変えない）

`want = wc -l < shard.txt` と `got = find cov -name coverage.cobertura.xml | wc -l` の一致は、
「走らなかった」と「二重に走った」を同時に捕まえる。**シャード数を変えても成立し続ける**根拠:

1. `shard.txt` は `--shard i --of 4` の標準出力そのものであり、`--slnx` に書く集合と**同一の配列**から出る
   （`picked` を 1 度だけ計算し、`buildSlnx(picked)` と `console.log(picked.join('\n'))` の両方に使う）。
   分配方式を変えても、この 1 対 1 は構造として保たれる。
2. LPT は各プロジェクトを**ちょうど 1 つのバケットへ push する**ため、`of` に関わらず和 = 全体・重複 0。
   自己試験がこれを固定する。
3. 各シャードが 1 件以上を担当する（51 ≥ 4）。0 件のシャードは `main()` が明示的に失敗させる。
4. `--filter "Category!=Integration"` は**テストの実行数**を減らすがアセンブリ数は減らさないため、
   レポートは担当プロジェクト数と一致し続ける（現行と同じ）。
5. カバレッジ床は集約ジョブが (ファイル, 行番号) の**和集合**で測るため、
   シャードの切り方で分母・分子が動かない。`coverage-floor.json` の `measuredNote`「51 レポート」も
   **プロジェクト数が変わらない本 PR では有効なまま**である（移行本体で 19 になったとき測り直す）。

## 未決事項・残余リスク

- 🔴 **重みは所要時間の代理変数であって実測ではない。完了前検証で代理誤差を測った。**
  4 分割 LPT を 3 尺度で評価すると makespan の理想比は
  **重み 1.001 / 実測テスト件数 1.246 / 実測所要 1.709**（旧ラウンドロビンは 1.301 / 1.350 / **1.704**）。
  **所要尺度ではこの 1 サンプルで差が出なかった。** `[Theory]` が `[InlineData]` の数だけ展開されること
  （属性 3,414 に対し実テスト 5,023）に加え、**所要が件数に比例しない**ことが効いている
  （最長は `AuditService.Infrastructure.Tests` の 15.0 秒 / 29 件）。
  実所要で重み付けするには CI から所要を回収する仕組みが要る。**本 PR では作らない**
  （設計書決定 2 が重みの定義を定めており、射程を広げない）。
  4 を採って 1 シャード分の余裕を残しているのは、この誤差の吸収代である。
  🔴 **本 PR の runner 時間の節約は、分配の質ではなく「脚を 7 → 4 にしてビルド重複を 3 回分減らす」ことから来る。**
- 移行本体でテストプロジェクトが 19 本へ減ると、`RiskManagementService` 単独が makespan の下限を
  支配するようになる（設計書 §3.2）。**そのときは 4 でも 3 でも makespan が変わらない。**
  設計書 §3.4 のとおり**プロジェクトを割らず** trait / `--filter` で分ける拡張点を将来検討する。
