# 仕様書: 月次費用上限の内訳と総額の整合・SC-01 の通貨（#1514・#1410 の子）

## 起点

- #1514（#1410 の網羅表 A-023 の合計の整合・A-024 の通貨の明示）。#1410 の棚卸しで、画面・後段とも実装が無いことが分かった。
- 計画 SC-01: 月次総費用上限と内訳は「必須・数値（円）・型・範囲チェック。**内訳の合計が総費用上限と矛盾しないこと**」。
- 計画 05_trading-assumptions §6: 「月次総費用上限: 20,000 円（LLM＋インフラ＋データの合計）」。内訳は LLM 15,000・インフラ 5,000・データ 0（円/月）。

## A-024 の通貨の確認（2026-10-30。オーケストレーターへ報告済み）

- 計画 §3 は判定の基準通貨（USD）を「リスク統制値・Stage 昇格の判定」に限り、表示通貨を JPY と別に定める。§6 の費用上限は「円/月」。
- IADR-0152（基準通貨を USD へ反転）の射程はリスク統制の判定・換算・SC-02 の表示単位で、費用上限に触れない。
- 実装も円である（`TradingAssumptions.cs`「月次費用上限（円）」・CostControlService の計上「金額[円]」・計器 `ast_llm_cost_jpy_total`）。
- **結論: 計画と実装は食い違っていない（環流は不要）。** 欠けているのは SC-01 が単位を出していないことだけ。

## 決定（IADR-0605）

1. 「矛盾しない」は **合計 ＝ 総額**（LLM＋インフラ＋データ ＝ 総額）とする。§6 が総額を内訳の合計として定義しているため。
2. 各欄は **0 を許し、負は拒否する**（データ費用 0 が既定）。
   **［2026-10-30 追記 / #1516 の AI レビュー］各欄は円単位の整数とし、小数も拒否する（後段も 400）。** 画面の 4 欄は `step=1`。初版の画面だけが浮動小数の誤差を許していた食い違いを解く（IADR-0605 決定 2 の追記）。
3. **後段（ConfigurationService の更新）を正（権威）とし、矛盾・負は 400 で拒否する**（理由を利用者へ見せる印つき）。**画面でも保存を無効にして理由を出す**。画面だけだと API の直叩きで抜けるため、両方入れる。
4. **読み取りは変えない**（既存の値の利用・gRPC の読み取り・消費側の費用統制の判定）。検証は保存のときだけ効く。
5. SC-01 の月次費用上限の 4 欄に単位「円」を明示する（表示だけ）。

## 母集合（規則 9）

- 前提条件を書く経路: `git grep -n "\.Update(\|store.Save" -- backend/Services/ConfigurationService` → `AssumptionsService.Update`（REST の PUT だけ）。gRPC の面は読み取りだけ。**検証はここ 1 か所に置く。**
- 既存の試験が保存する費用上限: ConfigurationService の試験は既定値（20,000＝15,000＋5,000＋0）か変更なし。フロントのフィクスチャは 50,000＝30,000＋15,000＋5,000 で、いずれも ＝ を満たす（`git grep -n "costLimits\|MonthlyCostLimits(" -- backend frontend`）。他サービスの試験は読み取りの側で、本変更の対象外。

## PoC 配備への影響

- ConfigurationService と フロントの再配備が要る。**稼働中の値が ＝ を満たしていないと、配備の後に SC-01 で（費用上限以外の欄も含めて）保存できなくなる**（読み取りと消費側の判定は変わらない）。
- 配備前の確認: 現在値を読み、`total == llm + infrastructure + data` かつ全欄 0 以上であることを確かめる（手順は PR 本文）。満たさなければ、配備の前に SC-01 で ＝ を満たす値へ直す（または配備の後に直してから他の欄を保存する）。
