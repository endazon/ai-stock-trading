# 作業仕様書: SC-02 のリスク上限を割合（%）入力へ作り直す

## 起点となる計画書（トレーサビリティ）

- 画面（SC）: **SC-02**（リスク設定画面）
- 機能要求（FR）: **FR-10**（リスク統制の上限）／ FR-13（利用者が設定を変更できる）
- ユースケース（UC）: **UC-06**（設定変更）
- 計画書リンク:
  - `planning/projects/ai-stock-trading/05_screens/01_screens.md` — SC-02「金額系 3 値の表記（2026-08-02 改定・project-planning#61）」

- 関連 ADR: 計画 ADR-0016（保有建玉数）／実装 [IADR-0130](../adr/IADR-0130_equity-ratio-risk-limits.md)（equity 比化）・

  [IADR-0141](../adr/IADR-0141_live-switch-explicit-confirmation.md)（画面だけの統制は API 直叩きで消える）
- 起点 issue: [#362](https://github.com/endazon/ai-stock-trading/issues/362)（由来 [#329](https://github.com/endazon/ai-stock-trading/issues/329) /
  先行 [#389](https://github.com/endazon/ai-stock-trading/issues/389)）

## 背景と問題

[#329] で金額系の統制上限が **equity 比**へ変わり（[IADR-0130] 決定1）、サーバの `RiskLimitSettings` は
`MaxOrderAmountRatio` / `MaxDailyOrderAmountRatio` を `required` で要求するようになった。
[#389] は**読み取り側（GET・表示）**だけを是正し、**書き込み側（PUT）は旧名（金額キー）のまま据え置いた**。
その結果、SC-02 からのリスク上限の保存は現在 **400 で拒否される**。

これは不具合ではなく、#362 が明示的に選んだ**安全側の状態**である。

> 入力欄が「金額」のまま `maxOrderAmountRatio` を送ると、利用者が従来どおり `35000` と入れたときに
> **equity の 35,000 倍**が上限として設定される。統制が事実上無効化された状態で保存が成功するくらいなら、
> 拒否される方が安全側である（#362 本文 / IADR-0130 決定）。

**本作業の核心は、この 400 を外す瞬間が最も危険であるという点にある。** PUT を `*Ratio` へ切り替えた瞬間に
保存は成功するようになる。したがって**入力の単位を人間に読める形へ作り直すことと、統制を無効化する値を
拒否する関門を置くことは、PUT の切り替えと同時か、それより先でなければならない**。

### 実地確認で判明した、より重い事実

**サーバ側にはリスク上限の値域検証が一切存在しない。**

```csharp
// RiskControlEndpoints.cs（変更前）
owner.MapPut("/settings/limits", (LimitsUpdateRequest req, RiskSettingsService svc, HttpContext http) =>
{
    svc.UpdateLimits(req.Limits, ActorOf(http), req.Reason);   // ← 値域を見ていない
    return Results.Ok(svc.GetCurrent());
});
```

`RiskSettingsService.UpdateLimits` も actor / reason の空検査しか行わない。つまり **`MaxOrderAmountRatio = 35000`
（equity の 35,000 倍）は現在のサーバがそのまま受理する**。今 400 が返っているのは値が危険だからではなく、
**フロントが送るキー名がサーバの `required` プロパティを満たさないから**にすぎない。

キー名を直せば、この偶然の防壁は消える。**したがって画面側のバリデーションだけでは足りない**——
画面だけの統制は API 直叩きで消える（[IADR-0141] 決定1 が発注先の切替で同じ判断をしている）。

## 対象範囲

- **対象**
  1. SC-02 のリスク上限フォームを**割合（%）入力**へ作り直す。表現（`0.25` か `25%` か）を決め、画面仕様書に記録する。
  2. **現在の equity での実額を併記**する。
  3. **値域バリデーション**を置く。**画面（送信前）とサーバ（`PUT /settings/limits`）の両方**に置く。
  4. PUT のペイロードを `*Ratio` キーへ是正する（＝ 400 を外す。**3 と同一コミット以降**）。
  5. 契約型（`frontend/src/features/risk/contracts.ts`）と `RiskSettingsPage` の追随・テスト更新。
  6. 計画が禁じている語「**保有銘柄数上限**」をラベルから排する（ADR-0016 決定9・計画 §5）。
- **対象外**
  - SC-01 / SC-03 の作り直し、空売り表示項目、変動閾値・収集間隔の UI（[#340] の範囲）。
  - 判定通貨の USD 移行（[IADR-0130] 決定3 の未決事項。後述「計画書との差異」）。
  - `GET` 応答の形の変更（契約フィクスチャの再生成は不要。§検証 参照）。

### [#340] との統合／分割の判断: **分割する**

[#340]（SC-01〜03 の全面作り直し）は本作業と画面が重なる。それでも**分割する**。理由は 3 つある。

1. **危険の先送りになる。** 本作業の焦点は「400 が外れる瞬間」に関門を間に合わせることである。#340 は
   SC-01 §2・SC-03 の空売り表示項目・段階/発注先の表示規約まで含む大きな範囲であり、そこへ畳むと
   **値域の関門が無いまま PUT だけ先に直る中間状態**が生まれ得る。本作業はその中間状態を作らないことが目的である。
2. **レビュー単位が壊れる。** 統制の値域という「読めば正誤が判定できる」変更を、画面の全面刷新の差分に
   埋めると人間がレビューできない（CLAUDE.md「人間がレビューできる変更単位を維持する」）。
3. **#340 の前提を先に固められる。** 割合の画面表現（%）と実額併記の形は #340 が SC-03 でも使う。
   先に決めて記録しておけば、#340 は表現を再検討せずに済む。

本作業は #340 のスコープのうち「SC-02 リスク上限の入力 UX」だけを先取りする。#340 の残りは触らない。

## 設計

### 1. 画面表現の決定: **百分率（`25%`）** — [IADR-0151](../adr/IADR-0151_risk-limit-percent-input-and-bounds.md) 決定1

計画 05_screens SC-02 は表記例を **「25%（$750）」**と明示している。加えて、誤入力の**外れる向き**が
百分率のほうが安全である（比率入力で `25` と打つと equity の 25 倍＝統制の消滅。百分率入力で `0.25` と
打つと 0.25%＝過度に厳しい＝安全側）。詳細は IADR-0151。

- **画面（表示・入力）は %**。ワイヤ（HTTP・永続化・ドメイン）は**比率のまま**（バックエンド無改変）。
- **% ⇄ 比率の変換は 1 か所に閉じる**（`contracts.ts` の `percentTextToRatio` / `ratioToPercentText`）。
  呼び出し側で `× 100` と書かない（[IADR-0130] 決定1 が解決点を 1 本に閉じたのと同じ規律）。
- 変換は**10 進文字列の小数点移動**で行い、`/100`・`*100` の浮動小数点誤差を持ち込まない。

### 2. 実額の併記

- equity は **`GET /risk-controls/status` の `capital`** を用いる（[IADR-0130] 決定2 が「判定に用いる自己資金
  ＝前営業日終値時点の評価額＝`PortfolioSnapshot.Capital`」と確定した値）。**新しい取得口を作らない。**
- **保存前の入力値に対する実額**は、`RiskStatusView.maxOrderAmount`（サーバが**現在の設定**から解決済みの実額）
  では表せない。入力中の値は保存されていないためサーバは知らない。よって画面が `capital × 入力比率` を計算する。
  この計算も 1 関数（`resolveEquityAmount`）に閉じる。
- 取得は**ページで 1 回**行い、リスク上限フォームと実弾切替モーダル（③）へ配る（同じ equity を 2 度取りに行かない
  ＝ 2 か所で違う equity を見る状態を作らない）。
- **equity を取得できないときは実額を出さず「—」とし、その旨を明記する。** 併記できないことを黙って隠さない。

### 3. 値域バリデーション（本作業の要）

**同じ表を画面とサーバの両方が持つ。** 単一情報源はサーバ（`RiskLimitBounds`・ドメイン）であり、画面は
利用者に即時フィードバックするための**前段**である（サーバ側だけだと保存を押すまで分からない／画面側だけだと
API 直叩きで消える）。

| 項目 | 単位 | 下限 | 上限 | 上限の根拠 |
| --- | --- | --- | --- | --- |
| 1 注文あたり発注額上限 | % of equity | > 0 | ≤ **100%** | 1 注文で equity 全額を超える発注枠は「上限」ではない |
| 1 日あたり発注額上限 | %/日 of equity | > 0 | ≤ **1000%** | 既定 150%（＝建玉 1 回転 75% の 2 回転）。10 回転超はスキャルピング領域で戦略時間軸と整合しない（計画 §5） |
| 保有建玉数上限 | 件（整数） | ≥ 1 | ≤ **20** | 既定 3（ADR-0016 決定9）。0 は「取引できない」であり上限設定ではない |
| 日次損失上限 | % of equity | > 0 | ≤ **20%** | 既定 2%。最大 DD 上限（10%）の桁を大きく超える日次許容は統制として成立しない |
| 1 取引あたりリスク | % of equity | > 0 | ≤ **10%** | 既定 1% |
| 最大ドローダウン上限 | % of equity | > 0 | ≤ **50%** | 既定 10%。50% 超の DD は再検証を要する水準（計画 §5 の目的） |
| 連敗しきい値 | 連敗（整数） | ≥ 1 | ≤ **20** | 既定 5 |
| 連敗時サイズ縮小係数 | 倍 | > 0 | **< 1**（1 を含まない） | 既定 0.5。**1.0 は「縮小しない」＝統制の無効化**であるため許さない |

- **上限値そのものは統制の値ではなく「設定できる範囲」である。** 計画 §5 は既定値を定めるが範囲は定めていない
  ため、上表は実装の決定であり [IADR-0151](../adr/IADR-0151_risk-limit-percent-input-and-bounds.md) 決定2 に根拠を記す。
- 整数項目は**小数を拒否**する（`3.5` 件の建玉は存在しない）。
- **`35` は 1 注文上限として `35%` に解釈され、これは受理される**（35% は妥当な設定である）。issue が例に挙げた
  「1 注文上限に 35 のような値が入らない」は**比率入力を前提とした表現**であり、百分率入力では
  同じ危険は `3500`・`35000` として現れる。**両方とも上限 100% を超えるため拒否される**（§テスト方針の否定形）。

### 4. サーバ側の関門

- ドメインに `RiskLimitBounds.Validate(RiskLimitSettings) -> IReadOnlyList<string>` を置く（規則の単一情報源）。
- `PUT /risk-controls/settings/limits` は保存前に呼び、違反があれば **400（`{error, details}`）**を返し
  **設定を一切変更しない・履歴も残さない**（[IADR-0141] が発注先の拒否で採ったのと同じ規律。
  拒否された要求を履歴に積むと、起きていない変更が監査上の事実になる）。
- `RiskSettingsService.UpdateLimits` も同じ関数を呼び、違反時は `ArgumentException` を投げる
  （エンドポイント以外の呼び出し口が将来増えても不変条件が保たれる。既存の例外フィルタが 400 へ写像する）。

## 計画書との差異（記録）

1. **実額の通貨**。計画 05_screens SC-02 は「25%（**$750**）」と **USD 表記**を求める。しかし実装が供給する
   `RiskStatusView.capital` は**基準通貨（円）建て**である（[IADR-0130] 決定3: equity の権威値は USD で持つが、
   基準通貨パイプラインへは参照レート 163.7 で 1 点換算して供給する。`MarketCurrency.Base = Currency.Jpy`）。
   **画面が「$」を付けて円建ての数値を出すことは、単位の取り違えそのものであり最も危険な誤りである**（IADR-0130
   決定1 の理由と同型）。よって**実額は基準通貨（円）建てとして表示し、その旨を画面に明記する**。
   USD 表記は**判定通貨の USD 移行（IADR-0130 決定3 の未決事項・未起票）と同時に行う**。本差異は新たに生じた
   ものではなく、既存の「判定通貨が計画 §3（USD）と実装（JPY）で食い違う」状態が画面に現れたものである。
2. **「保有銘柄数上限」の語**。計画 §5・ADR-0016 決定9 は同語の使用を禁じている（同一銘柄で複数の建玉を
   持ち得るため）。現行 SC-02 のラベルが違反していたため「保有建玉数上限」へ是正した（計画への追随であり差異ではない）。

## 未決事項

- **値域の上限値は実装の決定である**（計画 §5 は既定値のみを定め、設定可能な範囲を定めていない）。
  運用開始後に「上限が狭すぎて正当な調整ができない」事象が出れば見直す。緩める変更は IADR の改定を要する。
- 判定通貨の USD 移行（上記 差異 1）。移行時は実額表示の通貨表記も同時に改める。
