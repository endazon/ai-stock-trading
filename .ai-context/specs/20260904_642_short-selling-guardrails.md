# 仕様書: ADR-0016 決定11 の空売り固有 AI ガードレール 4 件をプロンプトへ追加する（#642）

> 本仕様書は実装着手前に作成する。計画書（`project-planning` の `projects/ai-stock-trading/`）を一次情報とし、
> 本書は「この作業で何をどう実装するか」を確定するための作業仕様である。

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: FR-04（LLM 判断は確定日報の方針・リスク制約の範囲内）
- ユースケース（UC）: UC-01, UC-02
- 画面（SC）: なし
- 関連 ADR: ADR-0016（空売り段階解禁）決定11「AI ガードレールの追加（ADR-0003 §決定の補完）」、ADR-0003（AI 判断ガードレール）
- 計画書リンク: `projects/ai-stock-trading/07_adr/ADR-0016_short-selling-staged-release.md`（決定11。隣接クローン参照）

## 目的・背景

issue #642（由来: #204 実装監査 更新版 2026-09-02）が検出した不具合を直す。

ADR-0016 決定11 は「AI ガードレールの追加」として次の 4 制約を定めるが、`TradeDecisionService`
全体に「空売り」「借株」「踏み上げ」の語が 1 件も無く（3 語とも `grep -rln` でヒット 0 件を実測
済み）、いずれもプロンプトに落ちていない。

| 制約 | 理由（計画書より） |
| --- | --- |
| 「下落を予想する」と「空売りする」は別である | 借株コストと踏み上げリスクを織り込まない判断を出させない |
| 急落した銘柄への追随空売りを禁止する | 反発リスクが最も高い。LLM が最も出しやすい判断であり、かつ最も危険である |
| ニュース由来の急落への即時空売りを保留する | 続報で反転しやすい |
| 空売りの枠を作る目的でロング建玉を取得することを禁止する | 決定9「空売り建玉 ≦ ロング建玉総額」と等価であるため、空売りをしたいのでロングを建てるという統制の趣旨と逆向きの誘因が生じ得る。判定式では塞げないため、ガードレールで禁じる（利用者裁定 2026-08-04・質問票 第1回 Q1） |

4 件目は計画が明示的に「判定式で塞ぐことはできないため、ガードレールで禁じる」と述べており、
**プロンプト以外に置き場が無い**制約である。

**現時点で実害は無い**（空売りは既定無効・`ShortSellEvaluator` は文脈 null で fail-closed）。危ないのは
順序であり、ADR-0016 決定3（借株照会）が成立し空売りが解禁される日に、AI 側の防御だけが空のまま
になる。

## 対象範囲

- 対象:
  - `backend/Services/TradeDecisionService/Features/TradeDecision/DecideTrade/TradeDecisionPromptBuilder.cs`
    の `Build`（本判断）へ「# 空売りの制約」節を無条件で追加する
  - `BuildScreening`（一次スクリーニング）へも同節（短縮版）を無条件で追加する
    （設計判断の理由は後述「設計」節・実装ADR IADR-0296 に記録する）
  - `ScreeningContextAssembler.PromptScaffoldChars` の見積りを追加分だけ引き上げる
  - `TradeDecisionPromptBuilderTests.cs` へ 4 制約の存在テスト（否定形を含む）・空売り無効構成でも
    プロンプトが変わらないことのテスト・スクリーニング側のテストを追加する
- 対象外:
  - 空売りの有効・無効を表すフラグをプロンプトビルダーへ新規に持たせること（受け入れ基準が
    「解禁時に初めて入る形にしない」と明示しているため、そもそも条件分岐を作らない）
  - `ShortSellEvaluator` 等、判定式（コード側の統制）の変更（本 issue はプロンプト側の欠落のみを扱う）
  - 借株照会（ADR-0016 決定3）そのものの実装（前提未着手であり別 issue の範囲）

## 設計

### 1. 本判断プロンプト（`Build`）

`# リスク制約` 節の直後・`# 採算評価（費用控除後の期待利益）`（`includeProfitability` 条件節）の前に、
無条件で `# 空売りの制約` 節を追加する。**`includeProfitability` のような条件分岐に入れない**——
受け入れ基準「空売りが無効な構成でもプロンプトの内容が変わらないこと（解禁時に初めて入る形に
しない）」を満たすには、そもそも空売り有効・無効という概念をこの関数へ持ち込まない（現状も
`TradeDecisionPromptBuilder` は空売り可否のフラグを一切受け取っていない。これを維持する）。

文言は禁止事項の列挙に留めず、**なぜ危険かという誘因の構造**を LLM に伝える。4 制約それぞれに
対応する定数文字列をコード内に置き、テストで「消えると落ちる」形に固定する（後述）。

### 2. 一次スクリーニング（`BuildScreening`）への採否

**入れる。** 理由:

- 二段判断は #667 で既定有効になっている。スクリーニング（軽量モデル）が空売り候補（Sell 方向の
  関心）を安易に通すと、本判断（高性能モデル・費用が高い）まで進んでから初めてガードレールに
  引っかかる。二段判断の目的（IADR-0039）は費用統制であり、**危険な候補を早期に弾ける情報を
  スクリーニング側に持たせないのは、費用を払ってから止める形になり、二段化の目的に反する**。
- IADR-0072 決定2「RAG 文脈はスクリーニングに載せない（費用統制）」は**取得文脈（可変長・件数に
  比例して膨らむ RAG 参考情報）**を対象にした決定であり、本節は固定長の静的な指示文である。
  性質が異なるため、決定2 の対象に含まれない（決定2 を上書きしない）。

**短縮版にする。** 全文（4 制約それぞれの理由まで含む本判断版）をそのまま複製すると、
`ScreeningContextBudgetChars`（IADR-0247・opt-in の縮退制御）が有効な構成で「削れない共有保護分
（`PromptScaffoldChars`）」を不必要に押し上げる。スクリーニングは「関心の方向（Buy/Sell/Hold）」
だけを絞り込む場であり、4 制約の**結論**（何を禁止するか）だけを 1 行ずつ渡せば絞り込みの用は足りる
——誘因の詳細な説明は本判断側で十分である。

`ScreeningContextAssembler.PromptScaffoldChars`（プロンプト骨格の概算・現行 600）は、この短縮版の
実文字数ぶんだけ底上げする（コメントに理由を残す）。これにより縮退制御が有効な構成でも、追加した
固定文言が「見積もりに入っていない超過」を起こさない。

### 3. 文言（ドラフト）

- 本判断側:
  - 「下落を予想する」ことと「空売りする」ことは別の判断である旨・借株コストと踏み上げ（急な
    買い戻しによる急騰）で損失が青天井になり得る旨
  - 急落直後は反発（踏み上げ）が最も起きやすい局面であり、急落への追随空売りが最も危険な判断で
    ある旨
  - ニュース由来の急落は続報で反転しやすく、即時の空売りは保留する旨
  - 空売りの余力（証拠金枠）を作る目的でロング建玉を取得しない旨・その仕組みは方向性リスクの
    相殺という本来の目的に反する旨
- スクリーニング側（短縮版）: 上記 4 点の結論のみを箇条書きで渡す

最終文言はコードコメントと合わせて実装時に確定する（本節はドラフト）。

## 受け入れ基準

- [ ] 生成プロンプト（本判断）に決定11 の 4 制約が含まれる
- [ ] **否定形**: 4 制約のいずれかがプロンプトから消えるとテストが落ちること（定数化した部分文字列
      をテストが直接参照する形で固定する）
- [ ] 空売りが無効な構成でも、プロンプトの内容が変わらないこと（解禁時に初めて入る形にしない）
- [ ] スクリーニング側にも短縮版が入り、同様に否定形テストで固定する
- [ ] 起点 ID コメント（FR-04 / ADR-0016 / ADR-0003）付き

## テスト方針

`TradeDecisionPromptBuilderTests.cs` に追加する。

1. 本判断プロンプトに 4 制約の定数文字列がそれぞれ含まれることを確認する `[Theory]`（`[InlineData]`
   で 4 制約の定数を列挙し、リフレクションではなく直接参照することで「削除すると即座に失敗する」
   形にする）。
2. 空売り無効相当（現状の既定呼び出し・追加パラメータなし）と、将来空売りが有効になった場合を
   模した呼び出し方の差異が無いこと——実装が空売り可否のフラグを持たない設計であるため、これは
   「既存のどの呼び出し方でも本節が同一に出る」ことを確認する形になる（`Build` の異なる引数の
   組み合わせ間でプロンプトの `# 空売りの制約` 節が同一文字列であることを比較する）。
3. `BuildScreening` にも短縮版の 4 制約それぞれの結論が含まれることを確認する。
4. 既存の完全一致テスト（`RAG取得文脈が空なら参考情報節を出さない` 等）が壊れないよう、
   `withNull.Should().Be(baseline)` 系のテストは新節を含めた文字列同士の比較のままで良い
   （両辺に同じ新節が乗るため差分は変わらない）。
