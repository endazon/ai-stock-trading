# 作業仕様書: BFF は上流の 401 を 502 へ写像する（#728）

## 起点

- issue #728。`AssumptionsBffEndpoints` / `RiskControlsBffEndpoints` / `MonitorBffEndpoints` は
  上流サービスへの pass-through プロキシで、上流のステータスコードをそのまま透過している。
- 各モジュールは `RequireAuthorization()` を持ち、**利用者の認証は BFF 自身が済ませている**。
  その先で上流が 401 を返すのは「利用者が未認証」ではなく「BFF↔上流の資格情報／構成が
  合っていない」という後段の不整合である（#727 のような認証レルム不一致が典型例）。
- 統合 SPA の `apiFetch`（MSP `foundation/api/apiClient.ts`）は 401 を「セッション失効」と
  解釈して `/bff/auth/login` へ強制遷移する。Keycloak SSO が生きていれば即座に戻り、同じ 401 →
  同じ遷移の無限ループになる（観測 2026-09-10）。
- #727 は原因（レルム不一致）そのものを直したが、**BFF が上流 401 を透過する限り、次に同種の
  構成不整合が起きればまた同じ症状が再発する**。本 issue はその症状自体を止める。

## 方針

- 上流が **401** を返した場合のみ、BFF は **502**（既存の「後段不達は 502 へ縮退する」fail-safe と
  同じ扱い）へ写像し、JSON 本文 `{ "reason": "upstream_unauthenticated" }` を返す。
- ログには **警告 1 行**を出し、上流パスと `WWW-Authenticate` ヘッダの `error` / `error_description`
  パラメータ（無ければ `(none)`）だけを記録する。**`Authorization` ヘッダ・トークンは一切ログへ
  出さない。**
- **403 は既存どおり透過する**（利用者の権限不足は正しい「権限不足」であり、存在秘匿は
  フロント側の `RequireRole → NotFound` が担う。#728 の対象外）。
- 200 / 400 / 404 / 409 / 5xx（401/403 以外の全て）の既存 pass-through 挙動は変えない。
- `OpendAuthBffEndpoints` は上流（サイドカー）が認証を持たず、`ProxyAsync` も共有していない
  （本文を作り直す別方式）ため対象外とする。issue 本文が「同じ写像を入れても害は無い」と
  述べる余地には触れるが、**計画外の変更を避けるため今回は変更しない**。

## 設計

`ProxyAsync` は 3 ファイル（`AssumptionsBffEndpoints` / `RiskControlsBffEndpoints` /
`MonitorBffEndpoints`）に**同一実装がそれぞれ private static として重複している**（共有クラスへの
抽出は行われていない）。共通クラスへ抽出すると新規の公開面・DI 登録・名前空間設計が発生し、
「計画外の過剰な抽象化を行わない」（CLAUDE.md 禁止事項）に抵触し得るため、**今回は抽出せず
3 ファイルそれぞれの `ProxyAsync` へ同一のロジックを追記する**（IADR-0326 決定）。

各 `ProxyAsync` で、後段からの応答を受け取った直後（`resp.StatusCode` 判定）に分岐を追加する。

```csharp
if (resp.StatusCode == HttpStatusCode.Unauthorized)
{
    var (error, description) = ParseWwwAuthenticateChallenge(resp.Headers.WwwAuthenticate);
    http.RequestServices.GetRequiredService<ILoggerFactory>()
        .CreateLogger(LoggerCategory)
        .LogWarning(
            "BFF proxy: upstream {UpstreamPath} returned 401 (mapped to 502). WWW-Authenticate error={Error} error_description={ErrorDescription}",
            path, error ?? "(none)", description ?? "(none)");
    return Results.Json(new { reason = "upstream_unauthenticated" }, statusCode: StatusCodes.Status502BadGateway);
}
```

- ロガーは `http.RequestServices` から都度解決する（既存の呼び出し規約が `ProxyAsync` の引数を
  `(IHttpClientFactory, HttpContext, HttpMethod, string, CancellationToken)` に固定しており、
  `MapGet`/`MapPut` 側のラムダ全箇所を書き換えずに済む。401 のときだけ発生する遅延解決のため
  平常時のオーバーヘッドは無い）。
- `WWW-Authenticate` の `error` / `error_description` はダブルクォート付きパラメータとして単純な
  正規表現で抽出する（RFC 6750 Bearer チャレンジの一般的な形）。パースできなくても例外にせず
  `null` を許容する（ログの欠落は許容し、本流を止めない）。
- 応答本文はここでは後段の本文を読まない（`resp.Content.ReadAsStringAsync` を呼ばない）。
  読むと後段の 401 本文がそのまま漏れる経路が増えるため、固定の理由コードだけを返す。

## 計画書との差異

差異なし。ADR-0028 決定3（破壊的統制操作は Discord Bot へ一元化）・既存の「後段不達は 502 へ
縮退する」fail-safe 方針を拡張するだけであり、計画書の要求・UC・画面設計と矛盾しない。

## 未決事項・残余リスク

- `WWW-Authenticate` を上流が返さない構成不整合（例: 単純な 401 のみ）では `error` / `error_description`
  ともに `(none)` になる。原因特定には上流側のログが別途要るが、これは本 issue の受け入れ基準の
  範囲外（BFF 側でログに残せる情報の上限）。
- `OpendAuthBffEndpoints` は今回対象外。将来同じ `ProxyAsync` 方式へ統合する場合は改めて検討する。
