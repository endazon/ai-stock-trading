# 仕様書: 監査の自由記述の伏せ字が壁時計に依存する不安定の根本原因と是正（#984）

## 起点

- [#984](https://github.com/endazon/ai-stock-trading/issues/984)。develop の `AuditService.Tests.AuditFreeTextTests` が
  高負荷時に断続的に赤（`長い反復入力でも伏せ字の処理は打ち切られない` / `代替レグの理由文が長くても台帳の全量JSONは上限を超えない`）。
  失敗文面: `Did not expect sanitized "（理由文は整形できなかったため記録しない）" to contain "整形できなかった".`
- 対象: `backend/Services/AuditService/Domain/AuditFreeText.cs`（#842 / PR #968 / IADR-0405 決定2）。
- 🔴 skip・再試行・閾値（200 ms）の引き上げだけの是正は禁止。**本番で理由文が黙って捨てられる条件を無くす**。

## 再現（是正前・実測。`origin/develop` = `a1826edf`）

4 コアの環境。他エージェントの並行ビルド・試験で load average は 20〜60 の間を動いていた。「負荷」は別に CPU を回し続ける
`while :; do :; done` を 6 本。

| 条件 | 結果 |
| --- | --- |
| `dotnet test AuditService.Tests --filter AuditFreeTextTests` を 3 プロセス同時 × 4 巡、負荷 6 本 | **12 回中 2 回赤**（`unit: "[f"`・`unit: "x"`。上の失敗文面と同じ） |
| `dotnet test AuditService.Tests`（全 198 件）× 3 回、負荷 6 本 | 3 回とも緑（1 プロセスでは再現しにくい）。4 回目は試験ホストが 13 分終わらず手で打ち切った（どの試験が止まっていたかは記録できていない。是正後の全件実行は `--blame-hang-timeout 5m` を付けて監視した） |
| 同じ正規表現（200 ms の予算）で 20,000 文字の 6 種の反復入力を 16 スレッド × 20 回照合（試作の計測器。負荷 6 本） | **1,920 回中 724 回が `RegexMatchTimeoutException`**。1 回の照合の壁時計は最大 50,697 ms |
| 同じ正規表現の予算を **1 tick** にする（決定的な再現） | 6 種の反復入力（`x` / `a.` / `1.` / `a-` / `ab://` / `[f`）の **6 種とも打ち切り**＝理由文は定型文へ置き換わる |
| 同じ正規表現を**予算なし**で、入力長を 2 倍ずつ（2 万〜16 万文字）にして CPU 時間を測る（負荷なし） | **線形**（例 `[f`: 7.2 → 15.3 → 32.6 → 57.4 ms。`x`: 6.5 → 17.4 → 25.3 → 39.9 ms）。2 万文字で CPU 7 ms 前後 |

## 根本原因（仮説ごとの判定）

### ① 正規表現のバックトラックが入力長に対して 2 乗で膨らむ ——**原因ではない**

- 入力長を 2 倍にすると CPU 時間もほぼ 2 倍（上表 4 行目）。IADR-0405 決定2 の「語の先頭からしか始まらず語の中を原子グループで
  読む」形は、既に線形に効いている。2 万文字で CPU は数 ms であり、200 ms に届くのは計算量ではない。

### ② 壁時計の予算（200 ms）が CPU の割り当ての遅れに負ける ——**これが原因（本番のコード）**

- `Regex` のマッチタイムアウトは**壁時計**で測る。CPU が混むとスレッドが走れない時間も予算を食い、数 ms の仕事でも 200 ms を超える
  （上表 2 行目: 最大 50 秒）。打ち切りは `RegexMatchTimeoutException` になり、`Sanitize` は理由文を捨てて定型文
  「（理由文は整形できなかったため記録しない）」を返す。
- 予算を 1 tick にすると決定的に同じ置き換えが起きる（上表 3 行目）＝**結果が入力ではなく実行時の混み具合で決まる**。
- 🔴 **本番でも同じ条件で理由文が台帳から黙って欠ける**（監査証跡の欠落。7 年保持の台帳に「整形できなかった」だけが残る）。
  是正前に本番で理由文が捨てられる条件: **伏せ字の照合 1 回の壁時計が 200 ms を超えたとき**（CPU の飢餓・GC の停止・
  入力長のいずれでも起きる。入力の中身とは無関係）。

### ③ 試験側の同期・並列の問題か ——**否**

- 試験は `AuditFreeText.Sanitize` を直接呼ぶだけで、待ち・共有状態を持たない。赤は本番の関数の戻り値そのもの（定型文）である。
  試験を直す筋ではない。

## 是正の設計（選択肢と判定）

| 案 | 判定 |
| --- | --- |
| A. 予算を伸ばす（例 2 秒） | **却下**（禁止事項。上表 2 行目の最大 50 秒のとおり、どの値でも「混めば捨てる」は残る） |
| B. 入力長の上限を先に切ってから照合する | **却下**。伏せ字は文面を縮める（長い URL → 5 文字）ので、出力の先頭 500 文字を決めるのに要る入力の長さは上から抑えられない。切れ目が接続先の途中に落ちると形が崩れて伏せ損ねる（例 `opend.x.svc:11111` → `opend.x.sv`）。**壁時計の予算も残る** |
| C. 旧パターンのまま予算だけ無くす（`InfiniteMatchTimeout`） | 実測では線形だが、**線形であることの保証がバックトラック・エンジンの挙動の論証頼み**。将来の選択肢の追加で 2 乗化しても検知されず、今度は台帳の購読が CPU を食い続ける |
| D. 手書きの走査器 | 線形は読めば分かるが、5 つの形の境界規則（後読み・先読み・原子グループの意味）を手で写す量が大きく、写し違いの危険が C/E より大きい |
| **E. `RegexOptions.NonBacktracking`（入力長に線形。.NET が保証）へ替え、予算を持たない**（採用） | 前後読み・原子グループは使えないので、**同じ意味の形へ書き換える**（下）。意味が変わっていないことは旧パターンとの差分試験で固定する |

### E の書き換え（IADR-0419）

- 語の先頭の条件（後読み `(?<![…])`）→ **直前の 1 文字（または文字列の先頭 `^`）を消費**する。伏せるのは名前つきの組 `e` だけ。
- 語の終わりの条件（先読み `(?!…)`）→ **直後の 1〜2 文字（または `$`）を消費**する（IPv4 の `(?![A-Za-z0-9_]|\.\d)` は
  `$|[^A-Za-z0-9_.]|\.(?:$|\D)`、ポートの `(?!\d)` は `$|\D`）。
- ホスト名の「英字を含む」（先読み）→ **英字が最初のラベルにあるか、後のラベルにあるか**の 2 通りの選択肢で表す。
- 原子グループ → 外す（NonBacktracking では意味を持たない。旧パターンでも `:` がクラスに無いので結果は同じ）。
- 消費した前後の文字は隣の接続先の境界を兼ね得る（例 `[::1]1.2.3.4`・`1.1.1.1 2.2.2.2`）。`Regex.Replace` は照合の末尾から次を
  探すので兼ねられない。**`Match(text, startat)` の繰り返しで、次の照合は伏せた `e` の末尾の 1 文字手前から始める**。
  次の `e` が前の `e` と重ならないこと: `e` の最後の文字が次の `e` の先頭になり得るのは IPv6 の `[` だけで、`[` で終わる `e` は
  URL だけ・URL の直後は区切り（空白・括弧・引用符）か文字列の末尾であり、IPv6 の 2 文字目にはなれない。
- **予算は `Regex.InfiniteMatchTimeout` を明示する**（未指定だと `REGEX_DEFAULT_MATCH_TIMEOUT` がプロセスに設定されたとき
  壁時計の予算が戻る）。`RegexMatchTimeoutException` の捕捉と定型文への置き換えは**消す**（到達しない分岐を残さない）。
- 是正後に本番で理由文が捨てられる条件: **無い**（伏せ字の照合に打ち切りが無い）。変わるのは従来どおり上限 500 文字での切り詰めだけ。

## 検証

- 試作での差分: 乱数 5,000,000 件で旧パターンとの差 0。再開位置を「末尾の 1 文字手前」から「末尾」へ変える変異では
  300,000 件中 1,086 件の差（差分試験が境界の兼用を捕まえることの確認）。
- 是正後の CPU 時間（負荷下・3 回平均）: 2 万〜32 万文字の反復入力 17 種で入力長に概ね比例（例 `[f`: 0.11 → 0.40 → 1.71 ms）。
- 変異の実測（是正後・`--filter AuditFreeTextTests`）:
  - 次の照合を「末尾の 1 文字手前」ではなく「末尾」から始める → `接続先を伏せる([::1]1.2.3.4)` と T-10-980 が赤。
  - 予算を 200 ms に戻す → T-10-981 が赤。
  - `NonBacktracking` を外す（同じ形をバックトラック・エンジンで照合）→ T-10-981 が赤（この変異では 37 件の実行が 0.6 秒 → 7 秒）。
  - IPv4 の終わりの条件から「`.` の後に数字が続かない」を落とす → T-10-980 と T-10-982（`1.` の反復）が赤。
- 是正前後の連続実行（4 コア・CPU を回し続ける負荷 6 本＋他エージェントの並行ビルド。load average 20〜60）:

  | 対象 | 是正前 | 是正後 |
  | --- | --- | --- |
  | `--filter AuditFreeTextTests` を 3 プロセス同時 | 4 巡 12 回中 **2 回赤** | 8 巡 **24 回連続緑**（37 件） |
  | `AuditService.Tests` 全件を 3 プロセス同時（load average 85〜100） | （未測） | 3 回とも**失敗 0**（192〜196 件が緑）だが、3 回とも試験ホストが `AuditCycleCompletenessTests` / `AuditConsumerCoverageTests`（Wolverine のホストを組む試験）で 5 分止まり、`--blame-hang-timeout` で打ち切られた（下の「射程外」） |

## 射程外

- 🔴 **全件実行が極端な高負荷（load average 85〜100）で止まる別の現象。** `AuditCycleCompletenessTests.契約イベントの全数が監査台帳へ記録される`・
  `AuditConsumerCoverageTests.全ドメインイベントに対応する監査コンシューマが存在する`（ほか 1 回 `AuditEventConsumersTests`）の実行中に
  試験ホストが 5 分無応答になった。表明の失敗ではない。是正前の全件実行の 4 回目も 13 分終わらずに止まっており（どの試験かは未記録）、本件の変更で生じた現象とは見ていないが、是正前の停止箇所を特定できていないので同一とは断定しない。
  本件の射程外として報告に留める（別 issue の候補）。

- 他の自由記述欄（`TradeDecisionMade.Rationale` 等）への伏せ字の適用（IADR-0405 の残余リスクのとおり）。
