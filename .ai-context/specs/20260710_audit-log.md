# 仕様書: 監査ログサービス（全ドメインイベントの時系列記録）

> Issue [#17](https://github.com/endazon/ai-stock-trading/issues/17)（FR-11・Must）の Slice A。取引パイプラインが発行する
> 全ドメインイベントを購読し、**追記専用の時系列監査台帳**へ永続化して、注文単位（`DecisionId` 相関）・期間で照会できる
> ようにする。「いつ・何を根拠に・何をしたか」を後から辿れること、拒否理由が記録・照会できることを満たす。

## 起点となる計画書・課題（トレーサビリティ）

- 機能要求（FR）: FR-11（全イベントの時系列記録・監査。Must）。関連: FR-04（判断根拠 Rationale）・FR-10/FR-19（拒否理由 RejectionReason）
- ユースケース（UC）: UC-07（取引履歴・判断根拠の参照）
- アーキ概要: `01_architecture-overview.md`（約定イベントの発行・「プロンプト・入力・出力・発注の全量をログに残す（監査・再現用）」）
- ADR: ADR-0001（platform 再利用・Database per Service）、ADR-0003（判断根拠の記録）
- 関連 IADR: 本作業で新規 [IADR-0019](../adr/IADR-0019_audit-log-service.md)
- 対象 Issue: #17（Slice A）

## 目的・背景

現状、`RejectionReason` 列挙・`OrderRejected` 等「監査で使う」契約はあるが、記録・保管・照会の実装がない（#17）。
取引の説明責任（いつ・何を根拠に・何をしたか）と、拒否理由の追跡を満たすため、全ドメインイベントを時系列で永続化する
専用の記録サービスを追加する。UC-07 の自然言語照会は基盤 RAG（FR-08・#18）を利用するため本スライス対象外とし、
本スライスは**構造化された直接照会**（`DecisionId` 相関・期間）を提供する。

## 対象範囲

### 新規サービス `AuditService`（Application + Worker。Domain 層なし＝監査に固有ドメインロジックなし）

- **購読対象イベント（全ドメインイベント）**: `PriceMovementDetected` / `StopLossTriggered`（市場監視）、`TradeDecisionMade`（取引判断）、
  `OrderApproved` / `OrderRejected`（リスク管理）、`OrderExecuted`（発注執行）。
- **正規化**（`AuditEntry` 値オブジェクト・`AuditEntryFactory`）: 各イベントを共通形へ写像する。
  - `Id`（冪等キー＝MassTransit `MessageId`）／`EventType`／`CorrelationId`（注文系は `DecisionId`、市場系は `EventId`）／
    `Symbol?`／`Summary`（人間可読の一行）／`Detail`（イベント全量の JSON・列挙は文字列化）／`OccurredAt`（イベント時刻）／`RecordedAt`（記録時刻）。
  - `OrderRejected` は `Summary`／`Detail` に `RejectionReason` 列挙を保持する（拒否理由の記録・照会）。
- **永続化**（`EfAuditEventStore` + `AuditDbContext` + `AuditEventRow`・専有 DB `audit_svc`・EF Migration）: 追記専用。
  `Id`（=MessageId）で冪等（MassTransit 再送で重複記録しない）。`CorrelationId`・`OccurredAt` にインデックス。
- **照会**（`AuditQueryEndpoints`・OwnerOnly＝利用者のみ・Keycloak `trading-owner`。監査台帳は取引履歴＝機微）:
  - `GET /audit/events/{correlationId}` — 注文単位の全記録（`OccurredAt` 昇順＝時系列）。
  - `GET /audit/events?limit=N` — 直近の記録（`OccurredAt` 降順・既定 100・上限 500）。
- **Worker ホスト**: 他サービス準拠（Serilog/OTel・Keycloak 認証・EF Npgsql・ヘルス＋NpgSql・MassTransit RabbitMQ 消費者＋再試行・
  起動時 `MigrateAsync`・相関ID）。実行時基盤は test-support shim（本番非使用・IADR-0013）。

## 受け入れ基準

CI で緑にする範囲（ユニット＋MassTransit テストハーネス＋EF InMemory＋WebApplicationFactory）:
- [ ] 各イベント（6 種）を購読すると、対応する `EventType`・`CorrelationId`・`Symbol`・`OccurredAt` を持つ監査記録が保存される。
- [ ] `OrderRejected` の記録に `RejectionReason` 列挙が含まれ、照会で取得できる（計画の受け入れ基準）。
- [ ] 同一 `MessageId` の再送は重複記録しない（冪等）。
- [ ] `GET /audit/events/{correlationId}` が同一注文の記録を時系列（昇順）で返す（＝いつ・何を根拠に・何をしたかを辿れる）。
- [ ] `GET /audit/events?limit=N` が直近の記録を降順で返し、`limit` 上限を超えない。
- [ ] 照会エンドポイントは OwnerOnly（未認証 401・ロール無し 403）。
- [ ] Worker が起動しヘルス `/health/live` が応答する（WebApplicationFactory）。
- [ ] 既存テストを緑に保つ。

実コンテナ前提（CI 既定では実行しない・Testcontainers）:
- [ ] RabbitMQ + PostgreSQL 経由の全イベント → 監査台帳の E2E 記録・照会。

## 対象外（後続）

- UC-07 の自然言語照会（基盤 RAG／KB エクスポート・FR-08・#18）。本スライスは構造化直接照会に限定。
- LLM プロンプト／入出力ログの記録（取引判断の実 LLM が未実装＝プレースホルダのため。実 LLM 実装時に `TradeDecisionMade` の
  根拠拡充と併せて追加）。
- 可観測性スタック（OTel/Loki）の運用テレメトリとの詳細な役割分担の運用設計（`docs/observability/`・後続）。本スライスは
  「監査台帳＝業務イベントの永続・照会／OTel・Loki＝運用テレメトリ」の役割分担を IADR-0019 で明記するに留める。
- 保持期間・パーティション・アーカイブ方針（運用仕様 `docs/operations/`・後続）。

## テスト方針

- `AuditEntryFactory` は純関数として各イベントの写像（EventType・CorrelationId・Symbol・Summary・拒否理由）を単体検証。
- `EfAuditEventStore` は EF InMemory で追記・冪等・相関/期間照会を検証。
- Consumer は MassTransit `ITestHarness` ＋ InMemory ストアで記録を検証。
- 照会エンドポイントは `AuditWorkerWebApplicationFactory`（InMemory DB・TestAuthHandler）で OwnerOnly・時系列・limit を検証。
