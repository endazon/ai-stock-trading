# 逆転監視の母集合を「現在の CI 構成以降」に限る（IADR-0208 決定 15）

## 背景

CI 高速化（IADR-0208）は完了し、逆転そのものは**直接実測で解消を確認した**
（`build-and-test` の完了オフセット 119 / 125 / 130 / 132 / 144 秒 vs `claude-review` の下限 146 秒）。

しかし逆転監視（`ci-latency-watch.yml`）は「まだ逆転している」と言い続けている。
実データ（2026-08-22 実測）で窓の中身を確認した:

| PR | マージ | 母集合 | `build-and-test` |
| --- | --- | --- | --- |
| #546 | 08-22 | ○ | 125 秒（最適化後） |
| #544 | 08-21 | ○ | 130 秒（最適化後） |
| #542 | 08-21 | ○ | 231 秒 |
| #540 | 08-21 | ○ | 240 秒 |
| #536 | 08-21 | ○ | 最適化前 |
| #534 | 08-20 | ○ | 223 秒 |
| #531 | 08-20 | ○ | 186 秒 |
| #545 / #538 / #535 | — | ×（docs） | 母集合から除外 |

**監視は嘘をついていない。** 直近 10 本のマージ済み PR のうち backend PR は 7 本で、
最適化後はまだ 2 本しかない。中央値 223 秒は残り 5 本が作っている。

🔴 **問題は「窓が入れ替わるまでの数週間、毎週同じ文言で鳴り続ける」ことである。**
その間、**本物の再逆転が起きても同じ文言に埋もれて見分けられない**。

決定 9 の定常性の門（中央値 ≧ 最小 × 2 なら判定しない）はこれを止められない ——
今回の改善は 223 → 125 秒＝**1.8 倍で、2 倍の門をくぐってしまう**。

### 同型の 3 度目である

| # | 形 | そのときの手当て |
| --- | --- | --- |
| 1 | 窓の 12 本中 11 本が最適化前で「遅い」と誤報しかけた | 決定 9: 定常性の門（2 倍） |
| 2 | 決定 11 の skip で母集合が二峰性になり門が永久発火した | 決定 13: 母集合から docs PR を外す |
| 3 | 1.8 倍の段差は門をくぐり、数週間の誤報になる（本件） | 本仕様書 |

規約「同型の事故が 2 回起きたら検査器・規約を足してよい」を満たす。
手当ての筋は 2 度目と同じ ——「**しきい値ではなく母集合を正す**」。
倍率を動かしても段差の大きさ次第で必ずまた漏れるためである。

### 副産物: PR #546 で直した欠陥は実データで効いていた

「変更ファイルを 1 ページ目しか見ない」欠陥は仮説ではなかった。
**#536 は変更 619 ファイル**で、1 ページ目だけでは `backend=false`（母集合から除外）、
全ページ読むと `backend=true` になる。**最初に見た実データの窓の中に既に該当例があった。**

## 決定（利用者裁定 2026-08-22）

- 母集合に「現在の CI 構成以降」を加える。判定できる本数に満たなければ理由を明示して判定しない。
- MSP（基盤リポジトリ）へは**別 PR で追随する**。本 PR は AST に閉じる
  （MSP には決定 11 も `detect-changed-areas.js` も無く、実測での検証がその場でできないため）。

## 変更内容

`scripts/check-ci-latency.js` のみを変更する。**`.github/workflows/` は触らず、必須チェック名も変えない。**

1. **epoch を GitHub API から導出する。**
   `GET /repos/{repo}/commits?path=.github/workflows/ci.yml&per_page=1` の
   `commit.committer.date` を「CI 構成が最後に変わった時刻」とする。
   - 🔴 **日付を焼き込まない。** 固定値は必ず腐る（決定 9 の「しきい値を固定値で持たない」と同じ理由）。
   - 🔴 **`git log` を使わない。** `actions/checkout@v7` は既定で shallow であり、
     出力が履歴の打ち切り位置を指し得る。**形式は満たすので気付けない。**
     API なら `contents: read`（既に有る）だけで足りる。
2. **`collect()` で `merged_at` が epoch より前の PR を母集合から外す。**
   外した本数を `skippedPreEpoch` として**必ず出力する**（黙って母集合を狭めない）。
3. 🔴 **epoch が引けなければ絞り込まない**（従来どおり全 PR を母集合にする）。
   理由を `::notice::` で出す。**監視を門に化けさせない。**
4. **最小本数 `MIN_SAMPLES = 3`。** 満たなければ `judge()` は skip し、
   epoch と本数を添えて「まだ判定できない」と言う。
   既存の skip 経路が「**緑は『逆転していない』を意味しない。判定していないだけである**」を出すのでそれに乗せる。
5. **定常性の門（決定 9）は残す。** epoch は**既知の構成変更**を、門は
   **`ci.yml` を触らない原因**（依存更新でテストが重くなる等）を扱う。役割が違うので片方に寄せない。
6. **`CI_LATENCY_EPOCH`（ISO 8601）/ `CI_LATENCY_MIN_SAMPLES` の環境変数上書き。**
   🔴 **実データに対して両方向を実測するために要る。** 片方向だけでは
   「常に skip する実装」と区別できない（決定 9 で確立した作法）。

**権限の追加は不要**（`contents: read` / `pull-requests: read` / `checks: read` を既に持つ）。

## 受け入れ基準

1. epoch より前にマージされた PR が母集合から外れ、**外した本数が出力される**。
2. epoch 以降の対象が `MIN_SAMPLES` 未満なら、**epoch と本数を添えて判定を skip する**。
3. 対象が足りていれば**判定する**（skip しっぱなしでない）。
4. epoch が引けないときは**従来どおり全 PR を母集合にする**（fail-open）。
5. 実データで**両方向**を実測できる（現状 → 判定しない／epoch を過去へずらす → 判定が再開する）。
6. 自己試験・`scripts.test.js`・全検査器が緑。必須チェック名は 1 つも変わらない。

## 母集合の取り方（規則 6: 引いた結果と除外の理由を残す）

- **コードの母集合**は `scripts/check-ci-latency.js` 1 ファイルである。
  同ファイルは MSP へ複写して使っているが、**今回は AST に閉じる**（利用者裁定）。
  MSP は別 PR で追随する ——「気付いたら受容として記録する」ではなく**追随する対象として残す**。
- **文書の母集合**は IADR-0208（決定 15 を追加）と `.ai-context/adr/README.md`（索引）である。
  `docs/ai-workflow.md` は監視の check 名を扱わないため対象外
  （`check-workflow-job-refs.js` の突合対象にも影響しない）。
- **除外**: `.ai-context/specs/` の既存記録は point-in-time のため書き換えない。

## 検証（実測でしか確かめない）

- 🔴 **変異試験で、追加した自己試験が実際に落ちることを確認する。**
  `ok` と表示されるだけの試験を足さない（#546 で同型の欠陥を踏んだ）。
- 🔴 **両方向を実測する。** 現状で「判定しない」ことと、`CI_LATENCY_EPOCH` を
  2026-08-20 へずらして**判定が再開し既知の中央値 223 秒を再現する**ことの両方。
- **issue #543 のクローズは上記が緑になってから。** 順序が逆だと
  「鳴らなくなったから閉じた」と「判定していないから鳴らない」が区別できない。

## 実施結果（2026-08-22）

### 両方向の実測

| | 実行 | 結果 |
| --- | --- | --- |
| ① 現状 | `check-ci-latency.js` | **10 本中 9 本を「現在の CI 構成より前」として除外**。対象 1 本のため判定せず、epoch と本数を添えて理由を出力。**exit 0** |
| ② epoch を 08-20 へ | `CI_LATENCY_EPOCH=2026-08-20T00:00:00Z` | **判定が再開**。既知の中央値 **223 秒** vs 下限 146 秒を再現し逆転を検出。**exit 1** |

**skip しっぱなしではない**ことを ② で固定した。①の参考値（判定には使っていない）は
`build-and-test` 中央値 125 秒 / `claude-review` 最小 178 秒であり、現在の構成では逆転していない。

🔴 **終了コードはパイプの先ではなく本体で測った。** 最初 `| grep` の後ろで `$?` を読み、
**grep の終了コードを見ていた**（集約ジョブを自身の所要で測った罠と同型である）。

### 変異試験（追加した自己試験が実際に落ちるか）

| 変異 | 落ちた試験 |
| --- | --- |
| epoch による絞り込みをしない | `partitionByEpoch: epoch より前の PR を落とす` |
| 最小本数の門を外す | 3 件（本数の門・門の順序・epoch 不明時） |
| 境界を `>` にする（同時刻を落とす） | `partitionByEpoch: 境界（epoch と同時刻）は残す` |

### 🔴 門の追加で、既存の試験 2 件が意味を失っていた

`judge()` に最小本数の門を足したことで、**対象 1 本で呼んでいた既存試験が本判定へ到達しなくなった**。

| 試験 | 影響 | 対応 |
| --- | --- | --- |
| `基準は中央値ではなく最小で見る` | **赤くなった**（skip の `ok:true` と期待値 `false` が食い違った） | 対象を 3 本にし、`skipped:false` の表明を足した |
| `同値は逆転ではない（境界）` | 🔴 **落ちずに素通りしていた**（skip の `ok:true` を「境界が通った」と読める） | 同上 |

**危ないのは後者である。** 赤くなる劣化は気付けるが、**緑のまま意味を失う劣化は気付けない**。
指摘された 1 件だけ直さず、`judge()` を呼ぶ試験を全数引き直して見つけた（規則 7）。
両方に「なぜ 3 本なのか」をコメントで残した。

### 全体

自己試験 50 → **60 件**。`scripts.test.js` 267 件・全検査器の自己試験と本走とも緑。
**必須チェック名は 1 つも変えていない。**

## AI レビューの指摘への対応（2026-08-22）

🔴 0 件・🟡 2 件・🟢 1 件。

### 🟡 ①「epoch はマージ時刻で判定しているが、計測は別の時刻に行われている」→ 是正した

指摘は妥当である。**CI が走ったのは構成変更の前、マージはその後**という PR は普通に起こり
（PR を放置している間に develop 側で `ci.yml` が変わり、リベースせずマージされた場合）、
その 1 本は旧構成の値なのに母集合へ残る。**決定 15 が塞ごうとした穴を epoch 自身が再現する。**

判定を**計測時刻（check 群の開始 `t0`）**へ移した。`t0` は待ち時間の尺度として既に算出しており、
新たに引くものは無い。

### 🔴 是正したら、実データで別の取りこぼしが出た

計測時刻だけで判定すると、**構成変更を持ち込んだ PR 自身**が落ちる。
その run は**新しい `ci.yml` で走っている**（`pull_request` の run は base を取り込んだ merge ref で動く）
のに、epoch＝develop へ載った時刻はその run より**後**になるためである。

実測では **#546 がこれに当たり、母集合が 0 本になった**。落ちるのは
「新しい構成での最初の 1 本」＝**最も知りたいサンプル**である。

**片方だけでは足りず、両方を見る必要がある**と分かった。変更ファイル一覧は backend の判定のために
既に引いているので、追加の API 呼び出しは無い（一覧の取得を 1 度にまとめた）。

🔴 **これは実データを見なければ気付けなかった。** 自己試験は「マージ時刻で判定していたら
落ちる形」を固定していたが、**是正後に新しく生まれた取りこぼしは自己試験に無かった**。
両方向の実データ実測を毎回やる作法が拾った。回帰テストとして両方を固定した。

### 🔴 0 本のときに「check 名の設定ミスを疑え」と言っていた

epoch で全部外して 0 本になった状態でも、既存の警告が
「`CI_LATENCY_TARGET` が check 名と一致しているか確かめよ」と出していた。
**原因が分かっているのに読み手を誤った方向へ差し向ける。**
`skippedPreEpoch` があるときは出さないようにし、あわせて `judge()` の本数の門を
null 判定より前へ移して、**0 本のときも epoch を理由に添える**ようにした。

### 🟢「トリビアルな `ci.yml` 編集でも epoch が前進する」→ 残余リスクとして記録

コメント追記のような `build-and-test` の挙動に影響しない編集でも epoch は前進し、
「判定できない」期間が延びる。**意図したトレードオフである**（構成変更を機械的に検出する以上、
「挙動に影響するか」は機械では判定できない）。IADR の残余リスクへ記録した。

### 検証

- 自己試験 60 → **65 件**。変異試験 5 種（絞り込み無効化・境界・配線・構成変更 PR の例外・警告の抑止）で
  すべて検出されることを確認した。**配線は自己試験では見えないため実データで確認した。**
- 実データの両方向: 現状 → 6 本を epoch で除外・対象 1 本（#546 の 125 秒）で判定せず **exit 0**／
  epoch を 08-20 へ → 対象 6 本・中央値 186 秒で逆転を検出し **exit 1**。
- `scripts.test.js` 267 件と全検査器が緑。

### レビューが追試できなかった点について

`CI_LATENCY_EPOCH=...` の前置き形コマンドがレビュー環境の許可判定で拒否され、
両方向の実測は追試できなかったとのことである。本作業では実行できており、出力を上に残した。
なお `workflow_dispatch` を API から叩くと **403**（既定トークンは `metadata=read` のみ）であり、
CI 上での確認は Web UI からの手動実行が要る（IADR-0208 決定 9 の残余リスクに既出）。
