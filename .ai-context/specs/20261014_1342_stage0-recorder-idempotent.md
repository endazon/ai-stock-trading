## 原因（コードで確かめた事実）

1. `Hosted/Stage0RecordingService` は起動ごとに 1 回 `Stage0DecisionRecorder.RunAsync` を呼ぶ。`Enabled=true` で承認値が見積りと一致すれば、**起動のたびに最初から記録し直す**（記録器は過去の実行を知らない）。
2. 承認ゲート（`ValidateApproval`）は 1 回の実行の見積りと承認額の一致だけを見る。実行中の停止（`actualCost > estimate.TotalJpy`）も**その実行の実績だけ**を見る。累計は誰も見ていない。
3. 記録は実行の最後に 1 回だけ `sink.SaveAsync` で書く。途中で落ちると、それまでの費用に対して何も残らない。
4. trade-decision の Pod の volume は `pipeline-config`（ConfigMap・read-only）だけ。values-local の `OutputPath=/tmp/stage0/records.json` は揮発領域。
5. trade-decision は DB を持たない（Program.cs 冒頭「判断はステートレス（DB なし）」）。永続の状態を置ける既存のストアは無い。

## 方針

- 状態は**永続ボリューム上のファイル**に置く（DB を新設しない。trade-decision に DB を足すのは本件の範囲を超える）。置き場は新しい構成 `Stage0Recording:StateDirectory`。**未設定なら記録しない**（`NotConfigured`。揮発領域の状態で記録を走らせない）。
- 完了の印・途中の記録（チェックポイント）・費用の累計の台帳・実行のロックを、その下に別々のファイルで持つ。
- 印の鍵（実行の同一性）は、期間・銘柄集合（並べ替え）・カットオフ・両層のモデル・多数決回数・1 日の判断回数・4 つのトークン量・承認額・承認回数から作る（SHA-256）。書き出し先は含めない（置き場を変えただけで別の実行にしない）。
- 台帳の鍵（承認の単位）は、承認額・承認回数・期間・銘柄集合から作る。**印の鍵とは別に計算し、別のファイルに置く**（片方が壊れても他方で止まる）。
- 上限は承認額（`ApprovedEstimateJpy`）。判断時点ごとに、**呼ぶ前**に「累計＋1 判断時点の見積り」を円未満 2 桁に丸めて承認額を超えるなら止める。呼んだ後に累計が承認額を超えても止める。
- 途中で落ちた実行は、チェックポイントから**途中から再開**する（記録済みの判断時点は LLM を呼ばない）。チェックポイントや印が読めないときは、人が状態のファイルを消すまで走らせない。
- 書き出し先と状態は helm の PVC（既定無効。有効にしたときだけ作る）に置く。

## 窓（規則 11）

窓の両端は「**記録の開始**（開始の印の書き込み）」と「**完了の印の書き込み**」である。その間に費用が出る。

### プローブ

- **増える側（A）**: 2 判断時点のうち 1 つを記録したところで落ち、再起動する。→ 記録済みの判断時点で LLM が呼ばれないこと（二重課金が 0）。
- **増える側（A'）**: 完了した後に再起動する。→ LLM が 0 回。
- **減る側（B）**: 同じく途中で落ち、再起動する。→ 人の操作なしに記録が最後までそろい、完了の印が付くこと（正当な実行が永久に止まらない）。
- **減る側（B'）**: 状態が無い（初回）。→ 記録が走る。

### 形と結果（実測は「実測（変異）」の節）

| 形 | A | A' | B | B' |
| --- | --- | --- | --- | --- |
| 後の端だけを見る（完了の印があれば走らない） | ✗（最初からやり直し・二重課金） | ✓ | ✓ | ✓ |
| 前の端だけを見る（開始の印があれば走らない） | ✓ | ✓ | ✗（人が消すまで止まる） | ✓ |
| **両端を突き合わせる**（開始あり・完了なし＝チェックポイントから再開） | ✓ | ✓ | ✓ | ✓ |

- 両端の形で残る二重課金は、「LLM を呼んでからチェックポイントを書くまで」に落ちた 1 判断時点ぶん（一次 1 回＋多数決回数）だけである。台帳は呼ぶ前に見込みを積む（予約）ので、その分も累計に入り、上限で止まる。

### 規則 10: この変更で新たに誤りになる自分の記述

- 既存の試験の `Options()` 4 か所と `Stage0RecordingLocalProfileTests` は `StateDirectory` を持たない → `NotConfigured` に倒れる。試験側で状態の置き場（メモリ上の偽装）を与える。
- 「超過は最大 1 判断ぶん」（`Stage0DecisionRecorder` のコメント・試験の名前）: 呼ぶ前の見込みの判定が加わるので、通常は超過する前に止まる。上振れ（見積りより重い応答）のときの超過の上限は 1 判断ぶんのまま → コメントを改める。
- 「見積り額を超えたら停止」: 比べる相手が見積り（その実行の実績）から承認額（累計）へ変わる → コメントと状態の理由文を改める。

## レビューでの是正（PR の AI レビュー・2026-10-14）

- 🟡 費用の累計で 1 件目より前に止まった実行が、既存の `records.json` を 0 件の集合で上書きし、`Stopped` の印で固めていた（印だけが消えた・印の鍵だけが変わった組）。0 件で止まった実行は書き出しも印も行わない。書き出し先も件数が減る上書きを拒み、一時ファイル経由で置き換える（M9・M10）。
- 🟡 chart README の再記録の手順に、`records.json` を先に退避するステップを足した。
- 🟢 `saved && (status is …)` に括弧を付けた。`docs/blocked-tasks.md` の上振れの記述を書き分けた。
- gitleaks（`generic-api-key`）の誤検知: 引数名 `runKey` / `ledgerKey` の直後に型名（`Stage0DecisionRecordSet` 等）が並ぶ形を鍵と値の組と読んだ。資格情報ではない。名前を `runId` / `ledgerId`（`Stage0RecordingIdentity.RunId` / `LedgerId`）へ変えて検出されない形にした（allowlist は足さない）。

## 残余

- 落ちた瞬間が「LLM の応答の後・チェックポイントの前」なら、その 1 判断時点は再開時にもう一度呼ぶ（上限 1 判断時点ぶん。台帳は予約で数える）。
- 状態は PVC 1 つに置く。PVC を消せば印も台帳も消える（`helm.sh/resource-policy: keep` で uninstall では消さない）。
- backtest へ渡す経路は従来どおり `kubectl cp`（PVC から取り出す。Pod の再起動では消えない）。backtest の Pod へ同じ PVC を mount するのは本件の範囲外。
