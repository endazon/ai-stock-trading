# 仕様書: 統合 E2E 基盤 Slice D（issue #82・s2s 同期照会 E2E・最終）

> Slice A/B/C（PR #114 / #116）に続く #82 の最終スライス。#117（[IADR-0051](../adr/IADR-0051_service-to-service-auth.md)・
> `ClientCredentialsTokenProvider`/`ServiceTokenHandler`・`trading-service` ロール・`OwnerOrService` 分離）が
> develop マージ済みとなり、**s2s トークン伝播つき同期照会の実コンテナ E2E** に必要な部品が揃った。本作業で
> これを検証し、#82 の全受け入れ条件を満たす。

## 起点となる計画書（トレーサビリティ）

- 起点: issue #82（残スライス）・issue #76（s2s 認証・受け入れ条件4「実コンテナ疎通」に対応）
- 参照: IADR-0051（s2s 認証・#117）・IADR-0050（マルチサービス/認証 E2E）・IADR-0049（E2E 基盤）・platform ADR-0004
- 本 PR で #82 を `Closes`。#76 の実コンテナ疎通も本 E2E で確認（#76 のクローズ可否は報告のみ・勝手に close しない）。

## 目的・背景

#117 は s2s 認証をユニット（fake token エンドポイント・DI 選択・ポリシー分離）で担保し、実 Keycloak 往復の
E2E は #82 に委ねた（IADR-0051 決定6）。本作業で、呼び出し側の実コンポーネント
（`ClientCredentialsTokenProvider`＋`ServiceTokenHandler`）が実 Keycloak から `trading-service` トークンを取得し、
読み取り系同期照会エンドポイントを認証済みで通せることを、実基盤で検証する。

## 対象範囲（Slice D）

- 対象（1 統合テスト・`Category=Integration`）:
  - 実 Keycloak（dev realm・`ai-stock-trading-svc` confidential クライアント＋`trading-service` ロール）＋
    実 PostgreSQL＋実 RabbitMQ を起動。
  - 提供側 Worker（リスク管理・報告書）を実 Keycloak 認証で結線（共有 PostgreSQL・IADR-0050 決定2）。
  - **呼び出し側の実コンポーネント**でトークンを取得: `ClientCredentialsTokenProvider`（client_credentials）で
    `trading-service` トークンを取得し、`ServiceTokenHandler`（DelegatingHandler）で送信要求へ付与する。
  - 検証（読み取り系3エンドポイント）:
    - `GET /risk-controls/open-positions`（RM）: 無トークン→**401** / trading-service→**200**
    - `GET /risk-controls/sizing-context`（RM）: trading-service→**200**
    - `GET /reports/daily-policy`（Report）: 無トークン→**401** / trading-service→**404**（空 DB＝未確定のため。
      401 ではなく 404 になること自体が OwnerOrService 認可を通過してハンドラへ到達したことを示す）
  - 非回帰（最小権限）: 書き込み系（`POST /risk-controls/kill-switch/engage`＝OwnerOnly）を trading-service で
    呼ぶと **403**（サービスロールは書き込み不可）。
- 対象外（引き続き分離）: 実 LLM 前段（#79）・実発注（#13）・実市場データ（#81）。

## 設計方針（要点）

1. E2E は Testcontainers＋in-process Worker（IADR-0049/0050）を踏襲。提供側 Worker は extern alias で参照し
   `Program` 曖昧を回避（発注執行=global・リスク管理/報告書=alias）。
2. 呼び出し側の実トークン取得を忠実に行うため、テストは **実 `ClientCredentialsTokenProvider`** で
   `trading-service` トークンを取得し、**実 `ServiceTokenHandler`** を `WebApplicationFactory.CreateDefaultClient`
   のハンドラに差し込む（トークン取得は実 Keycloak へ実 HTTP、API 呼び出しは in-process トランスポート、
   JWT 検証は提供側が実 Keycloak の OIDC/JWKS で行う）。
3. fail-safe を維持（読み取りのみ・ペーパー相当・書き込みは 403 で非回帰）。`Category=Integration` で
   既定 CI から分離（nightly `integration.yml`）。

## 受け入れ基準（#82 の残・#76 受け入れ条件4）

- [x] `ClientCredentialsTokenProvider`/`ServiceTokenHandler` 経由で実 Keycloak から `trading-service` トークンを
      取得し、読み取り系3エンドポイント（open-positions / sizing-context / daily-policy GET）を認証済みで通せる
- [x] 無トークン→401、trading-service→読み取り系通過（open-positions/sizing-context=200・daily-policy=404＝
      空 DB のため。いずれも認可通過）を実コンテナで確認
- [x] 書き込み系（OwnerOnly）を trading-service で呼ぶと 403（最小権限の非回帰）
- [x] 既定 CI から分離（`Category=Integration`）・実基盤 E2E は nightly

## 検証方法

- ローカル（Docker）: `dotnet test --filter Category=Integration` で Slice D が緑（実 Keycloak/PG/MQ 起動）。
- 既定 CI: `--filter Category!=Integration` で全ユニット緑・E2E 非実行。`dotnet format` 緑。

## 計画書との差異

- 差異なし（IADR-0051 決定6で #82 に委ねられた実 E2E を実装）。
