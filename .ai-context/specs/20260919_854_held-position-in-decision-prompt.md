# 仕様書: 取引判断のプロンプトへ保有状況を載せる（#854）

## 起点

- #854（稼働環境で 2 夜連続の実測）。取引判断が **Buy しか出さない**。5 分周期のサイクルが当日の発注枠を使い切るまで
  買い増しを続け、含み損が拡大しても判断文は「新規買いを検討可能」のままだった。
- 計画 ADR-0003 の決定は **「AI の判断入力は『確定済み日報＋保有ポジション＋収集情報＋過去判断のRAG』に限定」** と
  定めている。**保有ポジションは計画が定めた判断入力であり、実装がそれを渡していなかった**（計画からの欠落。計画の変更ではない）。

## 原因（現物で確認した）

- `TradeDecisionPromptBuilder.Build` / `BuildScreening` が LLM へ渡すのは、方針・現在値（または価格変動）・リスク制約・
  空売りの制約・参考情報だけである。**保有数量・取得単価・含み損益・損切りライン・保護の状態のいずれも無い。**
- 出口の経路は既にある: `Sell` が出れば `PositionEffectResolver.Resolve(side, heldQuantity)` が保有ロングの決済（Close・
  **保有全量**）へ解決する（IADR-0119 決定1）。**欠けているのは LLM への入力だけ**である。
- 損切りの自動執行が効かない構成（S2、および S0 が拒否される moomoo SIMULATE）では、出口は LLM の判断と人手しか無い。

## 値の出所（自分で引いた結果）

| 項目 | 出所 | 取得できないとき |
| --- | --- | --- |
| 保有数量（符号付き）・平均取得単価・記録上の損切りライン | リスク管理の既存 `GET /risk-controls/open-positions`（`OpenPositionView`＝symbol / market / side / quantity / entryPrice / stopLossPrice）。**取引判断は既に `IHeldPositionProvider`（`HttpHeldPositionProvider`・`risk` HttpClient・s2s トークン）でここを引いている**（数量だけを読んでいた） | **不明**（null）。空配列・一覧に無い＝**保有なし**（0）。IADR-0119 決定3 の区別をそのまま使う |
| 含み損益（額・率） | 取引判断が計算する: `(評価価格 − 平均取得単価) × 符号付き数量`。評価価格は**プロンプトに出している現在値と同じ値**（価格変動トリガー＝`trigger.Price`／定時＝`ICurrentPriceProvider` の現在値）。LLM に計算させない（FR-16 と同じ規律） | 現在値が無ければ**不明** |
| 損切りライン到達 | 取引判断が判定する（ロング: 現在値 ≤ ライン／ショート: 現在値 ≥ ライン。市場監視の `StopLossEvaluator` と同じ向き） | 現在値かラインが無ければ**不明** |
| 保護の状態 | **建玉ごとの保護の成否を持つ射影は存在しない**（台帳の承認行は保護レグの決済と判断由来の決済を区別しない。`ProtectiveStopWaived` はリスク管理が購読していない）。供給できるのは**損切りの実行機構の設定**（S0〜S3。`RiskManagementSettings.StopLossMethod`）だけである。これを既存の `GET /risk-controls/sizing-context` へ加法的に足して運ぶ（取引判断が毎判断で既に引いている経路。HTTP 呼び出しは増えない） | **不明**（項目が無い旧応答・照会失敗の安全既定はいずれも null） |

🔴 **保護の状態は「設定」であって「この建玉に逆指値が今効いているか」ではない。** プロンプトはそれを偽らない:
S2 だけは「無保護」と断定でき（保護レグを発注しない）、S0 / S1 / S3 は「その設定である。ただしこの建玉の逆指値が
現在有効かは供給されていない（不明）」と書く。S0 でも保護が失われた建玉は残り得る（#847）。

## 決定（詳細は IADR-0351）

1. **保有状況は既存の 2 つの同期照会から取る。新規エンドポイント・新規イベント・新規構成キーを作らない。**
   - `IHeldPositionProvider` へ `GetPositionAsync`（`HeldPosition?`＝符号付き数量・平均取得単価・損切りライン）を足す。
     `GetSignedQuantityAsync` は残し、同じ取得の数量だけを返す。
   - `SizingContextView` / `SizingContext` へ `StopLossMethod` を末尾に足す（取引判断側は nullable＝未供給は不明）。
2. **プロンプトは「保有あり／保有なし／不明」の 3 状態を必ず書き分ける。** 節は無条件に出す（引数の既定＝不明。
   不在が「保有なし」を意味する形にしない）。不明のときは Hold を選ぶことを明示する。
   コード側の既存の安全網（不明・保有なしの Sell は見送り＝IADR-0119 決定2）は変えない。
3. **保有中の銘柄では、買い増し（Buy）・保有継続（Hold）・手仕舞い（Sell）のいずれかを判断すると明示する。**
   方針（PolicySummary）は一字も書き換えない。**出口の基準の優先順**:
   ① 方針に出口（利確・損切り・保有期間）の基準があればそれに従う。
   ② 方針に出口の基準が無いときは**保有継続（Hold）が既定**。ただし**現在値が記録上の損切りラインに達している建玉は、
      リスク制約（損切りライン）に基づいて手仕舞いを選べる**。損切りラインは FR-04 が判断の枠として並置する
      「リスク制約」の一部（FR-10 の銘柄別損切りライン。建てた時点で判断が決め、台帳が保持する権威データ＝IADR-0035）であり、
      方針の範囲外の行動ではない。
   ③ 買い増しは方針が支持する場合に限る（同じ根拠で新規買いを繰り返さない）。
4. **一次スクリーニングにも短縮版を載せる。** 一次は門であり、Hold を返すと本判断が走らない。保有を知らない一次は
   「新規の関心なし」で損切りライン割れの建玉を落とし得る——**出口の判断が本判断へ届かない**。費用統制のため数行に留める。
5. **手仕舞いの数量は変えない（保有全量）。** IADR-0119 決定1 が既に全量と定めており、LLM は数量を出力しない
   （ADR-0040 決定5・`QuantityIsSystemDecidedRule`）。プロンプトは「保有の全量をシステムが決済する」と事実を述べるだけ。
6. **発注に使う保有数は従来どおり LLM 判断の後に引き直す**（プロンプト用の取得を使い回さない）。LLM 呼び出しの間に
   逆指値が約定し得るため、決済数量は直前の事実で決める。鮮度切れレートの経路だけは従来どおり先読みを再利用する（#506）。
7. **Stage 0 の記録器（`Stage0DecisionRecorder`）は「保有なし」を明示して渡す。** 記録は銘柄 × 判断時点で独立であり、
   保有は再生側のシミュレーションでしか決まらない。既定（不明）のままでは全件 Hold へ倒れ、Stage 0 が成立しない。
   **本番のプロンプトが保有に依存するようになったことで、Stage 0 の記録が「保有なし」の枝しか検証しない**という
   乖離が新たに生じる（IADR-0351「残る制約」。計画への環流候補）。

## 母集合（着手前に引いた）

`grep -rn "TradeDecisionPromptBuilder\.\(Build\|BuildScreening\)("`（テスト以外）:

| 箇所 | 扱い |
| --- | --- |
| `TradeDecisionAppService.cs` `Build`（本判断） | 保有状況・保護の状態を渡す |
| `TradeDecisionAppService.cs` `BuildScreening` ×2（縮退あり／なし） | 同上（短縮版） |
| `Stage0DecisionRecorder.cs` `Build` | `HeldPosition.None` を明示（決定7） |

`IHeldPositionProvider` の実装・偽物: `HttpHeldPositionProvider` / `NoOpHeldPositionProvider` /
`TradeDecisionServiceTests` の `FakeHeld`・`ThrowingHeld`。全て追随する。

`new SizingContext(`（テスト以外）: `PlaceholderProviders.cs`（末尾の既定値つき項目のため無改修＝不明）・
`HttpSizingContextProvider.SafeDefault`（同）。`SizingContextView` の生成は `SizingContextService` の 1 箇所。

`/risk-controls/open-positions` の他の消費者（市場監視 `HttpPositionStore`・報告書 `HttpOpenPositionSource`）は
**触らない**（応答の形を変えない）。`sizing-context` の消費者は取引判断のみ（加法的な項目追加）。

スクリーニングの骨格見積り（`ScreeningContextAssembler`）: 保有状況の短縮版は銘柄側の保護分であるため
`PerSymbolLineChars` を実測ぶん底上げし、これに依存するテストの予算を同幅でずらす（IADR-0297 の先例）。

除外: `docs/`（取引判断のプロンプトを記述する機能仕様書は無い＝FR-04 は必須範囲外。`docs/tests/` に FR-04 系のテスト仕様も無い）。
フロントエンド・通知・監査はプロンプトを扱わない。

## LLM 費用の増分（NFR-13・月次上限 15,000 円）

**実装後にプロンプトの実文字数を測った**（一時的な採取テストで `Build` / `BuildScreening` の出力を書き出して数えた。
採取テストは削除済み。条件: 定時トリガー・AAPL・現在値 217.5・方針 11 文字・参考情報なし。従来のプロンプトは
本判断 1,048 文字・一次 622 文字）。

前提: 単価は `values-local.yaml` の表（本判断 sonnet-5 入力 0.327 円/1k トークン・一次 haiku-4-5 入力 0.164 円/1k）。
換算は**保守側 1.0 トークン/文字**（IADR-0313 決定1 と同じ係数。同 IADR の実測の混在比は約 2.15 文字/トークンであり、
実費はおおよそ半分以下になる見込み）。周期 5 分 × 米国の立会 6.5 時間＝78 サイクル/日 × 21 営業日＝1,638 サイクル/月/銘柄。
**毎サイクル一次と本判断の両方が走り、多数決は 1 回**と仮定する（一次が Hold で打ち切れば本判断ぶんは掛からない。
多数決 N 回なら本判断ぶんが N 倍）。出力トークンは増えない（出力形式は不変）。

| 状態 | 本判断の増分（文字） | 一次の増分（文字） | 1 サイクルの増分（円・保守側） | 月次の増分（円/銘柄・保守側） |
| --- | --- | --- | --- | --- |
| 保有なし | +38 | +38 | 0.019 | 約 31 |
| 不明 | +108 | +108 | 0.053 | 約 87 |
| 保有あり（保護の状態＝S2 の文言） | +477 | +200 | 0.189 | 約 309 |
| 保有あり（同 S0: +19 文字／S1: +37 文字） | +496〜514 | +200 | 0.195〜0.201 | 約 319〜329 |

- **上限は「1 銘柄を 1 か月ずっと保有し続けた場合」で月 約 330 円**＝月次上限 15,000 円の約 2.2%。現行の監視銘柄は 1 銘柄
  （`values-local.yaml` の `TradeCycle__Watchlist__0`）。
- 既存の入力に対する比率: 従来の本判断プロンプトは骨格だけで 1,048 文字、これに方針全文と参考情報（1 件あたり最大
  約 1,160 文字 × TopK 5）が載る。保有ありの +477〜514 文字は参考情報 1 件の半分以下である。
- 間接の効果は見積もらない（保有を知った一次が Hold で打ち切る回数が増えれば費用は減り、手仕舞いの候補として本判断へ
  進める回数が増えれば増える。実 LLM を呼ばない本 PR では測れない）。

| # | 基準 | 検証 |

| 2 | 保有中は買い増し・保有継続・手仕舞いのいずれかを判断すると明示し、手仕舞いは全量をシステムが決めると述べる | 同 |

| 10 | アプリサービスが保有状況を本判断・一次の両プロンプトへ渡す。照会の例外は不明へ縮退する | `TradeDecisionServiceTests` |
| 11 | 保有ロング＋損切りライン割れ＋LLM が Sell → 保有全量の Close が発行される（既存経路の回帰） | 同 |

| 13 | Stage 0 の記録器のプロンプトは「保有なし」で、不明へ倒れない | `Stage0DecisionRecorderTests` |

## 変更しないもの

- 方針（`DailyPolicy.Summary`）・出力 JSON の形・パーサ・多数決・サイジング・`PositionEffectResolver`・決済の数量（全量）。
- リスク管理の `open-positions` の応答・台帳・射影。市場監視・報告書の照会。
- 不明・保有なしでの Sell の見送り、不明での Buy＝Open（IADR-0119 決定2。**保留点**として IADR-0351 に記す）。
