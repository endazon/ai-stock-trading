# 仕様書: ガード適用範囲の裁定の反映

- 機能要求: **FR-19**（取引ガード）／ FR-10（手仕舞い・損切りを止めない共通不変条件）／ FR-11（監査）

## 目的・背景

**3 論点は 2026-08-04 に計画側で裁定済みだが、実装側の文書は「裁定待ち」のまま残っている。** 読んだ担当者が「まだ決まっていない論点」と誤読する。

### 計画側の裁定（ADR-0007 追補・実測）

| ガード | 適用範囲 |
| --- | --- |
| 商品種別（現物 / 信用買い / 空売り） | **新規建て（Open）のみ** |
| 市場別の有効 / 無効 | 全注文 |
| **取引禁止銘柄リスト** | **全注文（手仕舞いにも適用する）** |
| 差金決済防止 | 新規建てのみ |
| 相場操縦とみなされ得る発注パターン | 全注文 |

**論点 2 の裁定は選択肢 A（現状維持＝ロックイン受容）**であり、理由も明記されている —— **インサイダー取引は売付けも対象**であるため、AI が利用者の関知しないタイミングで規制対象銘柄を自動売却する経路を残さない。

**あわせて ADR-0007 は「非対称は意図である」と明示している。**

> ガードごとに適用範囲が異なるのは各ガードの目的が異なるためであり、**揃えるべき不整合ではない**。

### 実装コードは裁定と一致している（着手前に再実測）

`RiskEvaluator` を読んで、5 ガードの `isEntry` 分岐が裁定表と一致することを確認した。**コードの変更は不要である。**

## テスト方針

**当初は「適用範囲は既存テストで固定済み」としてテストを追加しない方針だったが、これは誤りであった**（PR #454 のレビュー指摘）。

実際に確かめると、**禁止銘柄ガードが手仕舞い（Close）を拒否することを固定するテストは存在しなかった** —— `BannedSymbol` 関連のテストはいずれも `Buy`（Open）しか使っていない。対照的に、同じ「全注文」適用の相場操縦ガードには `相場操縦パターンは手仕舞いの注文にも適用する` という Close 専用テストがある。

**本 Runbook が「詰まる原因」として説明している挙動が、テストで固定されていなかった**ことになる。将来 `RiskEvaluator.cs` の禁止銘柄判定へ誤って `isEntry &&` を足しても、既存テストは検知しない。**Runbook を新設するほど重要と位置づけた挙動なら、テストで固定するのが筋である。**

したがって **`禁止銘柄ガードは手仕舞いの注文も拒否する` を追加**した（市場ガードも同型のため併せて固定する）。

**代わりに、取りこぼしを grep で確認する**（#358 で「税は後続」が 5 文書 8 か所に散り、3 度に分けてしか潰せなかった教訓）。**issue が列挙した 5 ファイルを鵜呑みにせず、自分で母集合を引く。**

## 残余リスク

1. **「裁定待ち」の文字列検査は機械化していない。** 計画側で裁定が下りたことに実装側が気付く経路は、人が環流記録を追うことに依存している（`check-feedback-reflux.js` は**未起票**は見るが、**起票済みで裁定が下りた**ことは見ない —— IADR-0170 決定5 が週次 AI 監査へ委ねた観点である）。
2. **Runbook は実機で試していない。** 禁止登録の解除・再登録は画面（SC-02）または API から行うが、**実際に建玉を持った状態での手仕舞いは未検証**である（実弾未開始のため）。
3. **段階別の商品種別強制への波及は #333 待ち。** ADR-0007 追補が求める「段階別強制にも Open のみを適用」は本作業では実施しない。
