# 仕様書: 試験ハーネスの中断と、母集合の規則の置き場所（#888 / #894）

## 起点

- #888 — `node scripts/scripts.test.js` を **Windows ローカル**で走らせると、`scripts.repo.test.js` の
  `setup.sh` 系テストが **soft fail ではなく未捕捉例外**（`spawnSync bash ENOENT`）で終わり、
  **スイート全体がそこで中断**する。以降に定義されたテストは**一度も実行されない**。
  実測で **#884 が足した 22 件は Windows では一度も実行されていなかった**。
- #894 — 「窓（時間差）を扱う是正では増える側・減る側の両方を先に測る」手続きが
  **#820 固有の凍結記録の中にしかない**。あわせて、**規則 9・10 が本リポジトリの
  `traceability.repo.md` に存在しないのに、多数のファイルが番号で引いている**齟齬がある。

## 🔴 なぜこの 2 件を 1 本の PR に束ねたか（グルーピングの根拠）

- **どちらも「検証を信用してよいか」を決める器**である。#888 は「**何が実際に走ったか**」を
  出力から読めるようにする話、#894 は「**何を測ってから是正するか**」を読める場所に置く話であり、
  対象は同じ「作業の妥当性を担保する仕組み」である。プロダクトの振る舞いは 1 ビットも変えない。
- **触るファイルが交差しない。** #888 は `scripts/scripts.test.js` ＋ `scripts.repo.test.js` の
  `setup.sh` ブロック、#894 は `.claude/rules/traceability.repo.md` ＋ `docs/how-to/` の新設別紙。
  同時に出した #886 / #895（`.ai-context/adr/` の索引行と ADR 索引の検査器）・#887（`docs/tests/` と
  テスト ID の検査器）とも重ならない。

  #894 は「是正が自分の鏡像を新設した」が 2 回）。同じ判断基準で入る変更をまとめてレビューできる。

**束ねなかったもの**: #886 / #895（別 PR）・#887（別 PR）。前者は索引行、後者は採番の規約であり、

## 設計

### 1. スイートを中断させない（#888 の本丸）

```js
function ok(name, fn) { try { fn(); } catch (e) { /* 記録して続ける */ } }
```

- `ok()` は例外を捕捉し、**その 1 件を fail として記録して次へ進む**。
- `skip(name, reason)` を足す。**黙って飛ばさず、理由つきで 1 行出す。**
- 末尾で **`総数 / 成功 / 失敗 / skip`** を出す。**失敗が 1 件でもあれば終了コード 1**
  （＝ CI の挙動は変わらない。変わるのは「どこで止まるか」だけである）。
- 失敗の詳細（テスト名とスタック）は**末尾にまとめて再掲**する
  —— 途中に混ざると、後続テストの出力に押し流されて読めない。
- companion へは `{ ok, skip, assert }` を渡す（既存の companion は `skip` を使わなくても動く）。

### 2. `bash` を解決できない環境では skip する（#888 の 2 点目）

`setup.sh` 系テストは `env.PATH` を `toolboxPathSs`（symlink を集めた一時ディレクトリ）で
**上書き**しており、Windows では `/usr/bin/bash` が実在しないため toolbox が空になる。
**呼び出し側が Git Bash を PATH へ足しても解消しない。**

- toolbox に `bash` が揃ったかを**実際に確かめ**、無ければ 4 件を `skip` する。
- 🔴 **`bash -n`（構文チェック）だけは PATH を上書きしない**ため、`bash` が PATH にあれば従来どおり走る。
  こちらは skip の対象にせず、`bash` 自体を解決できないときだけ skip する。
- **skip の理由に「なぜ PATH を上書きしているのか」を書く**（CI の ubuntu イメージが `/usr/bin/dotnet` を
  持つため、PATH を絞らないと自己修復の分岐へ入らない）。読み手が「直せる skip」と誤解しないため。

### 3. 規則 9・10 と「窓を扱う是正」の置き場所（#894）

必読規約へ足す節（**1.5 KB 以内**を上限とする）:

- **規則 9**: 「追随する文書」を記憶で挙げない。**誤りの側の文字列で全文書を走査してから**挙げる。
- **規則 10**: 是正のたびに「この変更で新たに誤りになる自分の記述」を引き直す。
  是正前の語で引いても捕まらない。**導出値は走査ではなく計算し直す。**
- **規則 11（新設）**: **窓（時間差）を扱う是正では、是正の形を決める前に「増える側」と「減る側」の
  両方のプローブを書き、3 通りの形で実測する。この表を出せるまで是正の形を確定しない。**
- 別紙への 1 行参照（破れた実例・3 通りの表・母集合の書き方の実務）。

別紙（`docs/how-to/`）に置くもの: #830 の 3 通りの表・同型 2 回の内訳・規則 9・10 の破れた実例。
🔴 **`docs/` 配下なので、計画 ID・IADR・仕様書名・修飾付き issue 参照は trace ブロックへ入れる。**

### 4. 「別紙にするだけでは効かない」への答え

起票者の但し書き（規則 6 が「規約として書くだけでは守られない」ことを実証済み）に対しては、
**番号を必読規約に実在させること自体が最小の担保**である。

- 番号が実在すれば、**監査が「規則 9 を破っている」と書いたときに読み手が原文へ到達できる**。
  #830 の 12・13 巡目は、まさにここが切れていた。
- **機械検査は置かない。** 「母集合を正しく引いたか」は機械では判定できない
  （規則 1〜8 にも検査器は無い）。**検査器を置けないことを明記する**ほうが、
  置いたふりをするより誠実である（IADR-0377 の残余リスク）。

## テスト方針

`scripts.repo.test.js` へハーネス自体の回帰テストを足す（受け口の既存テストと同じ場所）。
**「中断しないこと」を中断しない形で確かめる**必要があるため、`ok` に相当する薄いスタブではなく
**本物の `ok()` を子プロセスで走らせて出力を読む**形は採らない（自己参照で壊れやすい）。
代わりに `loadCompanionTests` の受け口テストと同じ作法で、**例外を投げるテストを登録した
一時 companion** を読み込ませ、`registered` と失敗件数が期待どおりかを見る。
