## 着手前の実測（原因の特定）

### 1. 伸びの内訳（PR の run の 1/3 抽出。週ごとの中央値。単位は秒）

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

- **Build と Test がそろって約 2 倍になった。** 脚の間の Test の差（中央値 14〜32 秒）は増えていない。
  したがって、**主因は LPT の分配の偏りではない。**

  同じ run の脚の間でも、Build は 56〜96 秒とばらつく（例: run 38069754220 では 57 / 87 / 95 / 95 秒）。
  これはランナーの速さの差である。
- 直近 5 run の脚の Test step は 42〜83 秒である。どのシャードかに一貫して偏ってはいない。

## 決定（対策の選定）

| 候補 | 効果 | 費用 | 採否 |
| --- | --- | --- | --- |
| **A. 脚が担当テストの参照閉包だけをビルドする** | Build 90 秒 → 推定 40〜65 秒。**4 脚すべてに効く** | 分配器へ閉包の計算と被覆の検査を足す。ランナー時間は**減る** | **採る** |
| B. シャード数を 4 → 6〜7 | Test 61 秒 → 推定 40〜45 秒。下限は RiskManagementService.Tests 単独（重みで全体の 20%） | Build は脚ごとに重複するので、**脚を足すほどランナー時間が増える**（1 脚あたり約 100 秒） | 採らない。A の後に Test が支配的になったら再検討する |
| C. LPT の重みを実測で更新する | 脚の間の差（中央値 25 秒）の一部 | 実所要の回収の仕組みが要る（IADR-0257 が射程外とした） | 採らない。偏りは主因ではない（表 1） |
| D. 重いアセンブリの中でテストを分割・並列化する | AuditService.Tests などの単体の所要 | テストコードの改修。計画外の大きな変更になる | 採らない |
| E. 1 回だけビルドして成果物を脚へ配る | Build の重複が 0 になる | 直列の前置き（ビルド 90 秒＋転送）がクリティカルパスに乗る。IADR-0208 決定 12 が消した形に戻る | 採らない |

### 実装（A）

1. `scripts/list-test-projects.js`
   - `projectRefs()` / `closure()`: `ProjectReference` を辿って推移的な閉包を求める。XML コメントは先に剥がす。
   - `--build-slnx <path>`: 閉包を solution の直下へ並べた `.slnx` を書く。
     🔴 **担当テストだけの `.slnx` をビルドしてはならない。** 参照先は「参照としてのビルド」になり、
     Web SDK のサービス本体で `obj/.../staticwebassets.build.json` が作られない。その結果、
     `dotnet publish --no-build` が落ちる（ローカルで実測した）。閉包を直下へ並べると、
     各プロジェクトは従来の `backend.slnx` と同じく「solution の項目」としてビルドされる。
   - `--publish-out <path>`: その脚が publish の乾式実行を担うサービス本体を書く。
     各サービスは、そのサービスを閉包に含む脚のうち、添字の最も小さい脚がちょうど 1 回だけ担う。
   - 🔴 **被覆の検査（fail-loud）**: `backend.slnx` の全プロジェクトと `Services/*/*.csproj` が、
     どれかの脚の閉包に入ることを毎回確かめる。入らないものがあれば、名前を挙げて exit 1 にする。
     **「どの脚でもビルドされない」（＝コンパイルエラーが入っても赤くならない）形を黙って作らない。**
   - 自己試験を 31 件から 43 件へ増やす。
   - `$(` を含む Include と Update= 形式の ProjectReference は解決できないので、exit 1 にする（fail-loud。コーディネーターの指摘 2026-10-12）。
   - Plan shard の出力（`shard.txt` / `publish.txt` / `shard.slnx` / `build.slnx`）は、リポジトリ直下に限って `.gitignore` に入れる。
2. `.github/workflows/ci.yml`（`backend-test`）
   - 新しい step「Plan shard」で、Restore の前に分配を決める。
   - Restore と Build は `build.slnx` に対して行う。Test は従来どおり `shard.slnx` に対して行う。
   - Publish (dry run) は shard 1 だけでなく全脚で行う。各脚は `publish.txt` の分だけを publish する。
   - **matrix（4 本）、`if:`、`needs:`、必須チェック名、Verify report count は変えない。**
3. IADR-0257 へ日付つきの追記をする。`scripts/README.md` の当該行を更新する。

## 結果（PR #1317 の CI 実測。2026-10-12）

比較の基準は、直近の backend PR 15 本（#1284〜#1312）と develop への push 4 本である。
PR 側は、同じ run を 3 回走らせた（attempt 1〜3）。

| 指標 | 変更前 | 変更後（attempt 1 / 2 / 3） |
| --- | --- | --- |
| Build step（脚ごと） | 中央値 90 秒（10/5 の週） | 29〜50 秒（中央値 41） |
| Test step（脚ごと） | 中央値 61 秒 | 44〜76 秒（中央値 56） |
| 最長脚の所要 | 中央値 198 秒（15 PR） | **143 / 156 / 138 秒** |
| 脚の所要の合計（ランナー秒） | 中央値 693 秒 | **515 / 575 / 528 秒**（約 −22%） |
| 課金単位（脚ごとに分へ切り上げ）の合計 | 中央値 14 分 | 12 / 12 / 12 分 |
| run の開始から `build-and-test` 完了まで | develop push 217 / 222 / 236 / 256 秒 | 184 / 210 / 204 秒 |
| check 群の開始から `build-and-test` 完了まで（PR） | 中央値 218 秒（15 PR） | 185 秒（attempt 1。2・3 は再実行のため同じ尺度で測れない） |

- **脚の所要は約 55 秒縮んだ（198 → 約 143 秒）。** これは Build の重複を除いた分である。
- 🔴 **完了オフセットは目安の 160 秒に届いていない。** 残りの差のほとんどは**ランナーの待ち行列**である
  （最後に始まる脚の待ちは 29 / 63 / 55 秒）。待ち行列は変更前の run にもあり（同じ尺度で 15〜75 秒）、本 PR では制御できない。
  脚を増やすと、ジョブが増えて待ち行列が伸びる側へ倒れる。これもシャードを増やさない理由の 1 つである。
- 次の候補（本 PR では作らない）: ① ビルド閉包の大きさを LPT の積み方に入れる
  （閉包の小さい脚 1・2 は Build 29〜44 秒、大きい脚 3・4 は 39〜50 秒）。② Test が支配的になったらシャードを 5 本にする。
- 費用: 本リポジトリは public なので、標準ランナーの分は課金されない。private にした場合の見積もりは、
  脚の合計で 1 run あたり約 −2.5 分（14 → 12 課金単位）である。
