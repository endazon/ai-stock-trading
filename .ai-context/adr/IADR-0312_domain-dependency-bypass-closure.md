# IADR-0312: Domain 依存規律の 2 つの迂回路は既存検査器の拡張で塞ぐ（NsDepCop は導入しない）

## コンテキストと課題

VSA 移送（IADR-0259）で層が**別プロジェクトからフォルダ**へ変わり、`*.Domain.csproj` が 0 本に
なった。csproj 静的解析版の `DomainLayerDependencyTests` は入力集合を失い、IADR-0265 の宣言どおり
退役した（#600）。規律の強制は `DomainSourceDependencyTests`（ソース走査）へ一本化された。

🔴 **一本化そのものは妥当だが、二重化が補っていた弱さがむき出しになった。** 層が別プロジェクト
だった頃は**コンパイラが構造的に防いでいた** 2 つが、フォルダ境界になった時点で検査を素通りする
（フェーズ末監査が違反を注入して実測。注入しても 78/78 緑のまま）。

1. **`global using` 迂回**: Domain **外**のファイル（同一プロジェクト＝同一コンパイル単位）に
   `global using Wolverine;` を置くと、Domain のソースが**非修飾で**外部型を使える。検査 (b) は
   `Domain/` 配下しか走査せず、検査 (c) は本文に `Wolverine` の文字列が現れないと当たらない。
2. **自サービス他層への完全修飾参照**: Domain から
   `RiskManagementService.Infrastructure.Persistence.RiskManagementDbContext` と書くと止まらない。
   検査 (d) は他サービス参照を見る検査であり、**自サービスのルートを設計上除外している**。
   🔴 `using` 形なら検査 (b) が止める —— **書き方によって止まったり止まらなかったりする**のが問題である。

**実ツリーの違反は 0 件**であり、両経路とも注入実験でのみ再現する（実測。#601 記載どおり）。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | #601 の記録のまま据え置く（「検査器の追加は同型事故 2 回から」） | ❌ 規約の趣旨は**新しい規律**を足すときの歯止めである。ここで問題なのは**既存の規律が書き方次第で効かない**ことであり、これは欠陥である。据え置くと「規律を定めた」と「規律が働いている」が読み分けられない |
| B | NsDepCop を入れ、名前空間依存を**ビルドエラー**にする | ❌ IADR-0259 で検討して撤回済み（依存方向は自前検査器のみで強制する）。覆すには改定 IADR が要り、**本件の穴を塞ぐ範囲を大きく超える** |
| C | Domain を再び別プロジェクトへ戻す（コンパイラで防ぐ） | ❌ VSA 移送（IADR-0259）を巻き戻すことになる。得られるのは 2 経路の閉鎖のみで、代償が釣り合わない |
| **D（採用）** | **既存検査器の母集合と照合器を広げ、2 経路だけを塞ぐ** | ✅ 規律・許可リスト（規約の単一情報源）は変えず、**見ていなかった場所を見るようにするだけ**である。実ツリーの違反は 0 件のまま緑になる |

## 決定

### 決定 1: `global using` は**コンパイル単位（サービス）全体**から拾い、Domain の許可リストに掛ける（検査 (f)）

- 母集合を `backend/Services/<Svc>/` 配下の `.cs` へ広げる（`ServiceCompilationArea`）。
  除外は **`Tests/`**（別プロジェクト＝別コンパイル単位であり Domain の名前解決に影響しない。
  実測: `Tests/` へ `global using Wolverine;` を注入しても緑）・`bin/` `obj/`・`*.g.cs`
  （`ImplicitUsings` が吐く `GlobalUsings.g.cs` を拾うと `global using System;` 等で無意味に赤くなる）。
- 拾うのは **`global using` 行だけ**である。Domain 外の通常の `using` はそのファイルにしか効かない。
- 判定は既存の `IsAllowedDomainNamespace` を**そのまま**使う（許可リストの単一情報源を増やさない）。
- 適用するのは **Domain のソースを同一コンパイル単位に持つサービスだけ**である。Domain を 1 ファイルも
  持たないサービス（実測: `ConfigurationService`。IADR-0264 で空になった）には守るべき Domain が無く、
  `global using` を禁じる根拠が無い。**Domain が生えれば自動で対象へ戻る**（一覧を手で持たない）。

### 決定 2: 自サービスの `.Domain` 以外の層への完全修飾参照を禁止トークンにする（検査 (e)）

- 禁止トークンは `<自サービスのルート>.<層セグメント>`。**層セグメントは実ツリーのフォルダ名から導く**
  （`Common` / `Features` / `Hosted` / `Infrastructure` / `Tests`。`Domain` だけ除く）。
  手書きの拒否リストにしない —— 次に足された層フォルダが素通りするからである
  （検査 (c) が CPM とリポジトリ内の実 import から導いているのと同じ作法）。
  この導出は**フォルダ名＝名前空間の第 2 セグメント**という IADR-0261 の一致に乗っている。
- 照合は既存の `ContainsQualifiedNameRoot` を再利用する（直前が `.`／識別子文字でない・直後が `.`）。
- 🔴 **コメントと文字列リテラルを取り除いた本文で照合する**（`StripCommentsAndStringLiterals`）。
  Domain のコメントには層の名前が地の文で現れ得る（「永続化は Infrastructure 側で解決する」）。
  **除去するのは本検査だけ**であり、検査 (c) はコメントも見る既存挙動のままにした（**弱めない**）。
- これで `using` 形（検査 (b)）と完全修飾形（検査 (e)）の**どちらで書いても止まる**。

### 決定 3: NsDepCop は導入しない

IADR-0259 の撤回を維持する。本件は**既存検査器の穴の閉鎖**であり、ビルド時強制という新しい機構を
持ち込む根拠にはならない。導入するには改定 IADR が要る（この条件を書き残すこと自体が、
「穴が塞がったから検討しなくてよい」と読まれないための担保である）。

### 決定 4: 「検査器の追加は同型事故 2 回から」との関係を明示する

CLAUDE.md（正本は計画リポの運用ガイド §8）は「検査器・規約の追加は**同型事故 2 回から**」と定める。
**本件はこれに当たらない。** 規約が歯止めを掛けているのは**新しい規律を足す**ことであり、
本件が足したのは規律ではなく**既存の規律（platform ADR-0030 §基本方針・IADR-0128 決定 6）の
検査母集合**である。**「規律を定めた」と「規律が働いている」を同じ検査器の中で読み分けられない状態**は
欠陥であり、事故の回数を待つ対象ではない。

- 実際、#601 は「1 回目なので記録に留める」と判断していたが、**その判断が守っていたのは規律ではなく
  検査器の行数**である。塞ぐコストは実測で 3 ファイルの拡張＋1 ファイルの新設に収まった。
- **新しい規律を足したくなったときは、引き続き 2 回目を待つ。**

### 決定 5: 新しい母集合にも下限（fail-loud）を置く

| 定数 | 値 | 着手時点の実測 |
| --- | --- | --- |
| `MinimumServiceCompilationSourceFiles` | 700 | 768（Domain を持つ 10 サービスの `Tests/` 以外の `.cs`。全 11 サービスでは 791） |
| `MinimumCrossLayerTokens` | 30 | 44（10 サービス × 直下の層フォルダ − `Domain`） |

🔴 **`global using` の「本数」に下限は置けない** —— 実ツリーは **0 本**であり、「無い」と
「解析器が壊れて拾えない」を件数では区別できない。**下限はファイル数に置き**、解析器が
load-bearing であることは陽性対照のユニットテストで固定した（この非対称を明示しておかないと、
次の担当者が「件数の下限が無い＝検査が弱い」と誤読するか、逆に 0 本を下限にして無意味な検査を足す）。

## 影響

- **本番コードは 1 行も変わらない**（検査器のみ）。実ツリーの違反は (e)(f) とも **0 件**。
- テスト件数: `AiStockTrading.Architecture.Tests` **合格 86 → 110**（総数 87 → 111。skip 1 は不変）。
  〔注〕この数値は本作業（#601）着手時点のスナップショットである。同じ PR #713 に同居する他作業
  （#705 の `KnowledgeTagVocabularyTests` 等）と上記追記の補間文字列テストで、PR 全体では合格 121 まで増えている。
- 注入実験（変異試験）で load-bearing を実測した:
  - `global using Wolverine;` を Features のファイルへ → **失敗 1 / 合格 109**。
  - 完全修飾 `RiskManagementService.Infrastructure.Persistence.RiskManagementDbContext` を Domain へ
    → **失敗 1 / 合格 109**。
  - 同じ参照を**コメントとして**書くと → **緑**（誤検出しない）。
  - `Tests/` 配下の `global using` → **緑**（除外どおり）。
  - いずれも実験後に復元し、緑を再確認した。

## 残余リスク

- **ソース走査はコンパイラより弱いままである。** ソースジェネレータの生成参照は `obj/` にしか現れず、
  母集合に入らない（`bin/` `obj/` を除外しているため）。ここを見るには決定 3 を覆す必要がある。
- **文字列リテラルを除去したため、リフレクションで層をまたぐ書き方**（型名を文字列で持つ）は
  検出できない。〔2026-09-09 追記・PR #713 の AI レビュー指摘〕**補間文字列の穴（`$"{X.Y}"` の `{…}`）は
  コンパイル時に評価される実コードであり、リテラルと同列に落とすと検査 (e) の迂回路になる**ため、
  `StripCommentsAndStringLiterals` は穴の中身をコードとして残すよう改めた（`{{`/`}}` のエスケープは
  リテラルとして落とす。肯定形・否定形のユニットテストで固定。合格 110 → 116）。
  リフレクション（型名を文字列で持つ）だけが引き続き未検出の経路である。Domain に実例は無く、止めたい対象（コンパイル時の依存）とも異なるため許容する。
  **実例が 1 件でも現れたら #601 の後継 issue へ記録する**（コメント除去だけ残して文字列は見る、
  という非対称へ倒せる）。
- **層フォルダ名から導く以上、層を表さないフォルダを直下に作ると禁止トークンが増える。**
  例えば `Docs/` を `Services/<Svc>/` 直下に置くと `<Svc>Service.Docs` が禁止トークンになる（実害は
  無いが、失敗メッセージが読みにくくなる）。**層はフォルダで表す**という VSA の前提（IADR-0259）が
  崩れたら、この導出も見直す。
