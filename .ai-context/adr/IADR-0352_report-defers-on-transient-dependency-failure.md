## コンテキストと課題

ホスト再起動の直後、report-service は Keycloak（60 秒前に再起動）からサービストークンを取得できず、
**認証なしで送信して 401 → 未供給**へ倒れた。建玉・OpenD 稼働率・運用段階が未供給、散文はプレースホルダになった。

値を騙らない倒れ方（「建玉なし」「稼働率 0%」と書かない）は設計どおりで正しい。問題は 3 つある。

1. **倒れたまま報告書が出来上がる。** 自動生成は PeriodKey の行が出来た時点でその期間を終える（IADR-0115 決定3）。
   数分待てば揃う入力を欠いた報告書が承認待ちに並び、以後は作り直されない。
2. **欠落が提示の時点で見えない。** 本文は節ごとに「照会できませんでした」と書くが、Discord の提示通知は
   数値と散文の要約だけを運び、`/report show` は版番号だけを返す。利用者は欠落を知らないまま確定でき、
   確定された日報の方針は翌日の取引に効く（ADR-0003 が人の確定を関門にしている意味が薄れる）。
3. **トークンを取れない要求を認証なしで送っている。** 結果の分かっている 401 を上流へ投げるうえ、
   「依存先がまだ起動していない」が「認可を拒否された」に化ける——前者は待てば直り、後者は待っても直らない。

## 検討した選択肢

### A. 失敗の理由をどこで掴むか

- **A-1 各供給元（Http*Source 11 本）のポートを `T?` から結果型へ変える**: 明示的だが、供給元ごとに 4 分岐
  （非 2xx・不正応答・タイムアウト・例外）× 11 本を書き換え、既存テストも全部動く。分類規則が 11 か所に散る。
- **A-2 HTTP の鎖で 1 か所で分類し、生成 1 回ぶんの観測へ記録する（採用）**: 供給元の契約（不達は null）を変えない。
  約定（不達でも空列へ倒れる）の欠落も同じ仕組みで分かる。代償は AsyncLocal での受け渡し（供給元は singleton・
  生成器は scoped で、引数で渡す経路が無い）。

### B. 「認証なしで送らない」をどこで直すか

- **B-1 共有の `ServiceTokenHandler` を直す**: 欠陥の所在には素直だが、消費側は報告書のほかに 5 サービス
  （CostControl・InformationCollection・MarketMonitor・TradeDecision・Notification）と共有 KB クライアントに及ぶ
  （仕様書の母集合 A5〜A7）。
- **B-2 報告書サービスの鎖にだけ門を足す（採用）**: 理由は決定 6。

### C. 再試行をどこで回すか

- **C-1 供給元の中で数秒間隔の再試行**（Wolverine の 2s/10s/30s・`GrpcAssumptionsClient` の試行回数と同型）:
  Keycloak の起動は 60 秒を超えており、秒単位の再試行では届かない。供給元 11 本が各々待つと 1 巡回が分単位で延びる。
- **C-2 常駐の巡回に任せ、見送った期間は行を作らない（採用）**: 既存の冪等（PeriodKey の不在）がそのまま再試行になる。
  新しい状態は「期間ごとの見送り回数」だけで済む。

## 決定

### 1. 門: サービストークンを取得できない要求は送信しない（報告書サービスの鎖でだけ）

`risk-ledger` / `audit-ledger` / `report-llm` の名前付き HttpClient の**最外**に `ReportDependencyHandler` を挿す
（`AddReportDependencyGate`。`AddHttpMessageHandler` は呼んだ順に外側から並ぶため、トークン付与より前に呼ぶ）。

- トークンが有効な構成で取得できなければ、**送信せず** `ServiceTokenUnavailableException`（`HttpRequestException` 派生）を
  投げる。供給元は既存の `catch (Exception)` で未供給へ倒れる（契約不変）。
- 取得できたときは本ハンドラが `Authorization` を付ける。内側の共有 `ServiceTokenHandler` は既存の
  `Authorization` を尊重するため二重取得しない。
- **資格情報が未整備の構成では素通し**（供給元が null / `NoServiceAccessTokenProvider`）。未整備は「取得に失敗した」
  ではなく、認証なしで動かす dev・単体実行の構成である。
- `report-llm`（MSP レルム）の供給元は `LlmGateway:Auth` から作り、**キー付き singleton** で持つ。キー無しで DI へ
  登録すると AST レルムの `IServiceAccessTokenProvider` と衝突し、レルムを跨いでトークンが漏れる（IADR-0323 決定1）。

### 2. 観測: 失敗を「待てば直り得る」と「待っても直らない」に分ける

同じハンドラが失敗を分類し、`ReportDependencyProbe`（生成 1 回ぶんの観測・AsyncLocal）へ記録する。
生成器は取りに行く入力を `Enter` で宣言してから供給元を呼ぶ（逐次に呼ぶので、失敗がどの入力のものかが定まる）。

| 失敗 | 分類 |
| --- | --- |
| サービストークンを取得できない（送信していない） | 一過性 |
| 接続できない（`HttpRequestException`） | 一過性 |
| タイムアウト | 一過性。**ただし LLM は恒常扱い**（モデルの所要時間であり、繰り返せば費用だけが増える・IADR-0123） |
| 5xx・408・429 | 一過性 |
| **401**（トークンを付けて拒否された） | **一過性**（［2026-09-19 追記 / #866］。下の実測） |
| **403**・その他の 4xx | **恒常**（ロール未付与などの設定誤りであり、待っても直らない） |

考え方は `GrpcAssumptionsClient.IsRetryable`（Unavailable / DeadlineExceeded だけを再試行し、Unauthenticated /
PermissionDenied は即座に倒す）と同じである。観測が開かれていない経路（手動の API など）では何も記録しない。

［2026-09-19 追記 / #866］**401 は恒常から一過性へ移した。** 当初は「トークンを付けて拒否されたのだから設定誤り」と
分類していたが、監査がプローブで**上流側の回復の遅れ**を実測した。上流の JwtBearer は IdentityModel の
設定取得器（8.0.1）で OIDC メタデータを引くが、起動時に取得へ失敗すると**バックオフが掛かる**。

```
t=59.6s metadata fetch attempt #9 (up=False)
--- t=70.1s keycloak comes up ---
t=94.6s metadata fetch attempt #10 (up=True)
validator recovered (24.6s after keycloak came up; every token-bearing request in between = 401)
```

**Keycloak が戻ってから 24.6 秒間、上流は正しいトークンでも 401 を返した。** report-service 側が先にトークンを
取れるようになる（＝門が開く）ため、この窓は #840 の再起動直後にそのまま重なる。恒常のままだと、
「待てば直る 401」で縮退した報告書が確定まで進む——#840 で直したかった事故が条件付きで再発する。

**403 は恒常のまま残す。** ロール未付与・クライアント設定の誤りは待っても直らず、一過性に入れると
「沈黙せず縮退した報告書を出す」までの時間が伸びるだけになる（401 と 403 を分けるのが本追記の眼目である）。
費用は保留点②（client secret 誤りでも上限まで見送る＝既定で最大 12.5 分の遅れ）で受容済みのものと同じであり、
新たな種類の費用は生まない（401 を返す要求は上流の認可で止まっており、LLM ではモデル課金の前である）。

### 3. 見送りと再試行: 巡回に乗せ、次の巡回を早める

生成器は「**その種別が使う入力が未供給**」かつ「**その入力の取得中に一過性の失敗を観測した**」とき、その期間を
**保存も提示も通知もせず**見送る（`ReportAutoGenerationResult.Deferred`）。

- 入力を集めた直後・**散文（LLM）を呼ぶ前**に判定する（見送る回の散文は捨てるしかなく、費用を出さない）。
  散文がプレースホルダへ倒れ、LLM への要求で一過性の失敗を観測していれば、そこでも見送る。
- 見送り回数は `ReportGenerationDeferralTracker`（singleton・プロセス内）が期間ごとに数える。**上限は既定 5 回**
  （`Reports:AutoGeneration:DependencyRetryMaxAttempts`。0＝見送らない＝本変更前の挙動。負値は既定へ）。
- 常駐は見送った期間があるとき**次の巡回を早める**: 30 秒 → 60 → 120 → 240 → …（基準は
  `DependencyRetryBaseSeconds`・既定 30）。**通常の巡回間隔（既定 300 秒）を超えない**——見送ったせいで通常より遅くなる
  向きへは倒さない。既定では最大 12.5 分待つ。
- 見送った巡回は常駐が**警告**を残す（欠ける入力・原因・何回目か・次に試すまでの秒数）。
- 🔴 **［2026-09-19 追記 / #866］見送りが「その期間が生成対象である窓」の終端を跨ぐなら、見送らない。**
  `ReportSchedule.Due` は月報を**当月内**・週報を**当 ISO 週内**でしか due にしない。月報の窓は
  「最終営業日 17:00 JST 〜 月末 24:00 JST」であり、**最短で 7 時間**（最終営業日が月末日のとき）しかない。
  見送っている間に窓が閉じると、その期間は**二度と due にならず**、上限 5 回が効く前に対象から外れる
  ——縮退版すら出ず、上限到達の警告も提示通知も出ない（**無音で永久に出ない**）。本変更前は同じ時刻に
  縮退した報告書が生成・提示されていたので、これは**退行**である。月報は方針連鎖の最上位であり、
  欠けると「上位方針が空の週報が確定される」（#839）と同じ状態を誘発する。
  よって生成器は、**次に試す時刻（`clock.UtcNow + 次の待ち時間`）にその PeriodKey がまだ `Due` に含まれるか**を
  確かめ、含まれなければ見送らずに決定 4 の縮退版を出す（待ち時間は回数を消費せずに先読みする）。

### 4. 上限到達・恒常的な失敗: 縮退した報告書を出し、警告を残す

- 上限に達したら見送らず、**縮退した報告書を従来どおり生成・提示する**。依存先が戻らないまま報告書が永久に出ない
  状態は作らない（提示されなければ利用者は異常に気付けない）。
- 恒常的な失敗（403。［2026-09-19 改訂 / #866］**401 はここから外した**）・未設定（`Unsupplied*`）による
  欠落は見送らない（待っても変わらない）。
  その巡回で縮退した報告書が出る＝本変更前と同じ速さである。
- ［2026-09-19 追記 / #866］**次の試行時刻に窓が閉じている場合も同じ扱いにする**（決定 3 の追記）。
  常駐は「上限に達した」とは別の文言で警告する（原因が違うものを同じ文にしない）。
- いずれの場合も常駐が**警告**を残す（どの入力が欠けたまま提示されたか・上限到達か窓の終端かどうか）。沈黙しない。
- ［2026-09-19 追記 / #866］**見送り回数の後始末**: 生成できた期間（縮退の有無を問わない）で捨てるのは従来どおりだが、
  **窓が閉じて対象から外れた期間の回数も 1 巡回の終わりに捨てる**（`RetainOnly`）。捨てないとプロセス内に
  永久に残る（その PeriodKey は二度と due にならないため、生成による解放が起きない）。

### 5. 見せ方: 未供給だった入力を記録し、確定の前に見せる

- 語彙は `ReportInput`（12 語）。**その種別が実際に使う入力だけ**を数える（`ReportInputs.AppliesTo`。週報は建玉を
  描かないので、建玉の欠落を週報の警告に混ぜない）。Stage 0 の見積り承認額は構成値であり、未設定が通常のため数えない。
- 記録は `reports.UnsuppliedInputs`（新列・列挙名のカンマ区切り・NULL＝なし。Migration `AddReportUnsuppliedInputs`）。
  **記録は本文に従う**——本文を差し替えない改訂（手動 upsert）では記録も残し、確定しても残る。
- **提示通知**: `ReportSummary.Build` が数値行の直後・散文より前に警告行を足す（上限で詰められるのは散文側）。
  `ReportDraftPresented` の契約は変えない。
  🔴 **［2026-09-19 追記 / #866］未供給の入力があるドラフトの提示は `NotificationSeverity.Warning` で出す**
  （未供給が無ければ従来どおり `Info`）。警告文が本文に入っていても、重大度が `Info` のままでは
  他の定常通知に埋もれる——**埋もれない経路で出す**のは `LlmFallbackFired`（ADR-0017 決定4-(2)）で既に採っている形である。
  判定は要約に含まれる警告行の印（`ReportSummaryMarkers.UnsuppliedWarningPrefix`・`Shared.Contracts` の定数）で行い、
  **イベントの形は変えない**（通知サービスは報告書サービスの型を参照できず、契約を増やすと旧版の発行側と
  読み分けが要る。印は発行側・消費側が同じ定数を引く）。
- **`/report show` と版番号なしの `/report approve`（確認ボタンの前段）**: `GET /reports/{periodKey}/review` の応答へ
  `unsuppliedInputs`（表示名の配列）を足し、通知サービスが警告を併記する。返すのは**コード定数の表示名**であり、
  報告書の本文・要約ではない（IADR-0240 決定4 に反しない）。通知サービスは別プロセスから届いた文字列として
  無害化する（制御文字・メンション構文・長さと件数の上限）。
- **確定を機械的に拒否はしない。** 縮退した報告書でも利用者が「これでよい」と判断する余地を残す
  （上限到達の後は、確定しない限り方針が更新されない）。

### 6. 共有の `ServiceTokenHandler` は直さない（報告書サービスに閉じる）

波及を全部確認したうえで、共有側の**挙動は変えない**。

- 共有の契約「取得不能なら null → 資格情報を付けずに送る → 上流が拒否 → 呼び出し元の fail-safe」は
  REST（IADR-0051 決定2）と gRPC（IADR-0328 決定2）で**同じ向きに揃えてある**。REST のハンドラだけを
  「送らない」に変えると輸送で縮退の向きが割れ、gRPC も変えるなら `CallCredentials` の中で例外を投げることになり、
  gRPC を使う呼び出し元すべてで例外の形（`RpcException` の状態）を検証し直す必要がある。
- 他サービスの倒れ先は**巡回ごとに評価し直される値**（残枠 0・既知の前提条件・ゲート）であり、依存先が戻れば
  次の巡回で自然に回復する。無駄な 401 は雑音に留まる。**報告書だけが「一度出来上がったら作り直されない成果物」**であり、
  一過性の失敗が恒久的な欠落として残る。直す価値があるのはここである。
- ただし共有の `ClientCredentialsTokenProvider` の**ログ文言だけ**は直す（「認証なしで送信し安全既定に倒します」→
  「トークンなしで続行します（要求の扱いは呼び出し側に従います）」）。供給元は送信の有無を知らないのに断言しており、
  送信しなくなった報告書サービスのログに事実と違う行が残るためである。挙動は 1 行も変えていない。

## 理由

- 再試行の仕組みを新設せず、既存の冪等（行が無ければ次の巡回で対象になる）へ乗せるのが最も壊れにくい。
- 失敗の分類を 1 か所に置くことで、供給元を足しても規則が割れない（名前付き HttpClient に乗れば自動で掛かる）。
- 「待っても直らない失敗で待たない」を守ることで、設定誤りのときに警告と縮退した報告書が出るまでの時間を
  本変更前と同じに保てる（沈黙の時間を延ばさない）。

## 結果・残余リスク（保留）

- **gRPC の LLM 経路（`LlmGateway:Grpc`）には門も観測も掛からない。** チャネルは HttpClientFactory の鎖を通らない。
  現行の配備は REST であり（helm の該当行はコメントアウト）、gRPC を有効にする時点で `CallCredentials` 側の扱いを
  決める必要がある（決定 6 の理由により共有側の検討になる）。それまで gRPC 経路は本変更前と同じ挙動である。
- **トークン取得失敗の細分はしていない。** Keycloak が落ちている（一過性）のか、client secret が違う（恒常）のかを
  供給元は区別して返さない（null とログだけ）。後者でも上限まで見送ってから縮退する（既定で最大 12.5 分の遅れ）。
  区別するには共有の供給元の契約を広げる必要がある。
- ~~**上流の 401 が一過性であり得る窓がある。**~~ ［2026-09-19 改訂 / #866］**実測した結果、恒常の分類を取り下げた**
  （決定 2 の追記）。上流の設定取得器はバックオフを持ち、**Keycloak 回復から 24.6 秒は正しいトークンでも 401** だった。
  401 は一過性に入れ、403 だけを恒常に残す。残るリスクは「ロール未付与に 401 を返す上流」があった場合に
  上限まで見送ってから縮退することだが、MSP のレルム構成では未付与は 403 である。
- ［2026-09-19 追記 / #866］**ゲートウェイ側の 504 / 502 は一過性として最大 5 回再試行される。**
  LLM ゲートウェイ（またはその手前のプロキシ）がモデルへ要求を投げた**後**に 5xx を返す構成だと、
  見送り 1 回ごとにモデル課金だけが積み上がり得る（本 PR の巡回では、散文は入力が揃ってから 1 回だけ呼ぶため
  1 巡回あたり 1 回だが、見送りの回数ぶん繰り返される）。現行のゲートウェイは受理前に落ちる形しか実測して
  いないため受容する。**429 の `Retry-After` は見ていない**（倍々の待ち時間で近似する。上流が指定した
  待ち時間より短く再試行し得るが、上限 5 回・最大 12.5 分の枠に収まる）。

- **見送り回数はプロセス内**であり、再起動で 0 に戻る（上限は再び効く）。多重レプリカでは各々が数える。
