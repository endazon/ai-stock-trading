# IADR-0428: 保護レグの「届いたか不明」は据え置き、突合で確定したエントリーに保護レグを張る

- 状態: Accepted
- 日付: 2026-09-25
- 決定者: claude（起票 #853。オーナー裁定 2026-09-25「据え置き・予約・保護レグを張る」を実装する）

## コンテキストと課題

`OrderExecutionAppService.PlaceProtectiveStopAsync`（エントリー同時）と `ProtectiveStopGuard.ReplaceOrCloseAsync`（失効後の再発注）は、
逆指値の発注例外を**種類を見ずに**「未受理」と同じ分岐（エントリーの取消・成行手仕舞い）へ落としていた。IADR-0117 改定 6 が
「送信後に結果を確認できない」を `BrokerDispatchIndeterminateException` にしてからも、逆指値のレグだけはこの分岐のままだった。

- **孤立**（#853 の 1）: 逆指値が実は証券会社で生きていれば、取消・成行で建玉だけが消えて逆指値が残る。発火すれば反対方向の建玉（ショート）。
- **重複**（2026-09-19 の追記）: ガードで成行も確実に未発注で終わると、記録が `Active` のまま残り、次の巡回が同じ `StopDecisionId` の
  逆指値をもう一度送る（3 巡回で 1→2→3。決定的な ID はあるが予約が無い）。
- **無保護の確定**（#853 の 2）: `OrderReservationReconciler` は突合で `Placed` と確定したエントリーに保護レグを張らない（IADR-0362 決定 3 が
  「見えるようにするだけ」とした）。

## 検討した選択肢

1. **据え置き**（成行へ倒さず、照会で確定するまで待つ）— 裁定で採る。
2. 不明でも従来どおり成行・取消へ倒す — 孤立の害（反対建玉・損失の上限なし）が不可逆。採らない（裁定）。
3. 不明のときガードから直接照会（remark）して即時に解決する — 照会の重複実装と OpenD の照会頻度制限を抱える。
   既存の突合（配備で有効）に委ねる（残余リスクに記録）。

## 決定

### 決定 1: 逆指値レグも予約 → 発注 → 確定の 3 相で送り、例外を種類で分ける

エントリー同時とガードの両方で、送る前に決定的な `StopDecisionId` を予約する（`IOrderReservationStore.TryReserve`）。

| 結果 | 予約 | 以降 |
| --- | --- | --- |
| 受理 | 記録を保存してから確定（注文 ID つき） | 従来どおり |
| 確認できた拒否（終端が返った）・`BrokerUnavailableException` | **解放** | 従来どおり（取消・成行へ） |
| `BrokerDispatchIndeterminateException`・分類できない例外 | **Reserved のまま** | **据え置き**（取消も成行もしない） |
| 予約が取れない | 触らない | 据え置き（送らない） |

分類できない例外を不明側へ倒すのは IADR-0117 改定 7（成行手仕舞い）と同じ規律である。確実に未発注が続くときの再試行
（ガードが巡回ごとに同じレグを送り直す）は変えない——送っていないものは送り直してよい。S3 の試行の記録（`AlternativeProtectiveStopAttempted`）は、
不明のときには出さない（状態の無い失敗を「拒否」として監査台帳へ残さない）。

### 決定 2: 据え置きは「送信結果待ち」の保護記録で表し、ガードが突合の結果で解決する

- 保護記録を `Active`・注文 ID が空・`StopDecisionId`＝据え置いたレグ・`Attempt`＝その試行で残す（`ProtectiveStopOrder.IsStopDispatchPending`）。
- ガードは送信結果待ちの行について、(1) 発注結果の記録があれば注文 ID を採用し（生きていれば `ProtectiveStopPlaced`、生きていなければ通常の失効として次の試行へ）、
  (2) 記録が無く予約があれば**据え置く**——**建玉が消えていても記録を完了させない**（逆指値が生きていれば孤立する）、
  (3) 記録も予約も無ければ（突合の門を開けて解放された・人が解放した）確実に未発注として通常の失効と同じに扱う。
- 可視化: `ProtectiveStopRemediation.StopDispatchIndeterminate`（末尾）。`CloseDecisionId`／`CloseIntent` は**逆指値レグ**を運ぶ。
  通知は Critical（「送信した・届いたか不明・取消も成行も重ねない・証券会社の画面で逆指値の有無を確かめ、無ければ手で置くか手仕舞う」）。
  据え置きが続くあいだ 1 時間ごと（と再起動後の最初の巡回）にガードが出し直す（`HeldCloseNotificationTracker` を共用・キーは逆指値レグ）。
  エントリー同時の経路はガードの記憶へ書かない（発行の補償が無いため。ガードの最初の巡回が 1 回重ねるが、黙るより重なる側へ倒す）。
- 取引台帳は `CloseIntent` を**逆指値の武装と同じ由来（`ProtectiveStopS0`）**で承認行にする。生きていて約定すれば相関でき、
  損切りの成立として数えられる（IADR-0394 決定 1）。後着の `ProtectiveStopPlaced` は DecisionId で冪等に 1 行のまま。

### 決定 3: 承認時の保護の文脈を送る前に残す（`ProtectiveStopState.AwaitingEntry`）

S0（未知の手法の S0 扱いを含む）・S3 の新規建ては、エントリーの予約を取った後・送る前に保護記録を `AwaitingEntry`（整数列の値 2。Migration 不要）で残す。
巡回・約定追跡・純額の計算は `Active` しか読まないので、この行は見られない。受理・据え置きで `Active` に上書きし、見送り（接続不能）・
エントリーの終端失敗・保護の失敗（取消・成行）で `Completed` にする。書けなかったら Error を残して発注は続ける。S1（エントリー前に `Active` で武装済み）・
S2（記録を作らない）は従来どおり。予約を取った**後**に書くのは、同じ承認の並行配送（予約を取れない側）が先に張られた保護記録を上書きしないためである。

### 決定 4: 突合で確定したエントリーに承認時の手法で保護レグを張る（`IReconciledEntryProtection`）

- 口は `IReconciledEntryProtection`。実体は `OrderExecutionAppService.ProtectAsync`（平常の経路と同じ `PlaceProtectiveStopAsync` を通す）。
  Program.cs が突合（`OrderReservationReconciler`）へ明示して渡す（T-10-1073 が本番の組み立てで固定する）。
- 突合は確定した 1 件の出口（`EmitAsync`）の**後**に呼び、結果を新しい出口 `EmitProtectionAsync` で記録・発行する（IADR-0371 の「確定済みの 1 件の出口を失わない」を保つ）。
  取消トークンは渡さない（確定後の後始末。送信の途中で打ち切ると「予約だけがあり記録が無い」逆指値を自分で作る）。
  呼ぶのは突合の `Placed`（競合なし）と phase-4 自己修復。競合（通常フローが確定中）では呼ばない。
- エントリーかどうかは**保護記録の有無**で判別する（IADR-0362 決定 3: 予約・プローブの `PositionEffect` は当てにならない）。
  `AwaitingEntry`（S0 / S3）→ 生きていれば承認数量で張る・終端で約定ありは約定数量・約定 0 なら文脈を閉じる。`Active` の S1 → 配置の事実（`SoftwareStopArmed`）だけ。
  記録なし → 張らない（S2 の免除・文脈を残す前に止まった注文・手仕舞いレグ）。突合で確定したものは Critical で知らせる。
- 突合の常駐の Critical（確定した 1 件）は残すが、文面の「この経路は保護逆指値を張りません」は偽になったので
  「この時点では保護レグがありません。続けて張ります（結果は直後の行と通知）」へ改めた（T-10-609 / 650 / 653 の部分文字列を追随）。

## 理由

- 裁定 1 の優先順位: 不明のまま建玉を落とす害（孤立した逆指値→反対建玉・損失の上限なし）は不可逆で、据え置く害（照会で確定するまで保護の有無が分からない建玉）は
  通知で人が確かめられる。確実に未発注のときだけは「逆指値なしの建玉を持たない」（FR-10）がそのまま効く——FR-10 の「未受理」は確認できた拒否であり、不明は含まない。
- 送り直しを止めるのは予約である（決定的な ID は既にあった）。成行手仕舞い（IADR-0117 改定 7）と同じ形にすることで、読み手が覚える規律が 1 つで済む。
- 突合に承認の文脈を運ばせる手段は、予約表の列追加（Migration）か保護記録の事前記録しかない。保護記録は既に S1 がエントリー前に書いており、
  状態を 1 つ足すだけで巡回・純額の計算から切り離せる（整数列のため Migration も不要）。

## 残余リスク

- 据え置きの解決は突合（配備: 滞留 2 時間・間隔 1 時間）頼みであり、**最大約 3 時間、保護の有無が分からない建玉が残る**。
  通知が「証券会社の画面で確認」を求める。解放の門が閉じている配備では「未発注」と出ても据え置きが続く（人が確認して解決する）。
- エントリーの予約を取った直後・事前記録の前、または逆指値の送信中にプロセスが止まると、文脈や送信結果待ちの行が残らない
  （突合は「保護の記録が無い」を Critical で知らせる。後者は従来の穴と同じ幅）。
- 送信結果待ちの行に乖離の取り込みが当たると、取消が失敗して主張を減らさない（安全側。IADR-0370 の「取消を確認できない」へ倒れる）。
- 突合で確定したエントリーの逆指値が未受理なら、平常の経路と同じく未約定分の取消・約定分の成行手仕舞いへ進む（突合の時点の状態で判断する）。
- 内蔵 paper 構成にはガード・突合の照会が無い（paper の発注は例外を投げない）。

## ［2026-09-25 追記 / PR #1005 監査］送信結果待ちを保護と数えない・予約の失敗を無音にしない・保護レグを「記録なし」と言わない

監査（GO-with-nits）の指摘を容れて次を改める。

- **照会不明の見送りの保護の記録（IADR-0424 決定 1）**: 同じ銘柄・方向に送信結果待ちの行があれば `Unknown` を返す。ブローカー側の注文の株数に
  数えると、無いかもしれない逆指値を「有る」と知らせる（IADR-0424 の「保護を少なく知らせる」向きの逆）。数えずに `Recorded` を返すと、
  生きているかもしれない逆指値を「無い」と断定する（原則 A）。
- **逆指値の予約そのものが例外で落ちた（DB 障害）**: 逆指値は送らない。エントリー同時の経路は保護記録を送信結果待ち（`Active`・注文 ID が空）で残し
  ——予約が無ければガードは未発注として次の試行で張り直し、実は書けていれば据え置く——Critical を残して保護喪失（`None`）を返す
  （保護記録も書けなければ Critical で「巡回されない」と残す。通知はメッセージ基盤を通って届く）。ガードは行を変えず（次の巡回で改めて評価）、
  Critical と `None`（`LapsedInFlight`）を出して `CloseFailed` を返す。どちらも成行・取消は送らない（DB が不確かなまま予約なしで注文を重ねない）。
  （［2026-09-25 追記 / PR #1005 再監査］`None` は `StopReservationFailed` に置き換えた。下の追記を参照）
- **突合が保護レグを確定したとき**: Active な保護記録の `StopDecisionId`（据え置いた逆指値）か、この試行の `CloseDecisionId`（ガードの成行手仕舞い）に
  一致すれば `ReconciledEntryProtectionKind.ProtectiveLeg` として張らず、常駐は Information で残す（「保護の記録がありません」の Critical を出さない）。
  エントリー同時の成行手仕舞い（保護記録が完了済み）や S1 の決済レグは判別できず、従来どおり「記録なし」の Critical になる。
- **配備の順序**（運用手順に記載）: リスク管理・通知・監査を先に、発注執行を最後に（逆指値の送信が進行中でないとき）。送信結果待ちの行が残るあいだは
  発注執行を旧い版へ戻さない。旧い通知は新しい列挙値を既定の件名「保護逆指値が成立せず建玉を解消」で表示し、旧いリスク管理は承認の由来を取り違えるため。

追加の残余リスク（記録のみ）:

- 送信結果待ちの行は、建玉が消えても突合が解決するまで残り、そのあいだ S0 の主張（数量）を持ち続ける。`ProtectiveStopNetting` は手法の異なる
  Active 行の主張を差し引いて持ち分を計算するため、同じ銘柄・方向の S1 の行に割り当てられる株数がその分だけ小さくなる。S1 は売り過ぎない側へ倒れるが、
  到達したとき建玉の一部しか決済しないことがある（通知は据え置きの Critical が続いている）。
- 突合が予約を確定した後に出口（`sink.EmitAsync`）が例外で落ちると、その 1 件について保護の口は呼ばれない（巡回はそこで止まり、確定済みの予約は
  次の巡回に載らない）。事前記録（`AwaitingEntry`）は残るが、それを拾い直す経路は無い。確定の Critical は発行より先に出ている。

## ［2026-09-25 追記 / PR #1005 再監査］予約の失敗は `StopReservationFailed` で事実どおりに知らせ、ガードの通知は 1 時間ごとに絞る

- 逆指値の予約そのものが落ちたときの保護喪失を `None` から **`ProtectiveStopRemediation.StopReservationFailed`**（末尾・値 6）へ改める。
  `None` の通知は件名・本文とも「未受理」「建玉の解消にも失敗」と読め、事実（逆指値は送っておらず、取消も成行も試みていない）と違った。
  `CloseDecisionId` は送らなかった逆指値レグ、`CloseIntent` は運ばない（台帳は押さえない）。通知は Critical のまま、原因で書き分ける:
  エントリー同時は「常駐ガードが次の巡回（約 30 秒後）で建玉を確かめて張る。それまで手で逆指値を置かない（二重になる）。
  数分たってもガードの『保護逆指値を発注』が来なければ手で手当てする」、ガードの再発注は「逆指値なしの建玉が残っている・巡回のたびに試み、
  約 1 時間ごとに繰り返す・障害が続くあいだは手で手仕舞う」。監査の要約と常駐の発行補償も追随した。
- ガードの予約の失敗は、読めるが書けない障害が続くと巡回（30 秒）ごとに Critical の通知が重なった。通知は据え置きと同じ間隔
  （`HeldCloseNotificationTracker`・キーは逆指値レグ。このプロセスで未通知、または前回から 1 時間）に絞る。ログ（Critical）は巡回ごとに残す。

追加の残余リスク（記録のみ）:

- 「常駐ガードが逆指値を張り直す」（予約が無い送信結果待ちの行・予約の失敗のあとの行）が成り立つのは、**エントリーが約定して建玉がブローカーに
  現れてから**である。未約定のエントリーでは建玉が 0 に見え、ガードはそれを「建玉が消えた」と読んで記録を完了させる（受理済みの逆指値なら取り消す）
  ——既存のガードの挙動であり、本件では直さない（#1013）。
