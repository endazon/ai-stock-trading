# IADR-0605: 月次費用上限の内訳と総額の整合（合計 ＝ 総額）を後段と画面の両方で検証する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: **Accepted**
- 日付: 2026-10-30
- 決定者: Claude Code（実装）／ endazon（＝・0 許容・両方に入れる・PoC の確認は、オーケストレーター経由の指示 2026-10-30）

## 起点・関連

- 計画: SC-01 の入力項目の表は、月次総費用上限と内訳について「型・範囲チェック。**内訳の合計が総費用上限と矛盾しないこと**」を求める。
  05_trading-assumptions §6 は「月次総費用上限: 20,000 円（LLM＋インフラ＋データの合計）」と定める（内訳 15,000＋5,000＋0）。
- 実装仕様書: [`.ai-context/specs/20261030_1514_cost-limits-sum-and-currency.md`](../specs/20261030_1514_cost-limits-sum-and-currency.md)
- issue: #1514（#1410 の網羅表 A-023・A-024）

## 背景

#1410 の棚卸しで、合計の整合が画面（`SettingsPage` の型の検証だけ）にも後段（`AssumptionsService.Update` は理由の必須だけ）にも
無いことが分かった。矛盾した前提条件（例: 総額 25,000・内訳の合計 20,000）を保存でき、費用統制の判定が総額と内訳のどちらに従うかで食い違い得る。

## 決定

1. **整合は「合計 ＝ 総額」とする。** §6 が総額を内訳の合計として定義しているため。「合計 ≦ 総額」は採らない
   （余りの枠がどの区分にも属さない状態を許し、§6 の定義と食い違う）。比較は decimal の完全一致（後段）。画面は浮動小数の誤差（1e-4 円未満）だけを同じ値とみなす。
2. **各欄は 0 以上。負は拒否する。** データ費用 0 が既定であり、0 は正当な値である。
3. **後段（ConfigurationService の更新）を正（権威）とする。** 矛盾・負は `ArgumentException` に利用者へ見せる印（IADR-0509）を付けて投げ、
   群のフィルタが 400 と理由に写す。**画面も同じ規則で保存を無効にして理由を出す**（両方に入れる。画面だけだと API の直叩きで抜ける）。
   文言は両方で同じにする（合計と総額を円で示す／負の欄の名前を示す）。
4. **検証は保存のときだけ効く。** 読み取り（REST・gRPC）・消費側の費用統制の判定・既存の保存値は変えない。
5. **費用上限の通貨は円のままとし、SC-01 に単位「円」を明示する**（表示だけ）。計画 §3 は判定の基準通貨 USD を
   リスク統制値・Stage 昇格の判定に限り、§6 の費用上限は「円/月」である。IADR-0152 の射程（リスク統制の判定・換算・SC-02 の表示）も費用上限に及ばない。

## 却下した案

- **画面だけで止める**: API の直叩き（Discord ボット・将来の自動化）で抜ける。
- **後段だけで止める**: 利用者は保存を押すまで矛盾に気付けない。
- **読み取りの時点で矛盾を検知して縮退する**: 既存の値の扱いを変え、配備の影響が大きい。今回の射程（保存の検証）を越える。

## 結果・残余リスク

- 🔴 **稼働中の値が ＝ を満たしていないと、配備の後に SC-01 で（費用上限以外の欄を含めて）保存できなくなる。** 読み取りは変わらないので
  業務は止まらないが、保存する前に費用上限を ＝ を満たす値へ直す必要がある。既定値（20,000＝15,000＋5,000＋0）は満たすことを試験で固定した。
  配備前の確認手順は PR 本文に書いた。
- 規則の写しが画面と後段の 2 か所にある。文言と規則の食い違いは試験（後段 xUnit・画面の単体テスト・L1 E2E）がそれぞれ固定するが、
  片方だけ変えると食い違い得る。正は後段である。
