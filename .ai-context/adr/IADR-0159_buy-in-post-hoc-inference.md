# IADR-0159: 強制買戻しは建玉消失と自らの決済指示の突合で事後推定し、過剰推定へ倒す

## コンテキストと課題

計画 ADR-0016 決定4 は当初「強制買戻しを**イベントとして検知**し、記録・通知する」と定めていたが、
**イベント検知の供給元が無い**ことが PoC（ADR-0019 項目5）で判明した——SIMULATE では強制買戻しが原理的に
発生せず、SDK に専用の通知 API も見当たらない。2026-08-06 の利用者裁定により決定4 は改訂され、
**建玉の消失を約定履歴と突合し、事後に推定する**方式になった。

実装側では `BuyInBanned`（クラス A）と 30 日の禁止期間判定は #374 で入っているが、
**`BuyInBanUntil` を立てる供給経路が無い**。本 IADR はその供給経路の設計判断を記録する。

決めるべき点は 4 つある。

1. 何をもって「自らの決済指示に対応しない消失」とするか（＝正常な手仕舞い・損切りとの区別）
2. 推定を**どちらへ倒すか**（過剰／過少）
3. **部分約定・分割決済**の扱い（数量差で見るか、消失＝ゼロで見るか）
4. **照会自体が失敗**したときの振る舞い

## 検討した選択肢

### 突合の相手（課題 1）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **前回のブローカ観測との差分**を取り、その区間の自約定と突合する | 区間の境界（観測の欠測・順序）で取りこぼす。前回スナップショットを durable に持つ必要があり、観測が飛ぶと差分が二重・欠落する |
| B（採用） | **取引台帳の建玉射影（＝自らの約定履歴の畳み込み）とブローカ観測の差**を取り、さらに**処理中の決済承認**を差し引く | 状態を持たずに「自らの指示で説明できない量」が一度に出る。既存の建玉突合（IADR-0118）と同じ入力で、経路が増えない |
| C | 約定履歴の**個々の約定を時刻で突合**する | ブローカ側に「強制買戻しの約定」を識別する情報が無い以上、時刻での対応付けは推測の上塗りになる |

### 倒す向き（課題 2）

| 案 | 過剰推定 | 過少推定 |
| --- | --- | --- |
| 結果 | 不要な 30 日禁止＝**機会損失**（空売り 1 銘柄が 30 日建てられない。資金は失わない） | **同じ銘柄で強制買戻しを繰り返す**（決定4 の目的そのものが果たせない。踏み上げ中の強制決済が反復する） |

### 部分約定（課題 3）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **消失＝ブローカ建玉が 0 になった時点**で推定する | ブローカが一部だけ買い戻した場合に推定が起きない（**過少推定**）。分割で買い戻されると永久に発火しない |
| B（採用） | **数量差**で突合し、前回までに推定済みの数量（帰属数量）を超えた**増分**だけを新たな推定とする | 部分買戻しでも直ちに発火する。毎巡回の再観測で禁止が延び続けることも無い |

### 照会失敗（課題 4）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 照会不能を「建玉ゼロ」として扱う（＝全建玉が消失＝全銘柄を禁止） | 名目上は最も過剰推定だが、**統制ではなく事故**である。OpenD の 1 回の切断で全監視銘柄が 30 日禁止になる |
| B（採用） | **推定しない。ただし「起きていない」とも言わない**（既存の禁止は有効なまま・報告は `NotSupplied`） | 推定の側では fail-open だが、**空売り自体が別の統制でフェイルクローズしている**（下記 決定4 の理由） |

## 決定

### 決定1: 突合は「台帳の空売り建玉 − ブローカの空売り建玉 − 処理中の決済」で行い、**過剰推定へ倒す**

```
未説明の消失 = max(0, 台帳の空売り数量 − ブローカの空売り数量 − 処理中の決済数量)
```

- **台帳**は自らの約定履歴の畳み込み（`PortfolioProjection.ProjectOpenPositions`）である。自分で手仕舞い・損切りを
  すれば約定が台帳に入り、台帳側の数量が減るため右辺は 0 になる。**これが正常な決済と強制買戻しを区別する
  唯一の手段である。**
- **処理中の決済**（`IPortfolioLedgerStore.GetInFlightCloseQuantity`・遡り窓 30 分）を引くのは、
  **承認済みだが約定が台帳へ届いていない決済**が「自らの決済指示」そのものだからである。これを引かないと、
  約定の反映遅れという**通常運行の事象**が毎回強制買戻しとして推定される。
- 未説明の消失が正なら**強制買戻しと推定する**。ブローカの応答に銘柄が現れない場合は数量 0（＝全量消失）として扱う。
- **過剰推定へ倒す**（上表）。この非対称はコードのコメントにも残す。手動売買・外部要因による消失も
  強制買戻しとして推定され得ることを**既知の取り違え**として受け入れ、根拠を監査ログへ残して人が検証できるようにする。

### 決定2: 部分約定・分割決済は**数量差**で突合し、帰属数量を超えた**増分**だけを新たな推定とする

- 同じ乖離を毎巡回で観測しても**推定は 1 回**である（禁止期間が巡回ごとに 30 日ずつ延びない）。
  台帳は自動では是正されないため、**乖離は解消しない限り毎巡回で観測され続ける**——ここを冪等にしないと
  30 日の禁止が事実上の恒久禁止になる。
- 段階的な消失（40 株 → さらに 60 株）は**増分ごとに推定**し、そのつど禁止期限を更新する（新たな買戻しだからである）。
- **自らの決済の部分約定は推定しない**。100 株の決済指示のうち 60 株が約定すれば台帳の空売り建玉も 60 株減り、
  未説明の消失は 0 になる（最重要の否定形。テストで固定する）。
- 乖離が解消したら帰属数量を 0 へ戻す**リセット記録**を追記する。**禁止期限は戻さない**——30 日は経過でしか解けない
  （`BuyInBanned` は「期間の経過で解除される禁止状態」であるという ADR-0016 決定10 の定義がここでも効く）。

### 決定3: 記録は**追記専用の推定台帳**とし、**発生回数の集計元をその行数に固定する**（ADR-0016 決定15）

- `buy_in_inferences`（リスク管理サービス専有 DB）に 1 推定 1 行を追記する。禁止期限は当該銘柄の行の最大値である。
- **発生回数の集計元は推定の件数であり、`BuyInBanned`（拒否理由）の件数ではない。** `BuyInBanned` は
  禁止期間中の発注拒否であり、**1 回の強制買戻しに対して 30 日のあいだ何度でも発生し得る**。
  拒否件数を発生回数として報告すると、実際より大きな数字が月報に載る（決定15 の明文）。
- **供給が無い間は 0 件と表示しない。** 報告書サービスから推定台帳への結線は無く（権威源への照会 API が無い）、
  既定の記録源は `null`（未供給）を返す。日報・月報は「照会できませんでした（供給元がありません）」と書く。
  **0 件と書けば「強制買戻しは起きていない」と読める**（決定15 が名指しで禁じた向き）。
- `BuyInBanned` は**クラス A のまま**である（決定10）。クラス C（`BannedSymbol` / `ManipulativeOrderPattern` ＝
  段階昇格ゲートの「統制違反 0 件」の計上対象）へ混ぜない。`BorrowUnavailable` へも写像しない。

### 決定4: 照会自体が失敗したときは**推定しない**。ただし既存の禁止は有効なまま、報告は「未供給」と書く

- ブローカ建玉を照会できないとき、発注執行サービスは**何も発行しない**（既存の fail-safe・IADR-0118）。
  推定は動かない。照会不能を「建玉ゼロ」と読む案 A は採らない——OpenD の 1 回の切断で全監視銘柄が
  30 日禁止になり、統制ではなく事故になる。
- **観測が届かない間も既存の禁止は有効なまま**である。禁止期限は日付でのみ失効し、観測の不在では解けない
  （解けると fail-open になる）。
- これは推定の側では fail-open だが、**同じ銘柄で空売りを繰り返す経路そのものが今は存在しない**——
  借株照会の供給元が無い以上、文脈（`ShortSellOrderContext`）は `null` であり、**すべての新規売り建ては
  `BorrowUnavailable` で拒否される**（IADR-0131 決定2 / IADR-0158）。推定の穴は、別の統制がフェイルクローズで
  塞いでいる。**この依存関係は借株照会が実装された日に消える**ため、そのときは本決定を再評価すること。

### 決定5: 禁止期限は**文脈とは独立に**判定コアへ供給する（値を発明しない）

- `ShortSellOrderContext` は借株可否・借株料・維持率・エクスポージャ・権利確定日を要求するが、
  **借株照会の供給元が無いため今も組めない**。組めないからといって、維持率 `null`・エクスポージャ `0` で
  埋めた**偽の文脈を作らない**（0 は「無い」ではなく「観測した結果ゼロだった」と読まれる）。
- そこで**供給できる値だけを供給する**——`BuyInBanSupply(Today, BanUntil)` を `RiskEvaluator` へ渡し、
  短期の空売り禁止だけを単独で判定する。判定式そのものは `BuyInBanPolicy.IsBanned` を**単一情報源**とし、
  `ShortSellEvaluator`（文脈経由）と共有する（規則を 2 か所に書かない）。
- 文脈が組める日が来ても**二重計上しない**（既に `BuyInBanned` が列挙されていれば追加しない）。

## 理由

- **決定1 の突合先を台帳にしたのは、台帳が「自らの決済指示」の唯一の完全な記録だからである。** 前回観測との
  差分（案 A）は、観測が 1 回飛ぶだけで区間が壊れる。台帳との差は**いつ観測しても同じ意味**を持つ。
- **処理中の決済を引くのは、引かなければ通常運行が毎回誤検知になるからである。** 決済の承認から約定が台帳へ
  届くまでの間、台帳とブローカは**正当にズレる**（IADR-0118 が連続観測条件を置いた理由と同じ事象）。
  ただしこちらは「連続観測で待つ」のではなく**承認そのものを説明に使う**——待つ方式は推定を遅らせるだけで、
  ズレの原因を説明できない。
- **過剰側へ倒すのは、決定4 の目的が「同じ銘柄で繰り返さない」ことにあるからである。** 過剰推定の代価は
  30 日ぶんの機会損失であり、過少推定の代価は損失に上限の無い取引での強制決済の反復である。**同じ重さではない。**
- **決定15 の集計元を固定するのは、拒否件数が発生回数の代理にならないからである。** 1 回の買戻しに対する
  拒否は禁止期間中に何度でも起こり得る。代理にすると月報の数字が実態より大きくなり、
  「強制買戻しが多発している」という誤った像を運用者へ与える。

## 結果

- 良い影響:
  - `BuyInBanUntil` に**供給経路ができた**（#374 の実装が発動し得る状態になった）。
  - 推定の根拠（消失した建玉・突合した自らの決済約定・処理中の決済・推定日時・禁止期限）が監査ログに残り、
    **推定であるがゆえに要求される事後検証**が可能になる。
  - 決定15 の集計元が**推定件数に固定**され、拒否件数による水増しが構造的に起きない。
- 悪い影響 / トレードオフ:
  - **手動売買・外部要因による建玉消失を強制買戻しと取り違える**（過剰推定側の既知の代価）。
  - **推定は遅い**。ブローカ建玉の定期照会の周期ぶん遅れる（決定4 の改訂が明示的に受け入れた性質）。
  - **報告書は当面 `NotSupplied` のまま**である（推定台帳への照会 API が無い）。実装が入っても表示は未供給であり、
    「実装したから見える」と読める記述を作らないこと。
  - **本経路そのものが Stage 1 では一度も発火しない**見込みである——ブローカ建玉の観測は OpenD の常駐を要し、
    空売り自体が借株照会の不在で全件拒否されているため、そもそも空売り建玉が存在しない。
- フォローアップ:
  - **実弾口座側の強制買戻しの通知・履歴 API は未調査**（ADR-0019 PoC 項目5）。見つかれば本代替を置き換える。
  - 報告書サービスから推定台帳への結線（照会 API）。
  - 借株照会の供給元が入った日に、決定4 の「別の統制が塞いでいる」という前提を再評価する。
