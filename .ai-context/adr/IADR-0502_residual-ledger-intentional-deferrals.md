# IADR-0502: 残作業の台帳（#1204）のうち、意図して保留する 3 件

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: **Accepted**
- 日付: 2026-10-07
- 決定者: claude（#1204 の受け入れ基準「意図した保留として IADR に記録した」に沿って起案）

## 起点・関連

- 関連する計画書 ID: 計画 ADR-0049 決定 4（1 注文上限を緩めるときは損切り幅の下限を前提条件とする）・ADR-0030 フォローアップ 3（欠落節の実装）・FR-20（段階ゲート）
- 対象 Issue: [#1204](https://github.com/endazon/ai-stock-trading/issues/1204)（第 4 回全体監査 B-18 / C-3 の台帳）
- 関連する実装仕様書: [20261007_1204_residual-ledger](../specs/20261007_1204_residual-ledger.md)（全行の仕分けと実測。本 IADR は (c) に当たる行だけを扱う）
- 関連 IADR: [IADR-0486](IADR-0486_stop-width-floor-atr14-flag-and-floor-marker-on-order-intent.md)（ATR の下限。残余に「1 注文上限を緩める検討は別途」）、
  [IADR-0272](IADR-0272_report-section-structure-arbitration.md) 決定 3（税金レビューの先送り）、[IADR-0291](IADR-0291_report-sections-follow-plan-numbering.md)
- 計画側の裁定待ち: planning#741 の項 1（ADR-0049 決定 3 の丸めの向き）。**本 IADR はその裁定の内容を先取りしない。**

## コンテキストと課題

#1204 は計画 ADR-0030〜0055 の突合で見つかった残作業の台帳であり、各行を「別 issue（番号）／直した（PR）／意図した保留（IADR）」のどれかにする。
振る舞いを変える行はすべて別 issue に切り出した（#1218〜#1225。作業仕様書の表）。**次の 3 件は、いま着手すると計画の値や裁定を先取りする、
または既に判断済みで起票すると重複する**ため、保留として外す条件とともに記録する。

## 決定

### 決定 1: 1 注文あたりの発注金額上限（equity の 25%）の緩和は検討を始めない（ADR-0049 決定 4）

- 計画 ADR-0049 決定 4 は「1 注文上限を緩める変更は、損切り幅の下限が**効いていること（実現手段が配備済みであること）**を前提条件とする」と定める。
  緩和そのものを求めてはいない。IADR-0486 の残余「1 注文上限（25%）を緩める検討は本件の後に別途行う」は、この前提条件が満たされた後の任意の検討である。
- 2026-10-07 時点で前提条件は満たされていない:
  1. ATR(14) の下限は**既定で無効**（IADR-0486 §結果「有効化は未実施〔取得枠の回復周期の記録の後に利用者が行う〕。実機〔SIMULATE〕での確認は未実施」）。
  2. 下限を呼値へ丸める向きが計画（決定 3「下限を割らない向き」）と実装（早く発火する側。最大 1 刻み未満だけ下限を割り得る）で食い違い、
     **planning#741 の項 1 で裁定待ち**である。どちらに揃うかで「下限が効いている」の意味が変わる。
- 25% は計画 05_trading-assumptions §5 の全体前提条件の値であり（`TradingDefaults` の試験が固定する）、緩めるのは**計画の変更**である。実装側で値を動かさない。
- **外す条件**: (1) ATR の下限が配備で有効になり、(2) planning#741 の項 1 が裁定され実装がそれに揃い、(3) 利用者が緩和を望む —— の 3 つが揃ったら、
  緩和の要否を planning へ環流する（feedback issue）。それまで本件の issue は立てない。

### 決定 2: 月報 §3 税金レビューは IADR-0272 決定 3 の先送りを維持する（ADR-0030 フォローアップ 3 のうち月報の 1 節）

- ADR-0030 フォローアップ 3（欠落節の実装）のうち、日報 §6 振り返りは #1218 へ切り出した。月報 §3 税金レビューは
  **IADR-0272 決定 3 が既に「前提整備が必要な欠落節は受容として記録し先送りする」と記録している**（年初来累積の権威源・口座区分〔NISA/特定口座〕・
  配当〔外国税額控除の前提〕がいずれもシステムに無い）。IADR-0291 は IADR-0272 の決定 1 だけを改めており、決定 3 は有効である。
- 実物（`origin/develop` `2458fc95`）: `backend/Services/ReportService/Domain/ReportRenderer.cs:70` が見出しを出したまま本文に未実装と書き、
  理由は同 `:123` の `TaxReviewReason`。ADR-0030 決定 3（未実装の節は見出しごと出し、本文に未実装と書く）に沿っている。
- **新しい issue は立てない**（前提整備の要否は IADR-0272 §フォローアップ 3 のとおり人の裁定を要し、実装 issue にしても着手できない）。
- **外す条件**: 年初来累積・口座区分・配当のいずれかの権威源を整える判断（人の裁定）が出たら、その時点で税金レビューの実装 issue を起票する。

### 決定 3: `StageProhibitsLiveTrading` のトートロジーは直さず、効いている統制として数えない（#204 D-5 の判断を記録として残す）

- `RiskEvaluator.cs:99-102` の `StageProhibitsLiveTrading` は、発注意図の `Mode` と段階の既定発注先を比べるが、
  `Mode` の供給元が `SizingContextService.cs:33` の `Mode: settings.Stage.Mode` であり、**比べる 2 値が同じ源から来る**。
  段階の変更の最中に古い意図を落とす陳腐化ガードとしては働くが、実弾を止める統制としては働かない。
- #204（go-live 前監査）の D-5 は「起票せず（安全側・計画上の穴でもない）。次回監査で効いている統制と数えない」と判断した。
  実弾を止めているのは `LiveTradingGate` の閂（IADR-0111・IADR-0056。両層の Stage 0 合格の前提は IADR-0498）と段階・商品種別の規則であり、本検査を外しても足しても実弾の可否は変わらない。
- **直さない理由**: 「独立の源から `Mode` を取る」には発注意図の側に段階とは別の発注先の申告が要るが、計画にその概念は無い（発明になる）。
  検査を消すと陳腐化ガードの効果を失う。
- **外す条件**: 発注意図が段階とは独立に発注先（`Mode`）を持つ設計が計画または IADR で入ったら、本検査を統制として数えられるか見直す。

## 理由

- 台帳の行を「とりあえず issue にする」と、着手できない issue（計画の値の変更・人の裁定待ち・既に判断済み）が増え、blocked の棚卸しの負担になる。
  着手条件が実装の外にある行は、条件を書いた保留の方が追跡しやすい（`.claude/rules/traceability.repo.md`「暫定の除外は外す条件と一緒に書く」と同じ考え方）。
- 決定 1 は planning#741 の裁定対象と前提を共有するため、実装・起票のどちらも裁定の先取りになり得る。

## 結果

- 良い影響: #1204 の全行が a / b / c のどれかに定まる（作業仕様書の表）。保留の 3 件に外す条件が付き、次の監査で「追跡が無い」と再指摘されない。
- 悪い影響・トレードオフ: 保留の 3 件は issue の一覧に現れない。次の監査・棚卸しは本 IADR を読む必要がある。
- 残余リスク: 決定 1 の外す条件 (1)(2) が満たされても、利用者が緩和を望まなければ環流は起きない（それで正しい —— 緩和は義務ではない）。
