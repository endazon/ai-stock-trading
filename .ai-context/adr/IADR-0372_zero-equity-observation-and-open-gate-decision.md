# IADR-0372: 残高 0 の観測と、新規建てを止めるかどうかの裁定

- 状態: **Proposed（未裁定）**
- 日付: 2026-09-23
- 決定者: **未定**（起票 #889。**裁定は利用者に残す**）

🔴 **本 IADR は「決めた」記録ではない。** 決定 A / B は**観測の追加**（挙動を変えない）についてのもので、
本題である「残高 0 で新規建てを止めるか」は**選択肢と害を並べたところで止めてある**。
`Accepted` にしていないのはそのためである —— 決めていないものを決めた形で残すと、次に読む人が誤読する。

## 起点・関連

- 関連する計画書 ID: **FR-10**（統制値の判定基準）・FR-19（口座照会）・NFR-07（可観測性）・UC-06
- 計画の裁定: **ADR-0041 決定 2**（基準資金の供給元をブローカーの口座照会と確定する）
- 関連 IADR: [IADR-0354](IADR-0354_capital-baseline-from-broker-account.md) 決定 7・§結果 フォローアップ 5
  （**受け入れた残余リスクの本体**。本 IADR はそこから切り出した）
- 関連する実装仕様書: [20260923_889_zero-equity-observation](../specs/20260923_889_zero-equity-observation.md)
- 起票: [#889](https://github.com/endazon/ai-stock-trading/issues/889)

## コンテキストと課題

基準資金は「当日より前の取引日で最新の行」を使う。口座照会が `TotalAssets <= 0` を返すと供給側の門が
未供給へ倒すため、**その取引日の行が 1 行も書かれない**。結果、読み出しは**前取引日の正の行を返し続け**、
鮮度（既定 4 日）が切れるまで**新規建ては止まらない**。

🔴 **2 つの門の帰結が非対称である。**

| 0 の出どころ | 効く門 | 帰結 |
| --- | --- | --- |
| ブローカーが 0 を返す | 供給側（行を書かない） | 前取引日の正の行が生き、**止まらない** |
| 人手で 0 を 1 行投入（Runbook 経路） | 読み出し側（`<= 0` を `null` へ） | **止まる** |

## 🔴 決められない理由（本 IADR が Proposed である理由）

issue が明記している ——

> **どれを採るにしても、実口座で `TrdGetFunds` が残高 0 のときに何を返すか（0 か・フィールド未設定か・
> エラーか）が分かっていない。まずそれを観測してから決めるべきである。**

**その観測は本作業では行えない。** 接続は模擬取引口座に固定されており（IADR-0016）、稼働クラスタにも触れない。
模擬口座の残高を 0 にする操作は取引そのものであり、実施しない。

**応答の形が分からないまま選ぶと、選んだ側が実機で成立しない。** #897 が同型の事故である ——
`Funds.currency` が載る前提で守りを入れ、実機では常に fail-closed になった。**同じ轍を踏まない。**

## 選択肢と害（裁定のための材料）

### 選択肢 1: 0 を観測した取引日を「未供給」として latch する（行を書き、読み出し側の門で止める）

| | 内容 |
| --- | --- |
| 効果 | 残高 0 を**確実に止められる**。2 つの門の非対称も解消する |
| 🔴 害 | **一過性の 0 でその取引日が丸ごと止まる。** OpenD の不調・応答の既定値・部分的な障害で 0 が 1 回返るだけで、その日の新規建てが出なくなる |
| 🔴 害 | 「鮮度（既定 4 日）まで読めなくても前取引日の値を使う」という**既に受け入れた設計判断と衝突する**（`MaxAgeDays` の存在理由そのもの）。読めない日を許すのに 0 の日は許さない、の線引きが要る |
| 前提 | **実口座が残高 0 で何を返すか**（0 か・欄なしか・エラーか）。欄なし／エラーなら「0 を観測した」自体が成立しない |
| 必要な実装 | 供給側の契約変更（`GetAccountEquityInBaseAsync` が「0 を観測した」と「照会できなかった」を区別して返す）。現在は両方 `null` |

### 選択肢 2: `Power` など別フィールドで「本当に残高 0」を確証してから止める

| | 内容 |
| --- | --- |
| 効果 | 一過性の 0 による誤検知が減る |
| 🔴 害 | **買付余力を統制へ引き込む**ことになり、ADR-0016 決定 6「buying power を基準にしない」との距離を決める必要がある（**分母には使わず検証にだけ使う**なら両立し得る） |
| 🔴 害 | `Power` は信用で約 2 倍になる値であり、「0 かどうか」以外の読み方を持ち込むと将来の誤用の芽になる |
| 前提 | 選択肢 1 と同じ。加えて**残高 0 のとき `Power` が何を返すか**の実測 |

### 選択肢 3: 人手の Runbook に委ねる（現状）

| | 内容 |
| --- | --- |
| 効果 | 実装を増やさない。一過性の 0 で止まらない |
| 🔴 害 | **気づけなければ止まらない。** 残高 0 のまま鮮度切れまで新規建てが通る |
| 前提 | **気づく手段があること** —— 本 PR の決定 A / B はこの前提を満たしにいったものである |

## 決定（本 PR で実施した範囲。**挙動は変えていない**）

### 決定 A: 読み出しの帰結を 5 つに分類して観測する（門は変えない）

`ICapitalBaselineStore.GetCurrent()` が返す値は従来と同じまま、帰結を
`CapitalBaselineReadOutcome`（`Supplied` / `SuppliedWithGap` / `UnavailableNoRow` /
`UnavailableStale` / `UnavailableNonPositive`）で数える（`ast.risk.capital_baseline_reads{outcome}`）。

🔴 **`SuppliedWithGap` が本件の症状そのものである** —— 「値は返っているが、直前の取引日の観測が
1 件も届いていない」。取引日は米国東部時間の暦日で数え、巡回（既定 5 分）は土日も回るため、
期待される間隔は 1 日である（IADR-0354 決定 2）。

- **原因（残高 0 / 照会障害 / プロセス停止）は区別しない。** 読み出し側から区別できないし、
  危険なのは原因ではなく**古い分母で統制が回っているという状態**である。
- `SuppliedWithGap` と `UnavailableNonPositive` は Warning でも残す。平常の読み出しは**ログを出さない**
  （読み出しは審査のたびに起きるため、鳴らし続けると本物の警告が埋もれる。#897 の教訓）。

### 決定 B: 評価額の無い観測を受けたとき、「行を書かない」ことを警告で名指しする

`BrokerAccountObservedHandler` は従来どおり行を書かない（正しい）。ただしその事実を Warning で
「この取引日の行は書かない＝前取引日の値が使われ続ける」と明示する。

🔴 **ここでは「残高 0 を観測した」と「照会できなかった」を区別できない**（供給側が両方を `null` へ畳む）。
区別するには供給側の契約を変える必要があり、**それは選択肢 1 の一部**である。

## 理由

- **観測の追加はどの裁定とも衝突しない。** 選択肢 1 を採るなら「0 の日」の頻度が要り、
  選択肢 3 のままなら「気づく手段」が要る。**どちらへ転んでも前提条件である。**
- **挙動を変えないので、裁定を待つ間に危険が増えない。**

## 結果

### できるようになったこと

- 「値は返っているが観測が途切れている」状態が、指標とログで見える。
- 人手投入の 0 で止まったことが分かる（従来は黙って `null` だった）。

### 🔴 残る制約（＝裁定に必要なもの）

1. **実口座が残高 0 のときに何を返すかは分かっていない。** 本 IADR の選択肢はすべてこの観測待ちである。
2. **2 つの門の非対称は解消していない。** 現時点では**意図した状態**として記録する
   （`CapitalBaselineReadOutcome.UnavailableNonPositive` の説明に明記）。
3. 供給側は「0 を観測した」と「照会できなかった」を区別しない。区別は選択肢 1 の実装に含まれる。

### フォローアップ

1. **実口座（または実口座相当）で残高 0 のときの応答形を観測する。** 観測できた時点で本 IADR を更新し、
   選択肢を 1 つ選んで `Accepted` にする。
2. 本 PR の指標（`SuppliedWithGap`）を実運用で数週間見て、**observed な頻度**を記録する。
   頻度が高いなら選択肢 1 の害（一過性の 0 で止まる）が現実的な問題になる。
