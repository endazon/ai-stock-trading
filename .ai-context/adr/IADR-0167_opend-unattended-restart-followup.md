# IADR-0167: OpenD 無人再起動の初回結論の撤回と、再起動最小化の維持

## コンテキストと課題

計画 ADR-0024（計画リポ）（2026-08-07・`Accepted`）が、**OpenD の無人再起動は「安定 egress IP」を条件に成立する**と定め、`ADR-0002` 前提条件1 の「検証は IP / セッション依存であり永続化では回避できない」を**誤りである**と名指しで訂正した。

**この訂正の元になった反証は、本リポジトリが自ら観測したものである。** 2026-07-15 の初回 PoC（#124）で「完全無人は不可（確定）」と結論した**同じ日**に、#13 の結合作業（#130）で Deployment を 3 リビジョン `Recreate` し、**3 回とも対話検証なしに `Login successful`** に到達していた。

**にもかかわらず、初回の結論は 3 週間そのまま残った。**

| 場所 | 状態（本 IADR の起案時点） |
| --- | --- |
| `deploy/opend/README.md` | ✅ 追検証節で訂正済み（ただし冒頭に断定が残存） |
| `docs/specs/20260714_124_opend-docker.md` | ✅ 追検証節で訂正済み |
| **`docs/adr/IADR-0053`** | ❌ **初回 PoC のまま。「不可（確定）」** |
| 計画 `ADR-0002` | ❌ `Accepted` のまま反証済みの記述を保持 |

**訂正が「作業ログ」には入り、「決定記録」には入らなかった。** これが本件の構造である。

## 決定

### 決定1: `IADR-0053` は `Proposed` のまま据え置く

`IADR-0053` は昇格条件に **2 つ**を挙げていた——「無人運用の一次確認」と「**海外 IP（Hetzner）接続の一次確認**」。

ADR-0024 で前者は満たされた。**後者は同 ADR 決定5-2 で依然未検証である**（`#24` / `#132`）。**片方だけで昇格させない。**

これは `IADR-0060` が既に置いた規律（「充足していないものを充足扱いしない」）と同じである。**むしろ ADR-0024 決定5-2 は「Hetzner はクラウドであり egress IP の安定性が単一ノード前提と異なり得る」と述べており、成立条件 (2) が Hetzner で保てるかは未知である。** 一次確認が最も要る相手が Hetzner である。

### 決定2: `livenessProbe` は引き続き付けない。ただし**理由を差し替える**

**結論は変えない。理由は差し替える。**

| | 内容 |
| --- | --- |
| **旧理由** | OpenD は**再起動＝対話再検証**であり、liveness による自動再起動は**再検証待ちで停止する状態**を招く |
| **新理由** | (a) **再起動の最小化を維持する**（ADR-0024 決定3）。(b) **SPOF であること自体は変わらない**（決定4）——単一インスタンスであり復旧までの発注不可時間が生じる。liveness による自動再起動は、**その不可時間を無人で繰り返し発生させ得る** |

**旧理由は ADR-0024 決定2 で否定された。** 否定された理由を残したまま結論だけを維持してはならない——**次に誰かが理由を確かめたとき、根拠が崩れているのに結論だけが立っている**という状態になり、そのとき結論は「根拠の無い慣習」として外される。**同じ結論を保つためにこそ、理由を書き直す必要がある。**

対象は `deploy/opend/README.md`・`deploy/helm/ai-stock-trading/{README.md,values.yaml,templates/opend.yaml}`・`.github/workflows/helm.yml`（既定描画の検査）である。**検査そのものは変えていない**（`livenessProbe` が付いていたら落ちる）。

### 決定3: 「再起動しても復旧できる」を「再起動してよい」へ広げない

ADR-0024 決定3 が明示している。**本作業の全編集で、緩和の対象は「再起動時の再ログイン」だけに限る。**

- **再起動の最小化は維持する**（単一レプリカ・`Recreate`・rolling 不使用・ノード固定）。
- **`IADR-0060` の「実弾への切替は人手に残す」は一切変えない。** ADR-0024 も「本 ADR が緩和するのは再起動時の再ログインであって、実弾への切替ではない」と明記している。

### 決定4: 初回 PoC の誤った記述を**削除せず、撤回として残す**

`docs/blocked-tasks.md` の方針（「解消の過程で本文書の記述が誤っていたと判明した場合は、**誤りも消さずに訂正として残す**」）を、IADR と `deploy/` の記述にも適用する。

**誤りの所在は「Pod IP（クラスタ内部）と egress IP（NAT 後）の混同」であり、これは再発しやすい形である。** 消すと、次に同じ観測をした者が同じ推論をたどる。**残す価値があるのは結論ではなく、誤り方である。**

### 決定5: 拒否理由の「総数 12 種」を実装側へ**新設しない**

`ADR-0021` 決定4-5（2026-08-07 改訂）は「拒否理由の総数は **12 種**になる（空売り 9 種 ＋ 本決定の 3 種）」と述べる。

**実装リポジトリには拒否理由の総数を述べた記述がそもそも存在しない**（`grep` で 0 件）。また `RejectionReason` の全メンバは **28** であり、計画の「12 種」とは**数えている対象が違う**（計画は ADR-0016 決定10 と ADR-0021 決定4-5 が新設した分の合計、実装は enum 全体）。

**したがって「10 種 → 12 種へ追随」は本リポジトリには適用対象が無い。無い記述を新設すると、二重の数え方を持ち込む**——後日どちらかが更新されずに食い違い、`RejectionReasonClassificationTests` が固定している**実際の分類**より弱い情報が「正」として読まれる。

**実装が計画と一致していることの担保は数ではなく、既存の分類テストである**（クラス A / B / C の内訳と序数を固定している）。

## 理由

- **決定2 が本 IADR の要である。** 「結論が同じなら書き換えなくてよい」は誤りである。**根拠を失った結論は、次の判断で最も外されやすい。** とくに `livenessProbe` は「なぜ無いのか」を後から問われる典型であり、答えが否定済みの命題だと、そこで初めて理由を調べた者が「もう成り立たないから付けてよい」と結論する。
- **決定1 と決定3 は同じ規律である**——**部分的な前進を全体の充足として扱わない。** ADR-0024 が緩和したのは 1 点であり、Hetzner も実弾切替も動いていない。
- **決定4 の「誤り方を残す」は、本件そのものが証拠である。** 誤りは「観測が間違っていた」のではなく、**限定的な観測から一般的な結論（「確定」）を引き出した**ことにある。観測ログだけ残して結論の訂正を残さないと、同じ飛躍が繰り返される。

## 結果

- 計画（ADR-0024）・実装 ADR（IADR-0053）・配備（`deploy/`）・CI（`helm.yml`）の前提が一致する。
- **`livenessProbe` を付けない理由が、否定されていない根拠に立つ。**
- **`IADR-0053` は `Proposed` のまま**であり、Hetzner の一次確認（#24 / #132）が唯一の残条件であることが明示される。

### 悪い影響（記録する）

- **「条件付き成立」は単一の真偽値ではないため、読み手が条件を落としやすい**（ADR-0024 §結果 の悪い影響そのもの）。本作業では条件 (1) デバイス信頼の永続化 と (2) 安定 egress IP を**必ず併記する**書式で統一したが、将来の追記で片方が落ちる余地は残る。
- **`docs/` に撤回線（`~~`）と訂正注記が増え、読み負荷が上がる。** 決定4 の意図した代償である。
- **本件の再発防止は仕組みではなく規律にとどまる。** 「作業ログには訂正が入り、決定記録には入らない」という失敗を機械的に検知する手段は本作業では作っていない。**環流記録（`feedback/`）が `status: open` のまま放置される**ことが遠因であり、`IADR-0166` の計画書ダイジェストは**逆方向**（計画→実装）しか見ない。実装→計画の未到達は [#439](https://github.com/endazon/ai-stock-trading/issues/439)（バックログ定期監査）の対象として扱う。
