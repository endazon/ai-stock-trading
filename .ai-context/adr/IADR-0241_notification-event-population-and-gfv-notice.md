# IADR-0241: 通知対象の母集合は「契約イベント全数 − 除外理由」で引き、GFV 違反の記録を通知へ加える

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（起票 #341。利用者レビューは PR で受ける）

## 起点・関連

- 関連する計画書 ID: FR-09（エラー・リスク統制の発動を Discord へ通知）・FR-19 / ADR-0025（GFV の自前計数）・
  ADR-0028 決定3（GFV 停止の解除窓口は Discord のみ）
- 関連する実装仕様書: [`20260828_341_discord-bot-and-notification.md`](../specs/20260828_341_discord-bot-and-notification.md)

## コンテキストと課題

`NotificationConsumerCoverageTests` は「**宣言したハンドラが 1 つ残らず発見されるか**」を見る。
これは「静かな未通知」（ハンドラはあるが Wolverine に発見されない）を止める検査であり、
**「通知すべき事象にハンドラが無い」ことは見ていない**——同テストのコメント自身が
「通知は選んだ事象だけを出す。全イベントに通知ハンドラを求めるのは誤り」と述べており、これは正しい。

しかし結果として、**「何を選び、何を選ばなかったか」がどこにも書かれていない**。#341 は
「通知すべき事象の網羅」を要求しており、選定の記録が無いままでは網羅を主張できない。

## 検討した選択肢

1. **全イベントに通知を義務づける**（母集合＝契約イベント型）
   — 定期観測（`BrokerPositionsObserved` 等）や逐次計上（`LlmCostIncurred`）まで Discord へ出ることになり、
   **損切り・統制発動の通知が埋もれる**。詳細設計07 §通知設計は「同種イベントの連発は集約」を前提にしており、
   その集約機構は未実装である。**却下**。
2. **選定を機械検査にする**（イベント型ごとに「通知する/しない」の宣言を持たせ、欠けたら落とす）
   — 運用標準「検査器・規約の追加は同型事故 2 回から」に照らして時期尚早である（同型事故は 1 回目）。
   宣言の維持コストも高い。**却下（記録に留める）**。
3. **走査の結果と除外理由を記録として残し、欠落分だけを実装する**（採用）

## 決定

1. 通知対象の母集合は **契約イベント型の全数（実測 33 件）** から引き、**除外は理由まで書く**。
   走査の生出力と 17 件の判定表は作業仕様書
   [`20260828_341_discord-bot-and-notification.md`](../specs/20260828_341_discord-bot-and-notification.md)
   §ギャップ分析が持つ（**ここへ複写しない**——2 箇所に置くと片方が古くなる）。
2. **`GoodFaithViolationRecorded` を通知へ加える**（`Critical`）。理由は 3 つ:
   - 契約コメントが「**ガードが正しく働けば 1 件も発行されない。発行された時点でガードをすり抜けた買付が
     現に約定した**」と定めており、詳細設計07 §通知設計の「リスク統制の発動（**ガード違反**）」に正面から当たる。
   - 積み上がると新規取引が止まり、**停止の解除窓口は Discord の `/gfv clear` だけ**である（ADR-0028 決定3）。
     通知が無ければ、止まったことも解除が要ることも利用者へ届かない。
   - **稀である**（設計上 0 件が正常）。集約機構が無くても通知を埋もれさせない。
3. **本文で「停止した」と断定しない。** 停止のしきい値は Risk 側が持ち、本イベントは件数を運ばない。
   通知は**観測した事実**（すり抜けた買付が約定した）と**限界**（自らのガードの失敗回数であって、
   ブローカの GFV カウンタの写しではない — ADR-0025 §理由）を書く。
4. **`SettledCashInBase` の `null` は「未供給」と表示し、0 と書かない**（#424 の表示規約・契約コメントの明示）。
5. **`BorrowFeeAccrualUnavailable`（システム異常＝収集失敗に該当）は本 PR では通知しない。**
   空売り建玉 × 取引日で発生し得るのに集約機構が無く、載せると可視性を下げる。**環流候補として記録する。**
6. **詳細設計07 §通知設計の「システム異常（API 障害・OpenD 切断・構成ドリフト警告）」に対応する契約イベントは
   本リポジトリに存在しない。** `BrokerAvailabilityObserved` は**発行＝到達できた事実**であり、停止は
   「発行しないこと」で表す設計のため通知に使えない。**沈黙は通知にできない。**
   死活の検知・通知は NFR-03 のとおり**基盤の可観測性スタックが担う別系統**である。**イベントの新設は
   供給側（他サービス）の作業であり本 PR の射程外**とし、環流候補として記録する。

## 理由

決定 1 は `.claude/rules/traceability.repo.md` の母集合規則（規則 9・10）の直接適用である。
**「追随する文書（ここでは通知すべき事象）を記憶で挙げない」**——記憶で挙げた結果が
「16 種あるのに 10 種と書かれていた」という既に起きた事故であり、`NotificationConsumerCoverageTests` の
冒頭コメントがそれを記録している。**今回は数ではなく選定そのものが記憶頼みだった。**

決定 6 は、**「エラー通知が無い」と「エラーを表すイベントが供給されていない」は別である**という切り分けである。
前者なら本 PR で直せるが、後者は直せない。**区別せずに何かを通知経路へ足すと、「エラー通知がある」という
誤った安心を生む。**

## 結果

- 良い影響: ガードのすり抜けが利用者へ届くようになる。選定の根拠が追える状態になる。
- 悪い影響・トレードオフ: 母集合の維持は人手である（機械検査を置かない＝決定 2 案の却下）。
- フォローアップ: 通知の集約（バッチ化）機構と「システム異常」イベントの供給は、環流候補として報告する。
