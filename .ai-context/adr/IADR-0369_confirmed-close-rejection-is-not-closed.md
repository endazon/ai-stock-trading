# IADR-0369: 確認できた拒否は「手仕舞い済み」ではない

- 状態: Accepted
- 日付: 2026-09-23
- 決定者: claude（起票 #857。利用者レビューは PR で受ける）

## 起点・関連

- 関連する計画書 ID: FR-10（損切りの実行機構・逆指値なしの建玉を持たない）、FR-11（監査）、UC-02、UC-06、ADR-0003
- 対象 Issue: #857（#851 の 3 巡目監査 B4 の過程で引き当てた**同型だが射程外**の穴）
- 関連する実装仕様書: [20260923_857_rejected-close-is-not-closed](../specs/20260923_857_rejected-close-is-not-closed.md)
- 関連 IADR: [IADR-0210](IADR-0210_broker-side-stop-loss-unification.md)（決定 3・4 の建玉解消）、
  [IADR-0117](IADR-0117_owner-position-close-path.md)（改定 7・改定 9。**届いたか不明**の扱い）、
  [IADR-0344](IADR-0344_s1-software-stop-loss.md)（決定 5-6。S1 の決済試行上限＝本 IADR が S0 へ写す形）、
  [IADR-0057](IADR-0057_order-dispatch-idempotency.md)（発注 3 相）

## コンテキストと課題

IADR-0117 の改定 6〜9（#848 / #851）は「**確実に未発注**」と「**送ったが届いたか不明**」を分離した。
その裏側に、同型の混同がもう 1 つ残っていた ——「**確認できた拒否**」を「**手仕舞い済み**」として扱っていた。

`ProtectiveStopGuard.ReplaceOrCloseAsync` と `OrderExecutionAppService.CloseUnprotectedPositionAsync` は、
`PlaceMarketOrderAsync` が**返り**さえすれば `closeOrder.Status` を見ずに成功として扱っていた。
発注前検証の棄却や OpenD の `retType != 0` は**終端 `Rejected` を返す**（例外ではない）ため、この経路に入る。

| 帰結 | 内容 |
| --- | --- |
| 通知が事実と逆 | Critical で「建玉を成行で手仕舞いました」と言うのに、建玉は残っている |
| 🔴 巡回から消える | 保護記録が `Completed` になり、**逆指値なしの建玉を誰も見なくなる**（IADR-0210 の不変条件が無音で破れる） |
| 台帳が空押さえ | 送られてもいない決済の承認行が足され、30 分の窓のあいだ在庫を押さえる |

SIMULATE は公式に「指値・成行のみ」だが、時間外の成行や数量の制約で拒否され得る（#809 で逆指値の拒否を実測済み）。

## 検討した選択肢

### 拒否された行の扱い

| 案 | 内容 | 判定 |
| --- | --- | --- |
| (a) 完了させる（現状） | 状態を見ずに `PositionClosed` | **不採用。** 本 issue そのもの |
| (b) 予約を `Reserved` のまま据え置く（改定 7 と同じ形） | 次の巡回は入口 (b) で据え置き | **不採用。確定した事実を「不明」として扱うことになる。** 撃ち直しも起きず、出口が恒久的に塞がる |
| **(c) 記録は `Active` のまま・試行番号を進めて次の巡回で再評価**（採用） | S1 の `Settle`（IADR-0344 決定 5-6）と同じ形 | 既に系内にある形であり、巡回の不変条件（無保護の建玉は必ず誰かが見ている）を保つ |

### 撃ち直しの上限をどこに持つか

| 案 | 内容 | 判定 |
| --- | --- | --- |
| 上限を設けない | 30 秒ごとに成行を送り続ける | **不採用。** 同じ理由で拒否され続ける注文を叩き続けるのは、実弾では発注制限にも当たる |
| 永続列（`protective_stop_orders` に `CloseRejections`） | 再起動をまたいで数える | **不採用。** 消えない側に倒れる＝**再起動しても出口が閉じたまま**になる。保護の帳簿（`RemainingProtected` 等）と違い、この数えは**安全側が「忘れる」側**である |
| **プロセス内の数え（`CloseRejectionTracker`）**（採用） | `HeldCloseNotificationTracker`（改定 9）と同じ作法 | 再起動で数えが消える＝**もう一度手仕舞いを試みる**。倒れ方が fail-loud の向きに一致し、スキーマも増えない |

## 決定

### 決定 1: 「未約定残を二度と約定させない終端」が**返った**ら `PositionClosed` を主張しない

判定は既存の純関数 `OrderStatusLifecycle.AbandonsUnfilledRemainder`（`Rejected` / `Cancelled` / `Expired`。
**`Filled` を含まない**）を使う。新しい述語は作らない（IADR-0117 改定 2 の「足すなら述語を足す」に対し、
ここは**既にある述語がそのまま当たる**）。真のとき:

- 保護記録は **`Active` のまま**残し、**試行番号だけ**を進める（`RemainingProtected` は動かさない ——
  減ったのは建玉ではない）。次の巡回は新しい `CloseDecisionId` で改めて評価する。
- 発注結果（`ExecutionRecord`）は**保存する**（拒否の一次証跡。終端なので約定追跡には載らない）。
- 予約は **`MarkCompleted` で確定する**。確認できた拒否は不明ではないため、据え置く理由が無い。
- `ProtectiveStopCoverageLost(Remediation=CloseRejected)`（Critical）を発行する。
  🔴 **`CloseIntent` は運ばない**（生きていない成行を取引台帳に押さえさせない）。
  `CloseDecisionId` は**載せる**（拒否された発注記録との相関）。この非対称は意図であり、
  `ProtectiveStopEventPayloadTests` が往復で固定する（台帳側は「レグの有無」で分岐するため承認行は足されない）。

### 決定 2: 「記録済みの手仕舞いレグ」を読む入口でも状態を見る

改定 7 の入口 (a)（`store.FindByDecisionId(closeDecisionId)` に記録がある）でも、その記録が終端（拒否）なら
完了させない。送信直後に保護記録の更新だけが失われたクラッシュ窓では、**拒否された記録**が残るため、
ここを塞がないと次の巡回が「記録があるから手仕舞い済み」と読む（決定 1 と同じ誤りが別経路で再発する）。

### 決定 3: 撃ち直しの上限は 3 回。数えはプロセス内に持ち、上限に達しても記録を閉じない

- 上限は S1（`SoftwareStopExecutor.MaxCloseAttemptsPerTrigger`）と同じ **3**。
- 数えと再通知の記憶は `CloseRejectionTracker`（singleton・**非永続**）。再起動で消える＝改めて 3 回試す。
- 上限に達した行は**成行を送らない**が、**記録は閉じない**（閉じると巡回から外れ、無音で無保護の建玉が残る）。
  未通知なら即座に、以後は **1 時間ごと**に `CloseRejected` を発行し直す（`CloseDecisionId` は null ——
  その巡回では 1 本も送っていないため、送っていない ID を載せない）。
- **逆指値の再発注には上限を掛けない**（保護の回復は常に試みてよい）。再発注に成功したら数えを 0 へ戻す。

### 決定 4: 出口を入口のガードで塞がない

上限は**成行手仕舞い（出口）だけ**に掛ける。逆指値の再発注・建玉消滅時の取消・S1 の決済・利用者の手仕舞いには
掛けない。また、上限に達しても保護記録を閉じない（閉じることは「出口を塞いだうえで忘れる」ことである）。

### 決定 5: 可観測性でも「拒否」を「不明」に混ぜない

`ProtectiveStopGuardResult` に `CloseRejected` 件数を**末尾へ**足し、`Unknown`（据え置き＝不明）とも
`ClosedOut`（解消した）とも混ぜない。通知・監査の文面も 3 者を書き分ける
（「手仕舞いました」／「送ったが届いたか不明」／「拒否された・建玉が残っている」）。

## 理由

- **fail-loud であって fail-close ではない。** 拒否は情報の欠落ではなく確定した事実であり、
  それを握り潰して完了扱いにすると、**唯一の保護であるはずの巡回から建玉が消える**。
  倒れる向きは常に「まだ守っている・まだ鳴っている」側に取る。
- **上限を非永続にするのは、消える向きが安全側だからである。** 保護の帳簿（`RemainingProtected`・
  `PendingExternalReduction`）は消えると売り過ぎ／保護喪失に直結するため永続だが、
  この数えは消えると「もう一度出口を叩く」だけである。IADR-0117 改定 9 の通知記憶と同じ判断。
- **S1 が既に持っている形を S0 へ写した**（IADR-0344 決定 5-6）。同じ問いに 2 つの答えを持たない。

## 結果

- 拒否された手仕舞いの建玉は巡回対象に残り、通知は Critical のまま**事実を言う**ようになる。
- 取引台帳は拒否された手仕舞いレグの承認行を持たなくなる（空押さえが消える＝利用者の手仕舞いが通る）。
- 30 秒ごとの成行の連打は 3 回で止まり、通知は 1 時間ごとに続く。

## 残余リスク

- **終端かつ部分約定ありの手仕舞いレグ**（一部約定してから `Cancelled` 等）は、約定追跡（IADR-0113）が終端記録を
  ポーリングしないため `OrderExecuted` が出ず、**部分約定が取引台帳へ届かない**。本 IADR 以前からの性質であり
  （`PositionClosed` を主張していた従来も台帳の建玉は減らなかった）、ここでは直さない。
  次の巡回は**ブローカーの建玉照会**から数量を引き直すため**売り過ぎは起きず**、差は乖離として検知される（IADR-0118）。
- **上限に達した後の自動復旧は無い**（人が証券会社の画面で手仕舞うか、原因を取り除く）。
  再起動・逆指値の再発注成功のどちらかで数えは戻る。
- エントリー同時の経路（`CloseUnprotectedPositionAsync`）には**保護記録が無い**ため、拒否された建玉を
  巡回へ載せる手段が現状ない（通知が唯一の検知）。保護レグを持たないまま台帳へ載る建玉の扱いは #853 の射程である。
