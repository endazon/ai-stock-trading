# IADR-0280: IADR 欠番 16 件は繰り下げず受容し、運用ルールを「欠番なし」から「再利用禁止」へ改める

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: Accepted
- 日付: 2026-09-02
- 決定者: 利用者（裁定） / Claude（worker・issue #573 担当）

## 起点・関連

- 関連する計画書 ID（FR/UC/SC/ADR）: なし（規約整備・工程管理のメタ作業。
  `.claude/rules/traceability.md` の無採番 NFR 許容 2 に該当）
- 関連する実装仕様書: `.ai-context/specs/20260902_573_iadr-gap-acceptance.md`
- 起点 issue: #573（「IADR 16 件の欠番」）
- 先例: `IADR-0060` の欠番解消（`.ai-context/specs/20260717_iadr-0060-gap-renumber.md`）、
  `IADR-0164` の欠番解消（`.ai-context/specs/20260807_iadr-0164-gap-renumber.md`）

## コンテキストと課題

`.ai-context/adr/README.md` の運用ルールは「連番はリポジトリ内で一意・昇順・欠番なし」と定めていた。
2026-08-28、計画大改定（#344）の全面再実装を 12 本のブランチで並行実装するにあたり、ウェーブごとに
5 番ずつ範囲を先行割当して採番衝突を防いだ。衝突は起きなかったが、各ウェーブが割当を使い切らず、
`IADR-0209` / `0213` / `0214` / `0229`〜`0239` / `0243` / `0244` の計 16 件が欠番として残った。

issue #573 は当初、この欠番を `IADR-0060`（5 件）・`IADR-0164`（2 件）の先例と同じ手順（繰り下げ）
で解消する前提で起票された（起票時点の誤カウントでは 20 件）。**しかし本作業の着手にあたり実測した
結果、繰り下げの対象範囲は先例と桁違いに大きいことが判明した。**

### 実測（着手時点・2026-09-02）

- 欠番 16 件（`.ai-context/adr` の実ファイル `0000`〜`0271` を走査。issue #573 のコメントの
  実測値と一致・その後の並行採番による変動なし）。
- 16 件を繰り下げて詰めるには、`IADR-0210`〜`IADR-0271`（欠番より上のすべて）のファイル改名が
  必要 —— **47 ファイル**。
- 改名対象の番号への参照は、本文・索引・仕様書・コード内コメント・PR タイトル等に
  **2,339 箇所／450 ファイル**（リポジトリ全体走査）。
- 加えて、`.claude/rules/traceability.md` §採番衝突時の改番手順が定める追随 5 項目のうち
  「PR タイトル」は**プッシュ済みの中間コミットの件名を force push 禁止のため書き換えられない**
  （`IADR-0164` 先例と同じ制約）。**本件は対象 PR 数が 12 本と多く**、develop へマージ済みの
  すべてのコミット件名が旧番号のまま恒久的に残ることは避けられない。
- **他の並行 PR との衝突**: 47 ファイルの改名は、`.ai-context/adr/` 配下で作業する他のすべての
  並行 PR（新規 IADR の追加・既存 IADR の更新）とファイル競合を起こす。運用標準は「並列作業は
  ファイル領域の非重複で判定」（`docs/ai-implementation-workflow-guide.md`）であり、47 ファイルの
  改名は実質的にこの領域全体を専有する。

## 検討した選択肢

### 案 A: 繰り下げて欠番を解消する（issue #573 原案・先例踏襲）

`IADR-0060`・`IADR-0164` と同じ手順で、欠番より上のファイルを 1 つずつ繰り下げ、
`0000`〜`0255`（当時の上端）を「一意・昇順・欠番なし」に戻す。

- 良い影響: 運用ルール「欠番なし」を変えずに済む。索引が連番のままで読みやすい。
- 悪い影響:
  - 47 ファイル改名・2,339 箇所／450 ファイルの参照追随という、先例（5 件・2 件）より
    2 桁大きい規模のコストが発生する。
  - PR タイトル・develop マージ済みコミット件名は force push 禁止のため遡及修正できず、
    「繰り下げたのに旧番号を名乗るコミットが恒久的に残る」という、先例と同じ不整合が
    12 本分に拡大して残る。
  - 実施期間中、`.ai-context/adr/` 配下のほぼ全域を専有し、他の並行実装（新規 IADR 追加を含む）
    と衝突する。

### 案 B（採用）: 繰り下げを行わず欠番を受容し、運用ルールを改める

「欠番なし」を運用ルールから外し、「一意・昇順。欠番は許すが再利用は禁止」へ改める。
16 件の欠番は恒久的に記録として残し、新規採番は現在の最大番号＋1を続ける。

- 良い影響:
  - ファイル改名・参照追随のコストがゼロ。他の並行 PR と衝突しない。
  - 「再利用禁止」は維持するため、**同じ番号が別の決定を指す**という実害の大きい事故
    （索引・trace ブロック・検査器がすべて誤った決定を指す）は引き続き防げる。
  - 欠番という状態そのものは実害が小さい —— IADR の実在性検査（`check-commit-messages.js` /
    `gen-knowledge-graph.js`）はいずれも「ファイルとして実在するか」の集合演算であり、
    「連番が連続しているか」は検査対象にしていない（後述）。
- 悪い影響・トレードオフ:
  - 索引に歯抜けが残り、一覧の見た目の連続性は失われる。
  - 「欠番なし」を無条件の規律としてきた運用文化からの転換であり、今後も欠番が生じた際に
    「今回は許容か、繰り下げるか」の判断が要る（本 IADR は「実測して参照数が先例と同桁なら
    繰り下げ、桁違いなら受容」という基準を残す）。

## 決定

**案 B を採用する。** `.ai-context/adr/README.md` の運用ルールを「一意・昇順・欠番なし」から
「一意・昇順。欠番は許すが再利用は禁止」へ改め、16 件の欠番（`0209` / `0213` / `0214` /
`0229`〜`0239` / `0243` / `0244`）を恒久的に受容する。`.claude/rules/traceability.repo.md` に、
本リポジトリ固有の上書きとして「採番衝突時は次の空き番号ではなく新たな最大＋1へ改番する」を
明記する（配布物 `.claude/rules/traceability.md` の「欠番を作らない」改番手順を、本リポジトリでは
採らない）。

## 理由

- **コストが便益に見合わない。** 「欠番なし」という見た目の整合性を回復するために、
  47 ファイル・2,339 箇所という、実際の意思決定内容には影響しない機械的な改名作業へ、
  他の全実装作業を止めて充てることになる。
- **検査器はいずれも実害（再利用・誤参照）だけを見ており、欠番の有無を見ていない。**
  `check-commit-messages.js` の `loadExistingIadrIds()` と `gen-knowledge-graph.js` の IADR 実在性
  検査は、いずれも `.ai-context/adr/` の実ファイル名から作った `Set` への所属判定であり、
  「番号が連続しているか」を要求するロジックを持たない（下記「結果」に実測を記す）。
  **したがって「欠番を許す」への変更は、既存の検査器を 1 つも変えずに安全に行える。**
- **先例との量的な違いが質的な違いを生む。** `IADR-0060`（5 件）・`IADR-0164`（2 件）は
  当時の未マージ PR が僅かで、繰り下げの追随範囲も小さかった。本件は 12 本の並行 PR・
  16 件という、同じ「繰り下げ」という手段を単純に拡大適用できる規模を超えている。

## 結果

- 良い影響:
  - 実装作業への影響ゼロで規約違反状態を解消できる（規約側を実態に合わせる）。
  - 今後、同種の大規模並行実装（先行割当の余剰）が起きても、繰り下げという高コストな手段に
    頼らず運用を続けられる。
- 悪い影響・トレードオフ:
  - 16 件の欠番は恒久的に残る（`.ai-context/adr/README.md` の注記で経緯を追跡可能にする）。
- フォローアップ:
  - 検査器 3 本（`check-adr-index-sync.js` / `check-commit-messages.js` /
    `gen-knowledge-graph.js --check`）を読んだ結果、いずれも欠番なしを前提にしていないことを
    確認した。**是正は不要**（`.ai-context/specs/20260902_573_iadr-gap-acceptance.md` §設計 に
    読解結果を記録）。
  - issue #573 は本 PR の内容（受容への裁定）でクローズする。project-planning への環流は
    行わない（本決定は製品要件ではなく工程のメタ規律であるため。
    `.claude/rules/traceability.md` の無採番 NFR 許容 2 と同じ扱い）。
  - **本 IADR 自身が、本ルールの初回適用例になった。** 着手時点では `IADR-0272` として起票したが、
    PR 作成後に develop 側の並行マージが立て続けに起き（#612 の `IADR-0272`・#500 の
    `IADR-0273`・#565 の `IADR-0274`・#566 の `IADR-0275`）、さらに `IADR-0276`〜`0279` は
    マージ前の他 PR がすでに予約していたため、その都度「その時点の新たな最大番号＋1」へ改番して
    `IADR-0272` → `0273` → `0274` → `0275` → `IADR-0280` と進んだ。いずれも develop への
    マージ順で先に確定した側を尊重した結果であり、本 IADR が定める「衝突時は次の空き番号ではなく
    新たな最大＋1」の運用どおりに解消した（欠番は生じていない）。
