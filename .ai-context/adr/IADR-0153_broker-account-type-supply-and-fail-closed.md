## コンテキストと課題

計画は 2026-08-04 の利用者裁定（ADR-0021）で「**信用口座と現金口座の双方に対応する**」方針を採った。
従来の前提（「米国は信用口座」で固定）から導かれていた「Good Faith Violation は発生しない → 差金決済ガードは
米国株に適用しない」（#332 / IADR-0132 決定5）は、**現金口座では成り立たない**。

**GFV の影響が運用上もっとも重い。** 違反しても即座には分からず、**3 回目で口座が 90 日間制限される**。
自動売買は回転数が多く、人間より速く 3 回に到達し得る（ADR-0021 46 行）。

ADR-0021 は「照会して判定する」「食い違えば止める」までは定めたが、実装に委ねた点が 5 つある。

1. **口座種別をどこからどう供給するか**（照会の頻度・キャッシュ・観測の鮮度を計画は定めていない）
2. **観測を永続化するか**（同じユニットの #385 / #386 / #387 は EF ストア＋マイグレーションまで作っている）
3. **決済済み資金を moomoo API から取得できるか**（ADR-0021 120 行が「確認する」を実装へ委ねた）
4. **内蔵 `paper` をどう扱うか**（ADR-0021 はブローカー口座の存在を前提としており、この形を想定していない）
5. **拒否理由を何種新設し、どう分類するか**（決定4-5 が明示したのは 1 種のみ。**起案時点の状態である**——
   本 IADR の環流を受けて **2026-08-07 に計画が 3 種を追認した**。下記 決定5 の追記を参照）

## 検討した選択肢

### 論点 A: 口座種別の供給経路

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | 注文ごとの文脈（`ShortSellOrderContext` と同じ形）で運ぶ | 口座種別は**注文ごとの外部入力ではなく運用状態**である。銘柄ごとの借株可否とは性質が違い、注文ごとに違う値が来ること自体が異常である |
| A-2 | 利用者設定（`TradingGuardSettings`）だけを情報源にする | ADR-0021 決定3 が明確に否定している。設定ミスが「統制が丸ごと無効になる」形で現れ、**しかも気づけない** |
| A-3 | リスク管理サービスから直接ブローカーへ照会する | ブローカー接続を持つのは発注執行サービスだけである。統制の判定コアに外部 I/O を持ち込むと、判定が非決定的になり `RiskEvaluator` の純関数性が壊れる |
| **A-4** | **発注執行の定期 probe が観測として発行し、リスク管理が最新 1 件を保持する** | #385 / #386 / #387 で確立した形に揃う。**新しい常駐を増やさない**（`TrdGetAccList` は接続確立時に既に呼ばれている）。沈黙が安全側に倒れる |

### 論点 B: 観測の永続化

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | EF ストア＋マイグレーションで永続化する（#385 / #386 / #387 と同じ） | それらが永続化するのは**時間をまたいで積み上げる集計**（稼働営業日数・取引件数・統制違反件数）であり、**再観測で復元できない履歴**である。口座種別は「いまブローカーへ照会すれば得られる現在値」であり性質が違う。永続化すると**ブローカーが応答しなくなった後も古い種別で回り続ける**危険が生まれる |
| B-2 | 永続化し、鮮度（有効期限）で古い値を切る | B-1 の危険は鮮度で消える。ただし**得るものが無い**——復元されるのは高々 1 probe 間隔ぶんの猶予であり、その間に口座種別が変わっていないという保証はどこにもない。マイグレーション・行の一意性・時刻の権威といった保守対象だけが増える |
| **B-3** | **永続化しない（プロセス内・最新 1 件）＋ 鮮度で古い値を切る** | 再起動で観測が消える＝**新規建てが止まり、次の probe（既定 5 分）で復帰する**。失敗モードが「止まる」側にしか無い。#385 系との差は「集計 vs 現在値」という性質の違いで説明でき、恣意的でない |

### 論点 C: 決済済み資金の取得可否（実測）

`moomoo-api` 10.8.6808（`MMAPI4Net.dll`）をリフレクションで全走査した（本セッションで独立に再実測）。

| 求める値 | SDK 上の該当 | 判定 |
| --- | --- | --- |
| 口座種別 | `TrdCommon.TrdAcc.AccType` / `TrdAccType_Unknown=0 / Cash=1 / Margin=2 / TFSA=3 / RRSP=4 / SRRSP=5 / Derivatives=6` | ✅ **取得できる**。列挙に `Unknown` があることは、**不明が起こり得る**ことを SDK 自身が認めている |
| **決済済み資金（settled cash）** | `TrdCommon.Funds` の 42 プロパティを全走査（`Cash` / `AvlWithdrawalCash` / `AvailableFunds` / `NetCashPower` / `Power` / `MaxWithdrawal` / `FrozenCash` / `DebtCash` / `PendingAsset` / `BeginningDTBP` / `RemainingDTBP` ほか）。アセンブリ全体で `Settl` / `unsettled` / `sellable` / `freecash` を含む取引系プロパティは **`TrdFlowSummary.FlowSummaryInfo.SettlementDate` のみ** | ❌ **専用フィールドは存在しない** |
| GFV 発生回数 | `GoodFaith` / `good_faith` / `Violation` / `Gfv` をアセンブリ全体で走査 → **0 件**。`Funds.IsPdt` / `PdtSeq` / `DtStatus` / `BeginningDTBP` / `RemainingDTBP`（PDT 系）はあるが GFV ではない | ❌ **存在しない** |

**紛らわしい候補を 2 つ明示的に棄却する**（「近い値があるから使えるのでは」という再検討を止めるため）。

- **`Funds.AvlWithdrawalCash` / `MaxWithdrawal`**: これは**出金可能額**であり、決済済み資金とは別概念である。
  出金可能性は入金の資金化・信用の拘束・規制上の保留といった別の制約を含み、GFV の分母（T+1 が未到来の
  売却代金を含めない買付可能残高）と一致する保証がない。
- **`MaxTrdQtys.MaxCashBuy`**（「現金で買える最大数量」）: **もっとも紛らわしいが、もっとも危険である。**
  ブローカーの「現金買付余力」は現金口座では**未決済の売却代金を含む**のが通例であり、
  それこそが GFV を引き起こす当の資金である。これを分母に使うと、**GFV 回避ガードが GFV を許可する**。

代替の導出経路として **`TrdFlowSummary`**（`ClearingDate` / `SettlementDate` / `CashFlowAmount` /
`CashFlowDirection` / `CashFlowID`）は存在する。`SettlementDate` を持つ入出金明細を積み上げれば決済済み資金を
導ける見込みだが、**実口座で値が返るかは未検証**（OpenD 非稼働・ADR-0019 の PoC 項目に無い）。

### 論点 D: 拒否理由の新設数

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D-1 | 計画が明示した `CashAccountSettlementHold` の 1 種だけを新設し、他は既存コードへ畳む | 決定3（照会失敗・食い違いで止める）と決定4-3（3 回目の手前で停止）は**統制としては要求されているのに、記録する理由コードが無い**。畳むと監査ログ（FR-11）が実態と食い違う |
| **D-2** | **3 種を新設する**（末尾へ追加・序数不変） | ADR-0016 決定10 の規律（原因も解除条件も異なるものを畳まない）に従う。3 種の解除条件は「T+1 の決済」「違反記録の失効 ※**2026-08-08 追補: 本記述は計画 ADR-0028 決定1/決定2 で部分改定された。**「失効」は採らず、**利用者の明示的な解除操作**（Discord `/gfv clear`）で解く（実装 [IADR-0182](IADR-0182_gfv-violation-clearing.md)）」「照会の成功」であり、いずれも互いに異なる。先例は `StopOrderRequired`（#329 で実装が先行し 2026-08-04 に計画が同名で追認） |

## 決定

### 決定 1: 口座種別は「定期 probe が発行する観測」として供給し、**沈黙を安全側に倒す**（論点 A）

```
[OrderExecutionService]                         [RiskManagementService]
MoomooBrokerAdapter : IBrokerAccountSource       BrokerAccountObservedHandler
  └ TrdGetAccList → TrdAcc.AccType                  ↓
        ↓                                       IBrokerAccountObservationStore（最新 1 件・鮮度つき）
BrokerAvailabilityProbeService（既存の 5 分巡回）     ↓
        ↓ **判明したときだけ**                   PortfolioSnapshot.Account
  BrokerAccountObserved ──────────────────→        ↓
                                              RiskEvaluator（純関数・決定的判定）
```

- **判明したときだけ発行する。** 到達不能・照会失敗・種別不明（`TrdAccType_Unknown` / TFSA 等の未対応値）は
  いずれも「発行しない」であり、受け手は沈黙を「口座種別を確認できていない」として扱う
  （`BrokerAvailabilityObserved` と同じ作法・IADR-0150）。
- 「不明である」をイベントで表す案は採らない。**その通知そのものが失われたとき**（プロセス断・ネットワーク断）に
  不明が届かないまま古い観測が生き残る。沈黙が安全側に倒れる向きを選ぶ。
- 口座種別は `PortfolioSnapshot.Account`（`KillSwitchEngaged` / `TradingPaused` と同じ場所）に載せる。
  **既定 `null` のプロパティ**にすることで、明示しない組み立てが統制の掛かる側へ倒れる。
- 判定コアは時刻を持たない（ステートレス・純関数を保つ）。観測の新しさは供給側（ストア）が担保する。
- 監査台帳（FR-11）へも記録する。「いつ・どの口座種別が観測されたか」の並びが無いと、事後に
  「なぜその時刻の注文で GFV 回避ガードが効かなかったのか」を再構成できない。

### 決定 2: 内蔵 `paper` は口座種別を要求しない（計画に無い判断）

`AccountTypePolicy.RequiresVerifiedAccount(BrokerProvider.InternalPaper) == false`。

- 内蔵 `paper` は**外部へ一度も発注しない擬似約定**であり、**ブローカー口座そのものが存在しない**。
  ADR-0021 はブローカー口座の存在を前提としており、この形を想定していない。
- **口座が無い以上、口座種別に依存する事故（GFV・日本の差金決済規制）も起こり得ない。**
  規制は現実の口座と現実の約定に対して働くものであり、擬似約定はどの規制の対象にもならない。
- **迂回路にはならない。** 迂回路とは「統制を避けて同じ結果（外部での約定）を得る道」であるが、
  内蔵 paper は外部へ注文を出さないため、そもそも侵し得る規制が無い。
- 供給側でも同じ判断を構造的に表す: `IBrokerAccountSource` は**moomoo 構成でしか DI 登録しない**。
  未登録なら probe は口座観測を発行せず、リスク管理側は moomoo 発注先の新規建てを止める。

### 決定 3: 観測は**永続化せず**、有効期間 30 分で失効させる（論点 B）

- `InMemoryBrokerAccountObservationStore`（singleton・プロセス内・最新 1 件）。EF ストアもマイグレーションも作らない。
- **有効期間 30 分**は `BrokerAvailabilityProbeOptions.IntervalSeconds` のクランプ上限（1800 秒）と同値である。
  健全な probe は**必ずこの窓の内に更新できる**（既定は 5 分間隔であり 6 倍の余裕がある）。逆に probe が
  止まれば観測は失効し、新規建てが止まる。
- **古い観測を無期限に信じる形は採らない。** 利用者が口座を切り替えた後も旧種別の統制が掛かり続けると、
  現金口座なのに信用口座の緩い統制で回転する（決定3 が防ごうとしている事故そのもの）。
- **有効期間が意味を持つには、probe が巡回のたびに実際にブローカーへ照会し直す必要がある**（2026-08-06 追記）。
  当初の実装は `MMApiMoomooTradeClient.GetAccountTypeAsync` が**接続時に確定した値をそのまま返して**おり、
  再照会していなかった。この形だと有効期間は「最後にブローカーへ聞いた時刻」ではなく「最後に自分の
  キャッシュを読んだ時刻」を測ることになり、**プロセスが起動しっぱなしで OpenD 接続が切れない限り、
  古い種別が「30 分以内に確認済み」の体裁で無期限に更新され続ける**。上の 2 項が主張する性質が
  成り立たなくなるため、毎回 `TrdGetAccList` を投げ直す形へ改めた（可用性の判定が毎回ライブで
  問い合わせているのと揃えた）。照会した口座が発注先の `accId` と異なる場合は、**種別を偽るより
  不明（null）へ倒す**。呼び出しは probe の巡回のみであり発注経路には乗らないため、費用は
  1 巡回あたり 1 リクエストである。
  なお `MMApiMoomooTradeClient` は `MMAPI_Trd` を直接生成しており差し替え口が無いため、
  **この再照会の挙動は単体テストで固定できていない**（アダプタ側の写像はフェイクで検証済み）。
- **逆行する観測（より古い時刻）は無視する。** 再配送・順序の入れ替わりで古い種別が新しい観測を上書きしない
  （ADR-0013 / IADR-0129 決定10 の冪等性）。
- **#385 / #386 / #387 と設計が違う理由**は「集計 vs 現在値」である。それらが永続化するのは
  稼働営業日数・取引件数・統制違反件数という**再観測で復元できない履歴**であり、失われれば段階ゲートの
  合格証跡が消える。口座種別は次の probe で復元でき、復元までの間は**止まっている**（＝安全側）。

### 決定 4: 決済済み資金・GFV 発生回数は**供給せず、供給が無ければ現金口座の買付を止める**（論点 C）

- moomoo API に該当フィールドは存在しない（論点 C の実測）。アダプタは `BrokerAccountState` の
  `SettledCashInBase` / `GoodFaithViolationCount` を **`null` のまま返す**。
- **推定値・代替値で埋めない。** 特に `MaxCashBuy` は現金口座では未決済の売却代金を含み得るため、
  分母に採ると **GFV 回避ガードが GFV を許可する**（論点 C の棄却理由）。
- **`null` は「通す」ではなく「止める」へ倒す。**
  - 決済済み資金が `null` → 現金口座の**買付**を `CashAccountSettlementHold` で拒否
  - GFV 発生回数が `null` → 現金口座の**新規建て**を `GoodFaithViolationLimitReached` で拒否
    （2 回に達していないことを**確認できない**ためであり、3 回で 90 日という不可逆な結果に対して
    「分からないから通す」は統制にならない）
- **帰結を明記する: 現時点で現金口座の新規建ては常に止まる。** これは欠陥ではなく設計である——
  決済済み資金を知らずに現金口座を回すことは、GFV 回避ガードが無いのと同じである。
  供給経路（`TrdFlowSummary` からの導出）は本作業の対象外とし、計画（ADR-0019 の PoC 項目）へ環流する。
- **売却（Sell）は本ガードの対象外**である。GFV は「未決済の売却代金で買った」ことで起きるものであり、
  売り自体を止める理由が無い。**手仕舞いも止めない**（ADR-0009 の不変条件）。
- 買付の判定は**当日の新規建て累計 ＋ 本注文**で行う。1 件ずつの比較では、決済済み資金の範囲内の注文を
  複数回通して累計で超過できる（Issue #27 と同じ穴）。ブローカーが約定時点で現金を引き落としていれば
  二重計上になり得るが、**過剰拘束（発注が止まる）側**であり安全である。

### 決定 5: 拒否理由を 3 種新設し、クラス A / B へ分類する（論点 D）

**新設は常に末尾**（序数不変・IADR-0134 決定2）。序数 25 / 26 / 27。

| 拒否理由 | クラス | 解除条件 | 根拠 |
| --- | --- | --- | --- |
| `CashAccountSettlementHold` | **A** | T+1 の決済 | ADR-0021 決定4-5 が明示 |
| `BrokerAccountTypeUnverified` | **B** | 照会の成功（と設定値の一致） | 「取引を止めている状態そのものの記録」。KillSwitch / Paused / 段階制約と同じ区分 |
| `GoodFaithViolationLimitReached` | **A** | 違反記録の失効 | 統制が設計どおり作動した記録 |

- **クラス C（`BannedSymbol` / `ManipulativeOrderPattern`）へ混ぜてはならない。** クラス C は
  「AI が禁止事項を犯そうとした件数」であり、段階昇格ゲートの「統制違反 0 件」が数える対象である
  （06_daytrading-review §4.1）。制度・決済・接続に由来する事象を混入させるとゲートが機能しなくなる。
- `SameDayReentry` の米国株への適用拡大は**クラス A のまま**である（分類は理由コードごとであり、
  適用範囲の拡大では変わらない）。

  **【✅ 差異は解消 2026-08-07】環流を計画が受理し、ADR-0021 決定4-5 が 3 種を同名・同クラス（A / B / A）で追認した**

### 決定 6: 口座種別依存の統制は `AccountTypePolicy`（純関数）に集約する

ADR-0021 112 行が「口座種別に依存する統制の切り替えが 1 か所で定義され、各文書はここを参照できる」ことを
良い影響として挙げている。実装側でも 1 か所に集める。

| メソッド | 意味 |
| --- | --- |
| `Supports(accountType, productType)` | その口座種別で**成立し得る**商品種別か（現金口座は現物のみ） |
| `AppliesSameDayReentry(market, effectiveProductType, accountType)` | 差金決済防止の適用可否。**現物**に限り、`日本市場 ‖ 現金口座` |
| `AppliesShortSellControls(accountType)` | ADR-0016 の空売り統制群を評価するか。**不明なら評価する**（省くと緩む） |
| `RequiresVerifiedAccount(provider)` | 口座種別の確認を要求するか（決定2） |
| `BlocksForGoodFaithViolations(count)` / `WarnsForGoodFaithViolations(count)` | GFV の停止・警告（しきい値 2） |

**`AppliesSameDayReentry` の条件が「市場 ‖ 口座種別」の**論理和**である点が要点である。**
#332 が確定した「日本株の現物」は日本の差金決済規制（金商法 161 条の 2）由来であり**口座種別に依存しない**。
#375 が足したのは Good Faith Violation 由来の第 2 の項だけであり、**#332 の是正は巻き戻していない**。

### 決定 7: 現金口座での信用系は**設定側と発注側の両方**で塞ぐ（多層防御）

- **設定側**: `RiskSettingsService.UpdateGuard` が、観測された口座種別で対応できない商品種別を有効化しようと
  する要求を `ArgumentException`（HTTP 400）で拒否し、**設定を一切変更せず履歴も残さない**
  （IADR-0141 / IADR-0151 決定2 と同じ規律。拒否された要求を履歴に積むと、実際には起きていない変更が
  監査上の事実になる）。計画は「**選べなくする**」（決定4-4）と定めており、「設定はできるが発注はできない」
  状態を作らない。
- **発注側**: 実効的に有効な商品種別を「利用者設定 ∩ 口座が対応する種別」で解決し、既存の
  `ProductTypeDisabled` で拒否する。設定側だけでは API を直に叩く経路と、口座種別を切り替えた後に
  古い設定が残る経路が塞がらない（IADR-0141 決定1「画面だけの統制は API 直叩きで消える」）。
- **観測が無いときは設定側では制限しない。** 設定の保存は発注そのものではなく、観測が無い状態で設定変更まで
  止めると「統制を厳しくする方向の変更」も道連れに止まる。**安全性は発注側が担保する**——同じ状態で
  新規建ては `BrokerAccountTypeUnverified` で止まっている。
- **適用は新規建てのみ**（ADR-0007 2026-08-04 追補）。**口座種別を切り替えた瞬間に、その口座で建てた
  信用建玉が閉じられなくなる**ことを防ぐ。手仕舞いを塞ぐと FR-10 の不変条件（ADR-0009）に反する。
- **決定5（ADR-0021）**: 現金口座では ADR-0016 の空売り統制群を**評価しない**。空売りが「無効に設定されている」
  （`ShortSellDisabled`）のとは別の状態であり、**口座の能力**の問題である。

### 決定 8: 利用者設定の口座種別は**省略を「変更しない」として扱う**

`PUT /risk-controls/settings/guard` は全置換であり、SC-02 の画面は口座種別を編集も送信もしない。
非 nullable enum で受けると**送り漏らした瞬間に既定値 0（＝信用口座）へ黙って戻る**——
禁止銘柄を 1 件足しただけで口座種別の設定が消える。`BrokerProviderUpdateRequest.Provider` と同じ規律
（「送っていない値へ黙って切り替わる経路を作らない」）で `AccountType?` として受け、`null` は現行値を保つ。

（結果としては fail-closed である——設定値が信用口座へ戻れば観測〔現金口座〕と食い違い、発注が止まる。
しかし「無関係な編集で利用者の設定が消え、発注が全面停止する」のは欠陥であり、安全側だからと放置しない。）

## 影響

### 良い影響

- 口座種別に依存する統制の切り替えが **1 か所（`AccountTypePolicy`）** に集約され、計画・仕様書がそこを参照できる。
- 失敗モードが**すべて「止まる」側**に揃った。照会失敗・種別不明・設定値との食い違い・決済済み資金の未供給・
  GFV 回数の未供給・観測の失効・プロセス再起動のいずれも新規建てを止め、手仕舞いは止めない。
- 新しい常駐を増やしていない（既存の 5 分 probe に相乗り）。OpenD への照会回数も増えない。
- #332 の是正（差金決済ガードの日本株現物への限定）が**信用口座では厳密に保たれる**ことをテストで固定した。

### 悪い影響・リスク

- **現金口座の新規建ては現時点で常に止まる**（決定4）。現金口座を実際に運用するには、決済済み資金と
  GFV 発生回数の供給経路が要る。`docs/blocked-tasks.md`「実装したが実際には発動しない機能」へ記載する。
- **有効期間 30 分と probe 間隔の最大値が同値**である。巡回間隔を上限（30 分）に設定すると観測が境界上に
  並び、巡回の遅延ぶんだけ失効の窓が生じ得る（既定 5 分では起こらない）。失効側＝発注が止まる側であり
  安全ではあるが、上限設定での運用は推奨しない。
- 観測を永続化しないため、**リスク管理サービスの再起動直後は新規建てが止まる**（最大 1 probe 間隔）。
  これは意図した挙動である。
- 2 回目の GFV 警告の**通知経路（Discord）は結線していない**。判定（`WarnsForGoodFaithViolations`）は
  純関数として置いてあるが、呼び出す側が無い。GFV 発生回数の情報源自体が無いため、結線しても発火しない。

## 代替案（不採用）

- **「不明なら信用口座とみなす」**: ADR-0021 79 行が防ごうとしている当の事故である。現金口座なのに
  GFV 回避ガードが無効のまま回転し、3 回の違反で 90 日の口座制限に至る。しかも**事後にしか分からない**。
- **決済済み資金を `AvlWithdrawalCash` / `MaxCashBuy` で近似する**: 論点 C を参照。とりわけ `MaxCashBuy` は
  未決済の売却代金を含み得るため、ガードが守ろうとしている当の資金を分母に据えることになる。
- **観測を EF で永続化する**: 論点 B-1 / B-2。得るものが無く、古い観測を信じる危険と保守対象が増える。
- **拒否理由を 1 種に畳む**: 論点 D-1。解除条件の異なる 3 状態が監査ログ上で区別できなくなる。
- **口座種別の確認を内蔵 paper にも要求する**: 存在しない口座の種別を要求することになり、
  「観測が永久に発行されない → 内蔵 paper で一切発注できない」＝ Stage 0/1 の検証が止まる。
  規制上の実益はゼロである（外部へ注文を出さないため）。
