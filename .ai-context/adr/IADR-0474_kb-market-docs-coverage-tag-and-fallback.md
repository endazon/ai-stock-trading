## 背景

2 本目の検索は `AttributeFilters: null`・TopK・新しい順で引き、取得後に `symbol` を持つ文書を落としていた。落とした枠は補充されない。
情報収集は銘柄を持つ文書（現在値・企業ニュース）を 5 分ごとに書くので、新しい順の上位 TopK 件（基盤の候補は関連度の 4×TopK）が
銘柄つきで埋まると、市場全体の文書（google-news・FRED・BoJ・収集状態）と確定報告書が 0 件になる。#1078 の目的に反する。
実データの混ざり方は測っていない。

基盤の `AttributeFilters` は**キー → 単一の値の完全一致**で、キー間は AND。多値の OR は `Scope` の `AllowedValues` にしか無い。
**「属性が無い」「値が等しくない」は書けない**（判定は集合帰属だけで否定を持たない。フィルタのキーを持たない文書は除外される）。
基盤は保存時に `confidentiality` 以外の属性を検証しない（辞書照合なし）。取り込みは全属性をチャンクの payload へ写すので、新しい属性でも絞れる。
保存時点で銘柄を持たない文書には「銘柄が無い」を表す属性が無かった（情報収集は `kind`・`source`・`publishedAt`、報告書は `periodKey`・`kind`・`assumptionsVersion`・`confirmedAt`）。

## 決定

### 決定1: 銘柄を持たない文書に保存時の目印 `coverage = market` を付ける

- 情報収集（`KnowledgeBaseWriterSink.ToDocument`）: 銘柄が空・空白のときだけ付ける（収集状態を含む）。銘柄を持つ文書には付けない。
- 確定報告書（`ReportKnowledgeMapper.ToDocument`。確定の REST・gRPC の代理書き込み・入れ直しの共通の写像）: 常に付ける。
  **付けないと、目印つきの収集情報が TopK 件たまった後は補充が止まり、報告書だけが 2 本目から構造的に落ちる**（UC-01 手順 3 の後退）。
- キーと値は共有物 `KnowledgeSearchAttributes.Coverage` / `MarketCoverage` の 1 か所に置く。
  キー名に `scope` を使わない（基盤の `Scope`〔ABAC の許可〕・`doc_scope`〔個人資料と組織文書〕と紛れる）。タグには載せない（タグは辞書検証を通る静的語彙。IADR-0315）。
- 後方互換: 属性を 1 つ足すだけで、既存の属性・タグ・保存済みの指紋は変えない。基盤は未知の属性キーを拒否しない。

### 決定2: 2 本目は `coverage = market` の単値フィルタで引く

フィルタは基盤で候補を取る前に効くので、銘柄つきの文書に候補の枠を取られない。クエリ・TopK・新しい順は従来どおり（クエリに銘柄を入れない）。

### 決定3: 目印つきが TopK 件に満たない間だけ、フィルタなし・TopK×4 件で補充する

- 2 本目から残った件数（銘柄なし・足切りを通ったもの）が TopK 未満のとき、3 本目をフィルタなし・`TopK × 4`（`int` の上限で頭打ち）・新しい順で引き、
  銘柄を持たない文書だけを、重複（文書 ID ＋ 本文＝チャンク）を除いて後ろへ足す。同じ文書の別のチャンクは従来どおり別に数える。
- 判定は**足切りの後**の件数で行う。目印つきが TopK 件あっても全部古ければ 0 件になるためである。
- 倍率 4 は基盤が関連度の候補を取る倍率と同じ値。配備前の文書（目印なし）を拾う確率を上げるだけで、確定ではない（残余）。
- 並びは「銘柄の文書 → 目印つき（基盤の新しい順）→ 補充（基盤の新しい順）」。目印つきは配備後、補充は主に配備前の文書なので、おおむね新しい順を保つ。

### 決定4: 市場側は TopK 件で切る

目印つき＋補充を TopK 件で切る。注入は従来どおり最大 2×TopK 件で、IADR-0313 の予算の前提（縮退は TopK 約 127 以上）を変えない。

### 決定5: 要求の回数

定常（目印つきが TopK 件以上）は 1 判断 2 回で、従来と同じ。目印つきが足りない間（配備直後・文書の少ない環境）だけ 3 回。

### 採らなかった案

| 案 | 評価 |
| --- | --- |
| (a) 2 本目の TopK を広げるだけ（`topK×4`） | 要求は 2 回のままだが確率の改善にとどまる。銘柄つきが 5 分ごとに増えるので、広げた範囲も埋まれば 0 件に戻る |
| (b) 目印で絞るだけ | 配備前の文書（確定報告書の過去分・直前のマクロ）が配備の瞬間から届かなくなる |
| (b) ＋ 常に補充 | 結果は採用案と同じで、定常の要求が毎判断 1 回増える |
| 補充の判定を足切り前の件数で行う | 目印つきが全部古いと 0 件のまま補充しない |
| 旧文書へ目印を遡及付与 | 基盤に属性の部分更新が無く、全文書の再登録になる |
| 基盤に「属性が無い」条件を足す | 基盤を改修しない。基盤の評価モデルは否定を持たない |

## 窓の表（規則 11）

配備の前後で目印を持つ文書と持たない文書が入れ替わる。P1＝配備後の市場全体の文書が新しい銘柄つきに囲まれる（増える側）、
P2＝配備前の文書だけがある（減る側）、P3＝目印つきが TopK 件以上ある（定常）。

| 形 | P1 | P2 | P3 |
| --- | --- | --- | --- |
| 後の端だけ（目印のフィルタだけ） | ✓ | ✗ 旧文書が届かない | ✓ |
| 前の端だけ（フィルタなしで広げる） | ✗ 広げた範囲も埋まれば 0 件 | △ 範囲内なら届く | ✓（P1 と同じ欠陥） |
| **両端（目印で引き、足りない間だけ補充）＝採用** | ✓ | ✓ | ✓（要求 2 回） |

## 結果

- 保存: 情報収集の銘柄を持たない文書と確定報告書の写しに属性 `coverage=market` が増える。
- 検索: 2 本目が `attributeFilters: {"coverage":"market"}` を送る。3 本目は条件付きで `attributeFilters` なし・`topK` は 4 倍。
- 試験: T-10-1980〜T-10-1989（テスト仕様書の該当節）。

### 残余リスク

- 実データの混ざり方は測っていない。配備前の文書が補充（4×TopK）に入るかは確率のまま。配備後に書かれた文書は確定で届く。
- 目印つきが TopK 件たまると補充は止まり、配備前の文書は以後届かない。報告書は確定のたびに目印つきの写しが入り、入れ直しも欠けた写しを目印つきで作る。既存の写しへの遡及はしない。
- 2 本目は市場全体の文書と報告書が同じ枠を取り合う。報告書の比率は収集の頻度に左右される（報告書の枠を分ける拡張は後続）。
- 新しい書き手が銘柄を持たない文書を書くときは同じ目印を付ける必要がある。付け忘れは補充の側で拾える場合があるが、確定ではない。
- 文書の少ない環境では毎判断 3 回の要求になる。
