# IADR-0379: 壁時計どうしの競争で合否が決まる試験の判別軸を定め、上限の試験は「応答しない上流」で固定する

- 状態: Accepted
- 日付: 2026-09-23
- 決定者: claude (Claude Code) / #885

## 起点・関連

- 起票: [#885](https://github.com/endazon/ai-stock-trading/issues/885)（集約 issue）。
- 先行: [IADR-0364](IADR-0364_grpc-deadline-test-excludes-connect-from-budget.md)（#885 本体・PR #896）／
  [IADR-0366](IADR-0366_per-kind-timeout-test-uses-synchronization-point.md)（#900・PR #906）／
  IADR-0367（#901・PR #907。本作業時点で未マージ）。**いずれも 1 ケースずつの是正**であり、
  本 IADR は**残りの同型を一括で扱う規律**を定める。3 者の決定を覆さない。
- 関連する実装仕様書: `.ai-context/specs/20260923_885_wall-clock-timeout-test-inventory.md`

## コンテキストと課題

全ソリューション並列実行（`dotnet test backend/backend.slnx`）でだけ 1 件落ちる試験が、
2026-09-19 の並行作業で繰り返し観測された。**原因が同定できた 3 件はすべて同じ形**である。

> **タイマーのコールバックはスレッドプールが配送する。** プールが塞がっている間は
> 100 ms の打ち切りも 600 ms の遅延も配送されず、空いた瞬間には**両方とも期限切れ**で、
> **どちらが先に走るかは保証されない。**（PR #906 / #907 の計装による実測）

したがって「短い打ち切り」対「長い遅延」は、**比が 40 倍でも順序が保証されない**。
これは待ち時間を延ばしても消えない（IADR-0364 決定 5 の実測: 1 秒の予算を 1287.9 ms 食う瞬間があった）。

🔴 **課題は「どれが同型か」を言い当てることだった。** #885 は最初の棚卸しで
「テスト自身が渡した遅延は競争ではない」という軸を採り、**その軸で `Http*Tests` の群を除外して**しまい、
のちに**除外した群から 2 件が実際に落ちて**訂正している。同じ棚卸しで
`CollectionPollingServiceTests` を grep の行だけから「最も形が近い」と名指しし、これも訂正している。

## 決定

### 決定 1 — 判別の軸は「合否を決める 2 つの時刻が、どちらも壁時計か」である

- **「テストが遅延を渡したかどうか」で分けない**（#885 が撤回済み）。
- **否定形の表明（「起きなかった」）は同型に数えない。** CPU 枯渇下ではむしろ通りやすくなる。
  肯定形（「起きたはず」）と、上限で倒れることの表明だけが危うい。
- **grep の行だけで性質を推定しない。呼び出し元と表明まで読む**（規則 9・10 を自分の推論にも当てる）。

### 決定 2 — 上限（タイムアウト）の試験は「遅い上流」ではなく「応答しない上流」で書く

`DelayingHandler(TimeSpan)` を **`NeverRespondingHandler`** へ置き換える。

```csharp
await Task.Delay(Timeout.InfiniteTimeSpan, cancellationToken).ConfigureAwait(false);
```

- 固定したい性質は「**上限に達したら安全側へ倒す**」であり、上流が何ミリ秒遅いかではない。
  無期限は「上流が上限より遅い」の極限であり、**性質は弱まらず、応答が勝つ余地だけが消える**。
- **上限値そのもの（50 ms 等）は動かさない。** 値を動かすと、固定したい対象がずれる。
- 呼び出しは `Guard`（30 秒）で包む。**合否の基準ではない** ——
  打ち切りが効かなくなったときに黙って固まる代わりに理由付きで赤くするためだけの上限である。
- **応答ではなく打ち切りで終わったこと**を、ハンドラ側の `TaskCompletionSource` で観測して確定させる。

### 決定 3 — 「赤くならない同型」も是正する

変異注入（遅延を勝たせる）で分けたところ、同型 10 ファイルのうち **4 件は遅延が勝っても緑**だった
（上流の応答本文が、打ち切り時の安全既定と同じ値に写るため）。

**これらも是正する。** 偽の赤は出ないが、代わりに**「タイムアウトを検査している」という名前が嘘になる**
——負荷が高い日には打ち切り経路を一度も通らずに緑になる。是正後は、上限を無効化する変異で赤くなる
（実測。それまでは緑のままだった）。

### 決定 4 — 検査器は「足す」。ただし投入は #906 / #907 のマージ後とし、allowlist は空で始める

- **条件は満たしている。** 運用標準は「同型の事故が 2 回起きたら」であり、**実際に落ちるところを捉えたのは 3 件**
  （#885 / #900 / #901）。
- **形 (a) は機械的に検出できる。** 「同一テストファイル内で、有限の実時間の打ち切り
  （`HttpClient.Timeout = TimeSpan.From…` / `CancelAfter(TimeSpan…)` / `new CancellationTokenSource(TimeSpan…)` /
  `Deadline = …Add…`）が、実時間の遅延（`Task.Delay(<定数>)` / `Thread.Sleep(<定数>)` /
  `DelayingHandler(TimeSpan…)`）より**小さい**」。試作で **632 テストファイル中 12 件**が当たり、
  **12 件すべてが真陽性**（偽陽性 0）。`Timeout.InfiniteTimeSpan` は有限でないため当たらない。
- **allowlist の形**: `check-tracked-session-timeout.js` の `ALLOWED_FILES` と同じく、
  **ファイル単位＋理由＋起票 ID** の定数表とする。**本決定の時点で登録すべき項目は無い**
  （本 PR ＋ #906 ＋ #907 で 12 件すべてが消える）。
- 🔴 **今は入れない。** 本 IADR の変換を当てた後も **1 件**（`HttpCostControlGateTests.cs`）が残り、
  これは**未マージ**の PR #907 が直す。先に入れると develop が赤くなり、それを避けるために
  allowlist へ先回りで登録するのは `check-banned-libraries.js` が明示的に採らないと書いている運用
  （「移行前に登録して検査を無効化する」）である。**#907 と本 PR が揃った時点で、allowlist 無しで入れる。**
- **形 (c)（Wolverine の `IServiceProvider.ExecuteAndWaitAsync`＝既定 5 秒）は別物として扱う。**
  既存の `check-tracked-session-timeout.js` が素の `TrackActivity()` だけを禁じており、この overload は素通りする。
  同スクリプトの拡張として別 issue **#922** で扱う（#357 が 5 秒をスケジューリング遅延だけで超えた実測を持つ）。
  **形 (a) の検査器そのものは #921** に、検出規則・的中率・allowlist の形・着手条件つきで起票した。

## 検討した選択肢

| # | 案 | 評価 |
| --- | --- | --- |
| A | 上限値を上げる（50 ms → 数秒） | **採らない。** 固定したい値そのものを動かす。IADR-0364 決定 5 が「予算を上げる」を採ったのは、そこでは**秒数自体が試験対象ではなかった**からであり、本件は上限で倒れることが対象である |
| B | 遅延を長くする（2 秒 → 30 秒） | **採らない。** 比を広げても順序は保証されない（#906 の実測。100 ms 対 600 ms の 6 倍差で実際に逆転した） |
| C | 注入した時計（`TimeProvider`）で上限を表現する | **採らない。** `HttpClient.Timeout` は `TimeProvider` を受け取らない。製品コードの構造を試験の都合で変えることになる |
| **D** | **応答しない上流＋打ち切りの観測** | **採用**（IADR-0367 の形をそのまま複製する。新しい判断を持ち込まない） |

## 理由

**測ってから直した。** 変異注入で「遅延が勝ったら何が起きるか」を 10 件すべてについて実測し、
赤くなる 5 件と黙って緑になる 4 件（＋ #906 / #907 の 2 件）に分けた。分けてから、同じ是正を当てた。

🔴 **再現は取れていない。** 是正前の `HttpDailyPolicyProviderTests` を、スピンループ 16 本＋24 本の下で
**冷えたプロセスから 100 回**走らせたが **0/100** だった。#907 の実測（是正前 3/110）と整合する低い率であり、
**「再現できなかったから欠陥ではない」とは読まない** —— 根拠は
①#906 / #907 が計装で確定させた機序（塞がったプールが、既に期限の切れた 2 つのコールバックの順序を入れ替える）
②本作業の変異注入（応答が勝てば判定が変わることの実測）である。**再現率の前後差は示せていない。**

## 結果

- 良い影響: 形 (a) の同型が**リポジトリから消える**（本 PR 11 ファイル ＋ #907 の 1 ファイル）。
  4 件は「黙って打ち切り経路を検査しなくなる」状態からも抜ける。
- 🔴 **走査は「1 ケース直したファイル」を『済み』と数えない。** 作業中に #906 が develop へ入ったが、
  同 PR が直したのは `HttpReportNarrativeDrafterTests` の**1 ケースだけ**で、同ファイルに同型が 3 ケース残っていた
  （走査の出力で気付いた。issue の記述を信じて数えていたら取りこぼしていた）。本 IADR の変換に含める。
- 代償: 各テストに `Guard` と打ち切りの観測が 1 行ずつ増える。**打ち切りが壊れた場合の所要は 30 秒**になる
  （従来は 2 秒で誤って緑になっていた）。
- 🔴 残余リスク: 形 (c)（5 秒の追跡窓・約 30 テスト）は**手つかず**である。別 issue で扱う。
- 🔴 残余リスク: 検査器が入るまでの間、**新しい同型は止まらない**。
