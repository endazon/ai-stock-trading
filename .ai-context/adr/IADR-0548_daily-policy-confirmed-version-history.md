# IADR-0548: 確定済み日報の版の履歴・二段の選び方・判断時点の組み直し・判断の記録の方針の版（#1373 段 A）

## コンテキスト

ADR-0068 は、効いている確定済み日報に版を足して再確定できるようにする（決定 1）。そのために、旧版を不変のまま確定時刻つきで残し（決定 2）、
Stage 0 が判断時点の版を組み直せること（決定 3・配備の条件）と、判断の記録に参照した方針の版を残すこと（決定 4）を求める。

実装の現状（AST `origin/develop` `4b2ff956`）:

- `reports` は会話キーごとに 1 行。最新の確定済み日報は「種別が日報・状態が確定済みの行のうち開始日が最大」で選ぶ（`GetLatestConfirmed`）。
- 判断時点の方針（`GetLatestConfirmedAsOf`）は「`ConfirmedAt ≤ at` の行のうち開始日が最大」で選び、**確定済みの行が不変であることに頼って**判断時点の答えと一致させていた（IADR-0528 決定 3）。行に版 n+1 を上書きすると、版 n の時点を組み直せなくなる。
- 取引判断が受け取る方針は日付と本文だけで、判断の記録に方針の版は残らない。

## 決定

### 決定 1: 確定した版の写しを別の表に、確定のたびに 1 行足す（書き換えない）

- 表 `report_confirmed_versions`（`ReportConfirmedVersionRow`）。列は期間キー・種別・開始日・**版（確定後の行の版。`VersionedReport` の版と同じ）**・**確定時刻（非 null）**・`BasedOn`・前提条件の版・方針の要約・本文・未供給の入力。
- 鍵は **`(Kind, Sequence)`**。`Sequence` は種別ごとの確定の通し番号（1 から）。`(PeriodKey, Version)` に一意の索引、`(Kind, PeriodStart, ConfirmedAt)` に選び方の索引。
- **ストアに写しを更新・削除する口を持たない**（確定済みの版は書き換えない）。`reports` の行は従来どおり現在の状態（ドラフトまたは確定済み）を持つ。**期間キーは変えない**（1 日 1 本の前提を保つ）。
- 写しはすべての種別に足す（週報・月報も 1 期間 1 版のまま同じ表から選ぶ）。読み手を 1 つの源に揃え、種別ごとに選び方を分けない。

### 決定 2: 確定は「行の確定」と「写しの追加」を 1 回の保存で行い、通し番号の衝突は読み直して決め直す

- `EfReportStore.Confirm` は、行の更新（状態・確定時刻・本文の状態表記・版 +1）と写しの追加を **1 回の `SaveChanges`（1 トランザクション）**で保存する。片方だけが残ることは無い。
- 通し番号は「同じ種別の写しの最大＋1」。**同じ種別の確定が並行すると鍵が衝突する**（後の保存が一意制約違反で負ける）。負けた側は追跡を外して読み直し、決め直す（最大 3 回。`MaxConfirmAttempts`）。読み直した行が確定済みなら冪等の答え（`Transitioned=false`）になる。
  - 同じ行の確定の並行（行の版の並行トークンの衝突）も同じ読み直しに入る。従来は例外のまま上がっていたが、読み直すと冪等の答えになる。
  - **読み直すのは衝突だけである**（`ReportConfirmConflict.IsConflict`。PR #1374 の AI レビュー 🟡）。衝突とは、行の版の並行トークンの衝突（`DbUpdateConcurrencyException`）と、Postgres の一意制約違反（23505）のうち制約名が写しの鍵（`PK_report_confirmed_versions`）か `(PeriodKey, Version)` の一意（`IX_report_confirmed_versions_PeriodKey_Version`）のものである。
    それ以外の保存の失敗（接続断・他の制約・他の SQLSTATE）は再試行せず、1 回目でそのまま投げる。`ArgumentException` は InMemory プロバイダのときだけ衝突とみなす（InMemory は鍵の重複を制約名なしの `ArgumentException` で返す。本番の Npgsql ではこの形にならない）。
    段 B の「なお効いている」の判定はこの衝突の上に載るため、衝突でない失敗を読み直しへ混ぜない。作業用の Postgres で、写しの鍵の衝突が 23505・制約名つきで返り、衝突と判定されることを確かめた。
- `InMemoryReportStore` は行の確定と写しの追加を同じ排他の中で行う。

### 決定 3: 最新の確定済み報告書は写しから二段で選ぶ

- 1 段目: 開始日が最大の期間キー（同じ開始日は期間キーの降順。従来の一覧の並びと同じ）。2 段目: その期間キーの中で確定時刻が最新の版。**同時刻は版番号の大きい方**。
- 実装は `(開始日↓, 期間キー↓, 確定時刻↓, 版↓)` の辞書順の先頭である。先頭 2 つで期間キーが決まり、残り 2 つはその期間キーの中だけで比べられるので、二段の答えと一致する。**確定時刻だけで期間キーをまたいで並べない**（古い期間キーの版が後から確定しても、新しい期間キーを差し置いて選ばない）。
- `GetLatestConfirmed` の呼び出し側（方針の照会・`/policy` の土台・自動生成の上位方針と前回・週報の目標・月報のブートストラップ）は変えない。段 A では各期間キーに版が 1 本しか無いため、答えは従来と同じである。

### 決定 4: 判断時点の組み直しは、判断時点までに確定した版だけを対象に同じ二段で選ぶ（ADR-0068 決定 3）

- `GetLatestConfirmedAsOf(kind, at)` は、写しのうち **確定時刻 ≤ at の版だけ**を対象に、決定 3 と同じ二段で選ぶ。**at より後に確定した版（同じ期間キーの版 n+1 を含む）は使わない。**
- 写しは書き換えないので、答えは時刻 at に `GetLatestConfirmed` が返した値と一致する。行の不変性には頼らない。
- 🔴 **ADR-0068 決定 3 の配備の条件を試験で固定した**（`ReportConfirmedVersionHistoryTests.判断時点より後に確定した版は判断時点の組み直しに使わない`。版 n+1 の写しを段 B の確定が書くのと同じ形で置き、再確定の前後・1 tick 前・同時刻の判断時点で版 n と n+1 を返すことを確かめる）。段 B は、版 n+1 を本番の経路で確定してから同じ答えになる試験を足す（ADR-0068 フォローアップ 2）。
- as-of の応答の `confirmedAt` は、選んだ**版の**確定時刻になる（取引判断の受け手の「照会の時刻より後に確定した方針は受け取らない」の検査は、そのまま版の時刻で働く）。

### 決定 5: 方針の応答と判断の記録に、期間キーと版番号を足す（ADR-0068 決定 4）

- 報告書: `ConfirmedDailyPolicy` と `ConfirmedDailyPolicyAsOf` の末尾に `PeriodKey`・`Version`（REST の JSON は `periodKey`・`version`）。gRPC の `DailyPolicyRecord` に `optional string period_key = 3`・`optional int32 version = 4`（非破壊の追加。proto の baseline を更新）。
- 取引判断: `DailyPolicy` の末尾に `DailyPolicyReference? Reference`（共有契約 `DailyPolicyReference(PeriodKey, Version)`）。REST・gRPC・as-of の 3 つの読み手が、期間キーが空でなく版が正のときだけ作る（`DailyPolicyReferences.From`）。
  🔴 **欠けていても方針は使う**（並走中の古い送り手。判断を止める理由にしない）。欠けた値を 0 や空で埋めて「記録された」ふりをしない（原則 A）。
  欠けたときは固定の文言「確定済み日報方針の応答に期間キーまたは版番号がありません」（`DailyPolicyReferences.MissingReferenceMessage`）で警告を 1 件出す（`source=rest|grpc|as-of`。送り手の値は `LogSanitizer` で無害化。PR #1374 の AI レビュー 🟡）。**並走の解消は、取引判断のログでこの文言の警告が 0 件であることで確かめる。**
- 判断の記録: `TradeDecisionMade`・`TradeDecisionHeld` の末尾に `DailyPolicyReference? Policy = null`（`event-schemas.baseline.json` を更新）。AI 判断の結論を得た経路（発注意図・判断後の見送り）のすべてで載せる。監査台帳は payload を丸ごと保存するので、台帳の側の変更は要らない。
  - `TradeDecisionForgoneBeforeLlm`（LLM を呼ぶ前の見送り）には足さない。AI 判断をしていないので「判断が参照した方針」が無い（日報未確定の見送りもここに入る）。

### 決定 6: 既存の確定済みの行は、その時点の版のまま写しへ移す

- マイグレーション `AddReportConfirmedVersions` が表を作り、`reports` の確定済みの行（`State = Confirmed` かつ確定時刻あり）を **その時点の行の版のまま** 写す（各期間キーにつき 1 本＝その期間の最初の確定版）。本変更の前は確定済みの行が不変だった（`UpsertDraft` が拒む）ので、行の内容はそのまま確定した版の内容である。
- 通し番号は種別ごとに確定時刻・期間キーの順で 1 から振る。確定時刻の無い確定済みの行は `Confirm` が作らない（確定は必ず時刻を書く）ため写さない。
- Postgres 16 の作業用クラスタで、前のマイグレーションまで当てた DB に確定済み 3 行・ドラフト 1 行を置いてから当て、確定済みの 3 行だけが種別ごとの番号で写ることを確かめた（PR に記録）。

## 検討した選択肢

### 版の履歴の持ち方

1. **確定した版の写しを別の表に足す**（**採用**） — `reports` の行（会話キーごとに 1 行）とその読み手（一覧・取得・会話キーの一覧・レビュー・入れ替え案の版の照合）を変えずに済む。期間キーも変えない。
2. `reports` の鍵を `(PeriodKey, Version)` にして版ごとに行を持つ — 現在の状態を読む箇所すべてが「その期間キーの最新の行」を選ぶ必要があり、追随の範囲が広い（母集合の表の 5〜14）。
3. 写しを本文の付録や JSON 列に持つ — 判断時点の選び方を SQL で書けず、不変性を列の更新で守ることになる。

### 「なお効いている」の判定と確定を 1 保存操作で行う足場（段 B）

1. **写しの鍵を種別ごとの通し番号にする**（**採用**） — 同じ種別の確定どうしが必ず衝突するので、判定（通し番号 S の時点の写しから二段で選ぶ）と確定（S+1 の写しの追加）を 1 回の保存で行えば、その間に別の確定が入る余地が無い。InMemory の DB でも鍵の衝突として試験できる。
2. 直列化可能な分離レベル（Postgres の SERIALIZABLE） — 試験の InMemory では再現できず、他の書き込みにも再試行が要る。
3. 種別ごとの「効いている日報」の行を別に持ち、並行トークンで守る — 同じ保証だが表が 1 つ増え、写しの表と二重の状態になる。

## 段 B への引き継ぎ（ADR-0068 決定 1・5・6）

- **保存 API の形（案）**: `IReportStore` に 2 つ足す。いずれも 1 回の `SaveChanges` で終える。
  1. `StartRevisionDraft(TradingReport draft, int expectedVersion)`（版 n+1 のドラフトを作る）: 行が確定済みで版が一致し、かつ**効いている日報**（決定 3 の二段で選んだ期間キーがこの期間キー）であるときだけ、行を Draft・版 +1 にして本文と方針を差し替える。写しの版 n は残る。効いていなければ理由つきで断る（新しい例外か結果型）。
  2. `Confirm` に「なお効いている」を要求する指定（例 `ConfirmIfStillEffective`）: 写しの通し番号の最大 S を読み、S までの写しで二段で選んだ期間キーがこの期間キーであることを確かめてから、行の確定と写し S+1 の追加を 1 回で保存する。
- **1 保存操作で行える根拠**: 効いている日報を動かすのは日報の確定だけであり（ドラフトの作成は動かさない。ADR-0068 決定 1）、日報の確定はすべて写しの鍵 `(Daily, S+1)` を取り合う。判定に使った S の後に別の日報の確定が入れば、その確定が S+1 を取り、こちらの保存は鍵の衝突で負ける。負けた側は読み直して判定し直し、移っていれば断る。勝った側の判定は、保存の時点の写しの全体（S まで）に対して正しい。Postgres の一意制約は、並行するトランザクションの挿入を相手の確定まで待たせてから違反にするので、READ COMMITTED のままで成り立つ。本 IADR の試験（並行した確定の割り込み）と、作業用の Postgres での確認（同じ割り込みで番号 1〜4 が重ならない）がこの性質を示す。
- 段 B で追随が要る読み手（作業仕様書の母集合の表 5・7・11・13・14）: `/policy` と `/report regenerate` の確定済みの判定、KB の入れ直し（行が Draft の間は写しの最新の確定版を入れる）、一覧・取得の表示（確定版と版 n+1 のドラフトの並び）、確定時の KB 保存（最新の確定版で置き換え）。
- 版の番号は会話キーの行の版を使い続ける（確定済み v → 版 n+1 のドラフト v+1 → 確定 v+2）。写しの `(PeriodKey, Version)` の一意はこれで保たれる。
- 断る応答（`AutoDailyPending`）での効いている日報の会話キーの案内、作成と確定の通知、ドラフトの写しの失効（ADR-0065）は段 B。IADR-0431 の「確定済みは改訂しない」もそこで改める。

## 残余リスク

- **同じ種別の確定が並行すると、後の確定は最大 3 回読み直す。** 4 回続けて負けると例外が上がる（従来、並行した確定は 1 回目で例外だった）。日報・週報・月報の確定は利用者の操作であり、4 回の連続した衝突は実際の運用では起きないとみる。
- **写しは本文の複製を持つ**（1 期間につき確定した版の数だけ）。日報の本文は数十 KB であり、段 B の再確定は `/policy` の上限（既定 10 回/日）の内側に収まるため、量は問題にならないとみる。
- **Stage 0 の記録（`Stage0DecisionRecord`）は参照した方針の版を持たない。** as-of の答えは判断時点の版そのものなので組み直しはできる。記録に残すかは、戦略の同一性（`StrategyId`）の導出を変えるため別に決める。
- **期間キーと版を返さない古い送り手の間は、判断の記録の `Policy` が null になる。** 並走の間に限られ、報告書サービスを先に配備すれば生じない。
