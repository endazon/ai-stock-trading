# IADR-0441: 発注予約の自動リコンサイルの「ブローカーへの操作」の棚卸しと判定の計数

- 状態: Accepted
- 日付: 2026-09-26
- 決定者: claude（[#856](https://github.com/endazon/ai-stock-trading/issues/856)。利用者レビューは PR で受ける）

## 起点・関連

- 対象 Issue: #856（本 PR では閉じない。残る受け入れ基準は `NotPlaced` の実機検証）
- 関連する実装仕様書: [20260926_856_reconciler-broker-action-map-and-metrics](../specs/20260926_856_reconciler-broker-action-map-and-metrics.md)
- 関連 IADR: IADR-0362（配備での有効化と解放の門）・IADR-0428 決定4（突合で確定したエントリーに保護レグを張る）・
  IADR-0371（確定した 1 件ごとの出口）・IADR-0074 / IADR-0092（リコンサイル本体・実照会プローブ）・IADR-0395（起動時の 0）・
  IADR-0439（helm のリリースとチャートの差。有効化が 8 日間届いていなかった件）

## コンテキスト

依頼は「滞留 `Reserved` の自動リコンサイルは稼働 PoC で既定では無効なので、『突合が解決する』が既定では成立しない」を前提にしていた。
着手時に実物を確かめると、**その前提はもう成立しない**。

- `deploy/helm/ai-stock-trading/values.yaml` の `services.order-execution.extraEnv` が `Reconciliation__Enabled` / `__UseBrokerProbe` を
  `"true"`、`__ReleaseOnNotPlaced` を `"false"`、滞留 2 時間・巡回 1 時間・50 件にしている（IADR-0362・PR #882）。
  `values-local.yaml` は `order-execution` を持たず、これを継ぐ。`helm.yml` が 3 描画で値を固定している。
- #856 のオーナーのコメント（2026-09-25）によれば、helm の 7〜8 版（2026-09-25）で初めて稼働中の発注執行に届き、
  起動ログ「発注予約の自動リコンサイルを開始します（…未発注時の解放 禁止…）」が出ている。以降の巡回で滞留は 0 件。
- #856 に残るのは `NotPlaced` 判定の実機検証（検証できる滞留の事例がまだ起きていない）と、それを受けて解放の門を開けるかの判断である。

一方、リコンサイラが**ブローカーへ何をし得るか**は、コードの注記と文書に分散しており、#853（IADR-0428 決定4）で
「突合で確定したエントリーに保護レグを張る」が加わった後の全体像はどこにも 1 枚で書かれていなかった。
IADR-0117 改定 6 の 9/19 追記・運用文書の 2 箇所・実弾解禁の手順書は、なお「突合が確定した建玉に保護逆指値は張られない」と書いていた。

## 検討した選択肢

1. **配備の値を変える（解放の門を開ける）** — IADR-0362 決定1 の条件（実機で `NotPlaced` の偽陽性が無いことを記録つきで示す）を
   満たしていない。二重発注に直結する。却下。
2. **何も変えず報告だけする** — 「不明な状態では書き込まない」は既存の試験に分散していて、**本物の保護の口を通した状態で**
   ブローカーへの書き込みの総数を 0 と固定した試験は無い（保護の口の試験は `Placed` 側、リコンサイラの試験はブローカーを数えない）。
   また #856 を閉じるための観測（ブローカーに存在する注文に対して「未発注」と判定されていないこと）はログの grep にしか頼れない。却下。
3. **棚卸しを残し、否定形の試験と判定の計数を足し、文書を是正する。設定と分岐は変えない**（採用）。

## 決定

### 決定 1: リコンサイラがブローカーへ行い得る操作は次のとおりであり、書き込みは確定した 1 件の保護の口に限る

- **読み取り**: 照会（`MoomooReservationBrokerProbe` → `FindOrderByClientIdAsync`）だけ。備考（remark＝DecisionId）で全市場の現在＋履歴を列挙する。
- **リコンサイラ本体は発注も取消もしない。** コンストラクタで受ける `IBrokerAdapter` から読むのは `Provider` だけである。
- **書き込み**は、照会が `Placed` と確定した（または記録がある自己修復の）1 件の出口の後に、保護の口（`OrderExecutionAppService.ProtectAsync`）を
  通るときだけ起きる。保護記録が `AwaitingEntry` のエントリーに限り、逆指値（S0）か代替注文種別（S3）を 1 本送る。それが確認できた拒否・
  接続確立の失敗なら、未約定ならエントリーを取り消し、約定済みなら成行で手仕舞う。届いたか不明なら取消も成行もしない（IADR-0428 決定1・4）。
- **`Indeterminate`・`NotPlaced`（門が閉）・1 件の例外では書き込みは 0 回**。`NotPlaced`（門が開）の解放は書き込みではなく**再発注の許可**であり、
  送り直すのは `_error` からの再投入か保護逆指値ガードの次の巡回である。

これを本物の保護の口と送信回数を数えるブローカー（`StopLegScriptedBroker`）で固定する（T-10-1550〜T-10-1556）。
**変える分岐は無い**（既存の挙動が原則 A を満たしていることの固定である）。

### 決定 2: 判定の内訳を業務メトリクス `ast.order.reservation_reconciliations{outcome}` で数える

- Counter。タグ `outcome` は `probe-placed` / `self-healed` / `held-not-placed` / `released` / `indeterminate` / `failed` の 6 値で、巡回サマリの内訳と
  1 対 1（サマリの「終端化」を①自己修復と②照会で確定に分ける——②だけが保護の口を通ってブローカーへ書き込み得るため）。語彙の外は例外で拒む。
- **確定（①②）は出口（`EmitAsync`）で 1 件ずつ、発行より先に数える。** 確定した予約は次の巡回に載らないので、発行の後ろに置くと
  発行が落ちた 1 件は永久に数えられない（IADR-0371 と同じ幾何。T-10-1561）。
- **据え置き・不確定・失敗・解放は巡回サマリの件数で数える。** これらの予約は `Reserved` のまま次の巡回に載るため、
  巡回が中断されて計上されなくても数え直される。その代わり**同じ予約が巡回ごとに数え直される**（件数は判定の回数であり、予約の数ではない）。
- **起動完了後、`Reconciliation:Enabled=true` のときだけ 6 系列を 0 で作る**（IADR-0395 と同じ理由）。無効な構成で作らないのは、
  0 の系列が「巡回して 0 件だった」と読めるためである。
- ダッシュボード（業務）にパネルを 1 枚足す（`check-observability-assets.js` の R2）。
- 🔴 **アラートは足さない。** `held-not-placed` は門が閉じている限り想定内の据え置きであり、何件で誰を呼ぶかの基準は決まっていない。
  この計器の第一の用途は、#856 を閉じるための否定形の観測——**証券会社に存在すると確かめた注文について `held-not-placed` が 0 であること**——を
  ログの保持期間に縛られずに数えることである。

### 決定 3: 設定は 1 つも変えない

`values.yaml` / `values-local.yaml` / `appsettings*.json` の `Reconciliation__*` は変えない。解放の門は `"false"` のまま。
門を開けるかは新しい運用判断であり、PR 本文でオーナーへ問う（計画への環流案は報告に添える。未起票）。

## 理由

- 決定 1 は既存の挙動の固定であり、稼働中の取引を変えない。固定するのは「どの変更で書き込みが漏れ出すか」——保護の口を確定の前へ動かす、
  不明・未発注でも保護の口を呼ぶ、門の既定を開ける、解放の後に自分で送り直す——であり、どれも二重発注・孤立した逆指値に直結する。
- 決定 2 の計器は観測であり、判定を変えない。巡回サマリのログは 1 巡回 1 行で、Loki の保持期間を過ぎると #856 の否定形の観測（期間中 0 件）が
  言えなくなる。

## 影響・追随

- `OrderReservationReconciliationService` のコンストラクタに `BusinessMetrics` が増える（**必須**。省略可能にすると DI の配線漏れで黙って数えなくなる）。
- `Program.cs` の起動完了のコールバックが 1 つ増える（有効な構成でだけ 0 を計上）。
- 文書: 運用仕様書（解禁条件 11・判定表とブローカーへの操作・監視・障害対応表）、実弾解禁の手順書（条件 3）、
  可観測性の 2 表、IADR-0117 改定 6 の追記（9/19 追記の「保護レグは張られない」が偽になったこと・稼働に届いた日）。

## 残余リスク

- 🔴 **`NotPlaced` の実機検証は行っていない。** 本 PR は実クラスタにも OpenD にもブローカーにも触れていない。門を開ける判断は #856 に残る。
- 計器が数えるのは判定の回数であり、`held-not-placed` が「本当に未発注だったか」は計器からは分からない。判定の真偽は証券会社の画面で
  `DecisionId`（備考）を確かめるしかない（運用仕様書に手順を書いた）。
- 巡回の途中で発行が落ちると、その巡回の据え置き等の件数は計上されない（次の巡回で数え直される）。
- ダッシュボードの `increase(...[1h])` は巡回間隔（1 時間）と同じ窓なので、1 巡回の件数がそのまま見える。巡回間隔を変えたら窓も見直すこと。
