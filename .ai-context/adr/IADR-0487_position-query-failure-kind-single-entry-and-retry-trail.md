# IADR-0487: 建玉照会の失敗の種類は共有の入口から受け取り、照会し直しの経過を台帳へ載せる（#1164）

## コンテキストと課題

- 分類器（`MoomooPositionQueryClassifier`）は moomoo のアダプタの 1 か所だけにあり、全経路が同じアダプタのインスタンスを通る。**同じ例外は同じ種類になる。**
- それでも PoC では 2 つの経路の「分類」が食い違って見えた。原因は分類ではなく、**結果の出し方**にあった。
  1. 観測の常駐・決済のゲート・S1 の武装前・S1 の決済・稼働 probe は、`GetPositionsAsync`（null か一覧だけ）で照会する。種類を捨て、台帳へは「種類 不明」で報告していた。観測の常駐の「Transient」は、呼び出し元を名乗らないアダプタのログからしか読めない。
  2. ガードは照会し直しの**最終結果**の種類だけを台帳へ載せる。最初が Transient で照会し直し、2 回目が Other で終わると、台帳には「Other」だけが残る。照会し直しが効いたかどうかを台帳から読めない。
  3. 2 つの経路は別々に照会する。同じ時刻でも分類器への入力は別の失敗である。SDK を逆コンパイルすると、切断・未接続の間の要求には返事が来ない（本実装の返信待ちの打ち切り＝Transient）。OpenD が返事として返す -1 は、頻度制限の文言でなければ Other である。
- PoC の実ログ（retType・retMsg・例外型）は手元に無い。上の 2. と 3. のどちらだったかは確定できない。

## 決定

### 決定 1 — 台帳へ報告する建玉照会は、すべて共有の入口（`PositionQueries.QueryAsync`）から種類を受け取って報告する

- 入口は、分類つきの口（`IClassifiedPositionSource`。moomoo のアダプタ）を持つ供給元ならそれで照会し、持たない供給元は `GetPositionsAsync` を呼んで種類を不明（None）とする。**分類器は増やさない**（アダプタの 1 か所のまま）。
- 対象: 観測の常駐（`BrokerPositionSnapshot`）・決済のゲートと S1 の武装前（`OrderDispatch`）・S1 の決済（`SoftwareStopClose`）。稼働 probe（`BrokerAvailabilityProbe`）は、probe が分類つきの口も持つときだけその口で照会する（moomoo のアダプタの到達判定は「建玉照会が null でない」であり、判定は変わらない）。
- ガードの本番の経路は従来どおり照会し直しつきの分類つきの口である。照会し直しを渡されない構成（本番では使わない）は IADR-0458 のとおり従来の口で 1 回だけ照会する（種類は不明）。
- 発注の経路（決済のゲート・S1 の武装前・S1 の決済）では照会し直さない（IADR-0211 決定3）。入口は照会し直しをしない。
- 台帳へ報告しない照会（ガードの建玉 0 の確かめ直し・乖離の取り込み）は対象外とする。null を据え置きへ倒すだけで、種類を運ぶ先が無い。分類はアダプタのログに出る。

### 決定 2 — 台帳へ載せる種類の書き方は `PositionQueryResult.ReportedFailureKind` の 1 か所に置き、照会し直した失敗は「最初→最後」で載せる

- 成功・分類の無い失敗は null（台帳では「不明」）。照会し直していない失敗は 1 語（`Transient` / `RateLimited` / `Other`）。**照会し直した失敗は `最初→最後`（例 `Transient→Other`）**。
- 照会し直しの回数と最初の種類は `PositionQueryRetry` が結果へ載せる（`Retries` / `FirstFailure`）。
- IADR-0462 決定2 の「ガードは照会し直しの最終結果の種類を載せる」を改める。観測は従来どおり巡回に 1 回（照会し直しの途中の失敗を観測として数えない）。

## 検討した選択肢

| 案 | 内容 | 判定 |
| --- | --- | --- |
| A（採用） | 共有の入口で種類を受け取り、全経路が同じ書き方で報告する。照会し直した失敗は `最初→最後` | ◎ 経路の間で比べられる。照会し直しの有無を台帳だけで読める |
| B | 最終結果の種類だけを載せる（是正前） | ✕ 照会し直しが効いたかを台帳から読めない（#1164 の取り違え） |
| C | 最初の種類だけを載せる | ✕ 据え置きの原因（最後の失敗）が台帳から消える |
| D | -1 の失敗のうち「一時的そうな文言」を Transient へ寄せる | ✕ PoC の retMsg が無く根拠が無い。分からないものを照会し直すと頻度制限の枠を消費する（IADR-0144 決定5・IADR-0458）。方針「分からないものは Other」を保つ |
| E | 台帳の事実（`PositionQueryStatusChanged`）に欄を足す（最初の種類・回数） | △ 契約の型を変える（監査・報告の受け手へ波及）。種類は文字列の欄で、表示は「種類 {値}」だけなので、欄を足さずに書けば足りる |

## 窓（規則 11）の確かめ

照会し直しの窓（最初の失敗 → 最後の結果）の後の端だけ（案 B）・前の端だけ（案 C）・両端（案 A）を、増える側（最初 Transient・最後 Other）・減る側（最初 Other・照会し直さない）・対照（照会し直して成功）の 3 つのプローブで比べた。両端だけが 3 つとも期待どおりである（作業仕様書の表。T-10-2213〜T-10-2215）。

## 統制と現在の実現手段

- 同じ失敗が全経路で同じ種類になること: T-10-2210（本物のアダプタ＋本物の分類器に同じ形の例外を与え、観測の常駐とガードの報告を突き合わせる）・T-10-2216〜T-10-2218（発注の経路・S1 の決済・稼働 probe）。
- ガードが一過性の失敗で 1 回だけ照会し直すこと: T-10-2211（本物のアダプタ越しに、ブローカへの照会の回数を数える）。
- 書き方の 1 か所: T-10-2219。

## 結果

- 台帳（`PositionQueryStatusChanged.FailureKind`）は、建玉照会のすべての発生源で同じ分類器の種類を持つ（是正前はガードだけ）。ガードの失敗は、照会し直したなら `Transient→Other` のように経過が分かる。
- 型・イベントの契約は変えない（`FailureKind` は文字列のまま。契約のコメントだけ改めた）。

## 残余

- PoC の 00:28 の失敗の入力（retType・retMsg・例外型）は確定していない。次に起きたら、台帳の種類（全発生源）と、ガードの `最初→最後` で区別できる。-1 の文言が一時的な失敗を表すと分かったら、分類器の表へ足すかを別に判断する（実測の文言が要る）。
- アダプタのログ（`分類 {Failure}`）は呼び出し元を名乗らない。台帳の発生源で読む。
- 稼働 probe は、分類つきの口を持つ probe では `IsOperationalAsync` を呼ばずに建玉照会で判定する。moomoo のアダプタの `IsOperationalAsync` が建玉照会以外の判定へ変わったら、ここも見直す。
