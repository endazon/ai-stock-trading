# IADR-0530: SC-02 の高ボラティリティ銘柄の設定と、銘柄コードの誤記の防ぎ方（#1291）

> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

## コンテキスト

- ADR-0066 決定 2: SC-02 から明示指定と区分の上限を表示・設定する。手続きは §5 の統制値と同じ（OwnerOnly・理由必須・値域外は拒否・履歴）。経路は既存の API を BFF 経由で使う。**画面は銘柄コードの誤記を防ぐ手段を持つ**（監視銘柄から選ばせるか、監視銘柄に無い銘柄に警告を出すかは実装が決める）。
- 現在の API（IADR-0527）は銘柄コードの書式も実在も検証しない（空と未知の市場を拒むだけ）。誤記は受理され、どの注文にも一致せず黙って効かない。
- 本リポには銘柄の実在を答える口（シンボル辞書・ブローカーの銘柄照会の API）が無い。監視銘柄（MarketMonitor `GET /monitor/watchlist`）は SC-02 が既に BFF 経由で読んでいる。

## 検討した選択肢

| 案 | 誤記の防止 | 先回りの指定（監視銘柄に入れる前の指定） | 費用 |
| --- | --- | --- | --- |
| A. 監視銘柄からの選択だけ | 完全（組で選ぶので銘柄も市場も誤らない） | **できない**（IADR-0527 が残した「監視銘柄に無い銘柄も指定できる」を画面で失う。AI の入れ替え案で監視銘柄に入った直後に区分を効かせたい場合に、順序の制約が生じる） | 小 |
| B. 自由入力＋監視銘柄に無ければ警告（通す） | 警告を読まなければ通る | できる | 小 |
| C. 実在検証の API（ブローカーの銘柄照会を新設） | 実在は確かめられる | できる | **大**（OpenD 経由の新しい口・照会の失敗時の扱い・PoC の権限〔日本株の市況権限が無い〕の影響。誤記と実在する別銘柄〔例 `TSL` が実在した場合〕は区別できない） |
| **D. A を主の経路にし、B を確認の印つきで併置（採用）** | 主の経路は完全。手入力は書式で拒み、監視銘柄に無い・市場が違う・照合できないときは**確認の印を付けるまで追加できない** | できる（確認の印で意図を残す） | 小 |

## 決定

### 決定 1: 誤記の防ぎ方は D（監視銘柄からの選択を主の経路、手入力は書式・照合・確認の 3 段）

1. **監視銘柄から選ぶ**（`Select`。表示は `銘柄（市場）`、値は組）。指定済みの組は選択肢から外す。
2. **手入力**（先回りの指定）:
   - 大文字へ正規化し、英数字と `.` `-` の 12 文字以内（先頭は英数字）でなければ追加できない（空白・記号の混入を止める）。重複は追加できない。
   - 監視銘柄と照合し、`監視銘柄にありません`／`監視銘柄では市場が違います`（同じ銘柄コードが別の市場にだけある）／`監視銘柄と照合できません`（監視銘柄の取得に失敗）のいずれかなら警告し、**「綴りと市場を確かめた」の確認の印を付けるまで追加ボタンを無効にする**。監視銘柄にある組は確認なしで追加できる。
   - 確認の印は**確かめた銘柄・市場の組に紐づく**（印を付けた後に銘柄コードや市場を書き換えたら外れる）。
   - 監視銘柄の**取得中**は照合の結果を出さず「照合中」と出し、手入力は結果が出るまで追加させない（取得前に警告を点滅させない・確認なしで通る窓を作らない）。
3. **保存済みの指定の各行に照合の印**（`監視銘柄にあります`／上の 3 種）を出す。API で直接入れた誤記（ADR-0066 決定 3 の暫定手段で入った値を含む）を画面で見つけられる。
- 理由: A の完全さを主の経路で得つつ、IADR-0527 決定 2 の「監視銘柄に無い銘柄も指定できる」を失わない。B の弱点（警告を読まずに通る）は確認の印で塞ぐ。C は費用に見合わず、しかも「実在する別銘柄」への誤記は防げない（照合で防げるのは監視銘柄との食い違いであり、利用者が監視している銘柄が区分の本来の対象である）。
- 🔴 **これは画面の親切であり統制ではない。** サーバは引き続き書式も実在も検証しない（API を直接呼べば誤記は通る）。サーバ側に書式検証を足すかは本 IADR の範囲外とした（ADR-0066 は画面の要件として定めた。既存の保存値の読み方が変わる変更は別の判断が要る）。

### 決定 2: フォームの形は §5 の他の統制値の編集に合わせる

- 構成: `HighVolatilityForm`（SC-02 の components）。取得は `useRiskSettings`（`highVolatility`）と `useWatchlist`、保存は `useSaveHighVolatility`（`useRiskSettingsMutation`。成功で設定・履歴・統制状態を無効化）。`apiFetch` は `lib/risk/queries.ts` の 1 段に閉じる（IADR-0288）。
- 置き場: リスク上限の直後（区分の上限は 1 注文上限の区分版）。**保存単位は分ける**（サーバの口が別）。
- 区分の上限は**百分率**で入力し（IADR-0151 と同じ。`percentTextToRatio` を通す）、現在 equity での実額を併記する。値域 1%〜25% は `contracts.ts` に持つ（即時提示のため。実効はサーバの `HighVolatilityOrderCap.Validate`。下端は ADR-0066 決定 1 の固定値）。
- 本文は**全置換**（比率と一覧を一緒に送る）。変更が無ければ保存できない（空の変更を履歴に積まない）。理由必須。400 は `details` を表示し、自動再試行しない。409 は再取得を促す。
- **統制を緩める変更（上限を上げる・指定を外す）は列挙して確認を求める**（取引ガードの危険な緩和と同じ。IADR-0086 決定 3）。確認後に緩める変更が増えたら確認を外す。
- 現在値の追随は描画中の同期調整（`useEffect` を使わない。#498 / #539）。

### 決定 3: BFF は素通しの 1 経路を足す

- `PUT /bff/risk-controls/settings/high-volatility` → 後段 `/risk-controls/settings/high-volatility`（`RiskControlsBffEndpoints`。認証必須・利用者トークンの伝播・状態と本文の透過・上流 401 は 502）。値域・理由・認可（OwnerOnly）は後段が実効する（IADR-0071）。新しい API は作らない（ADR-0066 決定 2）。

## 結果

- SC-02 から明示指定と区分の上限を表示・設定できる（ADR-0066 決定 2・ADR-0063 フォローアップ 5 の実装）。配備後は暫定手段（owner の API）に代わる。
- 受け入れ基準はコンポーネント試験（T-10-2593〜T-10-2602・T-10-2604・T-10-2605）と E2E（T-10-2603）、BFF の試験（T-10-2591・T-10-2592）で固定した。

## 残る制約

- サーバは銘柄コードの書式も実在も検証しない。API を直接呼べば誤記は通る（画面の照合の印で後から見つけることはできる）。
- 照合は監視銘柄との突き合わせであり、監視銘柄に無い実在銘柄と誤記は区別できない（確認の印は利用者の確認であって検証ではない）。
- 楽観排他は他の SC-02 の統制値と同じ（DB の並行トークン。画面の読んだ時点の版は送らない）。
- モックアップ（hi-fi / wireframe の sc-02）は未反映（ADR-0066 フォローアップ 2。人間）。
