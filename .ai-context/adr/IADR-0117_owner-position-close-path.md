# IADR-0117: 建玉の手仕舞いは利用者専用の同期経路で受け、統制を通さず既存の注文パスへ載せる

## 背景・課題

`PositionEffect.Close` を生む経路は `StopLossExecutionService.BuildCloseApproval()` **1 つだけ**で、
`StopLossTriggered`（市場監視が損切りラインへの到達を検知したとき）にしか発火しない。判断由来の発注は
`TradeDecisionService.cs:208` が `PositionEffect.Open` をリテラル固定している（IADR-0004）。

したがって **損切りラインに触れない限り建玉を手仕舞う手段が存在しない**。利益確定も、運用判断による撤退も、
異常時の清算もできない。実害として、#270（約定が台帳へ伝播しなかった期間）に積み上がった過大建玉を
正規手段で清算できず、AI 自動取引を清算済みの状態から再開できない。

## 検討した選択肢

1. **リスク管理サービスに利用者専用の同期エンドポイントを置き、`OrderApproved` を発行する**（採用）。
   損切りの機械執行と同じ層・同じ出力に揃える。
2. **発注執行サービスに決済 API を置く**。ブローカに近い層に置く案。ただし決済の材料（建玉・`FxRateToBase`・
   段階 Mode・現在値）はすべてリスク管理側にあり、s2s で取り直す往復と権威の二重化が生じる。
3. **決済専用のイベントを作り、発注執行が専用に処理する**。既存の `OrderApproved` → 予約 → 発注 → `OrderExecuted`
   とは別の経路を新設する案。台帳・枠回復・通知・監査の受け口を二重に持つことになる。

## 決定

**選択肢 1 を採る。** 具体的には次の 4 点を決める。

### 決定 1: 配置と出力（リスク管理・`OrderApproved` を出す）

`POST /risk-controls/positions/close`（OwnerOnly）で受け、`PositionCloseService` が判定して
**既存の `OrderApproved` を発行する**。以降は 1 行も新しい経路を作らない
（発注執行 → `OrderExecuted` → `trade_fills` → 建玉・実現損益・枠回復 → Discord 通知 → 監査）。

売買方向は**要求に含めない**。建玉方向の反対売買としてサーバが決める（誤方向の指定で建て増しさせない）。
`FxRateToBase` は建玉の加重平均約定時レートを引き継ぎ（IADR-0107）、`StopLossPrice` は持たせない。

### 決定 2: 発注前スクリーニングを通さない

`OrderScreeningService`（`RiskEvaluator`）を経由しない。kill switch・日次損失ロックアウト・一時停止・
取引ガード・段階資金上限のいずれでも手仕舞いは止まらない。

**これは逸脱ではなく FR-10 本文の実装である。** 構造的な保証として `PositionCloseService` は統制ストア
（`IKillSwitchStore` / `ILockoutStore` / `IPauseStore`）を依存に持たず、その事実をテストで固定する。

### 決定 3: 過剰決済ガードは「処理中の決済」を在庫から引く（時間窓つき）

取引台帳は**約定でしか動かない**。決済要求から約定が届くまで建玉数量は減らないため、在庫判定を建玉数量だけで
行うと多重投入で在庫を超える決済（意図しないショート化）を作れてしまう。

`IPortfolioLedgerStore.GetInFlightCloseQuantity(symbol, market, approvedAtOrAfter)` を足し、

```
利用可能数量 = 建玉数量 − Σ max(0, 決済承認数量 − 当該 DecisionId の約定累計)   （窓内の承認のみ）
```

を在庫とする。数量省略（全量指定）は「保有全量」ではなく**この利用可能数量**と解釈する。

**時間窓（既定 30 分）で切る**のが要点。窓が無いと、#270 破損期のような「永久に約定しない滞留承認」が
建玉を**恒久的にロック**し、手仕舞い手段を作ったのに手仕舞えないという最悪の状態になる。窓は構成キーにしない
（運用で触る値ではなく、広げれば二重決済の窓が広がるだけである）。

［2026-09-19 追記 / [#848](https://github.com/endazon/ai-stock-trading/issues/848)］
**本決定は「終端になった承認」を除いていなかった。** 稼働環境（2026-09-18 23:2x JST）で、利用者が板に残った
手仕舞いを moomoo アプリで取り消した**後**も、指値を変えた再要求が `ExceedsAvailable`（422）で拒否され続けた。
発注執行の台帳は取消を正しく検知していた（`OrderId=1149564921959476304 Quantity=3381 Filled=0 Status=4(Cancelled)`）
のに、上式が承認数量 − 約定累計だけで数えていたため、**取り消された注文が 30 分間ずっと建玉をロックした**。
無保護の建玉 3,381 株・含み損 −5,133 USD を抱えた状態であり、**損切りが必要な下落局面で手仕舞えない**という
最悪の形で露呈した。上式を次のとおり改める（作業仕様書 `20260919_848_terminal-close-approvals-release-inventory`）。

```
利用可能数量 = 建玉数量 − Σ max(0, 決済承認数量 − 当該 DecisionId の約定累計)
               （窓内の承認のうち、終端になったと**確認できていない**ものだけ）
```

- **改定 1（台帳が終端を持つ）**: `approved_orders` に `TerminalAt`（終端になったと確認できた時刻）と
  `TerminalStatus`（診断用）を足す。**判定に使うのは `TerminalAt` だけ**で、一度立ったら消さず後着でも
  上書きしない（単調。`EfWorkingEntryOrderSource` と同じ規約——状態は遅着イベントで巻き戻り得るが時刻は戻らない）。
  🔴 **本 ADR の「Migration 無し」は本追記で覆る**（下の「影響・追随」の該当行を参照）。
  - 🔴 **`TerminalAt` という列名は `order_activity`（IADR-0067）にも既にあり、規約が違う。**
    こちら（`approved_orders`）は**単調**（一度立ったら動かさない）、あちら（`order_activity`）は
    `EfOrderActivityStore.RecordCancellation` が**無条件に上書き**する。**同じ名前で違う規約**である。
    寄せない —— 射影の意味論を変えると相場操縦検知の入力（生存区間）が動くためであり、
    **読むときは必ずどちらの表かを確かめる**。
- **改定 2（在庫解放に使う終端に `Filled` は入れない）**: 本集計で除きたいのは
  「**未約定残が二度と約定しない**」承認、すなわち `Cancelled` / `Rejected` / `Expired` である。
  **全量約定（`Filled`）は入れない** —— 上式の `max(0, 承認数量 − 約定累計)` が
  **自然に 0 にする**ので得るものが無い一方、**終端の記録と約定の記録は別トランザクションである**ため、
  前者だけが commit された区間で建玉が**丸ごと**空いて見える（実測: 建玉 100 / 処理中 0 / 利用可能 100）。
  その瞬間の手仕舞い要求が同じ株数をもう一度売れてしまう。加えて矛盾したイベント
  （`Status=Filled` かつ約定 0）では**恒久的に**在庫が戻る。
  終端述語の単一情報源（`Domain.OrderStatusLifecycle`）は **2 つの述語**を持つ ——
  `IsTerminal`（`Filled` を含む。**注文アクティビティ射影の生存区間**が使う）と
  `AbandonsUnfilledRemainder`（`Filled` を含まない。**本集計の在庫解放**が使う）。
  🔴 **共有関数を書き換えて片方へ寄せない。問いが違う。**
- **改定 3（不明は処理中のまま。上流の写像まで含めて成立させる）**: `TerminalAt` が `null` ＝
  **終端だと確認できていない**であり、「終端でない」ではない。従来どおり全量を処理中として数える。
  **除外し過ぎると二重決済で意図しないショート化を作る**——本 ADR 決定 3 が塞いだ穴そのものであり、
  fail-safe の向きは変えない。
  - 🔴 **この不変条件は台帳だけでは成立しない。** 状態は moomoo アダプタの写像を通って届く。
    従来 `MMApiMoomooTradeClient.MapState` は OpenD の `-1`（NONE）・`4`（TIMEOUT＝**結果未知**）・
    未知コードを `Failed` へ畳み、`MoomooBrokerAdapter.MapState` がそれを `Rejected`（＝終端）にしていた。
    **在庫解放が `Rejected` を引き金にした瞬間、この既定は fail-safe から fail-open へ反転する**
    （「安全側: 不明/失敗は Rejected」というコメントは、その時点で事実と食い違っていた）。
    本追記で **`MoomooOrderState.Unknown` を新設**し、確認できた失敗（`3` / `21` / `22` / `23`）と
    **不明**（`-1` / `4` / 未知コード）を分ける。`Unknown` は `OrderStatus.Accepted`（＝非終端）へ写し、
    **写像の既定も `Accepted` へ倒す**（名前を付けられない状態で在庫を解放しない）。
    `Failed` → `Rejected` は変えない（**発注拒否での解放は #848 の射程内**であり、
    `Rejected` を外すと 2 つ目の恒久ロックを作る）。`12` / `13`（取消進行中）を非終端へ倒している
    既存の配慮も変えない。副次的に、不明は約定追跡（`OrderFillPoller`）が非終端として
    **引き直し続けるため本当の状態へ解決する**（`Rejected` へ畳むと二度と引き直されなかった）。
- **改定 4（届け方は「既に届いているイベント」）**: 新しいイベントも同期照会も作らない。`OrderExecuted` は
  `Status` を**既に運んでおり**、約定追跡（`OrderFillPoller`・30 秒周期）は終端化したときも再発行する。
  リスク管理は既にこれを購読していたが、`OrderExecutedLedgerHandler` の `FilledQuantity <= 0` 早期 return が
  **約定 0 の取消を丸ごと捨てていた**。この早期 return を畳み、
  **「約定があるときだけ `AppendFill` → そのあと必ず `MarkTerminal`」**の順にする
  （🔴 **終端の記録は約定の記録より後ろ**。改定 2 と併せて、約定が台帳に載る前に在庫が解放される区間を無くす）。
  明示的な取消（`OrderCancelled`。既に購読済み・キューは既存）は `OrderCancelledLedgerHandler` で
  同じく記録する。**新しいキューは 1 本も増えない。**
  - 同期照会（発注執行へ `executed_orders.Status` を s2s で引く）を採らないのは、手仕舞い判定のホットパスへ
    他サービスの可用性を持ち込むからである（IADR-0018 / IADR-0067 が繰り返し「同期契約は Risk 専有 DB への
    射影で供給する」と決めている）。新イベントを作らないのは、同じ事実を 2 契約で運ぶと片方だけ届く事故の面が
    増えるからで、本 ADR が「決済専用の経路を作らない」と決めたのと同型の理由である。
- **改定 5（`order_activity` は読まない）**: `order_activity`（IADR-0067）は既に `TerminalAt` を持ち、
  IADR-0346 決定 1 は `approved_orders` へ左結合して終端を除いている。同じ結合なら migration 無しで直せるが、
  **母集合が違う**——保護レグの決済 Intent は `OrderApproved` を流さず台帳へ直接承認行を足すため
  （IADR-0210 決定 2/3。流すと発注執行が二重発注する）、`order_activity` に**行が無い**。保護レグも
  `PositionEffect.Close` であり本集計の対象に入るので、同じ不具合が残ってしまう。
  **台帳が数える承認の終端は台帳が持つ。**
- **改定 6（発注側の「届いたか不明」も終端 `Rejected` へ畳まない。改定 3 の裏側）**: 改定 3 は**照会側**の
  写像（`MoomooOrderState`）を直した。**発注側**には同じ穴が残っていた ——
  `MoomooBrokerAdapter.PlaceWithRejectionDetailAsync` の包括 catch が、**送信後**の SDK 例外・応答異常を
  終端 `Rejected` に倒していた。ここへ落ちる代表例は `SendAsync` の返信待ちタイムアウトで、
  **`send()` は既に実行済み**である（実測: `status=Rejected terminal=True orderId=1b26000f…`＝`Guid.NewGuid` の
  偽 ID → 台帳で `OrderExecuted(Rejected, 約定 0)` → 処理中 = 0 ＝**建玉の押さえが解ける**）。
  - **決済では二重決済でショート化する** —— 手仕舞いが証券会社側で生きているかもしれないのに押さえが解け、
    再要求が通って同じ株数に 2 本の決済が並ぶ。本 ADR 以前は 30 分の窓が偶然これを防いでいた
    （それが #848 の不便の正体でもあった）。
  - **エントリーでは無保護の建玉ができる** —— `Rejected` は発注執行で「終端失敗＝建玉が生じない」と読まれ、
    **保護レグを張らずに正常終了**する。注文が生きていれば建玉は無保護のまま残る。
  - **是正**: 包括 catch を廃し、**`BrokerDispatchIndeterminateException`**（`BrokerUnavailableException` と
    **対になる**新しい契約。「確実に未発注」の逆側＝「送信は済んだが結果が確認できない」）として伝播させる。
    発注執行は本例外を**明示的に捕捉して Error でログし再送出**する ——
    予約を**解放しない**（解放すると再配送で二重発注。`BrokerUnavailable` との決定的な違い）、
    予約を**確定しない**・結果を**保存しない**（**偽の注文 ID の終端記録を作らない**）、
    **見送りにもしない**（見送りは「発注していない」という主張であり、`Rejected` と同じ誤りになる）。
    予約は `Reserved` のまま残り、**client order id による突合**（IADR-0092 / IADR-0074）が
    `Placed` / `NotPlaced` / `Indeterminate` に解決する。**予約を勝手に完了させない。**
    🔴 **ただし突合は既定で無効である**（`Reconciliation:Enabled=false`・`UseBrokerProbe=false`。
    `deploy/` にも上書きは無い）。**いまの配備では滞留 `Reserved` は自動では解決せず、人が解決する**
    （手順は `docs/operations/broker-execution-paths-runbook.md`。有効化は #856）。
    本項の初稿は「突合が解決する」と**断定**していたが、それは機構が**存在する**という意味でしかなかった
    （3 巡目監査の指摘）。**安全側（撃ち直さない・押さえを解かない）は突合の有無に依らず成立する**が、
    **滞留の解消は依る**。
    🔴 ［2026-09-19 追記 / [#856](https://github.com/endazon/ai-stock-trading/issues/856)・IADR-0362］
    **上の「突合は既定で無効」「`deploy/` にも上書きは無い」は、配備については偽になった。**
    `deploy/helm/ai-stock-trading/values.yaml` が `Reconciliation__Enabled` / `__UseBrokerProbe` を `true` にし、
    滞留閾値 2 時間・巡回 1 時間で回す（アプリ側の既定は 3 つとも `false` のままであり、そちらの記述は真）。
    **ただし解放（`NotPlaced` → 予約の削除）だけは新設の門 `Reconciliation__ReleaseOnNotPlaced=false` で閉じている**
    ——解放は再発注の許可であり、「未発注」の根拠は remark 突合であって証券会社が「無い」と答えた事実ではない
    （SIMULATE が remark を往復させるかは実機未検証。往復しなければ全件が `NotPlaced`＝全件二重発注になる）。
    したがって**いま自動で解決するのは `Placed` 側（＋記録ありの自己修復）だけ**であり、`NotPlaced` と
    `Indeterminate` は据え置かれて人が解決する。門を開ける判断は #856 に残る。
    なお下記「残余リスク」の**「突合で発注済みと確定したエントリーに保護レグは張られない」は解消していない**
    （#853 が裁定を持つ）。有効化でこの経路が実際に踏まれるようになったため、常駐が 1 件ずつ Critical でログし、
    runbook にも確認手順を書いた（**黙って通り過ぎないことだけ**を先に成立させた）。
  - **変えない側**: 発注執行で `Rejected` を作る箇所は 3 つあり、誤っていたのは包括 catch だけである。
    **発注前検証での棄却**（確実に未送信）と **`MoomooTradeRequestException`**（`retType != 0`＝
    **確認できた**非受理）は `Rejected` のままとする（確認できた拒否による在庫解放は #848 の射程内）。
    🔴 **［2026-09-19 追記 / #848・B5］「`retType != 0`＝確認できた非受理」は誤りだった**（4 巡目監査）。
    確認できた非受理は `retType == -1` だけである。**改定 8** で訂正した。
  - **共有契約 `OrderStatus` へ値は足さない。** 必要なのは「不明という状態を運ぶこと」ではなく
    「**結果を確認できていないのだから何も主張しないこと**」である。`OrderStatus` は
    **証券会社に存在する注文の状態**の集合（FR-05）であり、存在するかが分からない注文はその要素ではない。
    足せば通知・監査・射影・ペーパーアダプタまで面が広がるうえ、**`Unknown` な注文記録**を台帳に作ることになり
    「偽の注文 ID を残さない」と正面から衝突する。**記録を作らず例外で終える**方が意味の上でも面の上でも小さい。
- **改定 7（「届いたか不明」を受ける**呼び出し側**も、未発注と仮定して撃ち直さない。改定 6 の裏側）**:
  改定 6 は「不明」を**例外**にした。その例外を**一括 catch で握る呼び出し側**が残っていた ——
  保護逆指値ガード（`ProtectiveStopGuard.ReplaceOrCloseAsync`）の成行手仕舞いである。
  catch は `MarkCompleted` を呼ばず `Remediation=None` で終わり、記録は `Active` のまま残るため、
  **次の巡回（既定 30 秒）で同じ数量の成行をもう一度送る**（実測: 不明のとき 1 巡目＝成行 1 回／
  2 巡目＝成行 **2 回**。改定 6 以前は終端 `Rejected` が**返って**いたので 1 回で完了していた）。
  1 巡回ごとに全数量の成行売りが 1 本増える＝**二重決済でショート化**であり、本追記が守る性質そのものが破れる。
  - **是正**: 成行手仕舞いを**予約 → 発注 → 確定の 3 相**（IADR-0057）へ載せる。DecisionId は既に決定的
    （`ProtectiveStopIds.CloseDecisionId(entry, attempt)`。手仕舞いが完了しない限り `attempt` は進まず、
    巡回をまたいで同じ値になる）で、足りなかったのは**予約**だった。送る前に `TryReserve`、
    取れなければ**送らない**。例外は 3 つに分ける —— **`BrokerUnavailableException`（確実に未発注）だけが
    予約を解放して次の巡回で撃ち直せる**。`BrokerDispatchIndeterminateException` と
    **分類できない例外**（送信後の保存失敗を含む＝未発注と言い切れない）は予約を `Reserved` のまま残し、
    **予約が残っている限り再送しない**。ソフトウェア逆指値（S1・#820）の決済と同じ作法である。
  - **巡回の入口で手仕舞いレグの痕跡を先に見る**（逆指値の再発注より**前**）。記録があれば送らずに完了、
    予約だけなら**逆指値の再発注も成行も行わず据え置く** —— 成行が生きているかもしれない建玉へ
    新しい逆指値を張ると、約定後に**建玉なき逆指値**が残り反対建玉になる。
  - **無音にしない／人を誤誘導しない**: `ProtectiveStopRemediation` へ **`CloseDispatchIndeterminate`** を足し
    （末尾。既存値の序数は動かさない）、不明になった巡回で Critical を 1 回出す
    （［2026-09-19 追記 / #848］**「1 回だけ」は改定 9 で「据え置きが続くあいだ 1 時間ごと」へ改めた**）。
    **`CloseDecisionId` / `CloseIntent` を運ぶ**ので、取引台帳は生きているかもしれない成行を
    **処理中の決済として押さえる**（`None` は運ばない約束であり、利用者の手仕舞い要求〔UC-06〕が通って
    同じ株数に 2 本並ぶ）。文面は「**送った・届いたか分からない・重ねる前に証券会社の画面で確かめよ**」
    （`None` の「解消にも失敗しました」は、読んだ人に手で成行を重ねさせる）。
    `OrderStatus` へ値を足さなかった改定 6 と矛盾しない —— あちらは**証券会社に存在する注文の状態**の集合、
    こちらは**システムが何をしたか**の集合であり、「送ったが確認できていない」はその正当な要素である。
  - **同じ反転は発注執行の成行手仕舞いにもあった**（`CloseUnprotectedPositionAsync`。エントリー直後に
    逆指値を張れなかったとき）。単発なので撃ち直しはしないが、改定 6 の前は偽 ID の記録＋`PositionClosed` で
    **台帳が 30 分押さえていた**ものが、改定 6 で `None`＝**押さえなし**に変わっていた。同じ 3 相へ載せた。
  - **変えない側**: 逆指値レグ（`PlaceStopOrderAsync` / `PlaceAlternativeStopOrderAsync`）の不明は
    従来どおり「未受理」と同じ分岐へ落ちる（改定 6 の前後で同一。孤立した逆指値の扱いは #853）。
    **確認できた拒否**が返った成行手仕舞いを「手仕舞い済み」と扱う既存の挙動も変えていない（#857）。
    `Place*` の全呼び出し元の判定は作業仕様書の B4 の節の表にある。
- **改定 8（発注応答の `retType` も、「確認できた非受理」は `-1` だけ。改定 6 の取りこぼし）**:
  改定 6 は「変えない側」として `MoomooTradeRequestException`（`retType != 0`）を**丸ごと**「確認できた非受理」に
  残した。**値域を実測していなかった。** SDK の列挙は
  `Succeed=0 / Failed=-1 / TimeOut=-100 / DisConnect=-200 / Unknown=-400 / Invalid=-500` であり、
  `moomoo-api 10.8.6808` を逆コンパイルして読むと、**`-100` と `-500` は OpenD の返事ではなく SDK が
  クライアント側で合成する値**である —— `-100` は送信済み要求を **12 秒**で打ち切ったとき、`-500` は
  **届いた応答の復号・パースに失敗したとき**に、SDK が応答オブジェクトを自前で組み立てて `retType` へ入れる。
  どちらも**送信は済んでおり、注文が受理されたかは分からない**。改定 3 が OpenD の注文状態 `4`（TIMEOUT）を
  不明へ分けたのと**同じ基準で扱うべき値**だった（4 巡目監査 B5。実測: `retType=-100/-400/-200` で
  `OrderExecuted.Status=Rejected orderId=<偽 32hex> reservation=Completed`）。
  - 🔴 **`-100` は既定構成での返信待ちタイムアウトの本線である。** 本実装の返信待ちの既定は 15 秒、SDK の打ち切りは
    12 秒なので、改定 6 が代表例として塞いだ `SendAsync` の `TimeoutException` より**先に** `retType=-100` が返る。
    **改定 6 だけでは、既定構成の返信待ちタイムアウトは塞がっていなかった。**
  - **是正**: 確認できた非受理を **`retType == -1`（`Failed`）に限る**（`MoomooRetType.IsConfirmedFailure`。
    値が SDK の列挙と一致することはテストで固定）。アダプタの `catch (MoomooTradeRequestException)` に
    `when (ex.IsConfirmedFailure)` を付け、**それ以外は改定 6 の「届いたか不明」の口へ落とす**
    （`BrokerDispatchIndeterminateException`。呼び出し側は改定 6・7 で既に正しく受けるので変えない）。
    未定義の値も不明へ倒す（改定 3 の「知らないコードは不明へ」と同じ規律）。
  - **`Invalid(-500)` は不明の側へ入れた。** 名前は「要求が不正で弾かれた＝確実に未発注」と読めるが、
    SDK の実装が `-500` を作るのは**応答を読めなかったとき**であり、受理の応答を読み損ねた場合もここへ落ちる。
    OpenD 自身が要求の不正を `-500` で返すことがあるとしても SDK 合成のものと区別できず、
    **区別できない以上「確実に未発注」とは言えない**。
  - **変えない側（回帰させない）**: 稼働環境で実測した確認できた拒否 2 件はどちらも `retType=-1` であり、
    従来どおり `Rejected`（在庫解放の引き金）のままである ——
    `The precision of Price in Place Order does not meet the specification.`（#844）／
    `Paper trading does not support Stop order.`（#809）。
  - `EnsureSucceeded` は変えない。照会（`null`＝不明・プローブは `Indeterminate`）と取消（失敗＝注文はまだ生きている）は
    どの `retType` でも**在庫を解放する向きへ倒れない**ため、分類が要るのは発注だけである。
  - 残余リスク: `-1` の `retMsg` の中身は検査しない。OpenD が自身の上流のタイムアウトを `-1` で返す可能性は
    SDK からは否定できないが、OpenD はタイムアウト・結果未知に専用の値（`-100` / `-400`）を持つので、
    それを契約として読む（`retMsg` の文言照合は版と言語で変わるため採らない）。
- **改定 9（成行手仕舞いの据え置きを無音にしない。改定 7 の補い）**: 改定 7 は Critical を**不明になった巡回の 1 回だけ**
  出した。通知を見逃すと、逆指値なしの建玉が無期限に残る（`None` は巡回ごとに Critical を出すので扱いが非対称だった）。
  さらに、**送信中にプロセスが止まった場合**（`OperationCanceledException`）と、巡回の結果を受け取ってから
  発行するまでのあいだに落ちた場合は、Critical だけでなく **`CloseIntent` も一度も発行されず、台帳が一切押さえない**
  （4 巡目監査の実測: 再起動後のイベント 0 件）。
  - **是正**: 「予約だけがある」分岐（巡回の入口）でも `CloseDispatchIndeterminate`（`CloseIntent` つき）を発行する。
    発行するのは ①**このプロセスがその `CloseDecisionId` をまだ通知していない**とき（＝再起動後の最初の巡回・
    送信中に止まった後）、②**前回の通知から 1 時間たった**とき、である。「通知したか」は**プロセス内の記憶**
    （`HeldCloseNotificationTracker`）で持ち、永続化しない —— **再起動で消えること自体が「再起動後に必ず再発行する」
    仕組みになる**。`PublishAsync` が失敗したときは常駐が未発行分の記憶を消してから投げ直す（次の巡回で再発行）。
  - 再発行は安全である: 台帳の `AppendApproval` は `DecisionId` で冪等（**窓も延びない**——最初の承認時刻のまま）、
    通知と監査は重複しても害が無い。通知の文面に「約 1 時間ごとに再通知する・同じ `CloseDecisionId` は同じ 1 本の成行」を
    足した（再通知を「もう 1 本送った」と読ませない）。間隔は定数（構成キーを足さない。本 ADR「なぜ構成キーを 1 つも足さないのか」）。
  - **塞がないもの**: 発注執行の `CloseUnprotectedPositionAsync`（エントリー直後の単発の成行手仕舞い）で送信中に
    止まった場合。巡回が無い（逆指値の記録が無くガードの対象にならない）ため、この仕組みは効かない。
    予約は残るので撃ち直しはしないが、Critical も台帳の押さえも出ない（残余リスク）。
- **窓は残す**（改定しない）。終端が**届かない**注文（照会不能・イベント欠落）は依然あり得るため、恒久ロックを
  防ぐ最後の受け皿として本決定の時間窓が要る。
- 残余リスク: 訂正（`OrderModified`）による減量は反映しない（終端ではないため承認数量のまま数える＝多めに
  押さえる安全側）。#847（成行での手仕舞い・取消の口）は本追記の射程外。

> ブロッキング 2 件として実測で指摘した ——（B1）在庫解放の終端に `Filled` を入れ、かつ終端の記録を
> 約定の記録より**前**に置いたため、全量約定の処理中に建玉が丸ごと空いて見える区間ができていた。

> **改定 2・改定 3 でどちらも塞ぎ、「不明は処理中のまま」は写像から集計まで通して成立するようになった。**

>
> **2 巡目の監査（head `94c0da10`）がブロッキング 1 件（B3）を追加で出した** —— 改定 3 が直したのは

> **改定 6 で塞いだ。** 3 度とも形は同じで、**「安全側」と書かれた既定が、下流の意味変更

> 🔴 **意味を変えたら、その意味に依存している既定を全部引き直す**（是正の母集合は「誤りの側の語」で引く）。

> 来なかった一括 catch（保護逆指値ガードの成行手仕舞い）の意味が「確実に失敗した → 次で再試行」から
> 「**届いたか不明 → 未発注と仮定して撃ち直す**」へ反転した。**改定 7 で塞いだ。**
> 作業仕様書と PR 本文はこの呼び出し側を「**変更なし——分岐は是正前後で同一**」と書いており、
> **事実と異なっていた**（同一だったのは逆指値の再発注だけ）。

> （B2 は注文状態の値域、B5 は応答コードの値域で、同じ穴を 2 度踏んだ）。

> 🔴 **教訓（B2・B3・B4 は 3 回とも同じ型だった）: 新しい引き金／新しい例外を足すと、

> ①**引き金・例外・戻り値の意味を足したり変えたりしたら、それを受ける側を全部引く**
> （メソッドの全呼び出し元・その型を捕まえ得る全 catch。`catch (Exception` は**新しい例外を黙って受ける**）、
> ②受ける側ごとに「**未発注／未約定／建玉なしを仮定していないか**」と「**次の巡回・次の配送で
> もう一度やらないか**」を確かめる、③「**変更なし**」と書く前に、その行を**誤りの側の語で引き直して
> コードを読む**（diff に現れない行こそ反転する）。

### 決定 4: 監査イベントを 1 つ足し、承認より先に発行する

`PositionCloseRequested`（`DecisionId` / 銘柄 / 市場 / 方向 / 数量 / 価格 / **Actor** / **Reason** / 時刻）を新設し、
`OrderApproved` より**先に**発行する。`OrderApproved` はアクターも理由も持たないため、これが無いと
「誰が・なぜ建玉を落としたか」が監査台帳に残らない（FR-11）。

順序の根拠は、「起きた操作に監査が無い」より「監査があるのに操作が無い」ほうが安全であること。後者は同一
`DecisionId` の後続イベント（`OrderApproved` / `OrderExecuted`）の不在として**検知できる**が、前者は検知できない。

## 根拠

### なぜ「決済専用の経路」を作らないのか（選択肢 3 を採らない理由）

二重計上を作らない唯一確実な方法が「約定を記録する経路を 1 本に保つ」ことだからである。決済専用の経路を作ると、
台帳・枠回復・通知・監査の受け口がそれぞれ 2 本になり、片方だけ落ちる／両方が同じ約定を計上する事故の面が増える。
既存経路に載せる限り、冪等性は `OrderId` 単位の単調 upsert（IADR-0113）と `DecisionId` 予約（IADR-0057）が
そのまま効く。

### なぜ `DecisionId` を決定的にしないのか

損切り（IADR-0015）は `StopLossTriggered.EventId` から決定的に採る。同一イベントの再配送で二重発注しないためである。
一方、利用者の決済要求は**各要求が独立した注文**であり、「同じ銘柄・同じ数量をもう一度落とす」は正当な操作になり得る。
内容から決定的に導くと、正当な連続決済が黙って冪等に潰される。多重投入に対する防御は決定 3（在庫ガード）が担い、
ネットワーク再送に対する防御は発注執行側の予約が担う。

### なぜ構成キーを 1 つも足さないのか

本経路は**利用者の明示操作でしか動かない**。常駐処理ではないため「既定オフで出荷し、有効化して使う」という
opt-in の型が意味を持たず、無効化スイッチは「手仕舞えない状態を作れるスイッチ」にしかならない。
Helm / values / compose / `.env.example` は不変で、本番描画はバイト等価である。

  （#768）。**訂正の口は依然として作らない**（実 OpenD へ `TrdModifyOrder` を配線していない）。
  🔴 取消が在庫の押さえを解くのは**確実に取り消せたと確認できたときだけ**である（IADR-0357 決定 3。
  本 ADR 決定 3 の改定 1/4 が定める `MarkTerminal` の引き金を、不明な取消で引かせない）。
- **AI は依然として自分で建玉を落とせない。** `TradeDecisionService` の `PositionEffect.Open` 固定は本 ADR の
  対象外で、判断由来の決済は #292 の PR 3/3（IADR-0119）で扱う。
- Discord の `/close` コマンドは本 ADR の対象外（HTTP 経路のみ）。

## 代替案を採らなかった理由

- 選択肢 2（発注執行に置く）: 建玉・換算レート・段階 Mode・現在値がリスク管理側にあり、s2s の往復と権威の二重化を招く。
  発注執行サービスは現状 HTTP クライアント／s2s 配線を持たず、そのためだけに認証サーフェスを増やすことになる。
- 選択肢 3（決済専用イベント）: 約定の記録経路が 2 本になり、二重計上・取りこぼしの面が増える。既存経路に載せれば
  冪等性の担保をそのまま再利用できる。
