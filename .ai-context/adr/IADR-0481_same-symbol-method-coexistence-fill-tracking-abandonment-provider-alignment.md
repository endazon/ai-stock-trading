# IADR-0481: 同じ銘柄の手法の併存を新規建てで止め、約定追跡の打ち切りを監査へ残し、発注先の食い違いを知らせる（#1048）

  [IADR-0406](IADR-0406_s0-stop-leg-fill-tracking-beyond-window.md)（S0 のレグは追跡上限の対象外・追跡の起点を進める）。いずれも覆さない。

## 背景

1. **Q2（同じ銘柄の手法の併存）**: 保護記録の持ち分（`ProtectiveStopNetting.RemainingPositionFor`）はブローカーの建玉照会＝銘柄単位の純額からしか
   測れない。S0 の側からは記録を持たない S2 の建玉を差し引けず（S0 の建玉が消えても S2 の数量で「建玉あり」と読み、逆指値を残す）、
   S0 と S3 は互いの主張を差し引き合って建玉残を 0 と読み得る（両方の逆指値を取り消す）。今は到達しない（SIMULATE で S0 の逆指値は拒否される・
   S2 は SIMULATE だけ・稼働は S1）が、実弾・S3 の常用の前に扱う約束だった。
2. **Q3（約定追跡の打ち切り）**: 約定追跡（`OrderFillPoller`）は追跡上限（既定 24 時間）を過ぎた非終端の記録を黙って対象から外していた。
   以後、その注文の終端の約定記録は台帳へ届かず、S2 の免除（`ProtectiveStopWaived`）の打ち消し・数量の確定（`ProtectiveStopWaiverSettled`）も
   付かない（発注数量のまま残る）。外れたことはどこにも残らなかった。
3. **Q1（発注先の設定値）**: 設定上の発注先（`RiskManagementSettings.BrokerProvider`）が内蔵 paper のまま、実際の発注は moomoo SIMULATE という
   食い違いが観測されていた。IADR-0413 決定 1 は「運用で揃える」と決めたが、揃っていることを確かめる手段が無かった。

## 決定

1. **Q2: 同じ銘柄・同じ向きに別の手法の有効な保護記録があれば、新しい手法での新規建てを見送る**（新しい見送りの理由
   `OrderDispatchForgoneReason.StopLossMethodConflict`。序数 8・末尾追加）。
   - 判定は純関数 `StopLossMethodCoexistenceGate`。「有効」＝完了していない記録（Active と、送信結果待ちの AwaitingEntry）。自分の記録・同じ手法・
     別銘柄・別市場・逆方向は数えない。手法は解決結果から写す（未実装の手法の読み替えは S0）。読み出しは新しいストアの口
     `IProtectiveStopOrderStore.FindOpenFor`（機構・件数を問わず、完了していない行。EF・インメモリで上書き）。
   - **窓の両端で確かめる**: 予約の**前**（前の端。保護記録の読み取りだけ）と、自分の記録を残した**後**・ブローカーへの送信の**直前**（後の端）。
     S1 は送る前に自分の行を、S0 / S3 は予約の後に AwaitingEntry を残すので、別の手法で同時に建てようとした 2 本は少なくとも一方が他方を見る。
     後の端で見つけたら予約を Forgone へ移し、自分の記録を閉じて送らない（接続確立の失敗と同じ経路）。どちらの端も**送信前**であり、
     リスク管理の在庫解放の分類（`OrderDispatchForgoneLifecycle`）は `true`（確実に未発注）。
   - **決済（Close）には効かない**（判定は新規建ての分岐の内側だけ）。手仕舞い・損切りは止めない（FR-10）。
   - 見送りは理由つきで監査台帳・通知・メトリクスへ出る（既存の見送りの経路。通知の文面は「決済は止めていない・その建玉を手仕舞ってから建てる」）。
2. **Q2（S2 の建玉）: moomoo SIMULATE の S0・S3 の新規建ては、記録の無い建玉（S2・人手）がある銘柄では見送る**（既存の理由
   `UnattributedPosition`）。S2 は記録を持たないので決定 1 の照合では見えず、帰属不明の建玉としてしか現れない。判定は S1 の武装の前提条件と
   同じ `HasUnattributedPositionAsync`（建玉照会の前と後で主張を読み、小さい方を採る＝IADR-0344 追記(11)）。
   - 対象は **moomoo SIMULATE だけ**（S2 は SIMULATE でしか選べない）。実弾・内蔵 paper の S0 の経路には建玉照会を足さない。
   - **建玉照会の能力が無い発注先では判定しない**（S0 / S3 の持ち分の計算＝常駐ガードの純額もその能力が無ければ行われず、併存の害が起きない）。
     能力はあるのに照会が失敗した（null）ときは S1 と同じく「ある」側へ倒す。
   - S1 の新規建てが S2 の建玉を見て見送る経路は従来どおり（`UnattributedPosition`）。
3. **Q3: 約定追跡の期限を過ぎて非終端のまま打ち切った注文は、打ち切ったことを監査へ残す**（新しい契約イベント `OrderFillTrackingAbandoned`）。
   - 打ち切りの対象は、追跡上限より古い非終端の記録のうち、**その追跡の起点で**まだ打ち切りを記録していないもの
     （`IExecutedOrderStore.FindTrackingExpired`。Active な S0 / S3 の逆指値レグは IADR-0406 決定 2 のとおり対象外）。
   - **窓の両端**: 期限（前の端）を過ぎた記録を、打ち切る直前に 1 回だけ照会し直す（後の端）。終端していれば通常どおり `OrderExecuted` を出して
     打ち切らない。非終端（不明・変化なし・一部約定の進捗）なら、最後の観測を載せて打ち切りを返す。
   - **印は「打ち切った追跡の起点」**（`executed_orders.TrackingAbandonedFrom`。列の追加だけの移行
     `20261002120000_AddExecutedOrderTrackingAbandonedFrom`）。起点が後から進められて（IADR-0406 決定 3 の `RenewTracking`）再び期限を過ぎたら、
     印と起点が食い違うので**別の打ち切り**として改めて記録する。
   - **発行の後に印を書く**（Worker＝`OrderFillPollingService`）。先に書くと発行に失敗した打ち切りが二度と記録されない。再発行は監査台帳が
     OrderId と追跡の起点から決定的に導いた Id（`AuditEntryFactory.FillTrackingAbandonedIdFor`）で 1 件に畳む。
   - 相関は注文の DecisionId（エントリーなら免除・保護レグと同じ）。要約は「以後、終端の約定記録は台帳へ届かない（免除があれば発注数量のまま）」。
     免除を打ち消さない（終端ではない）。Discord 通知は足さない（警告ログ 1 行と監査台帳）。
4. **Q1: 設定上の発注先と実際の発注先の食い違いを、口座照会の観測のたびに確かめて知らせる**（`BrokerProviderAlignment.Check`・
   `BrokerProviderAlignmentHandler`）。実際の発注先は発注執行が `BrokerAccountObserved.Provider` に載せる自己申告（IADR-0153）。
   - 食い違えば Warning（実際が実弾なら Error）で、揃える操作 `PUT /risk-controls/settings/broker-provider` と揃える先の値を名指しする。
     揃っていれば 1 件も出さない。観測は既定 5 分ごとなので、起動の直後に最初の判定が走る（起動時の警告を兼ねる）。
   - **設定値を書き換えない**（観測から黙って書き換えると、実弾への切り替えに求める確認操作〔FR-20〕を迂回する経路になる）。
     揃えるのは利用者の操作である（IADR-0413 決定 1 の「運用で揃える」を維持し、確かめる手段だけを足す）。
   - 観測の記録（`BrokerAccountObservedHandler`）とは別のハンドラにする（判定の失敗で口座種別・基準資金の供給を止めない）。設定を読めなくても例外を投げない。

## 採らなかった案

- Q2 の案 a（S2 にも保護記録の行を持たせて差し引く）・案 c（建玉がある間は設定側で手法の切り替えを拒否）・案 d（運用で回避）: 利用者が案 b を選んだ。
- **前の端だけ（予約の前だけ）で確かめる**: 照合の後に現れた別の手法の記録（並行した別の承認）を見落とす（作業仕様書のプローブ P2-増）。
- **後の端だけ（送信の直前だけ）で確かめる**: 予約の前に見えていた記録が送信までに完了した（決済を送って記録を閉じたが、まだ約定していない）とき、
  建玉が残っているのに建ててしまう（プローブ P2-減）。両端なら両方を塞ぐ。
- **S2 の建玉を発注の記録から推定する**（保護記録を持たない新規建ての記録＝S2）: 建玉がまだ残っているかを知る手段が建玉照会しかなく、
  人手・判断の決済で消えた後も見送り続ける。
- **打ち切りを期限だけで判定する**（打ち切る直前の照会をしない）: 最後の巡回の後・期限の前に終端していた注文を「打ち切った」と残し、
  終端の約定も取りこぼす（プローブ P3-減）。
- **打ち切りの印を真偽で持つ**: 起点が進められて再び期限を過ぎた 2 回目の打ち切りが残らない（プローブ P3-増）。
- **印を持たず毎巡回すべての期限切れを発行し、監査台帳の決定的 Id で畳む**: 期限切れの記録が残る限り 30 秒ごとに発行と照会が続く。
- **Q1 で設定値を観測から自動で揃える**: 上の決定 4 の理由（確認操作の迂回）。

## 結果

- 手法の違う建玉が同じ銘柄に新たに併存しなくなる（S0 と S1・S2・S3、S1 と S2・S3、S2 と S3 のどの組み合わせも）。既存の差し引きの規則
  （`ProtectiveStopNetting`）は変えていない——併存を作らないことで、その規則の前提（同じ銘柄に手法は 1 つ）を保つ。
- 約定追跡を打ち切った注文が監査台帳に残り、免除の記録が発注数量のまま残る理由を相関で辿れる。
- 設定上の発注先の食い違いはログに出続け、利用者が揃えた時点で止まる。

## 残余リスク

- **配備より前に既に併存している建玉**は見送りでは解けない（今は到達しない構成のため、併存は無い見込み）。差し引きの規則の S0 と S3 の相互の差し引きは残る。
- **S2 の新規建ては自分の記録を残さない**ので、S2 と S0 / S3 の同時の新規建て（設定の切り替えの瞬間に 2 本の承認が並行）は、S0 / S3 の側の
  建玉照会がまだ S2 の約定を映していない窓では両方が通り得る（S2 の側の後の端は S0 / S3 の AwaitingEntry を見る）。
- **S0 / S3 の主張は承認数量**（一部約定でも満額）なので、自分の S0 の一部約定と S2 の建玉が重なると帰属不明が過少に読まれ得る。
  逆に、送信結果待ち（AwaitingEntry）の自分の S0 / S3 は主張に数えないので、その約定は帰属不明に見えて 2 本目が見送られ得る（安全側）。
- 人手で建てた建玉も「記録の無い建玉」として moomoo SIMULATE の S0・S3 の新規建てを止める（S2 と区別できない）。
- 送信結果待ちの記録が人の対応まで残ると、その銘柄では別の手法での新規建てが止まり続ける（安全側。Runbook の据え置きの手順で解く）。
- 打ち切りの記録は監査台帳だけで、Discord 通知は出さない。S1 の決済レグを打ち切っても再武装はしない（従来どおり。記録だけが残る）。
- 設定上の発注先を揃える操作そのもの（稼働中の `PUT`）は利用者が行う。揃えるまで警告が続く。
