# IADR-0555: 方針の改訂の出力上限を 16384 へ上げ（effort は下げない）、出力上限での打ち切りを利用者への応答で区別する（#1383）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: **Accepted**
- 日付: 2026-10-17
- 決定者: Claude Code（実装）。#1383（PoC 2026-10-17 の `/policy` の失敗）を受けた。
- 改める決定: IADR-0522 決定 1 の値（8192）と追記 1 の「実効の天井」の見積り（毎秒 50〜80 トークン）。IADR-0522 の他の決定は有効のまま。

## コンテキスト

PoC 2026-10-17 18:11 JST（AST rev 49 `31b1a087`）の `/policy`（日報・指示 412 文字）が失敗した。報告書サービスのログ:

| 項目 | 値 |
| --- | --- |
| モデル | `claude-sonnet-5-5`（purpose `report-daily`） |
| 入力 / 出力トークン | 5,898 / **8,192**（上限ちょうど） |
| 終了理由 | `max_tokens` |
| 見える本文 | **1,609 文字**（JSON の途中） |
| 費用 | ¥15.34（= 5,898 × 0.327 ＋ 8,192 × 1.637 円/1k。values-local の単価と一致） |
| 利用者への応答 | 「AI の案を作れませんでした（AI の出力が JSON ではありませんでした）。方針は変わっていません。」 |

直前（18:09）の改訂は出力 5,697 で通った。IADR-0522 の実測（3,805 / 3,378）は 4.5 / 5 系で取った値である。
5.5 系では Sonnet 5.5 の thinking を無効にできず（`disabled` は 400）、既定 effort は `high` である（計画 ADR-0064 実測 5・MSP の ADR-0138 実測 4）。
思考トークンは `max_tokens` に含まれ、量は呼び出しごとにぶれる。同じ規模の改訂でも通ったり切れたりする。

利用者への応答も誤っている。上限で切れた JSON を「JSON ではない」（形式の誤り）と返すため、再試行で通り得ることが分からない。

### 手元で取れる材料

1. **思考の分の推定**: 本文 1,609 文字は、日本語の 1 文字を 0.7〜1.2 トークンとすると約 1,100〜1,900 トークンである。
   したがって思考は少なくとも約 6,300〜7,100 トークンを使った。通った回の出力全体（5,697）より多い。
   案の本文の全体（方針 2,000 文字以内＋入れ替え案＋説明）を約 2,000〜3,500 トークンとすると、この回に必要だった出力は約 8,300〜10,600 トークン以上である。
2. **出力の速さの下限**: 失敗した呼び出しは上限時間（報告書サービスの既定 95 秒）の内に 8,192 トークンを返した。
   **出力の速さは少なくとも毎秒 86 トークン**（8,192 ÷ 95）である（入力の処理の時間を含めた平均。実際の生成の速さはこれより速い）。
   IADR-0522 追記 1 の仮定（毎秒 50〜80 トークン）はこの実測と矛盾する。
3. **上限時間の連なり**（IADR-0522 追記 1。本 IADR では変えない）: ゲートウェイの上流の待ち 100 秒（MSP#1872 で `Llm:AnthropicTimeoutSeconds` として構成化されたが、既定は 100 秒のまま）＞ 報告書サービス 95 秒。通知サービスの外側 120 秒 ＞ 95＋10 秒。
4. **effort の置き場所**: effort は基盤のゲートウェイの `Llm:PurposeEffort`（purpose → effort）で決まる（MSP:IADR-0531）。既定は `rerank=low` だけで、AST の用途は提供元の既定が効く。
   🔴 **方針の改訂の purpose は報告書の散文と同じ `report-daily` / `report-weekly` / `report-monthly` である**（計上区分だけ `policy-revision`。IADR-0432 決定 2）。
5. **計画の effort の決定**: 計画 ADR-0064 決定 5・MSP の ADR-0138 決定 4 は「用途ごとの effort は設定値で持つ。既定は提供元の既定。**既定から変える用途は理由と実測を実装の IADR に記録する**」と定める。effort はゲートウェイの用途別設定で決まり、設定を持つのは基盤側である。
6. **単価**（values-local。円/1k）: sonnet-5-5 入力 0.327・出力 1.637、opus-5-5 入力 0.655・出力 3.274。1 日の改訂は既定 10 回で、失敗も 1 回に数える（IADR-0432 決定 1）。費用は月次 LLM 上限の対象外である（ADR-0042 決定 3）。

実 API はこの作業では呼べない（PoC の Anthropic キーへ届かない）。上の数は PoC のログ 1 件と既存の記録からの推定である。PoC で取る計測は下の §PoC での計測 に書く。

## 決定

### 決定 1: 方針の改訂の `MaxTokens` を 8192 → 16384 に上げる。effort は下げない

- `LlmReportPolicyReviser.MaxTokens` を **16384**（4096 の 4 倍）とする。判断・一次スクリーニング・報告書の散文は 4096 のまま（決定 4）。
- 16384 の根拠: 材料 1 の推定（約 8,300〜10,600 トークン以上）の 1.5 倍以上で、思考のぶれを吸収できる。4096 の整数倍で、値の由来を追いやすい（IADR-0522 決定 1 と同じ）。
  `max_tokens` は上限であり固定消費ではないため、上限に届かない回の費用は変わらない（IADR-0101）。
- **effort（`medium` / `low`）を採らない理由**:
  1. effort は purpose 単位で効く（材料 4）。方針の改訂だけ下げる手段が無い。`report-daily` を下げると日報の散文も下がる。方針の改訂専用の purpose を作ると、基盤の割当表に無い値は既定モデルへ無音で落ちる（IADR-0120 の罠）。割当表（計画 ADR-0064 決定 1）と基盤の設定の両方を変える必要がある。
  2. 計画は「既定は提供元の既定。変えるなら実測を IADR へ」と定める（材料 5）。effort を下げた方針案の質（取引に効く方針の妥当さ）は測っていない。実測の無いまま既定から外すことは計画の原則に反する。
  3. 設定の持ち主は基盤である（材料 5）。AST の 1 定数で直せる上限と違い、2 リポジトリの配備順序が絡む。
  - **上限を上げる案は既定の effort のままで、計画と矛盾しない。** 計画への環流は要らない。
- **実効の天井は上限時間で決まる。** 95 秒 × 出力の速さ（材料 2 で毎秒 86 トークン以上）である。毎秒 172 トークン未満なら、16384 に届く前に上限時間が来る。
  16384 は時間の天井より上に置いた。思考が長い回は打ち切り（`max_tokens`）ではなく時間切れ（`TimedOut`・案なし）になり得る。どちらも案なしで安全側である（時間切れの理由は従来どおり「AI の応答が 95 秒以内に返りませんでした」）。
  上限時間を延ばす（ゲートウェイの `Llm:AnthropicTimeoutSeconds` と AST の 95 / 120 秒の連なりを合わせて見直す）ことは本 IADR ではしない。PoC で時間切れが出たら判断する（§PoC での計測）。
- **最悪の費用**（上限まで出力した 1 回。入力は今回の 5,898 トークン）:

| モデル（purpose） | 8192（従来） | **16384（本決定）** | 1 日 10 回の上限 |
| --- | --- | --- | --- |
| sonnet-5-5（日報） | ¥15.34 | **¥28.75**（26.82＋1.93） | ¥287 |
| opus-5-5（週報・月報） | ¥30.68 | **¥57.50**（53.64＋3.86） | ¥575 |

  回数は 1 日 10 回（既定）で抑えられ、費用は `policy-revision` の区分で月報 §7 に載る（月次 LLM 上限の対象外）。時間切れの回は費用が計上されない（IADR-0522 追記 2 の残余リスク。本決定で頻度が増え得る）。

### 決定 2: 出力上限で JSON が壊れたら、失敗の種別を `Truncated` とし、利用者へ「途中で切れた」と返す

- 案の検証が通らず、かつ終了理由が `max_tokens` なら、`PolicyRevisionFailure.Truncated` を返す。理由（利用者へ見せる文言）は
  「AI の出力が上限で途中で切れました。再試行で通ることがあります（1 日の回数に数えます）。通らなければ指示を短くしてください」とする（`LlmReportPolicyReviser.TruncatedMessage`）。
  本文が空・無い場合も同じ（思考で上限を使い切った）。
- 終了理由が `max_tokens` でない形式違反は従来どおり `InvalidOutput`（パーサの理由）とする。
- 閉じた JSON が `max_tokens` で返った場合は従来どおり案として返す（IADR-0522 決定 2・IADR-0104 決定 5）。上限到達の警告ログも従来どおり出る。
- 応答の経路は変えない。`ReportPolicyRevisionService` は理由を「AI の案を作れませんでした（…）。方針は変わっていません。」に包んで返し、通知サービス・Discord はそれをそのまま出す。
  `Truncated` は報告書サービスの内部の種別で、ワイヤ（REST・gRPC）にも台帳にも載らない（台帳の結果は従来どおり `AiFailed`）。

### 決定 3: 応答を受け取ったら、所要時間と出力トークンを情報ログに 1 行出す

- 行: `方針の改訂 LLM の応答を受け取りました（elapsedMs=… outputTokens=… maxTokens=16384 textLength=… stopReason=… model=…）`。本文は載せない。
- 理由: 出力の速さ（＝上限時間の内に出せる出力の天井）は今のログから取れない（費用計上のログは DBG で、所要時間を運ばない）。`textLength` は思考の分の推定に使う。PoC の計測（下）に要る。

### 決定 4: 報告書の散文（report-daily / weekly / monthly）は上限 4096 と扱いを変えない。上限到達の警告に上限・出力トークン・モデルを足す

- 点検の結果: 散文は**同じ構造では失敗しない**。
  - 散文は JSON を解析しない。打ち切られた本文は捨てずに報告書へ採る（IADR-0104 決定 5）。方針の改訂のように「形式違反で全部失い、理由を取り違える」ことは起きない。
  - 思考で上限を使い切って本文が空なら、プレースホルダ散文へ倒れる（報告書は発注を伴わず、承認の前に利用者が読む）。ログは「応答本文が空です（stopReason=max_tokens）」で原因が分かる。
  - 利用者が再試行を判断する対話の応答が無い（自動生成。作り直しは別の機能で、本文を見て判断する）。区別した理由を返す先が無い。
- 4096 を上げない理由: 5.5 系での散文の出力の実測が無い。IADR-0522 の実測（最大 1,048）は 5 系で、旧 `claude-sonnet-5` も thinking が既定で有効（effort `high`）だった（MSP:IADR-0531）。上げる根拠は 5.5 系の実測で取る。
- 実測を取れるよう、上限到達の警告に `maxTokens`・`outputTokens`・`model` を足す（方針の改訂の警告と同じ形）。上限は `HttpReportNarrativeDrafter.NarrativeMaxTokens`（4096）として 1 箇所に置く。

## 検討した選択肢

1. **上限を 16384 に上げ、effort は既定のまま（採用）** — AST の 1 定数で直り、計画の effort の原則（既定のまま）と矛盾しない。
2. effort を `medium` / `low` に下げる — purpose を散文と共有しており方針の改訂だけを下げられない。下げた案の質の実測が無く、計画の原則（既定から変えるなら実測）に反する。設定の持ち主は基盤（決定 1）。
3. 上限を 12288（3 倍）にする — 材料 1 の推定の上側（約 10,600）に対して余裕が 1.2 倍しかなく、思考のぶれで再び切れ得る。
4. 上限を 32000 以上にする — 時間の天井（95 秒 × 速さ）を大きく超え、上げた分のほとんどが使えない。最悪の費用だけが増える。
5. 上限時間も延ばす（ゲートウェイ 100 秒 → 180 秒等、AST 95 / 120 秒を合わせて） — 基盤の構成と AST の 3 箇所を同時に変える。今回の失敗は打ち切りで、時間切れではない。PoC で時間切れが出てから判断する。
6. 切れたら自動で再試行する — 失敗も課金され、1 日の回数を消費する。利用者が指示を短くする選択を奪う。

## 結果

- 良い影響: 方針の改訂が 5.5 系の思考で切れにくくなる。切れたら利用者に「上限で切れた・再試行で通り得る・指示を短く」と伝わる。所要時間と出力トークンから出力の速さが測れる。
- 悪い影響 / トレードオフ:
  - 上限まで出力した回の費用が約 2 倍（sonnet-5-5 で ¥28.75、opus-5-5 で ¥57.50）。
  - 思考が長い回は打ち切りの代わりに時間切れになり得る。時間切れの回の費用は計上されない（IADR-0522 追記 2）。
- 残余リスク:
  - 推定（材料 1・2）は PoC のログ 1 件に基づく。思考の量の分布は測っていない。
  - 時間切れ（95 秒）で上流の生成が止まるか、課金がどこまで発生するかは確かめていない（gRPC の deadline はゲートウェイへ伝わるが、ゲートウェイから上流への取り消しの扱いは基盤に依る）。
  - 散文の 4096 が 5.5 系で足りるかは未確認（決定 4。警告で測る）。

## PoC での計測

配備後、次を取って本決定を確かめる（実 API を呼ぶため PoC で行う）。

1. **回数と条件**: 日報の `/policy` を **10 回以上**（1 日の上限 10 回のため 2 日に分ける）。指示の長さは短い（約 50 文字）・中（約 400 文字。今回と同じ規模）・長い（約 1,000 文字）を混ぜる。週報（opus-5-5）でも 2〜3 回。
2. **見るもの**（報告書サービスのログ）:
   - 決定 3 の行の `elapsedMs`・`outputTokens`・`textLength`・`stopReason`・`model`
   - 費用計上の行（`purpose=policy-revision ... in= out= amount=`）
   - 結果（案あり／`Truncated`／時間切れ「方針の改訂 LLM がタイムアウトしました」）
3. **出すもの**:
   - 出力の速さ = `outputTokens ÷ elapsedMs`（中央値と最小）と、時間の天井 = 95 秒 × 速さ
   - 思考の分 ≈ `outputTokens` − 本文のトークン（`textLength` × 0.7〜1.2）。最大と中央値
   - `max_tokens` と時間切れの件数
4. **判断の基準**:
   - 打ち切り 0・時間切れ 0・出力の最大が 16384 の 70%（約 11,500）以下 → 本決定のまま。
   - 時間切れが出る → 上限時間の連なりの見直し（選択肢 5）か、方針の改訂の effort を下げる（選択肢 2。専用の purpose と割当表・基盤の設定が要るため、計画へ環流する）。
   - 16384 でも打ち切りが出る → effort の見直し（同上）。
   - 散文: `報告書散文 LLM の応答が出力上限に到達しました` と `応答本文が空です（stopReason=max_tokens）` の件数と `outputTokens`。出たら 4096 を見直す。
