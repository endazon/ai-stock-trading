# IADR-0529: 新規建ての審査を直列化し、承認した新規建てを同じトランザクションで予約する（#1319）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

## コンテキスト

定時サイクル（`InformationCollectedHandler`）は監視銘柄を 1 件ずつ判断し、判断ごとに `TradeDecisionMade` を発行する。Wolverine はハンドラが成功した後に発行をまとめて送るため、**1 サイクル分の判断 N 件はリスク管理へ同時に届く**。

審査（`OrderScreeningService`）は 1 件ごとに snapshot を組むが、承認しても台帳に何も書かない。承認行（`approved_orders`）は `OrderApproved` が RabbitMQ を往復してリスク管理自身へ戻ってから `OrderApprovedLedgerHandler` が書く（その前に認識時レートを非同期で解決する）。保有建玉数・日次発注累計・段階資金は、約定と「承認行のある未終端の新規建て」（IADR-0346）から数える。したがって同じサイクルの N 件は、すべて**同じ古い snapshot**で判定される。建玉 0 で 6 銘柄が買いと判断されれば 6 件とも承認される。1 注文あたりの上限（25%）は効くので、1 サイクルで 25% × 6 ＝ 150% まで承認され得る。

IADR-0346 は残余リスクで「承認直後の数秒は次の審査から見えない。定時判断の周期（5 分）に比べて無視できる」「並行審査は互いの未約定を見ない（直列化は範囲外）」と書いた。**次の判断は 5 分後ではなく同じ瞬間に届く**ので、この評価は誤りだった。

## 決定

### 決定 1: 新規建ての審査は DB の advisory lock で直列化する

- 新規建て（`PositionEffect.Open`）の審査は、`IEntryReservationStore.RunSerializedAsync` の中で行う。EF 実装（`EfEntryReservationStore`）は次の順で動く。
  1. トランザクションを始める。
  2. `SELECT pg_advisory_xact_lock(<定数>)` でロックを取る。
  3. 審査（再配送の判定 → snapshot の読み取り → 判定 → 予約の書き込み）を行う。
  4. コミットする。例外で抜けたらロールバックする。
- ロックは DB が持つ。**単一レプリカの前提に頼らない**（プロセス・レプリカをまたいで新規建ての審査が 1 本ずつになる）。トランザクション境界のロックなので、コミット・ロールバックで自動的に外れる（外し忘れが無い）。
- 審査の読み取り（台帳・注文源・設定など）と予約の書き込みは、同じ scoped の `RiskManagementDbContext` の上で走る。このため、すべてこのトランザクションに入る。READ COMMITTED の各文は文の開始時点でコミット済みの行を読むので、**ロックを取った後の読み取りは、前の審査がコミットした予約を必ず見る**。
- 再配送の判定（決定 4）も臨界区間の中に入れる。外に置くと、同じ判断の並行な 2 配送が両方とも「予約なし」と読み、2 本目が自分の予約で自分を拒否する（IADR-0407 の反転が並行で戻る）。
- 関係 DB でないプロバイダ（テストの EF InMemory）はトランザクションも advisory lock も持たない。この場合はプロセス内のセマフォへ縮退する。本番の配線は常に Npgsql である。インメモリ実装（`InMemoryEntryReservationStore`）はインスタンスのセマフォを使い、例外で終わった臨界区間の予約を取り消す。
- 依存は**必須**（`OrderScreeningService` のコンストラクタ引数。IADR-0163 決定 2）。不在は「定時サイクルの同時到着で上限をすり抜ける」穴そのものである。

### 決定 2: 承認した新規建ては、同じトランザクションの中で予約行（`entry_reservations`）に記録する

- 🔴 **予約は承認行（`approved_orders`）とは別の表に書く。** 承認行は IADR-0407 の「発行済み」の印である（再配送の判定は承認行の有無で見る）。審査の中（発行の前）に承認行を書くと、書いた後に `OrderApproved` の発行が失敗した場合や、プロセスが落ちた場合に、再配送が「発行済み」とみなして再発行しない。その結果、**発注が永久に出ない**。
- 列は次のとおり（主キーは `DecisionId`）。
  - 注文源へ載せる値: 銘柄・市場・方向・数量・価格・`FxRateToBase`・承認時刻。数量・価格・レートは承認行と同じ値（Intent）にする。こうすると、承認行へ引き継がれたときに算入の額が変わらない。
  - 承認を組み直すための値（決定 4）: 承認数量・承認時刻・損切りの実行機構。
- 承認時刻はマイクロ秒に切り詰めて承認と予約の両方に使う。PostgreSQL の timestamp はマイクロ秒精度なので、切り詰めないと組み直した承認の時刻が最初の発行と 100ns 単位でずれる（実 DB で実測）。
- 拒否した審査は予約を書かない（トランザクションの中で何も書かない）。
- 予約の書き込みは判断 ID で冪等である。**古い行は消さない。** 統制の状態であり、自動パージの対象外として切替でも保全する（`scripts/cutover-count-reconcile.sh` の manifest に `state` として載せる）。注文源は承認時刻の下限と当日の判定で切り出すので、古い行は算入されない。行は新規建ての承認 1 件につき 1 行で、増え方は承認行と同じである。
- マイグレーション: `AddEntryReservations`（表と `ApprovedAt` のインデックスを作るだけ。既存の表は変えない）。

### 決定 3: 予約は注文源（`IWorkingEntryOrderSource`）が「承認行がまだ無い承認」として返す

- 注文源は次の和集合を返す。
  - 承認行がある未終端の新規建て（IADR-0346 決定 1。従来どおり）。
  - **承認行が無い**予約のうち、注文アクティビティが終端でないもの。
- 予約の寿命（どう終わるか）は次のとおりである。

| 出来事 | 予約の扱い | 理由 |
| --- | --- | --- |
| `OrderApproved` の射影で承認行が書かれた | 返さない（承認行の側で 1 回だけ数える） | **二重に数えない**。以後の約定・終端は承認行の側の規則（IADR-0346）に従う |
| 審査が拒否した | 書かれない | 枠を使わない |
| 承認行より先に注文アクティビティが終端になった（見送り・取消・失効・ブローカー拒否） | 返さない | 枠を返す（IADR-0346 決定 2・5 と同じ） |
| 発行に失敗して判断が再配送された | 決定 4 で同じ承認を発行し直す。予約は 1 行のまま | 二重に数えない（判断 ID が主キー） |
| 承認の射影が最後まで届かない（`OrderApproved` が error キューへ落ちた等） | 承認時刻の取引日が終わるまで数える | 止める側に倒れる。翌取引日には数えない（IADR-0346 決定 2 の当日の判定と同じ規則） |

- 当日の判定・残数量・金額の換算は従来どおり純関数（`PortfolioProjection.ProjectWorkingEntries`）が行う。予約は約定を持たない（約定は承認行が無いと台帳に入らない）。そのため、予約の残数量は承認数量のままになる。
- 注文源を読むものはすべて自動で予約を含む: 審査の snapshot（保有建玉数・日次発注累計・段階資金）、空売り文脈（1 銘柄の空売り建玉・空売り合計・建玉総額）、新規建ての可否の口（#1113）、サイジングの残枠、画面の状態、判断の入力（`GET /risk-controls/working-entry-orders`）。審査以外は読むだけ（承認しない）なので、直列化の外で読んでよい。
- 同日再エントリーの入力（`SymbolsTradedToday`）には算入しない（IADR-0346 決定 4 と同じ）。

### 決定 4: 承認行が無く予約がある判断の再配送は、再審査せず予約から同じ承認を発行し直す

- 新規建ての審査は、臨界区間の中で次の順に判定する。
  1. 承認行がある → `ApprovedReplay`（IADR-0407。何も発行しない。**変えない**）。
  2. 承認行が無く、予約がある → **`ApprovedRepublish`**（第 4 の形）。再審査せず、予約が持つ承認数量・承認時刻・損切りの実行機構と、判断（Intent・サイクルの起点）から `OrderApproved` を組み直す。
  3. どちらも無い → 通常の審査。承認なら予約を書く。
- ハンドラ（`TradeDecisionMadeHandler`）は `ApprovedRepublish` を受けたら次のように動く。
  - `OrderApproved` を発行する。最初の発行が失敗していれば、これを出さないと発注が永久に出ない。
  - 観測は記録する（DecisionId で冪等。最初の審査が記録の後・発行の前に落ちた場合も埋まる）。
  - 審査メトリクスは刻まない（新しい審査ではない）。
- 最初の発行が届いていた場合の 2 本目は、発注執行が DecisionId で止める（IADR-0057）。台帳・注文アクティビティの射影も DecisionId で冪等である。
- **IADR-0407 との関係**: IADR-0407 は「承認行から `OrderApproved` を組み直して発行し直す」案を、承認時点の損切りの実行機構を台帳が持たないことを理由に棄却した。本決定は**承認行からではなく予約から**組み直す。予約は承認時点の値を持つので、その棄却理由に当たらない（現在の設定で埋めない）。承認行がある場合の決定（再発行しない）は変えない。

### 決定 5: 手仕舞い（Close）は直列化しない・予約しない

- 手仕舞いの審査はロックを取らない（新規建ての審査の待ちで手仕舞いを遅らせない。ADR-0009）。予約も書かない（決済は日次発注累計・段階資金・保有建玉数を増やさない）。
- 承認を出す他の経路（owner の手仕舞い・維持率割れの自動縮小）はどれも決済なので、対象外である。

## 棄却した案

| 案 | 棄却理由 |
| --- | --- |
| 審査の中で承認行（`approved_orders`）を書き、後から来る `AppendApproval` を何もしない操作にする | 承認行は「発行済み」の印である（IADR-0407）。発行の前に書くと、発行の失敗・プロセスの停止の後に再配送が再発行せず、発注が永久に出ない（#1319 の注意 1） |
| 受信を直列にし、承認済みで台帳にまだ無い分をプロセス内に保持して加算する（#1319 の案 B） | プロセスの再起動で保持が消え、複数レプリカでは互いの保持を見ない |
| 行ロック（`SELECT … FOR UPDATE`）で直列化する | 鍵になる単一行が無い（設定の行を流用すると、設定の更新と審査が無関係に待ち合う）。advisory lock は表を持たずに同じ効果を得る |
| SERIALIZABLE 分離レベルで直列化の失敗を再試行する | 審査は外部照会（借株可否）と DB の読み取りを交互に行い、再試行で照会を繰り返す。失敗の再試行を Wolverine の共通再試行に任せると、拒否・承認のメトリクスと観測の記録の順序が崩れる |
| IADR-0346 の棄却案どおり予約を持たない（承認行の到着を待つ） | 承認行は `OrderApproved` の往復の後にしか書けない（認識時レートの解決を審査へ移さない・#1319 の注意 2）。待てば審査がメッセージの往復に依存する |

IADR-0346 は「予約テーブル」案を、状態を 2 か所に持つことと、戻し損ねで恒久の枠漏れになることを理由に棄却していた。本決定の予約は、**承認行が届くまでの間だけ**数える。承認行が届いた後の生死は承認行の側の規則（既存の 2 射影）で毎回導出する。戻し損ねても当日の取引日で消えるので、恒久の枠漏れにはならない。

## 結果

- 定時サイクルの同時到着でも、保有建玉数・日次発注累計・段階資金は、先に承認した分（予約）を含めて判定される。並行に審査しても上限を超える分は拒否される（実 PostgreSQL の並行テスト T-10-2579 で、6 件中 3 件の承認・3 件の `MaxPositionsExceeded`）。
- 判断側（新規建ての可否・サイジング・判断の入力）も、承認直後の予約を見る。
- 承認の発行が失敗しても、再配送で同じ承認が出る（発注が永久に出ない状態にならない）。

## 残余リスク

- **借株可否の照会（空売りの新規建てだけ）がロックの内側で走る。** 照会が打ち切り（5 秒）まで待つと、その間は他の新規建ての審査が待つ。手仕舞いは待たない（決定 5）。空売りは既定で無効であり、照会は空売りの新規建てのときだけ行う。
- **同じ判断の承認が 2 回発行され得る。** 最初の発行が実際には届いていて、承認行の射影の前に判断が再配送された場合である。発注執行の予約（IADR-0057）が 2 本目を止めるので二重発注にはならない。監査台帳には同じ DecisionId の承認が 2 行並び得る（IADR-0407 の残余リスクと同じ形）。
- **承認の射影が最後まで届かない注文は、当日中は枠を食う**（止める側に倒れる。翌取引日には数えない）。IADR-0346 の「終端が届かない注文」と同じ向きである。
- テストの EF InMemory プロバイダでは、直列化はプロセス内のセマフォになり、ロールバックが無い。本番と同じ意味論の検証は実 PostgreSQL の統合テスト（T-10-2579）が担う。統合テストは既定 CI では走らず、日次の `integration.yml` で走る。
- 審査の待ち行列が伸びるのは、新規建ての判断が 1 サイクルに集中するときだけである（1 件の審査は DB の読み取り数回）。待っている間は接続を 1 本ずつ保持する。
