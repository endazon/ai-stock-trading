# IADR-0309: 業務メトリクスの否定形テストは Meter をテストごとに隔離する（検査器は足さない）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

## 起点・関連

- 関連する計画書 ID: なし（テスト基盤の是正。`NFR` 無採番＝工程のメタ作業）
- 起点 issue: [#695](https://github.com/endazon/ai-stock-trading/issues/695)（Integration E2E の失敗）
- 関連する実装仕様書: [20260905_695_meter-capture-test-isolation](../specs/20260905_695_meter-capture-test-isolation.md)
- 関連 IADR: [IADR-0255](IADR-0255_business-metrics-and-dashboards.md)（`MeterCapture` を新設し
  「計器を定義した」と「計器が発火した」を分けた決定。**本 IADR はその否定形の書き方を補う**）、
  [IADR-0307](IADR-0307_end-to-end-latency-instrumentation.md)（#689 の計器。否定形の表明を 2 件持つ）

## コンテキストと課題

`System.Diagnostics.Metrics.Meter` は**プロセス全体で観測される**。`MeterCapture` は Meter 名で
購読するため、**同時に走っている別テストの測定値まで拾う**。

`MeterCapture` のクラスコメントはこの性質を警告し「表明は『含む（Contain）』の形で書け」と定めていた。
🔴 **しかし否定形の表明（「発火しなかった」）は、原理的に『含む』では書けない。** 規約が
否定形の書き方を示していなかったため、**6 箇所の `BeEmpty()` がすべて偽陽性を抱えていた。**

2026-09-04 の Integration E2E（develop `a5613718`）で実際に赤が出た。
`finnhub系ソースが未有効なら銘柄設定があっても見積らない` は
`ast.finnhub.daily_request_estimate` を**自分では 1 度も発火させない**にもかかわらず、
**値 24.0（別テストの発火）**を拾って失敗した。

**赤くなるかどうかは同時に走るテストのタイミング次第**であり、プロジェクト単体では再現しない
（実測: 該当プロジェクト単体で 477 件緑）。**Integration E2E が全プロジェクトを 1 プロセスで
走らせるため混入の確率が上がる**という、環境差で顔を出す種類の欠陥である。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 否定形の表明をやめる | ❌ 「発火しないこと」は**統制の性質そのもの**である（未有効なら見積らない・承認では拒否カウンタが動かない・経過が負なら値を捨てる）。表明をやめると計上点の暴発が検知できない |
| B | テストの並行実行を止める | ❌ アセンブリ全体の並行を切ることになり、**全テストが遅くなる**。混入は「同じ Meter 名を見ている」ことが原因であって並行そのものではない |
| C | 混入し得るタグで絞り込む | ❌ 実際に混入した測定値は `Tags = {empty}` であった。**タグでは分けられない** |
| D | 表明を「他人の発火ぶんを引いた件数」にする | ❌ 引く量が分からない（他人がいくつ発火させるかはタイミング次第）。**テストが不安定なまま複雑になる** |
| **E（採用）** | **否定形の表明だけ Meter をテストごとに隔離する** | ✅ 捕捉の母集合がそのテストの発火だけに閉じる。**本番の挙動は変わらない**（既定引数） |

## 決定

### 決定 1: `BusinessMetrics` に省略可能な `meterName` 引数を足す

```csharp
public BusinessMetrics(string? meterName = null)
{
    _meter = new Meter(meterName ?? BusinessMetricNames.MeterName);
```

**既定は従来と同一**であり、本番コードの呼び出しは 1 か所も変わらない。**テストのためだけに
本番クラスへ引数を足すこと**は一般には避けるべきだが、ここでは代替が無い —— Meter は
`BusinessMetrics` の private フィールドであり、**外から名前を変える手段が他に無い**。
引数には「テストの否定形の表明のためである」ことと**実際に起きた事故**を doc コメントで残した。

### 決定 2: `MeterCapture.NewIsolatedMeterName()` を新設する

一意名の作り方を 1 か所に集める（各テストが `Guid` を書き散らすと、**うっかり同じ名前を配って
隔離が成立しない**形が生まれる）。`[CallerMemberName]` を付け、名前から出所が読めるようにした。

### 決定 3: 隔離するのは**否定形の表明だけ**である

肯定形（`ContainSingle` / `HaveCount` / `Equal` など）は**他人の測定値が混ざっても壊れない**。
むしろ隔離すると「**本番と同じ Meter 名で発火していること**」を表明できなくなり、
IADR-0255 が固定したかった性質（計器が実際に流れる）が薄まる。**一律に隔離しない。**

### 決定 4: 隔離そのものを証明するテストを置く

`隔離した捕捉は既定名の計器の発火を拾わない` を新設した。既定名の `BusinessMetrics` が同じ計器を
発火させても隔離側は 0 件であること、かつ**隔離側の発火はちゃんと見えること**（捕捉が死んでいない
ことの対の肯定形）を固定する。`隔離用のMeter名は呼び出しごとに異なる` も置いた。

🔴 **変異試験で load-bearing を実測した** —— 証明テストの捕捉を既定名へ戻すと
**当該テストが失敗する**（`失敗: 1 / 合格: 0`）。復元して緑を再確認した。

### 決定 5: 検査器は足さない

CLAUDE.md は「検査器・規約の追加は同型の事故が **2 回**起きてから」と定める。**本件は 1 回目**である。
代わりに `MeterCapture` と `BusinessMetrics` の doc コメントへ、書き方と**実際に起きた事故**を書いた。

**2 回目が起きたら**、「既定名の `MeterCapture` に対する `BeEmpty()`」を静的に検知する検査を足す
（`RetrievalSourceVocabularyTests` と同じソースの静的解析で書ける）。**この条件を本 IADR に
書き残すこと自体が、暫定を恒久化させないための担保である。**

## 影響

- **本番の挙動は変わらない**（既定引数。`BusinessMetrics` の本番呼び出しは 1 か所も変更していない）。
- 否定形の表明が**同時に走る他テストの発火で赤くならなくなる**。
- テスト件数: `Shared.Contracts.Tests` 359 → 361（証明 2 件）。他 2 プロジェクトは不変。

## 残余リスク

- **`SumOf(...)` を使う表明は今回触っていない。** 合計は混入で狂い得るが、赤の実測がまだ無いため
  母集合から外した（作業仕様書の除外表に理由を記載）。**赤が出たら #695 へ追記して同じ隔離を適用する。**
- **doc コメントは機械が守らせない。** 決定 5 のとおり、同型 2 回目で検査器へ格上げする。
