# IADR-0326: BFF は上流の 401 を利用者未認証と区別し 502 へ写像する

> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

## 起点・関連

- 関連する計画書 ID（FR/UC/SC/ADR）: FR-17, UC-06, SC-01
- 関連する実装仕様書: `.ai-context/specs/20260910_728_bff-upstream-401-to-502.md`

## コンテキストと課題

`AssumptionsBffEndpoints` / `RiskControlsBffEndpoints` / `MonitorBffEndpoints` の 3 モジュールは
上流サービスへの pass-through プロキシで、上流の HTTP ステータスをそのまま透過する。各モジュールは
BFF 側で `RequireAuthorization()` を掛けており、**利用者の認証は BFF で完了している**。にもかかわらず
上流が 401 を返すケース（認証レルムの不一致など、BFF↔上流間の資格情報・構成不整合）が起き得る。

401 をそのまま透過すると、統合 SPA（MSP 基盤）の `apiFetch` がこれを「セッション失効」と誤認し、
`/bff/auth/login` へ自動遷移する。Keycloak の SSO セッションが有効なままだと即座にログイン画面から
戻り、同じ 401 → 同じ遷移が繰り返される無限ループになる。利用者からは原因が見えず、BFF のログを
読まない限り診断できない。

決めるべきことは「BFF は上流 401 をどう扱うか」である。

## 検討した選択肢

1. **現状維持（透過）**: 実装コストゼロだが、上流の構成不整合が毎回 SPA のログインループとして
   露出し続ける。利用者に誤った原因（自分のセッション切れ）を伝える。
2. **401 を 502 へ写像する（採用）**: 「後段の不整合・不達」を表す既存の 502 fail-safe パターンに
   合流させる。SPA 側は 502 を「セッション失効」として扱わないため自動遷移が起きない。理由コード
   `upstream_unauthenticated` を本文に載せ、診断可能にする。
3. **401 を 403 へ写像する**: 403 は「利用者の権限不足」を意味し、実際の原因（BFF↔上流の構成不整合）
   と異なる誤帰属になる。フロントの存在秘匿ロジック（`RequireRole → NotFound`）とも意味がずれる。
4. **ProxyAsync を共有クラスへ抽出したうえで写像する**: 3 ファイルの重複は解消できるが、新規の
   公開面・DI 登録・名前空間設計が発生し、本 issue の受け入れ基準（401→502 の写像）を超える
   リファクタになる。CLAUDE.md 禁止事項「計画外の過剰な抽象化を行わない」に抵触し得る。

## 決定

**選択肢 2（401→502 へ写像）を、3 ファイルそれぞれの既存 `ProxyAsync` に同一ロジックを追記する
形で採用する**（選択肢 4 の共有抽出は行わない）。

- 上流 401 → BFF は 502、本文 `{ "reason": "upstream_unauthenticated" }`。
- 警告ログ 1 行に上流パスと `WWW-Authenticate` の `error` / `error_description` のみを記録する。
  `Authorization` ヘッダ・トークンは記録しない。
- 上流 403 は変更せず透過する。
- `OpendAuthBffEndpoints` は対象外（上流が認証を持たないサイドカーであり、`ProxyAsync` も
  共有していない）。

## 理由

- **既存の fail-safe パターン（後段不達は 502）に合流させる**のが最小の変更である。SPA 側に
  502 専用の新しい解釈を追加させる必要がなく、既存の「502 は後段の問題」という理解と一致する。
- **403 は意味が違う**ため転用しない。403 は「利用者は認証済みだが権限が無い」であり、今回の
  事象（BFF↔上流の構成不整合）とは原因が異なる。将来 403 の意味を薄めると存在秘匿ロジックの
  安全性が下がる。
- **共有抽出を見送る**のは、3 ファイルの `ProxyAsync` は現状シグネチャ・呼び出し規約が完全に
  同一ではあるが（メソッド判定の違いのみ）、抽出には新しい型・DI 登録・名前空間の意思決定が
  伴い、issue の射程（401→502 の写像）を超える。同型の重複が「2 回目の事故」として観測された
  時点で改めて抽出を検討する（本リポの「検査器・規約の追加は同型事故 2 回から」という運用原則
  に倣う）。
- **ログにトークンを残さない**のは、OpendAuthBffEndpoints の既存方針（検証コード・トークンを
  一切ログへ出さない）と一貫させるため。

## 結果

- 良い影響:
  - 上流の認証構成不整合が SPA のログインループとして露出しなくなる（診断可能な 502 になる）。
  - 既存の 502 fail-safe パターンとの一貫性を保つ。
  - 3 ファイルとも変更が対称的で、レビューコストが低い。
- 悪い影響・トレードオフ:
  - `ProxyAsync` の重複がわずかに増える（3 ファイターン × 401 分岐 1 つ分）。
  - `WWW-Authenticate` を上流が返さない場合、ログの `error`/`error_description` は `(none)` に
    なり診断力が下がる（上流側ログとの突合が必要）。
- フォローアップ:
  - `ProxyAsync` の重複が今後 2 回目の同型変更で問題になれば、共有クラスへの抽出を別 IADR で
    検討する。
  - `OpendAuthBffEndpoints` を将来 `ProxyAsync` 方式へ統合する場合、同じ 401→502 写像を適用する
    かどうかを改めて判断する。
