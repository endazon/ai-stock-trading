# IADR-0215: LLM 用途別割当表を実装側に持ち、基盤が返した実効モデルを検証する

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: 実装エージェント（w1b）／#335

## 起点・関連

- 関連する計画書 ID: FR-04・FR-06 / ADR-0011（ピン留め）・ADR-0014（用途別割当）・ADR-0015（月報 ZDR）・ADR-0017（フォールバック方針）
- 関連する実装仕様書: [20260828 作業仕様書](../specs/20260828_335_347_llm-allocation-and-cost-governance.md)

## コンテキストと課題

計画は用途別の割当モデルとフォールバック順序を確定させた（ADR-0014 §決定1 の 2026-08-01 改訂表・ADR-0015・ADR-0017 決定1）。
一方 01_architecture-overview は「**層別のピン留めは基盤 LLM ゲートウェイの用途別ルーティング（`Llm:Routing:PurposeModels`）を
層別に拡張して行う。取引判断サービス側で直接モデル ID を指定する経路は採らない**」（利用者裁定）と定めている。

つまり**モデルを選ぶ権限は基盤にあり、実装側はモデル ID を要求しない**。ではモデルの割当が実際に効いているかを
どう確かめるのか、が本 ADR の問いである。着手前の実測で次が分かった。

1. **AST 側に割当表は存在しない。** purpose 文字列を送るだけで、応答の `Model` は費用の単価解決にしか使っていない
   （報告書側は受け取りながら捨てていた）。
2. **基盤側の `PurposeFallbackModels` に `report-monthly` / `report-weekly` / `report-daily` / `trade-decision` の鎖は無い**
   （実測。登録済みは `analysis` / `diagram-coding` / `default` / `rag-answer` の 4 件）。
3. 基盤の `LlmRouter` は**用途エントリが未登録・ZDR 除外・提供終了のいずれでも、例外もログも出さずに `DefaultModel` へ落ちる**
   （platform IADR-0102 が「無音失効」と呼ぶ罠）。

3 が本質である。**呼び出し側に検知の仕組みが無ければ、ADR-0014 §決定3 が実弾解禁の条件に掲げた
「検証したモデルと本番モデルの一致」は成立しない** —— 割当が失効しても、システムは何ごともなく応答を返し続ける。

## 検討した選択肢

| # | 案 | 割当の失効を検知できるか | 計画との整合 |
| --- | --- | --- | --- |
| 1 | 何も持たない（現状。purpose を送るだけ） | できない。基盤の構成ドリフトが無音のまま通る | ADR-0014 §決定3 が空洞化する |
| 2 | AST がモデル ID を要求に載せる（`Model` を明示指定） | 要求は固定できるが、越境ルーティングで別モデルへ着地する余地は残る | 🔴 **01_architecture-overview の裁定に反する**（「直接モデル ID を指定する経路は採らない」） |
| 3 | **AST は用途だけを送り、応答の実効モデルを割当表と突き合わせる** | できる。落下は「割当表に無いモデル」として現れる | 整合する（要求はモデル ID を持たない） |

## 決定

**選択肢 3 を採る。** `AiStockTrading.Shared.Contracts.Llm.LlmAssignments` に用途別割当表を置き、
**期待値の単一情報源**とする。表は基盤の解決を置き換えず、**基盤が返した実効モデルを検証する**ためだけに使う。

### 決定 1: 表の内容は計画の確定値をそのまま持つ

| 用途 | 第 1 候補（ピン） | 第 2 候補以降 | フォールバック |
| --- | --- | --- | --- |
| `trade-decision` | `claude-sonnet-5` | （なし） | **禁止** |
| `trade-decision-screening` | `claude-haiku-4-5` | （なし） | **禁止** |
| `report-monthly` | `claude-opus-5` | `claude-sonnet-5` | 許可 |
| `report-weekly` | `claude-opus-5` | `claude-sonnet-5` | 許可 |
| `report-daily` | `claude-sonnet-5` | `claude-haiku-4-5` | 許可 |

### 決定 2: 「鎖が空」と「フォールバック禁止」を型で区別する

`LlmAssignment.FallbackAllowed` を持つ。**空の鎖だけでは「たまたま空」と「禁止」を区別できず、
後から鎖を足す変更が統制の逸脱であることに気づけない。** ADR-0017 決定2 は禁止を明文で置いており、
実装もそれを表現できる形にする。

### 決定 3: 禁止モデルは表の外に別枠で持つ

`claude-fable-5` は ADR-0015 / ADR-0017 決定1 により本システムで使用しない。表に「載っていない」だけでは
「未知のモデル」と区別できないため、`ForbiddenModels` として明示し、評価結果も `Forbidden` と `Unassigned` に分ける。
**「未知だった」と「使わないと決めていた」は別の運用事実**であり、通知の読み手が取るべき対応も違う。

### 決定 4: スナップショットテストの期待値は表から組み立てない

`LlmAssignmentsTests` の期待値は**計画の条文からリテラルで書き写す**。表から組み立てるとトートロジーになり、
値が変わっても緑のまま通る（本 ADR がやろうとしていることの全部が無意味になる）。

## 理由

- 計画は「**明示エントリが無いと基盤の既定モデル改定で無音に失効する**」（ADR-0015 §決定）ことを繰り返し警告している。
  基盤側にエントリを置くのは基盤の責務だが、**置かれているかを確かめるのは呼び出し側にしかできない**。
- 表を持つこと自体は「二重定義」に見えるが、役割が違う —— 基盤の表は**解決**、AST の表は**期待**である。
  期待を持たない検証は成立しない。
- ADR-0017 決定4 が求める可視化 3 経路（報告書メタ・警告通知・月報集計）は、いずれも
  「割当どおりだったか」の判定を前提とする。本表がその判定の唯一の根拠になる。

## 結果

- 良い影響: 基盤の構成ドリフト（用途未登録・ZDR 除外・提供終了）が**その場で観測可能**になる。
  取引判断では見送りとして、報告書ではメタ情報と警告として現れる。
- 悪い影響・トレードオフ:
  - **計画が割当を改定したら本表も直す必要がある**（追随は人手）。ただし追随漏れは
    「実効モデルが表に無い」として**赤くなる形**で現れるため、黙って失効はしない。
  - 基盤が正しく割当を持っていても、AST の表が古いと**正常な応答を拒否し得る**（取引判断では見送りになる）。
    これは意図した倒し方である —— ADR-0017 決定2 が「判断できないので見送る」を正常な結果と定めている。
- フォローアップ:
  - **基盤に `report-*` / `trade-decision-screening` の鎖・エントリが無い**（実測）。本リポからは直せないため
    環流候補として作業仕様書へ記録した。配備までは AST 側の検証が「割当が効いていない」ことを顕在化させる。
