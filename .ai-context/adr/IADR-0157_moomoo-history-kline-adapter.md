## コンテキストと課題

[IADR-0156](./IADR-0156_us-ohlc-history-source-absence.md)（2026-08-06・PR [#415](https://github.com/endazon/ai-stock-trading/pull/415)）は
「**米国株日足 OHLC の履歴源が無く、Stage 0 は一度も発火し得ない**」ことを記録し、
**moomoo の採用には ADR-0023 の改定裁定が要る**として実装を見送った（同 決定6）。
その裁定が**同日中に下りた**。

> **ADR-0023 決定5（2026-08-06 追加・利用者裁定・環流 planning#205）**
> 米国株の日足 OHLC 履歴源は **moomoo OpenAPI の履歴 K 線**（`QotRequestHistoryKL`・`KLType_Day`・
> `RehabType_Forward`）とする。1 リクエスト 1,000 件上限・`NextReqKey` でページング。**追加費用なし**。
> Stooq の扱い（決定1）は変更しない。単一障害点の集中は**許容する**。

**したがって IADR-0156 決定6 の前提（裁定が無い）は消滅した。** アダプタを実装する。

### ただし決定5 は「実装側で確認を要する 2 点」を**本決定の前提**とした

ADR-0023 決定5 の原文は明確である——「**本決定の前提であり、確認するまで本番のバックテストへ流さない**」。

| # | 確認事項 | 未了である理由 |
| --- | --- | --- |
| 1 | **取得枠の単位と回復周期。** `remainQuota: 300` が銘柄数かリクエスト数か分からない（PoC は 2 リクエストを投げたが `usedQuota` は 0 のままだった）。**多数銘柄を遡ると枠を使い切る可能性がある。** 枠が銘柄数単位ならバックテスト対象銘柄数の上限が制約になる | **実 OpenD でしか観測できない。** 本実装環境に OpenD は無い |
| 2 | **前復権（`RehabType_Forward`）の調整方式が ADR-0016 決定14 の費用モデル（借株料・配当相当額）と整合するか。** 復権方式と配当の扱いが**二重計上や欠落**を起こさないか | 実データで確認する必要がある。復権後の系列と配当の扱いは提供側の実装に依存する |

**これが本 IADR の中心的な緊張である。** 「採用された ＝ 使ってよい」ではない。
実装が入ることで「動くのだから流してよい」と読まれる経路が新たに生まれる。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | アダプタを実装し、**既定 provider を `moomoo` にする** | **棄却** |
| B | 未確認 2 点が済むまで**実装もしない**（IADR-0156 の状態を維持） | **棄却** |
| C | アダプタを実装し、**既定は `none` のまま**・明示構成でのみ使う・未確認 2 点を実行時に必ず見える場所へ残す | **採用** |
| D | C に加え、確認済みを宣言する**第 2 の構成フラグ**（`Acknowledged=true` 等）を要求する | **棄却** |

### A（既定を moomoo にする）の棄却理由

**決定5 の明文（「確認するまで本番のバックテストへ流さない」）に反する。** 加えて、既定を実データ源にすると
**構成していない環境が起動しただけで実 OpenD を叩き始める**。本リポジトリの過去データ源は
[IADR-0105](./IADR-0105_backtest-historical-bar-source.md) 決定2 以来「**外部接続は opt-in**」であり、
その規律は履歴源が確定したことと無関係に維持すべきである（Stooq が確定していた時期も既定は `none` だった）。

### B（実装もしない）の棄却理由

**裁定は下りている。** 実装を止める根拠は「計画の決定が無い」ことだったが、それは消滅した。
未確認 2 点は**流してよいかの前提**であって、**書いてよいかの前提ではない**。むしろ実装が無ければ
枠の消費も復権後の系列も観測できず、**確認そのものが永久に始まらない**（確認は実装したアダプタで行う）。

### D（確認済みフラグを要求する）の棄却理由

**計画が求めていない構成項目を発明することになる。** 「確認したか」は人間の判断であり、
フラグはそれを機械が検証したかのように見せる（自己申告を統制と誤認させる）。
本リポジトリは既に「明示構成でのみ有効」という opt-in を持っており、**閂を二重にしても
確認していない人が両方立てるだけ**である。**残すべきは閂ではなく、構成した人が必ず読む警告である**。

## 決定

**案 C を採る。**

### 決定1: `MoomooHistoricalBarSource` を実装する（ADR-0023 決定5 に一致させる）

| 項目 | 値 | 落とすと起きること |
| --- | --- | --- |
| K 線種別 | `KLType_Day` | 日足以外の系列でバックテストが走る |
| 復権 | **`RehabType_Forward`（前復権）** | **株式分割を跨いで価格が不連続になり、結果が壊れる** |
| 1 リクエスト上限 | **1,000 件**（`MaxAckKLNum`） | — |
| 継続 | **`NextReqKey` が返る限り繰り返す** | **長期間の履歴が黙って切り詰められ、最大 DD・ウォークフォワードの判定が歪む** |
| 市場 | 米国株のみ（`QotMarket_US_Security`） | 決定5 が定めたのは米国株の履歴源である。日本株は写像せず**欠測**として残す |
| 期間外のバー | `[from, to]` で濾す | データ源の揺れを素通しさせる（Stooq 実装と同方針） |
| 失敗・写像不能 | **銘柄ごとの欠測**（`HistoricalBarGap`）として残し他銘柄は続行 | 欠けた検証を合格材料にしてしまう |
| ページング途中の失敗 | **その銘柄のバーを 1 本も採らない** | 半端な履歴で Stage 0 を合格させ得る |
| レート自制 | `IRateLimiter`（既定 30 回/分・0 以下は 1 回/分へクランプ） | [IADR-0064](./IADR-0064_official-source-connectors.md)「送信前に自制する」に反する |

**層の分け方**: 「ページング」「前復権の指定」「1,000 件」という**壊れると黙って結果が歪む判断**は、
SDK 非依存の `MoomooHistoricalBarSource` に置き、実 OpenD 無しで単体検証できるようにした。
SDK（protobuf）依存は `MMApiMoomooHistoryKLineClient` の 1 クラスに閉じる（発注側 `MMApiMoomooTradeClient` と同型）。
SDK 側へ置いた値（`RehabType_Forward`＝1・`KLType_Day`＝2・`QotMarket_US_Security`＝11・OHLCV のフィールドビット）は
**protobuf 定義そのもの**であり、写像関数として切り出して単体テストで固定した。

**取得枠の照会（`RequestHistoryKLQuota`）は実装していない。** 枠の単位・回復周期の確認は実 OpenD を要する
未了の作業であり、推測で機構を足さない。

### 決定2: 既定は `none` のまま。provider 選択の **allow-list 構造を崩さない**

```
configured switch
{
    "stooq"  when ベース URL が正当      => stooq,
    "moomoo" when OpenD の接続先が正当   => moomoo,
    _                                     => none,   // 未知の provider は実アダプタへ落ちない
}
```

- **既定・空・`none`・未知の値・構成不備はすべて no-op**（`BarDataOptions.Provider` の既定値は変更していない）。
- **実効 provider が `moomoo` なのに OpenD 接続（`IMoomooHistoryKLineClient`）が未提供なら停止する。**
  これは構成不備ではなく**配線の誤り**であり、黙って no-op へ倒すと実効構成の自己申告が `moomoo` を
  示したまま 1 本もバーを取らない（[IADR-0105](./IADR-0105_backtest-historical-bar-source.md) 決定5.1
  「自己申告と実際の選択は一致する」が破れる）。`BrokerFactory` の moomoo 未提供と同じ扱いである。
- **OpenD への接続は `provider=moomoo` のときだけ作る**（composition root で条件付き登録）。
  それ以外の構成では TCP 接続を 1 本も張らない。

### 決定3: 未確認 2 点は「**構成した人が実行時に必ず目にする場所**」へ残す

**コメントと仕様書だけでは、構成した人が読まなければ効かない。** 4 か所に同じ 2 点を置く。

| 場所 | 形 | 誰が見るか |
| --- | --- | --- |
| `MoomooHistoricalBarSource.LoadBarsAsync` | **取得のたびに警告ログ**（テストで固定） | 実際に流した人 |
| `MoomooBarDataOptions` / アダプタのヘッダコメント・XML doc | 文面 | 構成を書く人・コードを読む人 |
| 本 IADR | 決定 | 判断を追う人 |
| [docs/blocked-tasks.md](../../docs/blocked-tasks.md) A-3 | 「実機確認が要る」項目として**解消済みにしない** | 残作業を追う人 |

**「実装したから使える」と読める記述を作らないこと。** 実装の存在と「流してよいか」は別である。

### 決定4: 現況の 4 点を書き換える（[IADR-0156](./IADR-0156_us-ohlc-history-source-absence.md) 決定2 の改訂）

IADR-0156 決定2 の 4 点のうち **3 と 4 が変わった**。以後は次の 4 点を**同時に**書く。

| # | 新しい現況 |
| --- | --- |
| 1 | **Stooq は取得不能である**（回避実装は禁止・ADR-0023 決定1。決定5 でも変わらない）。候補からは削除しない |
| 2 | **ADR-0023 決定5 で moomoo が採用され、本リポジトリにアダプタがある**（追加費用なし） |
| 3 | **ただし決定5 は「実装側で確認を要する 2 点」を本決定の前提とし、確認するまで本番のバックテストへ流さないと定めた。** いずれも実 OpenD を要して**未了**である |
| 4 | したがって **既定は `none` のままであり、Stage 0 の合格判定はまだ発火しない。** 発火させるには moomoo を明示的に構成する必要があり、それは 3 の確認が済んでから行う |

**落としてはならない理由**（それぞれ、落とすと生じる誤読）。

| 落とす点 | 生じる誤読 |
| --- | --- |
| 1 | 「設定すれば Stooq が使える」。回避実装に手を出す動機にもなる |
| 2 | **「使える履歴源が無い」＝裁定と実装の否定**（IADR-0156 時点の記述をそのまま残すとこうなる） |
| 3 | **「moomoo で解決した」＝決定5 の明文の前提の消失。** 未確認のまま本番のバックテストへ流す経路そのもの |
| 4 | 「Stage 0 はもう動く」。既定は `none` であり、動かすには明示構成と確認が要る |

### 決定5: PR [#415](https://github.com/endazon/ai-stock-trading/pull/415) が置いた関門テストは**書き換える**（削除しない）

PR #415 は `未採用の代替源moomooを指定してもno_opへ倒れる_ADR0023の改定裁定待ち` を
「**採用が裁定された日にわざと赤くなり、記録の追随を強制する関門**」として置いた（IADR-0156 決定4）。

**関門は設計どおり発火した。** 本 PR で `provider_moomoo_の明示指定で履歴K線アダプタを組み立てる_ADR0023決定5` へ
書き換え、**同じ PR で IADR・機能/テスト仕様書・`blocked-tasks`・環流記録を追随させた**。
これは**関門が意図どおり働いた記録**であり、削除ではない。**次に同種の関門を置くときの先例とする。**

なお、関門が守っていた「**既定が安全側であること**」は
`構成を何も与えなければ実効providerはnone_既定で外部へ接続しない` が引き続き固定する（変異検査で確認済み）。

### 決定6: 構成不備は**起動時に落とす**。そのために `Program.cs` で**明示的に強制解決する**（2026-08-06 追加）

[IADR-0060](./IADR-0060_opend-production-cutover-gates.md) 決定5 は「**Secret のマウント漏れは起動時に落とす**」と定めている。
発注経路（`MMApiMoomooTradeClient`）はコンストラクタで `MoomooPreflight.Validate` を呼び、これを満たしている。
履歴経路は満たしていなかった——`File.ReadAllText` を無防備に呼ぶだけで、鍵の不在は**初回の履歴取得まで
表面化せず**、しかも素の `FileNotFoundException` として出るため「なぜ落ちたか」が読み取れなかった。

そこで `MoomooBarDataPreflight` を新設した（`MoomooPreflight` の実体を共有しないのは**サービス境界を
跨ぐため**である。横断参照はしない）。**鍵パスが未設定であることは正当な構成なので落とさない**——
相場（Qot）系は暗号化必須ではない。落とすのは「**設定されているのにファイルが無い**」場合だけである。

#### コンストラクタへ置くだけでは「起動時」にならなかった（本決定の核心）

**最初の是正（`8451255`）は不十分だった。** コンストラクタに検査を置き、コミットメッセージにも
「起動時に落とす」と書いたが、**その主張は成り立っていなかった。**

- `AddSingleton<T>(factory)` で登録したシングルトンは**遅延生成**であり、組み込み DI は
  `builder.Build()` の時点では構築しない。
- 発注経路は `AddHostedService<BrokerAvailabilityProbeService>` → `IBrokerAvailabilityProbe` →
  `IBrokerAdapter` → `IMoomooTradeClient` の連鎖により、ホスト起動時（hosted service の `StartAsync`）に
  DI がコンストラクタを**強制的に呼ぶ**。だから本当に起動時へ落ちる。
- **BacktestService には対応する eager な消費者が無い。** 本番戦略（`IBacktestStrategy` 実装）が
  未実装で、`IHistoricalBarSource` を解決する実消費者すら存在しない。

結果として、鍵のマウントを誤っても**プロセスは正常に起動し続け、失敗は初回のバー取得まで顕在化しない**。
**例外の種類と文言は改善されたが、是正しようとした「表面化のタイミング」という核心の性質は
変わっていなかった。** 検査を足したことで「起動時に落ちる」と読める記述だけが増え、実態が伴わない
状態を作っていた——**本リポジトリが繰り返し潰してきた「実装したが効いていない」の一例である。**

#### 採った形

`Program.cs` が `builder.Build()` の**直後**に `IMoomooHistoryKLineClient` を明示的に強制解決する
（`provider=moomoo` のときだけ）。**通常の遅延 DI から外れる非定型な記述であり、理由をコード上にも残した。**

- **接続は張らない。** `EnsureConnectedAsync` は初回要求まで遅延する。ここで走るのは構成の検査だけである。
- **`provider` 未指定なら moomoo の構成を一切見ない。** 見てしまうと、moomoo を使わない環境が
  moomoo の構成不備で起動できなくなる（否定形としてテストで固定した）。

#### 検証で守ること

**「例外が出ること」ではなく「ホストの起動そのものが失敗すること」を検証する**
（`BacktestWorkerStartupPreflightTests`。`act = () => _ = factory.Services`）。
前者だけを検証すると、コンストラクタを直接呼ぶ単体テストは緑になる一方で**起動時には発火しない**という
今回の欠陥をそのまま見逃す。強制解決を外す変異で当該テストが落ちることを実測した。

- `IsUsableOpenD`（Host / Port のみ）と `MoomooBarDataPreflight`（RSA パスも見る）の**役割は別である**——
  前者は provider 選択（allow-list）、後者は選択後の構成妥当性。混同しないこと。

## 理由

- **裁定は下りたが、決定5 の前提は下りていない。** 「採用」と「流してよい」を同じものとして扱うと、
  未確認の取得枠でバックテストを回し（枠切れで銘柄が欠けた検証を合格させ）、
  復権と配当の二重計上を含んだ成績で Stage 1 へ昇格させ得る。**どちらも静かに間違う種類の失敗である。**
- **既定を変えないことが最も強い安全策である。** 警告は読まれないことがあるが、既定 `none` は
  「構成しない限り何も起きない」を機械的に保証する。
- **実装しないという選択は、確認そのものを永久に止める。** 枠の消費も復権後の系列も、
  アダプタで実際に取得して初めて観測できる。

## 結果

- 良い影響:
  - **FR-15 のバックテストに流せるデータ源が初めて実装として存在する**（ADR-0023 決定5 への追随完了）。
  - 未確認 2 点が**実行時のログ**に出るため、「知らずに流した」経路が塞がる。
  - allow-list 構造が維持され、綴り誤り 1 つで意図しないデータ源が実接続を始めることはない。
- 悪い影響 / トレードオフ:
  - **未確認 2 点は解けていない。** 本 IADR は「実装したが既定では使わない」状態を作るだけである。
  - moomoo への集中がさらに進む（履歴・時価・発注が同一ベンダ）。**ADR-0023 決定5 が明示的に許容した**
    （履歴 OHLC は停止しても取引が止まらないため障害の性質が異なる。二重化は別要求）。
  - `BacktestService.Infrastructure` が moomoo SDK に依存する（`MMSPI_Qot` の 133 コールバックの
    no-op 実装を抱える）。SDK の要求であり選択ではない。
- **残余リスク（明記）**:
  1. **実 OpenD に対する疎通は一度も検証していない。** protobuf の組み立て（`QotRequestHistoryKL` の
     ビルダ・`NextReqKey` の往復・`KLine.Time` の実書式）は**本実装環境では確認できない**。
     PoC は Python 相当の probe で成立を確認しており、本アダプタは**その手順を C# SDK で書き直したもの**である。
     **最初に実 OpenD へ繋ぐ人が疎通を確認すること**（`docs/blocked-tasks.md` A-3）。
  2. **`KLine.Time` の書式**は日足で `"yyyy-MM-dd"` と仮定した（時刻付きも受ける）。
     解釈できない行は**採らない**（架空の日付のバーを作らない）ため、書式が違えば
     「0 件で欠測」に倒れる＝安全側だが、**原因が分かりにくい**。
  3. **取得枠を使い切ったときの OpenD の応答**（非成功か、空応答か）を知らない。
     非成功なら欠測として記録されるが、**空応答なら「データなし」と区別できない**。
  4. **1 リクエストあたりの上限 1,000 件は決定5 の記述に従った定数である。** 提供側が変えれば
     過大要求になるが、その場合も応答は上限で切られるだけで**ページングが吸収する**。
  5. 決定5 の未確認 2 点が**「確認した」と記録される仕組みは無い**。確認の完了は人間が
     `blocked-tasks` A-3 と本 IADR を更新することに依存する。
