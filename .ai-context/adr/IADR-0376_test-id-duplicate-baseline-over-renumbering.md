# IADR-0376: テスト ID の既存の重複は改番せず baseline へ記録し、新規の衝突だけを機械で止める

- 状態: Accepted
- 日付: 2026-09-23
- 決定者: claude (Claude Code)

## 起点・関連

- 関連する計画書 ID: FR-10（リスク統制）・FR-15（バックテスト）のテスト仕様書。要求そのものは変えない
- 関連する実装仕様書: `.ai-context/specs/20260923_887_test-id-duplicate-numbering.md`
- 起点 issue: #887（PR #883 のフェーズ末監査で検出・射程外として分離）

## コンテキストと課題

`docs/tests/*.md` は **テスト ID（`T-<機能要求番号>-<連番>`）採番の単一情報源**である
（新しいテストを足す人が「既存の最大値」を測る先）。ここに**重複採番**があると、
**採番の衝突を検知できない**。

### 自分で引き直した母集合（2026-09-23 / `origin/develop` = `03737bd3`）

#887 のコメントは「件数は数え方に依存するので、是正する人は自分で引き直すこと」と明示している。

| 値 | issue 起票時（`be97cf2b`） | 本作業の実測（`03737bd3`） |
| --- | --- | --- |
| 走査対象 | `FR-10_risk-controls-tests.md` のみ | **`docs/tests/*.md` 全件** |
| 重複 ID | 20 件 | **24 件**（FR-10 が 21 件・**FR-15 が 3 件**） |
| 差分の中身 | — | `T-10-410`（起票後に develop で生じた）／`T-15-69`〜`71`（issue の射程外だった） |

**「FR-10 だけの問題」ではなかった。** 規則 9（誤りの側の文字列で全文書を走査してから挙げる）に
従って `docs/tests/` 全件を走査したことで出てきた差である。

### 何を「採番」と数えるかを先に決める必要があった

実データには 3 つの形が在る。

| 種別 | 形 | 実例 |
| --- | --- | --- |
| 採番行 | 行頭セルが ID そのもの | `\| T-10-450 \|` / `\| **T-10-450** \|` |
| 枝番 | 行頭セルが ID ＋ 英小文字 1 文字 | `\| T-15-40b \|`（`T-15-40` の枝。**別の採番**） |
| 参照行 | 行頭セルが ID ＋ 全角括弧の注記 | `\| T-10-127（否定形） \|`（**同じテストの別観点**） |

🔴 #887 のコメントが指摘した「厳格 20 件 / 緩い 23 件」の差は、**参照行を数えるかどうか**で生じていた。
参照行を採番として数えて別番号を振ると、**1 つのテストが 2 つの ID を持つ**ことになる。

### 採番空間はファイルを横断する

`T-10-…` は `FR-10_risk-controls-tests.md`（127〜621）と `FR-10_risk-guard-core-tests.md`（01〜21 / 70〜95）の
**2 ファイルに跨って**採番されている（両者の衝突は現時点で 0 件）。**1 ファイルだけを見て最大値を測ると衝突する。**

## 検討した選択肢

| # | 選択肢 | 評価 |
| --- | --- | --- |
| 1 | **後から足した側を最大値＋1 へ改番する**（#887 の「やること（案）」） | **採らない**（下記の理由 1〜3） |
| 2 | **既存の重複は改番せず baseline へ記録し、新規の衝突だけを止める** | **採用**。既存 ID の意味を 1 件も変えずに、目的（衝突の検知）を満たす |
| 3 | 機械検査を置かず記録に留める（1 回目として） | **採らない。** 採番帯が 4 か所で衝突しており、運用標準の「同型 2 回」は既に満たす |
| 4 | 別ファイルの採番台帳（連番の払い出し簿）を新設する | **採らない。** 実物（テスト仕様書）と台帳の 2 か所になり、必ず片方が古くなる |

## 決定

**選択肢 2 を採る。**

- **決定 1**: **既存の重複 ID を 1 件も改番しない。** 24 件を
  `scripts/test-id-duplicate-baseline.json` へ「ID・在り処のファイル・件数・**なぜ改番しないか**」つきで記録する。
- **決定 2**: `scripts/check-test-traceability.js` へ検査 4（T2）を足す。
  ①baseline に無い重複 → fail ②baseline に在るがもう重複していない → fail（**ラチェット**。解消したら消す）
  ③baseline と在り処・件数が食い違う → fail ④参照行が指す ID がどこにも採番されていない → fail
  ⑤採番行を 1 件も走査できない → fail（**0 件走査で緑を返さない**）。
- **決定 3**: 検査器は**機能要求ごとの採番の最大値を毎回出力する**。これが「次の採番者が読む単一情報源」である。
- **決定 4**: 採番規約（採番行・枝番・参照行の区別／ファイル横断の採番空間／再利用・改番の禁止／
  並行レーンでの帯の確保）を `docs/tests/README.md` に置く。**確保中の帯は書かない**（書いた瞬間から腐る）。

## 理由

1. **改番はサービスコードの書き換えを要求する。** 外部参照を走査すると `T-10-410` は
   **9 ファイル 37 箇所**、`T-10-450` は 5 ファイル 15 箇所、`T-10-451` は 5 ファイル 9 箇所が
   `backend/**/Tests/*.cs` と `.ai-context/specs/` に在る。本件は文書・検査器の作業であり、
   サービスコードへ波及させる射程を持たない。
2. **どちらの出現を指しているかが外部参照からは決まらない。** `T-10-197` は
   `.ai-context/adr/IADR-0174`（1 つ目＝FX 鮮度の警告域）と
   `MaintenanceMarginReductionServiceTests.cs`（2 つ目＝維持率の縮小）から**両方**参照されている。
   **どちらを改番しても、残った側の参照が別のテストを指す。**
3. **`.ai-context/` は凍結記録であり、本文を後から書き換えない。** 改番の追随ができない。
4. **本リポジトリは同じ判断を既に IADR 採番で下している**（IADR-0280。繰り下げのコストが参照数に
   比例して肥大化するため「欠番は許す・再利用禁止・改番しない」へ改定した）。**思想を揃える。**
5. **並行レーンが採番中の帯がある。** 本作業と同時に `T-10-622..669` を別レーンが確保している。
   改番はその帯と衝突し得る。**本 IADR の決定は新しい番号を 1 件も消費しない。**

## 結果

- 良い影響: **新しい衝突が CI で止まる。** 既存 ID の意味は 1 件も変わらず、
  外部参照（コードのコメント・凍結記録）はすべて有効なまま残る。
  採番の最大値が毎回出力されるので、次の採番者が実物を読み違えない。
- 悪い影響・トレードオフ: **既存の 24 件の重複はそのまま残る。**
  `T-10-450` と書いたコードコメントは、依然として 2 つのテストのどちらかに曖昧である
  —— baseline の `reason` が「どちらが何か」を書くことでしか解けない。
- 残余リスク:
  - **baseline が「とりあえず足して通す」に使われうる。** 新しい重複を記録すれば検査は通る。
    ラチェット（解消したら消す）と `reason` 必須で圧力はかけるが、**機械では意図を判定できない**。
  - **枝番（`T-15-40b`）の運用は規約化していない。** 実在するので採番として数えるが、
    新規に枝番を作ってよいかは決めていない（実害が出たら決める）。
  - 検査は `docs/tests/*.md` の**表の行頭セル**だけを見る。別の書式で ID を振れば母集合から落ちる。
- フォローアップ: 重複した 24 件のうち**外部参照が 0 件のもの**（`T-10-261` / `262` / `263`）は、
  サービスコードを触る別の作業と同時であれば改番できる。**単独では行わない**（改番のたびに
  「どちらの出現か」の判断が要り、間違えると参照が別のテストを指す）。
