# IADR-0202: `traceability.md` は分類 A である（分類表がファイル自身の要求と矛盾していた）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-08-15
- 決定者: Claude Code（[IADR-0200](IADR-0200_cross-repo-ref-notation.md) が残した残余リスクの解消）

## 起点・関連

- 計画書 ID: **NFR**（無採番。工程の統制であり計画側の非機能要件表に当たる番号が無い／環流しない）
- 対象 Issue: [#517](https://github.com/endazon/ai-stock-trading/issues/517)
- 作業仕様書: [20260815_517](../specs/20260815_517_kit-sync-and-exclusion-removal.md)
- 計画側の反映: [planning#342](https://github.com/endazon/project-planning/pull/342)（環流 6 件の裁定・反映）

## コンテキストと課題 — 🔴 **分類が、ファイル自身の要求と食い違っていた**

| 出典 | 何を言っているか | 含意する分類 |
| --- | --- | --- |
| `scripts/kit-sync-classification.json` | 「本リポの中身そのもの（雛形から書き起こした実体、または**置換点を持つ配布物**）。**同期しない**」 | **C** |
| `.claude/rules/traceability.md` の冒頭（**当のファイル自身**） | 「本ファイルはキットの配布物である。直接編集しないこと」「**直接編集するとバイト一致が崩れ**、キットを同期するたびに手動マージが要る」 | **A** |

**C の定義のどちらにも当たらない。**

- **置換点を持たない。** 実測（`grep -n '置換点' .claude/rules/traceability.md` → 2 行）で当たったのは
  `check-cross-repo-refs.js` / `check-plan-id-qualification.js` の置換点を**説明している本文**であり、
  このファイル自身が埋める欄ではない。
- **雛形から書き起こした実体でもない。** 固有規約は companion（`traceability.repo.md`）へ分離済みで、
  **直接編集する必要が構造的に無い**（[IADR-0200](IADR-0200_cross-repo-ref-notation.md) で新設した）。

### 🔴 実害 — 「同期しない」ので、誰も気づけなかった

分類 C は「同期しない」であるため、**`check-kit-sync.js` は何も言わない**。
結果として**本リポの写しだけが古いまま固定され、それを検出する機械が無かった。**

**実測で 2 件取りこぼしていた。**

| # | 取りこぼした内容 | 由来 |
| --- | --- | --- |
| 1 | `planning issue #202`（空白区切り）が**本リポの写しにだけ残っていた**。キット側は既に `planning#202` へ是正済み | planning#349（**本リポからの環流**） |
| 2 | 母集合の取り方「**規則 8**」が丸ごと欠けていた（「走査対象に自分の記録が入るときは、記録を書く行為が母集合を動かす」） | planning#350（**本リポからの環流**） |

> 🔴 **どちらも自分が環流したものである。** 計画側は反映したのに、**受け取る側の分類が「同期しない」
> だったため戻ってこなかった。** 環流の往路だけが動き、復路が構造的に塞がっていた。

**これは「緑だが検査されていない」の再発である**——[IADR-0191](IADR-0191_kit-sync-classification.md) が
分類表そのものを作った動機と同型であり、**分類表を作っても、分類を間違えれば同じ穴が開く。**

## 決定

### 決定1: **`.claude/rules/traceability.md` を分類 C → A へ移す**

`check-kit-sync.js` が**バイト一致を機械検査する**ようになる（A 80 → 81 件 / C 17 → 16 件）。
**ファイル自身が要求していることを、機械が見る状態にした。**

分類表の `$comment` に**移した理由を残す**（分類だけ書き換えると、次に見た人が「なぜ A なのか」を
再導出できず、C へ戻しかねない）。

### 決定2: **キット版へ追随する**（規則 8 と `planning#202` の是正が入る）

### 決定3: 🔴 **暫定の検査除外を外す。外す条件が書いてあったから外せた**

[IADR-0200](IADR-0200_cross-repo-ref-notation.md) の残余リスクは
「**planning#349 が是正されたら除外を外すこと（外し忘れると、キットが直った後も検査が 1 件甘いままになる）**」
と明記していた。**条件は満たされた。**

外した箇所は **2 つ**（`traceability.repo.md` の env・`scripts.repo.test.js` の env）。
**`traceability.repo.md` の除外表からは「外した除外」の節へ移し、消さない**——
「なぜ以前は除外されていたのか」が残らないと、次に同じ判断を再現できない（規則 6 と同じ理由）。

> **暫定の除外は、外す条件と一緒に書く。条件を書かない除外は恒久化する。**

### 決定4: **`check-commit-messages.js` の直書きは対象外**

あちらは**パスの除外を持たない**（コミット件名・本文・PR タイトルという**パスの無い面**を検査するため）。
実測で確認した（`grep -n 'EXCLUDE\|pathspec\|:!' scripts/check-commit-messages.js` → **0 件**）。
[IADR-0201](IADR-0201_cross-repo-refs-commit-face.md) 決定2 の直書きは触らない。

### 決定5: 🔴 **追随したフラグは、その場で使う。使わないなら追随していない**

キットが `check-feedback-status-sync.js` へ **`--require-planning`**（参照できないとき skip ではなく fail）
を新設した（planning#343。**本リポの環流が起点**）。**取り込むだけでは fail-open は閉じない。**
`ci.yml` の本検査へ渡し、**同時に「フラグを持たない」と書いていたコメントを訂正した**
（従前は「キット配布物を書き換えず、ジョブ側で populate を明示的に確かめて塞ぐ」＝**唯一の歯止め**と
書いてあった。**もう唯一ではない**）。

**populate の明示確認は残す。** フラグは「参照できない」ことしか見ず、
**`planning/draft/feedback` が無い**という具体的な壊れ方を名指しできない。**二重に塞ぐ。**

> 🔴 **これが「維持されない記述はあるだけ有害」の 3 度目である**
> （[IADR-0198](IADR-0198_fx-expired-visibility.md)・[IADR-0201](IADR-0201_cross-repo-refs-commit-face.md) に続く）。
> **今回は自分が環流した改善が届いたことで、自分の書いたコメントが偽になった。**
> **追随とは、ファイルを揃えることではなく、揃えた結果として偽になる記述を探すことである。**

## 対照実験（実走した実測）— **外してよいことを両方向で示す**

| # | 操作 | 結果 |
| --- | --- | --- |
| A | **同期前**の写し ＋ **除外なし** | 🔴 **違反 1 件**（`traceability.md:153 [空白区切りの修飾] planning issue #202 → planning#202`） |
| B | **同期前**の写し ＋ **除外あり**（従来の状態） | ✅ OK・**292 件**の Markdown |
| C | **同期後**の写し ＋ **除外なし** | ✅ OK・**293 件**の Markdown |

**B → C で走査対象が 292 → 293 に増えている。これが「除外を外したこと」の実測である。**
**A は「外したうえで、もし古いままなら赤くなる」ことの実測である。**

### 変異試験（追加した回帰テストが実際に効くか）

| # | 変異 | 結果 |
| --- | --- | --- |
| 1 | 分類表で `traceability.md` を **A → C へ戻す** | ✅ **赤**（`分類 A に無い`） |
| 2 | `ci.yml` から **`--require-planning` を外す** | ✅ **赤**（`本検査に --require-planning が無い`） |
| 3 | `ci.yml` から **populate 確認を外す** | ✅ **赤**（`populate の確認ステップが無い`） |

> 🔴 **変異 2 の初版テストは、ジョブ内の `echo` 行を実行行として数えていた**
> （`check-feedback-status-sync.js` というファイル名だけで引いたため、
> エラーメッセージ中の同名文字列に当たった）。**`node scripts/…` の形で絞り直した。**
> **規則 2「あり得る形をすべて列挙してから引く」を、テストの側で踏んだ**ものである。

> 🔴 **C だけを見ても意味がない。** 「除外を外しても緑」は、**外れているのかどうかを区別できない**——
> [IADR-0200](IADR-0200_cross-repo-ref-notation.md) の対照実験 2 / 3 が
> 「**緑のまま**（現ツリーには該当が 0 件）」で終わったのと同じ形である。**否定形を必ず取る。**

## 影響

- **良い影響**: 環流の**復路が開いた**。計画側が反映したキット改善が、**機械検査つきで戻ってくる**。
  暫定除外が 1 件減り、`.md` 面の検査が**キット配布物そのものにも効く**ようになった。
- **悪い影響**: キットが違反や表記ゆれを持ち込むと、**本リポの CI が赤くなる**（手元で直せない分類のまま）。
  ただしこれは**設計どおりの痛み**である——**気づけずに古い写しを抱え続けるより良い**、というのが本 ADR の判断である。

## 残余リスク

- 🔴 **キット版 `traceability.md` の「規則 8」が、表の外に落ちている。**
  規則 7 の行との間に**空行がある**ため、GFM は**ヘッダ行を持たない表本体を表として描画しない**——
  **規則 8 だけが素の文字列 `| 8 | … |` として表示される。** 分類 A のため**手元では直さず環流する**。
  **表示は壊れているが内容は届いている**ため、本 PR では取り込みを優先する。
- **分類の誤りを検出する機械は無い。** `check-kit-sync.js` は「分類 A のものがバイト一致か」を見るだけで、
  **「C に置いたものが本当は A ではないか」は見ていない**（見るには各ファイルの意味論を理解する必要がある）。
  🔴 **今回は違反 1 件が偶然この矛盾を暴いた**のであって、**構造的に見つけたのではない。**
  残る C 16 件について同種の取り違えが無いとは言えない。
- **キット追随のたびに手動の突き合わせが要る点は変わらない**（A へ移したのは検出のためであり、
  自動マージが入ったわけではない）。
