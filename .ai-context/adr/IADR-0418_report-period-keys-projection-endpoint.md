# IADR-0418: 入力補完が読む一覧は報告書サービスの専用ルート `GET /reports/period-keys` とし、配備順の窓では 404 のときだけ従来の一覧へ退避する

- 状態: Accepted
- 日付: 2026-09-25
- 決定者: claude（起票 #843 項目 1。利用者レビューは PR で受ける）

## 起点・関連

- 対象 Issue: #843（#841 の監査の非ブロッキング指摘）の項目 1「一覧 API が本文つき全件を返す（最優先）」と、
  項目 6 の受容に付いていた再考の条件（「項目 1 の実装時」）。
- 関連する実装仕様書: [20260925_843_report-period-keys-projection](../specs/20260925_843_report-period-keys-projection.md)
  （前段: [20260925_843_autocomplete-audit-followups](../specs/20260925_843_autocomplete-audit-followups.md) 決定 3 が項目 1 を見送った）
- 関連 IADR: [IADR-0240](IADR-0240_discord-report-review-window-and-idempotent-confirm.md)（決定 4・5・9・11。本 IADR は覆さず補う）

## コンテキストと課題

`/report` の `period` の入力補完（IADR-0240 決定 9）は、報告書サービスの一覧 `GET /reports` を**打鍵ごとに**読む。
この一覧は射影もページングも持たず、**本文（Markdown）を含む全件**を返す（`EfReportStore.List`）。通知サービスが使うのは
会話キーと開始日の 2 項目だけで、残りは読み捨てている。日報が貯まるほど転送と逆シリアル化の量が線形に増え、
補完の時間予算（2.5 秒）に当たって「候補なし」へ倒れる帯が広がる。

前段（PR #975）は「射影・ページングの前例がどのサービスにも無い」として形の決定を見送ったが、実測では
**`/reports` の直下に `/{periodKey}` と並ぶリテラルのルートが既に 3 本ある**（`GET /daily-policy`・`GET /monthly-bootstrap`・
`POST /pnl-summary`）。専用ルートには同じ集約・同じ階層の前例がある。

## 検討した選択肢

1. **専用ルート `GET /reports/period-keys` → `[{periodKey, periodStart}]`**（採用） — 応答の形が固定で、既存の
   `GET /reports` を変えない。リテラル一致が `/{periodKey}` より優先されるのは `/daily-policy` 等と同じ。
2. **`GET /reports?fields=periodKey,periodStart`** — 既存ルートのまま射影できるが、射影の文法（値の検証・応答の型が
   可変になる）を新設することになり、前例が無い。**却下**。
3. **`GET /reports?view=keys&limit=N`（ページングつき）** — 2 と同じく前例が無い。加えて、絞り込み（前方一致 → 部分一致）は
   通知サービス側の `ReportPeriodSuggestions.Filter` が**全キーに対して**行うため、**サーバ側で件数を切ると、打った文字に
   一致する古いキーが候補から消える**。`limit` を入れるなら絞り込みもサーバへ移す必要があり、射程が変わる。**却下**。

配備順（通知サービスだけが新しく、古い報告書サービスに新ルートが無い窓）の扱いは、規則 11 の 3 つの形で比べた
（プローブ: P1＝古い報告書サービスで新ルートが 404、P2＝新しい報告書サービスが正常、P3＝新しい報告書サービスが 500）:

| 形 | P1 | P2 | P3 |
| --- | --- | --- | --- |
| A. 新ルートだけ（退避なし） | ✗ 窓のあいだ補完が黙って候補なし | ✓ | ✓ |
| B. **404 のときだけ従来の一覧へ退避**（採用） | ✓ | ✓ | ✓ 退避せず候補なし |
| C. 失敗なら何でも従来の一覧へ退避 | ✓ | ✓ | ✗ 障害中の報告書サービスへより重い全件照会を重ねる |

A と C は変異で実測した（B の単体試験のうち、A では新ルートが 404 を返す 2 件〔P1 と「退避先も失敗」〕、C では P3 の 3 件が落ちる）。

## 決定

1. **報告書サービスに `GET /reports/period-keys` を足す**（OwnerOnly。`GET /reports` と同じ認可）。応答は
   `[{ "periodKey": string, "periodStart": "YYYY-MM-DD" }]`、並びは開始日の降順・同日は会話キーの降順。
   **本文・要約・状態は載せない**（IADR-0240 決定 4・5 と同じ射影）。`GET /reports` は変えない。
2. **ストアに `ListPeriodKeys()` を足し、EF 実装は SELECT で 2 列だけを射影する**（本文の列を読まない）。
   **ページング・件数上限は入れない**（選択肢 3 の理由）。
3. **通知サービスのアダプタは新ルートを読み、404 のときだけ従来の `GET /reports` へ退避する**（形 B）。
   500・401/403・例外・タイムアウトでは退避しない。退避は補完の時間予算（2.5 秒）の内側で起き、Information ログを 1 行残す。
   応答の受け口（会話キー＋開始日を `JsonElement` で受ける射影）は両ルートで共用する。
4. **項目 6（候補に確定済みも含む）は再考した上で受容を据え置く。** 新しい射影に状態を載せれば「レビュー待ちを先に出す」
   ことはできるが、候補の並び（新しい順）を変えるのは補完の見え方の変更であり、押し出しは観測されていない。状態を載せるなら
   表現非依存の形（IADR-0240 決定 5）も別途決める必要がある。**再考の条件を「押し出しの報告、または報告書の件数が数百件に
   近づいたとき」へ書き直す。**

## 理由

- 補完の負荷の大半は本文の転送であり、2 列の射影でそれが消える。1 行は数十バイトで、PoC 運用の件数（数十〜数百）では
  ページングが無くても補完の予算に比べて無視できる。
- 専用ルートは既存の 3 本と同型で、読み手・検査の双方に新しい規則を持ち込まない。
- 退避を 404 に限るのは、404 が「新ルートが無い」ことだけを意味する（古い報告書サービスでは `/{periodKey}` に当たり、
  会話キー `period-keys` の報告書は存在しない）からである。他の失敗は報告書サービスの状態を表しており、退避しても直らない。

## 結果・残余リスク

- 良い影響: 補完 1 回あたりの転送から本文が消える。配備順の窓でも補完が黙って死なない。
- **会話キー `period-keys` の報告書は 1 件照会（`GET /reports/period-keys`）で取れない**。`daily-policy` 等と同じ性質であり、
  会話キーは `daily-` / `weekly-` / `monthly-` で始まる形で生成されるため実害は無い。
- 退避の分岐は配備が揃えば通らない。**全環境で報告書サービスが本 IADR 以降の版になったら撤去してよい**（撤去しないまま残っても
  P2 の挙動は変わらない）。
- 件数が数千件規模へ増えた場合はページング（と絞り込みのサーバ側への移動）を再検討する（選択肢 3）。
- 実 Discord・実 PostgreSQL での疎通は未検証（`docs/blocked-tasks.md` A-7a の再測定手順 ④ で補完の疎通を測る）。
