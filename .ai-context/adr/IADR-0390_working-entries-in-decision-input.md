# IADR-0390: 判断の入力へ未約定の新規建て注文を第 3 の状態として渡す

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: Accepted
- 日付: 2026-09-24
- 決定者: endazon（[#934](https://github.com/endazon/ai-stock-trading/issues/934)）/ Claude Code（起案）

## 起点・関連

- [#934](https://github.com/endazon/ai-stock-trading/issues/934)（稼働 PoC の実測・2026-09-23 JST）: AAPL の買い判断が 5 分おきに 2 本続き、
  2 本とも根拠に「保有なし」と書いた。2 本目の時点で 1 本目（指値 715 株 @337.63）は**ブローカーに受理済み・未約定**だった。
  結果として AAPL 1,428 株・資金の約 50% が 1 銘柄に集中した。
- [IADR-0346](IADR-0346_count-working-entry-orders-in-risk-limits.md)（#829）: リスク管理は未約定の新規建てを日次枠・段階資金・保有建玉数へ
  算入していた。**統制上限は破れていない。破れているのは判断の前提である。**
- [IADR-0351](IADR-0351_held-position-in-decision-prompt.md)（#854）: 判断プロンプトへ保有状況（保有あり／保有なし／不明）を載せた。
  その「保有」は `GET /risk-controls/open-positions`＝**約定だけ**の射影であり、未約定は見えない。
- [IADR-0358](IADR-0358_skip-open-when-holdings-unknown.md)（#865 / #877）: 実結線のもとで保有が不明なら新規建てを見送る。
- 計画 ADR-0003: 判断入力は「確定済み日報＋保有ポジション＋収集情報＋過去判断の RAG」。「不確実な場合は必ず Hold」。
- 作業仕様書: `.ai-context/specs/20260924_934_working-entries-in-decision-input.md`。

## コンテキスト

判断サービスが見ている保有は約定済みの建玉だけである。指値が板に残っている間（moomoo SIMULATE の指値・S2）、
判断は「保有なし」を前提に同じ銘柄の新規買いを毎サイクル評価し、LLM は同じ根拠で Buy を繰り返す。
リスク管理は同じ未約定を IADR-0346 の `IWorkingEntryOrderSource` で知っているが、**外へ公開する読み取り口が無かった**。

## 決定

### 決定1: データ源はリスク管理の IADR-0346 の未約定ビューを再利用する（新しいストアを作らない）

- 残数量の導出を `PortfolioProjection.ProjectWorkingEntries(fills, now, workingEntries)`（純関数）へ切り出し、
  **統制（`Project`）と判断の入力の両方がこれを呼ぶ**。当日（承認時刻の市場の現地取引日・IADR-0246）かつ
  残数量（承認数量 − 同じ DecisionId の約定累計）> 0 の注文だけを返す。定義を 2 か所に持つと、片方だけ直した時点で
  「統制は数えるが判断は知らない」（本件）が別の形で再発する。
- リスク管理に読み取り口 **`GET /risk-controls/working-entry-orders`**（`OwnerOrService`・読み取り専用・新規テーブル／イベントなし）を足す。
  応答は `WorkingEntryOrderView(DecisionId, Symbol, Market, Side, RemainingQuantity, Price, ApprovedAt)`。
- **`/open-positions` には混ぜない。** 同口は市場監視の損切り検知と報告書が読み、未約定を建玉として混ぜると
  損切り検知が存在しない建玉を見る。

棄却: 発注執行の `executed_orders` / 予約を読む案は、判断サービスからの結線（URL・認可・fail-safe）を新しく作ることになり、
しかも統制（リスク管理）と別の定義の未約定を判断が見ることになる。

### 決定2: 判断側のポートは `IHeldPositionProvider.GetWorkingEntryOrdersAsync` —— null＝不明／空＝無い

- `HttpHeldPositionProvider` は非 2xx・例外・タイムアウト・不正応答（`null`・残数量が正でない行）を **null（不明）** にする。
  一致する行が無ければ `WorkingEntryOrders.None`（無い）。`NoOpHeldPositionProvider` は常に null。
- 判断サービスは保有状況と同じく LLM 呼び出しの前に 1 回引く（fail-safe ラッパで例外は null）。

### 決定3: 未約定は約定済みの保有に混ぜない（別の型・別の行）

`HeldPosition`（数量・平均取得単価・損切りライン）は変えない。未約定は `WorkingEntryOrders`（方向・残数量・承認価格・承認時刻）で運ぶ。
含み損益・平均取得単価・建玉効果（`PositionEffectResolver`）・決済の数量は**約定済みだけ**で決まる。
未約定を建玉効果へ足すと、決済の数量が在庫を超える（IADR-0119 決定1 の「保有全量」が約定していない数量を含む）。

### 決定4: プロンプトは「保有: なし」を出す条件を狭める

| 約定済み | 未約定 | 本判断・一次の保有状況節 |
| --- | --- | --- |
| 0 株 | 無い | 従来どおり `保有: なし` |
| 0 株 | **在る** | `保有: なし` を**出さない**。「約定済みの建玉は 0 株ですが、未約定の新規建て注文があるため『保有なし』ではありません」＋注文ごとの行＋「同じ方向を重ねると約定後に合算される」規則 |
| 0 株 | **不明** | `保有: 不明（…未約定の新規建て注文の有無を取得できませんでした。「保有なし」とは扱いません）`＋「不明なら Hold」 |
| あり | 在る | 約定済みの行は一字も変えず、末尾に未約定の行と規則を足す |
| あり | 不明 | 約定済みの行は残す（手仕舞いの判断材料を消さない）＋「未約定が不明なため買い増し・売り増しは選ばない」 |
| 不明 | — | 従来どおり `保有: 不明`（未約定が在れば行を添える） |

`Build` / `BuildScreening` の `working` 引数は **null＝不明**（既定）。「無い」は `WorkingEntryOrders.None` を明示する
（IADR-0351 決定2 と同じ規律）。`Stage0DecisionRecorder` は `WorkingEntryOrders.None` を明示する（IADR-0351 決定7 と同じ理由）。

### 決定5: 実結線のもとで未約定が不明なら新規建て（Open）を見送る。手仕舞いは止めない

IADR-0358 と同じ形である（`_heldPosition.IsEnabled` かつ未約定が null かつ建玉効果が Open）。プロンプトの「不明なら Hold」は
LLM への依頼であってコードの統制ではない（IADR-0358 の論拠）。決済（Close）の数量は約定済みの保有だけで決まり、
未約定の照会とは独立に引き直される（IADR-0351 決定6）。未結線（NoOp）は「照会していない」であり、従来どおり新規建てを通す。

### 決定6: 未約定が在っても新規建てそのものはコードでは止めない

本件が正すのは判断の**前提**である。同じ銘柄への重ね買いを止める統制（クールダウン等）は #935 で利用者の裁定を待つ。
金額の統制（1 注文上限・日次枠・段階資金）は IADR-0346 の算入が既に担う。

## 原則 A の扱い（「送っていない」「送ったが結果不明」「受理済みで生きている」を混ぜない）

| 状態 | 扱い |
| --- | --- |
| 送っていない（見送り・取消・失効・拒否） | 終端（`TerminalAt` あり）。未約定に**入らない** |
| 送ったが結果が不明（承認済みで `order_activity` の行なし・終端イベント未着） | 未約定に**入る**（IADR-0346 決定1 と同じく生きている側へ倒す） |
| 受理済みで生きている（Accepted / PartiallyFilled） | 未約定に入る |
| 照会できない | **不明**。「無い」と読まない。実結線なら Open を見送る |

🔴 **限界**: `order_activity` は「ブローカーの受理を確認した」ことと「承認済みで結果待ち」を区別する列を持たない
（`RecordPlacement` が承認時点で `Accepted` を書く）。本決定は両者を**同じ第 3 の状態**として扱い、プロンプトでは
「受理済み」と断定せず「発注済み・終端未確認」と書く。どちらも約定し得るため「保有なし」の反証としては十分である。
区別には列の追加（マイグレーション）が要り、本件では行わない。

## 棄却した案

| 案 | 棄却理由 |
| --- | --- |
| 未約定を `HeldPosition.SignedQuantity` へ足す（`/open-positions` に混ぜる） | 含み損益・平均取得単価・決済数量が約定していない数量を含む。市場監視の損切り検知が存在しない建玉を見る |
| 未約定の照会失敗を「無い」に倒す（判断を止めない） | #934 の実測そのものを再現する。原則 A（不明を無いと読まない） |
| 未約定の照会失敗で保有も不明にする（`GetPositionAsync` を null にする） | `GetSignedQuantityAsync` は決済の数量の出所であり、未約定の照会が落ちただけで手仕舞いが止まる（FR-10「手仕舞いは止めない」） |
| 未約定が在れば同じ銘柄の新規建てをコードで止める | 重ね買いの統制は #935（利用者の裁定待ち）。本件の射程は前提の是正 |
| 発注執行の `executed_orders` を読む | 決定1 の棄却理由 |

## 結果

- 良い点: 判断は板に残った指値を知り、「保有なし」を根拠に同じ銘柄を重ねて買うことが前提の誤りとしては起きなくなる。
  統制と判断が同じ定義の未約定を見る。照会が落ちても「無い」とは読まず、新規建てだけが止まる。
- 注意点（残余リスク）:
  - **LLM が未約定を知ったうえで重ねて買うことは止めない**（決定6。#935）。金額の統制だけが上限を守る。
  - 承認→`OrderApproved` の射影はメッセージ経由であり、**承認直後の数秒は未約定として見えない**（IADR-0346 と同じ）。
    判断の周期（5 分）に比べて小さいが、同一サイクル内で同じ銘柄を並行判断すると互いを見ない。
  - 当日の判定は承認時刻の市場の現地取引日である。**前取引日に承認され終端イベントが届かない注文は見えない**
    （moomoo の注文は当日限りであり、IADR-0346 決定2 と同じ規則。統制と判断で見え方を揃えるための選択）。
  - 「受理済み」と「結果待ち」を区別しない（上の限界）。
  - 判断 1 回につきリスク管理への同期照会が 1 本増える（同じ `risk` HttpClient・s2s トークン）。
- 追随: テスト仕様書 FR-10（T-10-712〜T-10-723）。IADR-0351・IADR-0358 に日付つき追記。

## ［2026-09-25 追記 / #943］約定済みの保有（`/open-positions`）にも同じ契約と「不明」を適用する

上の追記 2 と同じ形の欠落が、約定済みの保有を読む `HttpHeldPositionProvider.GetPositionAsync` に残っていた。送り手
`OpenPositionView.Symbol` を `Ticker` へ改名しても TradeDecisionService.Tests 751 件（ほか市場監視 157 件・報告書 1101 件）が
すべて緑のまま、実行時は一致 0 件＝`HeldPosition.None`（保有なし）になり、建玉を持っているのにプロンプトは `保有: なし` と書き、
IADR-0358 の「不明なら新規建てを見送る」も効かなかった。決定そのものは変えていない（決定2 の「不正応答は null」の具体化）。

1. **保有の DTO を全項目 nullable にする。** 銘柄が null／空・市場が無い行が 1 つでもあれば**応答全体を不明**（null）。
   一致行の方向・数量が無い、または数量が正でない（射影は数量 0 の建玉を出さず、数量は常に正）なら**不明**。
   価格 2 項目の欠落は従来どおり価格だけを不明にする。3 状態は **保有あり**（一致行）／**保有なし**（全行が識別でき一致なし）／
   **不明**（照会失敗・不正応答・識別できない行）であり、不明は IADR-0358 の見送りへ流れる。T-10-801。
2. **契約テストは本番の配線で読む。** 送り手の本物の `OpenPositionView`・`SizingContextView` を web 既定で直列化し、
   `RiskManagement:BaseUrl` を与えた本物の Program.cs から解決したアダプタ（"risk" HttpClient の一次ハンドラだけを差し替える）に
   読ませる（T-10-800・T-10-802）。サイジング文脈の既存テストは**受け手自身の型**を直列化しており、送り手の改名を検出できなかった
   （連敗数・DD 比率の改名は 0 に化け、`PositionSizer.GetSizeFactor` の縮小が外れる）。
3. **送り手側で前提を固定する。** 受け手の契約テストはどれも「送り手が web 既定（camelCase・列挙は数値）のまま出している」ことに
   立つ。リスク管理の本物の Program.cs が返す `open-positions`・`sizing-context`・`working-entry-orders` の本文が、応答型を web 既定で
   直列化したものと一致することを T-10-805 で固定した（費用統制・報告書の Program.cs は現に文字列列挙へ変えている）。
4. **同じ応答を読む他サービスにも契約テストを足した。** 市場監視の損切り検知（`HttpPositionStore`。損切り価格の改名は 0 に化け、
   ロングの損切りが発火しない）は T-10-803、日報の建玉（`HttpOpenPositionSource`。銘柄の改名は全行が落ちて「建玉なし」）は
   T-10-804。**両アダプタの実行時の挙動は変えていない**（各経路の縮退の向き——空列・未供給——に合わせた「不明」の設計は追随）。

サービス間の読み取り（他サービスの HTTP 応答を自前の型で読む箇所）の全走査は作業仕様書 `20260925_943_cross-service-read-contracts`
にある。安全に関わる経路で fail-open するもの（保有・サイジング文脈・損切り検知・日報の建玉）は本追記で契約テストを持った。
残り（日報方針・費用統制・監視銘柄・報告書の各照会・通知の操作結果）と、上の 3 アダプタの実行時の堅牢化は追随 issue #957。

［2026-09-25 追記 / PR #959 監査］上の 4 の市場監視の影響は過小に書いていた。`Symbol` の改名では、実運用の市況源（Finnhub）で巡回全体が例外で止まり、**全建玉の損切り検知が止まる**（エラーログのみ・アラート無し）。`StopLossPrice` の改名では含み益のショートがライン 0 で毎巡回誤発火する。本 PR の契約テストで改名は CI で赤になるが、**実行時の堅牢化（#957）がマージされるまで、`OpenPositionView` と市場監視の `HeldPosition` の契約を変える変更を入れてはならない**（2 サービスが異なる版で動く間、損切りが止まり得るため）。
