# IADR-0190: AI レビューの判定の有無をジョブの結論へ結び付ける

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-08-14
- 決定者: Claude Code（PR #489 で 3 回連続の実測を得たため）

## 起点・関連

- 計画書 ID: **NFR**（運用保守。工程の統制であり計画側の非機能要件表に当たる番号が無いため無採番。planning#311 の 2）
- 対象 Issue: [#490](https://github.com/endazon/ai-stock-trading/issues/490)
- 作業仕様書: [20260814_490_review-verdict-gate](../specs/20260814_490_review-verdict-gate.md)
- 発生: PR [#489](https://github.com/endazon/ai-stock-trading/pull/489)
- 既存の安全弁: `scripts/check-permission-denials.js`（[IADR-0170](IADR-0170_backlog-audit-automation.md) 系の規律）

## コンテキストと課題

**同一 PR で 3 回連続、AI レビューが判定（🔴/🟡/🟢）を投稿しなかった。**

| 試行 | 実行時間 | 結論 | 判定 | 形 |
| ---: | --- | --- | --- | --- |
| 1 | 3m55s | **`success`** | **無し** | **A: 待たずにターンを終える** |
| 2 | **20m16s** | `cancelled`（job timeout） | 無し | B: 待って timeout |
| 3 | 11m16s | **`success`** | **無し** | **A** |

3 回とも PR に残ったのは進行中のプレースホルダだけで、1・3 回目には
**「`dotnet test backend/backend.slnx` をバックグラウンドで実行中です。完了後にサマリを投稿します」**
と書かれたまま終わっていた。`claude-code-review.yml` の `timeout-minutes: 20` に対し、
2 回目は 20 分 16 秒でタイムアウトしている。

### 🔴 形 A が危険である

| 形 | 結論 | 実害 |
| --- | --- | --- |
| **A: 待たずに終える** | **`success`** | 🔴 **「レビュー済み・指摘なし」と読まれるが何も判定されていない。マージも止まらない** |
| B: 待って timeout | `cancelled` | マージは止まる（gate としては正しい）が、レビューが完了しない |

**A は本リポジトリが繰り返し扱ってきた「緑だが検査されていない」そのものである。**

> **本 ADR の起点となった PR #489 は、実際にこの形 A の green でマージされた。**
> 自前の検証（CI 24/24 緑・`backend/` 差分 空・build 0/0・test 1798 件・検査器 4 種）があったため
> 内容の risk は低かったが、**レビュー gate は何の signal も出していなかった。**

### 既存の安全弁では捕まらない

`check-permission-denials.js` は「**AI がツールを 1 つも実行できなかった**」形を捕まえる。
本件は**ツールは正常に動いており、最後の投稿だけが無い**。**別の穴である。**

### 🔴 引き金は「コード差分ゼロの PR で全テストスイートを回したこと」である

**#489 は `backend/` の差分が空**の docs のみの PR であった。それでもレビューは
全スイートを実走しようとし、その待ちで詰まった。プロンプトは「可能な限り自分で実走して確認」と
求めるが、**変更範囲を見て絞る指示が無かった。**

## 決定

### 決定1: 判定の有無を**ジョブの結論へ結び付ける**（形 A を緑にしない）

`scripts/check-review-verdict.js` を新設し、`Run Claude Code Review` の後段へ
**`if: always()`** で配線する。実行ログ（`steps.claude.outputs.execution_file`）を読み、
**AI の出力に判定セクションが無ければジョブを落とす。**

- 入力は `check-permission-denials.js` と**同じ実行ログ**であり、`parseEvents` を借りる（2 本セット）。
- **実行ログを読めないときは warn ＋ exit 0**（fail-open）。**その形は既存の検査器が捕まえる**ため、
  二重に落とす必要は無い。

### 決定2: 判定の検出は**見出しの構造**で行い、語の一致に頼らない

**本文の語を素で探すと、レビューが本文中でその語を使った瞬間に誤検出する。**
これは planning#319 知見3 で実証済みの同型のアンチパターンである
（検査器について書いた記録が、語の一致だけで自己発火した）。

**`### 🔴 重大` / `### 🟡 推奨` / `### 🟢 軽微` の見出しを 3 種そろって持つこと**を条件とし、
**1 つでも欠ければ判定と認めない**。**絵文字と語の両方**を要求する
（「重大な問題は無い」という散文で緑にしない）。

### 決定3: プロンプトへ**バックグラウンド実行の禁止**を明記する

「実行制約・最重要」節はサブエージェントの spawn 待ちでの停止を既に禁じていたが、
**バックグラウンドプロセスの待ちは書かれていなかった**。同じ形の停止であるため足す。

- **コマンドをバックグラウンドで起動しない。** 前景で実行し、完了を待ってから次へ進む。
- **サマリの投稿は、どの検証よりも優先される。** 時間が足りなければ待たずに
  **「未検証（理由）」と書いて投稿する。**

### 決定4: プロンプトへ**変更範囲に応じた検証の絞り込み**を明記する

- **`backend/` の差分が空なら `dotnet build` / `dotnet test` を実行しない。**
- **`frontend/` の差分が空なら frontend の検証を実行しない。**
- **実行しなかったことは「実行できなかったこと」節へ理由付きで書く**（黙って省略しない）。
- 差分がある場合も**まず対象プロジェクトだけを絞る**。全スイートは最後の手段である。

### 決定5: kit へ環流する

**同じ穴はキットを配る全リポジトリにある。** 検査器とプロンプトの是正を計画側へ環流する。

### 🔴 決定6: 「判定が無い」と「読めていない」を区別する（初版の欠陥の是正）

**本 ADR の初版は、PR [#491](https://github.com/endazon/ai-stock-trading/pull/491) の初回実行で偽陽性を出した。**

- レビューは**判定を正しく投稿していた**（🔴 0 / 🟡 1 / 🟢 0）。
- それでも `Check review verdict` ステップが**落ちた**。出力は
  **「見つかった見出し: （無し）」** —— つまり**判定が無かったのではなく、こちらが実行ログから
  AI の出力を 1 文字も取り出せていなかった。**
- 初版の `assistantText()` は `assistant` メッセージの `text` ブロックしか読まず、
  **実際の配送経路を取り違えていた。**

**是正は 2 つ。**

1. **配送経路を 3 つ見る** —— `assistant` の `text` ／ `result` イベントの `result` ／
   **コメント投稿ツールの `input.body`**。3 つ目は AI レビュー自身の 🟡 指摘による
   （`--allowedTools` に `add_issue_comment` 等があり、**判定をそれで投稿すると 1・2 に現れない**）。
2. **取り出せなかったときは落とさない**（判定不能として warn ＋ exit 0）。
   **イベント種別の内訳を診断として出す** —— 次に同じことが起きたとき、ログを漁らずに形が分かる。

> 🔴 **全文を走査する解決は採らない。** 実行ログには**プロンプト自身**が含まれ、その中に
> 判定フォーマットの雛形（`### 🔴 重大` 等）が書かれている。**全文検索にすると常に一致して
> 緑になり、ゲートが無意味になる。** 同じ理由で `tool_use` は **`input.body` に限定する**
> （全 `input` を見ると `Bash` の `command` 等まで拾い、見出しを含むコマンドで緑にできてしまう）。

## 対照実験（実走した実測）

| 実行ログ | exit | 予測 |
| --- | ---: | --- |
| 判定 3 種を含む | **0** | 一致 |
| **判定を欠く**（#489 の形 A の再現） | **1** | 一致 |
| 判定のうち 1 つだけ欠ける | **1** | 一致 |
| 本文に語だけがある（見出しではない） | **1** | 一致 |

**自己試験 16 件 all passed**（見出しレベル 1〜6 の許容・`assistant` 以外のテキストを使わない・
複数メッセージの連結・fail-open の 2 形を含む）。

### 🔴 実 CI での初回実行（決定6 の根拠）

| | 結果 |
| --- | --- |
| レビューの判定 | **投稿された**（🔴 0 / 🟡 1 / 🟢 0） |
| `Check review verdict` | **failure（偽陽性）** |
| 検査器の出力 | **「見つかった見出し: （無し）」** |

**予測（「判定が出れば緑になる」）は外れた。** 判定の有無ではなく**抽出そのものが失敗していた。**

**副次的に、決定4 が効いていることも実測できた** —— レビューは `backend/`/`frontend/` の
差分が空であることを確認し、**ビルド・テストを対象外と判断して 3 分 14 秒で完了した**
（#489 では 3 回とも 4〜20 分かけて判定を出せなかった）。

### 実 CI での 2 回目の実行（決定6 の是正後）

| | 結果 |
| --- | --- |
| レビューの判定 | **投稿された**（🔴 0 / 🟡 1 / 🟢 1・所要 2m29s） |
| `Check review verdict` | **success（判定を検出）** |
| CI 全体 | **24/24 緑** |

**偽陽性は再発しなかった。** 決定6 の配送経路 3 種化により、**実データから判定を取り出せることが確認できた。**

> **ただし、これは「判定があれば緑になる」ことの確認であって、「判定が無ければ落ちる」ことの
> 確認ではない。** 後者は自己試験・対照実験でしか再現していない（残余リスク参照）。

**この回のレビューが指摘した 🟢 も採った** —— 決定6 の実装は `tool_use` であれば**ツール名を問わず**
`input.body` を拾うのに、コメントは特定のツール名を列挙していた。**実測でこのワークフローが実際に
使う投稿経路は `mcp__github_comment__update_claude_comment` であり、列挙に含まれていなかった**
——**ツール名で絞る設計にしていたら取りこぼしていた。** コメントを実装（フィールド名で絞る）に合わせた。

## 影響

- 肯定的:
  - **形 A を緑にしない仕組みを置いた**（ただし実データでの発火は未確認。残余リスク参照）。
  - **引き金そのものにも手を入れた**（決定4）。検査器は事後の網であり、
    **差分ゼロの PR で全スイートを回さなくなれば、そもそも詰まらない。**
  - 検査器は**自己試験を内蔵**しており、判定規則が壊れれば CI で分かる。
- 否定的 / トレードオフ:
  - **見出しの書式に依存する。** レビューが判定の見出しを別の書式で書くと**偽陽性**になる
    （ジョブが落ちる）。**偽陰性より偽陽性へ倒した** —— 落ちれば人が気付くが、
    緑のまま素通りすると誰も気付かない。
  - **判定の「中身」は見ない。** 空の判定（3 種すべて「指摘なし」）でも緑になる。
    **本検査が守るのは「判定が在るか」だけである。**

## 残余リスク

- 🟡 **実データで確かめられたのは「抽出が効くこと」までであり、「発火すること」ではない。**
  決定6 の是正後の初回実行で、**判定あり → 抽出成功 → 緑**を実測した（下記「実 CI での 2 回目の実行」）。
  **これで「黙って skip し続ける」形は否定できた** —— 判定不能の fail-open へ落ちてはいない。
  ただし**判定を欠く実データでジョブが落ちること（exit 1）は、まだ観測していない**。
  自己試験と対照実験では再現しているが、**実ログの形での発火は未確認**である。
  **「配線したから守られている」ではなく「抽出は実データで動いた」までが、現在言えることである。**
- 🔴 **プロンプトの遵守は機械では守れない。** 決定3・決定4 はプロンプトへの記述であり、
  **守られなかったことを検出する機械は無い**（決定1 の検査器が捕まえるのは結果であって過程ではない）。
  **決定4 が守られなくても、判定さえ投稿されれば緑になる。**
- **見出しの書式が変わると偽陽性になる。** レビューのフォーマットを変更するときは
  `VERDICT_HEADINGS` を同時に直す必要がある。**両者が離れていることが弱点である。**
- **B の形（timeout で `cancelled`）は本 ADR では直らない。** 決定4 で頻度は下がるはずだが、
  **重い PR では依然として起こり得る**。その場合はマージが止まる（安全側）。
- **kit への環流は起票まで済んでいる**（決定5。[planning#333](https://github.com/endazon/project-planning/issues/333)）が、
  **反映されるまで配布先の他リポジトリは同じ穴を踏み続ける。** 決定6 の是正も併せて環流が要る。
