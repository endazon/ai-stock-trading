# IADR-0549: 効いている確定済み日報の再確定（#1373 段 B）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

## 決定

### 決定 1: 効いている確定済み日報への `/policy` は、行を版 n+1 のドラフトへ戻して版を足す

- `ReportPolicyRevisionService.ResolveTarget` は、確定済みの行が**日報で、かつ効いている日報**（`GetLatestConfirmed(Daily)` の期間キー＝二段で選んだ最新の確定済み日報）なら、確定済みの版 n の方針を土台に改訂案を作る。
  保存は `IReportStore.StartRevisionDraft`（新設）で、行を Draft・版 +1 にして方針と本文を差し替える。確定した版 n の写しは残るので、**確定するまで版 n が効き続ける**（FR-07）。
- 本文は確定済みの本文の状態の行だけを未確定へ戻し（`ReportBodyStatus.MarkDraft`。`MarkConfirmed` の逆）、改訂の記録を末尾へ足す。
- 当日（JST）の日報には限らない。会話キーを省略した対象は従来どおり当日の日報である。
- それ以外の確定済み（より古い日報・週報・月報）は従来どおり 409（`AlreadyConfirmed`）で、返答に再確定できる日報（効いている日報）の会話キーを書く。
  従来の「明日の日報の作られ方」の案内は、当日の確定済み日報（＝効いている日報）に当たったときのものだったので削った（その場合は版を足す）。
- 会話キーを省略した `/policy` を `AutoDailyPending` で断るときは、効いている日報の会話キーと `/policy period:<key>` で再確定できること（承認待ちの版 n+1 があればその版）を書く。
- 未確定の版 n+1 のドラフトへの `/policy` は、そのドラフトを改訂する（従来の未確定の報告書と同じ）。
- 回数は `/policy` の 1 日の上限（IADR-0432）に数える。別枠は作らない。上限に達した日は再確定のための改訂も断る（ADR-0068 決定 5）。

### 決定 2: 版 n+1 の確定は、写しの通し番号の最大 S までで「なお効いている」を判定し、同じ 1 回の保存で確定する

- `Confirm`（EF・InMemory）は、まず写しの通し番号の最大 S を読む。同じ期間キーに確定版の写しが既にあれば（＝版 n+1 の確定）、**S までの写し**で二段で選んだ期間キーがこの期間キーであることを確かめ、違えば `ReportNoLongerEffectiveException`（409・理由に効いている日報の会話キー）で断る（状態は変えない・ドラフトは残す）。
  通れば行の確定と写し S+1 の追加を 1 回の `SaveChanges` で保存する。
- 🔴 **S を判定の前に読むのが要点である。** 判定の後に別の日報の確定が入れば、その確定が S+1 を取り、こちらの保存は鍵の衝突で負けて読み直す（IADR-0548 決定 2 の衝突の分類）。S を判定の後に読むと、間に入った確定を見落としたまま S+2 で通る。
- 効いている日報を動かすのは日報の確定だけで（ドラフトの作成は動かさない）、より新しい日付の日報の確定は常に通る（新しい日付の確定には判定を掛けない）。並行したら先に保存を終えた方が勝つ（ADR-0068 決定 1）。
- 再確定のときは `ConfirmResult.SupersededVersion` にそれまでの確定版の版を返す（通知・KB が読む）。
- `StartRevisionDraft` の作成時の判定は保存の外で行う（行の版の並行トークンだけを掛ける）。並行して移った後にできたドラフトは、確定で必ず断られる。

### 決定 3: 効いている日報が移った後の版 n+1 は、確定・`/policy`・`/report regenerate` をすべて断る

- 見分けは `EffectiveDailyReport`（行が Draft で、同じ期間キーに確定版の写しがあり、その期間キーが効いていない）。`/policy` は `NoLongerEffective`（409・AI を呼ばない・回数を使わない）、作り直しも `NoLongerEffective`（409・入力も LLM も呼ばない・枠を使わない）。確定は決定 2 のとおり保存の中で断る。
- レビュー照会（REST・gRPC `GetReportReviewResponse`）に `confirmedVersion`（効いている確定版の版）と `noLongerEffective` を足し、通知サービスの `/report show` が「確定するまで版 n が効く」「この版は確定できない」を出す（非破壊の追加）。
- 一覧・取得は行の現在の状態（版 n+1 のドラフト）を返す。効いている確定版は `daily-policy` とレビュー照会で読む。

### 決定 4: 作り直しは効いている間の版 n+1 に当たり、作り直しの枠に数える

- ADR-0052 のとおり、方針の節は保ち事実と散文だけを作り直す。回数は作り直しの上限（IADR-0491）に数え、`/policy` の上限には数えない。確定済みの版は従来どおり作り直さない。

### 決定 5: KB は最新の確定版で置き換え、失効した版 n+1 の写しは印つきで残す

- **再確定**（`SupersededVersion` あり）の確定時の KB 保存は、保存の口（作成）を通らず、KB の入れ直し（IADR-0436）を **1 つの期間キーだけ・既存の本文も差し替える指定**で走らせる（`ReportKnowledgeReingestScope.Single`）。基盤に外部 ID の upsert が無いので、作成すると同じ期間の確定版の写しが 2 件になる。入れ直しは残った承認待ちの写しも消す（ADR-0065 決定 2 の順序）。入れ直しが別に実行中なら置き換えず警告する（次の入れ直しで揃う）。
- **入れ直し**の対象は、行の現在の状態ではなく**期間キーごとの最新の確定版**（`IReportStore.ListLatestConfirmedVersions`）にする。行が版 n+1 のドラフトの間も確定版を入れる。
- **効いている日報が移った**（日報の確定で効いている期間キーが変わった）とき、移る前の日報の版 n+1 のドラフトの写しを `IReportDraftKnowledgeCopy.MarkExpiredAsync` で**失効の印つきの写し**に置き換える（作れたときだけ元の写しを消す・削除はしない。ADR-0065 決定 5）。
  印は新しい属性 `reportDraftStatus=expired`。🔴 `reportState` は `draft` のまま保つ。基盤の重複の棚卸しは `reportState=draft` でない写しを確定報告書の写しに数えるため、`reportState` を変えると誤検知になる（MSP 側の `AstStaleCopyRules` の試験で確かめた）。属性は作成の 1 回だけで持つ規律（IADR-0526。PATCH は全置換で露出のキーが落ちる）なので、印は作り直した写しで付ける。
  入れ直し・確定時の削除は失効の写しを消さない。
- **入れ直しも同じ判定で写しを扱う**（PR #1375 の AI レビュー 🟡）。行が版 n+1 のドラフトなら、その日報が効いている間（承認待ち）は承認待ちの写しを残し（確定済みの報告書に「残った」写しとは扱わない）、
  効いている日報が移った後は失効の印つきの写しへ置き換える。判定は `EffectiveDailyReport.Classify`（`/policy`・作り直し・確定時の失効と共有）。
  確定時に印を付けそこねた写し（並行した別の日報の確定・KB の障害）は、次の入れ直しで回復する。

### 決定 6: 版を足したことと再確定したことを通知する

- 版 n+1 のドラフトを承認待ちにしたら、提示の通知（`ReportDraftPresented`）を出す。末尾に `ReconfirmingFromVersion`（任意）を足し、通知は「日報に版を追加（承認待ち）」「確定するまでは確定済みの版 n の方針が効き続けます」と書く。`/policy` の通常の改訂は従来どおり提示の通知を出さない（応答の確認ボタンで足りる）。
- 再確定は `ReportConfirmed` の末尾に `Version`・`SupersededVersion`（任意）を足し、通知は「日報の再確定（効いている方針の版が変わりました）」と、それまでの版からこの版へ変わったことを書く。初回の確定の文は変えない。
- いずれも非破壊の追加（`event-schemas.baseline.json` を更新）。

### 決定 7: Stage 0 の記録に方針の期間キーと版を持たせる（戦略 ID には含めない）

- `Stage0DecisionRecord` の末尾に `DailyPolicyReference? Policy`（既定 null）を足し、記録器は判断時点に組み直した方針（as-of の応答の期間キーと版）を載せる。
- `Stage0StrategyIdentity.ComputeContentHash` には足さない。方針の本文は入力の指紋に既に入っており、版を足すと同じ入力の記録の戦略 ID が版の有無で変わる。したがって戦略 ID の導出に影響しないので、別 issue にせずこの PR に入れた（作業仕様書の判断）。

## 検討した選択肢

### 「なお効いている」の判定の置き場所

1. **`Confirm` の中に置く**（**採用**） — REST・gRPC・入れ替え案の確定ボタンのどの経路でも同じ判定が掛かる。判定と確定が同じ保存に入る。
2. 別の口（`ConfirmIfStillEffective`）を足し、呼び出し側が選ぶ — 呼び忘れた経路が判定なしで版 n+1 を確定できる。

### 失効の印の付け方

1. **`reportState=draft` を保ち、別の属性で失効を示す写しを作り直す**（**採用**） — 基盤の棚卸しを誤らせず、属性の全置換も使わない。
2. `reportState=expired` へ変える — 基盤の棚卸しが確定報告書の写しに数え、重複の組として誤検知する。
3. 本文の見出しだけで示す — 計画は「状態の属性で示す」と定める。属性で見分けられない。

### 再確定の確定版の写し

1. **入れ直しを 1 つの期間キーで走らせる**（**採用**） — 既存の「一覧で探して本文を差し替える・残った承認待ちの写しを消す」をそのまま使う。監査（`ReportKnowledgeReingested`）も残る。
2. 確定時に毎回作成する — 同じ期間の確定版の写しが 2 件になる（検索・RAG に両方出る）。

## 結果

- 確定した方針の誤りを、その日のうちに直せる（効いている日報なら当日・前日付を問わない）。配備までの暫定手段（翌日の日報で直す）は要らなくなる。
- 判断の記録（段 A）と Stage 0 の記録に方針の版が残るので、再確定の前後でどの版で判断したかを追える。

## 残余リスク

- 版を足すドラフトの作成時の判定は保存の外で行う。より新しい日付の日報の確定と並行すると、効いていない日報に版 n+1 のドラフトができ得る。確定は必ず断られるので方針には効かない（`/report show` は確定できないことを示す）。
- 再確定の写しの置き換えは、入れ直しが実行中なら行わない（警告。次の入れ直しで揃う）。
- 確定時の失効の印は best-effort である（KB の障害・確定エンドポイントの外で効いている日報が移った場合は付かない）。その写しは承認待ちの表記のまま残るが、
  次の入れ直しが同じ判定で失効の印を付ける（回復の手段は入れ直しである。自動の定期実行は無いので、運用者が `POST /reports/knowledge-base/reingest` を実行する）。
- 失効の印つきの写しは基盤の側では承認待ちの写しと同じ扱い（`reportState=draft`）であり、基盤の画面は失効を区別して表示しない（本文の先頭の見出しで読む）。
- 実 Discord での通知の見え方は AI セッションでは確かめていない（PoC の手順で確かめる）。
