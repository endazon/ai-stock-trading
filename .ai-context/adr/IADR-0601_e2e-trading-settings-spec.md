# IADR-0601: live の取引影響層の SC-01 / SC-02 の spec（#1419 / E-61）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: **Accepted**
- 日付: 2026-10-30
- 決定者: claude が起案（起点 #1419＝MSP#2013 の分割 E-61。親 #1410）。

## 起点・関連

- 起票: #1419（網羅表 A-026・A-044〜A-048）。
- 前提: IADR-0565 決定 1・3（送らないもの・スナップショットと復元）、IADR-0599（門と復元の本体）、IADR-0589（live-ro の書き込みの保険）。

## 決定

### 決定 1: 書き込みの保険は「危険な 3 種だけを abort し、ほかは通して記録する」

- live-ro の保険（`support/guard.ts`）は `/bff/` への書き込みをすべて abort する。trading 層は設定を書くので、それは使えない。
- trading 層の spec は、context の経路で `/bff/` への書き込みを記録し、危険な 3 種（発注先の変更・OpenD 認証のコード送信と再送）だけを abort する。3 種の定義は `guard.ts` の `DANGEROUS` を使う（綴りを 2 か所に置かない）。
- 各 test の後に、危険な 3 種を送ろうとした記録が 0 件であることを見る（abort は保険で、送ろうとしたこと自体を失敗にする）。

### 決定 2: A-046（409 の競合）は、版を要求に載せる SC-01 で検証する

- 網羅表の A-046 は SC-02 の行である。しかし SC-02 のリスク上限・監視の PUT は版を持たない。409 は DB の同時書き込みの競合でしか出ず、live では決定的に起こせない（L1 が 409 の描画を固定している）。
- 版を要求に載せて楽観排他を掛けるのは、全体前提条件（SC-01 の `expectedVersion`）だけである。行の意図（別 context で版を進めた後の保存 →「競合」・自動再試行なし → 再読込）を、SC-01 で検証する。網羅表の画面 ID の訂正は #1410 に返す。

### 決定 3: A-048 の閉場前の統制・テーマは、保存値が効いているときだけ同値で保存する

- 閉場前の統制とテーマの定義は、保存すると「構成の値が効いている」から「画面で保存した値が効いている」へ由来が移る。同値でも戻せない副作用である（スナップショットの突合は効いている値だけを見るので、差分としても出ない）。
- そのため、両方とも既に保存値が効いているときだけ、同値で保存する。構成の値のときは保存せず、test の注記に理由を残す。変動閾値・クールダウン・Stage 1 最小件数は値だけを持つので、いつも同値で保存する。

### 決定 4: 各 test の後に、事前スナップショットと突合して戻す

- `afterEach` で `restoreCore.reconcile`（IADR-0599 決定 3 と同じ本体）を呼び、事前スナップショットへ戻す。理由は `[e2e <runId> restore]`。復元の失敗も、残った差分も赤にする。globalTeardown も同じ突合をもう一度行う。
- 履歴は消せないので、履歴を見る test は「理由に `[e2e <runId>]` を持つ自分の行が増えた」ことだけを見る。絶対件数は見ない。

## 結果

- 良い点: 取引に影響する設定を変えても、各 test の後に戻り、戻らなければ赤になる。発注先・OpenD 認証は送られない。
- 悪い点: live でしか流せない（門が閉場と in-flight なしを要する）。本 PR の時点では、live で流していない。
- 残余リスク:
  - A-047 は監視銘柄に空きがある（巡回の時間の検査で足せる）ことを前提にする。空きが無ければ追加が 400 になり、赤になる。
  - A-044 で保有建玉数上限が 1 のときは 1 上げる（緩める向き）。閉場中に限られ、各 test の後に戻す。
