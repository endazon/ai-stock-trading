# IADR-0462: 照会の失敗と LLM を呼ぶ前の見送りを監査台帳へ出す（#1092 段 2）

## 背景

2026-09-29 の夜、PC のスリープで Pod が作り直され、02:00 以降のログが消えた。稼働クラスタに Loki / Prometheus は無い。
段 1（作業仕様書 `20260929_1092_nightly-ledger-summary`）は既存の台帳だけで夜を要約したが、次は台帳に無かった。

- moomoo の建玉照会の失敗（保護逆指値ガード・スナップショット・S1 の据え置きのどれも記録を残さない）と、取引判断の保有照会の失敗。
  段 1 は `BrokerPositionsObserved` の欠けから推定したが、Pod の停止と区別できず、ガードの 30 秒ごとの照会は表れない。
- LLM を呼ぶ前の見送り（日報の未確定・現在値なし・換算レートの未解決・鮮度切れで保有なし）。
- 判断中の例外。

## 決定

1. **照会の状態は、発生源ごとに「変わったときだけ」台帳へ出す**（新しい事実 `PositionQueryStatusChanged`）。
   - 状態は `Unknown`（起動直後）/ `Healthy` / `Failing`。遷移の表:

     | 前 \ 観測 | 成功 | 失敗 |
     | --- | --- | --- |
     | `Unknown` | **出す**（1 回だけ） | **出す** |
     | `Healthy` | 出さない | **出す** |
     | `Failing` | **出す**（失敗の始まり・続いた回数つき） | 出さない（回数だけ数える） |

   - 🔴 **状態はプロセスの中だけに持つ**（永続しない）。再起動で状態が消えても、起動直後の失敗は `Unknown → Failing` として必ず出る。
     起動直後の成功も 1 回だけ出す。前のプロセスで始まった失敗の区間を、再起動の後に閉じるためである（回復の時刻は「再起動の後の最初の成功」までしか分からない。
     `PreviousStatus=Unknown` で読み分ける）。1 プロセス・1 発生源につき 1 回なので、平常の周期的な成功は出ない。
   - 永続しない理由: これは「次に出すか」の判定であって期間の集計ではない（IADR-0254 決定3 の禁じた形ではない。集計は台帳から取る）。
     失われても最悪で起動直後に 1 件余計に出るだけであり、取りこぼす向きには倒れない。永続の保存先を足す費用に見合わない。
   - 発行に失敗したら状態を戻し、次の観測で出し直す（黙って `Failing` のまま沈まない）。その後に別の変化が起きていたら戻さない。報告は例外を投げない。
   - 実装は共有物 `PositionQueryHealthTracker` / `PositionQueryHealthReporter`（Shared.Infrastructure）。各サービスに singleton を 1 つだけ置き、業務クラスへ同じ実体を渡す。
2. **発生源は呼び出し元で分ける**（アダプタで数えない。アダプタでは誰の照会か分からない）。7 つ:
   `ProtectiveStopGuard`（巡回の先頭。照会し直しの最終結果を 1 回として数え、分類できた失敗の種類〔IADR-0458〕を載せる）・
   `BrokerPositionSnapshot`・`BrokerAvailabilityProbe`・`SoftwareStopClose`（S1 が自ら照会した回だけ。ガードから渡されたスナップショットは数えない）・
   `OrderDispatch`（決済のゲート〔例外も失敗〕と S1 の武装前）・`TradeDecisionHoldings`・`TradeDecisionWorkingEntries`（取引判断は実結線〔`IsEnabled`〕のときだけ）。
   数えない呼び出し元（ガードの建玉 0 の確かめ直し・乖離の取り込み・市場監視・報告書）と理由は作業仕様書の母集合の表にある。
3. **発行はランタイムの `MessageBus` から行い、監査台帳だけが購読する**（通知しない）。発注・S1 のハンドラの処理中に呼ばれても、その処理が例外で終わったときに記録が捨てられない。
   相関は発生源ごとの決定的 GUID（`position-query:<発生源>`）。
4. **LLM を呼ぶ前の見送りは、1 回につき 1 件の新しい事実 `TradeDecisionForgoneBeforeLlm` で出す**（理由 4 値の `DecisionForgoneBeforeLlmReason`。名前は `DecisionSkipReason` と一致）。
   - 出口は `SkipBeforeLlmAsync` の 1 か所（4 地点）。見送りの計上（`Skip`）は従来どおり 1 件。発行の失敗で見送りを壊さない（キャンセルだけ伝える）。
   - 🔴 `TradeDecisionHeld` / `TradeDecisionSkipped` / `OrderDispatchForgone` は流用しない（IADR-0358 決定4）。`TradeDecisionHeld` は市場監視が急変の基準値を進める事実であり、
     判断をしていない見送りで基準値を動かしてはならない（IADR-0452 決定1）。
   - IADR-0358 決定4 の「新しいイベントを作らない」は「語彙を 1 件だけ特別扱いしない」ためであった。本決定は LLM より前の見送りの**全部**（4 地点）を 1 つの事実に載せるので、その理由に反しない。
     LLM より後の 10 地点は `TradeDecisionHeld`（IADR-0452）が既に台帳へ出している。
   - 抑止しない。件数を数えるためである（日報が未確定のまま夜が過ぎると、銘柄数 × 巡回数の行になる）。発行は判断サービスのスコープの `IMessageBus`（見送りはハンドラを例外で終わらせない）。
5. **判断中の例外は本決定では台帳へ出さない。** LLM・保有照会・サイジング文脈などの失敗は例外にならず fail-safe の値へ倒れ、残る例外はバグの類である。
   定時の経路は銘柄ごとに捕まえて続け、価格変動の経路は Wolverine の再試行の後に `<queue>_error`（RabbitMQ・永続）へ移る。再試行ごとに数えない設計と、
   例外の語彙（型名だけにする・秘密を載せない）を決める必要があり、別件とする。
6. **夜間の要約**（`scripts/nightly-ledger-summary.sh`）に §10（照会の失敗の区間・発生源別。窓の前から続く失敗も出す）・§10a（状態の変化の件数）・§11（LLM を呼ぶ前の見送り・理由 × 起点）を足す。
   段 1 の §9（観測の欠けからの推定）は残す（本決定の配備より前の夜と、Pod の停止の読み分けに使う）。

## 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 照会ごと（30 秒ごと）に失敗を記録する | 失敗が続くと台帳が洪水する（1 夜で 1,000 行超）。回数は回復の記録に載せれば足りる |
| 状態を DB に永続する | 決定1 のとおり。失っても取りこぼさない向きであり、保存先と移行を足す費用に見合わない |
| 起動直後の成功を出さない | 前のプロセスで始まった失敗の区間が、台帳の上で閉じないまま残る（再起動をまたぐと「窓の終端まで続いた」と誤読する） |
| アダプタ（`MoomooBrokerAdapter`）で一律に数える | 発生源が分からない。ガードの照会し直しの途中の失敗まで数える |
| 見送りを `TradeDecisionHeld` に載せる | IADR-0358 決定4・IADR-0452 決定1（誤帰属・基準値を誤って進める） |
| LLM を呼ぶ前の見送りを状態の変化だけで出す | 件数が知りたい（#1092）。状態の変化では「何件見送ったか」を復元できない |
| 通知にも流す | 平常の運用で鳴り、止まった事象の通知が埋もれる。建玉照会の失敗は既存の見送り（`BrokerPositionsIndeterminate`）の通知と重なる |

## 結果

- 翌朝、台帳だけで「どの照会が・いつから・いつまで・何回失敗したか」と「LLM を呼ぶ前に何件・どの理由で見送ったか」を数えられる（Pod の再起動の後も）。
- 統制・発注の判定、見送りの計上、`BrokerAvailabilityObserved` / `BrokerPositionsObserved` の意味は変えない。
- **残余**:
  - 取引判断や発注執行を複数台で動かすと、状態は台ごとに持つ（同じ失敗が台数分出る）。現行の配備は 1 台。
  - 再起動をまたいだ失敗は、回復の時刻が「再起動の後の最初の成功」までしか分からない。
  - 照会の失敗の 1 回ごとの時刻は残らない（状態の変化の時刻と、回復までの回数だけ）。
  - 市場監視の保有照会（損切りライン到達の判定）・報告書の照会は対象外。判断中の例外も対象外（決定5）。
  - LLM の後の見送りで判断時点の価格が無い・解析不能の回は、引き続き台帳に出ない（IADR-0452 の残余）。
  - 状態の変化の発行が続けて失敗すると、その間の遷移は台帳に出ない（出し直しは次の観測で行う。発行先が戻るまで記録は無い）。
  - 最初の失敗の発行が失敗して状態を戻すと、次の観測での出し直しは「その時点で失敗が始まった」として出る。`FailingSince`（と
    回復に載る回数）は出し直した時刻から数え直され、実際の失敗の始まりより遅れる（PR #1110 の監査 L1。記録のみ。
    発行できなかった間の失敗は、発行先が戻るまで台帳には無いという上の残余の一部である）。
