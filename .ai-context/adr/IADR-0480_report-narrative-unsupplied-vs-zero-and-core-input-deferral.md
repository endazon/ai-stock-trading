# IADR-0480: 報告書の散文へ未供給と 0 を区別して渡し、中核の入力の一過性の欠落では長く見送る（#1156）

## 背景

再起動の直後に生成された日報の散文（LLM）は「評価損益についても参照すべき建玉がなく」と書いた。実際は 3 銘柄を保有していた。
週報の散文は費用 0.00 USD を「費用面での負担は発生しておらず」と書いた。実際は経費明細が未取り込み（#1086）である。

コードで確かめた原因は次のとおり。
- 散文のプロンプトは建玉も未供給の入力の一覧も受け取っていなかった。渡すのは損益の集計値・方針・上位方針だけである。
- 評価損益は**当期間の約定から畳んだ建玉だけ**の値で、期間より前から保有する建玉を含まない。当日に約定が無ければ 0 になる。LLM はこの 0 と約定 0 件から「建玉なし」と推測した。2 回目の試行で建玉は供給されていたが、プロンプトに無いので同じ推測が起きた。
- 費用合計は前提条件の料率からの概算（手数料＋為替スプレッド相当）である。取引諸費用・借株料・実際の経費明細を含まない。それを確定値として渡していた。
- 約定の不達は空列へ倒れる（IADR-0115 決定5）。プロンプトは 0 件・損益 0 を確定値として渡していた。
- 見送りの上限（5 回 ≒ 12.5 分）は入力の重さを区別しなかった。

## 決定

### 決定 1: 散文の文脈へ未供給の入力の一覧と建玉を渡し、プロンプトは未供給と 0 を区別する

- `ReportNarrativeContext` に `UnsuppliedInputs`（生成器が判定した未供給の入力）と `Positions`（日報だけ。null＝照会できていない／空列＝建玉なし）を足す。生成器 → `DraftRequest.UnsuppliedInputs` → `ReportDraftService` → 文脈、の順で渡す。
- プロンプト（`ReportNarrativePromptBuilder`）:
  - 未供給の入力があれば「取得できなかった入力（未供給）: …」の一覧と規則（「無い」「0」「発生しなかった」と言い切らず、触れるなら「未供給（取得できなかった）」と書く）を載せる。**未供給が無ければ節ごと出さない**（供給されている入力を未供給と言わせない。05_screens の逆向きの禁止）。
  - 日報の建玉は 3 通りで渡す。未供給なら「未供給（取得できなかった）」と「建玉なし」と書かない指示。空なら「0 件（建玉なし）」。あれば件数と銘柄（自サービスの台帳由来のティッカー。外部の自由文ではない）。週報・月報は建玉を入力に持たないので、建玉の有無に触れない指示を入れる。
  - 評価損益の行に「当期間の約定から畳んだ建玉だけの値。この値や約定件数から建玉の有無を推測しない」を添える。
  - 約定が未供給なら、実現損益・税・評価損益・件数・費用合計の値を渡さず「未供給（取得できなかった）」と渡し、取引の有無・損益に触れない指示を入れる。手動売買の取り込みが未供給なら評価損益の値だけを渡さない（在庫の畳み込みが崩れ、実在しない建玉の値になり得る。IADR-0360）。
- 数値の権威はコード集計のまま（FR-16）。プロンプトへ新しい数値を足すのは建玉の件数だけで、これも系が数えた値である。

### 決定 2: 費用合計は「概算」として渡し、0 でも「負担なし」と書かせない

- 行は `- 費用合計: <値>（概算）` とし、注記で「前提条件の料率から見積もった売買手数料と為替スプレッド相当額。実際の経費明細は取り込まれておらず、取引諸費用・借株料を含まない。0 でも『費用負担は無かった』と書かない」を渡す。
- 条件をつけず常に付ける。report-service は経費明細（#1086 の `TradeExpenseRecorded`）を取り込む経路を持たず、費用合計は常に概算だからである。
- 本文（Markdown）の費用の節は既に「取引諸費用は記録源が無い」「費用合計は過小」と描いている（IADR-0305 / IADR-0306）。変えない。

### 決定 3: 中核の入力（約定・建玉・手動売買の取り込み）の一過性の欠落では、見送りの上限を別に持つ

- `ReportInputs.IsCore` を足す。中核は約定・建玉・手動売買の取り込みの 3 つ。欠けると報告書の主張（損益・取引の有無・保有の有無）そのものが崩れる。監査台帳の記録（為替・LLM 実績・借株料・判断根拠・損切りの実行機構など）は、各節が「照会できませんでした」と描けば主張は崩れないので中核に入れない。
- `ReportDeferralSettings.CoreMaxDeferrals`（既定 12。構成 `Reports:AutoGeneration:DependencyRetryCoreMaxAttempts`）。待ち時間は従来どおり 30 秒からの倍々で、巡回間隔（既定 300 秒）が上限である。合計は 30+60+120+240+300×8 ＝ 2850 秒（約 47.5 分）。
- 一過性の失敗で欠けた入力に中核が 1 つでもあれば、中核の上限を使う。回数は期間ごとに 1 本で数え、上限だけを選ぶ。
- 中核の上限は通常の上限を下回らない（下回る構成値は通常の上限へ揃える）。通常の上限が 0（＝「見送らない」を明示した構成。#840 からの約束）なら中核も 0 にする。
- 生成窓の終端（#866）の判定はそのまま効く。窓が閉じる前に縮退版を出す。

### 決定 4: 縮退した下書きを作り直す経路（issue のコメントの期待）は実装しない。計画の裁定に回す

既存の状態遷移（`PendingApproval → Revise → Drafting → Present`）を使えば、生成器が縮退した下書きを上書きすることは技術的にはできる。それでも実装しない理由は次のとおり。
- 計画の業務フロー（03_reporting-cycle）でドラフトが更新されるのは、利用者の修正指示・質疑による対話だけである。利用者の操作なしに、提示済みの下書きを系が書き換える経路は計画に無い。
- 上書きは利用者の `/policy` の改訂（方針の差し替え・改訂の記録）を消し得る。版番号つきの確定（`/report approve <版>`）との競合の規則も要る。
- `/report regenerate <periodKey>` は Discord のコマンドの追加で、07_discord-bot-design と画面設計の変更になる。

裁定に回す選択肢:

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | `/report regenerate <periodKey>`（OwnerOnly）。下書き（未確定）の本文を、その時点の入力で作り直す。方針は現在の下書きの方針を保ち、版を上げて再提示する | 利用者の操作でだけ書き換わる（ADR-0003 の精神と整合）。縮退の有無を問わず使える | コマンド・API・画面設計の追加。`/policy` の改訂の記録を本文へ引き継ぐ規則が要る |
| B | 自動の作り直し。未供給の入力を記録した下書きのうち、利用者が改訂していない版（自動生成の版のまま）だけを、依存先の回復後に生成器が作り直して再提示する | 利用者の手間が無い | 提示済みの文書を系が書き換える経路の新設（計画の裁定が要る）。確定直前に書き換わる競合。通知が 2 回届く |
| C | 中核の入力が未供給のまま提示しない（窓の終端・上限でも出さない） | 誤った「建玉なし」が提示されない | 依存先が戻らないと報告書が出ない（#866 で退けた「無音の消失」）。無応答時の方針継続の判断材料が欠ける |
| D | 現状維持（本件の決定 1〜3 で頻度と害を下げる） | 変更なし | 縮退した下書きを消せない状態は残る |

本件の決定 3 で「中核の入力が一過性に欠けたまま提示する」頻度は下がり、決定 1 で散文が未供給を「無い」と言い切る害は下がる。ただし作り直しの経路が無いことは変わらない。

### 決定 5: 採らなかったもの

- **未供給の入力を本文（Markdown）の冒頭にも一覧で描く**: 各節は既に null を「照会できませんでした」と描き、未供給の一覧は提示の通知と `/report show` に出る（IADR-0352 決定 5）。本文の節の変更は計画（04_report-templates・ADR-0030 の節番号）に触れるため、本件では足さない。
- **見送りの基準の待ち時間（30 秒）を延ばす**: 回復の直後に拾える早さを落とす。上流の 401 の窓（24.6 秒。#866 の実測）を跨ぐには 30 秒で足りる。延ばしたのは上限（合計の待ち）である。
- **恒常的な失敗（403）でも中核なら見送る**: 待っても変わらない設定誤りで報告書を遅らせる（IADR-0352 決定 4 の判断を保つ）。
- **費用合計の注記を「経費明細を取り込んだか」の旗で切り替える**: 取り込む経路がまだ無い（#1086）。旗を先に作ると、常に偽の旗が増えるだけである。取り込みを足すときにこの注記を見直す（残余）。

## 結果

- 散文は、取得できなかった入力を一覧で受け取り、「無い」「0」と言い切らない指示を受ける。日報の散文は建玉の件数と銘柄、または未供給を受け取る。評価損益 0 から「建玉なし」と推測しない指示を受ける。
- 散文は費用合計を概算として受け取り、0 でも「負担なし」と書かない指示を受ける。
- 約定・建玉・手動売買の取り込みが一過性に欠けている間は、最長 約 47.5 分（既定）見送る。それ以外の入力は従来の 約 12.5 分。
- 試験 T-10-2160〜T-10-2177。

### 残余リスク

- プロンプトの指示は LLM の出力を保証しない。散文が指示に反して「建玉なし」と書く可能性は残る。散文を機械で検査する仕組み（禁止語の検出など）は無い。
- 縮退した下書きを作り直す経路は無い（決定 4。裁定待ち）。
- 費用合計の注記は経費明細を取り込んだ時点で見直しが要る（#1086）。取り込んだ後もこの注記が残ると、実額を「概算」と呼ぶ誤りになる。
- 中核の上限はプロセス内の回数であり、再起動で 0 に戻る（IADR-0352 と同じ）。
- 建玉が「供給された空列」でも、それがリスク管理の射影の起動直後の未構築によるものなら、散文は「0 件（建玉なし）」を受け取る。供給元が正しく未供給を返すことが前提である。
