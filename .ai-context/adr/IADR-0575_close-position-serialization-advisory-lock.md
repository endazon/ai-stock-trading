# IADR-0575: 同じ建玉を売る決済を (銘柄, 市場, 決済の方向) ごとに直列にする

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: **Accepted**
- 日付: 2026-10-23
- 決定者: Claude Code（#1446 の求めに沿う実装の形。計画の規則は変えない）

## 起点・関連

- 起点: #1446（親 #1423 の M-2「判断の決済と S1 決済の並行送信の競合は、最終的にブローカーの『建玉不足で拒否』に依存している」）。
- 計画: ADR-0050 決定 1（判断の手仕舞いは処理中の決済を引いた残りだけを送る・損切りも判断の手仕舞いを理由に止まらない）、決定 3（売れる数量を押さえるかは実弾解禁前の確認）。
  決定 4 の表は、重なったときの二重売りを IADR-0461・IADR-0466 が防ぐと書く。**本 IADR はその前提（両者が相手の記録を読めること）を、並行のもとでも成り立たせる。**
- 前提（覆さない）: IADR-0461（差し引き）、IADR-0466（S1 は判断の手仕舞いを取り消してから送る）、IADR-0515（利用者・自動縮小の決済は取り消さず差し引く）、
  IADR-0057（予約 → 発注 → 確定）、IADR-0529（新規建ての審査の直列化＝同じ作法の advisory lock）、IADR-0561 決定 3-3、IADR-0573、IADR-0574。

## コンテキスト

1. 判断の決済（承認の受け口）は、建玉照会 → 処理中の決済の差し引き（**発注の記録** `ExecutionRecord` を読む）→ 予約 → 送信 → 記録の保存の順で進む。
   S1 は、建玉照会 → 処理中の判断の決済の取消（記録を読む）→ 利用者の決済の差し引き → 予約 → 成行 → 記録の保存の順で進む。
2. **記録は送った後に書かれる。** 先発が証券会社へ送っている最中（予約の後・記録の前）に後発が読むと、後発は先発を見ずに全量を送る。
   予約（IADR-0057）は DecisionId ごとの一意であり、DecisionId の違う 2 本（判断の決済と S1 の決済）は止めない。
3. SIMULATE は未約定の売りが売れる数量を押さえるので、2 本目は「建玉不足」で拒否される（2026-09-29 の実測）。**押さえない証券会社では二重に売る**（ADR-0050 決定 3 の未確認事項）。
4. IADR-0561 決定 3-3 は「発注執行の承認の受信は 1 通ずつ（Wolverine の RabbitMQ 受信は Inline）」を前提に書くが、共通の配線（`UseAiStockTradingRabbitMq`）にモードの明示は無い。
   **Wolverine 6.24.5 の既定を実測した**（実 RabbitMQ 3.13 コンテナ・共通配線と同じ形の使い捨てのホスト。手順と表は作業仕様書）:
   - RabbitMQ キューのリスナは `Mode=Inline`・`ListenerCount=1`。同じキューへ 8 通（各 500 ミリ秒）で**最大並行 1**。
   - **別々の 2 キューへ同時に流すと最大並行 2。** キューごとにリスナが立つ。
   - よって前提は既定で成り立っている（承認のキューの中では 1 通ずつ）。しかし **S1 は `StopLossTriggered` のキュー（別のリスナ）と常駐ガードの巡回から来る**ので、承認と並行に走る。
5. 発注執行は helm で `replicas: 1` だが、`RollingUpdate`（Stage 0 の記録器を持つ構成だけ `Recreate`）の間は新旧の Pod が重なり、両方が承認を受け、両方のガードが巡回する。

## 決定

1. **承認の決済と S1 の決済は、(銘柄, 市場, 決済の方向) の鍵の直列化（`IClosePositionLock`）を取り、建玉照会から記録の保存（相 4）までを握る。**
   - 承認の受け口: `OrderExecutionAppService.ExecuteAsync` が Close のときだけ取る（新規建ては取らない）。見送り（予約の前・後）・送信の不明（例外）でも外れる。
   - S1: `SoftwareStopExecutor.TryCloseAsync`（到達の購読とガードの撃ち直しの共通の入口）で取る。🔴 **ガードの巡回の先頭の建玉（`snapshot`）は使わず、直列化の後に照会し直す**。
     先頭の照会は直列化の外で読んだ値で、その後に同じ建玉を売った判断の決済（即時に約定していれば処理中の記録にも現れない）を映さない。
     照会の増分は「到達済みで決済できていない行」の数だけである（平常時は 0）。S1 が自ら照会した回は S1 の発生源として成否を報告する（IADR-0462。ガードの報告と発生源が違う）。
   - 後発は先発の記録を読んでから数量を決める: 判断が先なら S1 は判断の決済を取り消してから送り（IADR-0466）、S1 が先なら判断は S1 の分を差し引いて送る（IADR-0461）。
2. **本番の直列化は発注執行の専有 DB の advisory lock（`PostgresClosePositionLock`）である。**
   - ロックだけを持つ専用の接続とトランザクションで `pg_advisory_xact_lock(<鍵>)` を取り、ハンドルの破棄でロールバックして外す（接続の切断・プロセスの停止でも外れる）。
     ストアの書き込み（DbContext）は別の接続でその都度コミットされるので、外す前に後発が読める（READ COMMITTED）。**ストアの書き込みをこのトランザクションに入れない**（送信の後にロールバックされると、証券会社へ送った注文の記録が消える）。
   - 鍵は `"AST:close-position:{Market}:{SYMBOL}:{Side}"` の SHA-256 の先頭 8 バイト（`string.GetHashCode` はプロセスごとに変わる）。**書式を変えない**（入れ替えで新旧が並走する間に直列化が割れる）。T-10-3006 が値を固定する（`BitConverter` はプラットフォームのバイト順で読み、x64 / ARM64 はどちらもリトルエンディアン）。
   - 待ちの上限は `lock_timeout` 2 分（`ClosePositionLockLimits.WaitLimit`）。先発が握る間に行うのは照会・取消・発注（OpenD の応答待ちは既定 15 秒）で、通常は数秒で外れる。
     🔴 **1 ミリ秒未満の上限は組み立てで拒否する**（PostgreSQL の `lock_timeout = 0` は無期限であり、丸めて 0 になると意図と逆になる。T-10-3006）。
   - 組み立ては `Program.cs` の scoped 登録 `PostgresClosePositionLock.ForContext(OrderExecutionDbContext)`: 関係 DB なら同じ接続文字列の advisory lock、そうでなければ（試験の EF InMemory）
     **ホストで 1 つ**の `InProcessClosePositionLock`（DI の singleton。IADR-0529 と同じ縮退）。3 つの組み立て（承認の受け口・S1 の実行器・ガード）へ渡す（T-10-3008 が本番の組み立てで固定する）。
   - 引数は省略可能で、省略時は**その組み立てだけ**の `InProcessClosePositionLock`（他の経路とは直列にならない）。直列にしたい試験は同じインスタンスを明示で渡す。
     🔴 **static の共有インスタンスは置かない。** ［2026-10-23 追記 / PR #1447 の CI・レビュー］初版はプロセスで 1 つの共有を省略時と InMemory の既定にしたが、
     並列に走る無関係な試験（別々のホスト・同じ AAPL / 米国 / 売り）どうしが同じセマフォで待ち合い、Wolverine の追跡の上限で 5 件が落ちた（backend-test の shard 4）。
     本番の渡し忘れは T-10-3008 が止める（省略時既定は安全側の後ろ盾にならない）。
3. **保護喪失の成行手仕舞い（`CloseUnprotectedPositionAsync`）とガードの成行の手仕舞い（`ReplaceOrCloseAsync`）も、予約から記録の保存までを同じ鍵で握る。**
   数量はそれぞれ自分のエントリーの約定・巡回の先頭の照会で決まり、他の決済を読まない。直列にするのは、**後から来る判断の決済・S1 がこの記録を読んで数量を決める**ためである。
   🔴 **入れ子にしない。** 4 経路はどれも直列化を握ったまま他の経路を呼ばない（承認の決済は Open の経路を通らない・S1 は取消だけを送る・ガードは S1 の撃ち直しを直列化の外で呼ぶ）。
   同じ鍵を同じ流れで 2 回取ると別の接続として待ち合い、上限まで止まる（例外で抜ける）。
   ［2026-10-23 追記 / PR #1447 の再レビュー］**ガードの成行は、直列化を取った後に建玉を照会し直し、送る数量を min(巡回の先頭の数量, 照会し直した決済方向の建玉) にする。**
   直列化を待つ間に判断の決済・S1 が約定していれば、古い数量のまま送ると押さえない証券会社では超過の売り（反対建玉）になる。照会し直して 0 なら送らず記録は Active のまま
   （次の巡回が建玉 0 を見て完了させる）、照会できなければ送らず人手対応（None）。照会の成否の報告（IADR-0462）は巡回の先頭の 1 回に留める（T-10-3011）。
   保護逆指値（初回・張り直し）は対象外: 保護レグは処理中の決済として差し引かない（ADR-0050 決定 1）ため、直列にしても算術が変わらない。
4. **取れなければ決済を送らない。**
   - 承認の受け口: 予約の前に例外（`ClosePositionLockUnavailableException`）で抜ける（証券会社に触れていない）。承認は共通の再試行（2s/10s/30s）で撃ち直され、使い切れば error キューに残る（真因は Error ログ）。
   - S1: 据え置き（到達の記録は残り、次の巡回で撃ち直す。猶予を過ぎれば「決済できていない」通知）。
   - 保護喪失の成行手仕舞い・ガードの成行: 確実に未発注として人手対応（`ProtectiveStopRemediation.None`）。保護記録は Active のまま次の巡回で撃ち直す。

## 検討した選択肢

| 案 | 採否 | 理由 |
| --- | --- | --- |
| (a) 承認の受け口のリスナを `ProcessInline()`＋`Sequential()` で明示し、IADR-0561 決定 3-3 の前提を実装に固定する | **不採用（単独では塞がらない）** | 既定がすでに Inline・1 リスナ（実測）であり、明示しても挙動は変わらない。S1 は別キューと常駐の巡回から来るので、承認のキューを直列にしても S1 と判断の決済は並行に走る（実測で 2 キューは並行）。入れ替え中の新旧の Pod も直列にならない |
| (b) (銘柄, 市場, 決済の方向) の DB advisory lock で「読む → 送る → 記録する」を直列にする | **採用** | 経路（キュー・常駐）とプロセス（Pod）をまたいで効く。IADR-0529 で同じ作法が実績を持つ。鍵が建玉単位なので、別の銘柄の決済・新規建ては待たない |
| (c) プロセス内のロック（鍵ごとのセマフォ）だけ | 不採用（試験と縮退にだけ使う） | 単一 Pod では (b) と同じだが、入れ替え中に新旧の Pod が重なると直列にならない |
| (d) 差し引き・取消で、予約だけの決済（Reserved・記録なし）も処理中に数える | 不採用（本件の外） | 予約は数量・銘柄を持たない（発注先と出どころだけ）。数量を足すには移行が要り、送信の結果が不明な予約の数え方（IADR-0461 の残余）も決め直しになる。直列化の後は「送信中」の予約を後発が読む窓そのものが無い |
| (e) (a) と (b) の両方 | 不採用 | (b) の下では承認の並行度に依らず決済は直列になる。(a) は既定と同じ値の明示であり、本件の安全性に寄与しない（IADR-0561 決定 3-3 の閉場前の手仕舞いの重複も (b) が覆う） |

## 計画との関係（環流の要否）

- 計画の規則は変えない（ADR-0050 決定 1 の差し引き・逆向きの取消を、並行のもとでも成り立たせる実装の形である）。決定 3（実弾で売れる数量を押さえるか）の確認は残る——本件で
  「押さえない証券会社で判断の決済と S1 が重なる」場合の二重売りは塞いだが、**保護逆指値（S0/S3）と判断の決済の併存**（決定 3 の表の行）は本件の対象ではない。
- よって環流は不要と判断した。

## 結果

- 判断の決済と S1 の決済がどちらの順で重なっても、板に残る売りの合計は建玉を超えない（T-10-3004）。直列化が無ければ同じ場面で 2,141 株（建玉 1,428 株）を出す（T-10-3005）。
- 平常時（同じ建玉に決済が重ならない）の挙動・送る数量は変わらない。S1 の決済の回だけ建玉照会が 1 回増える。
- 運用での見え方: 取れなかったときだけ Error ログ（「決済の直列化を取れなかった」）。平常時は何も出ない。

## 残余リスク

1. **送信の結果が不明な決済（予約が Reserved・記録なし）は後発に数えられない**（IADR-0461 の残余のまま）。直列化は先発が抜けた後に後発を走らせるが、先発の記録が無ければ後発は見ない。
2. ~~**ガードの成行の手仕舞いの数量は巡回の先頭の照会で決まる**~~ **［2026-10-23 追記 / PR #1447 の再レビュー］本 PR で解消した**（決定 3 の追記）。ガードは直列化の後に照会し直し、min(先頭の数量, 照会し直した建玉) を送る。
3. **直列化を握る間、承認の受信（1 本のリスナ）と常駐の巡回は後ろで待つ。** 先発が OpenD の応答待ちで止まれば、後発は上限（2 分）まで待つ。上限を超えれば各経路の「送らない」で扱う。
   🔴 **待つ側も専用の接続を 1 本ずつ握る**（最大 2 分）。承認のリスナ・S1 の購読・ガードはそれぞれ直列なので同時に握る接続は数本だが、Npgsql の接続プールの上限（既定 100）が
   他の DB 処理（ストア・耐久アウトボックス）と競合しないことが前提である。並行度を上げる変更（リスナの並列化・レプリカ増）をするときは、この前提を測り直す。
4. **DB が落ちている間は決済を送らない。** 予約・記録のストアも同じ DB に依存しており、従来も送信の前後で失敗していた（新しい依存ではない）が、失敗の位置が送信の前へ揃う。
5. **保護逆指値と判断の決済の併存**（ADR-0050 決定 3）は対象外。実弾で逆指値が数量を押さえるかの確認は残る。
