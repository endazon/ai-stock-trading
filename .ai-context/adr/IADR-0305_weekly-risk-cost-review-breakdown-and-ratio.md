## コンテキストと課題

計画 `04_report-templates` 週報 §5 は 2 行である。

```
## 5. リスク・費用レビュー
- 損切り執行 <n 件>・発注拒否 <n 件>・上限使用率の週間最大 <n%>
- 費用の内訳（手数料/諸費用/税）と損益に対する費用率 <n%>
```

IADR-0291 以来、本節は「本節は未実装です（#615 で実装予定）」だけだった。**#615 が実装対象としたのは
2 行目（費用の内訳・費用率）だけ**であり、1 行目の 3 項目は記録源が無い（同 issue が「上限使用率」を
明示的に対象外としている）。

実測した記録源の有無:

| 項目 | 記録源 |
| --- | --- |
| 損切り執行の件数 | **無い**。判断の起点は取引判断サービスのプロセス内にしかなく、`TradeDecisionMade` にも `OrderIntent` にも列が無い（`TradeHistoryViewBuilder` は `Trigger: null` を直書きしている） |
| 発注拒否の件数 | **無い**。本サービスに拒否の記録源が無く、**約定列には拒否が現れない**（約定していないため） |
| 上限使用率の週間最大 | **無い**（日報の同項目も同じ理由で出せていない） |
| 手数料 | `CostCalculator` の commission 項 |
| **諸費用** | **無い**。計画 `05_trading-assumptions` §2「米国株 売却時諸費用（SEC Fee・TAF 等）」は **要確認**のままで、`CostCalculator` は `commission + fxSpread` しか計算していない |
| 為替スプレッド相当額 | `CostCalculator` の fxSpread 項 |
| 税 | `PnlSummary.TaxWithheld` |
| 損益に対する費用率 | **分母の定義が計画に無い** |

## 検討した選択肢

### 費用の内訳をどう作るか

1. **期間・区分を切って `PnlAggregator.Aggregate` を呼び直す** — **採らない。** IADR-0301 決定1 と同じ理由で
   内訳の合計が §1 サマリと一致しなくなり、**しかもテストは緑のままである**。
2. **`FillPnlAttribution` へ `Commission` / `FxSpread` の列を足す** — 採らない。帰属は `Quantity`・`Price`・
   `Market` を持っており、**費用関数を同じ引数で呼び直すだけで分解できる**。列を増やすと `ReportView` を
   手組みしている全フィクスチャが動く（本 PR の差分が「新設 1 節の中身だけ」でなくなる）。
3. **帰属をそのまま数え直す純関数を新設する（採用）** — `PeriodCostReviewBuilder`。

### 「諸費用」をどう描くか

1. **`0` と書く** — **採らない。** 「費用が発生しなかった」と読めるが、実際は「記録していない」である。
   本サービスが全節で守っている規律（未供給と 0 の区別）に正面から反する。
2. **行ごと落とす** — 採らない。計画が求めた区分が落ちたことが読み手に見えない。
3. **`**未供給**` と描き、費用合計が過小であることを凡例に書く（採用）**。

### 費用率の分母

1. **§1 の実現損益（税引後・費用込み）** — **採らない。費用と税を既に引いた値であり循環する**
   （費用が増えるほど分母が縮んで比率が跳ね上がる）。
2. **約定代金の合計（売買代金に対する費用率）** — 採らない。計画は「**損益に対する**費用率」と書いている。
3. **実現損益（税引前・費用前）（採用）** — 費用を引く前の損益であり、循環しない。

## 決定

### 決定1: 費用の内訳は `FillPnlAttribution`（期間全体を 1 回だけ畳み込んだ帰属）から数える

`Domain/PeriodCostReview.cs` に純関数 `PeriodCostReviewBuilder.Build(entries, assumptions, taxWithheld)` を置く。
**帰属へ列を 1 つも足さない**——`Quantity × Price` と `Market` から費用関数を同じ引数で呼び直せば分解できる。

🔴 **期間・区分を切って `PnlAggregator.Aggregate` を呼び直さない**（IADR-0301 決定1）。
**内訳の合計 = §1 の費用合計**をテスト（純関数・出口の両方）で固定する。

### 決定2: `CostCalculator` へ内訳版を**非破壊で追加**し、既存関数はその合計を返す

```csharp
public readonly record struct OneWayCostBreakdown(decimal Commission, decimal FxSpread) { decimal Total => …; }
public static OneWayCostBreakdown EstimateOneWayCostBreakdown(TradingAssumptions, Market, decimal);
public static decimal EstimateOneWayCost(…) => EstimateOneWayCostBreakdown(…).Total;   // 既存の署名は不変
```

🔴 **式を 2 か所に書かない。** 内訳版を別式で書くと、内訳の合計と費用合計が一致しなくなる——
**しかも両方とも「それらしい数字」なので気付けない。** 既存の呼び出し元（判断時の事前見積り・リスク判定・
事後集計）は**1 行も変えない**（戻り値が 1 円も変わらないことをテストで固定する）。

**`OneWayCostBreakdown` は諸費用の区分を持たない。** 前提条件が値を持っていないものを 0 の列として
持つと、「諸費用 0 円が計上された」と読める形が構造的に作られてしまう。

### 決定3: 「諸費用」は `**未供給**` と描き、**費用合計が過小である**ことを凡例へ書く

**0 と書かない**（決定の理由は上記「検討した選択肢」）。あわせて凡例で
「全体前提条件に設定点が無く、概算費用関数も手数料と為替スプレッドしか計算していない——
**費用合計は諸費用のぶんだけ過小である**」と明記する。**計画が定義した費用合計（手数料＋諸費用＋為替
スプレッド）と、実装が出している費用合計は別物である**——それを黙って同じ名前で出さない。

### 決定4: 費用率の分母は「実現損益（税引前・費用前）」とし、**分母 ≤ 0 は「算出不能」**と描く

- **本文に分母を併記する**（`5.0%（費用合計 +100.00 USD ÷ 実現損益〔税引前・費用前〕 +2,000.00 USD）`）。
  計画に定義が無く実装が定めたものなので、**読み手が定義を目で確認できる形でしか出さない。**
- 🔴 **負・0 の分母で割らない。** 割ると比率の符号が反転し、損失の週が「費用が少ない週」に見える。
  `**算出不能**` と描き、**`0%` とも `**未供給**` とも書かない**（既存の LLM 費用消費率と同じ語を使う）。
- **計画に無い定義なので planning へ環流した**（planning#535）。裁定が出たら本実装を追随させる。
  同 issue では**分子（費用合計）が計画の定義より過小である**こと（決定3）も併せて記録している。

### 決定5: 記録源が無い 3 項目（損切り執行・発注拒否・上限使用率）は**行ごと落とさず**、理由を項目ごとに書く

ADR-0030 決定3 と同じ理由である——**計画が求めた項目が出ていないことは、報告書自身に見えていなければ
ならない。** 3 項目とも `**未供給**` とし、**それぞれ別の理由**を子箇条書きで書く（まとめて 1 行にすると、
「どれも同じ理由で出ない」と読める）。**「0 件」とは書かない。**

### 決定6: 射程は週報 §5 のみ。月報 §2 は `AppendNotImplemented` のまま残す

ゴールデンの差分が「新設 1 節の中身だけ」であることをレビューで機械的に確認できる状態を保つ
（IADR-0291 決定5・IADR-0301 決定7 と同じ理由）。**既存の §4・§6 の番号は動かさない**（ADR-0030 決定1・決定2）。
**月報 §1 の「費用合計 / 費用率」も本 PR では触れない**（同じ分母定義が要るが、月報のゴールデンが動く）。

## 理由

- **内訳の合計が §1 と一致しないことは、報告書の中で最も見つけにくい壊れ方である**（IADR-0301 と同じ）。
  だから「同じ費用関数・同じ帰属から数える」ことを、純関数と出口の両方でテストに固定する。
- **未供給・0・算出不能は 3 つとも別の事実である。** 本節はその 3 つが同時に出る初めての節であり
  （諸費用＝未供給／為替スプレッド 0＝事実／費用率＝算出不能）、潰すと読み手は費用を過小に見積もる。
- **定義を発明したことを隠さない。** 費用率の分母は実装が決めたものなので、本文に分母を併記し、
  計画へ環流したうえで裁定を待つ。

## 結果

- 良い影響:
  - 週報 6 節のうち 5 節が実体になった（残るのは無し——§1〜§6 すべてに中身が出る）。
  - **費用の内訳が読める**ようになり、手数料と為替スプレッドの比が週ごとに追える。

- 悪い影響・トレードオフ:
  - **費用合計は諸費用のぶんだけ過小である**（凡例で明示しているが、数値そのものは直らない）。
  - **費用率の分母が計画の定義と一致している保証が無い**（裁定待ち）。
  - 節の半分（1 行目の 3 項目）が `**未供給**` であり、情報量は計画が期待した水準に達していない。
- フォローアップ:
  1. **月報 §2 週別・市場別の内訳**（#615 スライス c）。**#615 はここでは閉じない。**
  2. **月報 §1 の「費用合計 / 費用率」**が `（データ連携後）` のまま残る。分母の裁定と同時に埋める。
  3. **損切り執行件数・発注拒否件数・上限使用率**の記録源。3 つとも本サービスの外に無い。
  4. **取引諸費用**の費用関数への算入（計画 `05_trading-assumptions` §2 が **要確認** のまま）。
