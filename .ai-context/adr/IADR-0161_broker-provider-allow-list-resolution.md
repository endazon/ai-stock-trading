## コンテキストと課題

計画 FR-20 に 2026-08-07 の裁定が入り、次の 3 点が明記された（質問票 第 13 回 Q5・Q6・補問 Q14）。

> **(1)** 設定は保存できるが、発注は段階が実弾を既定とするまで拒否する。Stage 1 のまま実弾を選んでも
> 発注は行われない。**この旨を SC-02 の警告モーダルにも含める。**
> **(2)** 確認文字列「REAL」の照合は、前後空白のみを除いた完全一致とし大文字小文字を区別する。
> **(3)** 発注先の初期値は内蔵 `paper` とする。**設定ストアの旧行（本項目を持たない場合）も同じ既定へ落とす**
> （「読めない行は実弾」に倒れないようにするため）。

実装の現況を調べたところ、**(1) の発注拒否と (2) の照合規則は既に成立していた**（`RiskEvaluator` の
`StageProhibitsLiveTrading`／`BrokerProviderChange` の `StringComparison.Ordinal`）。裁定はこれらを追認したものである。
残る欠陥は 2 つであった。

### 欠陥1（主眼）: 発注先の読み取りが deny-list である

設定ストアは**単一行の JSON**（`risk_settings.Json`）であり、読み取りは
`dto.BrokerProvider ?? BrokerProvider.InternalPaper` だった。これは「`null` だけを弾く」**deny-list** であり、
それ以外の異常値は素通りする。

| 永続行の値 | 是正前 | 裁定が求める結果 |
| --- | --- | --- |
| キーが無い（旧行）・`null` | `InternalPaper` | `InternalPaper` |
| `7`（未知の序数） | **`(BrokerProvider)7`** がそのままドメインを流れる | `InternalPaper` |
| `"MOOMOO REAL"` / `true` / `{}` | **`JsonException`** で設定行**全体**が読めなくなる | `InternalPaper` |

未知の序数は「今は実弾ではない」ため直ちに実弾を撃つわけではない。**しかし「今は当たらない」ことを
安全性の根拠にしない**——4 値目（例: 別ブローカの `REAL`）が末尾へ足された日に意味が変わる。
計画が「読めない行は実弾」という表現をわざわざ使ったのは、この形の失敗を名指しするためである。

### 欠陥2: 画面が「発注されない」ことを言っていない

SC-02 の警告モーダル②は「この組み合わせは段階ゲート…を飛ばしています」としか書いていなかった。
これは**裁定と逆に読める**——「飛ばせる」＝実弾で発注が始まる、と読めてしまう。
実際には 1 件も発注されない。計画はこの誤読（「同意したのに 1 件も発注されない＝壊れている」）を
名指しし、画面へ出すことを義務づけた。

## 決定

### 決定1: 発注先の解決は allow-list（`BrokerProviderResolution`）とし、既知の 3 値の明示一致だけを受理する

`Shared.Contracts/Trading/BrokerProviderResolution.cs` を「どの値が既知か」の**単一情報源**とする。

- `Default = BrokerProvider.InternalPaper`（**外部へ一度も発注しない唯一の値**）。
- `Resolve(BrokerProvider?)` / `Resolve(string?)` は 3 値の明示一致だけを返し、**それ以外はすべて `Default`**。
- 文字列側は**前後空白のみを除いた完全一致（`Ordinal`）**。`"MOOMOO REAL"` / `"moomooreal"` は一致しない
  （(2) の「REAL」照合と同じ規律を、値の解決にも適用する）。

**`Enum.IsDefined` で置き換えてはならない。** それは「enum に書いてあるか」を見るものであり、
「本規則が承認したか」ではない。4 値目を足した瞬間に未検討の値が黙って通る。
形は [IADR-0105](IADR-0105_backtest-historical-bar-source.md) の `HistoricalBarSourceFactory.ResolveProvider`
（未知の provider はすべて no-op）に揃えた——**本リポジトリで繰り返し出ている欠陥類型に対する既定の型**である。

### 決定2: 旧行はマイグレーションで書き換えず、読み取り時に allow-list が既定を与える

設定は単一行 JSON であり、**DDL 上の列を足さない**。「既存行に列を足す」に相当するのは JSON へキーを
足すことであり、**旧行はキーを持たないまま残る**。したがって既定値は**読み取り時に**与える。

- `SettingsDto.BrokerProvider` は `BrokerProvider?` の省略可能パラメータ（既定 `null`）。
  キーが無ければ `null` のまま allow-list へ入り `Default` になる。
- `BrokerProviderJsonConverter` が**どのトークンが来ても例外を投げず** allow-list を通す
  （数値／文字列／`null`／それ以外〔真偽値・オブジェクト・配列〕を明示的に扱う）。
- 書き込みは**現行どおり数値の序数**。ワイヤ形式を変えると旧版が読めなくなる。

**「読めない行は例外」も採らない。** 例外はフェイルクローズに見えるが、実際には設定行**全体**
（統制値・ガード設定・段階）が失われ、`GetCurrent` が 500 を返してリスク判定そのものが動かなくなる。
裁定は「同じ既定へ落とす」と明言しており、そちらへ従う。

### 決定3: 読み取りは黙って倒し、書き込みは拒否する（非対称は意図的）

`BrokerProviderChange.Evaluate` の未定義値検査は `BrokerProviderResolution.IsKnown` を通す（単一情報源）が、
**振る舞いは従来どおり `UnknownProvider` での拒否**である。

- **読み取り**（既に書かれてしまった行）: 黙って内蔵 `paper` へ倒す。読めない行を実弾にしないため。
- **書き込み**（これから書く値）: 拒否する。黙って倒すと「実弾を選んだのに paper になった」という
  説明のつかない状態遷移が生まれ、利用者が選んだ値と保存された値が食い違う。

### 決定4: 「段階が実弾を既定とするまで発注は行われない」旨を SC-02 に出す。ただし段階が実弾なら出さない

警告モーダルと一覧側の警告の**両方**に出す（モーダルは裁定の名指し。一覧側はモーダルへ進まない利用者にも届かせるため）。

- 条件は既存の `skipsStageGate`（＝切替先が実弾かつ段階の既定が実弾でない）と**同一**である。
- **段階が既に実弾（Stage 2 / 3）のときは出さない。** その場合は実際に発注されるため、同じ文言は**嘘になる**
  （狼少年にもなる）。「含める」を無条件と読むと、正しい状態で誤った警告を出すことになる。

### 決定5: 拒否理由は新設しない

Stage 1 のまま実弾を選んだ状態の発注は `StageProhibitsLiveTrading`（既存・クラス B）で止める。
**ADR-0016 決定10 の規律**（原因も解除条件も異なるものだけを分ける）に照らして本件は同一である
——原因＝段階が実弾を既定としない／解除条件＝段階の昇格。理由コードを足すと監査集計・通知文言・
画面の対応表がすべて分岐し、**同じ事象が 2 通りに数えられる**。

代わりに、**「保存は受理される」と「発注は拒否される」を 1 つのテストで同時に固定する**
（`Stage1LiveProviderOrderRejectionTests`）。保存側と発注側のテストは別々に存在していたが、
**同時に成り立つことこそが裁定の内容**であり、片方だけを見ていると「保存できる＝統制が無い」
「発注が止まる＝保存できないはず」の 2 通りの誤読のどちらにも倒れ得る（画面は前者に倒れていた）。

## 検討した代替案

| 代替案 | 却下理由 |
| --- | --- |
| `?? 既定` のまま注記だけ足す | **コメントは実行されない。** 未知の序数・文字列は依然として素通り／例外になる |
| `Enum.IsDefined` で検査する | 「enum に書いてあるか」であり「承認したか」ではない。4 値目で黙って穴が開く |
| 読めない値は例外にする（厳格） | 設定行**全体**が失われリスク判定が動かない。裁定は「同じ既定へ落とす」と明言 |
| 発注先の列を DB へ切り出しマイグレーションで既定を埋める | 設定は単一行 JSON という既存構造（IADR-0012）を壊す。**読み取りの穴は塞がらない**（列でも未知値は入る） |
| 新しい拒否理由（例: `LiveProviderWhileNonLiveStage`）を足す | ADR-0016 決定10 の規律に反する（同一原因・同一解除条件） |
| モーダルの文言を無条件に出す | 段階が実弾のときは**嘘**になる。誤った警告は統制の信頼を落とす |

## 結果

- **良い点**: 発注先の解決点が 1 か所になり、未知の値が実弾側へ落ちる経路が構造的に消えた。
  設定行の一部が壊れても統制値ごと失われない。画面が「保存できる」と「発注できる」を区別して説明する。
- **悪い点 / トレードオフ**: 手編集で `"MOOMOO REAL"` と書いた運用者には、**黙って内蔵 `paper` になる**
  （警告ログを出していない——設定ストアの読み取りは高頻度であり、毎回のログは実質ノイズになる）。
  未知値が入っていること自体は SC-02 の現在値表示で内蔵 `paper` と見えるため気づける。
- **残余リスク**:
  - **`StageSettings.Mode`（段階の既定発注先）は allow-list になっていない。** 未知の序数が入っても
    `!= MoomooReal` となり実弾は止まる（安全側）が、構造で担保されているわけではない。
    裁定 (3) の対象は「発注先の初期値」＝現在の発注先の軸であり、範囲を広げなかった（`docs/blocked-tasks.md` へ登録）。
  - **文字列表現は本リポジトリの永続形式では現れない**（設定 JSON は数値で往復する）。手編集・外部ツール
    由来の行を想定した保険であり、実地で踏まれた事例はない。
  - **実弾は `LiveTradingGate`（閂 0）が起動時に止めている。** 本 ADR はその閂に触れていないため、
    ここで整えた段階ゲートの正しさは**まだ実地で観測できない**。
  - **E2E（Playwright）はサンドボックスでブラウザを取得できず未実行**。型検査のみ通している。
