# IADR-0247: スクリーニング入力の縮退順序を純関数で固定し、保護対象は型として削れない

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（起票 #337）

## 起点・関連

- 関連する計画書 ID: FR-02・FR-04・FR-06（月報の件数記載）・FR-11（記録）・ADR-0003
- 計画の一次情報: 06_technical/01「判断の二段化」（利用者裁定 2026-08-02・planning#53 で縮退順序を確定）
- 関連する実装仕様書: [`20260828_337_trading-cycle-and-screening.md`](../specs/20260828_337_trading-cycle-and-screening.md)

## コンテキストと課題

`claude-haiku-4-5`（スクリーニング層）はコンテキスト 200K であり、監視銘柄・材料の増加で入力が上限に
当たり得る。計画は縮退の順序を確定した—— ① 銘柄分割（材料は減らない）→ ② RAG 参照を削る →
③ ニュース・開示を古い順・関連度の低い順に削る。**確定した日報の方針と当日の市況・価格データは
削らない。上位モデルへの退避は採らない。切り詰めの発生は記録し月報に件数を記載する
（分割と切り詰めは分けて数える）。**

実測では縮退の概念そのものが無く、一次スクリーニングのプロンプトは方針＋銘柄のみだった
（IADR-0072 決定2 が RAG をスクリーニングに載せないと決めていたため、超過も起きない代わりに
計画が想定する「材料つきスクリーニング」も存在しなかった）。

## 決定

1. **縮退順序は `ScreeningContextPlanner`（Domain 純関数）が単一情報源。** 入力は「共有保護分（方針）・
   銘柄ごとの保護分（市況・価格）・削減可能材料（RAG / ニュース。サイズ・発行時刻・関連度つき）・予算」。
   **保護対象は削減可能集合に現れない＝型として削れない**（`CollectionDegradation.ClosesAllowed` と同じ
   構造防御）。全段を使っても収まらなければ `UnresolvableOverflow` を立てて**削らずに**返す。
   **プランナはモデルという概念を持たない**——上位モデルへの退避という選択肢が構造的に存在しない
   （否定形テストで公開面に `Model` を含む名前が無いことまで固定）。
2. **分割と切り詰めは別カウンタで返す**（`SplitOccurred` / `DroppedRagCount`+`DroppedNewsCount`）。
   月報の件数記載の単位（planning#53）をそのまま写す。
3. **材料の分類は出所タグで行う**（`ScreeningContextAssembler`）。市況源（`finnhub` / `moomoo`）と
   欠測の明示（`collection-status`）は**保護**（後者を削ると ADR-0020 が塞いだ「無言の空データ」が復活する）、
   `report`（過去の判断・振り返り）は段 2、それ以外（ニュース・開示・マクロ）は段 3。語彙は
   `RetrievalSourcePolicy.Default` と同一（新しい信頼の定義を作らない・ADR-0003 追補と同じ規律）。
4. **縮退制御は opt-in**（`Decision:ScreeningContextBudgetChars`。未設定＝従来プロンプト＝IADR-0072 決定2 の
   現行挙動）。有効時のスクリーニングは市況（保護）と縮退後の参考情報を載せる——**IADR-0072 決定2
   「RAG はスクリーニングに載せない」は、本構成が有効なときに限り本決定が置き換える**（費用は予算そのもの
   が抑える。決定2 の目的＝費用統制は予算で引き継がれる）。既定（無効）では決定2 のまま。
5. **発生は `ScreeningContextReduced` イベントで記録する**（監査台帳が保持・全イベント購読の
   カバレッジテストが強制）。通知は追加しない（計画の要求は「記録し月報に件数」であり、
   `InformationSourceDegraded` と同じ扱い）。**月報テンプレートへの描画は #338 の射程**
   （#336 が同じ線引きを確定済み。本 issue の到達点は台帳の種別 × 期間照会まで）。
6. **予算は文字数プロキシ**（200K トークンへの換算係数は実測待ち・運用構成で与える）。
   現行アーキテクチャは銘柄ごとに独立呼び出し（＝常に最大分割）であり、段 ① は構造的に満たされている。
   多銘柄バッチ化した場合に備えプランナは分割を実装・テスト済みだが、**呼び出し形の変更は行わない**。

［2026-08-28 追記 / #337］ **段 1 の詰め方を Next-Fit から First-Fit Decreasing へ改めた**（PR #561 の AI レビュー 🟢 指摘）。
初版は「現在のバッチにだけ入れ、入らなければ即座に閉じる」Next-Fit であり、**一度閉じたバッチの空きを二度と使わない**（近似比 2×OPT）。
バッチ数はそのまま LLM の呼び出し回数＝費用と待ち時間であり、**本 IADR の目的が費用統制である以上、詰めの弱さは目的に直接反する**。
実測例（共有 100・材料 0・予算 260・銘柄 150,150,10,10）: Next-Fit は 3 バッチ、FFD は 2 バッチ。

🔴 **決定 6（呼び出し形は変えない＝現行は銘柄 1 件固定）は維持する。** 変えたのはプランナ内部の割当だけである。
**並べ替えは割当を決めるためだけに使い、出力の順序には持ち込まない**——バッチ内は入力順、バッチ列は各バッチの最小添字順に戻す。
監視銘柄の並びが優先度を表す運用へ移っても、本型が黙って順序を入れ替えることはない（不変条件を 2 本のテストで固定し、変異試験で確認済み）。

## 結果

- 良い影響: 「静かに判断材料が減っていた」状態が構造的に起きない（削減は記録され、保護対象は削れない）。
- 残余リスク: `RetrievedContext` に発行時刻が無く、段 3 の「古い順」は現状**関連度順のみ**が実効
  （発行時刻 null＝最古扱いで先に削る保守側）。`KnowledgeHit` への発行時刻の伝搬は KB 契約の拡張であり
  別作業。予算の実値も実測待ち（既定は未設定＝縮退制御オフ）。

［2026-08-29 追記 / #568］ **上記の発行時刻の残余リスクは解消済み。** `KnowledgeHit` へ発行時刻を追加し、
`HttpKnowledgeBaseSearch` が platform 検索応答の ABAC 属性 `publishedAt`（`KnowledgeBaseWriterSink` が
書き込み側で既に載せていた値）を復元して供給する形で埋めた。段③のソート式自体（本 IADR の決定）は
無改修。詳細・設計判断は [IADR-0270](./IADR-0270_knowledgehit-published-at-supply.md) を参照。
**予算の実値が実測待ちである点は未解消のまま残る。**
