# IADR-0626: 第 2 要素の試行回数の制限と、2 サービスでの状態の共有

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: **Accepted**
- 日付: 2026-11-07
- 決定者: 利用者裁定（2026-11-07「稼働前にすべて直す」）／ Claude Code（起案・実装）

## 起点・関連

- 起点: クラウドへの移行の前の点検で、危険な操作の第 2 要素（IADR-0615）の試行回数の制限・失敗の通知・2 サービスでの共有・操作への結び付きが足りないと判定された（詳細は非公開。公開の場には書かない）。利用者は 2026-11-07 に稼働前に直すと裁定した。
- 前提: IADR-0615（TOTP を提供側で確かめる・7 操作・段で切り替える・決定 9 の「書き込みの直前だけ」）。IADR-0623（クラウドは段 2＝Enforce で始める）。
- 実装仕様書: [`.ai-context/specs/20261107_second-factor-attempt-limit.md`](../specs/20261107_second-factor-attempt-limit.md)

## コンテキストと課題

IADR-0615 の門は次の形だった。

- 状態（最後に受け付けた段・連続の失敗の数・停止の終わり）を**プロセスの中**に持つ（決定 8）。リスク管理と報告書で別々である。再起動で消える。
- 連続 5 回の失敗で 15 分止め、**止めるたびに失敗の数を 0 に戻す**。止める長さは延びず、上限も無い。
- 失敗と停止はログの Warning だけで、オーナーへ届かない。監査の記録にも残らない。
- 確かめた結果は操作の種類をログに出すだけで、対象（どの期間の報告書か・どの段階への昇格か）を持たない。使ったコードの記録はサービスごとなので、同じコードを 2 つのサービスで 1 回ずつ使える（IADR-0615 残る制約 2）。

6 桁のコードは前後 1 段で 3 つ受け付ける。止める長さが延びず上限も無いと、時間をかければ試行の回数に上限が無い。2 サービスで別に数えれば回数は倍になる。オーナーは試されていることに気付けない。

## 検討した選択肢

J-1（どこで共有するか）:

1. **リスク管理の DB に持ち、報告書はリスク管理へ問い合わせる（採用）** — 状態の持ち主を 1 つにする。報告書は既にリスク管理を同期で照会している（`risk-ledger` の HttpClient・サービスの身元のトークン・依存先の門と観測）。新しい通信の経路・NetworkPolicy・資格情報は要らない。
2. 共有の DB の表（両サービスが同じ表を読み書きする） — 報告書がリスク管理の DB へ接続することになり、Database per Service（ADR-0001）とサービスごとの DB の利用者へ分ける方向に反する。採らない。
3. 共有のキャッシュ（Redis 等） — 新しい基盤の部品が要る（基盤の変更）。採らない。

J-2（止め方）:

1. 固定の長さを繰り返す（従来） — 時間をかければ上限が無い。採らない。
2. **段階的に延ばし、上限で手動の解除まで閉じる（採用）**。
3. 一定回数で即座に手動の解除 — 正当なオーナーの打ち間違いで止まりやすい。採らない。

J-3（手動の解除の手段）:

1. **シークレットの作り直し（既存の `--rotate`）で解く（採用）** — SSH の経路だけで行える（Discord の経路では解けない）。上限に達したことは Discord の経路が奪われた疑いを意味するので、観測されたコードを無効にする作り直しが妥当である。新しい解除の口（攻撃の面）を足さない。
2. 解除の API を足す — Discord の経路（ボット）から届かない口を新たに作る必要があり、口そのものが攻撃の面になる。採らない。
3. DB の行を手で消す — 手順が DB の接続を要し、誤操作の余地が大きい。採らない。

J-4（操作への結び付き）:

1. **確かめに操作の種類と対象を渡し、受け付けた段を全操作・2 サービスで共有して 1 回だけ通す。結果（操作・対象）をオーナーへ知らせる（採用）**。
2. 提供側が要求ごとの ID を出し、ボットが画面に出し、オーナーが確かめて往復させる — 最上位の操作で取り違えを原理的に防げるが、ボットの画面と 7 操作の流れを作り直す。本変更の範囲外とする（フォローアップ）。

## 決定

1. **状態はリスク管理の DB の単一行 `owner_second_factor_state` に 1 つだけ持つ**（最後に受け付けた段・連続の失敗の数・止めた回数・停止の終わり・手動の解除の要否・最後に受け付けた操作と対象・シークレットの指紋・版）。読み・決め・書くは版（並行トークン）で守り、競合したら読み直す（上限 5 回）。門（singleton）は呼ぶたびにスコープを作る（要求の書き込みと混ぜない。使ったコード・数えた失敗は、その後に操作が失敗しても残す）。**コードとシークレットそのものは持たない**（指紋は SHA-256 の先頭 16 バイト）。
   - **報告書の 2 操作（報告書の確定・方針の確定）は `POST /risk-controls/owner-second-factor/verify` でリスク管理が確かめる**（サービスの身元だけ。ボット・利用者のロールを持つトークンは 403。報告書の 2 操作の外は 400）。報告書は `RiskManagement:BaseUrl` があればこの口を使い、無いとき（単体の実行・試験）だけプロセスの中の状態で確かめる。段（Audit / Enforce）は各サービスの構成のまま（値の形は変えない。values-cloud は Enforce のまま）。
   - 状態を読み書きできない・リスク管理へ届かない・知らない応答は、新しい結果 `Unavailable` とする。**Enforce は拒む**（閉じる向き）。Audit は記録だけ。
2. **止め方**: 連続 5 回の失敗（使い回しを含む。欠けは数えない＝IADR-0615 決定 3 のまま）で止める。止める長さは 1 回目 15 分、以後は倍（15・30・60 分）。**4 回目で時間では解かず、手動の解除（シークレットの作り直し）まで閉じる**。止めている間は照合しない（正しいコードも受け付けない・数えない）。停止の後の失敗の数は 0 から数え直すが、止めた回数は**成功まで残す**。成功で失敗の数と止めた回数を 0 に戻す。
   - 数値の根拠: 1 回の失敗で当たる確率は最大 3/10⁶。手動の解除までに試せるのは 20 回なので、1 つのシークレットあたり最大 6×10⁻⁵（従来は 1 日に 1 サービスあたり 480 回）。時間で解ける停止の合計は 105 分で、正当なオーナーの打ち間違いが 4 回続けて重なる（20 回の連続の失敗）ことは現実的でない。止めた回数を成功まで残すので、停止の明けを待って試し直しても回数は増えない。
   - 構成: `OwnerSecondFactor:MaxConsecutiveFailures`（既定 5）・`LockoutMinutes`（既定 15）・`ManualUnlockAfterLockouts`（既定 4）。chart の値は変えない（既定で効く）。
   - 手動の解除: `scripts/ast-owner-totp-enroll.sh --live --rotate`（クラウドは `--openbao` を併せる）。指紋が変わると状態は新しく始まる。**再起動では解けない**（状態は DB にある）。
3. **確かめた結果を `OwnerSecondFactorChecked` として発行する**（Verified・Invalid・Replayed・LockedOut。欠けと未構成は状態を変えないので発行しない）。監査は全件を記録する。通知は成功（操作と対象）・失敗（続けた回数）・停止の始まり（解ける時刻）・手動の解除まで閉じたこと（解き方）をオーナーへ知らせ、**止めている間の試行は知らせない**（連打で通知を溢れさせない）。イベントにコードは載せない。発行の失敗は確かめの結果を変えない（ログに残す）。
4. **確かめは操作の種類と対象に結び付ける**: 門は `Check(operation, target, code)` で、対象は記録・通知・状態に載る（kill switch の解除は `kill-switch`、再開は `trading-pause`、昇格は `stage:<段階>`、GFV 停止の解除は `good-faith-violations`、乖離の取り込みは `drift:<市場>:<銘柄>`、報告書・方針の確定は `report:<期間キー>@v<版>`）。受け付けた段は全操作・2 サービスで 1 つなので、**一度使ったコードは別の操作・別の対象・別のサービスでは通らない**。
5. IADR-0615 決定 9（門は書き込みの直前だけ）・決定 4（段）・決定 5（コードの運び方）・決定 6（シークレット）は変えない。

## 結果

- 良い影響: 時間をかけた試行に上限ができる。2 サービスで回数が倍にならない。再起動で数え直しにならない。オーナーは失敗・停止・コードの使われ方を Discord で知る。同じコードを 2 つのサービスで使えない。
- 悪い影響: 報告書の確定の第 2 要素がリスク管理の稼働に依存する（届かなければ Enforce は確定しない。止める向きの操作は影響しない）。確定のたびに同期の照会が 1 回増える（上限は `risk-ledger` の 10 秒）。成功のたびに通知が 1 件増える（7 操作は人の手で稀）。
- 残る制約:
  1. **乗っ取られたボットが、オーナーの入れたコードを先に別の操作へ使う取り違えは、TOTP では原理的に防げない。** 先に使われた側が通り、オーナーの操作は「使用済み」で拒まれ、両方がオーナーへ通知される（気付ける）。要求 ID の往復（提供側が提示した要求とだけ突き合わせる）はフォローアップ。
  2. 停止はわざと失敗させてオーナーの解除・再開を妨げることにも使える（IADR-0615 残る制約 3 と同じ）。上限まで進めばシークレットの作り直しが要る。止める向きの操作には影響しない。
  3. 報告書の確定は、門の callback（同期）の中で同期にリスク管理を待つ（ASP.NET Core に同期文脈は無い。上限は HttpClient の Timeout）。
  4. 確かめの口はサービスの身元（`trading-service`）なら呼べる。どのサービスが呼んでも同じ状態で数えるので、試行の回数は増えない。呼べるクライアントを報告書に限る（azp の一覧）のは、サービスごとのクライアントの整理の後。

## フォローアップ

- 最上位の操作（昇格・kill switch の解除）の要求 ID の往復（提供側が要求を提示し、ボットの画面に対象を出し、確かめを要求に結び付ける）。
- 確かめの口を呼べるクライアントの一覧（azp）。

## ［2026-11-07 追記］Enforce で宛先が無いときは閉じる・報告書はシークレットを読まない

- 報告書は、段が Enforce で `RiskManagement:BaseUrl` が無い・読めないとき、プロセスの中の状態へ落とさず `Unavailable` で危険な操作を拒む（落とすと失敗の数が 2 サービスで別々になり、上限が実質 2 倍になる）。Audit・Off は従来どおり（警告ログとプロセスの中の状態）。
- values-local・values-cloud の報告書は宛先（`RiskManagement__BaseUrl`）を持つので、Secret `ast-owner-totp` の参照を外した（照合はリスク管理だけが行う）。既定の values.yaml は報告書に宛先が無く Audit なので、参照を残す。
- `Unavailable`（リスク管理が状態を読み書きできない）も `OwnerSecondFactorChecked` で流す。監査は全件、通知は続いた 1 回目だけ（`UnavailableStreak`）。**残る制約 5: メッセージも出せない障害（DB とブローカの両方）ではログだけになり、報告書の側の `Unavailable`（リスク管理へ届かない）もログだけである**（オーナーは Discord の拒否の応答とログで気付く）。
- 報告書は欠けたコードも持ち主へ問い合わせ、持ち主の判定（停止中は `LockedOut`、そうでなければ `Missing`）に揃える。持ち主は欠けを数えないので状態は変わらない。持ち主へ届けられない構成の門は、欠けも含めて `Unavailable` を返す。

## ［2026-11-07 追記 / IADR-0637］残る制約 4 を改めた（確かめの口は報告書のクライアントだけ）

- 確かめの口（`POST /risk-controls/owner-second-factor/verify`）に口の名前 `risk-controls.owner-second-factor.verify` を付け、既定の一覧（`ServiceCallerNames.DefaultCallers`）で
  報告書のクライアント（`ai-stock-trading-svc-report`）だけを許した（段 `Auth:ServiceToken:Mode=Enforce` のとき。ほかのサービスのクライアントは 403）。
- 🔴 **例外: 移行の段（`Auth:ServiceToken:LegacyClients` に旧の共有クライアント `ai-stock-trading-svc` が在る間）は除く。** 旧の共有クライアントは口の名前と一覧を見ずに
  サービスに開いたすべての口を通るので、確かめの口も通る。旧の共有クライアントの資格は 7 つのサービスが持っていたため、その間は**残る制約 4 は実質残る**。
  values-cloud の初回は移行の段である。解けるのは、取引ユニットの手順書（サービスごとの機密クライアントの Runbook）の段 3 で `legacyClients` を外した後である。
- 既定（Off）・ローカル・CI は従前どおり（サービスのロールなら呼べる）。上の「残る制約 4」「フォローアップ（azp の一覧）」は、クラウドの段 3 の後に解ける。
