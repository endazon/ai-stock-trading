# IADR-0145: 権限拒否を可修正性で分類し、失敗判定を A（直せる拒否）に限定する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-08-05
- 決定者: endazon（利用者裁定「②はベストを選択」）/ Claude Code（起案）

## 起点・関連

- 対象 Issue: [#391](https://github.com/endazon/ai-stock-trading/issues/391) やること 3（「拒否 1 件でジョブが落ちる設計を見直すかを判断する。**トレードオフを実装 ADR に残すこと**」）
- 作業仕様書: [20260805_391_ai-review-allowlist](../specs/20260805_391_ai-review-allowlist.md)
- 対象: `scripts/check-permission-denials.js`

## コンテキストと課題

### 起票時の前提が 1 つ古い

**#391 は「拒否が 1 件でもあるとジョブが落ちる構成」と書いているが、これは現状と異なる。** `check-permission-denials.js` は既に段階ポリシーを持ち、**既定は「4 件超、またはターン数の半分以上」で失敗**する。拒否 1 件では落ちない。

実際に失敗した run（`30998236984`）を確認したところ、原因は **5 件**でしきい値 4 をわずかに超えたことであった。内訳も issue の想定（npm / dotnet ef）と違い、`git -C <絶対パス>` 2 件と MCP ツール 3 件であった。

### 段階ポリシーが残した本当の問題

段階ポリシーは「探索的な少数の拒否では落とさない」という妥当な妥協だが、**性質の違う 2 種類の拒否を同じ土俵で数えている**。

| 種別 | 例 | 許可リストで直せるか |
| --- | --- | --- |
| **A. 許可漏れ** | `npm ci` / `dotnet ef` / `git ls-files` / MCP ツール | ✅ **直せる** |
| **B. 構文上ありえない形** | env 前置き・リダイレクト・プロセス置換・ループ・`cd`・`git -C <絶対パス>` | ❌ **原理的に直せない** |

B はレビュープロンプトが既に「試みる必要はない」と明示しているが、**モデルが試みてしまえば計上される**。結果として次のジレンマが生じる。

- **しきい値を下げる / 維持する** → 許可リストを完璧にしても B で偽の赤が出続ける。「権限拒否の赤は無視してよい」という学習を生み、A の検出が実質的に無効化される。
- **しきい値を上げる** → A の検出が鈍る。5 件の許可漏れが素通りする。

**#391 が「維持すると偽の赤が出続け、緩めると許可漏れに気づけなくなる」と書いたトレードオフは、2 種類を分けていないことから生じている。** しきい値の上下では解けない。

## 検討した選択肢

1. **しきい値を上げる**（例: 4 → 8）— A の検出が鈍る。許可漏れが 5〜8 件でも素通りする。今回の実測（A 3 件 + B 2 件）のような混在では、A だけが増えたときに気付けない。
2. **ゲートを外す**（拒否では失敗させない）— 本検査器を入れた目的（レビュー未実施を見逃さない）が消える。元障害は「17/21 ターンが拒否で潰れ、レビュー本文が 1 文字も無いのに CI は緑」であった。
3. **B をプロンプトで根絶する** — 既に試みて残っている。プロンプトには 3 巡分の実測に基づく禁止事項が列挙済みであり、それでも出る。モデルの挙動に依存する対策は保証にならない。
4. **可修正性で分類し、失敗判定を A だけで行う** — トレードオフの原因そのものを除く。

## 決定

**選択肢 4 を採用する。拒否を A（許可リストで直せる）/ B（直せない）に分類し、失敗判定は A の件数のみで行う。**

### 決定 1: 分類は「許可リストのエントリを書けば通るか」で決める

B と判定するのは次の形である。いずれも**許可リストの前方一致では表現できない**か、**設計上許可してはならない**ものである。

| 形 | 理由 |
| --- | --- |
| `VAR=1 cmd` | 先頭トークンが `VAR=1` になり前方一致に当たらない |
| `> file` / `>> file` | レビュー用は書き込み手段を持たない（設計） |
| `<(…)` / `$(…)` / バッククォート | 中のコマンドが許可済みでも拒否される |
| `for` / `while` / `if` / `case` | 先頭が予約語になり許可リストで表現できない |
| `cd` | 許可リストに無く、後続が許可済みでも先頭で落ちる |
| `git -C <絶対パス>` | `Bash(git -C:*)` の一括許可は**書き込み系まで通る**ため禁止済み |

Bash 以外（MCP ツール等）は名前を書けば必ず通るため、**常に A** とする。

### 決定 2: しきい値（既定 4）は据え置く

分母から B が抜けるぶん、**A に対しては実質的に厳しくなる**。今回の実測（A 3 件 + B 2 件 = 5 件）は、従来なら失敗、分類後は成功である。**許可リスト是正後に残るのは B だけになる**ため、これが正しい挙動である。

新しい余裕幅を発明しない（既存値を動かさない）ことで、「しきい値をいじって赤を消した」形にならないようにする。

### 決定 3: 迷ったら A（直せる）へ倒す

**B と誤判定すると、本物の許可漏れが分母から抜けて検出できなくなる。** 逆に A と誤判定しても、出るのは従来どおりの赤である。**誤りの向きが非対称**であるため、分類器は保守的に作る。

内訳を特定できない経路（`permission_denials_count` しか無い版）では、**全件を A として扱う**。分類できないことを理由に失敗を免れると、本検査器が塞いでいる「見えずに緑」へ戻る。

### 決定 4: B も必ず可視化する

**失敗させないことと、見せないことは別である。** B の件数と理由の内訳を、アノテーションと実行サマリの両方へ必ず出す。

見せないと 2 つの害がある。**B が何件あるか誰にも判らなくなる**こと、そして**分類器が壊れて A を B と誤判定しても気付けない**ことである。既存の方針（「見えるが緑」と「見えずに緑」はまったく別物）をそのまま適用する。

### 決定 5: 否定形テストを正の確認と同数以上置く

分類器は**効きすぎる方向に壊れると CI が緑のまま気付けない**（A を B と誤分類すると赤が消えるだけで、症状が出ない）。したがって「A と分類されるべき形」のテストを、「B と分類されるべき形」と同数以上置く。

- B 判定 9 件 / **A 判定 9 件** / 失敗判定 5 件 / 実測 run の再現 1 件 / B の可視化 1 件
- 実測 run（`30998236984` の 5 件）を**そのまま再現するテスト**を常設する。分類の結果 A が 3 件になり失敗しないことを固定する。

## 影響

- **肯定的**:
  - 許可リストを是正すれば、**構文由来の偽の赤が構造的に出なくなる**。「拒否の赤は無視してよい」という学習を断てる。
  - A に対するゲートは**むしろ強くなる**（分母から B が抜けるため）。
  - `STRICT_PERMISSION_DENIALS=1`（1 件でも失敗）と `ALLOW_PERMISSION_DENIALS=1`（失敗させない）の既存の逃げ道は維持する。
- **制約 / 残余リスク**:
  - **分類器が誤ると検出が鈍る方向に壊れ得る。** 決定 3（迷ったら A）と決定 5（否定形テスト）で抑えるが、**新しい「原理的に直せない形」が現れたときは B に分類されず偽の赤が出る**。そのときは分類器へ足す（症状が出るぶん、逆向きの誤りより気付きやすい）。
  - **B が多発していても失敗しない。** プロンプトが効いていない状態を赤では検知できない。可視化（決定 4）に依存する。
  - 分類はコマンド文字列の静的解析であり、**実際に拒否された理由と一致する保証は無い**（実行ログに理由は残らない）。`cd x && npm ci` のように A と B が混在する鎖は B と扱う（鎖全体が実行されないため）。
