## コンテキストと課題

moomoo の模擬取引は指値・成行しか受け付けず（`OrderType_Stop` は拒否・当日限り）、S0 では SIMULATE に建玉が残らない。
S2 は建玉を残すが損切りが起きない。S1 は「市場監視の到達検知（60 秒周期の `StopLossTriggered`）を発注執行が購読して成行で決済する」
ことで、ペーパーでも損切り決済までを観測可能にする。ADR-0040 は S1 が 2026-07-31 の裁定で消した**二重決済の経路を SIMULATE に戻す**
ことを悪い影響として明記しており、実装の中心課題は**二重決済を作らないこと**である。

決めるべきは (a) ソフトウェア逆指値をどこに永続化するか、(b) 市場監視は S1 の損切りラインを知っているか、(c) 到達をどう冪等に決済へ変えるか
（市場監視は価格が戻るまで毎巡回再発火する・メッセージは再配送される・ガードと並行し得る）、(d) 部分約定・未約定の扱い、
(e) ガードと手法混在、(f) 監査・通知・台帳、(g) 再起動耐性、である。

## 検討した選択肢

1. **(a) 新テーブル `software_stop_orders`** — 意味は分かれるが、ガードの巡回・EF ストア・インメモリ実装・テストの足場を二重に持つ。
   手法混在の按分では両テーブルを突き合わせることになる。**却下**。
2. **(a) 既存 `protective_stop_orders` に機構列を足す**（採用）— 1 エントリー＝高々 1 保護の主キーがそのまま効き、ガードは同じ巡回で両方を見られる。
3. **(b) 市場監視へ手法と損切りラインを別経路で供給する** — 不要と判明した。市場監視は台帳（リスク管理 `GET /risk-controls/open-positions`）の
   建玉を評価し、損切りラインは承認 Intent の `StopLossPrice`（IADR-0035）である。S1 の承認も `StopLossPrice` を必ず持つ（無ければ見送り）。**変更しない**。
4. **(c) リスク管理が到達を受けて Close の `OrderApproved` を出す**（旧 IADR-0015 の形）— 保護記録（手法）を持つのは発注執行だけであり、
   S0 / S2 の建玉にまで決済を出す危険がある。発注執行の購読で閉じる。**却下**。
5. **(e) 損切り到達の通知に建玉ごとの手法を載せる**（台帳の承認行に手法を保存 → open-positions → 市場監視 → `StopLossTriggered`）—
   3 サービスとリスク管理の migration を要し、台帳は銘柄単位で最新エントリーの値しか持たない（混在時に誤る）。**本 IADR では採らない**（決定 7）。

## 決定

1. **永続化**: `protective_stop_orders` に `Mechanism`（`StopLossExecutionMethod`・非 null・既定 0＝S0）・`TriggeredAt`（null）・`TriggeredPrice`（null）を足す
   （migration `AddSoftwareStopColumns`。既存行は S0 として読まれる）。S1 の行は `StopOrderId=""`、`StopDecisionId=ProtectiveStopIds.SoftwareStopId(entry)`、
   `TriggerPrice`＝承認の `StopLossPrice`、`Quantity`＝承認数量、`Attempt`＝**送った決済の試行数**（0 始まり）。
   `IProtectiveStopOrderStore.FindActiveSoftwareStops(symbol, market, entrySide)` を足す。
2. **解決**: `StopLossMethodPolicy` は S1 を `StopLossMethodDisposition.SoftwareStop` へ解決する（S0→S0／非 SIMULATE→拒否／空売り→S0／S2→免除 の順序は不変。
   S3・未知だけが従来のフォールバック）。
3. **発注時**（`OrderExecutionAppService`）: S1 はブローカーの逆指値能力（成行決済に使う `IProtectiveOrderBroker`）と保護記録ストアを要し、
   欠ければ見送る（`StopOrderUnsupported`）。🔴 **エントリーを送る前に行を Active で保存する**（行が無ければのみ）——送った後に保存すると
   「建玉はあるのにソフトウェア逆指値が無い」窓ができる。送った結果が生きていれば（Accepted / PartiallyFilled / Filled）`SoftwareStopArmed` を発行し、
   終端失敗・見送り（接続断）なら行を Completed にする。送信後の不明（例外）は行を Active のまま残す（ガードが扱う）。
4. **到達**（発注執行の新ハンドラ `StopLossTriggeredHandler` → `SoftwareStopExecutor.OnTriggeredAsync`）: 銘柄・市場・建玉方向が一致する Active な S1 行のうち、
   **行の作成が検知時刻以前**で、**検知時の価格が行自身の損切りラインに達している**（買い建て: 価格 ≦ ライン）ものだけを対象にする。
   🔴 **決済の前に到達を永続化する**（`TriggeredAt` / `TriggeredPrice`。既に記録済みなら上書きしない）。以降の決済が据え置きになっても、
   次の到達を待たずにガードが再試行する。**一度到達したら価格が戻っても決済する**（FR-10: 損切りラインは到達で発動する。遅れて届いた到達も同じ）。
   行自身のラインで判定するのは、台帳の損切りラインが銘柄単位で最新エントリーの値に丸められるため（同一銘柄の別エントリーを巻き込まない）。
5. **決済**（`SoftwareStopExecutor.TryCloseAsync`。ハンドラとガードが共有）:
   1. エントリーの記録（`executed_orders`）があり**未終端**ならブローカーで取り消し、再照会して**終端になるまで決済しない**（据え置き）。
      約定 0 で終端 → 行を Completed にし、自分が取り消したなら `SoftwareStopExecuted(EntryCancelled)` を出す。記録が無い（送信後不明）なら行の数量を上限に扱う。
   2. 建玉を照会し（null＝不明は据え置き）、**決済数量＝min(エントリーの約定数量, 建玉残)**。建玉残は同じ銘柄・方向の建玉から
      **手法の異なる Active 行の数量を差し引いた値**（決定 6）。0 以下なら決済せず Completed（手動決済等で既に無い）。
   3. `attempt = Attempt + 1`、`CloseDecisionId = ProtectiveStopIds.SoftwareCloseDecisionId(entry, attempt)`。
      🔴 **二重決済の防止は 3 重**: (i) 同じ DecisionId の発注記録があれば再送せずその結果で扱う、(ii) 送る前に予約表で DecisionId を確保し
      （IADR-0057 の一意制約）、確保できなければ送らない（ハンドラとガードの並行・再配送）、(iii) 行が Completed なら候補にならない。
   4. 成行を送る（参照価格＝検知時の価格）。接続断（`BrokerUnavailableException`）は予約を解放して据え置き。その他の例外は予約を残して据え置き
      （届いたか不明＝同じ DecisionId では再送しない。滞留予約はリコンサイルの領分）。
   5. 受理（Accepted / PartiallyFilled / Filled）→ 記録を保存し予約を確定、行を Completed、`SoftwareStopExecuted(ClosePlaced)`（決済 Intent 同伴）。
      約定は既存の約定追跡（IADR-0113）が `OrderExecuted` で台帳へ届ける。
   6. 拒否（Rejected / Cancelled / Expired）→ 記録を保存し `Attempt` を進める。**到達 1 回につき 3 試行で打ち切り**、到達の記録を外して
      `SoftwareStopExecuted(CloseRejected)`（Critical・手動決済を促す）。次の到達で再開する（市場監視は価格が戻るまで再発火する）。
      moomoo の模擬取引は時間外の成行を受け付けない可能性があり、無制限に送ると拒否注文を積み続けるため。
6. **ガード**（`ProtectiveStopGuard`）: **S1 行はブローカーの注文照会をしない**。到達済みなら決定 5 を再試行、未到達なら
   「エントリーが約定 0 で終端」または「建玉残（決定 5-2 の按分）が 0 以下」で Completed、それ以外は据え置く。
   **S0 行の建玉残もソフトウェア逆指値の約定数量（記録が無ければ 0）を差し引いて判定する**（#826 項目 3 の S1 側）——差し引かないと
   S1 の建玉が S0 の逆指値を生かし続け、建玉消滅後に残った逆指値が反対建玉を生む。S1 が無い構成（実弾・S0 のみ）では差し引く量が 0 で**挙動は不変**。
   S2 は記録を持たないため按分に入らない（残余リスク）。
7. **通知文**（#826 項目 2）: 損切り到達を検知する市場監視は建玉ごとの手法を知らない（選択肢 5 を採らない）。`StopLossTriggered` の通知と
   リスク管理の検知ログは「S0＝ブローカー側の逆指値が決済／S1＝システムが成行で決済（別途通知）／S2＝誰も決済しない（手動で決済）」を
   **列挙**する文へ改める。S1 の決済・拒否は `SoftwareStopExecuted` の通知が建玉を特定して伝え、S2 は免除の通知が建玉ごとに明示済みである。
8. **契約**: 新イベント 2 種（既存イベントの形は変えない）。
   - `SoftwareStopArmed`（EntryDecisionId, Symbol, Market, Side, ProductType, Quantity, StopLossPrice, Provider, OccurredAt）— 監査・通知（Warning:
     「システム停止中は決済されない」を明記）。
   - `SoftwareStopExecuted`（EntryDecisionId, Symbol, Market, Outcome, Quantity, StopLossPrice, TriggeredPrice, Attempt, CloseDecisionId?, CloseOrderId?,
     CloseIntent?, OccurredAt）・`SoftwareStopOutcome`（`ClosePlaced=0` / `EntryCancelled=1` / `CloseRejected=2`）— 監査・通知
     （ClosePlaced / EntryCancelled は Warning、CloseRejected は Critical）・リスク管理の台帳結線（ClosePlaced のとき `AppendApproval`。冪等は DecisionId）。
9. **購読と再起動耐性**: 発注執行は `StopLossTriggered` を `ai-stock-trading.order-execution-service.StopLossTriggered` で購読する（IADR-0129 の共通ヘルパ。
   Wolverine 6.24.5 の RabbitMQ キューは既定で durable）。停止中に発行された到達はキューに残り再開後に届く。行は DB にあり、再起動後の到達・ガードの巡回が
   そのまま決済する。ハンドラは Wolverine の規約発見とビルド時 codegen に載り、依存（`SoftwareStopExecutor`）は構成を問わず登録する
   （建玉照会は moomoo 構成でだけ解決され、内蔵 paper では据え置きになる。S1 は内蔵 paper で選べない＝行ができない）。
   宣言 `pipeline.json` に段 `execute-software-stop` を足す（変換段: 到達 → 決済）。

## 理由

- **到達の永続化を決済より先に置く**のは、損切りの発動を「その時点で決済できたか」に依存させないためである。据え置き（接続断・建玉不明・取消待ち）を
  ガードの巡回（既定 30 秒）で拾えば、価格が戻って到達が途絶えても決済が失われない。
- **予約表の再利用**は、IADR-0057 が発注の at-most-once を既に保証している仕組みであり、新しい排他（行ロック・楽観並行）を足さずに
  ハンドラとガードの並行・再配送を塞げる。
- **未終端のエントリーを取り消してから決済する**のは、決済後に残りが約定すると無保護の建玉が生まれるため。終端を待つ間の遅延はガードの巡回 1 回分である。
- **数量を建玉と約定数量の小さい方にする**のは、手動決済・一部決済の後に全量を売ると反対建玉（空売り）を作るためである。

## 結果・残余リスク

- 良い影響: SIMULATE＋S1 で建玉が残り、損切りライン到達で成行決済まで観測できる。S0・S2・実弾の挙動は不変（S0 のガードは S1 行が無ければ差分 0）。
- **システム停止中は決済されない**（S1 の本質。ブローカー側に保護が無い）。`SoftwareStopArmed` の通知が明記する。
- **到達の遅延**: 市場監視 60 秒周期＋キュー＋（据え置き時）ガード 30 秒。損切りラインから価格が離れて約定し得る（成行）。
- **moomoo アダプタは送信後の SDK 例外を Rejected に丸める**（既存の挙動）。実際には届いていた場合、次の試行（別 DecisionId）が重なり得る。
  次の試行の前に建玉を照会し直すため、先の注文が約定済みなら数量 0 で止まるが、**未約定のまま滞留していると二重に出る**。SIMULATE 限定で頻度は低い。
- **即時約定で返った決済は約定追跡に載らない**（非終端だけを追跡する。S0 の保護喪失の手仕舞いと同じ既存の穴）。moomoo は発注応答を Submitted で返すため現状は起きない。
- **同一銘柄の S1 と S2 の混在**: S2 は記録を持たないため按分できず、S1 側の建玉が手動決済で先に消えていると S1 の決済が S2 の建玉を売り得る。
- **損切り到達の通知は建玉ごとの手法を示さない**（列挙文。決定 7）。手法の表示は #823。
- 市場監視は平日判定だけで時間外も到達を出す。時間外の成行拒否は決定 5-6 の打ち切りで抑える。

## ［2026-09-18 追記 / #820 の監査］同じ銘柄の複数行への配分と、エントリー記録が無い行の扱い

監査（フレッシュな文脈・PR #830）が 2 件の売り過ぎを実測した。**挙動を直した。決定 1〜9 の方針は変えない。**

1. **決定 5-2 を改める（配分）**: 行ごとに「建玉残」を上限にしていたため、同じ銘柄・方向の S1 行が同じ建玉を二重に
   主張した（実測: 10 株の行 2 件＋手動売却 5 株 → 20 株の決済 vs 保有 15 株＝反対建玉）。**同じ銘柄・市場・方向の
   Active な S1 行へ、記録の作成時刻（＝エントリーの発注順）→ EntryDecisionId の順に建玉残を配分する**
   （`ProtectiveStopNetting.AllocateSoftwareStops`）。配分は決定的で、ハンドラとガードのどちらから呼んでも同じになる。
   - 🔴 **順序に到達時刻を混ぜない**。1 回の到達を処理する途中で行へ到達を書き込むと順序が変わり、どの行にも
     持ち分が回らなくなる（実測で 2 件とも据え置きになった）。
   - 🔴 **発注済みで未約定の決済数量を差し引く**。建玉照会は決済が約定するまで減らないため、差し引かないと
     次の行へ同じ建玉をもう一度配分する（実測で 20 株になった）。窓は 1 日（当日有効の注文しか出さない）。
   - **持ち分が 0 の行は完了させず据え置く**。他行の決済で建玉が減れば次の巡回で持ち分が生まれる。完了させると
     保護のない建玉が残る。建玉そのものが無い（方向の純額が 0）ときだけ従来どおり完了する。
2. **決定 5-7 を足す（孤立行）**: エントリーの発注記録が無い行は、従来は**行の数量で決済していた**ため、同じ銘柄の
   別のエントリーの建玉を売った（実測: 孤立行＋実在の 10 株で 20 株）。**記録が無いあいだは 1 株も決済しない。**
   `SoftwareStopExecutor.DefaultOrphanGrace`（15 分）を過ぎても記録が無ければ、決済を出さずに行を閉じて
   `SoftwareStopExecuted(EntryMissing=3)` を発行する（通知・監査は Critical）。閉じないと毎巡回この行で決済を試み続ける。
   猶予は、送信と記録のあいだのクラッシュ窓・予約のリコンサイルが記録を補える長さに合わせた。
3. **記録済みの決済を配分より先に確定する**: 同じ試行の決済記録がある（クラッシュ窓）ときは、建玉照会も配分も行わず
   記録の結果で行を確定する。差し引きを先に効かせると自分の決済で持ち分 0 になり、確定できなくなる（実測）。

残る監査指摘（**本追記では直していない**）: 決済が受理後に取消・失効した場合の再武装、拒否の連発に対する待ち時間、
古い写しからの上書き（楽観並行）、無期限の据え置きの Critical 化。**#833 で扱う。**

## ［2026-09-18 追記（2） / #820 の 2 巡目監査］差し引きの単位を「建玉照会がまだ映していない決済」にする

1 巡目の是正（上の追記 1 の 3 点目「発注済みで未約定の決済を差し引く」）が**新たな売り過ぎと取りこぼしを作っていた**。
2 巡目の監査が再現テストで実測した。**挙動を直した。決定 1〜9 の方針は変えない。**

1. **S0 の数量を二重に引いていた（B1・損切りが黙って止まる）**: S0 の逆指値レグは本番では必ず
   `PositionEffect=Close` / `Accepted` の発注記録として残る。配分は「手法の異なる Active 行の数量」で既に
   S0 を引いており、そこへ未約定の決済としてもう一度引いていた。**S0 と S1 が同数なら S1 の決済が 1 株も出ず、
   無期限に据え置かれる**（Critical も出ない）。→ 差し引きの母集合から **Active な S0 行の `StopDecisionId` を除く**。
   - 受け入れ基準 8 のテストが緑だったのは、**本番に必ず在る S0 のレグ記録を置いていなかった**ためである。
     テストの配置を本番と同じにした（`BrokerStop` ヘルパ）。**存在しない状態を固定したテストは防御にならない。**
2. **即時約定した決済を差し引けていなかった（B2・売り過ぎ）**: ガードは 1 巡回に 1 回しか建玉を照会しない。
   先の行の決済が終端（`Filled`）で返ると、**古い建玉にも未約定一覧にも現れない**ため、後の行が同じ建玉を
   再配分された（実測: 保有 15 株に 10＋10＝20 株の決済＝反対建玉）。moomoo アダプタの `MapState` は
   `FilledAll → Filled` を返し得るので、「Submitted で返る」は観測であって保証ではない。
   → 差し引く単位を「未約定の数量」から **「建玉照会がまだ映していない数量」** へ改める。
   **建玉を照会した時刻**（照会の**前**に採る）をガードから配分へ渡し、その時刻より後に置かれた・動いた決済は
   **丸ごと未反映**とみなす。約定が建玉へ映るまでの遅れとして 30 秒の余裕を見込む。
3. **倒れ方は過大側（差し引き過ぎ）へ寄せる**。過大なら行が据え置かれ、次の巡回が新しい建玉を見て決済する。
   過小は反対建玉（空売り）を作り、取り返しがつかない。
   - ただし **拒否（`Rejected`）は 0 として扱う**——市場へ届いていない。差し引くと拒否のたびに持ち分が消え、
     決定 5-6 の再試行ができなくなる（テストが捕まえた）。
   - **反映済みの古い決済は引かない**。引くと持ち分が永久に足りず損切りできない（T-10-359 が固定）。
4. 決済の記録は非終端だけでは足りないため、`IExecutedOrderStore.FindClosesSince`（終端・非終端を問わず
   決済を**新しい順**に返す）を足した。新しい順に切るのは、打ち切りで**直近の決済**を落とさないため
   （落とすと売り過ぎ側へ倒れる）。

## ［2026-09-18 追記（4） / #820 の 4 巡目監査］決定 5-2 を配分方式から**残保護数量方式**へ改める

4 巡目の監査がブロッキング 4 件を出した。**うち BLK-1 は 3 巡目の是正（追記(3)）が作った回帰**である
（S1 の完了判定から差し引きを外した結果、自分の建玉を失った S1 行が不死化し、同じ銘柄の別エントリーの
**生きた S0 逆指値を毎巡回・恒久的に黙って取り消す**）。

**個々のバグではなく設計の問題であると判断し、持ち分の決め方ごと作り直す。決定 1〜4・7〜9 は変えない。
決定 5-2（決済数量の決め方）と決定 6（ガード）を本追記で改める。**

### 根本原因

ブローカーの建玉照会は**銘柄単位の純額**であり、どの建玉がどの保護記録のものかを区別しない。
それを**毎巡回ゼロから計算し直して**持ち分を決めていたため、規則をどう変えても
「売り過ぎ（反対建玉）」か「損切りが黙って出ない」のどちらかへ倒れた。

| 巡 | 是正 | その是正が作った欠陥 |
| --- | --- | --- |
| 1 | 行ごとの「建玉残」上限をやめ、行へ配分する（追記(1)） | B1（S0 のレグ記録で二重差し引き → S0 と同数なら決済が 1 株も出ない）・B2（即時約定した決済を取りこぼして売り過ぎ） |
| 2 | 差し引きを「建玉照会が映していない決済」へ（追記(2)） | B3（差し引きが対称で、S0 と S1 が同数だと双方から見て残 0 → 建玉が残ったまま保護が外れる）・B4（再発注済み S0 の前試行レグが除外漏れ） |
| 3 | 保護を外す判定を方向の純額だけに（追記(3)） | BLK-1（幽霊行が生きた S0 の逆指値を消す） |

**毎巡回引き直す限り、規則の調整では止まらない**——4 巡の実測がそれを示している。

### 改めた決定

1. **決定 5-2'（持ち分は状態である）**: `protective_stop_orders` に `RemainingProtected`（int?・null＝未確定）と
   `StalledNotifiedAt`（DateTimeOffset?）を足す（migration `AddProtectiveStopRemainingProtected`。**既存行は `Quantity`**）。
   値を動かすのは次の 3 つだけである。
   1. **確定**: エントリーの発注記録が**終端**になった時点で、残保護数量＝**エントリーの約定数量**。
   2. **自分の決済で減算**: 受理された決済の数量だけ減らす（決定的な `SoftwareCloseDecisionId` の試行と 1:1。
      試行番号を進める保存と同じ 1 回で減らすため、再入しても二度減らない）。
   3. **外部要因の減少の一度きりの割り当て**: 主張の合計が方向の純額を超えていれば、超過分を
      **作成時刻 → EntryDecisionId** の順に**古い行から**削り、**保存する**（＝削ったことの記録）。
      次の巡回は保存された値から始まるため、**持ち分が巡回ごとに揺れることが構造的に無い**。
2. **決済数量は残保護数量そのもの**。配分（`AllocateSoftwareStops`）と「建玉照会がまだ映していない決済」の
   差し引き（`UnreflectedCloseQuantity` / `IExecutedOrderStore.FindClosesSince` / `SnapshotLagAllowance` /
   ガードから渡していた照会時刻）は**撤去した**。**持ち分の計算に発注記録を一切使わない**ため、
   完了済み S0 行の取消済みレグで持ち分が食われる経路（BLK-2）が構造的に消える。
3. **行を完了させるのは残保護数量が 0 になったときだけ**（決定 6 の改定）。純額や他手法の主張では完了させない
   ——B3（建玉が残っているのに保護が外れる）と BLK-1（幽霊行の不死化）の両方がここで止まる。
   **部分的にしか決済できていない行も完了させない**（BLK-3）。残りは次の巡回・次の到達で決済する。
4. **ガードの評価順は S0 → 到達済み S1 → 未到達 S1**。
   - S0 を先にするのは、S1 の予算が「**この巡回の後も生きている S0**」の数量を引くべきだからである
     （約定・取消で役目を終えた S0 の数量を引くと B3 が再発する）。
   - 到達済みを先にするのは、未到達の行に持ち分を先取りされて**到達した損切りが出ない**のを防ぐため（BLK-4）。
5. **S0 行は「全部か 0 か」でしか削らない。** S0 の主張は**ブローカーに実在する逆指値の数量**であり、
   帳簿だけを部分的に削っても注文は縮まない——縮まない注文が建玉より大きいまま残ると、発火して反対建玉を作る。
   全部削られた S0 行はガードが**逆指値そのものを取り消して**完了させるので、帳簿と注文が一致する（#826 項目 3）。
6. **S1 の主張が 1 株も無い群には割り当てを行わない。** 割り当ての目的は S1 の持ち分を確定させることであり、
   S0 だけの群（実弾・S0 のみ）では従来の判定がそのまま働く。**S1 が無い構成で S0 の挙動は変わらない。**
7. **決定 9 の追加（無音の失敗を残さない）**: 到達済みなのに決済できない状態が猶予
   （`SoftwareStopExecutor.DefaultSettlementGrace`＝15 分）を過ぎたら、`SoftwareStopOutcome.CloseStalled=4`（Critical）を
   **1 行につき 1 回**出す（`StalledNotifiedAt` に記録）。据え置き自体は正しい fail-safe だが、無期限に黙って続くと
   「損切りが出ていない」ことに誰も気づかない。行は Active のまま再試行を続ける。

### 方針と合わなかった点（記録）

- 4 巡目の指示は「保護記録の残保護数量の合計とブローカーの純額を比べ、超過分を古い行から削る」であった。
  **S0 行を部分的に削る**と、ブローカーに実在する逆指値が帳簿より大きいまま残って反対建玉を作るため、
  S0 は「全部か 0 か」に限った（上の 5）。また **S1 が 1 件も無い群では割り当てを行わない**ことにした（上の 6）
  ——削ると「同一銘柄に複数の S0 が併存し純額がそれを賄えない」既存の近似の挙動が変わり、
  「S1 が無い構成では従来と同一」が破れるためである（既存テスト `一件の評価が例外でも残りの件は処理し失敗として数える` で実測）。

### 残る制約

- ブローカーの純額は建玉の出自を区別しないため、**どの記録の建玉が外部で消えたかは原理的に分からない**。
  本方式は「古い行から削る」という**決定的な規則で一度だけ**決め、記録する。誤って割り当てても
  合計は純額を超えないため**反対建玉は作らない**（倒れ方は「据え置き／完了」側である）。
  - 🔴 **［2026-09-18 追記（5） / #820 の 5 巡目監査］この一文の後半は誤りであり、監査が実証した。**
    「倒れ方は据え置き／完了側である」は**成り立たない**。誤って割り当てた先が S0 の行だと、その行の主張は 0 になり、
    ガードが**ブローカーに実在する生きた逆指値を取り消して**完了させる——**無音かつ不可逆な破壊**である

   ```
     → first: Active Remaining=10 Pending=10 Obs=0 Effective=0（永久に 0）

     → s1: Active Remaining=10 Pending=10 Effective=0 / closes=[]（10 株が無保護）
   ```

   🔴 **P13 が示すとおり、これは異常系ではなく S0 の標準的な終わり方で起きる。**
   追記(7) の「残る制約」はこの状態を「到達済みなら 15 分で `CloseStalled` が出るため無音ではない」と書いていたが、
   **未到達の行には効かない**（監査の実測: 20 巡回 100 分でイベント 0 件）。射程を実態より狭く書いていた（下の「訂正」）。

2. **BLK-8-2（他人の建玉が先に在ると、幽霊行がそれを自分の損切りラインで売る）**:
   追記(7) の復元撤去が塞いだのは「幽霊行が**先に**超過を観測した後で他人の建玉が現れる」経路（T-10-411）だけだった。
   **他人の建玉（S2・人手・S0 の発注窓）が先に在ると超過が一度も観測されず**、主張は満額のまま残る。
   監査の実測（**稼働中の S2 から S1 へ切り替えた直後そのものの時系列**）:

   ```
   1. 切替前からの S2 建玉 10 株（保護記録なし）
   2. 切替後の S1 エントリー 10 株が約定 → 純額 20（超過は出ない）
   3. S1 の建玉だけ人手で決済 → 純額 10（S2 のぶん）。超過は依然 0
   4. 到達 → closes=[10@940/Sell]  ← S2 の建玉を S1 のラインで売った
   ```

   追記(7) 自身が「到達可能性は高い。本 PR の反映手順は稼働中の S2 から S1 へ切り替えることが前提」と
   書いていながら、**その配置が未修正**だった。

### 根本原因

**追記(7) は「観測を増やす」方向だけを持ち、「観測を減らす」方向を持たなかった。**
確定（2 巡回連続の観測）は対称な相手（2 巡回連続の不在）を欠いており、一度積んだ観測が消えない。
BLK-8-2 は逆に、**武装の時点で純額の帰属が付いていない**ため観測がそもそも起こらない。
**どちらも「銘柄単位の純額からは自分の建玉と他人の建玉を区別できない」という同じ限界の裏表**である。

### 改めた決定

1. **観測を対称に失効させる（BLK-8-1）**。超過が `ExternalReductionConfirmations`（＝2）回**連続で消えた**ら、
   `PendingExternalReduction` を 0 に戻す（`ProtectiveStopNetting.Expire`。新しい列
   `ExternalReductionAbsences`＝migration `AddProtectiveStopSuspension`）。
   🔴 **これは「復元」ではない。** 帳簿（`RemainingProtected`）を書き戻さないので、6・7 巡目の復元問題
   （送信済み未反映の決済を「戻った建玉」と読む／他人の建玉で幽霊行が復活する）は生じない。
   観測が増える方向（真の追加減少）では従来どおり不在の連続回数を 0 へ戻す。
2. 🔴 **ただし到達済みの行では失効させない。** その行は失効した瞬間に成行決済を出すため、
   「戻ってきた自分の建玉」と「他人の建玉」を取り違えたときの倒れ方が**不可逆（反対建玉）**になる
   ——これは 7 巡目 BLK-7-2（T-10-411）そのものである。**方針との差異であり、実測で決めた**（下の「方針と合わなかった点」）。
   到達済みの行は据え置いたまま `CloseStalled`（到達からの猶予）と下の決定 3 で人手へ回す。
3. **実効数量 0 が猶予（15 分・`ProtectiveStopNetting.ProtectionSuspendedGrace`）を超えたら
   `SoftwareStopOutcome.ProtectionSuspended=6`（`SoftwareStopExecuted`・Critical）を 1 行 1 回出す（BLK-8-1 の無音対策）。**
   **到達の有無に依らない**——未到達の行には `CloseStalled`（到達からの猶予）が効かない。
   計時は新しい列 `ProtectionSuspendedSince` / `ProtectionSuspendedNotifiedAt`（同 migration）で持ち、
   実効数量が戻ったら両方を `null` へ戻す（再発したら改めて数え直す）。
   猶予は孤立行（`DefaultOrphanGrace`）・据え置き（`DefaultSettlementGrace`）と**同型の 15 分**にする。
4. **S1 の武装に前提条件を置く（BLK-8-2）。** `OrderExecutionAppService` は S1 で新規建てを武装する時点で、
   同一銘柄・同方向に**帰属不明の建玉**（＝方向の純額 − Active な保護記録の主張合計 > 0）があるなら、
   **エントリーを送らず建玉を持たずに見送る**（`OrderDispatchForgoneReason.UnattributedPosition=4`）。
   「保護レグを張れない Open では建玉を持たない」（IADR-0210 決定 1）と同じ倒し方である。
   - 🔴 **確かめられない場合も「ある」側へ倒す**（建玉照会の能力が無い発注先・照会が `null`）。
     「不明」を「無い」と取り違えると、他人の建玉を S1 のラインで売る不可逆な事故になる。
   - 判定は**初回の武装のときだけ**行う（再配送で既に行がある場合は触らない。決定 3 の冪等を壊さない）。
   - **既存の S0 / S2 / S3 の経路は 1 バイトも変えない**（分岐は `disposition == SoftwareStop` の内側だけ）。
   - 結果として「S2 の建玉が残ったまま S1 へ切り替える」構成では、**帰属不明の建玉が無くなるまで
     S1 の新規建てが出ない**。安全側であり、運用手順（先に手仕舞ってから切り替える）とも一致する。

### 方針と合わなかった点（記録）

🔴 **監査が示した「超過が N 巡回連続で消えたら観測を 0 に戻す」を、そのまま（到達済みも含めて）実装すると
7 巡目 BLK-7-2 が再発する。** 監査は「帳簿を書き戻さないので 6・7 巡目の復元問題は生じない」としていたが、
**決済数量の上限は帳簿ではなく `EffectiveProtectedQuantity` である**ため、観測を捨てれば到達済みの行はその場で売る。
実測（本 PR で一度そう実装して測った）:

```
$ dotnet test --filter "FullyQualifiedName~S1の記録を持たない建玉が現れても幽霊行は主張を取り戻さない"
  失敗 …S1の記録を持たない建玉が現れても幽霊行は主張を取り戻さない
  エラー メッセージ:
```

そこで**失効を未到達の行に限った**（決定 2）。これは方針（「超過が 2 巡回連続で消えたら 0 に戻す」）を
**狭めた**ものであり、別方式へ倒したのではない。根拠は「失効で得るもの（未到達の行の保護が戻る）と
失うもの（到達済みの行が他人の建玉を売る）の非対称」である——未到達の行の失効は
**次の到達の時点で改めて純額と突き合わされる**のに対し、到達済みの行の失効は**その場で不可逆に注文を出す**。

### 残る制約

- **到達済みの行の観測は依然として単調である**（決定 2）。この状態に陥った行は、確定するか人手が介入するまで
  1 株も決済しない。**無音ではない**（`CloseStalled` と `ProtectionSuspended` がいずれも Critical で出る）が、
  **自動では回復しない**。これは「他人の建玉を売らない」ことと引き換えに選んだ倒れ方である。
- **武装の前提条件は「武装の時点」しか見ない**（決定 4）。武装より**後**に他人の建玉が同一銘柄・同方向へ現れる経路は、
  従来どおり観測（超過）として現れ、決定 2 により幽霊行が売ることはないが、その行の保護は止まる。
- **確定前（エントリーの約定がまだ終端でない）の S1 行は 1 株も主張しない**（追記(4)）ため、
  同一銘柄・同方向へ **S1 の新規建てを続けて出すと、2 本目が「帰属不明の建玉がある」と判定されて見送られ得る**
  （1 本目の約定がガードの巡回で確定するまでの窓）。**安全側の見送り**であり建玉は作らないが、
  同一銘柄の連続エントリーは取りこぼす。
- 追記(7) の他の残る制約（`SentCloseScanLimit`＝50 の走査上限、`Filled` 直後の建玉照会の窓、
  T-10-369 の損切り価格の近似）はそのまま残る。

10 巡目の監査は**売り過ぎ（反対建玉）を乱数 6,000 列の掃きで 1 件も再現できなかった**。

追記(8) の「到達済みでは失効させない」は変えない。**

### BLK-10-1 — 何が区別できないのか

未到達の行が超過を観測し、失効（追記(8) 決定 1）で主張を取り戻したあと、次の到達で 10 株を売る。
この 10 株が**自分の建玉なのか他人の建玉なのかは、純額の系列からは決められない**。
次の 2 つは純額の系列が `[0, 10, 10]` で**完全に同一**である。

| 実際に起きたこと | あるべき挙動 | 根拠 |
| --- | --- | --- |
| **一過性の過少照会**（建玉照会が 1 巡回だけ 0 を返した） | 主張を**戻すべき** | 戻さないと、その行の損切りが二度と出ない（8 巡目 BLK-8-1） |
| **真の減少の後に、保護記録を持たない他人の建玉が現れた** | 主張を**戻してはいけない** | 戻すと、他人の建玉を自分の損切りラインで売る（7 巡目 BLK-7-2） |

9 巡目の「失効は未到達の行だけ」でも解けない。未到達の幽霊行が失効で主張を取り戻し、
**次の到達の時点では純額 10・主張 10 で超過 0 になるため、そのまま他人の 10 株を売る**（監査の P1）。

🔴 **どんな規則でも両方は満たせない。** 利用者の裁定は**案①「残余として明示的に受容する」**である
（案②＝ブローカーの注文一覧から「自分が出していない約定」を特定する、は **#863** として起票済み。本 IADR の射程外）。

### 改めた決定

1. **武装の判定を `EffectiveProtectedQuantity` に替える**（追記(8) 決定 4 の「Active な保護記録の主張合計」を改める）。
   帳簿の主張（`ProtectedQuantity`）で引いていたため、**未確定の観測を抱えた幽霊行が他人の建玉を「帰属済み」に見せ、
   新しい S1 が武装されていた**（監査の P6(1)。実測 SOLD=20）。実効数量で引けば幽霊行は 0 株しか主張せず、
   帰属不明が正しく見えて**安全側（見送り）へ倒れる**。
2. **武装の判定の前に `ProtectiveStopNetting.ConfirmEntryFills` を通す**。
   終端になったエントリーの約定数量がまだ帳簿へ書かれていない窓（追記(8) の残る制約 ③＝
   「同一銘柄への連続エントリーは 2 本目が見送られ得る」）では、直前のエントリーが実際には主張しているのに
   主張 0 と読まれていた。確定を先に通せば**ガードの巡回を待たずに主張が立つ**ので、この窓が消える。
   確定は建玉照会を要さない純粋な突き合わせであり、ガードが巡回の先頭で行っているのと同じ操作である。
3. **ガードが毎巡回「帰属不明の建玉」を検知して 1 回だけ知らせる**
   （`SoftwareStopOutcome.UnattributedPosition=7`・`SoftwareStopExecuted`・**Warning**）。
   判定は **方向の純額 − Active 行の主張の合計 − `SharesAccountedElsewhere`（送信済みで未反映の決済＋確定前エントリーの約定分）> 0**。
   - 🔴 **材料は武装の時点にしかなかったが、ガードは毎巡回これを持っている。** 1 本出すだけで、
     追記(8) の**残る制約 ②**（武装より後に他人の建玉が現れる経路）と、
     **受理後に 0 約定で取り消された決済の残り**（監査の P5。行は既に `Completed` で `FindActive` に現れず、
     どのイベントも出ないまま建玉が無保護で残る）が可観測になる。
   - **走査は建玉の側から行う**——P5 の配置には Active な行が 1 件も残らないため、Active 行の群を回すだけでは見えない。
     S1 の足跡がある群（Active ∪ `FindCompletedSoftwareStops`）に限る。
     **S1 が 1 件も無い群（実弾・S0 のみ）では 1 バイトも動かない。**
   - **同じ状態で毎巡回鳴らさない**: 群の S1 行のうち**作成が最も新しい 1 行**へ
     `UnattributedNotifiedQuantity` / `UnattributedNotifiedAt` を記録し（migration `AddProtectiveStopUnattributedNotice`）、
     **株数が変わったとき**か **`UnattributedRenotifyInterval`（60 分）**が経ったときだけ出す。
     帰属不明が消えたら両方を `null` へ戻す（再発したら改めて知らせる）。
   - 🔴 **通知は「検知」であって是正ではない。** 建玉を売らず・記録も作らず・主張も動かさない。
     BLK-10-1 を直すものではなく、**受容した残余が起きていることを人に見せる**ためだけに出す。
4. **`RecordObservation` は観測値を増やすときに `ExternalReductionAbsences` も 0 へ戻す**（監査の非ブロッキング 6）。
   決済経路が観測を積み増しても不在の連続回数が残っていたため、**真の追加減少の直後の 1 巡回で失効し得た**
   （確定と対称であるべき失効が、対称でなくなる）。`Confirm` 側は既に 0 へ戻していた。
5. **`NotifySuspended` は S1 の行にだけ効かせる**（監査の非ブロッキング 7）。
   S0 の行も `IsProtectionSuspended` になり得るが、S0 の保護は**ブローカーに実在する逆指値**であり、
   帳簿の主張が一時的に打ち消されても**建玉は現に守られている**——「ソフトウェア逆指値が 1 株も決済できない」という
   `ProtectionSuspended` の文面はその行に当たらない。S0 側の帰結は確定時の `ProtectionReduced`
   （＋ガードによる逆指値の取消）が既に 1 回残す。

### 受容した残余（BLK-10-1）

- **発生条件**: 未到達の S1 行が外部要因の減少を観測し、**その観測から次の観測までのあいだ（ガードの巡回 1 回ぶん・
  既定 30 秒。失効の確定までは約 2 巡回＝約 60 秒）**に、**保護記録を持たない建玉が同じ銘柄・同方向へ現れる**こと。
- **起こること**: 失効で主張が戻り、次の到達でその建玉を S1 の損切りラインで成行決済する（最大でその行の主張ぶん）。
- **起こらないこと**: 🔴 **売り過ぎ（反対建玉）にはならない。** 決済数量は常に
  `EffectiveProtectedQuantity`（≦ 方向の純額）で頭打ちであり、10 巡目の監査は乱数 6,000 列の掃きで 1 件も再現していない。
- **射程**: **SIMULATE 限定**である（実弾では `StopLossMethodPolicy` が S1 を拒否し、空売りは常に S0）。
  被害は「模擬口座の他人の建玉が意図しない価格で手仕舞われる」ことに留まる。
- **恒久対策**: **#863**（ブローカーの注文一覧から「自分が出していない約定」を特定する）。
  それが入れば「減ったのは誰の注文か」が分かり、推測が要らなくなる。
- **可観測性**: 決定 3 の `UnattributedPosition` が、この残余が起き得る状態（帰属不明の建玉の存在）を
  **到達より前に**知らせる。テストで挙動を固定した（T-10-483。**不具合の固定ではない**ことをテスト名と注記で明示した）。

### 🔴 S1 を選ぶときの運用上の前提条件

10 巡目の監査は「**次の 3 つが満たされるかぎり取引は成立する**」ことを実測した。
S1 へ切り替える前に確認する。

1. **切替の時点で、S2 由来の建玉（および人手で建てた建玉）を手仕舞っておく。**
   残っていると決定 1 の前提条件で S1 の新規建てが出ない（安全側）か、上の残余の入口になる。
2. **非終端の一部約定が無い。** エントリーが部分約定のまま終端していない行は主張が確定せず、
   その窓では帰属が付かない。
3. **受理後に取り消された決済の残りが無い**（監査の P5）。決済が受理された時点で行は完了するため、
   その決済が 0 約定で取り消されると建玉だけが無保護で残る。決定 3 の通知がこの状態を知らせる。

  失効を未到達に限った判断そのものは変えない（到達済みの失効は**その場で**売るのに対し、
  未到達の失効は**次の到達まで猶予がある**——歯止めではなく**時間差**が違いである）。
- 🔴 追記(8)「残る制約」の「武装より**後**に他人の建玉が同一銘柄・同方向へ現れる経路は、…
  決定 2 により**幽霊行が売ることはない**」は、**未到達の行では偽**である。
  未到達の行は追記(8) 決定 1 の失効で主張を取り戻し、次の到達で売る。**到達済みの行では真**（失効しないため）。
  上の「受容した残余」がこの経路そのものである。
- 追記(8) の残る制約「同一銘柄への連続エントリーは 2 本目が見送られ得る」は、**決定 2（確定を先に通す）で
  エントリーが終端になっている場合は解消した**。まだ終端でない（約定の記録が届いていない）場合は残る。

### 残る制約（追記(8) から更新）

- 🔴 **受容した残余（BLK-10-1）は上の「受容した残余」節が正本である。**
- 🔴 **帰属不明の検知は、Active な行が 1 件も無い巡回では走らない。** ガードは
  `stops.FindActive(batchSize)` が空なら建玉を照会せずに戻る（「巡回対象が無ければ建玉照会もしない」は
  無駄な OpenD 往復を避けるために**明示的に固定された不変条件**であり、既存テストが守っている）。
  そのため「受理後に取り消された決済の残り」が**その口座で唯一の S1 の痕跡**である場合、
  次にどこかの銘柄で S1 の行が Active になるまで検知が走らない。
  - **完全に無音ではない**——その銘柄へ次の S1 を武装しようとすると、武装の前提条件が
    `UnattributedPosition` で見送り（`OrderDispatchForgone`）を出す。
  - 直すには「対象ゼロでも建玉を照会する」へ変えるほかなく、**上の不変条件を壊す**ため本 IADR では採らない。
    #863 が入れば注文一覧から直接特定できるようになる。
- **到達済みの行の観測は依然として単調である**（追記(8) のまま）。
- 追記(8) の残る制約「同一銘柄への連続エントリーの 2 本目が見送られ得る」は、決定 2 により
  **エントリーが終端していれば解消**した。まだ終端でない（約定の記録が届いていない）場合は残る。
- 追記(7) の他の残る制約（`SentCloseScanLimit`＝50 の走査上限、`Filled` 直後の建玉照会の窓、
  T-10-369 の損切り価格の近似）はそのまま残る。**帰属不明の検知も同じ走査上限を共有する**
  （完了済み S1 行が 50 件を超えて積み上がった銘柄では、古い行の未反映レグを数え落として
  「帰属不明あり」へ倒れ得る——**倒れ方は「余計に知らせる」側**であり、売買は起こさない）。
