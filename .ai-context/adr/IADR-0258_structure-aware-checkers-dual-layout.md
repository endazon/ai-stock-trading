# IADR-0258: 構造依存の検査器は「新旧レイアウトの和」を走査し、母集合の厚みを別の不変条件として表明する

## コンテキストと課題

VSA 全面移行は、`backend/Services/<Svc>/{src,tests}/<Svc>.{Api,Application,Domain,Infrastructure}/`
という 2 階層を畳み、`backend/Services/<Svc>/` の**直下**に `Program.cs` / `appsettings*.json` /
`Features/` / `Domain/` / `Infrastructure/` / `Common/` / `Tests/` を置く。
移行は 1 サービス = 1 PR で進むため、**混在期間が 11 PR ぶん続く。**

パス構造を前提にした検査器は、この期間に 2 通りの壊れ方をする。**危険度は対称でない。**

| 壊れ方 | 例 | 危険度 |
| --- | --- | --- |
| 赤くなる（fail-loud） | 期待するファイルが無い、と報告して落ちる | 🟡 気付ける |
| **黙って母集合が痩せる（fail-open）** | パスがマッチしないファイルを捨て、**「違反 0 件」で緑になる** | 🔴 **失敗メッセージにも現れない** |

対象は 3 本である。

- `validate-runtime-scaffold.js`: `hostDir()` が `<Svc>.Api` / `<Svc>.Worker` の 2 通りしか見ない。
  統合後は `appsettings.json` が 1 つも見つからず**赤くなる**（fail-loud）。
- `check-consumer-endpoint-names.js`: `^backend/Services/[^/]+/src/` に当たらないファイルを
  `continue` で捨てる。統合後のファイルが**全て捨てられる**。
- `check-test-traceability.js`: `testFiles()` の収集条件 `e.name === 'tests' || e.name.endsWith('.Tests')`
  は、統合後のディレクトリ名 `Tests`（大文字始まり）のどちらにも当たらない。**着手時点では
  「射程外・残余リスクとして記録するに留める」としていたが、この判断は誤りだった**
  （後述「3 本目を射程へ入れた理由」）。

🔴 **着手前の設計書は 2 本目を「0 件走査で緑になる」と評価していたが、実測はそうではなかった。**
同検査器には既に **M1（走査サービス数 ≥ 11）** があり、統合後ツリーでは `[M1] 0 件` で落ちる。
**設計の懸念そのものは残っている**が、現に効いているのは M1 であって、パス正規表現ではない。

### 3 本目を射程へ入れた理由（着手時点からの訂正）

`check-test-traceability.js` は当初、次の 3 点を理由に射程外としていた。

1. 変更してよい検査器が 2 本と指示されていた。
2. 必須 FR（FR-10/12/15/19/20）の参照が **全滅**すれば赤で落ちる fail-closed であり、
   本 PR が塞ぐべき「黙って緑」の壊れ方ではないと判断した。
3. 素朴に `'Tests'` を足すと `backend/Tests/`（横断テスト）が新たに条件へ当たり、
   現行の走査母集合が変わってしまう懸念があった。

**再検討した。** 理由 2 は**全滅ケースにしか効かない**——**部分移行時**（1 サービスだけ新樹形へ
移送された状態）は、そのサービスのテストが母集合から静かに落ちても、他サービスが必須 FR を
参照していれば緑のままであり得る。これは本 PR が正面から塞ごうとしている「黙って母集合が痩せる」
fail-open そのものであり、「全滅すれば落ちる」ことは部分痩せを見逃してよい理由にならない。
理由 3 も、**新樹形の判定を名前だけでなく位置**（`backend/Services/<Svc>/Tests` かどうか）**まで
見れば解決する**——`check-consumer-endpoint-names.js` の決定 2（許可リストから除外リストへの反転）
と同じ「誤りの倒れ方で決める」思想の適用先が違うだけである。**よって 3 本目も射程へ入れる。**

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A: 許可リストへ統合後の形を足す | `^…/(src/\|Features/\|Domain/\|Infrastructure/\|Common/)` のように許す階層を列挙する | ✕ **知らない階層を黙って捨てる方向へ倒れる。** 移行の写像規則（設計 §7）は 16 行あり、`Foundation/` や `Hosted/` のような階層がまだ増える。**足し忘れは緑で現れる** |
| **B: 除外リストへ反転する（採用）** | 「テストであるか」だけを見て落とし、**それ以外は全て走査する** | ○ 知らない階層は**走査される側**へ落ちる（誤りの倒れ方が安全側）○ 新旧が同じ 1 つの規則で分かれる ○ 規則が 2 行で書ける |
| C: 検査器を移行完了まで止める | 混在期間は skip する | ✕ **キュー名の一意性は #258 の実損（取引判断の消失）に直結する不変条件**であり、最も構造が動く期間に止めるのは本末転倒 |

母集合の厚みについても選択肢を検討した。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D: M1（サービス数）で足りるとする | 既存の下限のまま | ✕ **M1 は「1 ファイルでもマッチしたサービス」を数える。** 統合後は `Program.cs` がサービスディレクトリ直下へ来るため、**判定が痩せて `Program.cs` しか当たらなくなっても M1・M2 は 11 / 10 を数えて通る**。そのとき N2 は 11 ファイルしか読まない |
| **E: 走査ファイル数の下限を別に置く（採用）** | `MIN_SCANNED_FILES` を新設し、OK 出力にも母集合を書く | ○ サービス「数」と読んだ「量」を別の不変条件として持てる ○ `McpExposureNotDeclaredTests.MinimumScannedFiles` ・ IADR-0127 ・ IADR-0256 決定 6 と同じ既存の作法 |

## 決定

**決定 1: `validate-runtime-scaffold.js` の `hostDir()` を 3 通りにする。**
`<Svc>/src/<Svc>.Api` → `<Svc>/src/<Svc>.Worker` → **`<Svc>`（統合後）** の順に
`appsettings.json` の実在を見る。**3 つとも無ければ従来どおり `.Api` の名前で報告する** ——
失敗メッセージに現れるパスを変えると、既存の失敗の読み方まで変わってしまう。

**決定 2: `check-consumer-endpoint-names.js` の走査対象判定を「許可」から「除外」へ反転する。**
`isProductionServiceFile()` は ①`backend/Services/<Svc>/` 配下であること ②サービス名より後ろの
**ディレクトリ要素**に `tests` / `Tests`（大小無視）が無いこと、の 2 点だけを見る。
🔴 **許可リストで書かない。** 許可リストは知らない階層を捨てる側へ倒れ、その捨て方は緑で報告される。

**決定 3: 走査ファイル数の下限 `M3` を新設する（`MIN_SCANNED_FILES = 550`。着手時点の実測 693）。**
M1（サービス数）とは**別の量**であり、M1 が通っても M3 が落ちる状態が実在する。
**OK 出力にも走査件数と下限を書く** —— 母集合を表明しない下限は、効いているかどうかを人が読めない。

**決定 4: 統合後の構造は「模擬ツリー」で実証し、実ツリーだけを根拠にしない。**
実ツリーでは統合後の候補が**1 度も評価されない**ため、実ツリーの緑は決定 1・2 の証拠にならない。
`scripts.repo.test.js` に統合後ツリー・混在ツリー・痩せたツリー・空ツリーを組み立てる試験を置く。
テスト資産には**わざと違反を仕込む**（除外されていることを、緑ではなく赤の不在で証明する）。

**決定 5: 一時ツリーを走査できる入口を両検査器に揃える。**
`RUNTIME_SCAFFOLD_ROOT`（既存）に合わせて `CONSUMER_ENDPOINT_NAMES_ROOT` を新設し、
`collectServices(root)` / `checkTree(root)` に省略可能な引数を足す。既定はリポジトリルートで、CLI の既定挙動は変えない。

**決定 6: 本 PR は本番コードを 1 行も動かさない。** 変更は `scripts/` と `.ai-context/` に閉じる。

**決定 7: `check-test-traceability.js` の `testFiles()` を新樹形対応にし、`T1`（樹形ごとの
条件付きの門）を新設する。** 収集条件へ `isNewLayoutServiceTestsDir()`（`backend/Services/<Svc>/Tests`
という**位置**の一致）を足し、`backend/Tests/`（横断テスト）との衝突を回避する。加えて
`serviceTestDirs()` / `serviceTestLayoutCounts()` で樹形ごとの母数と走査件数を分け、
「実在する樹形なのに 0 件」を `[T1]` として落とす——**決定 8（0 件走査の門は実在から動的に
導く）と同じ思想**を、この検査器にも適用する。

**決定 8: `check-consumer-endpoint-names.js` に `M4`（樹形ごとの条件付きの門）を新設し、
0 件走査の門は「樹形の実在」から動的に導く方式へ統一する。静的な下限は置かない。**
（M4・T1 の共通実装原則。M3〔決定 3〕は走査件数の絶対下限であり、これとは別の不変条件として残す。
下の「★ 0 件走査の門の置き場」に詳述）

### ★ 0 件走査の門の置き場（決定 8。基盤 microservices-platform の同名の判断との異同）

決定 8（M4・T1）は「走査が空振りしても緑になる」経路を塞ぐが、**門をどちらの
樹形側に置くかは、基盤側の先例と AST とで前提が違う。**

基盤 microservices-platform の `check-unit-dependencies.js`（IADR-0130 / IADR-0282 決定 2）は、
規則 3 の新判定（単一プロジェクト＋VSA フォルダ）側へ**静的な** 0 件走査の門を置いている。
同ファイルの「★ 0 件走査の門の置き場」はその理由をこう書く: 「FeedbackService が新樹形へ
移送済みの現在以降は、新判定の対象 .cs が 0 件になるのは走査の壊れか移送の巻き戻りでしかない」。
すなわち**基盤では新樹形がすでに非空**であり、非空であることを前提に静的な門が成立する。

🔴 **AST は前提が違う。** 本 PR 着手時点で AST の新樹形（VSA 統合後）へ移送済みのサービスは
**0 件**である。基盤と同じ発想で新樹形側へ静的な門を置くと、**移行に着手する前から新樹形の
走査が恒常的に 0 件になり、その門が着手初日から CI を赤にする**——基盤が警告する「移送完了後に
正しく 0 件になった側で誤って赤くなる」の**鏡像**が、移行前の AST で起きる。

したがって AST では **M4・T1 のいずれも、樹形の実在から動的に導く条件付きの門**にした
（実装 `dirs[layout] > 0 && scanned[layout] === 0`）。旧樹形・新樹形のどちらであっても、
「そのサービスディレクトリが実在するのに、その樹形からは何も読めていない」ときだけ発火する。
これにより、**静的な定数を「最初のサービスが移送されたら引き上げる」約束を残さずに済む**
（「あとで上げる」約束は必ず腐る、という基盤側と同じ教訓を、AST では「静的な門をそもそも
置かない」形で先取りして避けた）。基盤とは**門の置き場が違う**が、**「0 件が正常な帰結になり得る
側には門を置かない」という設計原則そのものは同じ**であり、本 PR は基盤の樹形（IADR-0282 決定 1）へ
**整合**させる一環である——検査器の実装が違うのは前提（移送済みサービスの有無）が違うからであって、
方針の逸脱ではない。

## 理由

- **誤りの倒れ方で決めた。** 許可リストと除外リストは「知らないものをどちらへ倒すか」だけが違う。
  移行期は「知らない階層」が毎 PR 生まれるため、**走査される側へ倒す**以外に選べない。
- **M1 と M3 は同じことを測っていない。** 「11 サービスある」と「693 ファイル読んだ」は独立であり、
  前者だけを持つと**サービスあたり 1 ファイル**でも通る。実測でその状態を作り、
  M1・M2 が通り M3 だけが落ちることを確認した。
- **設計書の評価を鵜呑みにしなかったから、既存 M1 の存在に気付けた。** 母集合は自分で引き直す
  （母集合の引き直しの規律）。

## 結果

- 現行構成での判定は変わらない（11 サービス / Wolverine 配線 10 件 / Worker 11 / 必須 FR 5 件のテスト参照）。
  `check-consumer-endpoint-names.js` の OK 出力は既存 3 行がバイト一致で、**母集合を表明する行が増える**
  （`check-test-traceability.js` の OK 出力も同様に 1 行増える）。
- 統合後ツリー・混在ツリーでも同じ判定が出る（模擬ツリーで実測。3 検査器とも）。
- 母集合が空・あるいは痩せたら落ちる（`[M1]` / `[M2]` / `[M3]` / `[M4]` / `[T1]`）。
  どちらの樹形も実在しない（サービスが 1 つも無い）ときは `[M4]` / `[T1]` は誤発火しない
  （その場合は `[M1]`（サービス数の下限）が先に落とす）。
- 自己試験は `check-consumer-endpoint-names --self-test` が 16 → 29 件、
  `detect-changed-areas --self-test` が 26 → 30 件へ増える（判定ロジックは触っていない）。
  `check-test-traceability.js` は `--self-test` を持たないため、`scripts.repo.test.js` へ
  正の確認・負の確認をそれぞれ置いた（T1 の 3 分岐すべてを固定。作業仕様書「受け入れ基準 4」参照）。

## 残余リスク

1. `scripts/k8s-local-images.sh` の 11 行テーブルは各サービス PR で 1 行ずつ直す（設計 §13.3 の割り当てに従う）。
2. `MIN_SCANNED_FILES = 550` は 2026-08-28 の実測 693 に対する床である。移行は純移動であり
   件数は減らない見込みだが、**床は実測と一緒に見直す**（据え置きの根拠を毎回書く）。
3. 統合後の形はまだ実在せず、本 PR の実証は模擬ツリーによる。**最初のサービス移行 PR で実物により再確認する**
   （M4 / T1 を含む）。
4. `check-test-traceability.js` の T1 は「樹形ごとの 0 件」しか見ない——**M3 に相当する走査量の
   絶対下限は本検査器には意図的に持たせていない**（必須 FR 参照の有無という既存の検査がその代わりを
   担うと判断した。理由は作業仕様書「残余リスク 3」）。**将来この判断を見直す条件は「同型の事故が
   2 回起きたら」**（検査器・規約の追加を判断する既定の基準。運用ガイド §8 と同じ基準）。
