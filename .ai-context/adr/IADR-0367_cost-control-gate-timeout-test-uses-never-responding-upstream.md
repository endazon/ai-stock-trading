# IADR-0367: 費用統制ゲートのタイムアウト試験は「応答しない上流」で固定し、打ち切りを観測で確定させる

## コンテキストと課題

`HttpCostControlGateTests.タイムアウト_応答遅延_は_Normal_停止せず` が全ソリューション実行でまれに落ちる
（起票者の実測 6 回中 1 回）。期待は `Normal`（`Halted=False` / `1×`）で、実際は
`Halted=False` / **`IntervalMultiplier = 0M`** だった。**起票時点で機序は未特定**であった。

### 🔴 機序（実測で特定した）

**① `0M` の出どころ。** テストの `DelayingHandler` は 2 秒後に `200 OK` ＋ 本文 `{}` を返す。
この本文を製品の写像へ通すと `CostStateDto` が既定値になり **`Halted=False` / `IntervalMultiplier=0`** になる
（計装で実測: `MAPPING 200 + body '{}' -> Halted=False IntervalMultiplier=0`）。**失敗値と一致する。**
つまり **50 ms の打ち切りより先に 2 秒の遅延が完了し、ハンドラの応答が採用されていた。**

**② 逆転の理由。** 製品の `HttpCostControlGate` をそのまま呼ぶ計装テストで、プールのワーカーを全部塞ぐと
（`Thread.Sleep` の作業項目 1024 本 × 2.5 秒・スピンループ 16 本併走）、
**50 ms のキャンセルも 2 秒の遅延も配送されない**。空いた瞬間には**両方とも期限切れ**であり、
**どちらが先に走るかは保証されない**。実測では配送が遅れた 6 本のうち **3 本で遅延が先に走り、
結果は `x0`**（＝ issue の失敗）になった。

🔴 **#900 と同じ機序である**（タイマーのコールバックはスレッドプールが配送する）。
`HttpClient.Timeout` はそのタイマー 1 本で実装されているので、**壁時計どうしの競争はプール枯渇下で逆転し得る。**

**③ 実テストの再現（是正前）**: 冷えたプロセス 1/30・1/60、暖まったプロセス 1/20 —— 合計 **3/110**。

## 検討した選択肢

| # | 案 | 評価 |
| --- | --- | --- |
| A | 遅延を伸ばす／上限を下げて比を広げる | **採らない。** 機序は「配送が両方とも遅れる」なので比では消えない |
| B | `TimeProvider` で仮想時間にする | **採らない。** 打ち切りを担うのは `HttpClient.Timeout` であり、**`TimeProvider` を受け付けない**。製品へ別の打ち切り機構を持ち込むのは #901 の射程を超える |
| C | assert を緩める（`Halted` だけ見る等） | **不可。** 固定したいのは縮退の**向き**（`Normal`＝1×で止めない）そのものである |
| **D** | **応答しない上流**（打ち切りでしか終わらないハンドラ）＋打ち切りの観測 | **採用。** 上限値も命題も動かさず、応答が勝つ余地だけを消す |

## 決定

### 決定 1 — ハンドラは打ち切られるまで応答しない

`NeverRespondingHandler` は `Task.Delay(Timeout.InfiniteTimeSpan, cancellationToken)` を待つだけで、
**応答が勝つ経路が存在しない**。「上流が上限より遅い」という前提は**無限に遅い**という極限で満たされ、
固定したい性質（遅い上流でも `Normal` へ倒す）は弱まらない。

### 決定 2 — 打ち切りで終わったことをハンドラ側の観測で確定させる

ハンドラは要求トークンの発火を `TaskCompletionSource<bool>` で公開し、テストは
「`Normal` が返った」だけでなく「**応答ではなく打ち切りで終わった**」ことを見る。
将来 `Normal` が別経路（例: 非 2xx への倒れ）で返るようになっても、**この試験が見ている経路は変わらない**。

### 決定 3 — `Guard`（30 秒）は合否の基準ではない

打ち切りが効かなくなれば `TimeoutException` で赤くなる（黙ってハングしない）。IADR-0364 決定 2 と同じ役割。

### 決定 4 — 弱めていないことは変異注入で示す

| 変異 | 結果 |
| --- | --- |
| タイムアウトの縮退先を `Normal` → 停止（`new CostControlGate(true, 0)`） | **赤**（`Expected … Halted = False …, but found … Halted = True`） |
| タイムアウトの `catch` を削る（例外を伝播） | **赤**（`TaskCanceledException` が漏れる） |

## 理由

起票時に「推測は書かない」と保留された機序を、**計装で特定してから直した**。
特定してみれば、`0M` は「縮退の失敗」ではなく**ハンドラの本文そのもの**であり、
直すべきはゲートでも上限値でもなく**試験の作り**だった。

## 結果

- 良い影響:
  - 是正前 **3/110 失敗** → 是正後 **0/80 失敗**（同一条件: 暖まったプロセス 20 回・冷えたプロセス 60 回）。
  - 当該テストが 2 秒の実時間待ちを持たなくなった（クラス実行が 0.17 秒）。
  - 失敗が「`x0` という謎の値」ではなく「打ち切られなかった」と読める形になる。
- 悪い影響・トレードオフ:
  - 🔴 **是正前の再現率が低い**（3/110）。再現条件は一時ハーネスで作ったものであり、
    **全ソリューション実行での前後比較は取れていない**（起票者の 6 回中 1 回とは条件が違う）。
  - `Guard` に達した場合の失敗は 30 秒かかる。
  - **上流が「2 秒で応答する」という具体的な形はもう試験していない**（無限に遅い上流に置き換えた）。
- フォローアップ:
  - 🔴 **`200 OK` ＋ 本文 `{}`（`intervalMultiplier` 欠落）を `0×` と写す製品の挙動は別 issue で扱う。**
    `0×` は安全既定でも停止でもない。本 PR では触らない（射程外）。
  - **同型の棚卸しと検査器の検討は #885 / #900 / #901 をまとめて別途。**
