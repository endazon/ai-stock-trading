# IADR-0321: OpenD 認証 BFF は自身が唯一の認可点として `trading-owner` を強制し、上流写像を 1 ファイルへ閉じる

- 状態: Accepted
- 日付: 2026-09-09
- 決定者: 実装担当

## コンテキストと課題

SC-04 の BFF（`/bff/opend-auth/*`）は、既存 3 モジュール（Assumptions / RiskControls / Monitor）と
**前提が 3 点で違う**。既存の型をそのまま踏襲すると、いずれも安全側に倒れない。

| # | 既存 3 モジュールの前提 | SC-04 で成り立たないこと |
| --- | --- | --- |
| 1 | 後段が `OwnerOnly` ポリシーを持ち、**認可を委譲できる** | 上流（OpenD 認証サイドカー）は**設計上まったく認証を持たない**（Ingress を持たず Pod 網にしか bind しない）。**委譲先が存在しない** |
| 2 | 要求本文を**丸ごと透過**してよい | 本文に**検証コード**が載る。透過すると、画面から来た本文の欄がそのまま上流へ届く |
| 3 | 応答本文を**丸ごと透過**してよい | 上流が将来コードをエコーし始めた瞬間に漏れる |

さらに、**上流サイドカーは本 PR と並行して実装中**であり（#722）、着地時に欄名が動くことが
着手時点で分かっている。

## 決定

### 決定 1: BFF 自身が `trading-owner` を強制し、権限外は 404（存在秘匿）とする

グループへ**エンドポイントフィルタを 1 つ**掛け、4 端点すべてへ機械的に効かせる。
端点ごとに書かないのは、**次に端点を足した人が落としても「動いてしまう」**からである。

- `trading-owner` を持たない認証済み利用者には **404**（403 ではない）。403 は「在るが権限が無い」と
  告げてしまう（NFR-06 の存在秘匿）。本画面は実口座のゲートウェイへの窓口であり、
  **存在そのものが情報である。**
- 🔴 **権限外では上流を 1 度も呼ばない。** 呼ぶと ① 応答時間の差で端点の存在が漏れ、
  ② **認証を持たない上流へ無権限の要求が到達する**。フィルタは上流呼び出しの**前**に位置する。
- 匿名は従来どおり **401**（`RequireAuthorization()`）。既存 BFF 全体と揃え、ログイン導線を壊さない。

**既存 3 モジュールとの非対称は意図的である。** 「BFF は認可を持たない」という従来の型は
「後段が持っているから」という理由に支えられていた。理由が消えた以上、型だけを踏襲すると
**認可がどこにも無い**状態になる。

### 決定 2: 上流との写像を `OpendAuthUpstream.cs` の 1 ファイルへ閉じる

エンドポイント側（`OpendAuthBffEndpoints.cs`）は**写像後の型しか知らない**。上流のパス・欄名・
コマンド名は 1 ファイルの中だけに現れる。

**理由**: 上流は並行実装中であり、着地時の調停が確実に発生する。**調停が 1 ファイルの編集で
済む形**にしておく。

> 🔴 **［着手時の実測・2026-09-09］並行実装中のサイドカーの現物は、本 IADR が実装した契約と 4 点で異なる。**
> ①`state` に `status` / `lastLoginAt` が無く `consoleAvailable` / `consoleTail` を持つ。
> ②`verify` の本文が `{ kind, code }` で `kind` を受け取る。③`/opend-auth/resend` が無く再送は
> `verify` の `kind: "resend"`。④エラー本文が `{ error }`。
> **本 PR は依頼で与えられた契約に対して実装した**（差異の調停は依頼者が行うと明示されている）。
> **② は BFF の対外契約に影響しない** —— BFF は待機中プロンプトから種別を自分で決めるのであって、
> 利用者から受け取るのではない（決定 3）。

### 決定 3: 送信コマンドは「いま上流が何を待っているか」だけで決める

- 画面から受ける本文は**コードだけ**（`CodeSubmission(string? Code)`）。
  **`command` / `kind` に相当する欄が型として存在しない。**
- BFF は投入前に上流の状態を読み、**待機中プロンプトからコマンドを決める**
  （`phone` → `input_phone_verify_code` / `pic` → `input_pic_verify_code`）。
- 待機していない・種別が読めない場合は **409** を返し、**上流へ 1 バイトも送らない**。
  計画は「サーバ側でも拒否する。画面の無効化だけに頼らない」と明記している。
- 上流へ渡す本文は**作り直す**（透過しない）。型に無い欄は構造的に落ちる。

🔴 **許可リスト方式であって拒否リスト方式ではない。** 送れるのは 3 コマンドだけで、
`relogin -login_pwd=` / `exit` / `close_api_conn` / `set_log_level` /
`show_delay_report -detail_report_path=` / `show_sub_info -sub_info_path=` は**経路が存在しない**。
後 2 者は **root 権限で任意パスへ書ける**（デバイス信頼の実体や `OpenD.xml` を潰せる）。

### 決定 4: 検証コードは応答にもログにも残さない（NFR-05 の適用範囲の拡張）

- 要求本文をログへ出さない。**例外メッセージも出さない**（`JsonException.Message` には
  本文の断片＝コードが入る）。
- 上流の応答本文は**捨てる**。返すのは状態と機械可読な理由の符号
  （`not_waiting` / `rejected` / `gateway_unavailable`）だけであり、
  **利用者の入力に由来する文字列を 1 つも含まない**。
- 画面側も、入力値を失敗表示へ反射せず、送信の直後に入力欄から消し、クエリキーへ入れない。

**これは NFR-05 の射程を広げた扱いである。** 同 NFR は資格情報の**保管**を定めており、
一時的な検証コードのログ残存を直接には定めていない。それでも **1 つでゲートウェイのログインが
通る値**である以上、同じ扱いにする（計画 05_screens SC-04 の明示）。

### 決定 5: 3 状態は既存の `MetricAvailability` の序数へ写す（新しい形を作らない）

`Available`(0) / `NotSupplied`(1) / `NotApplicable`(2)。フロントは既存の
`isNotSupplied` / `METRIC_NOT_SUPPLIED_TEXT` をそのまま再利用する。

| 実態 | 宣言 |
| --- | --- |
| SMS / 画像の入力を待っている | `Available` ＋ `prompt` |
| ログイン済みで入力待ちではない | `NotApplicable`（**対象なし。正常である**） |
| 上流不達・未構成・`waiting` なのに種別が読めない | `NotSupplied`（**供給が無い**） |

🔴 **判らないものはすべて `NotSupplied` へ倒す。安全側は「取れていない」であって「対象なし」ではない。**
取り違えると、**ゲートウェイへ到達できていないのに「正常にログインできている」ように見える。**

型を参照せず序数を再宣言するのは、本 BFF ライブラリが ASP.NET Core の `FrameworkReference` だけで
自己完結する契約だからである（platform → 可変ユニット参照は禁止・IADR-0057）。

### 決定 6: `OpendAuth:BaseUrl` の既定は空とし、空は「未構成 → 供給が無い」を意味する

`KnowledgeBase__Search__BaseUrl` の空＝no-op と同じ fail-safe な既定である。
未構成のとき `/state` は **200 で `NotSupplied` を宣言**する（エラーにしない）——
画面が 3 状態を描き分けるために、宣言そのものが要るためである。
`/code` / `/resend` は **503**、`/captcha` は **404** へ倒れ、いずれも上流を呼ばない。

デバイス信頼の永続化・egress IP の安定性は**配備構成（PVC・固定 NAT）から静的に決まる**ため
（計画 05_screens SC-04「表示項目の供給元」の表）、サイドカーではなく構成
（`OpendAuth:DeviceTrustPersisted` / `OpendAuth:EgressStable`）から読む。未設定は供給なし。
**上流へ到達できなくてもこの 2 指標は供給され得る。**

## 検討した代替案

| 案 | 採らなかった理由 |
| --- | --- |
| 既存どおり pass-through にし、認可をサイドカーへ持たせる | サイドカーへ Keycloak 検証を持たせると、**実口座のコンソールに直結するコンポーネントの攻撃面が増える**。Pod 網に閉じ込めて認証を持たせないほうが安全であり、その代わり BFF が認可を持つ |
| 権限外へ 403 を返す | 「在るが権限が無い」と告げてしまう。既存 3 画面（SC-01〜03）はいずれも存在秘匿で揃っており、SC-04 だけ緩めない |
| 画面から `kind` を受け取り、サーバで検証する | **検証は必ず漏れる。**「受け取らない」ほうが強い（型に欄が無ければ、検証の書き忘れが起こり得ない） |
| 送信履歴の照会 API を新設する | 4 端点の外へ口を増やさない。口が増えるほど攻撃面が増える。計画も「照会 API は未実装」と明記しており、画面は**供給が無い**として描く |
| ルートを `/trading/opend-auth` と宣言する | 既存 3 画面がユニット相対（`/settings` / `/controls` 等）であり、`/trading` は基盤 SPA がユニットを載せる位置である。ここへ書くと二重になる |

## 影響

- **良い影響**: 認可が 1 か所（グループのフィルタ）に集まり、端点を足しても自動で掛かる。
  上流の欄名変更が 1 ファイルの編集で済む。検証コードの漏洩経路（ログ・応答・例外メッセージ・
  クエリキー・失敗表示）が塞がれ、それぞれに回帰テストがある。
- **悪い影響**: 既存 3 モジュールと BFF の型が揃わなくなる（本 IADR がその理由を持つ）。
  `/code` は投入前に状態を 1 回読むため、往復が 1 つ増える（**有人操作であり、頻度は初回と
  再認証だけなので許容する**）。

## 残余リスク

- 🔴 **本統制は本画面と裏側 API の配備後に働く。** 配備までの唯一の経路である `kubectl attach` には
  及ばず、禁止した 6 コマンドを送れる状態が残る。暫定手段は `kubectl attach` の実行権限を
  運用者に限ることである（クラスタの認可に依存し、本 BFF の許可リストとは別の統制である）。
  **「統制を定めた」と「統制が働いている」は別である。**
- 🔴 **platform 合成点（`Platform.Bff/Composition`）への登録は本リポジトリから行えない**
  （別リポジトリの所有物）。登録が漏れている間、画面は 404 を受け取り**供給が無い**として描く
  ——安全側だが、**画面だけが存在する**状態にはなる（#340 と同型の穴）。
- **上流サイドカーの契約差異**（上記 4 点）は未調停である。調停は `OpendAuthUpstream.cs` の編集で閉じる。
- **再送のレート制限は上流が課す。** BFF は 409 を透過するだけであり、**BFF 単独では連打を止めない**。
  間隔（暫定 60 秒）は算定根拠が無く実測待ちである。
- **`lastLoginAt` が `null` のとき「未供給」へ倒している。** 上流の契約が「まだ一度もログインしていない
  （対象なし）」と「取得できていない」を区別しないためである。区別できる欄が入ったら見直す。
