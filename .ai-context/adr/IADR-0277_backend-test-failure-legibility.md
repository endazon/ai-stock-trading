# IADR-0277: backend-test の「失敗 0 件なのに exit 1」は誤診であり、失敗の可読性を TRX で機械化する

## コンテキストと課題

[#596](https://github.com/endazon/ai-stock-trading/issues/596) は、`backend-test` のシャードが
**テストを 1 件も失敗させていないのに exit 1 で落ちる**現象が 3 回観測されたと報告し、
**テストホストプロセスの異常終了**を推定した。仮説は (1) メモリ枯渇 (2) `WebApplicationFactory`
系の後始末 (3) シャード構成の変化との相関の 3 つであった。

### 🔴 実測: 前提が誤っていた

3 本すべての **attempt 1** のジョブログを全文で取得して突き合わせた
（`gh run list` は再実行後の conclusion しか返さないため、
`actions/runs/<id>/attempts/1/jobs` から job id を引く必要がある）。

| # | PR | run / job（attempt 1） | シャード | 実際に落ちたテスト |
| --- | --- | --- | --- | --- |
| 1 | #587 | 33198144355 / 98940484935 | `backend-test (2)` | `MarketMonitorService.Api.Tests.Contracts.MonitorContractFixtureTests.監視設定応答がフロントの契約フィクスチャと一致する` |
| 2 | #591 | 33232430367 / 99047480228 | `backend-test (2)` | `TradeDecisionService.Api.Tests.LlmPurposeWiringTests.費用計上イベントも層別の用途で発行される` |
| 3 | #594 | 33237115480 / 99059907940 | `backend-test (1)` | `TradeDecisionService.Tests.LlmPurposeWiringTests.費用計上イベントも層別の用途で発行される` |

**3 回とも `Failed: 1` がログに出ており、テスト名・アサーションメッセージ・スタックトレースが
すべて記録されていた。** `The active test run was aborted` / `Test host process crashed` /
`OutOfMemory` / 終了コード 134・137・139 は**全文検索して 1 件も無い**。
ホストは異常終了していない。

### なぜ「失敗 0 件」に見えたのか

`dotnet test <solution>` はプロジェクトを並列に走らせ、**各 VSTest のコンソールロガーが
同じ標準出力へ同期せずに書く**。その結果サマリ塊が他プロジェクトの逐次出力に割り込まれ、
**塊自体が分断される**。#594 の実ログ:

```
1427:  Total tests: 537
1428: Test Run Failed.        ← 割り込みで塊の内側へ入り込んでいる
1429:      Passed: 536
1430:      Failed: 1
...
1540: Test Run Successful.    ← ログ末尾に最も近いサマリは *別* プロジェクトのもの
1541: Total tests: 229
1542:      Passed: 229
```

🔴 **#596 が「失敗 0 件」の根拠として引用した `Test Run Successful. / Total tests: 229 /
Passed: 229` は、失敗したプロジェクトとは別のプロジェクトのサマリである。**
1,600〜1,700 行のログを末尾から読むと、必ずこれに当たる。

### 4 つの「症状」の判定

| 症状 | 判定 |
| --- | --- |
| `Failed` が 1 行も無い | **誤り**。前後を他プロジェクトの `Passed` 行に挟まれて 1 行だけ現れる（#591 は 1269 行目、#594 は 1237 行目） |
| `Build FAILED` なのに `0 Warning(s) / 0 Error(s)` | **異常ではない**。VSTest の MSBuild ターゲットはテストの失敗を**戻り値**で伝え、MSBuild のエラーイベントとして上げない。MSBuild のサマリが 0 件を数えるのは仕様どおりである |
| カバレッジ添付＝担当プロジェクト数 | **異常ではない**。アサーション失敗はホストを落とさないので、全アセンブリが走り切ってレポートを出すのは当然である |
| orphan の `dotnet` 3 件 ＋ `VBCSCompiler` 1 件 | **異常ではない**。🔴 **同じ run の緑のジョブ（33237115480 attempt 2 / job 99060230849 = `backend-test (1)` success）にもまったく同じ orphan 掃除が出る。** MSBuild のノード再利用プロセスと Roslyn コンパイラサーバが残るのは**毎 run の定数**であり、失敗の信号ではない |

### 仮説の判定

| # | 仮説 | 判定 |
| --- | --- | --- |
| 1 | メモリ枯渇 | **棄却**。失敗はアサーション失敗であり、そのテストは結果を報告して終わっている |
| 2 | `WebApplicationFactory` 系の後始末 | **棄却**。orphan は緑のジョブにも同数出る（上表） |
| 3 | シャード構成の変化との相関 | **趣旨は正しいが機序が違う**。ホストを落としたのではなく、**同時に走る顔ぶれが変わったことで既存の順序依存テストが露出した**（[#597](https://github.com/endazon/ai-stock-trading/issues/597) が実測込みで特定し PR #598 が修正済み）。#587 は契約フィクスチャの乖離で並列とは無関係 |

### 残る実在の欠陥

テスト側に直すべき欠陥は残っていない（#591 / #594 の当該テストは PR #598 で順序非依存へ、
#587 のフィクスチャ乖離は当該 PR 内で解消済み）。**残るのは可読性である。**
名前の付いた失敗が並列ログに埋もれ、**「失敗 0 件なのに落ちた」という誤診で issue が 1 本立った。**
分配は PR ごとに変わり続けるため、同じ誤診は再発する。

## 検討した選択肢

| # | 案 | 評価 |
| --- | --- | --- |
| A | 何もしない（#596 を「誤診」と説明して閉じる） | 誤診の**原因（ログの読み違えやすさ）が残る**。次に落ちたときも同じ人時が消える。採らない |
| B | `--verbosity minimal` へ落として逐次の `Passed` 行を消す | ログは短くなるが、**サマリ塊が分断される問題そのものは残る**（複数プロジェクトのサマリが並ぶことは変わらない）。加えて要約器が壊れたときに参照できる生の記録まで失う |
| C | `-m:1` でプロジェクト間の並列を止める | ログは直列化されて読めるようになるが、**恒久策として遅い**（IADR-0208 と正面から衝突する）。しかも**原因が並列度ではない**ことが判明している。#596 自身も「切り分け用」と書いている |
| D | **TRX を出し、失敗時に「実際に落ちたテスト」を機械で名指しする** | TRX は構造化データで**割り込みの影響を受けない**。費用は TRX の書き出しのみ。**採用** |
| E | D ＋ 本物のホスト異常終了に備えた成果物（blame / `--diag`）を失敗時のみ残す | D だけだと、**本物の**ホスト異常終了が起きたとき（＝ TRX に失敗 0 件のまま exit≠0）に依然として手掛かりが無い。**採用** |

## 決定

**D ＋ E を採る。** `.github/workflows/ci.yml` の `backend-test` に次を入れる。

1. **`--logger trx` を足し、`scripts/summarize-test-failures.js` が失敗時に TRX を全部読む。**
   失敗テストの完全修飾名・メッセージ・スタックトレースを**ジョブログの末尾**と
   `$GITHUB_STEP_SUMMARY`（PR の Checks 画面から 1 クリック）へ出し、`::error::` 注釈も付ける。

2. 🔴 **要約器は TRX を 1 件も読めなければ落ちる（fail-loud）。**
   0 件検査で「失敗テストなし」と報告して緑にするのは、**#596 の誤診を機械で再生産する形**である。
   実行条件は `steps.test.outcome == 'failure'` に絞る —— Test より前（Build 等）で落ちた場合に
   TRX が無いのは当然であり、そこで fail-loud を鳴らすと信号が濁る。

3. 🔴 **「TRX は読めたが失敗 0 件」を要約器が明示的に名指しする。**
   **これが #596 が疑った本物の形**であり、そのときだけ「テストホストの異常終了・`dotnet test`
   自体の失敗・後続ステップの失敗を疑え」と、次に見るべき成果物を挙げる。
   #596 で人手にかかった切り分けを 1 行にするのはこの分岐である。

4. **壊れた TRX は読み飛ばさず malformed として報告する**（黙って抜くと 0 件検査へ退行する）。

5. **`--blame-crash --blame-hang --blame-hang-timeout 10m` を付ける。**
   クラッシュもハングも起きなければ成果物を書かないので定常の費用はほぼゼロで、
   本物のホスト異常終了が起きたときだけ Sequence.xml / dump が残る。#596 が求めた保険である。

6. **`--diag` の VSTest 診断ログを付け、blame の成果物・TRX とまとめて失敗時のみ artifact
   として上げる**（`if: failure()`）。常時上げると保管と転送を毎 run 払うことになる。

7. **`free -m` / `nproc` を実行の前後で記録する。** 仮説 1 は棄却済みだが出力は数行で費用が無く、
   **次に同じ疑いが出たとき推定ではなく実測で棄却できる**。

8. 🔴 **`-m:1` は入れない**（選択肢 C）。恒久策として遅く、原因が並列度ではない。
   自己試験がこの不在を固定する（入れ直すと赤くなる）。

9. 🔴 **ジョブ名 `backend-test` / `build-and-test` を変えない**（必須チェック名。
   `scripts/check-workflow-job-refs.js` が検査する）。自己試験がこれも固定する。

10. 🔴 **テストの skip / 無効化 / quarantine は行わない。**

11. **`--verbosity normal` は据え置く**（選択肢 B を採らない）。要約器が壊れたときに
    参照できる生の記録を残す。

12. 🔴 **カバレッジレポートの数え方と artifact の glob を「深さ 2」に限定する。**
    **TRX ロガーは実行ごとに deployment root（`cov/<user>_<machine>_<ts>/In/<machine>/`）を作り、
    添付をそこへ複製する。** 実測（run 1・4 シャードすべて赤）では期待 6 件に対し 11 件、
    7 件に対し 13 件になった。収集器が書く本体は `cov/<guid>/coverage.cobertura.xml`（深さ 2）
    なので、`find cov -mindepth 2 -maxdepth 2` と `path: cov/*/coverage.cobertura.xml` に限定する。
    **複製の件数は本体と同数にならないことがある**（タイミング依存。6 → 11 と 6 → 12 が同一 run に
    並んだ）ため、複製の数そのものは不変条件にできない。

## 理由

- **誤診の原因は「情報が無かったこと」ではなく「情報が読めなかったこと」である。**
  失敗テスト名は 3 回とも記録されていた。足すべきは新しい観測ではなく、
  **既にある事実を割り込みの影響を受けない形で提示する経路**である。
- **要約器を fail-loud にする理由は、この検査器自体が誤診を再生産し得るからである。**
  「TRX が 0 件だったので失敗テストは無い」と緑で報告する要約器は、#596 の読み違えを
  機械化しただけであり、**人が読み違えるより悪い**（機械の出力は疑われにくい）。
- **blame と `--diag` を入れるのは、仮説 1・2 を棄却したこととは矛盾しない。**
  棄却したのは「今回の 3 観測がホスト異常終了だった」という主張であって、
  「ホスト異常終了は起こり得ない」ではない。起きたときに**また手ぶらで調べ始める**ことを避ける。
- **`-m:1` を退けるのは IADR-0208 と整合するためである。** シャーディングは
  「1 ランナー内は既に 4 並列で頭打ち」という実測の上に立っており、
  プロジェクト間並列を止めることはその前提を自ら壊す。

## 結果

- 実測で分かったこと（決定 12 の裏取り）:
  - 🔴 **計装は既存の不変条件を壊し得る。** `--logger trx` を足した最初の run で
    「1 テストプロジェクト = 1 カバレッジレポート」（IADR-0208 決定 10）が 4 シャードすべてで
    赤くなった。**その不変条件が無ければ、複製されたレポートが黙って artifact に載っていた。**
  - 🔴 **2 つの直し先のうち、赤くなるのは片方だけである。** 件数の不変条件は赤くなるが、
    **artifact の glob は赤くならない** —— カバレッジ集計は (ファイル, 行番号) の**和集合**なので
    率は変わらず、重複を黙って運ぶだけになる。だから glob 側は
    `scripts/scripts.repo.test.js` のテストで固定した（`cov/**/...` へ戻すと落ちる）。
  - **仮説 1 は定量的に棄却された。** 4 シャードの `free -m` で **available は最低でも 13.4 GB
    （全体の 85%）を割らず、used のピークは 2.3 GB**（total 約 16 GB・`nproc=4`）。枯渇には程遠い。
  - **`--blame-crash` は Linux ランナーで実際に有効**（テストホストごとに
    `Blame: Attaching crash dump utility to process dotnet (NNNN).` が出る）。かつ
    `All tests finished running, Sequence file will not be generated.` ＝
    **異常終了しなかったので何も書かない**。定常費用ゼロを実測で確認した。
- 良い影響:
  - `backend-test` が落ちたとき、**落ちたテストの名前が Checks 画面と ジョブログ末尾に必ず出る**。
    ログを 1,700 行読む作業が消える。
  - 「テストは全部通ったのにジョブが落ちた」という**本物の異常**が、初めて自動で名指しされる。
  - #596 の 3 仮説が実測で判定され、再燃したときに同じ調査を繰り返さずに済む。
- 悪い影響・トレードオフ:
  - TRX の書き出しと `--diag` の分だけ Test ステップが遅くなる。**実測値は作業仕様書
    「実測 4」に記録する。** 目に見える増加があれば `--diag` を opt-in（`workflow_dispatch`
    入力またはリポジトリ変数）へ落とす —— そのときも決定 1〜5 は残す（費用の主因は `--diag`）。
  - 失敗時に赤いステップが 2 つ（Test と Summarize）並ぶ。要約器が黙って 0 を返すより良い。
- フォローアップ:
  - `--diag` の費用が無視できないと実測されたら opt-in 化する。
  - 本物のホスト異常終了が実際に観測されたら、blame の成果物を持って改めて起票する。
    そのとき**この ADR の「症状の判定」表を先に読むこと**（同じ 4 症状は毎回出る）。

### 比較

| | diag あり（3 run 平均） | diag off（2 run 平均） | 差 |
| --- | --: | --: | --: |
| 合計 | 135.0 秒 | 121.5 秒 | **13.5 秒（約 10%）** |
| 最大シャード | 44 秒（5 run 全てで一致） | 40 秒（2 run とも一致） | **4 秒（約 9%）** |

**5 run すべてで「diag あり＝最大 44 秒」「diag off＝最大 40 秒」ときれいに分かれた**
（run 間のばらつきに埋もれる差ではない）。`--diag` 単体の寄与は Test ステップ全体の
約 1 割であり、無視できるほど小さくはないが、致命的な遅さでもない。

### 決定（決定 6 の更新）

**寄与は中程度（約 1 割）だが、既定は無効にする。** 根拠:

- `--diag` が保険として狙う仮説（テストホストの異常終了）は本 ADR の調査で実測により
  棄却済みである。**棄却済みの仮説のために、Test ステップ全体の約 1 割を毎 run 払い続ける
  ことになる。**
- `--logger trx` と `--blame-crash --blame-hang` は残す（決定 D・E は本追記の対象外）。
  本物のホスト異常終了が起きたときの一次的な手掛かり（失敗テスト名・Sequence.xml・dump）は
  これらだけで揃う。`--diag` の VSTest 診断ログは、その一次的な手掛かりでは足りない
  ときの**二次的な**保険であり、平時のコストに見合わない。
- **取り外さず、切り替え口として残す。** `.github/workflows/ci.yml` の Test ステップへ
  環境変数 `VSTEST_DIAG` を足し、既定は空文字列（無効）にした。`"1"` にした PR を出せば
  いつでも `--diag` を再現できる。`scripts/scripts.repo.test.js` が既定無効・素の `--diag`
  直書き禁止を回帰テストで固定する。

### 影響

- `scripts/summarize-test-failures.js` の `CRASH_HINT` の `--diag` 案内を、既定無効を前提にした
  文言（`VSTEST_DIAG` を `"1"` にした PR を出して再現させる）へ更新した。
- 決定 1〜5・7〜12 は変更しない（`--diag` の有無に関わらない）。
