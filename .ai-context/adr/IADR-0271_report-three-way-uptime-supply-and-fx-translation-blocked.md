# IADR-0271: 三者比較は「実際の発注先 × 現在段階」で供給し、OpenD 稼働率は仮説の最小値で渡す。為替差損益は推定を避けて供給しない

## コンテキストと課題

IADR-0250 は報告サイクル拡張の**描画と集計（純関数）**を入れ、供給が無い 4 項目を
「照会できませんでした」と明記する形で残した。そのフォローアップとして残っていたのが
**三者比較・OpenD 稼働率・為替差損益**の 3 項目である（#569）。

3 項目は独立しており、供給の難しさもまったく違う。**まとめて「供給できない」とも
「供給できる」とも言えない**ため、1 件ずつ根拠を確かめた。

## 検討した選択肢と決定

### 決定1: OpenD 稼働率は「2 仮説の最小値」で渡し、母集団を OpenD 経由の発注先に限る

権威源（`stage1_session_uptime`）は**その日の実際の通常取引時間を知らない**ため、
半日取引日（210 分）と通常日（390 分）の 2 つの窓で分数を持つ（IADR-0150 決定3）。
報告書側の型は**比率だけ**を受け取り、そこから算入可否を導く。

- **選択肢A: 通常日の窓で割った比率を渡す** — 半日取引日に過少・過大が生じ、
  権威源の算入判定（**すべての仮説で 50% 以上**）と食い違い得る。
- **選択肢B: 2 仮説の最小値を渡す（採用）** — `min(ratio) >= 0.50` と
  `MeetsUptimeThreshold`（すべての仮説で 50% 以上）は**恒等に一致する**。
  報告書が「算入」と描いた日は、権威源でも必ず算入される。
  この恒等性は**全入力を走査するプロパティテスト**で固定した。

母集団は **OpenD を経由する発注先**（moomoo `SIMULATE` / `REAL`）に限る（許可制）。
内蔵 `paper` は「外部へ一度も発注しない」ため OpenD を経由しない。その稼働分数を
OpenD 稼働率として報告すると、**OpenD が落ちていた日を「稼働していた」と描く**ことになる。
🔴 **除外した日を 0% として並べない**——「終日停止していた」は別の事実である。行として現れないだけとする。

照会は `GET /risk-controls/session-uptime`（OwnerOrService・IADR-0051 と同型）で行う。
**`from`・`to` の省略・逆順は 400** とする（`/buy-in-inferences` と同じ向き）——黙って空を返すと、
それが「稼働率 0%」「算入 0 日」として報告書に載り得る。

### 決定2: 三者比較の SIMULATE 列と実弾列は「実際に発注した発注先」で分ける（台帳へ列を足す）

- **選択肢A: 承認 Intent の `Mode` を使う（列追加なし）** — **採らない。**
  実行アダプタの発注先は構成（`BrokerSelection.ToBrokerProvider()`）から解決され、
  **`intent.Mode`（段階が定める既定・IADR-0140 決定3）とは独立に決まる**。
  取り違えると**実弾の約定が SIMULATE 列へ載る**。IADR-0149 決定1 が同じ理由で実際の発注先を選んでいる。
- **選択肢B: Stage 1 の約定観測ログ（`stage1_fill_observations`）を使う** — **採らない。**
  同ログは段階遷移で**窓ごと破棄される**（`ResetWindow`）。期間の実績照会の権威源にならない。
- **選択肢C: 取引台帳へ `trade_fills.Provider` を足す（採用）** — 追記専用の台帳が
  `OrderExecuted.Provider` をそのまま保持する。EF マイグレーション 1 本（列追加のみ）。

**既存行の扱い（推定で埋めない）**: 新列は **nullable** とし、列追加前の行は `null`（発注先不明）のままにする。
不明の約定は **SIMULATE 列にも実弾列にも算入しない**。🔴 ただし**黙って落とさない**——
未算入の件数を月報へ別行で明記する。出さないと読み手は「その段では 1 件も取引していない」と読む。

### 決定3: 「空欄（該当なし）」と「値 0」は**現在の運用段階**で分ける

計画は「列が埋まらない期間がある（Stage 1 の間は実弾列、Stage 0 の間は SIMULATE 列も空欄）」と定め、
「空欄」と「値が 0」を区別できる表記を求めている。**段階を知らずに「約定 0 件」を 0 と書くと、
まだ到達していない段を「走らせた結果 0 だった」と読ませる**——乖離の読み方が反転する。

そこで `GET /risk-controls/stage-gate`（読み取り専用）を **OwnerOrService へ移し**、
現在段階を s2s で引く（遷移 `POST /stage-gate/transition` は OwnerOnly のまま据え置く）。
🔴 **照会できないときは Stage 0 等の既定へ倒さず、節ごと「照会できませんでした」とする。**
既定へ倒すと、到達済みの段の列が静かに空欄になる。

**バックテスト列は常に空欄である。** これは供給の手抜きではなく事実である:
`BacktestService` は**永続化もメッセージバスも持たず**、本番戦略（`IBacktestStrategy` 実装）が
まだ存在しない。唯一のサービス間契約 `BacktestEvaluated` は
**勝率・平均損益・取引件数を運ばない**（`Passed` / `MaxDrawdownRatio` / DSR / PBO のみ）。
供給点が生まれたときの継ぎ目は `ThreeWayComparisonAggregator` の 1 箇所である。

**最大ドローダウンはどの列も供給しない。** DD は**エクイティ曲線**に対する比率であり、
その権威源は段階ゲートの実績（段の窓で latch する観測値）であって期間集計ではない。
報告書側で期間の実現損益から別定義の DD を発明すると、**同じ語が 2 つの意味を持つ**——
分母を発明しないという既存の規律と同じ理由で供給しない。
🔴 ただし**「該当なし」で済ませない**——表の「該当なし」は「その段をまだ走らせていない」と
宣言しているため、供給元が無いだけの指標を同じ記号で描くとその宣言が嘘になる。**別行で明記する。**

### 決定4: 為替差損益は供給しない（推定を避ける）

#569 は「台帳が**換算前の外貨額と換算レート**を保持していないため schema 変更が要る」としていたが、
**この前提は文言としては誤りである**。台帳は両方を保持している:

- `LedgerFill.Price` は**銘柄の市場の通貨（ローカル通貨）**、`FxRateToBase` は**適用した換算レート**である。
- `ApprovedOrderRow.FxRateToBase` として**2026-07-27 のマイグレーションで永続化済み**である。
- 落ちているのは報告書側のアダプタが `Price * FxRateToBase` を掛けてから渡している点だけであり、
  **schema 変更では直らない**（素通しすれば済む）。

**本当に無いのは JPY/USD レートである。** 為替差損益の集計は
「**基準通貨（USD）建ての金額**を、**認識時のレート**と**期末のレート**の両方で**円換算**した差」と
定義されており、必要なレートは **1 USD あたりの円**である。ところが:

- `FxRateToBase` は**ローカル通貨 → USD** のレートであり、契約上
  **基準通貨（米国株）では外部へ問い合わせず必ず 1 を返す**。為替差損益を生むのはまさにその
  USD 建て金額であり、その認識時の円レートは**どこにも記録されない**。
- 期末レートの照会経路も無い。取引判断サービスは **HTTP エンドポイントを 1 つも公開していない**。
- 監査台帳からも復元できない。`FxRateSourceUsed` は**どの源を使ったか**だけを持ち、**レートの値を持たない**。

したがって供給には**推定**が要る。為替差損益は**税務にも効く数値**であり、
🔴 **推定値を実績として出さない。既存・新規を問わず「未供給」で確定する。**

必要な変更は次の 2 点であり、いずれも**発注経路と共有契約（`OrderIntent`）に及ぶ**ため、
本 issue の射程（報告書の供給経路）を超える。フォローアップとして残す。

1. 認識時点の **JPY/USD** レートを承認台帳へ persist する（基準通貨市場の注文でも解決が要る）
2. **期末レートの照会経路**を作る（現在どのサービスも公開していない）

## 結果

- 良い影響: 3 項目のうち 2 項目に**実値**が出る。区別（未供給 / 該当なし / 値 0）は
  出口の全文ゴールデンとプロパティテストで固定した。
- 悪い影響・トレードオフ:
  - 為替差損益は当分「供給されていません」と出続ける。**読み手には正しく伝わる**が、行としては空に見える。
  - 三者比較の**バックテスト列と最大ドローダウン行**は当分埋まらない。前者は「まだ走らせていない」で正しく、
    後者は表の外の 1 行で理由を明記して区別する。
  - 列追加前の約定は発注先不明であり、月報の列の合計は期間の全約定より少なくなる（件数を別掲する）。
- 残余リスク:
  - `stage1_session_uptime` は**観測窓（段階遷移）で区切られる**ため、遷移をまたぐ期間の稼働率は
    一部の日しか返らない。**返らなかった日を 0% と読んではならない**ことを契約に明記したが、
    **機械検査は無い**（呼び出し側の実装が守る）。
  - `GET /risk-controls/stage-gate` を s2s へ開いたことで読み取り面が 1 つ広がった。
    遷移は OwnerOnly のままであり、書き込みは開いていない（テストで固定）。
