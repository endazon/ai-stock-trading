## コンテキストと課題

### 🔴 「気づくための段」が実効していなかった

[IADR-0174](IADR-0174_fx-freshness-warning-and-hard-limit.md) は 3 段縮退（5 日以下＝通常／5 日超〜30 日以下＝
警告つき続行／30 日超＝新規建て停止）を入れた。**しかし情報源が FRED 単独のままでは実効しない。**

`DEXJPUS` は系列こそ営業日次だが**公表は H.10 週次リリース**であり、最新観測の齢は**最大 12.84 日**まで
積み上がる。**5 日のしきい値に対して警告域へ常駐する。**

> **常時鳴る警告は無視される警告である。** 計画が名指しした罠——「`DEXJPUS` は系列としては営業日次だが
> **公表は週次**であり、裁定『為替レートを日次化する』を満たさない」——がそのまま残っていた。

### 実測（本作業で実走した一次情報・2026-08-15 13:16 JST）

**計画の記述を信じずに実 API を叩いた。**

| # | 確かめたこと | 実測 |
| --- | --- | --- |
| 1 | 認証なしで叩けるか | **HTTP 200**（API キーの概念が無い） |
| 2 | 系列名 | `FXERD04` = `US.Dollar/Yen Spot Rate at 17:00 in JST, Tokyo Market` |
| 3 | 🔴 中心相場は別物か | `FXERD05` = `Central Rate`。**同じ 08-12 で 159.38 対 159.35 と実際に値が違う** |
| 4 | 収録ラグ | 最新値は **08-12（水）**。08-13・08-14・08-15 は `null`。**取得日 08-15 時点で齢 3 日** |
| 5 | 祝日 | **08-11（火・山の日）は `null`** |

**実測 4 は計画の「翌々営業日 8:50 頃の収録」を再現した** —— 平常時の齢は 2〜4 日であり、
**5 日のしきい値がそれを吸収する**（ADR-0022 決定4 の 3 → 5 日改訂の根拠）。

## 決定

### 決定1: 既存の `BojInformationSource` を再利用せず、FX 専用アダプタを新設する

**同じ日銀 API を叩く実装が既にある**（`InformationCollectionService`）。しかし**再利用しない。**

| 理由 | 内容 |
| --- | --- |
| 契約が違う | あちらは `RawInformationItem`（マクロ指標のテキスト）、FX が要るのは `FxRate?`（`decimal` ＋ `AsOf`） |
| サービスが違う | 共有するなら `Shared.Infrastructure` への抽出になる |
| 抽出は範囲外 | 動いているサービスの改修を伴い、**#381 の受け入れ基準と 1 対 1 で対応しない diff** が混ざる |

**重複するのは JSON の DTO 約 15 行**である。CLAUDE.md 禁止事項「**過剰な抽象化**」に照らし、
**2 つ目の利用者で共通化しない。3 つ目が現れたら抽出する。**

### 決定2: `format=json&lang=en` を使う（CP932 を持ち込まない）

🔴 **#381 の受け入れ基準は「CP932 デコード」と書いているが、実測では CP932 は現れない。**
CP932 は `format=csv&lang=jp` の話であり、**JSON/en は純 ASCII** である。

**基準を字面どおり満たすと、不要な文字コード依存を持ち込むことになる。** 既存の `BojInformationSource` も
JSON/en であり、そちらへ揃えることで**日銀 API の応答形式についての知識が 1 つで済む。**

### 決定3: フォールバックは**順位つき**であり、既存の合成器とは別物である

情報収集側の `CompositeInformationSource` は**全ソースを合算**する（どれも等価）。
**FX が要るのは「第一が駄目なら次」**であり、合算ではない。`FallbackFxRateSource` を新しく書いた。

- **「駄目」の定義は `null` を返したこと。** 各アダプタが通信・解析の失敗を内部で null へ縮退させる。
- **`OperationCanceledException` は伝播させる** —— 取り消しを「源の失敗」と読み替えて次を試すと、
  **取り消したのに外部通信が続く。**

### 🔴 決定4: 合成の順序は `Caching( Fallback( Boj, Fred ) )` とし、**鮮度判定を最外に置く**

```
CachingFxRateSource            ← TTL・5 日超の警告・30 日超の停止
  └ FallbackFxRateSource       ← 順位つき
      ├ BojFxRateSource        ← 第一
      └ FredFxRateSource       ← フォールバック
```

**3 段縮退は「採用された値」に対して効くべきである。** 内側に置くと源ごとに別々の警告が出て、
**どちらの値が使われたのか読めなくなる。**

**あわせて、フォールバックは鮮度で切り替えない。** 日銀が 3 日・FRED が 8 日のときに FRED を採ってはならない
—— **順位は「取れたか」で決まり、「どちらが新しいか」では決まらない。** ADR-0022 決定1 が日銀を第一と定めたのは
**公表頻度の構造**によるものであり、個別の観測日で入れ替わってよいものではない。

### 決定5: `boj` は API キーを要さないため、キー無しでも no-op へ倒さない

FRED はキーが無ければ no-op へ倒す（IADR-0107）。**日銀は認証不要**であり、同じ規則を当てると
**第一の情報源が永久に使われない。** `Fx:Provider: "boj"` だけで動く。

**ただし FRED のキーが無い＝冗長化が無い状態は ADR-0022 決定2 が求める形ではない。**
**黙って単独運転にしない** —— 起動時に警告を出す（否定形テストで「揃っていれば警告しない」ことも固定した）。

### 決定6: 「カレンダーを持たないこと」を**構造で**固定する

ADR-0022 決定3 は「鮮度は営業日カレンダーではなく冗長化で担保する」と定めている。
**#381 起票時の実測では、この不変条件を固定するテストが存在しなかった。**

`FxCalendarIndependenceTests` を新設し、**FX 経路の型が `IMarketCalendar` / `MarketCalendar` を
参照しないこと**を反射で検査する。

> **なぜ「参照しないこと」を検査するのか**: 値の一致を見るテストでは捕まらない。カレンダーを導入しても
> 平常時のレートは同じ値になり、**祝日の並びが特殊な日にだけ挙動が変わる** ——
> つまり**普段は緑のまま、稀に誤判定する。最も見つけにくい壊れ方である。**

**「参照が無いこと」を確かめるテストは、検出器が壊れていても緑になる**（対象がゼロ件だからである）。
そこで**意図的に参照を持つ型を食わせて検出できることを同じ経路で示す**テストを対で置いた。

## 🔴 決定7: 受け入れ基準を実測した結果、計画との乖離を 1 件発見した（#506 へ切り出す）

**#381 の受け入れ基準「30 日超でも手仕舞い・損切りが止まらないこと（現状は未検証）」を検証したところ、
一致しなかった。**

```
Expected decision not to be <null> because
  ADR-0022 決定5 は 30 日超で新規建てのみを停止し、手仕舞い・損切りは止めないと定めている.
```

**機序**: `TradeDecisionService` の換算レートのゲートが**建玉効果を決めるより前**に置かれている
（LLM 費用を避けるための意図的な配置・IADR-0107 決定2/3）。**建玉効果が分かるのは LLM の判断後**であり、
結果として**出口が入口と同じゲートで塞がれている。**

**影響は非基準通貨（日本株）のみ**である（米国株は鮮度判定を経ず `FxRate.Identity` が返る）。
日本株の取引自体が [#397](https://github.com/endazon/ai-stock-trading/issues/397) で止まっているため**実害は潜在的**である。

**本 PR で直さない理由**: 決済へ載せる `FxRateToBase` の扱いを決める必要がある。
**既定の `1m` をそのまま載せると、JPY 建ての約定金額が USD として台帳へ記録され、
監査台帳（FR-11・7 年保持）の金額が約 150 倍にずれる。** 契約と永続化の変更を伴い、
**「情報源の二段化」とは別の決定**である。[#506](https://github.com/endazon/ai-stock-trading/issues/506) へ切り出した。

**現状はテストで固定した**（`鮮度切れは非基準通貨の手仕舞いも止める_計画との乖離_506`）。
**#506 が直した時点で赤になる** —— `KnownPlanDeviations` と同じ規律で、**乖離が解消したのに記録が残る状態を作らない。**

## 影響

- 肯定的:
  - **「常時鳴る警告」が解消する** —— 齢が最大 12.84 日から平常時 2〜4 日へ下がる。
  - **計画適合の逸脱 `Fx.RateSourceProviders` が解消した**（赤→緑を実測。下記）。
  - **カレンダー非依存が規約から機械の検査へ移った**（決定6）。
  - **未検証だった受け入れ基準を検証し、計画との乖離を 1 件発見した**（決定7）。
- 否定的 / トレードオフ:
  - **日銀 API の応答形式が変われば静かに壊れる。** CI は実 API を叩かない（外部依存で CI を落とさないため）。
    壊れたことは「レート無し → FRED へ縮退」として現れるため**安全側**だが、**気づくのは遅れる。**
  - **DTO が約 15 行重複する**（決定1・意図的）。
  - **切替・警告の可視化（日報・監査ログ・Discord）は未了。** 下記「残余リスク」。

### 🔴 変異試験（否定形テストが実際に効いているかを、実装を壊して確かめた）

| # | 変異 | 落ちたテスト |
| ---: | --- | ---: |

#### 🔴 変異試験そのものが欠陥を 1 件見つけた —— **弱い変異が生き残った**

**最初に試した変異 5 は生き残った**（`Failed: 0 / Passed: 2`）。原因は**変異が弱かった**ことである。
`ReferencesMarketCalendar` は「引数・フィールド・プロパティ・シグネチャ」の 4 つを `||` で繋いだ検出器であり、
**先頭の節だけを潰しても残り 3 つが拾ってしまう。**

> 🔴 **これは検出器ではなくテストの弱さである。** 初版は**4 経路すべてを備えた型を 1 つだけ**食わせており、
> **「どれか 1 つが生きている」ことしか示していなかった。1 つの節が静かに壊れても誰も気付かない** ——
> シグネチャの節だけが壊れれば、**メソッド引数でカレンダーを受け取る形が検出対象から漏れる。**

**是正**: 検出の**経路ごとに型を分けた**（引数のみ／フィールドのみ／プロパティのみ／シグネチャのみ／具象型）。
**無関係な型を誤検出しない**否定形も足した（何でも `true` を返す検出器は検査になっていない）。
**検出器全体を潰す強い変異では、是正後に 1 件が落ちる**ことを確認した。

> **「変異試験をした」だけでは足りない。変異が弱ければ何も示さない。**
> **変異の設計そのものがレビュー対象である**ことの実例である。

## 残余リスク

- 🔴 **切替と警告の可視化（ADR-0022 決定2・決定5）は未了である。**
  フォールバックへ切り替わった事実・鮮度警告は**現在ログにしか出ない。**
  計画は**日報・監査ログ・Discord の 3 経路**を求めている。**#381 の第 2 層として残っている** ——
  イベント型の新設を起点に **4 サービス（Contracts / Audit / Notification / Report）へ波及**するため分割した。
  **それまでは「黙って劣化する」状態が続く**（劣化そのものは第 1 層で大きく減るが、気づく手立ては弱いままである）。
- 🔴 **[#506](https://github.com/endazon/ai-stock-trading/issues/506) の乖離が残る**（決定7）。非基準通貨の手仕舞いが鮮度切れで止まる。
  **日本株が #397 で止まっている間は顕在化しない。**
- **日銀のクレジット表記が報告書へ出ていない。** 定数 `BojFxRateSource.Credit` は持たせたが、
  **報告書の為替欄への配線は第 2 層である。**
- **`null` の意味を区別できない**（欠測・休場・未収録が同じ `null`）。**計画も「区別しない」と明記している。**
- **実 API を叩くテストが無い。** 応答形式の変更は CI では捕まらない（決定は「外部依存で CI を落とさない」）。
