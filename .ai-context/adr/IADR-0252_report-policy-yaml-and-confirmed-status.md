# IADR-0252: 目標値の YAML 併記と、確定時の状態表記の同期

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（起票 #338）

## 起点・関連

- 関連する計画書 ID: FR-06・FR-07・FR-16・FR-17、計画 INDEX 決定29（YAML ブロック併記）・決定43（機密区分）
- 関連する実装仕様書: [`20260828_338_reporting-cycle-and-templates.md`](../specs/20260828_338_reporting-cycle-and-templates.md)

## コンテキストと課題

計画 INDEX 決定29 は次を定める。

> 報告書 Markdown 内に、人間可読の表と、AI 判断が機械パースする **YAML ブロック（```yaml フェンス）を併記**する。
> 翌営業日の売買条件（対象・条件・上限）は YAML を正とし、表は表示用とする。
> `report_type+period` をキーにナレッジベースへ保存し、**取引判断サービスは YAML ブロックのみを読む**。

ここには 2 つの罠がある。

1. **売買条件の構造化された供給が存在しない。** 方針本文（`PolicySummary`）は利用者が書く自由記述であり、
   自動生成では直近の確定済み方針を引き継ぐだけである（IADR-0115 決定4 / IADR-0125）。
   ここで散文から条件を読み取って YAML へ書き起こせば、それは**機械が発明した取引条件**である。
2. **本文は生成時に一度だけ組み立てられ、確定では作り直されない。**
   そのため frontmatter と YAML の `status:` は確定後も `draft` のまま残る。
   **確定済みの報告書が自分を「未確定」と名乗る**——#310（確定後も「未確定」を名乗る本文が
   取引判断へ渡っていた）と同じ形である。

## 検討した選択肢

1. 散文をパースして売買条件を YAML へ起こす
2. **機械が確実に知っている値だけを書き、売買条件は `null` と明示する**（採用）
3. YAML ブロックを出さない（供給が入るまで見送る）

確定状態については:

- A. 確定時に本文を**作り直す**
- B. **状態の行だけを書き換える**（採用）
- C. 何もしない（現状維持）

## 決定

**決定1: YAML には `report_type` / `period` / `status` / `based_on` / `assumptions_version` /
`confidentiality` を書く。** いずれも機械が確実に知っている値である。

**決定2: `trading_conditions: null` と明示し、注記で「未供給であり『条件なし』ではない」と書く。**
🔴 **空配列（`[]`）にしない**——「条件が無いことが確定した」と読め、
取引判断サービスは「条件ゼロ＝何も建てない」と読むか「制約なし」と読むかを決められない。
**散文からの推測でこの欄を埋めてはならない**ことを YAML 自身へ書く（読む側にも書く側にも効く）。

**決定3: 選択肢 3（見送り）を採らない。** 決定29 は「YAML を正とする」と定めており、
ブロックが無ければ取引判断サービスは Markdown 表をパースする経路を作らざるを得ない
（決定29 が明示的に禁じたこと）。**枠を先に置く。**

**決定4: 確定時は状態の行だけを書き換える**（`ReportBodyStatus.MarkConfirmed`・選択肢 B）。
`status: draft` の行と `confirmed_at:` の行のみを対象とし、**それ以外は 1 バイトも変えない**。
🔴 選択肢 A（作り直し）を採らない——**確定とは「その本文でよい」と利用者が承認した行為**であり、
散文（LLM 出力）が確定後に変わり得る実装は承認の意味を壊す。

**決定5: 書き換えは行単位で行う。** 散文に現れる同じ語（例: 引用としての `status: draft`）は変えない。
状態表記は必ず行そのものであるため、行一致で十分に区別できる。

## 理由

- 決定2 は FR-16（数値・条件を機械に発明させない）の直接の帰結である。
- 決定4/5 は、**確定という行為の意味**（承認した本文が保存される）と
  **読む側の要求**（状態は YAML から読む）を両立させる最小の変更である。

## 結果

- 良い影響: 取引判断サービスが YAML だけを読む前提が成立する。確定済み報告書が「未確定」を名乗らない。
- 悪い影響・トレードオフ: 売買条件は当分 `null` であり、取引判断サービスは
  従来どおり `GetConfirmedDailyPolicy()`（散文の方針）を読むしかない。
  **YAML が「正」になるのは売買条件の構造化された供給が入ってからである。**
- フォローアップ: 売買条件の構造化（画面または Discord から構造化入力を受ける経路）。
