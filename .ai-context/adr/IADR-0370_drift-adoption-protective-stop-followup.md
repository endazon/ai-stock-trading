## コンテキストと課題

取り込み（IADR-0350）は**リスク管理側の取引台帳だけ**を観測値へ合わせる。発注執行側の保護記録
（`protective_stop_orders`）は何も知らされず、ブローカー側の保護注文も残る。

- 記録が `Active` のまま残ると、ガードは実在しない建玉の保護レグを巡回し続ける。
- 🔴 より重いのはブローカー側である。**建玉が無いのに売りの逆指値が残れば、発火して意図しないショートが建つ。**

### ガードとの重なりを正直に測る

**S0 についてはガードが動いていれば既に収束する**（毎巡回ブローカーの建玉を照会し、残 0 の行の逆指値を
取り消して終端化する）。本 IADR が新たに閉じるのは 4 点である。

1. **即時性**（取り込みの瞬間。巡回 1〜2 周＝30〜60 秒を待たない）
2. **取消の確認**（ガードは `CancelOrderAsync` を投げっぱなしで記録を閉じる。確認しない）
3. **在庫の押さえの解放**（確認できた取消は `OrderCancelled` を出す。ガードの経路は 1 通も出さない）
4. **取り消せないときの Critical**（ガードは無音）

**建玉照会を持たない構成ではガードそのものが配線されない**ため、本 IADR が唯一の追随経路になる。

## 検討した選択肢

### 部分的な取り込みで、建玉を上回る保護レグをどうするか（issue の問い）

| 案 | 判定 |
| --- | --- |
| **数量を縮小する** | **不可。** 実 OpenD へ `TrdModifyOrder` を配線しておらず、訂正の口（`IOrderAmendmentBroker`）は moomoo 構成では登録されない（IADR-0067 / #847）。**構造的に選べない** |
| 取消 → 小さい数量で張り直す | **不採用。** 生きた保護を**確実に消して**、再発注が通る保証のない窓を作る（#857 で拒否の経路を実測済み）。IADR-0344 が繰り返し引いた赤線（生きた S0 の逆指値を取り消さない）と同じ判断 |
| **既存規則のまま「全部か 0 か」**（採用） | 帳簿だけの行（S1）が先に吸収し、S0 の実注文は残る。建玉を上回る逆指値が残り得る点は IADR-0344 追記(4) が既に受容した性質であり、本件で新たに生じるものではない |

### どの保護レグから減らすか（issue の問い: 新しい順／古い順／按分）

**巡回（`ProtectiveStopNetting`）が既に持っている規則を再利用する**——帳簿だけの行（S1）を先に使い切り、
実注文を持つ行（S0）は最後・全部か 0 か、それぞれ作成時刻 → `EntryDecisionId`。
新しい規則を作らないのは、**同じ問いに 2 つの答えがあると必ず片方が腐る**からである
（IADR-0344 追記(4) は、この順序を 5 巡の監査で決めている。作成時刻だけで決めると生きた逆指値が 0 にされる）。

## 決定

### 決定 1: 発注執行が `PositionDriftAdopted` を購読する

`PositionDriftAdoptedHandler`（`Infrastructure/Steps`）が受け、業務は `ProtectiveStopDriftAdopter`
（`Features/OrderExecution/AdoptPositionDrift`）が行う。**発行はハンドラ**（Features 層はメッセージ基盤を参照しない）。
キューは規約発見（IADR-0129）。サービス間の直接参照はしない（IADR-0350 決定 5 の指定どおり）。

### 決定 2: 目標は**絶対値**、割り当ては巡回と同じ規則

群＝その銘柄・市場・**方向**の `Active` な保護記録。目標＝`|LedgerQuantityAfter|`。
減らす量＝`群の主張の合計 − 目標`を `ProtectiveStopNetting.AllocateReduction`（既存の私有 `Allocate` を公開したもの）で配分する。
**差分ではなく絶対値**にするのは IADR-0350 決定 2 と同じ理由であり、**イベントの再送で二重に取り消さない**が
構造的に成り立つ（2 回目は「主張 ≦ 目標」で何もしない）。**増える方向・方向の反転は何もしない**
（リスク管理側で拒否済みだが、受け取った値を無条件に信じない）。

### 決定 3: 取り消す前に**新しい建玉照会**で裏を取る。取れなければ取り込みの観測に従う

取り込みが許す観測の古さは最大 60 分（IADR-0350 決定 1）。その間に利用者が買い戻していれば、
消すのは**実在する建玉の保護**である。よって建玉照会（`IBrokerPositionSource`。無い構成では null）が使えるなら
**その純額と取り込みの目標の大きい方**を目標に採る（**保護を消しすぎない側**へ倒す）。
照会が `null`（不明）なら取り込みの観測に従う——**何もしないと孤立した逆指値が残る**（本 issue が閉じる穴そのもの）
うえ、取り込みは利用者が承認し、処理中の決済が無いことも確認された操作である。
🔴 **いずれの分岐でも建玉を売る操作は 1 つも行わない**（取消と帳簿だけ。不明が自動決済を招かない）。

**［2026-09-24 追記 / PR #918 監査］照会が `null`・例外のときの扱いを改めた。** 末尾の追記 決定 3′ を参照。

### 決定 4: 数量の縮小・張り直しはしない

上表のとおり。S0 は「全部か 0 か」でしか動かさない。

### 決定 5: 取消は**確認できたときだけ**終端化する。できなければ Critical で知らせ `Active` のまま残す

`OrderAmendmentService.CancelAsync`（IADR-0357）を使い、確認できた（`AbandonsUnfilledRemainder`）ときだけ
返る `OrderCancelled` を発行して記録を終端化する。確認できない・例外のときは:

- 記録を**終端化しない**（`Active` のまま＝ガードが巡回を続ける）
- `SoftwareStopExecuted(Outcome=StopCancelUnconfirmed)`（Critical・末尾へ追加）を発行する
- **ハンドラは例外を投げない。** `PositionCloseCancellationHandler` は投げる作法だが、あちらは失敗を記録する
  経路が他に無く、再試行と `_error` キューが唯一の可視化である。こちらは
  「記録が `Active`」「Critical」「ガードの巡回」の 3 つが残り、投げると成功した行の処理まで捨てて再配送になる。

**［2026-09-24 追記 / PR #918 監査］建玉照会が不明・失敗のときだけは投げる**（どの行にも触る前なので捨てる成功が無い）。末尾の追記 決定 3′ を参照。

### 決定 6: 減らした行の未確定の観測は捨てる

取り込みで確定した減少は、ガードが観測していた**同じ外部要因**である。減らした行の
`PendingExternalReduction` / `ExternalReductionObservations` / `ExternalReductionAbsences` を 0 へ戻す
（残すと次の巡回が同じ減少をもう一度数えて削る）。

### 決定 7: 減少の通知は既存の `ProtectionReduced` を使う

「外部要因（手動決済・強制決済など）で建玉が減ったぶんを保護記録の主張から差し引いた。決済は出していない」は
取り込みそのものである。既に S0 の行の取消もこの結果で知らせる契約になっている（IADR-0344 追記(5)）。
**新しいイベント型は作らない**（監査・通知・契約基準の母集合を増やさない）。

## 理由

- **観測を権威にしない原則（IADR-0118）は保たれている。** 台帳を書き換えたのは利用者の承認つきの取り込みであり、
  発注執行はその結果に**保護の帳簿と注文を合わせる**だけである。建玉を売る判断はどこにも無い。
- **「取り消せた」と誤って主張しないこと**が最優先である（IADR-0357 と同じ）。誤って終端化すると、
  生きた逆指値が誰の巡回からも外れ、発火して反対建玉を生む——無音かつ不可逆である。
- **割り当て規則を再利用した**のは、#820 が 5 巡の監査で到達した順序（S1 → S0・全部か 0 か）を
  ここで独自に決め直すと、同じ事故（生きた逆指値が 0 にされる）を別経路で再現するからである。

## 結果

- 取り込みで建玉が消えた銘柄は、取り込みの瞬間に保護レグが取り消され、記録が終端化され、監査に残る。
- 取り消せなかった場合は Critical が出て、記録は巡回に残る（無音にならない）。
- 取り消せた場合は `OrderCancelled` が出るため、保護レグの承認行が押さえていた在庫が解放される。

## 残余リスク

- **部分的な取り込みでは、建玉を上回る S0 の逆指値が残る**（決定 4）。訂正の口が配線されれば縮小が選べる。
  現状は IADR-0344 追記(4) の受容範囲と同じであり、本 IADR で新たに生じるものではない。
- **建玉照会を持たない構成**では、最大 60 分古い観測だけを根拠に取り消す（決定 3）。
- ガードと本経路は**同じ規則**で同じ帳簿を動かすため、ほぼ同時に走っても結果は同じ（目標は絶対値）だが、
  **同一行への同時書き込みは後勝ち**である（既存の保護記録ストアの性質。本 IADR で変えていない）。

## 追記

### ［2026-09-24 追記 / PR #918 監査］決定 3′: 建玉照会が不明・失敗なら、帳簿もブローカーも変えずに再試行へ回す

**変更した決定**: 決定 3 の後段「照会が `null`（不明）なら取り込みの観測に従う」を撤回する。
建玉照会を持つ構成（`IBrokerPositionSource` が登録されている＝moomoo 構成）で、照会が `null` を返す・例外で落ちるときは:

1. **保護記録もブローカー側の保護注文も 1 つも変えない**（S0 の取消も、S1 の主張の削減もしない）。照会は群のどの行にも触る前に行う。
2. **Critical をログする**（取り込み ID・銘柄・台帳の前後・依頼者と、「証券会社の画面で建玉と未約定の逆指値を確認する」）。
3. `ProtectiveStopDriftPositionsUnknownException` を投げ、**共通の再試行（IADR-0129 決定 5: 2s/10s/30s → `<queue>_error`）**に照会をやり直させる。
   作法は `OrderDispatchReservationConflictException` と同じであり、新しい仕組みは足さない。

**空の一覧は信じる**（照会は成功し、0 株と答えた）。**建玉照会を持たない構成**（内蔵 paper。注入が null）は従来どおり取り込みの観測に従う ——
そこでは「照会が落ちた」ではなく「照会という手段が無い」であり、何もしなければ唯一の追随経路が消える。

**併せて**: 主張の合計が取り込みの目標以下なら、**照会せずに**何もしない（目標は `max(照会の純額, 取り込みの目標)` なので、
照会の答えに依らず減らすものが無い）。照会が落ちているときに無用な再試行と `_error` を作らないためである。

**理由**: 保護を取り消してよいのは「建玉が消えたと確かめられたとき」だけである（所有者の常設の規則）。
取り込みの観測は最大 60 分古く、確かめたことにならない。旧決定は「孤立した逆指値を残さない」を優先して、
その間に買い戻された実在の建玉の保護を消し得た —— 無保護は無音で、逆指値の残存（下記）より重い。
監査は旧決定を固定していた試験（照会の例外でも取り消して `Completed`）と、生き残った変異
（「`null` を 0 株と読む」）を指摘した。

**Critical を発行（イベント）ではなくログで出す理由**: Wolverine はハンドラが例外を投げると、その処理中に発行したメッセージを捨てる
（`Executor.ExecuteAsync` の失敗経路が `context.ClearAllAsync()` を呼ぶ。WolverineFx 6.24.5 を逆コンパイルして確認）。
発行してから投げる形は、単体試験（発行を記録するだけの替え玉）では緑になり、本番では 1 通も届かない。
`_error` キューの滞留と Critical ログで気付く運用は既存の「発注予約の滞留」と同じである（運用手順書）。

**代償（受け入れたもの）**: 照会が落ち続けるあいだ、**取り込みで消えたはずの建玉の保護逆指値がブローカーに残る**。
建玉が本当に無ければ、発火して意図しないショートが建ち得る（#853 のリスク）。この状態は**無音ではない** ——
Critical のログが再試行のたびに出て、使い切ったメッセージは `_error` キューに残る（再投入はインシデント対応）。
照会が回復すれば、ガードの巡回が既存の規則（外部要因の観測・確定）で保護を収束させる（S0 の残 0 の取消を含む）。

**試験**: T-10-734（照会の例外 → 変えない・Critical・例外）、T-10-735（`null` を 0 株と読まない。S0 と S1 の両方を変えない）、
T-10-736（主張 ≦ 目標なら照会しない）、T-10-737（増加・反転の検査を S1 で固定。S0 だけでは「全部か 0 か」が覆い隠していた）、
T-10-738（同じ銘柄の S1 が 715 株・713 株の 2 行。古い行から使い切る）、T-10-739（ハンドラは握らずに投げる）。
