# IADR-0269: 日報の取引履歴・ポジション一覧は出口のゴールデンで結線を固定し、判断根拠は監査台帳の記録を LLM を介さず転記する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-08-29
- 決定者: endazon（利用者・マージ判断）/ 実装エージェント（起案）

## 起点・関連

- 関連する計画書 ID: FR-16（テンプレート準拠・**数値はコード集計であり LLM に計算させない**）、FR-06（報告書の階層管理）、FR-11（監査記録）、UC-05（日報）
- 対象 Issue: [#563](https://github.com/endazon/ai-stock-trading/issues/563)
- 関連する実装仕様書: [20260829_563_trade-history-wiring-and-supply](../specs/20260829_563_trade-history-wiring-and-supply.md)
- 関連 IADR: [IADR-0042](IADR-0042_report-review-state-machine-and-detail-rendering.md)（明細を独立純関数レンダラにし、**本文への合流は後続**と明記した）、[IADR-0032](IADR-0032_report-generation.md)（純関数テンプレート化）、[IADR-0115](IADR-0115_report-auto-generation-scheduler.md)（自動生成・供給不達の倒し方）、[IADR-0199](IADR-0199_fx-status-supply-wiring.md)（監査台帳からの期間照会の作法）、[IADR-0251](IADR-0251_report-numeric-aggregation-outside-llm-context.md)（数値を LLM の文脈へ入れない）

## コンテキストと課題

`TradeHistoryRenderer`（日報 §2）は IADR-0042 で純関数として実装され、単体テストも揃っていた。しかし
**本番コードからの呼び出しが 1 件も無く**、生成される日報の本文に §2 取引履歴（全明細）・取引詳細・
見送り判断・§3 ポジション一覧が**一度も現れていなかった**（#563）。

見逃された理由は 2 つあり、どちらも「検査はあるのに検知しない」形である。

1. `TradeHistoryRendererTests` は**レンダラを直接叩く**ため、結線が無くても緑になる。
2. `ReportRenderer` のゴールデンは**現在の出力**を固定する。節が無い状態がゴールデンとして凍結され、
   **不在が「正しい」として守られていた。**

さらに、結線するだけでは明細が埋まらない。レンダラが求める項目のうち、**判断根拠・トリガー・取引詳細・
見送り判断**は台帳から引けない。これらを LLM に書かせることは FR-16・IADR-0251 が禁じている。

## 検討した選択肢

### A. 結線の固定の仕方

1. **`TradeHistoryRenderer` が呼ばれたことを検証する**（呼び出し回数のスパイ）— **採らない**。
   「呼ばれたこと」と「結果が出口へ出たこと」は別の事実である。整形の途中で落ちても呼び出しは成立する。
2. **出口（`ReportRenderer` の本文）の全文ゴールデンで固定する（採用）** — 節が消えれば全文が一致しなくなる。
   加えて出口の焦点テスト（`ReportRendererTradeHistoryTests`）と、供給から永続化まで通す
   `ReportAutoGeneratorTradeHistoryTests` を置く。

### B. 判断根拠の供給元

1. **報告書生成時に LLM へ書かせる** — **禁じられている**（FR-16・IADR-0251）。
2. **取引判断サービスへ同期照会する** — あちらは根拠を**ログにしか残さず**、状態もプロセス内であるため、
   期間の集計の権威源にならない（IADR-0199 決定1 と同じ理由）。
3. **監査台帳の `TradeDecisionMade` を `DecisionId` で引く（採用）** — 判断時に記録された文字列を
   7 年保持しており、**そのまま転記できる**。

### C. 引けない項目の描き方

1. 0・空文字・列挙の既定値で埋める — **採らない**。「税 0」「定時」「見送りなし」はいずれも**事実の主張**になる。
2. 節ごと出さない — **採らない**。#563 はまさに「節が消えていた」事故である。
3. **未供給として明示する（採用）** — 本サービスの既存 2 系統（節レベルの「照会できませんでした」／
   セルレベルの標識）に倣う。

## 決定

### 決定 1: 結線は**出口の全文ゴールデン**で固定する

`ReportRenderer` が日報の本文で `TradeHistoryRenderer` を呼び、§3 ポジション一覧を描く。
固定は `Golden/daily-supplied.md` / `Golden/daily-unsupplied.md` の**全文**で行う。
**呼び出しの有無を見るテストは置かない。**

あわせて、`ReportRendererReportingCycleTests` の順序検査が `IndexOf` の **-1 を許していた**穴を塞ぐ
（見出しが消えても「YAML はそれより後ろ」が真になり、**節の消滅を緑で通していた**）。
順序を見るテストは**見出しの実在を先に主張する**。

### 決定 2: 判断根拠は監査台帳の記録を `DecisionId` で引いて**そのまま**載せる

- 新ポート `ITradeRationaleSource` と `HttpTradeRationaleSource`（`GET /audit/events/by-type?types=TradeDecisionMade`）。
- 突き合わせの鍵として、**台帳の約定に `DecisionId` を載せる**（`LedgerFill` → `/risk-controls/fills` の
  JSON → `PeriodTradeFill`）。台帳は `TradeFillRow.DecisionId` を既に保持しており、公開していなかっただけである。
- **相関できない約定へ近い記録を当てはめない。** `Guid.Empty`・辞書に無い鍵・空の根拠はその行だけ未供給になる。
- **契約イベントは新設しない。** 引きたい記録は既に発行・監査記録されているため、6 レジストリへの追随は生じない。

### 決定 3: 引けない項目は**未供給として明示**する（0・「該当なし」へ倒さない）

供給できない項目と、その理由（記録源が無いこと）は次のとおりである。

| 項目 | 引けない理由 |
| --- | --- |
| 銘柄名 | 台帳は銘柄コードのみを保持する（`LedgerFill` / `ApprovedOrderRow`） |
| 税 | 源泉徴収税額は**期間合計にのみ**課される（`PnlAggregator`）。約定単位へ配分する規則が計画にも実装にも無く、按分は発明になる |
| トリガー | 判断の起点は記録されていない。`DecisionTriggerKind` は取引判断サービスの**プロセス内**にしか無く、`TradeDecisionMade` にも `OrderIntent` にも列が無い |
| 取引詳細（5 項目） | 選定理由・参照情報・想定シナリオ・結果と評価を**分けて持つ記録が無い**。`Rationale` は単一の自由文であり、5 項目へ割り付けると構造の捏造になる |
| 見送り判断 | Hold は**ログにしか残らない**（`TradeDecisionAppService` の Hold 分岐は `return null` する）。台帳に 1 件も無いため「（見送りなし）」は嘘になる |
| 借株料累計（§3） | 引けるのは**当期間の計上額**であり、建玉開始からの累計ではない |
| 保有日数（§3） | 台帳の射影が建玉の**開始時刻**を持たない |

表記は既存の 2 系統に揃える。**新語を作らない。**

- **節レベル**: `- **<対象>を照会できませんでした（供給元がありません）**: 「<言い換え>」とは区別しています。`
- **セルレベル**: `**未供給**`（標識）＋**表の直下の凡例**で意味を定義する。
  セルごとに長文を書くと 12 列 × N 行が読めなくなるため、意味の定義は 1 箇所に置く。

**約定 0 件は未供給ではない**（§1 サマリの取引回数 0 と整合する事実）。`（当日の約定なし）` を出す。

### 決定 4: 供給不達の倒し方は「その値が本番で実在し得るか」で決める

| 供給 | 不達時 | 理由 |
| --- | --- | --- |
| 約定（既存） | **空列** | 約定 0 件は §1 サマリの取引回数 0 と整合する事実であり、報告書は発注判断をしない（IADR-0115 決定5） |
| 判断根拠（本決定） | **`null`（未供給）** | 判断根拠は本番で実際に記録されている。「根拠なし」は説明責任が果たされていない状態を正常に見せる |
| 建玉（本決定） | **`null`（未供給）** | 建玉は本番で実在し得る。空列は「今は何も持っていない」という別の主張になる |

**隣に逆向きの前例があるため、後から「揃える」方向の整理で壊されやすい。揃えてはならない。**

### 決定 5: 日報の節番号を計画の並びへ寄せる（週報・月報は動かさない）

> 🔴 **［2026-09-03 追記］本決定の「出力順に連番を振る」部分は、計画 ADR-0030（Accepted・2026-09-03）で覆された。**
> ADR-0030 決定1 は「報告書の節番号・節順は計画 `04_report-templates` を正とする」と定め、**「見出し語は計画から採る」は
> 維持したうえで「出力順に連番を振る」だけを改めた**。あわせて決定5（日報の §5 市況・特記事項と §6 振り返りの統合）も
> 覆り（ADR-0030 決定5）、日報は計画どおり 7 節・週報 6 節・月報 8 節を出す。**未実装の節は番号を詰めず、見出しごと出す**
> （ADR-0030 決定2・決定3）。実装側の追随は [IADR-0291](IADR-0291_report-sections-follow-plan-numbering.md) にある。
> **以下の本文は 2026-08-29 時点の記録として残す（凍結記録は書き換えない）。**

日報は §2 に散文、§3 に方針を置いていたため、計画の §2 取引履歴と**衝突する**。
本実装は既に「**出力順に連番を振り、見出し語は計画から採る**」規約で動いている
（月報の §5 稼働率 / §6 三者比較 / §7 LLM 実績は計画の §6.2 / §5 / §7 と番号が違う）。これに従い日報は

`1 当日サマリ / 2 取引履歴（全明細）/ 3 ポジション一覧 / 4 リスク統制の記録 / 5 市況・振り返り / 6 翌営業日の方針`

とする。§1〜§5 は計画の日報テンプレートと一致する。**計画 §5 市況・特記事項と §6 振り返りを実装が
1 節へ統合している**ぶん、計画 §7 翌営業日の目標が実装では §6 になる。**週報・月報の並びと番号は変更しない**
（計画の粒度対応表が明細ではなく集計を求めているため、明細も §3 も出さない）。

### 決定 6: §3 の建玉は**照会時点**であり、期間末のスナップショットではない

台帳は建玉の履歴スナップショットを持たない。生成は当該取引日の生成境界の直後に走る（IADR-0115）ため
実務上は「当日終了時点」に一致するが、**過去の期間を後から再生成しても当時の建玉は復元できない**。
そのため `IOpenPositionSource` は**期間を引数に取らない**——期間で絞れているかのように読める形にしない。

## 理由

- 出口で固定することで、**結線を外すと全文ゴールデンが赤くなる**。#563 の再発経路（レンダラ単体テストだけが
  緑で、不在がゴールデンに凍結される）を構造的に塞げる。
- 判断根拠を台帳から転記することで、**説明責任の記録を報告書に出しつつ FR-16 の禁止（LLM に書かせない）を守る**。
  相関の鍵（`DecisionId`）は台帳が既に持っており、新しい記録も新しい契約イベントも要らない。
- 未供給を明示することで、「引けなかった」と「無かった」が**読み分けられる**。これは本サービスが
  他の全ての節で守っている規律であり、明細だけ例外にする理由が無い。

## 結果

- 良い影響: 日報の本文に §2 / 取引詳細 / 見送り判断 / §3 が**実際に出る**。判断根拠は記録から出る。
  引けない項目は「引けていない」ことが読者に伝わる。
- 悪い影響・トレードオフ:
  - 明細の表に `**未供給**` が多く並ぶ（現在の記録の実態そのものである）。記録源が増えれば減る。
  - 日報の節番号が動くため、既存の日報本文（生成済み）と番号が揃わない。**過去の本文は書き換えない**
    （生成物であり、生成時点の形が記録である）。
  - `/risk-controls/fills` の JSON に項目が 1 つ増える。**後方互換**（欠落は `Guid.Empty`＝相関できない）。
- フォローアップ（**いずれも計画側の欠落ではなく実装側の未実装**。planning への環流はしない）:
  1. **トリガーの記録**: `TradeDecisionMade` へ起点（定時 / 変動）を載せるか、別の記録を足す。
     計画の「損切り」区分は機械執行であり `DecisionTriggerKind` にも無いため、3 区分の写像を先に決める必要がある。
  2. **見送り判断の記録**: Hold をイベント化する（現状はログのみ。IADR-0104 決定6 の「イベントを増やさない」
     方針との整合を先に判断する）。
  3. **取引詳細の 5 項目**: 記録の形（構造化された判断記録）を決める。**LLM に書かせない前提を崩さない形**が要件。
  4. **銘柄名・保有日数・借株料累計**: それぞれ記録源の追加が要る。
