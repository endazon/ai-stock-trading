# IADR-0316: ログ出力前の正規化を共有純関数へ集約し、契約プロジェクトへ置く

- 状態: Accepted
- 日付: 2026-09-09
- 決定者: 実装担当（#708 の是正）

## 起点・関連

- 関連する計画書 ID: NFR（無採番。理由は作業仕様書 §起点 —— 計画の非機能要件表に「ログの完全性」に当たる番号が無い）
- 関連する実装仕様書: `.ai-context/specs/20260909_708_log-forging-sanitization.md`
- 起票: #708（CodeQL `cs/log-forging` 2 件・CWE-117。`MSP#1015` の受け皿）

## コンテキストと課題

`HttpReportNarrativeDrafter` が `logPrompts=true` のときプロンプト本文と LLM 生出力を
`ILogger` の引数へ素通ししていた。どちらも改行・CR・ESC・U+2028 を含み得るため、
**行指向のログへ偽の行を注入できる**（CWE-117）。走査の結果、同型は他サービス・共有物にも
**計 13 箇所 / 8 ファイル**あった（内訳は作業仕様書）。

決めるべきは 3 点である。

1. **既定オフ（IADR-0061 決定1）で足りるか。**
2. **共通の正規化関数をどこへ置くか。**
3. **長さ上限をいくつにし、超過をどう表すか。**

## 検討した選択肢

### (1) 既定オフを統制とするか / 発生源で正規化するか

| 案 | 評価 |
| --- | --- |
| A. 既定オフのままとし、有効化を運用で戒める | ✗ **有効化した瞬間に露出する。** 有効化するのは障害調査の最中——最も注意が薄い局面である。「統制を定めた」と「統制が働いている」が一致しない |
| **B. 既定オフは維持し、加えて発生源で正規化する** | ✔ 採用。既定オフ（機微をログ基盤へ流さない＝最小権限）と、正規化（流すときは行を割らせない）は**別々の脅威に効く**ため排他ではない |
| C. ログ基盤側（Serilog sink / OTel collector）で正規化する | ✗ 基盤（microservices-platform）の管掌で本リポからは配備できない。多層防御として望ましいが、**本件の代替にはならない** |

### (2) 共有関数の置き場

| 案 | 評価 |
| --- | --- |
| **A. `AiStockTrading.Shared.Contracts`（`Logging/LogSanitizer.cs`）** | ✔ 採用。**消費側 8 ファイルすべての推移閉包に既に入っている唯一の共有プロジェクト**であり、`ProjectReference` を 1 本も足さずに済んだ（実測: 追加後 `dotnet build backend/backend.slnx` が csproj 無改修で緑）。外部ライブラリ依存ゼロという同プロジェクトの制約（`SharedProjectDependencyTests`）も、純関数であるため満たす |
| B. `AiStockTrading.Shared.Infrastructure` | ✗ #708 の当初案。`NotificationService` と `Shared.KnowledgeBase` が同プロジェクトを参照しておらず、**参照を 2 本足す**ことになる。とくに `Shared.KnowledgeBase`（platform 文書 API の細いクライアント）が**文字列関数 1 個のために OpenTelemetry を推移的に引く**のは、依存の向きとして不健全である |
| C. `AiStockTrading.Shared.Kernel` | ✗ 「サービスを跨いで共有する **Domain 型**」の置き場（IADR-0260）。ログはインフラの関心事であり Domain 型ではない |
| D. サービスごとに小さな static ヘルパを置く | ✗ 13 箇所 8 ファイルに同型が散る。**規約の一致を人手で保つ**ことになり、次の追加で必ずずれる |
| E. 既存の `ReportSummarySanitizer` / `PromptSafetySanitizer` を流用・統合する | ✗ **要件が逆である。** 両者は人が読む本文（Discord 投稿・LLM プロンプト）向けで**改行を残す**。ログ値は 1 行に収める必要がある。IADR-0116 決定3 が「宛先の脅威モデルが違うなら型を共有しない」と決めた判断をここでも踏襲する |

> 🔴 **B を採らなかったことの読み替え注意。** これは「ログはインフラの関心事ではない」という主張ではない。
> **純関数であるがゆえに、依存グラフ上いちばん浅い場所へ置ける**という理由であり、
> 外部ライブラリを要するログ関連の共有物が将来出てきたら、それは `Shared.Infrastructure` 側である。

### (3) 上限と超過の表し方

| 案 | 評価 |
| --- | --- |
| **A. 既定 4,000 文字で切り、`…(truncated N chars)` を付ける** | ✔ 採用。**切ったことを黙らせない**（黙って切ると「LLM の出力が短かった」と読めてしまい、調査を誤らせる）。呼び出し側は引数で上げられる |
| B. 上限なし | ✗ 数万文字のプロンプトが 1 レコードに入り、ログ基盤側で切られる。**どこで切れたか誰も知らない**形になる |
| C. 上限で切り、注記も付けない | ✗ 上記のとおり、切れた事実が失われる |

## 決定

1. **既定オフ（IADR-0061 決定1）は維持する。本 IADR はそれを置き換えず、加える。**
   ログへ渡す外部由来の文字列は、**その値をログの引数に渡す直前**で正規化する。
2. 正規化は `AiStockTrading.Shared.Contracts.Logging.LogSanitizer.Sanitize` に集約する
   （純関数・外部依存ゼロ・`ProjectReference` の追加なし）。
3. 変換規則: 制御文字（C0・C1。U+0085 を含む）と U+2028 / U+2029 を `'_'` へ **1:1 置換**する。
   既定 4,000 文字で切り、`…(truncated N chars)` を付ける。サロゲートペアは割らない。`null` は透過。
4. **消さない。** 値をログから落とす実装は採らない —— 落とすと「正規化した」と「そもそも書かなかった」が
   区別できず、IADR-0061 決定1 の全量記録という目的自体が失われる。テストは
   **陽性対照**（素通しなら行が割れること）と**残存**（正規化後も本文の識別部分が残ること）を対で持つ。
5. **原文は改変しない。** 正規化するのは**ログへ渡す値だけ**である。送信本文・保存内容・欠測記録
   （`HistoricalBarGap.Reason`・`CreateDocumentBody.Title`）は原文のまま残す。

## 理由

- **統制は「有効化した瞬間」に効いていなければならない。** 既定オフは露出面を狭めるだけで、
  露出したときの安全性を何も担保しない。発生源で正規化すれば、`logPrompts` の値に関係なく行は割れない。
- **置き場は依存グラフで決まる。** 関数が外部ライブラリを要さない以上、
  いちばん浅いプロジェクトへ置くのが最も追加コストが小さい（実測で `ProjectReference` 追加 0 本）。
- **上限は「調査に足りる長さ」であって「全量」ではない。** 全量が要る調査は、
  ログではなく LLM ゲートウェイ側の記録を見るべきである（本リポからは配備できない）。

## 結果

- 良い影響:
  - 走査で見つかった同型 13 箇所が 1 つの規則を通る。次に同型が増えても呼び出しは 1 行で済む。
  - `ProjectReference` を 1 本も足していないため、依存グラフと Architecture.Tests の前提が変わらない。
- 悪い影響・トレードオフ:
  - **`Shared.Contracts` に「契約でないもの」が入った。** 既に `LlmStopReasons` 等の純粋な判定関数が
    同居しており前例はあるが、**契約プロジェクトの意味が薄まる**方向の変更ではある。
    外部ライブラリを要するログ共有物が出た時点で `Shared.Infrastructure` 側に第 2 の置き場ができ、
    **2 箇所に分かれる**。そのときは本 IADR を supersede して置き場の規則を決め直すこと。
  - **上限 4,000 文字はプロンプト全量には足りない。** 障害調査でプロンプト全量が要ると分かった時点で、
    呼び出し側が `maxLength` を上げられる形にしてある（既定値の変更ではなく呼び出し側で上げる）。
  - **素通しの再発を止める機械検査は無い。** 規約「検査器の追加は同型事故 2 回から」に従い、
    本件（1 回目）では検査器を作らない。再発検知は CodeQL に委ねる。
- フォローアップ:
  - `MSP#1015`（基盤側）のクローズは本作業の範囲外。**AST 側の是正のみ**を行った。
  - 計画の非機能要件表に「ログの完全性（外部由来文字列の無害化）」に当たる番号が無い。
    番号を新設するか、以後も無採番で通すかの裁定を計画へ環流する候補である（起票は親が判断する）。
