# IADR-0151: リスク上限の画面表現は百分率（%）とし、統制を無効化する値はサーバのドメイン値域で拒否する

- 状態: Accepted
- 日付: 2026-08-05
- 決定者: 実装（Claude Code）／ 起点 [#362](https://github.com/endazon/ai-stock-trading/issues/362)
- 作業仕様書: [20260805_362_sc02-ratio-input](../specs/20260805_362_sc02-ratio-input.md)

  [IADR-0146](./IADR-0146_backend-response-contract-fixtures.md)（契約フィクスチャ）
- 関連する実装仕様書: [画面仕様書 SC-02](../../docs/screens/20260718_SC-02_risk-settings.md)

## コンテキストと課題

[IADR-0130] 決定1 が金額系の統制上限を **equity 比**へ入れ替えた結果、SC-02 の入力欄が扱う値は
「35,000（円）」から「0.25（比率）」へ**意味ごと**変わった。[#389] は読み取り側だけを是正し、
**書き込み側（PUT）は旧名のまま据え置いた**——キー名だけを合わせると、金額のつもりで `35000` と
入力した値が **equity の 35,000 倍**として保存され、統制が無効化された状態で保存が成功するためである。

**この 400 は今この事故を防いでいる唯一の壁である。** そして本作業はその壁を外す。

外した先で何が守るのかを実地に確認したところ、**サーバ側にリスク上限の値域検証は一切存在しなかった**。
`PUT /risk-controls/settings/limits` は `RiskSettingsService.UpdateLimits` を呼ぶだけで、actor / reason の
空検査しか行われない。**`MaxOrderAmountRatio = 35000` は現在のサーバがそのまま受理する。**
今 400 になっているのは値が危険だからではなく、**フロントが送るキー名が `required` プロパティを
満たさないから**にすぎない。キー名を直せば、この偶然の防壁は消える。

決めるべきことは 2 つある。

1. **画面が扱う割合の表現**（`0.25` か `25%` か）
2. **統制を無効化する値をどこで拒否するか**

## 検討した選択肢

### 論点 A: 割合の画面表現

| 案 | 内容 | 誤入力が外れる向き | 評価 |
| --- | --- | --- | --- |
| A-1 | 比率（`0.25`）をそのまま入力させる | 百分率のつもりで `25` → **equity の 25 倍**（統制の消滅） | 棄却 |
| **A-2** | **百分率（`25`）で入力させ、ワイヤは比率のまま** | 比率のつもりで `0.25` → **0.25%**（過度に厳しい＝取引が止まる） | **採用** |
| A-3 | 両方を並べて入力させ、一方から他方を自動計算する | 2 つの入力欄が同じ値を表す＝どちらが正かが画面上に現れない | 棄却 |

**誤入力の向きが決定的である。** どちらの表現でも「桁を 100 倍取り違える」誤りは起こるが、
**A-1 の取り違えは統制を消し、A-2 の取り違えは統制を過度に締める**。前者は資金を失う経路であり、
後者は発注が通らないだけである。統制の設計では、外れる向きが安全側であるほうを選ぶ。

計画（05_screens SC-02）が表記例を **「25%（$750）」**と百分率で書いていることとも一致する。

A-3 は一見親切だが、**同じ値の入力口を 2 つ作る**ことになる。[IADR-0130] 決定1 が「固定額と比率の両方を持つ」
案（A-2）を「2 つの真実源。どちらが効いたかが実行時にしか分からない」として棄却したのと同じ理由で採らない。

### 論点 B: 値域の関門をどこに置くか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | 画面（フロント）だけに置く | **API 直叩きで消える。** [IADR-0141] 決定1 が発注先の切替で同じ判断をしている。統制の関門を画面だけに置くのは「鍵をかけたつもり」に等しい | 棄却 |
| B-2 | サーバだけに置く | 迂回はできないが、利用者は**保存を押すまで誤りに気付けない**。8 項目のフォームで 1 つが範囲外のとき、どれが悪いかを 400 の本文から読ませることになる | 不十分 |
| **B-3** | **ドメインに規則を 1 本置き、サーバ（実効）と画面（前段の即時提示）の双方がそれを満たす** | 規則の記述は 1 か所（`RiskLimitBounds`）。画面は同じ表を UI として持つが、**実効はサーバ側**である | **採用** |

### 論点 C: 値域の上限をどう決めるか

計画 §5 は**既定値**を定めるが、**設定できる範囲**は定めていない。したがって範囲は実装が決めるほかない。
決め方には次の 2 案がある。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C-1 | 「既定値の N 倍まで」のように既定値からの相対で決める | 既定値が変われば範囲も動く。既定値の変更（計画改訂）が意図せず範囲を緩める | 棄却 |
| **C-2** | **各項目の意味から「それを超えると統制でなくなる」点を絶対値で決める** | 根拠が項目ごとに説明できる。既定値の改訂と独立している | **採用** |

## 決定

### 決定1: 画面（表示・入力）は百分率（%）、ワイヤ（HTTP・永続化・ドメイン）は比率のまま（案 A-2）

- SC-02 のリスク上限のうち **equity 比の 5 項目**（1 注文発注額上限・1 日発注額上限・日次損失上限・
  1 取引あたりリスク・最大 DD 上限）を **%** で表示・入力する。既定値は `25` / `150` / `2` / `1` / `10` と表示される。
- **バックエンドは一切変えない**（`RiskLimitSettings` は比率のまま）。[IADR-0130] の決定は 1 つも動かない。
- **% ⇄ 比率の変換は `contracts.ts` の 2 関数（`percentTextToRatio` / `ratioToPercentText`）だけを通す。**
  呼び出し側で `× 100` / `÷ 100` と書くことを許さない（[IADR-0130] 決定1 が解決点を 1 本に閉じたのと同じ規律。
  分散すると「どちらの単位の値か」が呼び出し側ごとにぶれる）。
- **変換は 10 進文字列の小数点移動で行う。** `Number(s) / 100` は `2 / 100 = 0.02` のように多くの場合は
  期待どおりだが、丸めの誤差が**統制値に紛れ込む経路**を残す（`decimal` で受けるサーバ側に
  `0.020000000000000004` が保存され得る）。文字列操作なら誤差は原理的に生じない。
- **単位が異なる 3 項目は % にしない**——保有建玉数上限・連敗しきい値は**件数**、連敗時サイズ縮小係数は**倍率**である。
  これらを % に見せると別の取り違えを作る。**各入力欄には単位を明示表示する**（`%` / `%/日` / `件` / `連敗` / `倍`）。

### 決定2: 値域はドメイン（`RiskLimitBounds`）に 1 本置き、サーバが実効させる（案 B-3・C-2）

| 項目 | 下限 | 上限 | 上限の根拠 |
| --- | --- | --- | --- |
| `MaxOrderAmountRatio` | > 0 | ≤ **1.00**（100%） | 1 注文で equity 全額を超える発注枠は「上限」として意味を持たない |
| `MaxDailyOrderAmountRatio` | > 0 | ≤ **10.00**（1000%/日） | 既定 1.50 は建玉 1 回転（75%）の 2 回転。10 回転超はスキャルピング領域であり戦略時間軸（日中スイング）と整合しない（計画 §5 の 1 日上限の根拠） |
| `MaxOpenPositions` | ≥ 1（整数） | ≤ **20** | 既定 3（ADR-0016 決定9）。0 は「取引できない」であって上限設定ではない |
| `DailyLossLimitRatio` | > 0 | ≤ **0.20**（20%） | 既定 0.02。最大 DD 上限（10%）を大きく超える日次許容は、DD 統制より先に効くことがなくなり統制として成立しない |
| `PerTradeRiskRatio` | > 0 | ≤ **0.10**（10%） | 既定 0.01。サイジングの基礎であり、10% を超えると 3 建玉で equity の 30% を 1 日で失い得る |
| `MaxDrawdownRatio` | > 0 | ≤ **0.50**（50%） | 既定 0.10。50% の DD からの回復には +100% を要し、「到達で全停止・再検証」（計画 §5）の目的を果たさない |
| `LosingStreakThreshold` | ≥ 1（整数） | ≤ **20** | 既定 5 |
| `LosingStreakSizeFactor` | > 0 | **< 1.00**（1 を含まない） | 既定 0.5。**1.0 は「縮小しない」＝連敗時縮小の無効化**である。統制を無効化する値を設定値として認めない |

- 違反時は **400**（`{error, details}`）を返し、**設定を一切変更せず履歴も残さない**（[IADR-0141] と同じ規律。
  拒否された要求を履歴に積むと、実際には起きていない変更が監査上の事実になる）。
- `RiskSettingsService.UpdateLimits` も同じ関数を呼び、違反時は `ArgumentException` を投げる。
  エンドポイント以外の呼び出し口が将来増えても不変条件が保たれる（既存の例外フィルタが 400 へ写像する）。
- **画面は同じ表を UI として持つ**が、それは利用者への即時提示のためであり、**実効はサーバ側である**。

### 決定3: PUT の是正はバリデーションと同一の変更で行う（分離しない）

PUT のキー名を `*Ratio` へ直すことと、値域の関門を置くことは、**同じ変更として入る**。
「先にキー名だけ直して後でバリデーションを足す」順序は許さない——その中間状態では、
**統制を無効化する値の保存が成功する**（現在の 400 が偶然の防壁であるため）。

### 決定4: 実額は基準通貨（円）建てで併記し、「$」を付けない

計画 05_screens SC-02 は「25%（**$750**）」と USD 表記を求めるが、実装が供給する
`RiskStatusView.capital` は**基準通貨（円）建て**である（[IADR-0130] 決定3。`MarketCurrency.Base = Jpy`）。
**円建ての数値に「$」を付けることは単位の取り違えそのもの**であり、[IADR-0130] 決定1 が最も危険と
指摘した誤りの型と同じである。よって実額は円建てとして表示し、**その旨を画面に明記する**。
USD 表記への切替は判定通貨の USD 移行（[IADR-0130] 決定3 の未決事項）と同時に行う。

保存前の入力値に対する実額は **`capital × 入力比率`** を画面が計算する（サーバの
`RiskStatusView.maxOrderAmount` は**現在保存されている設定**から解決した実額であり、入力中の値は表せない）。
この計算も 1 関数（`resolveEquityAmount`）に閉じ、equity の出どころを 1 つに保つ。

## 理由

- **決定1（%）**: 取り違えは必ず起こる。設計で選べるのは「起きたときにどちらへ外れるか」だけであり、
  百分率入力は**過度に厳しい側**へ外れる。計画の表記例とも一致する。
- **決定2（サーバ側の実効）**: 画面だけの関門は API 直叩きで消える。本 issue は「保存が通るようになる」
  変更であり、通る先に何も無ければ危険は移動しただけである。
- **決定2 の上限値**: 「統制でなくなる点」を項目ごとに言葉で説明できる値にした。既定値からの相対（案 C-1）に
  すると、計画が既定値を改訂したときに範囲が黙って動く。
- **決定3（同時性）**: 中間状態を作らないことが本 issue の本体である。
- **決定4（円建て）**: 記録としての不一致（IADR-0130 が既に明記）を、**画面上の嘘に変えない**。

## 結果

- 良い影響:
  - SC-02 からリスク上限を**保存できるようになる**（#329 以降できなかった）。
  - **統制を無効化する値が、画面からもサーバの API からも保存できなくなる**（従来はサーバに値域が無かった）。
  - 利用者が「25%」と「現在の実額」の両方を見て判断できる（割合だけでは実効額が読めない）。
  - 単位が画面上に常に出るため、比率／百分率／金額の取り違えが目視で検出できる。
- 悪い影響・トレードオフ:
  - **値域は実装の決定であり、計画に根拠が無い**。正当な調整が上限に阻まれる可能性が残る（緩めるには本 IADR の改定を要する）。
  - 画面（%）とワイヤ（比率）で単位が違う。変換を 1 か所に閉じることで担保するが、**新しい入力欄を足す人が
    変換を通し忘れる**余地は残る（型が `%` と `ratio` を区別しないため）。
  - 実額の通貨が計画（USD）と食い違ったまま画面に出る（決定4）。
- フォローアップ:
  - 判定通貨の USD 移行（[IADR-0130] 決定3 の未決事項・未起票）。移行時に決定4 を改める。
  - [#340](https://github.com/endazon/ai-stock-trading/issues/340)（SC-01〜03 の作り直し）は本決定の表現規約に従う。
