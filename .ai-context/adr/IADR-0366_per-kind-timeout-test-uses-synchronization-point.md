# IADR-0366: 種別ごとの打ち切りは「壁時計どうしの競争」ではなく保持ハンドラと順序で固定する

- 状態: Accepted

## コンテキストと課題

`HttpReportNarrativeDrafterTests.タイムアウトは報告書種別ごとに効く_日報は打ち切られ週報は通る` が
全ソリューション実行でまれに落ちる（起票者の実測 6 回中 1 回）。日報の期待はプレースホルダ散文だが、
実際にはハンドラの応答本文（`週次の所感です。`）が返っていた。

テストは **壁時計 100 ms の打ち切り** 対 **壁時計 600 ms のハンドラ遅延** という構成であり、
**合否を決める 2 つの事象がどちらも壁時計**であった（#885 で訂正した判別の軸に該当する）。

### 🔴 機序（実測で確かめた）

製品の `HttpReportNarrativeDrafter` をそのまま呼ぶ一時的な計装テストで、
①ハンドラ入場 ②要求トークンのキャンセル通知 ③`Task.Delay(600ms)` の完了 の時刻を記録し、
**要求を投げた直後にスレッドプールのワーカーを全部塞いだ**（`Thread.Sleep` の作業項目 1024 本 × 1.5 秒。
スピンループ 16 本を併走）。

| サンプル | キャンセル通知 | 遅延の完了 | 結果 |
| --- | --- | --- | --- |
| 0 | 1543.3 ms | （キャンセル済み） | 打ち切り（緑） |
| **1** | **走らず** | **1502.0 ms** | **応答が返る（＝ issue の失敗）** |
| 2 | 1503.8 ms | （キャンセル済み） | 打ち切り（緑） |

🔴 **どちらのタイマーのコールバックもスレッドプールが配送する。** プールが塞がっている間は
**期限 100 ms も 600 ms も配送されない**。空いた瞬間には**両方とも期限切れ**であり、
**どちらが先に走るかは順序として保証されていない**。先に遅延が走れば、製品が正しく
100 ms の打ち切りを構成していても、日報は応答を受け取ってしまう。

**実テストそのもの**を同じ条件（暖まったプロセス・要求の 2 ms 後に枯渇波）で 20 回反復すると
**6 回失敗**し、失敗の文言は issue と同一であった。**冷えたプロセスでは再現しない**
（1 プロセス 1 回を 100 回試して 0 回。初回要求の JIT が 100 ms を食い、打ち切りが先に立つためと
**見込まれる**が、測っていないので断定しない）。

## 検討した選択肢

| # | 案 | 評価 |
| --- | --- | --- |
| A | 日報の上限を下げる／遅延を伸ばして比を広げる | **採らない。** 機序は「配送が両方とも遅れる」ことなので、比を広げても同じ逆転が起こり得る。しかも**固定したい上限値そのものを動かす** |
| B | `TimeProvider` / `FakeTimeProvider` を注入して打ち切りを仮想時間にする | **採らない（今回は）。** 製品コード（`HttpReportNarrativeDrafter` と輸送層）へ時計注入を持ち込む変更になり、#900 の射程を超える。`HttpClient.Timeout` は `TimeProvider` を受け付けないため、多層防御の上限は結局壁時計のまま残る |
| C | 片方の assert（週報側）を落として単純化する | **不可。**「種別ごとに効く」は**差が出ること**が本体である |
| **D** | **応答を時間ではなく同期点で出す**（テストが解放するまで応答しないハンドラ＋順序の観測） | **採用。** 秒数も上限値も動かさず、競争そのものを消す |

## 決定

### 決定 1 — ハンドラは時間で応答せず、テストが解放するまで保持する

`HeldRespondingHandler` は到達した要求を `Channel` へ載せ、`TaskCompletionSource` が解放されるまで応答しない。
**終わり方は「解放」か「打ち切り」だけ**で、壁時計では終わらない。

### 決定 2 — 種別差は時刻の比較ではなく**前後関係**で観測する

1. 週報を飛行中にする（到達を待つ）→ 2. 同じドラフタ・同じハンドラで日報を投げ、**解放しないのに戻る**ことで
打ち切りを観測する → 3. その時点で**週報の要求トークンが未発火**であることを見る → 4. 解放すると週報は本文を受け取る。

週報は日報より前から飛んでおり、日報の上限（100 ms）は既に発火しているのだから、
**週報が「日報の上限より長く飛んでも切られない」ことは順序だけで言える**。

### 決定 3 — `HttpClient.Timeout` は無期限にする

従来は 30 秒で、これも理屈上は日報を切り得た（＝「種別ごとの上限で切れた」と言えない経路が残っていた）。
無期限にすることで、**日報を戻せる経路は種別ごとの打ち切りだけ**になる。

### 決定 4 — 上限（`Guard` = 30 秒）は合否の基準ではなく、固まらないための安全網

打ち切りが効かなくなれば `TimeoutException` で赤くなる（黙ってハングしない）。IADR-0364 決定 2 と同じ役割。

### 決定 5 — 弱めていないことは変異注入で示す

| 変異 | 結果 |
| --- | --- |
| 種別ごとの上限を無効化（`timeout = null`） | **赤**（`System.TimeoutException`。30 秒の `Guard` が拾う） |
| 週報へも日報の上限を適用（`timeoutFor(ReportKind.Daily)` 固定） | **赤**（`Expected weeklyRequest.Token.IsCancellationRequested to be False because 週報の上限は日報より長い…, but found True`） |

## 理由

**測ってから直した。** 起票時点では「なぜ 100 ms のタイマーが 600 ms に負けるのか」は未特定であり、
計装して初めて「**両方のタイマーの配送が遅れ、期限切れどうしの順序は保証されない**」と分かった。
機序が分かれば、直すべきは秒数ではなく**観測の形**である。

## 結果

- 良い影響:
  - 是正前 **6/20 失敗** → 是正後 **0/40 失敗**（同一条件・同一ハーネス）。
  - 当該テストの実行時間が短くなった（クラス全体で 1.49 秒 → 0.87 秒。600 ms の待ちが消えたため）。
  - 失敗の形が読みやすくなった（「本文が返った」ではなく「週報が切られた」「打ち切りが効かない」と出る）。
- 悪い影響・トレードオフ:
  - テストが**要求の前後関係**に依存する（週報を先に飛ばす必要がある）。読み手には一手間増える。
  - 🔴 **打ち切りが「構成した秒数どおりか」は、このテストではもう測れない**（元から測っていない——
    従来版も 100 ms と 600 ms の大小しか見ていない）。秒数の正しさを固定したいなら別のテストが要る。
  - `Guard` に達した場合の失敗は 30 秒かかる（CI の失敗コストは増える。IADR-0364 と同じトレードオフ）。
- フォローアップ:
  - 🔴 **同型の棚卸しと検査器の検討は #885 / #900 / #901 をまとめて別途行う。** 本 ADR の射程は #900 の 1 本。
  - 再現条件（暖まったプロセス＋要求直後のプール枯渇）は**一時ハーネスでのみ**作った。
    ハーネスはコミットしない（手順は作業仕様書に残す）。
