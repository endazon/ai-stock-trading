# IADR-0240: 報告書の確定は Discord から版番号付きで行い、二重適用を 2 層で防ぐ

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（起票 #341。利用者レビューは PR で受ける）

## 起点・関連

- 関連する計画書 ID: FR-14（Discord からの報告書の確定）・FR-07（確定した方針のみ取引に適用）・
  UC-03〜05・ADR-0003（確定は利用者のみ）
- 関連する実装仕様書: [`20260828_341_discord-bot-and-notification.md`](../specs/20260828_341_discord-bot-and-notification.md)

## コンテキストと課題

詳細設計07（fixed）は「確定要求は `対象ID＋版番号` を必須とする」「確定 API は冪等とする」と定め、
issue #341 の受け入れ基準にも「同一確定操作の二重送信で方針が二重適用されないこと」がある。

実測すると、**機構（`VersionedConfirmationGuard`）は存在するがどこからも呼ばれていない**。
`BotCommandParser` にも Gateway のスラッシュコマンドにも `/report` が無く、**Discord から報告書を確定する
経路そのものが無い**。IADR-0062 決定6 が「報告書ドラフトへの結線は #14 側で行う（交差回避）」として保留した
ままであり、#14 側（報告書サービス）は既に版番号付き冪等の確定 API
（`POST /reports/{periodKey}/confirm` ＋ `GET /reports/{periodKey}/review`）を実装済みである。

決めるべきは、**二重適用をどこで止めるか**である。

## 検討した選択肢

1. **報告書サービスの冪等 API だけに委ねる**（Bot は素通しで確定 API を叩く）
   — 二重適用そのものは起きない（版番号で弾かれる）。だが**多重押下のたびに OwnerOnly の HTTP を叩き**、
   利用者への応答も「409 競合」になる。窓口としての振る舞いが悪い。何より、**既にある `VersionedConfirmationGuard`
   が未使用のまま残る**——「機構はあるが使われていない」は本プロジェクトが繰り返している事故の型である。
2. **Bot 側の予約ガードだけに委ねる**（確定 API を非冪等に扱う）
   — Bot はステートレスであることが詳細設計07 の前提であり、**再起動でガードが空になる**。
   チャット UI と Discord の同時確定も止められない。**却下**。
3. **2 層で防ぐ**（採用）— 窓口（Bot）は予約ガードで多重押下を弾き、権威（報告書サービス）は版番号付き
   冪等 API で真の二重適用を弾く。

## 決定

1. `/report show <periodKey>` / `/report approve <periodKey> [<version>]` /
   `/report request-changes <periodKey> <version>` を実装する。
   確定は **確認ボタン（版番号を CustomId に載せる）→ 押下で実行**の 2 段階とする（詳細設計07 §認証・認可 4項）。
2. 二重適用は **2 層**で防ぐ。**権威は報告書サービスであり**、Bot の `VersionedConfirmationGuard` は
   「窓口での多重押下を弾く前段」と位置づける（同クラスの既存コメントの位置づけを変えない）。
   同一 `periodKey ＋ 版番号` の 2 回目は **確定 API を呼ばずに**「確定済み」を返す。
3. **予約は失敗時に解放する**（`VersionedConfirmationGuard.Release`）。確定 API が HTTP 失敗・
   タイムアウト・解釈不能で終わったら予約を戻す。**解放しないと、唯一の確定窓口で同じ版を二度と
   確定できなくなる**（Bot 再起動まで詰む）。
4. **`/report show` は版番号だけを返し、報告書の本文・要約を取りに行かない。** 要約は
   `ReportDraftPresented` 通知が届けており、その経路は**発行側でサニタイズ済み**である（IADR-0116 決定3/4）。
   Bot が生本文を直接取得すると、**そのサニタイズを迂回する経路を新設する**ことになる。
5. **`ReviewState`（enum）を読まない。** 版番号（`version`）と `periodKey` だけを射影する。
   Risk 側アダプタと同じく **JSON 表現（数値/文字列）に結合しない**（IADR-0081 決定1 と同型）。
6. **`periodKey` は `^[a-z0-9-]{1,32}$` に限定し、書式外は `Unknown` へ倒す。** そのまま URL パスへ載るため、
   パス・トラバーサルの余地を parser の段階で構造的に消す。

   ［2026-09-18 追記 / #835］**値域を `^[A-Za-z0-9-]{1,32}$` へ広げ、会話キーの大小文字を保つ。**
   週報の自然キーは ISO 週の `W` が大文字（`weekly-2026-W38`・`ReportPeriod.ExpectedKey`）である。
   パーサはコマンド全体を小文字化してから会話キーを採っていたため、**週報は Discord から一度も確定できなかった**
   （稼働環境で実測。日報・月報は英小文字と数字だけなので露呈しなかった）。確認ボタンの CustomId 経由も同じ
   パーサを通るため両経路が同時に詰んでいた。動詞・副コマンドの大小文字は従来どおり吸収する。
   値域制限の目的は記号（`/` `.` `%` `?` 等）の遮断であり、**大文字英字を許しても目的は損なわれない**。
   会話キーの推測補正はしない（実在しないキーは報告書サービスが 404 で返す）。利用者がキーを覚えずに済む
   入力補完は #834 の射程。

   ［2026-09-19 追記 / #837］**値域のアンカーを `\A…\z` にする（`\A[A-Za-z0-9-]{1,32}\z`）。**
   .NET の `$` は `RegexOptions.Multiline` が無くても**末尾 LF の直前にマッチする**（`\Z` も同じ）ため、
   `^…$` は `abc\n` を通していた（#836 の監査が実測。初版からの挙動であり退行ではない）。パーサは半角空白だけで
   トークンへ割るので、`/report approve abc\n 1` の会話キーは LF を含んだまま `ReportApprove` になっていた。
   `Uri` がパーセント符号化するためリクエスト分割は起きず実害は 404 止まりだが、**「parser の段階で構造的に消す」
   という本決定の趣旨に反する**（この文字列が将来ログ・ファイル名・別プロトコルへ渡ると意味が変わる）。
   **入力の正規化（LF を空白とみなして割る・落とす）はしない**——書式外は Unknown へ倒す方針を保つ。
   入力補完の候補側（決定 9）は同じ判定 `IsPeriodKey` を共用するため同時に直る。
   **同じ落とし穴の走査結果**: 追跡下の C# の正規表現を全件引き、`$` で外部入力の値域を検証しているのは
   本箇所だけであった（`OpendConsoleCommand` の 2 本は初めから `\A…\z`。他は行単位の抽出＝Multiline を
   意図して使うもの・LF を含み得ない 1 行の判別・アンカー無しの抽出と置換・テストの表明）。母集合と 1 件ずつの
   除外理由は作業仕様書 `.ai-context/specs/20260919_837_parser-anchor-trailing-lf.md` に置く。
   段階・版番号（`int.TryParse`）は前後の空白類を許すが、結果が `int` で LF を下流へ運ばないため変更しない。
   **以後、外部入力の値域を正規表現で検証するときは `\A…\z` で書く。**
7. 多層認証は kill switch と同水準を掛け、**ボタン押下時にも再評価する**（押下者のすり替え防止）。
8. **自然文リプライの AI 分析サービスへの中継は本決定の射程外**とする（`MessageContent` Intent と
   #14 側の対話 API を要する）。Discord からの「修正指示」は**差し戻し（`request-changes`）**として実装する
   ——報告書サービスのエンドポイントのコメントが「#15 Discord Bot はこれらの HTTP を呼んで
   提示→差し戻し／承認を駆動する」と明示している。

9. ［2026-09-18 追記 / #834］**`period` に入力補完（Discord autocomplete）を足す。** 候補は報告書サービスの
   一覧 API（`GET /reports`・OwnerOnly）から採り、**新しい順に最大 25 件**（Discord の上限）返す。
   **射影するのは会話キーと並び替えに使う開始日だけ**で、本文・要約（決定4）も状態 enum（決定5）も読まない
   ——一覧に載る報告書はレビュー待ちも確定済みも等しくレビュー操作の対象であり、絞り込みに状態は要らない。
   **取得に失敗したら候補なしで素通しする（fail-safe）。** 補完は入力の補助であって統制ではなく、
   一覧が引けないことを理由に `/report` 自体を壊さない。**絞り込みは利用者が打った文字だけで行い、推測補正は
   しない**（前方一致 → 部分一致・大小文字は無視。決定6 の値域外のキーは候補に出さない）。**候補にも多層認証を
   掛け、許可外の利用者へは返さない**（決定7 と同水準——補完は「どの会話キーが存在するか」を漏らす経路である）。

10. ［2026-09-18 追記 / #834］**404 は「その会話キーの報告書が見つかりません（例: `daily-2026-09-18`）」と
    案内する。** 従来は汎用の失敗文言（「レビュー局面の照会に失敗しました（HTTP 404）」）だけで、**何が悪いのか・
    正しい形が何かを伝えていなかった**。利用者が `period` に日付だけ（`2026-09-15`）を入れて 4 回続けて 404 に
    なり、報告書を確定できなかった（稼働環境で実測）。**404 以外の状態の文言は変えない**（401/403 の owner
    クライアント設定の手掛かりも従来どおり）。

11. ［2026-09-19 追記 / #774］**確定者は Bot が本文で運び、報告書サービスは「信頼するクライアントのトークン」に
    限ってそれを採る。認可の主体（クライアント）と実際に操作した利用者の両方を残す。**
    稼働環境で「報告書確定」通知が確定者を `unknown` と表示した。Bot は owner マップ機密クライアント
    （`client_credentials`・IADR-0062 決定4 / IADR-0098）のトークンで確定 API を呼ぶ。**そのトークンの主体は人では
    ない**——報告書サービスが `Identity.Name`（`preferred_username`）から採っていた確定者は、名前クレームが無ければ
    `unknown`、在っても `service-account-<clientId>` になる。この値が `ReportConfirmed.Actor` に載り、
    **通知本文と監査台帳（要約・ペイロード）の両方**へ出ていた（監査も同じ問題を持っていた）。
    - **どの層で解決するか**: ①Bot が確定要求に操作者を添え、報告書サービスが採る（**採用**）／②報告書サービスが
      トークンのクレームから解決する（却下: `client_credentials` のトークンに人は居ない。token exchange は計画
      MSP:ADR-0086 決定2 が採らない）／③通知側で補う（却下: **監査台帳が直らない**。Bot はステートレス前提で、
      確定とイベントの相関をプロセス内に持つとレプリカ・再起動で外れ、**別人の確定に名前を当て得る**）。
    - **他の Bot 経由操作との整合**: kill switch・pause/resume・GFV 解除は、権威側の actor をトークンの主体に
      据えたまま、**操作した利用者を本文（理由欄 `…（actor=<利用者>）`）で運んで併記している**（計画 MSP:ADR-0086
      決定1「利用者文脈は本文で運ぶ」と同じ向き）。確定要求には理由欄が無いので、**同じ作法を構造化した欄で行う**:
      要求の末尾に `onBehalfOf`（任意）、イベントの末尾に `AuthorizedBy`（任意・既定 null。追加は末尾へ＝IADR-0134
      決定2 と同じ規律・後方互換の追加のみ＝IADR-0079）。代理確定は `Actor`＝操作した利用者・`AuthorizedBy`＝
      クライアント ID、利用者本人のトークンは従来どおり `Actor`＝本人・`AuthorizedBy`＝null。
    - 🔴 **なりすましの閉じ方**: 本文の名前をそのまま信じない。**トークンの `azp` が構成
      `Reports:DelegatedActor:TrustedClientIds`（カンマ区切り）に一致するときだけ**採る。当該クライアントは機密
      （secret 必須）・`standardFlowEnabled:false`・`directAccessGrantsEnabled:false`（IADR-0098 決定1）で、
      **利用者トークンの `azp` にはなり得ない**——`onBehalfOf` を効かせられるのは**そのクライアントの secret を
      持つ者（Bot）だけ**である。**利用者トークン直叩き・一覧外のクライアントの `onBehalfOf` は無視する**（確定は通し、
      確定者はトークンの主体。無視したことは警告ログに残す）。**一覧の既定は空＝誰も信じない**（設定漏れで信頼を
      開かない）。一覧は通知側 `OwnerAuth:ClientId` と**同じ秘密鍵**（`ast-secrets/discord-owner-auth-client-id`）から
      注入する（単一情報源）。Bot 側の操作者は**着信の Discord ユーザー ID から多層認証が引いた Keycloak 利用者名**
      （決定7）であり、コマンド文字列からは採らない。
    - **値域**: `onBehalfOf` は `\A[A-Za-z0-9._@+-]{1,64}\z`（決定6 の 2026-09-19 追記に従う）。通知本文・監査要約へ
      そのまま載るため空白・改行・マークダウンの記号を通さない（**Discord のメンションは塞げていない**——メール形式の利用者名の
      ために `@` を許しており、`@everyone` / `@here` は値域を通る。#861 の監査が実測。塞ぐのは送信側の
      `allowed_mentions` で、#867 で扱う）。信頼クライアントが値域外を送ったら **400 で確定しない**
      ——**確定者を記録できない確定は行わない**（IADR-0062 決定3「actor を特定できない操作はさせない」と同じ向き）。
      Bot は失敗として利用者へ返し、予約を解放する（決定3 の既存の経路）。
    - **操作者が取れないとき**（`onBehalfOf` を添えない旧版 Bot／名前クレームの無いトークン）: `unknown` へ倒す前に
      **`client:<azp>`** を確定者にする（人は分からなくても、**誰の資格で確定されたかは残る**）。`azp` も無いとき
      だけ従来の `unknown`。表示側（通知・監査要約）は `unknown`／空を **「確定者不明」** と書く（内部の既定値を生で
      出さない）。旧版 Bot を 400 にしないのは、報告書サービスと通知サービスの配備順で**唯一の確定窓口が塞がる**のを
      避けるためである。
    - **表示**: 代理確定の通知は「（developer・ai-stock-trading-owner 経由・前提条件 v1）」、監査要約は
      「（developer・代理 ai-stock-trading-owner・前提 v1）」。
    - **射程外（保留）**: 差し戻し・提示の actor は永続化も発行もされない（空でないことの検査だけ）ため変えない。
      **`/stage`（段階遷移）は理由欄が無く、承認者が同じくクライアント主体で残る**——同型だが Risk 側の契約を
      変えるため本追記の射程に入れない。kill switch・pause・GFV の actor 欄もクライアント主体のまま
      （操作者は理由欄に残っている）。**実 Keycloak のトークンで `azp` が届くことは実クラスタでは未検証**
      （単体テストはクレーム注入で代替）。作業仕様書: `.ai-context/specs/20260919_774_report-confirmed-actor-on-behalf-of.md`。

## 理由

決定 2 の 2 層は、**どちらか一方では守れない**からである。窓口だけではステートレス前提と競合し、
権威だけでは窓口の応答が壊れる。**「二重適用は起きない」という保証は権威側が持ち、「多重押下を静かに吸収する」
という運用品質は窓口側が持つ**——役割が違う。

決定 3 は、**失敗の倒れ方の非対称**による。予約を解放しない誤りは「確定できない」という**気付きにくい詰み**を
生み、解放する誤りは「確定 API をもう一度呼ぶ」だけで、権威側が版番号で弾く。**安全側は解放である。**

決定 4・6 は攻撃面・迂回面を増やさないための選択である。**唯一の破壊的操作面であるという前提**は、
機能を足すときに毎回効く。

［2026-09-18 追記 / #834］決定 9・10 は**利用者に回復手段を返す**ための選択である。会話キーは人が覚えて
いられる形ではなく（#835 の週報の大文字もこの形式の難しさの表れである）、誤入力の応答が状態番号だけでは
何度打ち直しても当たらない。**候補を出して誤入力そのものを減らし、外したときは正しい形を見せる。** 同時に、
補完は決定 4・6 の前提を崩さない——候補に載せるのは会話キーだけで、本文へは触れず、値域外のキーは出さず、
許可外の利用者には返さない。**利便性のために迂回路を作らない。** 補完の失敗が `/report` を止めないのは、
**統制でないものを統制の前に置かない**ためである（失敗を成功に見せない方針との違いは、補完が「報告書が
無い」と主張しないことにある——実在しないキーは従来どおり報告書サービスが 404 で返す）。

［2026-09-19 追記 / #774］決定 11 は**「誰が確定したか」を ADR-0003（確定は利用者のみ）の証跡として成立させる**
ための選択である。Bot を「利用者の代理」と位置づけた IADR-0062 決定4 は、認可（誰の資格で通すか）を機密
クライアントへ寄せたが、**帰属（誰が操作したか）を運ぶ経路を用意していなかった**。帰属を本文で運ぶこと自体は
他の Bot 経由操作が既にやっている。違いは、確定者が**イベントで配られ通知と監査に出る**ことである——だから
自由文ではなく構造化した欄にし、**信じる条件をトークンの `azp` に結び付けた**。本文の値を無条件に信じれば
利用者トークンで他人の名前を確定者にできてしまい、無条件に捨てれば確定者は永遠にクライアントのままになる。
**「値を送れる者」を secret の保有者に限る**ことで、その間を取った。信頼の水準は「Bot（＝OwnerOnly の資格を持つ
機密クライアント）が正直であること」であり、これは Bot が多層認証の結果に基づいて確定 API を呼ぶという
既存の信頼と同じものである（新しい信頼を足していない）。

## 結果

- 良い影響: 未使用だった冪等機構が経路上で検査されるようになる。`docs/blocked-tasks.md` A-7a を除けば、
  FR-14 の「確定」がテストで担保される。
- 悪い影響・トレードオフ: `/report show` の情報量が版番号に留まる（要約は通知側でしか読めない）。
  詳細設計07 の `/report show`（「最新ドラフト/確定版の要約と閲覧リンク」）に対しては**縮退**である。
- フォローアップ: 要約表示と自然文リプライの中継は、`MessageContent` Intent の可否と AI 分析サービスの
