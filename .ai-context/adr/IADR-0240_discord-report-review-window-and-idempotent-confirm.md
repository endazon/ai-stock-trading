# IADR-0240: 報告書の確定は Discord から版番号付きで行い、二重適用を 2 層で防ぐ

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（起票 #341。利用者レビューは PR で受ける）

## 起点・関連

- 関連する計画書 ID: FR-14（Discord からの報告書の確定）・FR-07（確定した方針のみ取引に適用）・
  UC-03〜05・ADR-0003（確定は利用者のみ）
- 関連する実装仕様書: [`20260828_341_discord-bot-and-notification.md`](../specs/20260828_341_discord-bot-and-notification.md)

## コンテキストと課題

詳細設計07（fixed）は「確定要求は `対象ID＋版番号` を必須とする」「確定 API は冪等とする」と定め、
issue #341 の受け入れ基準にも「同一確定操作の二重送信で方針が二重適用されないこと」がある。

実測すると、**機構（`VersionedConfirmationGuard`）は存在するがどこからも呼ばれていない**。
`BotCommandParser` にも Gateway のスラッシュコマンドにも `/report` が無く、**Discord から報告書を確定する
経路そのものが無い**。IADR-0062 決定6 が「報告書ドラフトへの結線は #14 側で行う（交差回避）」として保留した
ままであり、#14 側（報告書サービス）は既に版番号付き冪等の確定 API
（`POST /reports/{periodKey}/confirm` ＋ `GET /reports/{periodKey}/review`）を実装済みである。

決めるべきは、**二重適用をどこで止めるか**である。

## 検討した選択肢

1. **報告書サービスの冪等 API だけに委ねる**（Bot は素通しで確定 API を叩く）
   — 二重適用そのものは起きない（版番号で弾かれる）。だが**多重押下のたびに OwnerOnly の HTTP を叩き**、
   利用者への応答も「409 競合」になる。窓口としての振る舞いが悪い。何より、**既にある `VersionedConfirmationGuard`
   が未使用のまま残る**——「機構はあるが使われていない」は本プロジェクトが繰り返している事故の型である。
2. **Bot 側の予約ガードだけに委ねる**（確定 API を非冪等に扱う）
   — Bot はステートレスであることが詳細設計07 の前提であり、**再起動でガードが空になる**。
   チャット UI と Discord の同時確定も止められない。**却下**。
3. **2 層で防ぐ**（採用）— 窓口（Bot）は予約ガードで多重押下を弾き、権威（報告書サービス）は版番号付き
   冪等 API で真の二重適用を弾く。

## 決定

1. `/report show <periodKey>` / `/report approve <periodKey> [<version>]` /
   `/report request-changes <periodKey> <version>` を実装する。
   確定は **確認ボタン（版番号を CustomId に載せる）→ 押下で実行**の 2 段階とする（詳細設計07 §認証・認可 4項）。
2. 二重適用は **2 層**で防ぐ。**権威は報告書サービスであり**、Bot の `VersionedConfirmationGuard` は
   「窓口での多重押下を弾く前段」と位置づける（同クラスの既存コメントの位置づけを変えない）。
   同一 `periodKey ＋ 版番号` の 2 回目は **確定 API を呼ばずに**「確定済み」を返す。
3. **予約は失敗時に解放する**（`VersionedConfirmationGuard.Release`）。確定 API が HTTP 失敗・
   タイムアウト・解釈不能で終わったら予約を戻す。**解放しないと、唯一の確定窓口で同じ版を二度と
   確定できなくなる**（Bot 再起動まで詰む）。
4. **`/report show` は版番号だけを返し、報告書の本文・要約を取りに行かない。** 要約は
   `ReportDraftPresented` 通知が届けており、その経路は**発行側でサニタイズ済み**である（IADR-0116 決定3/4）。
   Bot が生本文を直接取得すると、**そのサニタイズを迂回する経路を新設する**ことになる。
5. **`ReviewState`（enum）を読まない。** 版番号（`version`）と `periodKey` だけを射影する。
   Risk 側アダプタと同じく **JSON 表現（数値/文字列）に結合しない**（IADR-0081 決定1 と同型）。
6. **`periodKey` は `^[a-z0-9-]{1,32}$` に限定し、書式外は `Unknown` へ倒す。** そのまま URL パスへ載るため、
   パス・トラバーサルの余地を parser の段階で構造的に消す。
7. 多層認証は kill switch と同水準を掛け、**ボタン押下時にも再評価する**（押下者のすり替え防止）。
8. **自然文リプライの AI 分析サービスへの中継は本決定の射程外**とする（`MessageContent` Intent と
   #14 側の対話 API を要する）。Discord からの「修正指示」は**差し戻し（`request-changes`）**として実装する
   ——報告書サービスのエンドポイントのコメントが「#15 Discord Bot はこれらの HTTP を呼んで
   提示→差し戻し／承認を駆動する」と明示している。

## 理由

決定 2 の 2 層は、**どちらか一方では守れない**からである。窓口だけではステートレス前提と競合し、
権威だけでは窓口の応答が壊れる。**「二重適用は起きない」という保証は権威側が持ち、「多重押下を静かに吸収する」
という運用品質は窓口側が持つ**——役割が違う。

決定 3 は、**失敗の倒れ方の非対称**による。予約を解放しない誤りは「確定できない」という**気付きにくい詰み**を
生み、解放する誤りは「確定 API をもう一度呼ぶ」だけで、権威側が版番号で弾く。**安全側は解放である。**

決定 4・6 は攻撃面・迂回面を増やさないための選択である。**唯一の破壊的操作面であるという前提**は、
機能を足すときに毎回効く。

## 結果

- 良い影響: 未使用だった冪等機構が経路上で検査されるようになる。`docs/blocked-tasks.md` A-7a を除けば、
  FR-14 の「確定」がテストで担保される。
- 悪い影響・トレードオフ: `/report show` の情報量が版番号に留まる（要約は通知側でしか読めない）。
  詳細設計07 の `/report show`（「最新ドラフト/確定版の要約と閲覧リンク」）に対しては**縮退**である。
- フォローアップ: 要約表示と自然文リプライの中継は、`MessageContent` Intent の可否と AI 分析サービスの
  対話 API が揃った時点で別 issue とする。**実 Discord での疎通は A-7a のまま未検証**である。
