## コンテキストと課題

稼働中の PoC で、システムの手仕舞い API が使えない状況（#847・#848）のまま、利用者が証券会社のアプリから全株を
直接売却した。ブローカーの建玉は 0 になったが、**取引台帳は 3,381 株を保有したまま**である。

```
GET /risk-controls/sizing-context
  capital                = 1,133,333
  stageCapitalRemaining  = 332.47      ← 1 株も買えない
  dailyOrderRemaining    = 566,998.97
trade-decision: サイジングで数量 0 のため見送り: AAPL
position_drift_state: ObservedSignature = AAPL:1:3381:0:1  ConsecutiveCount = 2  （検知・通知済み）
```

台帳は約定イベントでしか動かず、観測（建玉照会）では書き換えない。**この設計は正しい**（IADR-0118。損益の権威を
観測へ明け渡さない）。足りないのは**検知の先**である —— 乖離を知らせるところで止まり、実態へ合わせる手段が無い。
実在しない建玉が段階資金の枠を占有し続け、**新規建てが 1 本も出ない**。

決めるべきことは 5 つある。(1) 誰が台帳を動かせるか、(2) 何へ合わせるか、(3) 分からない約定価格＝実現損益をどう扱うか、
(4) 台帳の読み手（サイジング・統制・日報・段階ゲート・乖離検知自身）へどう波及させるか、(5) 発注執行側の保護記録をどうするか。

## 検討した選択肢

### 実現損益の扱い（課題 3）

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **(a) 記録しない**（採用） | 数量だけを合わせる。損益は「不明」と明示する | 台帳の実現損益は**確定値だけ**のまま。日報・税の参考値・段階ゲートの実績に推定が混ざらない | 実際に生じた損益が統制へ入らない（下の「結果」参照） |
| (b) 現在値で近似し「推定」と明示 | 取り込み時点の現在値で決済したとみなす | 日次損失上限・DD・連敗が実態に近づく | 推定を運ぶ通り道が無い。`PortfolioState.DailyRealizedPnl` は単一の decimal で、ロックアウト・段階ゲート・報告書の実現損益・源泉徴収税額の概算へそのまま流れる。**「推定」の印は最初の集計で消える** |

(b) の推定誤差は小さくない。利用者が売ったのは取り込みの数時間〜数日前であり、3,381 株なら 1 ドルの差が 3,381 ドルになる。
その誤差が**確定値と同じ列に**入る。

### 取り込み行の置き場所（課題 4）

| 案 | 内容 | 判定 |
| --- | --- | --- |
| 既存の 2 表（`approved_orders` ＋ `trade_fills`）へ合成の承認・約定を入れる | 読み手は無改修で追随する | **不採用。** 約定価格でない値が約定の単価列へ入り、後から区別できない。`approved_orders` は「審査を通った注文」であるという意味も壊れる |
| **専用の追記専用表 `position_drift_adoptions` に置き、`GetFills()` で合流させる**（採用） | 行が約定でないことをスキーマで保つ。読み口は 1 点のまま | 射影に 1 つ分岐が要る（決定 3） |
| 射影の外で建玉を差し引く（補正表を各読み手が引く） | — | **不採用。** 読み手が 12 箇所あり、1 つ漏らすと統制ごとに違う建玉を見る |

## 決定

### 決定 1: 最新の観測を耐久に保持する。鮮度は取り込みの瞬間に判定する

`IBrokerPositionObservationStore`（単一行 `broker_position_observation`）を足し、`BrokerPositionsObservedHandler` が
観測のたびに上書きする（逆行する観測は無視）。乖離の追跡状態（IADR-0124）はシグネチャしか持たず、**観測時刻が無い**ため、
「いま観測されている値」と「それがいつの観測か」を同じ行から読めるようにする。永続にするのは、replicas>1 で観測を受けた
Pod と API を受けた Pod が違い得るためである（IADR-0124 と同じ理由）。

- **照会不能は「行が更新されない」ことで表れる。** 発注執行は照会できなかったとき観測を発行しない（IADR-0118）。
  空の `Positions` は「建玉が無いと観測した」事実であり、不明ではない。保持している JSON が読めないときは**不明**として扱い、
  空列へ倒さない（空列へ倒すと、取り込みで台帳の全建玉が消える）。
- **最大経過時間は 60 分**（`PositionDriftAdoptionService.DefaultMaxObservationAge`）。発注執行の建玉照会が許す最大間隔
  （`PositionReconciliationOptions` のクランプ上限）と同値にする —— 健全な巡回は必ず更新できる（IADR-0153 決定 3 と同じ決め方）。
  構成キーは持たせない。
- 🔴 **観測の購読は台帳を書かない。** 記録するだけである（IADR-0118 の原則は変えていない。テスト T-10-473 が固定する）。

### 決定 2: 取り込みは OwnerOnly・理由必須の API で、目標は観測が決める

`POST /risk-controls/position-drift/adopt`（本文 `{ symbol, market, reason }`）。`RiskControlEndpoints` の owner グループに置き、
`ActorOf(http)` を操作者とする。**サービストークンには開かない**（生成 AI・自動処理が台帳を書き換えられないようにする。
FR-10・ADR-0003。手仕舞い〔IADR-0117〕と同じ権限管理）。

**数量は受け取らない。** 「いま観測されているブローカーの建玉へ合わせる」操作であり、利用者が任意の数量で台帳を書き換える
API ではない。次のいずれかに当たれば**拒否し、台帳を 1 行も書かない**（HTTP 422。入力の欠落は 400）。

| 拒否 | 条件 | 理由 |
| --- | --- | --- |
| `ObservationUnavailable` | 観測が一度も届いていない／保持値が読めない | 不明な値へ合わせない |
| `ObservationStale` | 最新の観測が 60 分より古い | 観測が止まっている間の値へ合わせない |
| `NoDrift` | 当該銘柄に乖離が無い（**取り込み済みを含む**） | 冪等。2 回目はここで止まる |
| `UnsupportedDirection` | 台帳に無い建玉・数量の増加・方向の反転 | 取得単価も損切りも分からない建玉を、システムの管理下にあるように見せない |
| `LedgerMovedAfterObservation` | 観測より後に台帳の当該銘柄が動いた | 観測が台帳に対して古い |
| `DriftNotReported` | その乖離（**双方の数量まで同一**）がまだ報告されていない | 連続観測条件を満たしていない乖離は、約定が台帳へ届く前の一過性の未反映かもしれない |
| `CloseInFlight` | 処理中の決済（承認済み・未約定。30 分窓）がある | 約定が後から届くと二重に減る |

- 乖離の計算は検知と**同じ純関数**（`PositionDriftDetector.Detect`）で、いまの台帳と最新の観測を突き合わせる。
- 「報告済み」の判定は `PositionDriftTracker.IsReported`（報告済みシグネチャに当該項目が含まれるか）。報告済みシグネチャは
  乖離が解消するまで保たれるため、複数銘柄の乖離を 1 件ずつ取り込む間も残りは報告済みのままである。
- **冪等**: 目標は絶対値（観測の数量）であり差分ではない。逐次の 2 回目は `NoDrift` になる。並行の二重投入は取り込み行の
  一意キー（銘柄・市場・取り込み前数量・観測数量・観測時刻）で 1 件に絞る（二重に減るとロングが意図しないショートへ反転する）。
- 取り込み行は専用の追記専用表 `position_drift_adoptions` に置き、`IPortfolioLedgerStore.GetFills()` が
  `LedgerFill.IsDriftAdoption = true` として合流させる。**台帳の読み口を 1 点に保つ**ことで、射影を読むすべての統制が同じ建玉を見る。

### 決定 3: 実現損益は記録しない（案 a）。射影は取り込み行を「その時点の平均取得単価」で畳む

取り込み行は数量だけを運ぶ。`PortfolioProjection.ApplyToLot` が**単一の入口**となり、取り込み行のときは決済単価に
**在庫の平均取得単価そのもの**を渡す。`SignedInventory.Apply` の実現損益は `(決済単価 − 取得単価) × 数量` なので、
**丸め誤差なしに 0** になる（行に保存した単価を使うと、為替換算の端数が「損益」として現れる。**実測: 日本株 300 株・レート 0.0067391 で当日実現損益が
`-0.000000000000000000000000300` になった** —— 負の実現損益は連敗カウンタを 1 つ進める）。
残りの建玉の取得単価と損切り価格は変わらない（一部決済と同じ規則・IADR-0035）。

取り込み行が**動かす**値と**動かさない**値:

| 値 | 扱い | 理由 |
| --- | --- | --- |
| 取得額累計（段階資金）・保有建玉数・建玉一覧・含み損益の対象 | **減る** | 実在しない建玉を数えない（本 issue の目的） |
| 当日実現損益・基準資金（`Capital`）・連敗・エクイティのピーク | **動かさない** | 分からない値を確定値として統制へ流し込まない |
| 当日発注累計 | **動かさない** | 取り込みは新規建ての発注ではない |
| 同日売買銘柄（差金決済防止の入力） | **動かさない** | システム外の売買が**いつ**だったかは分からない。取り込みの日を売買日として記録するのは事実の捏造になる |

**推定は監査イベントと通知にだけ載せる。** 取り込み時点の現在値が取れたとき、`PositionDriftAdopted.ReferencePrice` /
`EstimatedPnlInBase` に参考値を載せ、監査要約と通知の本文で必ず「推定・未記録」と添える。現在値が取れなければ両方 null
（0 で埋めない）。`RealizedPnlRecorded` は常に false であり、受け手が「損益 0 の決済」と読まないために明示的に運ぶ。

### 決定 4: 取り込み行は約定として外へ返さない

`GET /risk-controls/fills`（`PeriodFillQuery`）は取り込み行を除外する。報告書（ReportService）は本列を約定として畳み込み、
実現損益・勝率・費用の概算・取引履歴・三者比較・為替差損益を作る。取り込み行を混ぜると、**「平均取得単価で売った損益 0 の決済」が
確定値として集計・表示される**（勝率の分母に入り、費用が概算され、取引履歴に架空の売り約定が並ぶ）。
強制買戻しの推定の根拠（`BuyInInference.CoveringFillsFor`）にも並べない（自らの決済指示ではない）。

`LedgerFill.IsDriftAdoption` は `[JsonIgnore]` とし、wire の形は変えない。

### 決定 5: 監査と通知。保護記録の追随は別 issue（#858）

- 新イベント `PositionDriftAdopted`（取り込み ID・銘柄・市場・取り込み前後の数量・観測値と観測時刻・取得単価・
  `RealizedPnlRecorded=false`・参考の現在値と推定・操作者・理由・時刻）。監査台帳は観測・乖離の報告と**同一相関**
  （`position-reconciliation`）で束ねる。通知は Critical。
- 永続化（取り込み行）が先で、それが権威である（イベントの発行に失敗しても台帳は一貫している。行自体が操作者・理由・観測を持つ）。
- **発注執行側の保護記録（`protective_stop_orders`・S0 / S1）は本 PR では触らない。** 追随にはブローカー側の保護注文の
  取消（建玉が無いのに売りの逆指値が残ると、発火時に意図しないショートになり得る）と記録の終端化が要り、発注執行の状態遷移と
  ガードの巡回に関わる。イベントは追随に要る情報（銘柄・市場・取り込み後の数量）を運んでいるため、発注執行が購読する形で
  後続 issue で実装する。それまでの間は、**通知の本文で「ブローカー側の保護注文が残っていないか確認する」よう案内する**。
  今回の実測は S2（保護記録なし）であり、緊急の実害は無い。

## 理由

- **観測を権威にしない原則（IADR-0118）を保ったまま詰みを解く**には、台帳を動かす主体を利用者に限り、合わせる先を観測に限るのが
  最小である。自動化すれば観測の誤り（照会の部分失敗・銘柄コードの写像ずれ）がそのまま台帳の破壊になる。
- 実現損益を記録しない（案 a）のは、**推定を確定値から分離して運ぶ通り道が系に無い**ためである。台帳の実現損益は日次損失上限・
  連敗・DD・段階ゲート・日報・月報の税の参考値へ 1 本の decimal として流れる。そこへ推定を入れた時点で、下流のどこにも
  「これは推定だった」と示す手段が残らない。
- 減らす方向に限るのは、増やす取り込みが**損切りの無い建玉を管理下に見せる**ためである。FR-10 は「逆指値が未受理・失効した場合は
  建玉を持たない」と定めており、保護の無い建玉を台帳へ作る経路はこれと矛盾する。

## 結果・残余リスク

台帳の射影を読む箇所（母集合は作業仕様書の表）への影響:

| 読み手 | 取り込み後 |
| --- | --- |
| サイジング（`sizing-context`）・発注前スクリーニング | 段階資金の残枠と保有建玉数が回復する。**新規建てが再び出る**（T-10-444 / T-10-463 が固定） |
| 日次損失上限・ロックアウト | 🔴 取り込み前に数えていた**含み損が消える**（実現へ振り替わらない）。システム外の売却が当日の損失だった場合、**日次損失上限の判定は実態より緩む**。利用者が承認して行う操作であり、必要なら一時停止（pause）を併用する |
| 基準資金（`Capital`）・DD・連敗 | システム外の損益が入らないため、**基準資金は実際の口座残高からずれたまま**になる。基準資金をブローカーの実残高へ合わせる手段は本 PR の射程外（現状も初期資金＋台帳の実現損益であり、口座照会とは結ばれていない） |
| 段階ゲート（`StagePerformance`） | 実 DD は定時サンプリングの最大値 latch であり、**過去に latch した値は消えない**。取り込み後のサンプルは含み損が消えた分だけ下がる。Stage 1 の約定件数・GFV 計数は `OrderExecuted` を直接数えるため動かない |
| 日報・週報・月報 | 取り込み行は届かない（決定 4）。**システム外の決済は報告書に現れず、当該建玉は「期間内に決済されなかった建玉」として畳まれる**（現状と同じ）。「システム外の決済・損益不明」を報告書に明示するのは #859 |
| 乖離検知 | 次の観測で乖離が解消し、追跡状態が初期化される（T-10-474） |
| 市場監視の損切り検知・手仕舞い・維持率の自動縮小・現在値の補充 | 実在しない建玉を対象にしなくなる |

その他の残余リスク:

- **台帳の約定が欠落していた場合**（システム外の売買ではなく、`OrderExecuted` の取りこぼしが乖離の原因だった場合）、取り込み後に
  その約定が届くと二重に減る。新しい乖離として検知・報告されるため無言にはならない。処理中の決済がある間は取り込みを拒否して
  窓を狭めている（決定 2）。
- **取り込みは取り消せない**（追記専用）。誤って取り込んだ場合は、次の観測で逆向きの乖離として現れる。
- 観測は最大 60 分古い可能性がある。その間に利用者がさらにシステム外で売買していれば、取り込み後に残差が新しい乖離として現れる。
