# IADR-0227: 監査台帳への秘匿情報の混入は契約イベントのプロパティ名の全数走査で止める

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: 実装担当（issue #339）

## 起点・関連

- 関連する計画書 ID: **FR-09**（Discord 通知）／**FR-11**（監査ログ）／非機能要件（セキュリティ）／
  NFR-10（監査ログの 7 年保持）
- 関連する実装仕様書: `.ai-context/specs/20260828_339_audit-and-trade-records.md`
- 先行: #289（Discord Webhook URL のログ露出を構造的に解消。`RedactedUriHttpClientLogger`）

## コンテキストと課題

issue #339 は「Discord 通知（FR-09）との連携・秘匿情報の取り扱い（既存 #313 / #318 の Webhook URL
露出問題を再実装で構造的に解消する）」と、退行防止として
「ログ・トレースへの秘密情報（Webhook URL 等）非出力の否定形テスト」を求める。

実測すると、**送信側は既に構造的に解消されていた**。

| 面 | 現状 | 判定 |
| --- | --- | --- |
| Webhook 送信の HTTP ログ | `DiscordWebhookHttpClientExtensions` が Webhook 専用クライアントの既定ロガーを `RemoveAllLoggers()` で外し、`RedactedUriHttpClientLogger` が `scheme://host/***` だけを出す。回帰テスト 4 本（成功・失敗・例外・他クライアント非干渉） | **解消済み**（#289） |
| **監査台帳** | 契約イベントを**全量 JSON で 7 年保持**（`AuditEntry.Detail`・NFR-10）。**ここは誰も見ていなかった** | **穴** |

監査台帳の危険は送信ログと性質が違う。**ログは保持期間で消えるが、監査台帳は 7 年消せない。**
契約イベントへ秘匿情報の項目が 1 つでも生まれたら、それは 7 年残る。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **1（採用）** | **契約イベントのプロパティ名を全数走査**し、秘匿情報を示す語を含む項目が 1 つも無いことを表明する | 母集合が閉じている（`EventTypeDiscovery` が単一情報源）。**契約が秘密を持ち得る場所そのもの**を見るため、テストが用意した値に依存しない |
| 2 | シリアライズ結果の**値**を正規表現（Webhook URL の形）で検査する | 検査できるのは**そのテストが作った値**だけである。実データに何が入るかは見ていない。項目が増えても気付けない |
| 3 | 監査記録時にマスキング処理を通す | 何をマスクすべきかを実行時に推測することになる。**契約に秘密を載せてよい**という設計を追認してしまい、伏せ漏れが必ず起きる |
| 4 | ルールを文書に書くだけ | 「毎セッション必読の規約」を増やしても守られたか誰も見ない。同型の事故が 2 回起きたら検査器、という運用規律にも合わない（本件は**事故が 2 回起きた後**である＝#313 と #318） |

## 決定

1. **`AuditPayloadSecretExposureTests`（共有契約テスト）が、`EventTypeDiscovery.GetEventTypes()` の
   全イベントの全プロパティ名を走査**し、秘匿情報を示す語
   （`webhook` / `token` / `secret` / `password` / `passwd` / `credential` / `apikey` / `accesskey` /
   `privatekey` / `connectionstring` / `authorization` / `bearer`）を大文字小文字を無視した部分一致で
   1 件でも見つけたら失敗させる。
2. **検出器が load-bearing であることを同じテストで証明する** —— 秘匿名を実際に検出できること
   （5 件）と、通常の項目名を誤検出しないこと（3 件）を固定する。
3. **母集合が空になって無条件に緑になる経路を塞ぐ** —— イベント型・プロパティが空でないことを表明する。
4. **秘匿情報は契約に載せず、送信側が保持して伏せる**（#289 の Webhook クライアントと同じ作法）を
   規範とし、上記テストのメッセージに書く。

## 理由

- **#313 / #318 は「同型の事故が 2 回」に当たる。** 本リポジトリの運用標準は「検査器・規約の追加は
  同型の事故が 2 回起きたら」を条件とする。送信ログ面は #289 が塞いだが、
  **より長く残る面（7 年保持の台帳）は塞がれていなかった。**
- **名前で見るのは、値で見るより母集合が閉じるからである。** 「秘密が漏れていないこと」は
  値の検査では原理的に言い切れない（見た値しか見ていない）。プロパティ名の集合は有限で列挙可能であり、
  **契約に秘密の置き場が無い**という強い形の表明になる。
- **偽陽性へ倒す。** 語の部分一致は、正当な項目名（例えば "TokenCount"）を誤って止め得る。
  それでよい —— 止まれば人が読んで判断できるが、**緑の素通りは誰も気付かない**。
  同じ判断は `check-review-verdict.js` が既に採っている。

## 結果

- **良い影響**: 契約へ秘匿情報の項目を足す変更は、監査台帳へ届く前に CI で落ちる。
  検査は共有契約テストにあり、どのサービスがイベントを足しても等しく効く。
- **悪い影響・トレードオフ**:
  - **語のリストは網羅ではない。** 命名が語に当たらない秘密（例えば `Uri` という名の Webhook URL）は
    捕まらない。これは残余リスクとして受け入れる —— リストを増やすほど誤検出も増え、
    **検査器そのものが外される**方向へ働く。
  - **項目名しか見ない。** 自由記述のフィールド（`Reason` / `SourceId` 等）へ実行時に秘密を
    書き込む経路は捕まえられない。`TradeExpense.SourceId` の docstring に
    「秘匿情報を入れない」と明記して補う。
- **フォローアップ**: 自由記述フィールドへの混入は、同型の事故が起きたら値の検査を追加する（今は入れない）。
