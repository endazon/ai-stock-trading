# IADR-0461: 決済の数量から、同じ建玉を売る処理中の決済を引く（#1105）

> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 日付: 2026-09-30

## 背景

PoC（2026-09-29 UTC）で AAPL 1,428 株（S1 の保護記録 713 株・715 株）を保有中、判断が 1,428 株の売りを決めた。直後に S1 が 713 株の成行決済を送り（Accepted）、
3 秒後に判断の決済 1,428 株が moomoo に「Not enough positions」で拒否された。715 株が残った。

ゲートが数えるブローカーの `Position.Qty` は、**約定していない売り注文が押さえている株数を引かない**。ゲートは発注執行が自分で出した処理中の決済も見ない。
一方、非終端の Close の記録には **S0 / S3 の保護レグ**も含まれる。これを引くと S0 の建玉への判断の決済は常に 0 株になる（FR-10 に反する）。

## 決定

1. **処理中の決済を数える。** ブローカーの建玉照会でゲートが数量を決めた直後・予約（相2）の前に、次を数える。
   - 対象: 発注執行の非終端の Close の記録で、銘柄・市場・決済の方向が同じもの（新しい問い合わせ `IExecutedOrderStore.FindPendingCloses`。EF・インメモリ・既定の実装）。
   - 除外: 今の承認（同じ DecisionId）の記録。**Active な S0 / S3 の保護記録（`!IsSoftwareStop`）の逆指値レグ**（記録の OrderId が `StopOrderId` と一致、または記録の DecisionId が `StopDecisionId` と一致）。
   - 保護記録ストアが無い・読めないときは保護レグを見分けられないので、**何も引かない**（是正前と同じ）。
2. **送る数量 ＝ min(ゲートの後の数量, 決済方向の建玉 − 処理中)。** 0 以下なら予約の前に見送る。理由は新設の `OrderDispatchForgoneReason.InFlightCloseCoversPosition`（序数 7・末尾）。
   送信前に return するので確実に未発注であり、リスク管理の在庫解放の allowlist に `true` で足す。通知は Warning（建玉はその処理中の決済が売っている）。
   拒否の後・見送りの後の自動の出し直しは足さない（IADR-0211 決定3）。
3. **縮めて送ったら、黙って数量を変えない。** Warning ログと、新設の事実 `CloseReducedForInFlightCloses`（承認の数量・決済方向の建玉・処理中の株数・送った株数・処理中の決済の DecisionId）を発行する。
   - **乖離イベント（`PositionReconciliationDrift`）は使わない**。台帳の乖離ではなく、乖離の Critical 通知と監査の分類を誤らせる。
   - 購読は**監査台帳だけ**。利用者の対処は要らない（判断の意図＝全量の手仕舞いは、処理中の決済と合わせて満たされる）。通知にすると平常の動作で鳴り、止まった事象の通知が埋もれる。
   - 台帳の乖離でも縮めた回は、乖離イベント（数量は変えない）と本事実の両方が出る。乖離に添える「実際に送った株数」は両方を引いた値である。
4. 🔴 **ブローカーが「まだ生きている」と答えた注文だけを数える（窓の形）。** 処理中の記録は建玉照会の**後**に読み、1 件ごとに `IBrokerAdapter.GetOrderAsync` で確かめる。
   株数は記録の数量 − max(記録の約定数, 照会の約定数)。照会が null・例外・終端なら数えない。
   - 理由: 記録の状態は約定追跡（30 秒周期。IADR-0113）が書くまで古い。既に約定した決済を処理中と数えると、建玉照会が映した約定と**二重に引き**、判断の決済を取り残す
     （713 株が約定済み・建玉 715 株のとき、記録だけなら 2 株しか送らない。是正前は 715 株を送れていた＝**是正前より悪くなる**）。
   - 確かめられないときに数えないのは、誤りを「是正前と同じ（拒否され得る）」側に限るためである。取り残す側（是正前より悪い）へは倒さない。
   - 作業仕様書の規則 11 の表（前の端・後の端・両端 × 増える側・減る側のプローブ）で、後の端だけが両方のプローブを満たす。
5. **適用範囲**: 建玉照会の能力を持つ発注先だけ（`brokerPositions` が構成されているとき。IADR-0355 決定4）。内蔵 paper では分岐に入らない。プロンプトは変えない。

## 採らなかった案

- **記録の値だけで数える（ブローカーに確かめない）**: 上の決定4。約定追跡の遅れのあいだ二重に引き、是正前より悪くなる。
- **S0 / S3 の保護レグも引く**: SIMULATE では逆指値が売れる数量を押さえないため、S0 の建玉への判断の決済が常に 0 株になる（FR-10 に反する）。
- **ブローカーの売れる数量（moomoo の `can_sell_qty` 等）を使う**: 共有ポート（`BrokerPositionSnapshot`）の契約変更になり、SIMULATE での値の意味も実測していない。本件の最小の是正は発注執行の記録で足りる。
- **拒否されたら縮めて出し直す**: IADR-0211 決定3・IADR-0458 決定4 に反する（届いたか不明を含む送信を重ねる）。
- **乖離イベントに載せる**: 台帳の乖離ではない（決定3）。
- **縮めた事実を通知にも流す**: 平常の動作で鳴る（決定3）。

## 結果

- 処理中の S1 の決済と判断の決済が重なっても、判断の決済は残りの株数だけを送り、拒否されない。
- 処理中の決済が建玉をすべて覆うときは送らず、確実に未発注の見送りとして台帳の在庫を戻す。
- 送る数量は是正前より増えない（空売りの側へは倒れない）。
- **残余**:
  - 🔴 S0 のブローカー側の逆指値が**実弾で**売れる数量を押さえるかは未確認（planning#704）。押さえるなら、S0 の建玉への判断の決済は是正の前後を問わず拒否され得る。
  - 送信の結果が不明な処理中の決済（予約が Reserved のまま・記録が無い）は数えない。
  - 訂正で数量を変えた注文は記録の数量が古い（ブローカーの照会は数量を返さない）。
  - 保護記録が Active でなくなった後も非終端のまま残る保護レグは引かれる（ブローカーで生きていれば売れる数量を押さえているので、引く側が正しい）。
  - 建玉照会の後・処理中の読み取りの前に約定し、建玉照会がそれを映していない短い窓では拒否され得る（是正前と同じ）。
  - S1 の決済・失効した S0 の成行手仕舞いの側は、判断の決済が処理中であることを見ない（範囲外）。
  - 処理中の注文 1 件ごとに OpenD へ注文照会を 1 回送る（処理中が無い通常時は送らない）。頻度制限（IADR-0144 決定5）に当たれば照会は null になり、数えない側へ倒れる。
