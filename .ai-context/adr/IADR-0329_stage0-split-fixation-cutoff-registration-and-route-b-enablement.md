# IADR-0329: Stage 0 の検証分割を固定し、学習カットオフ日は構成へ登録し、駆動の有効化は経路B に置く

## コンテキストと課題

#632 が求めた 2 つ（本番の `IBacktestStrategy` 実装と、Stage 0 判定を走らせる駆動）は、#688（[IADR-0310](IADR-0310_stage0-driver-and-placeholder-verdict.md)）と #713（[IADR-0318](IADR-0318_stage0-ai-decision-record-and-replay.md)）で配備済みである。**残っていたのは、実装が既定値を発明せず計画へ環流して待っていた 2 点**であり、いずれも 2026-09-09 に裁定が下りた。

1. **計画 `ADR-0037` 決定 2**: `claude-sonnet-5` の学習カットオフ日を **`2026-01-31`** として計画 `05_trading-assumptions` §6.1 へ登録した（提供元 Models overview の training data cutoff〔Jan 2026〕を**その月の月末へ写した**値。確認日 2026-09-09）。同決定は「これで `ADR-0033` 決定 3 の『登録されるまで Stage 0 の合否判定を実行しない』という制約が解ける」と明記している。**実装側には、値を構成へ入れる作業が残っている。**
2. **計画 `ADR-0036` 決定 2 / フォローアップ 3**: ウォークフォワードの IS:OOS 比と PBO 分割数を**実装の裁量として追認**したうえで、**「ただし決めたら固定する。分割を後から動かすことを禁じる」「根拠を IADR へ残す」**と実装へ課した。実装は運用値（2:1 / 4）を持つが、**根拠を残した IADR が無い。**

あわせて 2 つの実装側の問題がある。

3. **駆動が本番既定で無効なままで、受け側（`BacktestEvaluatedProjectionHandler`）へ verdict が一通も届かない。** #632 の本文が「待っているが一通も来ない」と述べた状態がそのまま残っている。
4. **評価を 1 度も走らせていない verdict が `placeholder/no-op` を名乗る。** バー 0 本の経路（`EmptyBarVerdict`）は `IADR-0310` 決定 3 のまま戦略識別子を固定しており、#713 で `Backtest:Stage0:Strategy` による評価対象の選択が入った後も追随していない。`Strategy=recorded-replay` の構成下でも同じ枝を通るため、**選ばれている戦略とも評価した戦略とも一致しない値**を受け手（Risk・監査）へ渡している。

## 検討した選択肢

### 論点 A: 学習カットオフ日をどこへ置くか

| 案 | 評価 |
| --- | --- |
| **A-1. 構成（Helm values / appsettings）へ登録する** | **採用**（決定 1）。`ADR-0033` 決定 3 の fail-closed（未設定＝未充足）を**コード側でそのまま保てる** —— 値は環境の側にあり、モデルのピンを変えたときに構成を引き直す |
| A-2. `Stage0EvaluationOptions` のコード既定にする | **採らない。** 未設定と「登録済み」が区別できなくなる。`ADR-0011` はモデルのピン変更時に本値の引き直しと Stage 0 再実施を求めており、**コード既定はそれを黙って満たしたことにしてしまう** |
| A-3. 登録しない（現状維持） | **採らない。** `ADR-0037` 決定 2 が「制約が解ける」と明記した状態を実装が受け取らないことになる |

### 論点 B: 分割（IS:OOS 比・PBO 分割数）の固定の仕方

| 案 | 評価 |
| --- | --- |
| **B-1. コードの `public const` にし、テストで値を固定する** | **採用**（決定 2）。`ADR-0036` 決定 2 は「機械検査は無い」と明記しているが、**回帰で動かないようにはできる** |
| B-2. 構成（`Backtest:Stage0:*`）へ出す | **採らない。** 🔴 **運用が動かせる形にした瞬間、`ADR-0036` 決定 2 の「後から動かすことを禁じる」は守れなくなる。** 分割を動かせる状態は PBO/DSR の過剰適合検出そのものを無効にする |
| B-3. `private const` のまま IADR にだけ書く | **採らない。** 根拠は残るが、**値が動いても何も落ちない**（探索の実装などで触られたときに気づけない） |

### 論点 C: 駆動の有効化をどこで行うか

| 案 | 評価 |
| --- | --- |
| **C-1. 経路B（`values-local.yaml`）で有効化し、本番既定は無効のまま** | **採用**（決定 4）。実DD 供給（`IADR-0114`）・日報自動生成（`IADR-0115` 決定 6）と同じ形であり、**dogfood で経路を通しつつ本番既定のバイト等価を保つ** |
| C-2. 本番既定（`values.yaml`）で有効化する | **採らない。** `IADR-0310` 決定 1 の fail-safe を、過去データ源（`ADR-0023` 決定 5 の未確認 2 点）と記録が揃う前に覆すことになる |
| C-3. 有効化しない（現状維持） | **採らない。** #632 の受け入れ基準①②が実測できないまま残る |

### 論点 D: 走らせていない verdict の戦略識別子

| 案 | 評価 |
| --- | --- |
| **D-1. 名乗らない（空文字）** | **採用**（決定 3）。空文字は `StagePerformance.BacktestStrategyId` の既定と同値であり、空売り実弾解禁 verdict は `StrategyChanged` として無効になる（fail-safe 側・`IADR-0281` 決定 3） |
| D-2. `placeholder/no-op` のまま（現状維持） | **採らない。** **走らせていない戦略の名を verdict が運ぶ。** 安全側ではあるが、監査が「プレースホルダを評価した」と読み違える |
| D-3. 構成の戦略名（`recorded-replay` 等）を名乗る | **採らない。** **より悪い** —— 走らせていない本番戦略の識別子が段階別実績へ入り、`StrategyChanged` による無効化が効かなくなる |

## 決定

### 決定 1: 学習カットオフ日 `2026-01-31` は**構成へ登録**する（コード既定にはしない）

- 登録先は 3 つ: `deploy/helm/ai-stock-trading/values.yaml`（**本番既定**）・`values-local.yaml`（経路B の写し）・`backend/Services/BacktestService/appsettings.Development.json`。
- 🔴 **駆動側（`Backtest:Stage0:LlmTrainingCutoff`）と記録側（`Stage0Recording:LlmTrainingCutoff`）の両方へ同値を置く。** 食い違うと記録再生の評価は `RecordingMismatch` で fail-closed し、原因が構成の不一致だと読み取りにくい。CI（`helm.yml`）が経路B 描画での 2 件一致を検査する。
- **コード側の fail-closed は不変**（未設定・解釈不能は検証条件①を未充足として扱う）。**モデルのピン（`ADR-0011`）を変えたら本値を引き直し、Stage 0 を再実施する。**

### 決定 2: IS:OOS 比 2:1・PBO 分割数 4 を固定し、根拠をここに残す（`ADR-0036` 決定 2 フォローアップ 3 の履行）

**なぜこの値か。**

- **PBO 分割数 4**: `ProbabilityOfBacktestOverfitting`（CSCV）は分割数に**偶数・2 以上・ブロック数以下**を要求する。4 は「**日次リターンが 4 本以上あれば組める**」最小の実用値であり、組合せ数 C(4,2)=6 で決定的に回る。2 では IS/OOS の組が 1 通りしか取れず、分布としての PBO が意味を持たない。6 以上にすると必要な日次リターン数が増え、**`ADR-0033` §残るもの が「カットオフ後データの期間が足りるかは未実測」と書いている状況で、期間側の制約を先に厳しくしてしまう。**
- **IS:OOS 2:1**: 🔴 **記録再生戦略はパラメータ探索を持たない。** したがって IS 区間の役割は「最適化する」ことではなく、**OOS 区間を「記録の後半だけで確かめる」ために切り分ける**ことに尽きる。2:1 は「OOS に評価期間の 1/3 を残す」という配分であり、**OOS を短くしすぎない**（1/4 以下では窓ごとの総リターンが数日の値動きに支配される）一方で、**IS を確保して窓が 1 つも取れない事態を避ける**。探索が無い以上、これ以上細かい根拠を計画へ求める余地は無く、`ADR-0036` 決定 2 が実装の裁量として追認したのはこの性質による。
- **公開（`public const`）にするのはテストが値を固定できるようにするためである。** `ADR-0036` 決定 2 には機械検査が無いと明記されているため、**回帰で動かないようにする**（`Stage0ReplayEvaluationTests` の 3 件）。
- 🔴 **構成へは出さない。** 運用が動かせる形にした瞬間、「後から動かすことを禁じる」は守れない。
- **変更するときは新しい IADR で、変更の理由と Stage 0 再実施の要否を明記する。**

### 決定 3: **評価対象を 1 度も走らせていない verdict は戦略識別子を名乗らない**（`IADR-0310` 決定 3 の当該 1 点を改める）

- 対象は `Stage0EvaluationService.EmptyBarVerdict`（バー 0 本＝判定を走らせていない経路）のみ。**戦略識別子は空文字**とする。
- **プレースホルダ走行（バーがある場合）は従来どおり `placeholder/no-op` を名乗る** —— 実際に走らせたからである。
- 記録が読めない・整合しない経路（`RecordingUnusable`）は既に `preparation.StrategyId`（記録が読めなければ空）であり、本決定と同じ向きである。
- 受け側では `StagePerformance.BacktestStrategyId` の既定と同値になり、空売り実弾解禁 verdict は `StrategyChanged` として無効になる（fail-safe）。

### 決定 4: 駆動の有効化は**経路B（`values-local.yaml`）だけ**で行い、本番既定は無効のまま据え置く

- 経路B で `Backtest__Stage0__Enabled=true`・`Backtest__Stage0__Strategy=recorded-replay`・評価銘柄 AAPL を与える。
- 🔴 **過去データ源（`Backtest__BarData__Provider`）は空のまま据え置く** —— `ADR-0023` 決定 5 の「実装側で確認を要する 2 点」が実 OpenD 待ちで未了（`docs/blocked-tasks.md` A-3）であり、Stooq は同決定 1 により取得不能である。
- 🔴 **したがって経路B の verdict は必ず不合格である**（バー 0 本 → `NoHistoricalBars` の fail-closed）。**開けるのは経路であって門ではない。** `BacktestPassed` は `false` のままで、Stage 0→1 の昇格は従来どおり止まる。
- CI（`helm.yml`）が両方向を検査する: 経路B 描画で有効化されていること／**本番既定描画で `Enabled` が `false` であり `recorded-replay` が現れないこと**。設定点そのものは本番 `values.yaml` にも置くため（実効値が自己申告から読めることに意味がある）、**漏れの検査は名前ではなく値で行う。**

## 理由

- **決定 1・2 は計画の裁定の履行であり、実装が新しい原則を立てたものではない。** `ADR-0036` / `ADR-0037` の決定は 1 つも覆していない。
- **決定 3 は #713 の是正が自分の記述を引き直していなかったことの後始末でもある**（母集合の規則 10）。同 PR は評価対象の選択を入れながら、選択に依存しない枝が固定の戦略名を名乗り続けることを見落としていた。あわせて本番コードの「本番戦略はまだ存在しない」という自己申告も現況へ是正した —— #632 の背景はまさにその自己申告を証拠として引いており、**陳腐化した自己申告は次の監査を誤らせる。**
- **決定 4 が経路B に留まるのは、fail-safe を覆す条件（過去データ源・記録）がまだ 1 つも揃っていないからである。** 揃わないうちに本番既定を開けると、「駆動は動いているのに毎日不合格」という状態が本番の既定として固定され、**後から本当に評価できるようになったときに違いが読めなくなる。**

## 結果

- **良い影響**: `ADR-0037` 決定 2 が解いた制約を実装が受け取り、**検証条件①（データ健全性）が構成の上で充足し得る状態になった**。分割が固定され、回帰で動かない。受け側の射影経路が経路B で実際に通る。
- **悪い影響・トレードオフ**: 経路B では**毎日 1 通の不合格 verdict が publish される**（過去データが空のため）。`BacktestPassed=false` は既定と同値であり実害は無いが、**「駆動は動いている／評価はできていない」という 2 つの状態を運用が読み分ける必要がある**（実効構成の自己申告 `stage0-driver` / `stage0-strategy` と verdict の未達理由で読む）。
- **残るもの（本 IADR では解かない）**:
  - 🔴 **合格は依然として出ない。** 記録再生は試行 1 本であり、判定器の試行数条件（最小 20）で必ず落ちる。**探索の実装は評価対象そのものの設計変更であり、計画の裁定が要る。**
  - **過去データ源の実値**（`ADR-0023` 決定 5 の未確認 2 点・blocked A-3）。
  - **記録の取得実行**（`ADR-0033` 決定 5 の見積り提示→利用者承認・blocked B-7）。
  - **`ADR-0036` 決定 1 の実装**（復元できない as-of 入力項目を記録へ残し、合否の集計から外す）。記録器側の契約追加であり、記録実行の承認と同じ単位で扱う。
  - **`ADR-0037` 決定 3 の実装**（月報 §7 へ `stage0-recording` の見積り承認額対比）。報告書生成側の作業。
  - **実 RabbitMQ・実過去データの E2E** は #82（`IADR-0310` 決定 5 のまま）。
