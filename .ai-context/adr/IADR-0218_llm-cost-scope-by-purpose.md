# IADR-0218: 月次 LLM 費用上限の対象範囲を用途で判別し、対象外を別カテゴリへ分離する

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: 実装エージェント（w1b）／#347

## 起点・関連

- 関連する計画書 ID: 非機能要件（費用）・FR-16・FR-17・UC-01 / 05_trading-assumptions §6・§6.1
- 関連する実装仕様書: [20260828 作業仕様書](../specs/20260828_335_347_llm-allocation-and-cost-governance.md)・[IADR-0027](IADR-0027_cost-control.md)・[IADR-0055](IADR-0055_llm-cost-metering-event.md)

## コンテキストと課題

計画 05_trading-assumptions §6.1 は次を定める（利用者裁定 2026-07-31）。

> 月次 LLM 費用上限 15,000 円の対象は**取引判断サイクルのみ**である。抑制動作（80% で定時サイクル間隔を延長、
> 100% で停止）も取引判断サイクルにのみ働く。報告書生成・情報収集の LLM 費用は上限の対象外とし、
> **抑制動作も行わず、月報に実績を記載する**。
>
> **実装上の注意**: 報告書生成の費用を同じカウンタに積むと、100% 到達で報告書生成が止まる。
> 日報が確定しないと翌日の取引が止まる（UC-01 の事前条件）ため、**費用統制が取引を止める連鎖**が生じる。
> **カウンタは対象範囲どおり分離する。**

実測した現状は、**この分離が構造的に存在しない**というものだった。

- `LlmCostIncurred(Amount, At)` は用途を持たない。
- `LlmCostIncurredHandler` は受け取った費用を**無条件に** `CostCategory.Llm`（＝上限の対象）へ計上する。
- 現在たまたま正しく見えるのは、**取引判断サービスだけがこのイベントを発行しているから**である
  （報告書側は費用を 1 円も計上していなかった。#282 の過少申告の原因でもある）。

つまり「報告書の費用を計上し始めた瞬間に連鎖が生じる」状態であり、計画が名指しで禁じた形そのものである。

## 検討した選択肢

| # | 案 | 分離が構造的か | 難点 |
| --- | --- | --- | --- |
| 1 | 発行側（サービス）ごとに計上先を変える | ❌ サービスは 1 つで複数用途を持ち得る（報告書 3 種＋将来の RAG） | 発行側が統制の知識を持つ |
| 2 | 別イベント（`ReportLlmCostIncurred` 等）を新設する | ✅ | イベント種別が用途ごとに増え、購読の配線が二重になる |
| 3 | **`LlmCostIncurred` に用途を載せ、購読側がカテゴリを決める** | ✅ | 契約変更（後方互換の追加）が要る |

## 決定

**選択肢 3 を採る。**

### 決定 1: `LlmCostIncurred` に `Purpose` と `Model` を追加する（既定値つき＝非破壊）

`Purpose` が**費用の対象範囲を決める唯一の入力**である。`Model` は実効モデル（IADR-0122 決定1）で、
単価解決の根拠と月報の利用実績に用いる。既定値つきの追加であるため既存の発行側・購読側は非破壊で通る。

### 決定 2: `CostCategory` に `LlmUncapped` を末尾追加する

対象外の LLM 費用（報告書生成・情報収集）を計上する先である。
🔴 **末尾に足す。** 永続化された値（`CostEntryRow.Category`）は序数で保存されており、
途中に挿入すると既存行の意味が変わる（**7 年保持の台帳を遡って壊す**）。

`CostGovernor.EvaluateLlm` の入力は従来どおり `CostCategory.Llm` の月次累計のみであるため、
分離だけで抑制動作の対象範囲は自動的に正しくなる（統制ロジックの変更は不要）。

### 決定 3: 🔴 用途不明（`null` / 空）は**上限の対象へ倒す**

費用統制の危険側は**過小計上**である。対象外へ倒すと月次上限が構造的に効かなくなる
（IADR-0122 決定3 が「未知モデルを 0 円に倒すと上限が効かなくなる」と判断したのと同じ形）。

計画が挙げる連鎖の危険は **purpose が既知の `report-*` のときにだけ**起こり、その経路は名指しで除外される。
加えて用途を持たない `LlmCostIncurred` は取引判断サービスが発行してきた従来の形であり、
対象へ倒すことで**既存データの解釈も変わらない**。

### 決定 4: 対象外も台帳へ記録し、月報へ供給する

`ICostLedger.GetMonthlyTotals(month)` と `GET /costs/usage`（OwnerOrService）を追加する。
**対象外＝計上しない、ではない。** §6.1 は対象外の費用について「月報に用途別の実測値を記載する」と定めており、
記録が無ければ #282 の過少申告が再発する。消費率（`GovernedPercent`）の分子は**対象分だけ**とする
（対象外を混ぜると「上限に近づいている」という誤った運用シグナルになる）。

## 理由

- 選択肢 2（別イベント）を退けたのは、**用途が増えるたびにイベント種別と購読の配線が増える**からである。
  用途は計画側で今後も増え得る（RAG・分析）。判別のロジックは 1 か所（`LlmCostScope`）にあるべきである。
- 決定 3 の向きは 2 つの fail-safe が衝突する箇所であり、**どちらへ倒すかを明記しておかないと
  後から逆向きに「安全側」を主張されうる**。危険の実測（IADR-0114 の「毎回 ¥0 計上」）がある側を優先した。

## 結果

- 良い影響: 「費用統制が報告書生成・取引を止める連鎖」が**構造的に**起こらなくなる（同じカウンタに乗らない）。
  対象外の費用も台帳に残り、月報へ供給できる。
- 悪い影響・トレードオフ:
  - `CostCategory` が 1 つ増え、既存の集計・画面が「Llm だけを見ている」ことを前提にしていると
    対象外の費用が見えない。`/costs/usage` が内訳を返すことで補う。
  - **用途を載せ忘れた発行は上限側へ積まれる**（決定 3）。過大計上は統制が実態より早く効くだけだが、
    報告書側で載せ忘れると計画が禁じた連鎖に戻る。ReportService の発行は用途を必須引数にして塞いだ。
- フォローアップ:
  - 月報テンプレートへの「当月の LLM 利用実績」節の**描画**は #338 の担当。本 ADR は供給までである。
