# IADR-0351: 取引判断のプロンプトへ保有状況を載せ、出口を判断できるようにする

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。
> 計画に影響する決定は planning へ issue で環流する（`feedback.yml` テンプレート）。

- 状態: Accepted
- 日付: 2026-09-19
- 決定者: endazon（[#854](https://github.com/endazon/ai-stock-trading/issues/854)）/ Claude Code（起案）

## 起点・関連

- 実測（稼働環境・2026-09-17 と 09-18 の 2 夜）: 取引判断が **Buy しか出さない**。5 分周期のサイクルが当日の発注枠を
  使い切るまで買い増しを続け（09-18 は 4 サイクルで 3,378 株）、含み損が拡大しても判断文は「新規買いを検討可能」のままだった。
- 計画 ADR-0003 の決定: 「AI の判断入力は『確定済み日報＋**保有ポジション**＋収集情報＋過去判断のRAG』に限定」。
  **保有ポジションは計画が定めた判断入力であり、実装がそれを渡していなかった。** 本 IADR は計画の変更ではなく欠落の是正である。
- 計画 FR-04: 生成 AI は「当日の日報の方針」と「リスク制約」の範囲内でのみ売買判断を行う。
- 出口の経路は既にある: [IADR-0119](IADR-0119_decision-derived-close.md)（保有ロング＋`Sell` → `Close`・保有全量）。
- 損切りの実行機構は選択式: 計画 ADR-0040 決定1 / [IADR-0342](IADR-0342_simulate-stop-loss-method-selection.md)。
  S2（逆指値なし）と、S0 が拒否される moomoo SIMULATE では、**出口は LLM の判断と人手しか無い**。
- 作業仕様書: `.ai-context/specs/20260919_854_held-position-in-decision-prompt.md`（母集合・費用の見積り）。

## コンテキスト

`TradeDecisionPromptBuilder.Build` / `BuildScreening` が LLM へ渡していたのは、方針・現在値（または価格変動）・リスク制約・
空売りの制約・参考情報だけで、**保有数量・取得単価・含み損益・損切りライン・保護の状態のいずれも無かった**。LLM は
毎サイクルを「何も持っていない状態での新規買いの是非」として判断していた。`Sell` を出せば決済へ解決する仕組みは
あったが、LLM は自分が建玉を持っていることを知らないため、出口を判断しようがなかった。

## 決定

### 決定1: 保有状況は既存の 2 つの同期照会から取る（新規エンドポイント・イベント・構成キーを作らない）

| 項目 | 出所 |
| --- | --- |
| 保有数量（符号付き）・平均取得単価・記録上の損切りライン | リスク管理の `GET /risk-controls/open-positions`。取引判断は既に `IHeldPositionProvider` でここを引いており（IADR-0119 決定3）、**数量だけを読んでいた**。`GetPositionAsync`（`HeldPosition?`）を足して同じ応答の残り 2 項目も読む |
| 含み損益（額・率）・損切りライン到達 | 取引判断が計算する。評価価格は**プロンプトが現在値として LLM に見せている値と同じ**（価格変動トリガー＝`trigger.Price`／定時＝`ICurrentPriceProvider`）。到達の向きは市場監視の `StopLossEvaluator` と同じ。**LLM に計算させない** |
| 保護の状態 | `GET /risk-controls/sizing-context` の応答へ `StopLossMethod`（損切りの実行機構の**設定**。S0〜S3）を加法的に足す。取引判断が毎判断で既に引いている経路であり、HTTP 呼び出しは増えない。取引判断側の `SizingContext.StopLossMethod` は nullable で、**項目の無い旧応答・照会失敗の安全既定・プレースホルダは null＝不明**（S0 と読まない） |

サービス間の直接参照は増やさない（取引判断はリスク管理の DTO を自前の `OpenPositionDto` で受ける。既存と同じ）。

🔴 **保護の状態は「設定」であって「この建玉の逆指値が今効いているか」ではない。** 建玉ごとの保護の成否を持つ射影は
リスク管理に存在しない（台帳の承認行は保護レグの決済と判断由来の決済を区別せず、`ProtectiveStopWaived` は購読されていない）。
プロンプトはこれを偽らない: **断定するのは S2（保護レグを発注しない＝無保護）だけ**で、S0 / S1 / S3 は
「その設定である。ただしこの建玉の逆指値が現在有効かどうかは供給されていない（不明）」と書く。S0 でも保護を失った建玉は
残り得る（#847: 保護喪失時の手仕舞いが下落で約定しない）。設定から「保護あり」を断定すると、無保護の建玉について
LLM に「自動の損切りが効く」という偽の前提を与える。

### 決定2: 「保有あり／保有なし／不明」の 3 状態を必ず書き分ける。不明を保有なしと書かない

- 保有状況節（`# 保有状況（この銘柄）`）は**無条件に出す**。`Build` / `BuildScreening` の `held` 引数は
  **null（既定）＝不明**、保有なしは `HeldPosition.None` を明示して渡す。**不在が「保有なし」を意味する形にしない**
  （IADR-0119 決定3 の「空配列＝0／失敗＝null」の区別をプロンプトまで貫く）。
- 不明のときは「保有状況が不明なときは、新規建て・買い増し・手仕舞いのいずれも判断できないため Hold を選びます」と述べる
  （計画 ADR-0003「不確実な場合は必ず Hold」）。
- 取得単価・損切りライン・現在値・保護の設定が個別に欠けるときも、その項目を「不明」と書く。**0 や空で埋めない**
  （取得単価 0 は含み損益を、損切りライン 0 は「未到達」を捏造する）。`HttpHeldPositionProvider` は応答に無い・正でない価格を
  null にする。**プロンプト側（`HeldPositionView.Of`）も取得単価について同じ境界を守る**——正でない取得単価は
  「不明」として扱い、含み損益（額・率）も「不明」と書く（`HeldPosition` は公開レコードであり、別の供給元が 0 を直接渡すと
  含み損益率の除算が `DivideByZeroException` になる。本番の供給元が弾くので現状は到達不能。#860 の監査・レビューの指摘を反映）。
- 照会の例外は null（不明）へ縮退する（`GetHeldPositionSafeAsync`）。コード側の既存の安全網（不明・保有なしの `Sell` は
  見送り＝IADR-0119 決定2）は変えない。
- ［2026-09-24 追記 / [#934](https://github.com/endazon/ai-stock-trading/issues/934)］**本決定の「保有」は約定済みの建玉だけであり、
  未約定の新規建て注文が見えていなかった**（稼働 PoC で、指値 715 株が板に残っている間に判断が 2 本とも「保有なし」と書いて
  同じ銘柄を重ねて買った）。[IADR-0390](IADR-0390_working-entries-in-decision-input.md) が**未約定を約定済みの保有とは別の第 3 の状態として、別の型・別の行で**
  渡し、`保有: なし` を出す条件を「約定済み 0 株**かつ**未約定が無いと判っている」へ狭めた（未約定が不明なら保有を「不明」と書く）。
  本決定の 3 状態の書き分けと `held` の意味（約定済み）は変えていない。

### 決定3: 方針は書き換えない。出口の基準が方針に無いときは保有継続を既定とし、損切りラインに達した建玉はリスク制約に基づいて手仕舞いを選べる

保有中の銘柄について、プロンプトは「買い増し（Buy）・保有継続（Hold）・手仕舞い（Sell）のいずれかを判断する」と明示する
（ショートは売り増し＝Sell／手仕舞い＝Buy）。**方針（`DailyPolicy.Summary`）は一字も書き換えず、上書きも複製もしない**
（テストが全文一致と出現回数 1 を固定する）。そのうえで出口の基準の優先順を次のとおり定める。

1. **方針に出口の基準（利確・損切り・保有期間など）があれば、それに従う。**
2. **方針に出口の基準が無ければ、保有継続（Hold）が既定である。** 方針が語っていない利確・時間切れの撤退を LLM に
   勧めない（それは方針の範囲外の行動を勧めることになる）。
3. **ただし、現在値が記録上の損切りラインに達している建玉は、リスク制約に基づいて手仕舞いを選べる。**

3 が方針の範囲外の行動ではない理由:

- FR-04 は判断の枠を **「方針」と「リスク制約」の 2 つ**で定めている。損切りラインは FR-10 が列挙するリスク統制
  （銘柄別損切りライン）であり、**その建玉を建てた判断が自分で決め、台帳が権威データとして保持している値**である
  （[IADR-0035](IADR-0035_stop-loss-authoritative.md)）。達した建玉を閉じるのは、建てた時点の判断が置いた条件の履行であり、
  方針への新しい解釈の追加ではない。
- 計画 ADR-0003 は「損切りは AI を経由せず機械的に執行する」と定める。**本決定はそれを置き換えない**——機械的な執行
  （ブローカー側逆指値）が効く構成ではそちらが先に働く。効かない構成（S2・SIMULATE で拒否される S0）で、
  **残る出口を塞がない**ための決定である。計画 ADR-0040 決定3「生成 AI は損切りの実行機構の選択を上書きできない」にも
  触れない（LLM が変えるのは建玉であって設定ではない）。
- 文言は「選べます」であり「選びなさい」ではない。到達・未到達・不明はコードが判定して事実として渡し、
  LLM は方針と合わせて判断する。

買い増しについては「方針がそれを支持する場合に限る。保有を踏まえずに同じ根拠で新規建てを繰り返さない」と述べる。
これは方針を狭めるのではなく、既存の冒頭文（方針の範囲外・不確実なら Hold）を保有中の文脈へ言い直したものである。

**4. 現在値が記録上の損切りラインに達している建玉へは、買い増し・売り増しをしない**（#860 の監査の指摘を反映）。
文言: 「現在値が記録上の損切りラインに達している建玉へは、買い増し・売り増しをしません（損切りラインはリスク制約であり、
方針が買い増しを支持していても同じです）。」保有ありの節へ無条件に出す（`NoAddAtStopLossLineRule`）。

- **これが無いと 3 の出口が消える。** リスク管理の `PortfolioProjection` は、建玉と同方向の約定のたびに記録上の損切りラインを
  **最新エントリーの値へ更新する**（IADR-0035。建て増しも対象）。含み損の中で LLM が買い増すと、記録上のラインは新しい
  （より低い）エントリー基準へ下がり、プロンプトの「達しています」が「達していません」へ戻って、既定が Hold（2）へ戻る。
  買い増しの歯止めは「方針がそれを支持する場合に限る」だけであり、方針が「押し目買い」なら含み損そのものが買い増しの
  根拠として読まれ得る——#854 の実測（含み損が拡大しても買い増しを続けた）と同じ形が、保有を知ったうえで再現する。
- **方針の創作ではない。** 3 と同じくリスク制約（FR-10 の銘柄別損切りライン）に由来する。FR-04 は判断を「方針」**と**
  「リスク制約」の**両方の**範囲内に限っており、方針が買い増しを支持していても、リスク制約が置いた撤退の条件に達した建玉を
  積み増すことはその範囲に入らない。方針（`DailyPolicy.Summary`）は書き換えない。
- 🔴 **これはプロンプト上の歯止めであり、コードの統制ではない**（残る制約）。LLM が従わずに Buy を返せば、買い増しは
  従来どおり通り、記録上のラインは下がる。

### 決定4: 一次スクリーニングにも短縮版を載せる

一次は**門**である（`Hold` を返すと本判断が走らない。IADR-0039）。保有を知らない一次は「新規の関心なし」で
損切りライン到達の建玉を落とし得る——**出口の判断が本判断へ届かない**。したがって 3 状態の短縮版を一次にも無条件で載せる:
保有ありは 1 行の事実（数量・取得単価・含み損益率・損切りラインと到達）＋「保有中の銘柄は手仕舞いの検討に値する場合も
本判断へ進める」の 1 行。**保護の状態と出口の規則の詳細は本判断側だけが持つ**（費用統制。IADR-0297 の短縮版と同じ線引き）。

保有状況は縮退の**保護対象**である（削ると出口を落とす）。`ScreeningContextAssembler` の銘柄側保護分の概算
（`PerSymbolLineChars`）を実測 200 文字＋余裕で 120→400 へ底上げした。

**縮退制御なしの経路（`Decision:ScreeningContextBudgetChars` を "0" / "off" にした構成）でも、一次へ現在値を渡す**
（#860 の監査の指摘を反映）。当初は渡しておらず、定時トリガー（価格を持たない）では一次の保有状況が常に
「到達したかは不明＝現在値が供給されていません」になっていた——本判断は現在値を知っているのに、門である一次だけが
損切りライン到達を知らない。代償として、この構成の一次プロンプトにも「- 現在値」行が 1 行出る（現在値が供給されている
ときだけ。既定の NoOp では従来どおり出ない）。既定構成（縮退制御あり）は元から現在値を渡しており、変わらない。

### 決定5: 手仕舞いの数量は変えない（保有全量・システムが決める）

IADR-0119 決定1 が「決済は常に全量」と定めており、現物を確認したところ `PositionEffectResolver` は `CloseQuantity`＝保有数を
返し、サイジング・採算ゲート・損切り幅の検証を通さない。**変えない。** 理由: LLM は数量を出力しない（計画 ADR-0040 決定5・
`QuantityIsSystemDecidedRule`）。部分決済には LLM 出力の拡張と「どれだけ残すか」の統制値が要り、どちらも計画に無い。
プロンプトは「手仕舞いは保有の全量をシステムが決済します（一部だけの決済は選べません）」と事実を述べる。

保有数量をプロンプトに出すため、LLM が根拠文で株数に触れる可能性は上がる。既存の `RationaleQuantityReconciler`
（[IADR-0343](IADR-0343_rationale-quantity-reconciliation.md)）がそのまま働く——決済では保有全量と一致し、買い増しで
食い違えば注記が付く。「rationale では株数に言及しないでください」の指示も残る。

### 決定6: 発注に使う保有数は LLM 判断の後に引き直す（プロンプト用の取得を使い回さない）

プロンプト用の保有状況は LLM 呼び出しの**前**に 1 回引く。建玉効果（Open / Close）と決済数量を決める保有数は、従来どおり
LLM 判断の**後**に引き直す。LLM 呼び出しには数秒〜数十秒かかり、その間に逆指値が約定し得る——古い数量で全量決済を出すと
在庫を超える（判断由来の決済は owner 決済経路の在庫検査〔IADR-0117〕を通らない）。代償はクラスタ内の GET が
毎サイクル 1 回増えること（LLM の前。Buy / Sell が出たサイクルでは前後の計 2 回になる）。鮮度切れレートの経路だけは従来どおり先読みを再利用する（#506）。

**回帰テストで固定する**（#860 の監査・レビューの指摘を反映。当初は偽物が LLM の前後で同じ数量を返しており、
「引き直している」ことと「先取りした値を使い回している」ことをテストが区別できなかった）。プロンプト時は保有あり →
LLM 後に 0 → **見送り**／LLM 後に不明 → **見送り**／LLM 後に数量が変わった → **変わった後の数量で Close**。

🔴 **ここでいう「発注直前の事実」は台帳の事実であり、ブローカーの事実ではない**（残る制約）。

### 決定7: Stage 0 の記録器は「保有なし」を明示して渡す

`Stage0DecisionRecorder` の記録は銘柄 × 判断時点で独立であり、保有は再生側（BacktestService）のシミュレーションでしか
決まらない。既定（不明）のままではプロンプトが「不明なら Hold」と述べ、全件が Hold へ倒れて Stage 0 が成立しないため、
`HeldPosition.None` を明示する。

## 棄却した案

| 案 | 棄却の理由 |
| --- | --- |
| 方針に出口の基準が無ければ、保有中は常に Hold（損切りライン到達でも Sell を許さない） | S2 と、S0 が拒否される SIMULATE では出口が人手だけになる。#854 の受け入れ基準「損切りライン割れで LLM が Sell を返せる」を満たさない。損切りラインは FR-04 のいうリスク制約であり、許しても方針を越えない |
| 含み損が一定率を超えたら Sell を勧める・利確の目安を示す | 方針にもリスク統制にも無い基準を実装が作ることになる。方針は利用者のものである |
| 損切りライン到達をコードで検知して LLM を介さず決済する（ソフトウェア逆指値） | S1（#820）そのものであり、本 issue の射程外。二重決済の整理（IADR-0210 決定5）も要る |
| 建玉ごとの保護の成否をリスク管理に射影させる | 台帳の承認行に保護レグの由来が無く、`ProtectiveStopWaived` の購読・保護注文の終端の追跡・永続化が要る（別サービスの新しい射影＋マイグレーション）。本 PR は設定を偽らずに伝えるところまでとし、残る制約に記す |
| `StopLossMethod` を `open-positions` の各行へ載せる | 設定を建玉の属性のように見せる（その建玉が建った時点の手法とも、今の保護の成否とも限らない）。`sizing-context` は既に「設定＋ポートフォリオ状態から導出した判断の文脈」であり、呼び出しも増えない |
| `held` 引数の既定を「保有なし」にする・節を保有ありのときだけ出す | 渡し忘れが「保有なし」になり、#854 と同じ事故が静かに再発する。不在が統制の無効を意味する形にしない（IADR-0163 決定2 の規律） |
| 不明のときは LLM を呼ばずに見送る／不明での Buy をコードで止める | IADR-0119 決定2（不明でも Buy は Open）を覆す挙動変更であり、既定構成（NoOp＝常に不明）の全経路に効く。プロンプトで Hold を述べるに留め、**保留点**とする（下記「残る制約」。追随は #865） |
| プロンプト用に引いた保有数を決済数量にも使う | 決定6 のとおり、古い数量での全量決済は在庫を超え得る |

## 結果

- 良い影響: LLM が保有を知ったうえで買い増し・保有継続・手仕舞いを判断できる。不明は不明として伝わり、安全側（Hold）へ倒れる。
  保有なしのプロンプトは、保有状況節（見出し＋1 行＋空行の 38 文字）を除けば従来と一字一句一致する（テストが全文で固定）。
- 悪い影響 / トレードオフ: 入力トークンが増える。実測の増分（文字数）は本判断 +38（保有なし）/ +108（不明）/ +557〜594（保有あり。うち +80 は
  決定3 の 4 の 1 文）、一次 +38 / +108 / +200。保守側（1.0 トークン/文字・常時保有・毎サイクル本判断まで到達・多数決 1 回）で
  **1 銘柄あたり月 約 350〜370 円**（月次上限 15,000 円の約 2.5%）。算出は作業仕様書。
- Stage 0 の入力の指紋（プロンプト全文の SHA-256）は本変更で変わる（プロンプトを変える変更に共通。IADR-0343 と同じ）。

## 残る制約

- 🔴 **LLM が実際に Sell を返すかは実 LLM でしか確かめられない。** 本 PR はプロンプトの内容をテストで固定するだけであり、
  実 LLM を呼んでいない。稼働環境での再実測を待つ。
- 🔴 **保護の状態は設定であり、建玉ごとの保護の成否ではない**（決定1）。S0 / S3 のもとで保護を失った建玉を「無保護」と
  伝える手段はまだ無い。
- 🔴 **Stage 0 の記録は本番プロンプトの「保有なし」の枝しか検証しない**（決定7）。本番の判断が保有に依存するようになったため、
  保有中の判断（買い増し・手仕舞い）は Stage 0 の評価対象に入らない。計画 ADR-0033（評価対象は AI 判断そのもの）との関係は
  計画側の判断が要る（環流候補）。
- 🔴 **台帳の乖離との相互作用**（#860 の監査）。決定6 の「発注直前の事実」は**台帳の事実であり、ブローカーの事実ではない**
  （プロンプト用の取得も LLM 後の引き直しも、同じ台帳の射影 `GET /risk-controls/open-positions` を引く）。台帳がブローカーと
  乖離していると（#849。2026-09-18 に実際に発生した）、プロンプトは**実在しない建玉を事実として提示**し、LLM の Sell は
  Close へ解決されて、ブローカー上では**保有 0 からの売り**になり得る。決済の注文はリスク統制を通らない
  （FR-10「手仕舞いは止めない」）ため、この経路に歯止めは無い。決済をブローカーの実建玉と突き合わせる対策は **#864**
  であり、本 PR では直さない。**本 PR は、台帳とブローカーの建玉が一致していることを確認してから稼働環境へ反映する。**
  本 PR より前は判断が Sell を出さなかったため踏まれなかった穴であり、本 PR が Sell を出させるようになって初めて踏まれる。
  ［2026-09-19 追記 / #864］**この穴は [IADR-0355](IADR-0355_close-order-broker-position-gate.md) で塞いだ。**
  決済は発注直前にブローカーの実建玉と突き合わせ、足りなければ実建玉の範囲へ縮め、無い／照会できないときは送らない
  （建玉照会の能力を持つ発注先に限る。内蔵 paper は従来どおり照合しない）。**本項の「この経路に歯止めは無い」は
  もはや成り立たない。** 決定6 の記述（発注に使う保有数は台帳の事実であってブローカーの事実ではない）は**そのまま生きている**
  ——突き合わせは発注執行が行うのであって、判断側が引く数量の出所は変わっていない。
- 🔴 **保有が不明のもとでの Buy をコードでは止めていない**（IADR-0119 決定2 のまま）。プロンプトは Hold を述べるが、
  LLM が従わなければ新規建ては従来どおり通る（金額系の統制は効く）。本番では保有状況の照会先とサイジング文脈の照会先が
  同じリスク管理であり、片方だけ落ちる状況は限られる。追随: **#865**（実結線のもとで保有が不明なら Open を見送る）。
  ［2026-09-19 追記 / [#865](https://github.com/endazon/ai-stock-trading/issues/865)］✅ **解消した**
  （[IADR-0358](IADR-0358_skip-open-when-holdings-unknown.md)）。保有状況の照会先が実結線のときに限り、不明のもとでの
  `PositionEffect.Open` を見送る（未結線の既定構成は従来どおり）。**上の棄却した案のうち採ったのは後半（不明での Buy を
  コードで止める）だけである**——前半（不明なら LLM を呼ばずに見送る）は棄却のままとした。発注に使う保有数は決定6 のとおり
  LLM 判断の後に引き直すため、**前で一律に見送ると「プロンプト時は不明・引き直しでは保有あり」の手仕舞いが消える**。
- **損切りライン到達中の買い増しの禁止はプロンプト上の歯止めである**（決定3 の 4）。LLM が従わずに買い増せば、
  リスク管理の射影は記録上の損切りラインを最新エントリーの値へ更新し（IADR-0035）、到達の表示は「達していません」へ戻る。
  コードで止める（到達中の Open を見送る）かどうかは本 PR では決めていない。
- 記録上の損切りラインは、権威データを持たない建玉（レガシー等）では既定比率の近似である（IADR-0030）。応答はどちらかを
  区別しないため、プロンプトも区別していない。

## ［2026-09-25 追記 / #936・IADR-0393］「買い増しで記録上のラインが下がる」は、先に建てたロットが残る限り起きなくなった

決定3 の 4 の理由文「リスク管理の `PortfolioProjection` は、建玉と同方向の約定のたびに記録上の損切りラインを**最新エントリーの値へ更新する**
（IADR-0035）」と、残る制約の「LLM が従わずに買い増せば、…記録上の損切りラインを最新エントリーの値へ更新し、到達の表示は
『達していません』へ戻る」は、[IADR-0393](IADR-0393_most-protective-stop-line-per-entry-lot.md) で**前提が変わった**（本文は凍結記録として残す）。

- 記録上の損切りラインは**保有中のエントリーのうち最も保護的な値**になった。含み損の中で低いラインの買い増しが入っても、
  先に建てたロットが残る限りラインは下がらず、「達しています」は「達していません」へ戻らない。
- **規則 4（到達中の建玉へは買い増ししない）は残す。** 買い増しが到達中の建玉を膨らませることに変わりはない。
  コード注記（`TradeDecisionPromptBuilder.NoAddAtStopLossLineRule` の上）も同じ形へ書き直した。プロンプトの文言は変えていない。
