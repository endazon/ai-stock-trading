# IADR-0208 PR の CI は速さを採り、落とした精度は後段（マージ時・日次/週次）で担保して失敗を自動起票する

## 状況

PR の CI が遅く、開発の反復が止まっていた。**着手前に実 run を測った**
（2026-08-21・run `32443950165`）。

| ワークフロー | 所要 |
| --- | --- |
| Claude Code Review | **4分21秒** |
| CI | **3分29秒** |
| Security | 1分30秒 |

測って分かったことが 3 つある。

**1 つ目。最長は CI ではなく AI レビューだった。** しかも `claude-review` は必須チェックである。
内訳の大半は「AI が動き出す前」の工具一式で、**docs だけの PR でも全額を払っていた**。
プロンプト側は「`backend/` が変わっていなければビルドするな」と指示しているが、
**セットアップはその時点で既に払い終わっている**。**指示では回収できない種類の無駄である。**

**2 つ目。「ジョブが多いから遅い」ではなかった。** `ci.yml` の 21 ジョブは `needs:` を 1 つも
持たず全並列で、16 個の軽量ジョブ（各 10〜15 秒）は待ち時間をほとんど作っていない。
クリティカルパスは `build-and-test` 1 本である。
**ジョブ数を減らす施策と、クリティカルパスを縮める施策は別の問題である。**

**3 つ目。`setup-dotnet` は 6 箇所すべてが `cache:` 未設定**で、101 個の csproj を毎 run
コールドで restore していた。

一方で、CI を速くする手段の多くは**検証の精度を落とす**。何をどこまで落としてよいかは
実装側だけでは決められないため、利用者へ裁定を求めた。

## 決定

### 決定 1: PR の精度は落としてよい。ただし落とした分は後段で必ず担保する

利用者裁定（2026-08-21）: **「毎プルリクの精度は下がってもいいが、develop ブランチ
マージ時か日時実行にするなどしてどこかで担保できる様にする。そのときに失敗したら
自動で issue 起票する」。**

この裁定が他のすべての決定の性格を決める。決定 4・5 は「検証をやめる」のではなく
**「検証を PR から後段へ移す」**である。両者は結果が違う。
**後段が黙って赤いまま放置されれば、移しただけで失っているのと同じになる。**
したがって**自動起票は付随的な便利機能ではなく、この設計の成立条件である。**

| PR で落とすもの | 担保する場所 | 後段の精度 |
| --- | --- | --- |
| CodeQL の生成コード解析 | `codeql.yml`（push ＋ 週次・`build-mode: autobuild`） | **現状と同一** |
| `vulnerable-scan` | `security.yml`（push ＋ 週次） | **現状と同一** |

`ci-failure-issue.yml`（再利用ワークフロー）を新設し、上記と `integration.yml` の末尾から呼ぶ。

### 決定 2: `integration.yml` にも同じ担保を入れる（今回落とすものではないが）

`IADR-0049` で統合テストは既に nightly 分離済みである。しかし**自動起票が無く、
落ちても誰も知らないまま赤が積み上がる形**だった。決定 1 で同じ構造の仕組みを作るのだから、
**同型の穴を 2 つ残さない**。あわせて `push: [develop]` を足し、マージ時にも回すようにした
（日次だけだと、朝までの間に別の PR が積み上がって原因の切り分けが難しくなる）。

### 決定 3: 🔴 `claude-code-review.yml` の工具導入を PR の差分で出し分ける

前段の `git diff --name-only` の出力で、4 つのセットアップを `if:` 条件付きにする。

🔴 **`--allowedTools` と `.claude/settings.json` は触らない。** 3 系統一致の規約があり
`check-ai-workflow-config.js` が STRICT で見ている。変えるのは**事前導入の有無だけ**である。

🔴 **判定は広めに倒す。** 取りこぼすと「許可されているのに実行できない」状態になり、
AI は「実行したが失敗した」と報告する。**原因が環境不備であることは本文から判らないため、
拒否されるより質が悪い**（#391 の教訓がそのまま当てはまる）。
迷ったら入れる —— 速度のために正しさを削る方向に倒さない。

### 決定 4: CodeQL は PR だけ `build-mode: none` にする（全面的に倒さない）

`build-mode` は式を受け付ける文字列入力（`none` / `autobuild` / `manual`）であるため、
イベントで切り替えられる。PR は `none`、push（develop/main）と週次 schedule は `autobuild`。
`Autobuild` ステップには `if: github.event_name != 'pull_request'` を付ける。

**PR で落ちる精度は具体的である**: 生成コードが解析対象外になる。
だから全面的に `none` へ倒さず、後段で `autobuild` を維持する。

⚠️ **同じ check 名で PR と後段の精度が違う。** 読み手が最も誤解しやすい点なので
`codeql.yml` のコメントに明記する。**PR が緑でも push で赤くなることがあり得る。
それは退行ではなく設計どおりである。**

### 決定 5: `vulnerable-scan` を PR から外す

見ているのは「既存の推移依存 × 後から公開された advisory」であり **PR の差分とは無関係**である
（ファイル冒頭のコメント自身が「schedule での定期実行が主目的」と書いている）。
PR 差分の依存レビューは `dependency-review` が既にカバーしている。必須チェックでもない。

### 決定 6: Node 検査ジョブは束ねるが、検査は 1 本も減らさない

15 ジョブを `static-checks` 1 つへ束ねる。
`commit-messages`（必須）・`scripts-tests`（子プロセスを多数回す重量級）は単独のまま残す。

🔴 **束ねる際、失敗の可読性を落としてはならない。** 単純に連続ステップへ並べると
**最初の失敗以降の検査が走らず**、1 回の CI で 1 件しか分からなくなって往復が増える。
各ステップへ `if: ${{ !cancelled() }}` を付け、落ちた検査が複数あれば一度に全部出るようにする。

🔴 **既存ジョブのコメントを 1 行も捨てない。** ADR 番号・事故の経緯・
「これを外すと検査が空回りする」という設計要点を持つ資産である。各ステップ直前へ移設する。

副次効果として、**統合前は 4 ジョブがそれぞれ 1147 個の `.cs` を個別に走査**していたのが 1 回になる。

### 決定 7: changelog 自動 PR では重いジョブを回さない

`automation/changelog-update-develop` の PR で CI が `action_required` のまま毎回起動していた。
`lint` / `build-and-test` / `frontend` / `frontend-e2e` へ
`if: !startsWith(github.head_ref, 'automation/')` を足す。

⚠️ **必須チェックのジョブへ `if:` を付けてよい根拠**: `if` でスキップされたジョブは
**必須チェック上「合格」として扱われる**（`docs/ai-workflow.md` に明記）。
`paths:` でワークフローごと起動しない場合と違い、恒久 pending にはならない。
**この 2 つは結果が正反対なので混同しないこと。**

## 却下した案

### 却下 A: CodeQL を PR から丸ごと外す

PR 時点で SAST の指摘が一切出なくなる。`build-mode: none` なら PR でも解析自体は走り、
落ちるのは生成コードの分だけで済む。**落とす量を最小にできる選択肢がある以上、
大きく落とす案は採らない。**

### 却下 B: `claude-code-review` のセットアップを丸ごと消し、AI に必要時インストールさせる

`--allowedTools` に `dotnet tool install` 等を足す必要があり、**3 系統一致の規約**
（ワークフロー 2 本 ＋ `.claude/settings.json`）を広げることになる。
ツールの許可面を速度のために広げるのは筋が違う。**事前導入の有無だけを変える。**

### 却下 C: 自動起票を後追いの別 PR にする

「PR から外す変更」と「後段で担保する仕組み」を別 PR に割ると、
**その間だけ担保が無い窓ができる**。決定 1 の趣旨に反するため同じ PR に入れる。

### 却下 D: ワークフローレベルの `paths:` で PR の実行を絞る

`paths:` を持つワークフローは対象外の PR で **report されず恒久 pending** になるため
必須チェックに指定できない（`docs/ai-workflow.md` の既存ルール）。
出し分けは**ジョブ条件 `if:`** で実装する（決定 3・7）。

## 影響

- **PR の待ち時間は縮む。** 一方で **develop へのマージ時と日次/週次はむしろ重くなる**
  （全量 CodeQL・vulnerable-scan・統合テストがそちらへ寄るため）。**それが狙いである** ——
  誰も待っていない場所へ重い検証を移す。
- **`develop` / `main` への push は `cancel-in-progress` の対象にしない。**
  担保がそこに載るため、途中でキャンセルしてはならない。
- 新しい依存として `actions/cache` / `actions/github-script` が加わる。
  `scripts/action-versions.json` の `expected` へ同時に追加した
  （片方だけ直すと `check-action-versions.js` が CI で落ちる）。

## 残余リスク

- 🔴 **自動起票は「動かないことに誰も気付かない」種類の仕組みである。**
  失敗したときにしか走らないため、平時は常に skip で緑になる。
  `integration.yml` の `workflow_dispatch` 入力 `force_failure` で**実際に 2 回走らせて**
  ① issue が立つ ② 2 本目が立たずコメントが足される を実測すること。
  実測しないまま「起票を入れた」と言わない。
- 🔴 **決定 3 の判定条件の取りこぼし。** `backend/` を触る PR で `dotnet` が入らないまま
  AI がビルドを試みると失敗する。判定は広めに倒してあるが、
  **docs のみの PR と backend を触る PR の両方を実測するまで完了としない。**
- PR と後段で CodeQL の精度が違う。PR が緑でも push で赤くなることがあり得る。
  それは退行ではなく設計どおりである。決定 4 のコメントで読み分けられるようにした。
