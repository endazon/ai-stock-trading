# IADR-0208 PR は速さを採り、落とした精度は回収先（push・日次・週次）で取り戻す。回収先の失敗は自動起票する

## 状況

PR の CI が遅く、開発の反復が止まっていた。**着手前に実 run を測った**
（2026-08-21・run `32443950165`）。

| ワークフロー | 所要 |
| --- | --- |
| Claude Code Review | **4分21秒** |
| CI | **3分29秒** |
| Security | 1分30秒 |

測って分かったことが 3 つある。

**1 つ目。最長は CI ではなく AI レビューだった。** しかも `claude-review` は必須チェックである。
内訳の大半は「AI が動き出す前」の工具一式で、**docs だけの PR でも全額を払っていた**。
プロンプト側は「`backend/` が変わっていなければビルドするな」と指示しているが、
**セットアップはその時点で既に払い終わっている**。**指示では回収できない種類の無駄である。**

**2 つ目。「ジョブが多いから遅い」ではなかった。** `ci.yml` の 21 ジョブは `needs:` を 1 つも
持たず全並列で、16 個の軽量ジョブ（各 10〜15 秒）は待ち時間をほとんど作っていない。
クリティカルパスは `build-and-test` 1 本である。
**ジョブ数を減らす施策と、クリティカルパスを縮める施策は別の問題である。**

**3 つ目。`setup-dotnet` は 6 箇所すべてが `cache:` 未設定**で、101 個の csproj を毎 run
コールドで restore していた。

一方で、CI を速くする手段の多くは**検証の精度を落とす**。何をどこまで落としてよいかは
実装側だけでは決められないため、利用者へ裁定を求めた。

## 決定

### 決定 1: PR は速さを採る。落とした精度は回収先で必ず取り戻す

利用者裁定は 3 段階で入った。**判断が 2 度動いている。経緯ごと残す。**

> **［2026-08-22 改定 3・本決定の現在の形］**「なぜ改善案を変更したのですか？**プルリク時の
> 精度低下は、どこかで回収できるならある程度許容する**ので、AI コーディング→プルリク→CI→
> AI コーディング…の**ループ効率が上がるように**してください」。
>
> 🔴 **改定 2 は読み違いだった。** 「なるべく精度は落とさない方向で」を「PR から外す案は全部
> 取り下げよ」と読んだが、正しくは「**両立する手段を優先せよ**」であり、
> 土台（［2026-08-21］の回収 ＋ 自動起票）は生きていた。**改定 3 で土台へ戻し、
> 評価軸を「PR の待ち時間 ＝ ループ 1 周の長さ」に置き直した。**
>
> **今後の判断基準**: 速くなるが精度が落ちない手段は無条件で採る。
> 精度が落ちる手段は**回収先を書けるなら採る。回収先が無いなら採らない。**

**［2026-08-21］**「毎プルリクの精度は下がってもいいが、develop ブランチマージ時か日時実行に
するなどしてどこかで担保できる様にする。そのときに失敗したら自動で issue 起票する」。

**［2026-08-22］**「なるべく精度は落とさない方向で」。

後の裁定により、**「PR から外して後段へ移す」案はすべて取り下げた**（決定 4・5）。
残したのは**解析やテストの中身を 1 行も削らない手段**だけである。

| 手段 | PR の検出力 | 効き方 |
| --- | --- | --- |
| `concurrency` | **不変** | 古い実行を捨てる |
| NuGet・Playwright キャッシュ | **不変** | restore とブラウザ取得を効かせる |
| ジョブ統合（決定 6） | **不変**（検査器の本数と対象は同一） | ランナー起動と同時実行スロットの節約 |
| 工具の事前導入の出し分け（決定 3） | **不変**（要るときは入る） | docs だけの PR で払わない |

**自動起票（`ci-failure-issue.yml`）は残す。** 当初は「PR から外した分の担保」として入れたが、
外すのをやめた今も価値は消えない —— **日次（`integration.yml`）・週次（`codeql.yml` /
`security.yml`）の実行は誰も見ていない**ためである。落ちたまま何日も気付かれない形を塞ぐ。

### 決定 2: `integration.yml` は自動起票を持ち、**フィルタを付けずに全量で回す**

`IADR-0049` で統合テストは既に nightly 分離済みである。しかし**自動起票が無く、
落ちても誰も知らないまま赤が積み上がる形**だった。決定 1 で同じ構造の仕組みを作るのだから、
**同型の穴を 2 つ残さない**。あわせて `push: [develop]` を足し、マージ時にも回すようにした
（日次だけだと、朝までの間に別の PR が積み上がって原因の切り分けが難しくなる）。

**［2026-08-22 改定 3］🔴 `--filter "Category=Integration"` を外し、全テストを 1 回走らせる形にした。**

理由は**両側でフィルタすると穴ができる**ことである。`ci.yml` は `Category!=Integration` で除外、
`integration.yml` は `Category=Integration` で選択 —— この対では、新しい統合テストへ
`[Trait]` を付け忘れると**PR でも日次でもどちらでも走らない**。
フィルタを外せば、付け忘れたテストは `ci.yml` 側に残る（**fail-safe な方向に倒れる**）。

副次的に **fail-closed の門（0 件実行で落とす）が不要になった。**
🔴 **これは門を諦めたのではない。** 門は「フィルタに依存するなら併設する」ものであり、
**依存自体を無くしたということである。ここに `--filter` を戻すなら門も必ず戻すこと。**

### 決定 3: 🔴 `claude-code-review.yml` の工具導入を「docs だけなら省く」で出し分ける

前段の `git diff --name-only` の出力で、4 つのセットアップを `if:` 条件付きにする。

🔴 **［2026-08-22 改定］判定を逆向きに書き直した。**
当初は「`backend/` `frontend/` のパターンに当たったら入れる」（＝**当たらなければ省く**）だった。
利用者裁定「なるべく精度は落とさない方向で」に従い、
**「入れる」を既定にし、docs だけだと確かめられたときにだけ省く**形へ改めた。

**同じ「取りこぼし」でも倒れる先が違う。**
- 旧: パターン漏れ → **省いてしまう** → AI が「実行したが失敗した」と報告する
- 新: 許可リスト漏れ → **余計に入れる** → **遅くなるだけで、検証は落ちない**

省くのは変更ファイルが**すべて `.md` / `LICENSE` / `.gitignore` / `docs/` 配下の画像**である
場合に限る。1 つでもそれ以外があれば全部入れる。**差分を解決できなかった場合も入れる**（fail-safe）。

🔴 **`--allowedTools` と `.claude/settings.json` は触らない。** 3 系統一致の規約があり
`check-ai-workflow-config.js` が STRICT で見ている。変えるのは**事前導入の有無だけ**である。

🔴 取りこぼすと AI は「実行したが失敗した」と報告する。**原因が環境不備であることは本文から
判らないため、拒否されるより質が悪い**（#391 の教訓がそのまま当てはまる）。

### 決定 4: CodeQL は PR だけ `build-mode: none`。全量解析は push / 週次で回収する

**［2026-08-22 改定 2］**「PR だけ `none`」を一度取り下げた。
**［2026-08-22 改定 3］利用者裁定（ループ効率優先）により再び採る。**

```yaml
build-mode: ${{ github.event_name == 'pull_request' && 'none' || 'autobuild' }}
```

- **PR**: `none`。**生成コードが解析対象外になる。これが落とす精度である。**
- **push（develop / main）／週次 schedule**: `autobuild` で全量解析。**ここで回収する。**
  失敗は `report-failure` が自動起票する。

🔴 **同じ check 名で PR と後段の精度が違う。読み手が最も誤解しやすい点である**ため、
ワークフローのコメントにも明記した。本ワークフローは**必須チェックではない**ので、
PR で軽くしてもマージ判定は変わらない。

### 決定 5: `vulnerable-scan` は PR から外し、push / 週次で回収する

**［2026-08-22 改定 2］**一度 PR へ戻した。
**［2026-08-22 改定 3］利用者裁定（ループ効率優先）により再び外す。**

本ジョブが見るのは「**既存の**推移依存 × **後から公開された** advisory」であり、
PR の差分とは元来無関係である。全ソリューションの restore を伴うため PR ごとの費用が大きい。

**PR で見えなくなるもの**: その PR が新しく持ち込んだ依存に既知の advisory がある場合。
**ただしこれは `dependency-review`（PR の必須チェック）が捕まえる。**
本ジョブ固有の価値（既存依存への新規 advisory）は時間の経過で現れるため、
**push ＋ 週次 schedule で間に合う。** 失敗は `report-failure` が自動起票する。

### 決定 6: Node 検査ジョブは束ねるが、検査は 1 本も減らさない

15 ジョブを `static-checks` 1 つへ束ねる。
`commit-messages`（必須）・`scripts-tests`（子プロセスを多数回す重量級）は単独のまま残す。

🔴 **束ねる際、失敗の可読性を落としてはならない。** 単純に連続ステップへ並べると
**最初の失敗以降の検査が走らず**、1 回の CI で 1 件しか分からなくなって往復が増える。
各ステップへ `if: ${{ !cancelled() }}` を付け、落ちた検査が複数あれば一度に全部出るようにする。

🔴 **既存ジョブのコメントを 1 行も捨てない。** ADR 番号・事故の経緯・
「これを外すと検査が空回りする」という設計要点を持つ資産である。各ステップ直前へ移設する。

副次効果として、**統合前は 4 ジョブがそれぞれ 1147 個の `.cs` を個別に走査**していたのが 1 回になる。

### 決定 7: changelog 自動 PR では重いジョブを回さない

`automation/changelog-update-develop` の PR で CI が `action_required` のまま毎回起動していた。
`lint` / `build-and-test` / `frontend` / `frontend-e2e` へ
`if: !startsWith(github.head_ref, 'automation/')` を足す。

⚠️ **必須チェックのジョブへ `if:` を付けてよい根拠**: `if` でスキップされたジョブは
**必須チェック上「合格」として扱われる**（`docs/ai-workflow.md` に明記）。
`paths:` でワークフローごと起動しない場合と違い、恒久 pending にはならない。
**この 2 つは結果が正反対なので混同しないこと。**

### 決定 8: テストのアセンブリ間並列化は**試したが不採用**（2026-08-22）

🔴 **採らなかった案も、実測とともに残す。** 次に同じ案を検討する人が同じ実測を繰り返さないためである。

#### 何を試したか

`dotnet test` へ `-- RunConfiguration.MaxCpuCount=0` を渡し、アセンブリ間を並列化した。

#### 結果: **何も変わらなかった**

実 CI で前後を比較した（ベースライン run `32503346711` / 適用後 run `32510016809`）。

| | Test 壁時計 | アセンブリ所要の合計 | 実効並列度 | **最大同時実行数** | `Test Run Successful` |
| --- | --- | --- | --- | --- | --- |
| 変更前 | 147 秒 | 531 秒 | 3.61 本 | **4 本** | 51 |
| `MaxCpuCount=0` | 133 秒 | 480 秒 | 3.61 本 | **4 本** | 51 |

**最大同時実行数は前後とも 4 本**である（アセンブリ 51 本の完了時刻と所要から開始時刻を復元し、
任意時点の同時実行数を数えた）。147 → 133 秒の差は**アセンブリ所要の合計が 531 → 480 秒へ揺れた
run 間のばらつき**で説明が付く —— 実効並列度（合計 ÷ 壁時計）はどちらも **3.61 本で同一**である。

**テストは元から 4 並列で走っていた。** ランナーが 4 コアだからである。指定しても何も変わらない。

#### 🔴 着手時の診断が誤っていた

「ログの `Test Run Successful` が **2〜6 秒間隔で 51 回**並ぶ。並列なら同時刻に固まるはずだから直列である」
と読んだ。**この推論は無効である。**

**完了時刻の間隔は、アセンブリの所要時間を反映するだけで、並列度の証拠にならない。**
4 並列でも平均所要が 10 秒なら、完了は平均 2.5 秒間隔で並ぶ。実際、**変更前のログにも
「同一秒に 3 本完了」が 7 箇所あった** —— 直列ではあり得ない形が、最初から出ていた。

🔴 **並列度を見るなら、開始・終了の区間を復元して同時実行数を数えること。**
完了時刻の疎密で判断しない。

#### 残すもの

- **`ci.yml` には「試したが不採用」と、足し直さない理由をコメントで残した**
  （効かないと実測済みの行を、次の人が「効くはず」で足し直さないため）。
- **テスト時間の下限は最長アセンブリの 28 秒**である。これを下回るには
  **並列度そのものを上げる**しかなく、それは段 3-a（シャーディングでランナーを増やす）である。
  1 ランナー内の指定では届かない。

### 決定 9: 「逆転」を機械で監視する（`ci-latency-watch.yml`・2026-08-22）

決定 1 で「PR は速さを採る」と決めたが、**速さは一度縮めて終わりではない。**
必須チェックの最長は当面 `claude-review` であり、`build-and-test` がその下限を
**下回っている間、多少伸びても待ち時間は変わらない —— レビューの陰に隠れる。**
しかし**超えた瞬間から、増加は 1 秒残らず待ち時間になる。**
ビルド時間は機能追加とともに連続的に伸びるため、**いつ超えたか誰も気付かない。**
本 IADR が繰り返し扱ってきた「気付けない種類の劣化」であり、検知を機械に任せる。

- `scripts/check-ci-latency.js` が直近のマージ済み PR（既定 10 本）を GitHub API で引き、
  **`build-and-test` の中央値 > `claude-review` の最小値**なら exit 1 とする。
- **しきい値を固定値で持たない（自己校正）。** 基準側も同じ run 群から実測する。
  固定値は必ず腐る —— 本作業でも「キャッシュは初回必ずミスする」という固定の思い込みが
  実測で誤りだった。
- **監視対象は中央値、基準は最小値。この非対称は意図的である。** 対象を中央値にするのは
  ランナーの当たり外れ 1 本で鳴らさないため。基準を最小値にするのは、**密なループでは PR が
  小さくレビューが下限へ寄る**ため、守るべき相手が中央値ではなく下限だからである。
- **必須チェックにしない。** 週次 ＋ `workflow_dispatch` のみ。
  監視自体が PR の待ち時間を増やせば、監視対象の悪化になる。
- 失敗したら `ci-failure-issue.yml` を `marker_key: ci-latency` で呼び、
  統合テストの失敗とは**別スレッドの issue** へ集約する。

#### 🔴 実装で踏んだ罠 6 つ（いずれも監視を無言で無力化する／誤起票させる）

**① check-run 自身の所要で測ってはならない。**
基盤側（MSP）の `build-and-test` は matrix の脚を `needs:` で束ねる**集約ジョブ**であり、
その所要（`completed_at - started_at`）は **15 秒**しかない（実測・`MSP#894` の head）。
脚が動いていた 111 秒はそこに現れず、所要で測ると実際の 1/8 に見えて**監視は永久に鳴らない**。
待ち時間として意味を持つのは
**その head の check 群が動き出してからの完了オフセット（同 126 秒）**である。
本リポの `build-and-test` は現状 集約ジョブではないが、**同じ検査器を両リポで使う以上、
尺度は集約ジョブでも壊れない側に揃える。**

**② 中央値は「直近 N 本が同じ CI 構成で走った」と仮定している。**
CI を作り変えた直後はこの仮定が崩れる。実測（2026-08-22・MSP）では最適化直後のサンプル 12 本の
うち **11 本が最適化前**で、中央値 456 秒に対し現在の構成は 126 秒だった。
**そのまま鳴らせば、直したばかりの CI を「遅い」と起票する。**
監視が最初の 1 回で狼少年になれば、以後の本物も無視される。
そこで**監視対象の中央値が最小の 2 倍以上なら判定しない**（定常性の門）。
ランナーのばらつきは実測 1.2 倍程度に収まるため、2 倍は構成変更だけを拾う。
**代償: 窓の途中で実際にビルドが 2 倍に伸びた場合も 1 週遅れる**（窓が入れ替われば次回鳴る）。
速さの監視は fail-open という本 IADR の方針と同じ向きであり、
**見逃しより誤報のほうが監視を壊す**という判断で意図的にこちらへ倒している。

**③ `permissions` はスクリプトが叩く API のスコープと一致していなければならない。**
当初 `actions: read` だけを付けていた。**足りない。** GitHub の一次情報で確認した ——
`GET /repos/{repo}/commits/{sha}/check-runs` は **Checks（read）**、
`GET /repos/{repo}/pulls` は **Pull requests（read）**を要求し、
どちらも Actions のスコープではない（`actions: read` は workflow run / artifact 用）。
**この誤りは静かに壊れる** —— 403 で早期終了し、fail-open で緑を返し、
**監視は一度も働かないまま緑を返し続ける。**
そこで `permissions` を直したうえで、**401/403/404 だけは fail-open せず赤くする**
（5xx・ネットワーク断は従来どおり fail-open）。
🔴 **AI レビューが 2 リポジトリで独立に指摘した。** どちらも「一次情報で確認できていないので
要確認として報告する」と断ったうえで挙げており、**推測を断定として出さない報告の仕方が、
指摘そのものと同じくらい効いている**（こちらで一次情報を当たる判断ができた）。

**④ `sort=updated` の順は「マージされた順」ではない。**
マージ後にコメントが付くと `updated_at` が進むため、古い PR が新しい PR より前に来る。
`merged_at` で並べ直す（同じく AI レビューの指摘）。

**⑤ 403 はレート制限でも返る。** ステータスだけで権限誤りと断じると、**待てば直る失敗で誤起票する。**
`x-ratelimit-remaining: 0` / `retry-after` を見て一過性へ倒す。

**⑥ 404 の意味は文脈で変わる。** リポジトリ／PR 一覧の 404 はリポジトリ名の誤りかアクセス権なし
（＝設定の誤り）だが、**個別コミットの check-runs が 404 なのは「その 1 本が消えただけ」**である
（スカッシュ後に head ブランチが削除され dangling commit が GC された等）。
一緒くたにすると**1 本 GC されただけでバッチ全体が赤くなり誤起票する。**
コミット側の 404 は落として続け、走査本数の内訳として報告する。

**⑤⑥ も AI レビューの指摘である。** 自己試験は 32 → **39 件**。

#### 実測（2026-08-22・両方向を確認した）

| リポ | 結果 | 意味 |
| --- | --- | --- |
| **本リポ（AST）** | **exit 1 で鳴った**（中央値 223 秒 > 下限 146 秒） | 既に逆転しており、鳴るのが正しい挙動である。**決定 8 が不採用になったため逆転は解消していない** —— 解消するには段 3-a（シャーディング）が要る。この監視は鳴り続けることで、それを忘れさせない |
| MSP | 判定を **skip**（最小 126 秒 / 中央値 456 秒 = 3.6 倍） | 定常性の門が効いた。**緑だが「逆転していない」ではない**旨を出力に明記させている |

🔴 **片方向だけでは「常に鳴る／常に鳴らない」実装と区別できないため、両方向を実測した。**
判定ロジックには**自己試験 39 件**を付け、**上記の罠①〜⑥はいずれも回帰テストとして固定してある**
（ワークフローが毎回 `--self-test` を走らせる。**監視が黙って壊れるのは監視が無いより悪い**）。

#### 次の手（鳴ってから設計を始めないための分析。採否は未定）

| 手 | 効果の上限 | 主なリスク |
| --- | --- | --- |
| **a. テストのシャーディング** | 成長を N 分割へ分散。**N を上げれば伸ばせる唯一の構造的な手**。決定 8 の実測により、**1 ランナー内では既に 4 並列で頭打ち**（下限＝最長アセンブリ 28 秒）と分かったため、**残る手はランナーを増やすこれだけである** | ジョブ起動が N×約 13 秒。ビルドが各シャードで重複する |
| **b. backend 非変更 PR で backend ジョブを skip** | 該当 PR で build を丸ごと 0 に | 影響判定を誤ると**退行が無検証でマージされる**。許可リスト方式で保守的に |
| **c. ビルド成果物の再利用** | 上限 48 秒 | **壊れ方が静か**（古い成果物でテストが通る）。鍵の設計と無効化が難しい |

**推奨の順序は a → b → c。** c は費用対効果が最も悪いので最後に置く。

### 決定 10: テストを 3 シャードへ分割する（利用者裁定 2026-08-22）

決定 8 で **1 ランナー内は既に 4 並列で頭打ち**（テスト時間の下限＝最長アセンブリ 28 秒）と
実測した。**残る手はランナーを増やすことだけ**であり、利用者裁定により採る。

- **`scripts/list-test-projects.js`** がテストプロジェクトを**内容で**発見し
  （`Microsoft.NET.Test.Sdk` / `xunit` を参照する `.csproj`）、パスでソートして
  **ラウンドロビン**で分配する（51 本 → 17/17/17）。
  - 🔴 **命名（`*.Tests.csproj`）で発見しない。** 命名から外れたプロジェクトを取りこぼす。
    着手前に両方で引いて **51 件で一致**することを確かめたうえで、内容側へ寄せた。
  - 🔴 **連続した塊で切らない（`slice`）。** パス順に並ぶため、塊で切ると同じサービスの
    テストが 1 シャードへ固まり所要が偏る。ラウンドロビンなら重いものが自然に散る。
  - 🔴 **0 件は必ず失敗させる。**「テストが 1 本も無い状態で緑」を作らない。
  - 自己試験 9 件。**網羅性（各シャードの和 ＝ 全体）と排他性（重複なし）を固定してある。**
- **必須チェック名 `build-and-test` は集約ジョブが保持する**（脚は `backend-test (1..3)`）。
  改名は恒久的なマージ不能を招く（決定 2 と同じ理由）。
- 🔴 **シャード内は `xargs -P 4` で 4 並列を維持する。** 1 本ずつ直列に回すと
  現在の 4 並列を失い、シャード時間が 480/3 ＝ **160 秒**となって**分割前の 133 秒より遅くなる**。
- **カバレッジは各シャードが artifact へ上げ、集約ジョブが集めて床を強制する。**
  `check-coverage.js` は **(ファイル, 行番号) の和集合**で集計するため、
  シャード間でレポートが分かれても分母・分子は変わらない。
- 🔴 **各シャードで「レポート数 ＝ 担当プロジェクト数」を検査する。**
  1 テストプロジェクト = 1 レポートの不変条件で、**「走らなかった」と「二重に走った」を
  両方**捕まえる。第 1 弾で同じテストプロジェクトが 2 回走り、レポートが 30 件・
  カバレッジが 20% へ半減した事故の再発防止である。
- **集約ジョブでレポート 0 件なら失敗させる**（「何も測っていないのに緑」を作らない）。

**代償**: ビルド（43 秒）が各シャードで重複し、ジョブ起動が 3 回ぶん増える。
**待ち時間は減るが CI の総消費は増える。** シャード数 3 は暫定で、実測して再検討する。

#### ［2026-08-22 追記・実測］シャード数 3 → 5、xargs → シャード用 solution へ改めた

**最初の実装（3 シャード・`xargs -P 4` で 1 プロジェクトずつ）を実測したところ、
`build-and-test` は 208 秒 → 181 秒にしかならなかった**（目標は 146 秒未満）。
内訳（run `32515066798`）:

| | 実測 |
| --- | --- |
| `changes`（直列の前置き） | 14 秒（うち **setup-node が 6 秒**、判定は 0 秒） |
| シャード最長 | 149 秒 ＝ セットアップ 12 ／ Restore 15 ／ **Build 48** ／ **Test 69** ／ upload 4 |
| 集約ジョブ | 18 秒（うち setup-node 5 秒） |

**Test は 133 秒 → 44〜69 秒へ確かに縮んだ**（分割は効いた）。
しかし**固定費（約 80 秒）が各シャードで重複して支配的になった。**

🔴 **モデルと実測を突き合わせて原因を特定した。**
所要の合計 498 秒を 4 並列で詰めた理論値は 48 秒だが、実測は 69 秒だった。
差の 21 秒は **`dotnet test` の起動コスト**であり、
**1 回あたり約 4.9 秒 ×（17 本 ÷ 4 並列）**として較正できる。
51 本なら **約 250 秒**が起動コストだけで消えている計算になる。

そこで 2 つ直した。

1. **シャード用 solution（`.slnx`）を生成し、`dotnet test` を 1 回だけ叩く。**
   起動コストがシャードあたり 1 回になり、プロジェクト間の 4 並列は
   **MSBuild が従来どおり面倒を見る**（分割前と同じ経路に戻る）。
   `list-test-projects.js --slnx` が組み立て、XML の妥当性と件数保存を自己試験で固定した。
2. **`changes` と集約ジョブから `setup-node` を外した**（合計 11 秒）。
   どちらも依存を持たない素の Node スクリプトで、ランナー既定の Node で動く。
   **どちらもクリティカルパス上にある**（前置きと最後尾）ため、この 11 秒は待ち時間そのものである。

較正済みモデルによる見込み（**実測 181 秒に対しモデル 174 秒＝誤差 4%** で検算した）:

| シャード数 | 方式 | 見込み | ランナー |
| --- | --- | --- | --- |
| 3 | xargs（当初） | 170 秒 | 3 |
| 6 | xargs | 139 秒 | 6 |
| **5** | **solution 生成** | **139 秒** | **5** |

**同じ効果をより少ないランナーで得られる solution 方式を採る。**
起動コストという**無駄そのもの**を消す手であり、ランナーを増やして覆い隠す手ではない。

⚠️ **solution 方式は手元で検証できなかった**（この環境に dotnet が無い）。
壊れ方は loud（シャードが赤くなる）なので CI で確かめる。

### 決定 11: backend に影響しない変更だけの PR では backend ジョブを skip する（利用者裁定 2026-08-22）

- **`scripts/detect-changed-areas.js`** が変更ファイル一覧を読み、
  **安全と分かっているパスの許可リストに全件が収まるときだけ** `backend=false` を返す。
  `build-and-test`（集約）・`backend-test`（脚）・`lint` を `if:` で出し分ける。
- ⚠️ **`if` でスキップされたジョブは必須チェック上「合格」**として扱われる
  （`paths:` の恒久 pending とは結果が正反対。決定 7）。
- 🔴 **既定は「走らせる」。未知のパスは必ず `backend=true` へ倒す。**
  誤りの倒れ方が非対称だからである —— 余計に走らせる誤りは遅いだけで**気付ける**が、
  **走らせない誤りは退行を無検証でマージし、緑のまま誰も気付かない。**
- 🔴 **`.github/workflows/**` は許可リストに入れない。**
  CI 自身を変える PR で backend を skip すると、**その変更を検証できない**。
  本決定を導入した PR がまさにその形である（自己言及の罠として自己試験に固定した）。
- `backend/**` は `.cs` に限らず**丸ごと**走らせる（`.json` フィクスチャ・`appsettings` も
  テストが読む）。`Directory.*.props` / `global.json` / `deploy/**` も同様。
- 自己試験 23 件。**「走らせるべきときに走らせる」側を厚く固定してある。**

#### 🔴 必須チェックへ `needs:` を足すときは `always()` と Gate を必ず対で置く（AI レビューの指摘）

`lint` は**必須チェック**である。決定 11 で `needs: [changes]` を足したが、
`if:` に `always()` を置き忘れていた。

**GitHub Actions では、`needs` のジョブが失敗すると依存ジョブは `if:` を評価する前に skip される。**
そして本 IADR 自身が決定 7 で書いているとおり、**`if` でスキップされた必須チェックは「合格」**である。
つまり `changes` が落ちると、**`dotnet format --verify-no-changes` が一度も走らないまま
マージできてしまう。**

集約ジョブ（`build-and-test`）には `always()` ＋ Gate（`needs.changes.result != 'success'` なら失敗）
を置いていたのに、**同じ設計を `lint` にだけ適用し忘れていた。**
`lint` にも同じ Gate を置いた。

🔴 **規則として残す: 必須チェックのジョブへ `needs:` を足すときは、`always()` と
「上流が success でなければ失敗させる Gate」を必ず対で置く。**
片方だけだと、**上流の一過性障害が必須チェックの黙殺に化ける。**
⚠️ `backend-test`（脚）は必須チェックではないので、この対処は要らない。

#### 🔴 見積もりを 2 度誤った。実測で直した

**① 「C# を触らない PR は skip できる」は誤りだった。**
最初「直近 40 マージ中 28 本（70%）に効く」と見積もったが、**`.github/workflows/` を触る PR が
19 本**含まれていた。これらは上記のとおり**必ず走らせる**ので skip されない。
**「C# を触らない」と「backend を skip してよい」は同じではない。**

**② 計測スクリプト自身に誤りがあり、skip 率が 0% に見えた。**
判定器は `backend=false` と小文字で出すのに、`backend=False`（Python の bool 表記）で
引いていた。**「0% だから無意味」と結論しかけた。**

実測し直した結果（母集合 52 マージ）:

| 規則 | skip 率 |
| --- | --- |
| 本決定の規則 | 8 本（**15%**） |
| workflows を「backend ジョブを定義するものだけ」へ精緻化 | 10 本（19%） |
| ＋撤去済みディレクトリ（`feedback/` / `planning`）を除く | **18 本（34%）** ← 今後の見込み |

**精緻化は +4% のためにワークフローのファイル名リストを抱えることになるので採らない**
（リストは改名で腐り、腐ったときの倒れ方が「skip する」側＝危険な向きである）。

## 却下した案

### 却下 A: CodeQL を PR から丸ごと外す

PR 時点で SAST の指摘が一切出なくなる。**`paths:` を持つため PR で起動しない回もあり、
「出ないこと」と「起動していないこと」が読み分けられない。**

**［2026-08-22 改定 3］同節にあった「PR だけ `build-mode: none`」は却下から外し、決定 4 として採った。**
生成コードが解析対象外になる点は変わらないが、**push / 週次で回収でき、回収先の失敗は自動起票される**ため、
利用者裁定（ループ効率優先）の下では許容できる精度低下である。**「丸ごと外す」だけが却下として残る。**

### 却下 B: `claude-code-review` のセットアップを丸ごと消し、AI に必要時インストールさせる

`--allowedTools` に `dotnet tool install` 等を足す必要があり、**3 系統一致の規約**
（ワークフロー 2 本 ＋ `.claude/settings.json`）を広げることになる。
ツールの許可面を速度のために広げるのは筋が違う。**事前導入の有無だけを変える。**

### 却下 C: 自動起票を後追いの別 PR にする

「PR から外す変更」と「後段で担保する仕組み」を別 PR に割ると、
**その間だけ担保が無い窓ができる**。決定 1 の趣旨に反するため同じ PR に入れる。

### 却下 D: ワークフローレベルの `paths:` で PR の実行を絞る

`paths:` を持つワークフローは対象外の PR で **report されず恒久 pending** になるため
必須チェックに指定できない（`docs/ai-workflow.md` の既存ルール）。
出し分けは**ジョブ条件 `if:`** で実装する（決定 3・7）。

## 影響

- **PR の待ち時間は縮む。** 一方で **develop へのマージ時と日次/週次はむしろ重くなる**
  （全量 CodeQL・vulnerable-scan・統合テストがそちらへ寄るため）。**それが狙いである** ——
  誰も待っていない場所へ重い検証を移す。
- **`develop` / `main` への push は `cancel-in-progress` の対象にしない。**
  担保がそこに載るため、途中でキャンセルしてはならない。
- 新しい依存として `actions/cache` / `actions/github-script` が加わる。
  `scripts/action-versions.json` の `expected` へ同時に追加した
  （片方だけ直すと `check-action-versions.js` が CI で落ちる）。

## 残余リスク

- 🔴 **自動起票は「動かないことに誰も気付かない」種類の仕組みである。**
  失敗したときにしか走らないため、平時は常に skip で緑になる。
  `integration.yml` の `workflow_dispatch` 入力 `force_failure` で**実際に 2 回走らせて**
  ① issue が立つ ② 2 本目が立たずコメントが足される を実測すること。
  実測しないまま「起票を入れた」と言わない。

  ✅ **［2026-08-21 実測・マージ後］期待どおり動いた。**
  1 回目で issue #541 が立ち、2 回目は**新しい issue が立たずコメントだけが足された**。
  新規ラベル `ci-failure` も自動作成され、**ラベル欠落で起票が失敗することはなかった**。
  MSP 側（`MSP#895`）でも同じ手順で同じ結果を確認しており、**2 リポジトリで配線が揃っている**。
  検証で立てた issue は記録を本文へ残したうえでクローズした。
  ⚠️ **`workflow_dispatch` を API から叩くと 403**（既定トークンは `metadata=read` のみ）。
  **Web UI（Actions タブ → Run workflow）から実行するのが確実である。**
  「403 が出た＝自動起票が壊れている」ではないので取り違えないこと。
- 🔴 **決定 3 の許可リストの漏れ。** 改定後は漏れても「余計に入れる」に倒れるため
  **検証は落ちない**（遅くなるだけ）。それでも
  **docs のみの PR と backend を触る PR の両方を実測するまで完了としない。**
- **統合テストは AST では従来どおり PR から外れている**（`IADR-0049`）。
  **［2026-08-22 改定 3］MSP も同じ形へ揃えたため、2 リポジトリの方針は一致した。**
- 🔴 **`integration.yml` から fail-closed の門を外した**（改定 3 でフィルタを外したため不要になった）。
  **門とフィルタはセットである。** 将来ここへ `--filter` を戻すなら、
  **門（1 件も実行されなければ落とす）も必ず一緒に戻すこと。**
  `dotnet test` はフィルタに 1 件も一致しなくても exit 0 で終わるため、
  門が無いと「0 件実行のまま緑」で通り続ける。
  参考: 門の判定に使っていた正規表現は実測で妥当だった —— 日次 run `32403939224` のログに対し
  **8 行に一致**（`Passed <テスト名> [24 s]` 形式の per-test 行。本リポジトリは xUnit v3 で
  MSP の v2 とランナーが違うため別に測った）。
  *注: GitHub の保存ログは行頭に時刻を付けるため、追試するときは時刻を落としてから照合すること
  （付いたままだと `^` が効かず 0 件に見える）。*
- 🔴 **CodeQL は PR と後段で精度が違う**（決定 4）。**同じ check 名なので最も誤解されやすい。**
  PR の Security タブのアラートが 0 件になっていたら「速くなった」ではなく
  **「何も解析していない」**を疑うこと。
- 🔴 **`vulnerable-scan` を PR から外した**（決定 5）。回収は push ＋ 週次である。
  **回収先が赤いまま放置されると「外した」が「やめた」になる。** 自動起票がその防波堤であり、
  上の 1 点目（起票そのものの実測）がまだ済んでいない。
