# IADR-0597: 閉じかぎで閉じて `"` が欠けた構造化出力を狭く補修する（#1332）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: **Accepted**
- 日付: 2026-10-29
- 決定者: 実装（Claude Code）。#1332 の PoC の追記（2026-10-29）と、オーケストレーターの指示（2 形で試験を固定して進める）への判断。

## 起点・関連

- 起票: [#1332](https://github.com/endazon/ai-stock-trading/issues/1332)。PoC 10/26〜28 の稼働で、一次スクリーニングの解析不能が 2 件あった（10/26 14:55:47 UTC NVDA Buy、10/27 19:08:20 UTC HOOD Sell）。どちらも rationale の文字列を `」` で閉じ、JSON の `"` が無いまま終わる `UnterminatedString`。HOOD は打ち切りで決済が 6 分遅れた。
- 前提（覆さない）: IADR-0248（解析不能は Hold）、IADR-0531 決定 1・2（原本の抜粋と指紋）・決定 4（再試行しない）。
- 改める: IADR-0531 決定 3 の「閉じない文字列の補修（D 向け）: どこで閉じるべきかを推測するしかない」を、本 IADR の 2 形に限って改める。決定 3 の他の項目（2 個目以降の `{` からの再走査・全角括弧の読み替え）は変えない。
- 仕様書: `.ai-context/specs/20261029_1332_kagikakko-closed-string-repair.md`

## コンテキスト

- 日本語の根拠文は「…」の引用をよく含む。モデルが文字列の終わりを `」` で閉じたと取り違えると、JSON の閉じの `"` が落ちる。抽出の走査は末尾まで文字列の内側に留まり、`NoJsonObject`（指紋は `UnterminatedString`）になる。
- IADR-0531 決定 3 が補修を退けた理由は「閉じる位置を推測するしかない」ことだった。しかし `」` の直後に JSON の構造（`,"action":` のような既知のキーと `:`、または閉じ括弧 `}`）が続く形では、閉じる位置が構造から一意に決まる。推測ではない。
- 🔴 実物の原本では形を確かめていない。オーケストレーターは抜粋を取得できず、PoC 実施側へ依頼した。実装はオーケストレーターが示した 2 形で試験を固定する。原本が届いたら照合する。

## 決定

### 決定 1: 補修の条件（すべて満たすときだけ）

1. 抽出が失敗し、最初の `{` からの走査が末尾で文字列の内側に終わった（`UnterminatedString`）。正しく閉じた出力・他の候補（`NoBrace` / `FullWidthBraces` / `UnclosedBrace`）には掛からない。
2. 文字列の内側の `」` の直後（空白を除く）が、次のどちらかである。
   - 形 1（`BeforeKnownKey`）: `,` → `"` → 既知のキー → `"` → `:`。既知のキーは出力形式の項目名だけ（`action` / `rationale` / `referencePrice` / `stopLossDistancePerShare` / `expectedProfitPerShare` / `entryCondition` / `entryReferencePrice`）。
   - 形 2（`BeforeClosingBrace`）: `}`。
3. その `」` の直後に `"` を補い、文字列の外へ出たとみなして走査を続ける。1 出力あたり最大 3 か所。
4. 補った結果から JSON を抽出できたときだけ採る。抽出できなければ補わなかったことにし、従来どおり `NoJsonObject` になる。補修の後も JSON 構文・action・数値（参照価格・損切り幅）の検査は従来どおり掛かる。

補修しないもの（否定形の試験で固定）:

- 素の `"` の混入（`監視銘"柄`）。閉じる位置が構造から決まらない。
- `」` の後が未知のキー（`"price"` など）。出力形式の外の項目へ閉じる根拠が無い。
- `」` の後に構造が続かない。
- `」` の後の `,` に `"` が続かない（引用符の無いキーなど）。
- 正しい JSON の中の `」`。抽出が成功するので補修の経路へ入らない。

### 決定 2: 一次・二次の両方に掛ける（パーサは共有のまま）

- 補修はパーサの共通の前段（`ReadEnvelope`）に置く。一次（打ち切りの判断）と二次（発注へ進む本判断）の両方に掛かる。
- 二次にも掛ける理由:
  - 二次で解析不能になると Hold 票になり、保有中の決済が遅れる。これは一次と同じ損失の形である。
  - 補修で開く経路は「同じ JSON の中の、`」` までの根拠文を閉じる」だけである。IADR-0531 決定 3 が恐れた「別の JSON を拾う」経路（2 個目の `{` からの再走査）は開かない。action と数値は補修の前後で同じ位置から読まれる。
  - 二次は多数決で、補修した 1 票だけでは向きが決まらない。補修の後も数値の検査（IADR-0248 の InvalidValues）が掛かる。
- Stage0 の記録は同じパーサで読み直す（決定的）ため、本番と記録が食い違わない。

### 決定 3: 補修した事実と形だけを WRN 1 行で残す（本文は書かない）

- `DecisionOrchestrator` が、一次・二次それぞれで補修したときに WRN 1 行を出す。
  - 目印: `構造化出力の閉じの引用符を補って読みました`
  - 値: `layer=screening|decision`、`shape=BeforeKnownKey|BeforeClosingBrace`（両方を補えば両方）。
- 応答の本文は書かない。補修した出力は解析できているので、IADR-0531 の原本の行（解析不能のときだけ）も出ない。根拠文は従来どおり判断の記録に入る。
- 補修の件数は出力の形の退行の信号として監査で数える。増えたら、プロンプトの出力形式の指示を見直す材料にする。

## 結果

- 良い点: 10/26・10/27 の 2 件の形は一次で読めるようになり、関心ありなら二次へ進む（HOOD のような決済の遅れを避ける）。補修した事実は WRN で数えられる。
- 悪い点: 構造化出力の取り違えを黙って直すため、補修の WRN を見ないと形の退行に気付かない。
- 残余リスク:
  - 根拠文の中に `」,"action":` のような JSON の構造そのものを書き、その後に正しく閉じない出力は、根拠文の途中で閉じて読む。そのとき action は根拠文の中の値を読む。日本語の根拠文に出力形式のキーを JSON の構文で書くことは考えにくく、補修の WRN で数えられる。
  - 形 2 も同じ形で残る: 根拠文の途中に `」}` があり、その後に正しく閉じない出力が続くと、そこで閉じて読む。action は先頭の値を読み、数値の検査も掛かるので、向きは変わらない。補修の WRN で数えられる。
  - 実物の原本で形を確かめていない。原本が届いて形が違えば、その形を試験へ足し、条件を見直す（別 PR）。

## 外す条件

- 外さない。ただし原本の照合で、2 件の形が本 IADR の 2 形のどちらでもなかったときは、条件を見直す IADR を起こす。
