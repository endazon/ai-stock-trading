# IADR-0381: 期間で切った在庫のまま持ち、期間前の建玉の決済は「算定できない」と明示する

## コンテキストと課題

報告書の在庫は**その期間の約定だけ**から畳まれる（期間の切り出しは権威源側の `PeriodFillQuery`）。
したがって**期間より前に建てた建玉は報告書の在庫に存在しない**。それを当期に決済すると、
`SignedInventory.Apply` が「在庫 0 への売り」を**新規建て**として畳み、平均取得単価＝決済価格の
**幻のショート**が開いていた。

#892 の実測（取り込みが 1 件も無くても再現する）:

```
PnlAggregator.Aggregate([Sell(100 株 @250)], 前提条件, 現在値 { AAPL: 300 })
→ unrealized=-5000 realized=0 realizing=0
```

前期に建てた 100 株を当期に 250 で決済しただけである。真値は「当期の在庫は残っていない」＝評価損益 0。

🔴 **[IADR-0360](IADR-0360_manual-trade-origin-and-report-drift-adoption-section.md) 決定 4 のクランプでは直せない。**
取り込みは「在庫を減らすだけ」の操作で建てる正当な用途が無いが、**約定は建てる操作でもある**
——「在庫 0 の売り」を一律に無視すると、当期に始めた**正当な新規ショート**まで消える。

## 決定

### 決定 1: 在庫の規約は「期間で切ったまま ＋ 算定できないことの明示」を採る

issue が挙げた 3 方向のうち**方向 2**（期間外の建玉に依存する値を「不明」にする）を採り、
方向 1（期間開始時点の在庫を供給する）・方向 3（期間を建玉の生涯で切る）は**採らない**。

- 方向 1 は**供給元が存在しない**。リスク管理の `ProjectOpenPositions` は**現在**の台帳全体を畳む口であり、
  **過去時点の射影**を返す口が無い。新設はサービス境界と台帳のスナップショット方式に触れ、報告書に閉じない。
- 方向 3 は計画の粒度定義（04_report-templates）に触れる。
- 方向 2 は**本サービスが全節で守っている規律**（未供給と 0 を区別する・推定で埋めない）と同じ形であり、
  実装側だけで閉じる。issue が認める副作用（「日報の評価損益が頻繁に未供給になる」）は**受容する**。

🔴 **幻の数字より「算出不能」のほうが読み手を誤らせない。** 報告書は発注判断を行わないため、
欠測が過大発注へ繋がる経路が無い。**誤った数字が方針の素になる経路のほうが重い。**

### 決定 2: 見分けるのは `PositionEffect`（新しい入力を増やさない）

issue が検出器の案として挙げた「在庫 0 への反対売買」は、**当期に始めた正当な新規ショートを巻き添えにする**。
代わりに**台帳が既に持っている軸** `PeriodTradeFill.PositionEffect` を使う。

`PositionEffect` は `PositionEffectResolver` が**判断時点の実保有数量**から解決し
（`signedHeldQuantity > 0 && Sell` ⇒ `Close`、`signedHeldQuantity < 0 && Buy` ⇒ `Close`、それ以外は `Open`）、
台帳 `LedgerFill.PositionEffect` へ記録され、`GET /risk-controls/fills` から `HttpPeriodFillSource` まで
**素通しで届く**。報告書の型（`PeriodTradeFill`）は以前から本列を運んでいたが、集計では未使用だった。

規則（`PeriodInventory` が単一情報源）:

| 約定 | 期間の在庫 | 扱い |
| --- | --- | --- |
| `Open` | 何であれ | 従来どおり `SignedInventory.Apply`（**正当な新規建て・建て増しはここに来る**） |
| `Close` | 賄える | 従来どおり `SignedInventory.Apply` |
| `Close` | 賄えない（0・同方向・不足） | 賄える分だけ決済し、**賄えない分は建てない（クランプ）**。実現損益は算定しない |

賄えない数量を `PeriodInventoryFill.UnvaluedQuantity` として返す。🔴 **呼び出し側は黙って捨ててはならない。**

🔴 **`Close` が期間の在庫を超える分は「反転」ではない。** 手仕舞いの数量は保有数（全量）から決まり
ゼロを跨ぐ分割は起きない（IADR-0038 / `PositionEffectResolver`）。是正前はここで `SignedInventory.Apply` の
反転分岐が働き、余りを**新しいショート建玉**にしていた（旧テスト
`反転_ロングからショート_は決済分の実現損益と残ショートの評価損益を扱う` が固定していた挙動）。
**この挙動は意図して変えた**——報告書の在庫が足りないのは期間で切られているからであって、反転したからではない。

### 決定 3: 規則は 1 か所に置き、5 つの畳み込みすべてを通す

報告書サービスで在庫を畳む箇所は 5 つあり、**すべて同じ順序・同じ規則でなければ内訳の合計が §1 とずれる**
（IADR-0301 の明文。ずれても各集計は自分の中では整合するため全テストは緑のままになる）。

`PnlAggregator` / `FillPnlAttributionBuilder` / `TradeHistoryViewBuilder` / `ReportDraftService`
（現在値を取りに行く銘柄の決定）/ `FxTranslationBuilder`（自前の同型分岐）を `PeriodInventory` へ寄せた。
**報告書サービスの本番コードから `SignedInventory.Apply` の素の呼び出しは消えた**（`PeriodInventory` の内側だけ）。

方向別の内訳（`PeriodBreakdownBuilder.IsLong`）も追随させた。素朴に「`!Realizing` なら建て」と読むと、
期間より前に建てたロングの手仕舞い（Sell）が**ショートの新規建て**として月報 §2 に載る
——在庫から消した幻が内訳の行に残る。`Unvalued` は `Realizing` と同じ側（決済）へ数える。

### 決定 4: 部分値は数字として出さず、既存の語彙で「算出不能」と描く

`UnvaluedSettlementCount > 0` の期間は、実現損益・源泉徴収税額・勝率・評価損益が**部分値**である。

- **§1 サマリ**（日報・週報・月報）: 該当セルを `**算出不能**（期間より前に建てた建玉の決済が N 件あり、
  その取得原価が当期間の約定に含まれていません）。**0 ではありません。**` にする。
  **取引回数・費用合計は事実なので出す**（費用は約定ごとに掛かり取得原価を要しない）。
- **日報 §2 の明細**: 当該行の実現損益を `**不明**` にする（§2-b と**同じ語**。`0` と書かない）。
- **週報 §2/§3/§5・月報 §2/§5**: 算入しなかった件数を明記する行を足す（§5 の
  「発注先が記録されていない約定」と**同じ作法**）。週報 §5 の費用率は分母が部分値になるため算出不能にする。
- **Discord の提示要約**: 実現損益と決済・勝ち件数を「算出不能」にする（要約だけを見て確定する利用者がいる）。

🔴 **新しい語彙を増やさない。** `算出不能`（計算できない・既存は費用率の分母 0）と
`不明`（計算できない・行単位。§2-b）と `未供給`（記録源が無い）の 3 語はすでに区別されている。

### 決定 5: 欠けている入力は `ReportInput.OpeningInventory` として記録する

`ReportInput`（IADR-0352 決定 5 の閉じた語彙）へ **`OpeningInventory`（期間開始時点の在庫）** を足し、
全種別に適用する。これで既存経路（`reports.UnsuppliedInputs` への記録・Discord 提示通知の Warning・
`/report show`・版番号なしの `/report approve` の警告）へ**そのまま乗る**。

🔴 **取りに行かない・見送らない。** 供給元が存在しないため HTTP は出さず、**期間より前に建てた建玉の決済を
実際に検出した回だけ**未供給に入れる。追加位置はドラフト生成の後であり、見送り判定（`TryDefer`）はその前に
終わっている——**待っても供給されない入力で報告書を遅らせない。**

## 影響・残余リスク

- **日報の実現損益・評価損益は、建玉を持ち越した日に「算出不能」になる。** これは受容した副作用である
  （issue の明文）。是正前は同じ状況で**幻のショートの評価損益**という誤った数字が出ていた。
- **計画（04_report-templates）の数値定義に触れ得る。** §1 の数値が「算出不能」になり得ることは
  テンプレートの読み方に関わるため、**planning への `decision-needed` 起票が要る**（本 PR では起票していない。
  実装は計画に反しない側＝数字を騙らない側へ倒している）。
- **`PositionEffect` の正しさに依存する。** 台帳の列が誤っていれば見分けも誤る。ただし本列は
  リスク統制（エントリー専用の統制を `Open` にだけ当てる。IADR-0004）が既に依存している軸であり、
  本 ADR が新たな依存を増やしたわけではない。列が欠けた古い行は JSON 既定で `Open`（＝従来どおり畳む）になり、
  **是正前の挙動へ倒れる**（安全側ではないが、新たな誤りは作らない）。
- **三者比較（月報 §5）は勝率・平均損益を部分値のまま出し、件数を注記する**に留めた。列そのものを
  「該当なし」へ倒すと「その段をまだ走らせていない」と読まれ、既存の宣言が嘘になるためである。
- **テスト ID** は `T-16-001`〜`T-16-015` を新設した（走査の結果、本リポジトリに `T-16` 帯は 1 件も
  存在しなかった。`docs/tests/` に FR-16 のテスト仕様書は無い＝網羅裁定 #211 の必須範囲外のため、
  採番の記録は本 ADR と作業仕様書が持つ）。
