# OpenD 認証操作画面

> moomoo OpenD がログイン時に要求する検証コード（SMS / 画像 CAPTCHA）を画面から入力し、
> ゲートウェイを稼働状態へ戻すための運用操作画面である。**取引の設定変更・統制操作は行わない。**
> データ源は BFF `/bff/opend-auth/*` → OpenD 常駐 Pod 内の認証サイドカー（#722）。

## 画面の位置づけ

platform SPA 認証済みレイアウト配下に feature `sc04-opend-auth` としてマウント
（route `opend-auth`・nav「OpenD 認証」）。

**なぜ画面が要るか**: ブローカー選定の計画 ADR（前提条件 1）と OpenD 無人再起動の計画 ADR（決定 2）は
「**初回のデバイス信頼の確立は有人である**」と定めるが、**その有人操作をどこで行うかが計画に無かった**。
現行の唯一の手段は `kubectl attach` であり、**運用者の手元に kubeconfig と CLI を要する**。
利用者裁定により画面の 1 つとして提供する。

**いつ要るか**: (1) 初回のデバイス信頼の確立、(2) 無人再起動の計画 ADR 決定 1 の 2 条件
（**デバイス信頼の永続化**・**egress IP の安定**）が崩れた場合の再認証。
🔴 **2 条件がそろう環境では再起動をまたいで無人で再ログインできるため、本画面は常用するものではない。**
画面の存在を「毎回の手作業が要る」と読み替えないこと。

**本画面はゲートウェイの認証であり、取引の破壊的統制操作ではない。** したがって
「破壊的統制操作は Discord Bot へ一元化する」対象では**ない** ——
画像 CAPTCHA の提示がテキスト対話で成立しないためである。逆に、取引の統制操作
（昇格承認・一時停止/再開・緊急停止）は本画面に置かない。

## アクセス制御

- 利用者（`trading-owner`）限定。`RequireRole anyOf=['trading-owner']`・権限外は `NotFound`（存在秘匿）。
- 🔴 **権限外では認証 API を呼ばない**（存在を推測させない）。
- **実効認可は BFF が持つ。** 既存 3 画面は後段のドメインサービス（`OwnerOnly`）へ認可を委譲するが、
  本画面の上流（OpenD 認証サイドカー）は**設計上まったく認証を持たない**ため、
  **BFF が唯一の認可点である**。権限外は **404**（403 ではない）で、**上流を 1 度も呼ばない**。

## 構成要素

内蔵 `paper` 稼働時の警告バナーを画面上部に常時表示する（必須 2 文言）。
🔴 **モックアップ本体には描かれていない**（共通要素は別画面のモックアップで代表して示される慣行）。
**見た目だけを頼りにすると実装を落とす。** 内蔵 `paper` の稼働中は OpenD を経由しないため
認証操作そのものが不要であり、バナーが無いと「認証できないから発注できない」と誤読される。

1. **ゲートウェイの状態（参照）**: 接続状態・**待機中のプロンプト種別**（SMS / 画像 / 無し）・
   最終ログイン成功日時・**デバイス信頼の永続化**・**egress IP の安定性**・現在の発注先。
   発注先は参照のみで、**変更はリスク設定画面が持つ**。
2. **検証コードの入力（本画面の主操作）**: 入力欄 1 つと送信・再送のみ。
   🔴 **利用者はコマンドを選べない** —— 送信するコマンドは**サーバ側が待機中のプロンプト種別から決める**
   （画面はコマンド名を持たない）。**自由入力のコンソールを置かない。**
   画像 CAPTCHA 待ちのときは OpenD が返した画像を提示する。
3. **この画面から送れる操作（許可リスト）**: 利用者への**情報**として表で示す。
   🔴 **表は統制ではない。** 実際に強制するのはサーバ側であり、この表はそれを見せているだけである。
4. **送信履歴**: 記録の粒度は監査ログが担保するが、**本画面が読む照会 API は未実装である**。
   したがって**供給が無い**として描く（後述）。

## 送信できるコマンドの限定（安全上の制約）

OpenD のコンソールは検証コード以外のコマンドも受け付ける。したがって**画面から送れるものを 3 つに限る**。

| コマンド | 目的 | 画面から | 条件 |
| --- | --- | --- | --- |
| `input_phone_verify_code` | SMS 検証コードの入力 | 許可 | 待機中プロンプトが SMS のときだけ |
| `input_pic_verify_code` | 画像 CAPTCHA の入力 | 許可 | 待機中プロンプトが画像のときだけ |
| `req_phone_verify_code` | SMS の再送要求 | 許可 | レート制限（**暫定 60 秒に 1 回。算定根拠が無く実測待ち**） |
| `relogin -login_pwd=` ／ `exit` ／ `close_api_conn` ／ `set_log_level` | 再ログイン・終了・接続切断・ログ水準変更 | **送れない** | 統制の外からゲートウェイを止められてしまう |
| `show_delay_report -detail_report_path=` ／ `show_sub_info -sub_info_path=` | レポート出力（任意パス指定） | **送れない** | 🔴 **root 権限で任意パスへ書ける** —— デバイス信頼の実体や `OpenD.xml` を潰せる |

- **許可リストはサーバ側（BFF）で強制する。** 統制を画面に紐づけて書くと、実装は画面の外側に穴を残す。
- 🔴 **上表は「現時点で確認できたコマンドの一覧」ではなく「送ってよいコマンドの一覧」である。**
  未知のコマンドが増えても既定は拒否である（**許可リスト方式であり、拒否リスト方式ではない**）。
- **画面から受ける本文はコードだけで、コマンド種別を受け取る欄が型として存在しない。**
  待機中でなければサーバが `409` を返し、**上流へ 1 バイトも送らない**
  （画面の無効化だけに頼らない）。

## 検証コードの取り扱い

🔴 **コードそのものは記録しない。** 監査ログ・画面の送信履歴・Discord 通知・サーバログ・応答の
いずれにも値を残さず、**送信した事実・日時・アクター・コマンド種別・結果**だけを記録する。

これは**認証情報の秘匿に関する非機能要件の適用範囲を広げた扱い**である。同要件は証券口座・API
認証情報の**保管**を定めており、一時的な検証コードを監査ログ・画面の履歴へ残さないことを直接には
定めていない。保管される長期の資格情報ではないが、**それ 1 つでゲートウェイのログインが通る値**である
以上、同じ扱いにする。

塞いだ漏洩経路は次のとおりで、いずれにも回帰テストがある。

| 経路 | 塞ぎ方 |
| --- | --- |
| サーバログ | 要求本文をログへ出さない |
| 例外メッセージ | **握り潰した例外のメッセージも出さない**（JSON 解析例外のメッセージには本文の断片が入る） |
| 応答本文 | 上流の応答本文を**捨て**、理由の符号（`not_waiting` / `rejected` / `gateway_unavailable`）だけを返す |
| 失敗表示 | 画面が入力値を反射しない（「483921 は誤りです」と描かない） |
| 画面の入力欄 | 送信の直後に消す（成否にかかわらず） |
| クエリキャッシュ | クエリキーへ入れない（投入の引数としてだけ通す） |

## 供給が無い値の表示規約（3 状態を取り違えない）

全画面共通の表示規約を本画面にも適用する。**供給可否はサーバが宣言し、画面は従う。**

| 状態 | 意味 | 表示 |
| --- | --- | --- |
| **値がある**（`Available`) | SMS / 画像の入力を待っている | プロンプト種別を表示し、入力欄を**有効**にする |
| **対象なし**（`NotApplicable`) | ログイン済みで入力待ちではない（**正常**） | 「いま OpenD は入力を待っていません」。入力欄は**無効** |
| **供給が無い**（`NotSupplied`) | 状態を取得できていない | **「取得できていません（供給元がありません）」**。入力欄は**無効** |

🔴 **「いま入力を待っていない」と「状態を取得できていない」を描き分ける。**
前者はログイン済みで正常、後者はゲートウェイへ到達できていない。
**取り違えると「正常にログインできている」ように見える** —— これが本画面で最も高くつく誤りである。

- 🔴 **判らないものはすべて未供給へ倒す。** サーバが「待機中」と言いながらプロンプト種別を返せない
  場合も未供給である（**安全側は「取れていない」であって「対象なし」ではない**）。
- **「—」は対象なし専用の記号である。** 未供給は必ず文言で述べる。
- **正当な値を未供給へ倒さない**（逆方向の否定形。「値の有無から供給可否を推測しない」は両方向に効く）。

### 表示項目ごとの供給元

| 表示項目 | 供給元 | 現況 |
| --- | --- | --- |
| 接続状態・待機中のプロンプト種別・最終ログイン成功日時 | OpenD の標準出力を認証サイドカーが解釈し、サーバ側が宣言する | 🟡 **条件付き。** 標準入力の FIFO 化は実装済み（#722）。**状態を宣言する照会 API は並行実装中** |
| デバイス信頼の永続化・egress IP の安定性 | **配備構成**（PVC・固定 NAT） | ✅ 構成から静的に決まる。**上流へ到達できなくても供給され得る**（未設定なら未供給） |
| 送信履歴 | 監査ログ | 🔴 **供給が無い。** 記録の粒度は担保されるが、**本画面が読む照会 API が無い**。「送信履歴はありません」と描くと**一度も送信していない**という別の事実になる |
| 現在の発注先 | RiskManagementService | ✅ 供給あり（実装済み） |

## データ取得（BFF `/bff/*` 経由・`apiFetch`）

| 操作 | 呼び出し | 応答/エラー |
| --- | --- | --- |
| ゲートウェイの状態 | `GET /opend-auth/state` | 供給可否を宣言する view。**未構成・上流不達でも 200** で未供給を宣言する（画面が 3 状態を描き分けるため、宣言そのものが要る）。取得自体の失敗（BFF 未登録＝404 等）はその領域のみ縮退 |
| 画像 CAPTCHA | `GET /opend-auth/captcha` | `image/png`。不在・未構成・不達は 404 |
| 検証コードの投入 | `POST /opend-auth/code` | 本文は**コードだけ**。204 / 400（受理せず）/ 409（待機中でない）/ 503（未構成・不達） |
| SMS の再送 | `POST /opend-auth/resend` | **本文なし**。204 / 409（レート制限等）/ 503 |

上流（認証サイドカー）の基底 URL は構成 `OpendAuth:BaseUrl` に置く。
🔴 **既定は空であり、空は「未構成 → 供給が無い」を意味する**（fail-safe）。

## 振る舞い（安全既定）

- **取引の統制操作の UI を持たない**（統制の入口は Discord Bot）。
- 待機中でないときは入力欄と送信を無効にする。**ただしこれは画面の親切さにすぎず、サーバ側でも拒否する。**
- 検証コードは待機中のプロンプト種別が示す形式で検証する（SMS は 6 桁の数字。画像は桁数・文字種が
  定まらないため空でないことだけを見る）。
- 取得失敗・BFF 未登録・権限外は安全側（縮退・存在秘匿）へ倒す。
- ゲートウェイの状態と発注先は独立に縮退する（一方の取得失敗が他方を巻き込まない）。

## 待ち・失敗・空の表示と再試行（2026-09-12）

取得結果の**待ち・失敗・空・本体**を 1 か所（共通部品 `QueryPhase`）で描き分ける。画面ごとの
手書き分岐は撤去した。

- **判定順は 失敗 → 待ち → 空 → 本体**である。**失敗を先に見るのは、0 件と失敗を混同しないため**
  である。空の判定は**成功した応答に対してだけ**行う。
- **失敗の告知には再試行ボタンを伴わせる。** 押すと同じ取得をやり直す（`refetch`）。
- 🔴 **404 では再試行ボタンを出さない。** 取得先が BFF に登録されていない場合の 404 は
  **再試行しても直らない**。この判定は画面側が持ち、共通部品へ渡す。
- 🔴 **状態の取得が失敗している間は、検証コードの入力欄と送信を無効にする。**
  入力欄を開けてよいのは**状態を読めているときだけ**である —— 取得の失敗を
  「いま入力を待っていない」に見せてはならない（前節の 3 状態の取り違えと同じ誤りである）。
- ゲートウェイの状態の取得と発注先の取得は**独立に縮退する**。
- **送信（投入・再送）の失敗は本節の対象外である。** 400・409・503 は従来どおり結果通知として出し、
  **破壊的な自動再試行をしない**。再試行ボタンは**取得の失敗にだけ**付く。
- **0 件・対象なし・供給が無いの描き分けは従来どおりである。** 本節は**取得そのものの状態**を
  扱うものであり、前節「供給が無い値の表示規約」を置き換えない。

## 計画書との差異

| 差異 | 理由 |
| --- | --- |
| ルートを `/trading/opend-auth` ではなく **`/opend-auth`**（ユニット相対）とした | 既存 3 画面も同じ形である（計画 `/trading/settings` → 実装 `/settings` 等）。`/trading` は基盤 SPA がユニットを載せる位置であり、ユニット側の宣言に含めると二重になる。**本画面だけ別の形にすると 4 画面の合成が壊れる** |
| 送信履歴を表示せず「供給が無い」と描く | 計画の供給元の表が「照会 API は未実装」と明記している。**4 端点の外に口を増やさない**（口が増えるほど攻撃面が増える） |

## スコープ外（後続）

- **認証サイドカー本体**（並行実装中・#722）。本画面は BFF から上流として呼ぶだけである。
- **platform 合成点（features / BFF）への登録**。別リポジトリの所有物であり本リポジトリから行えない。
  🔴 登録が漏れている間、画面は 404 を受け取り**供給が無い**として描く（安全側だが、
  **画面だけが存在する**状態にはなる）。
- **送信履歴の照会 API**（監査ログへの照会経路）。
- **Playwright E2E**（既存 3 画面と同じ枠組みで別途）。
- **再送間隔の実測**（暫定 60 秒は算定根拠が無い。OpenD 側の制限と SMS の到達所要を実測して置き換える）。

## 残存リスク

🔴 **本統制は本画面と裏側 API の配備後に働く。** 配備までの唯一の経路である `kubectl attach` には及ばず、
禁止した 6 コマンドを送れる状態が**配備までそのまま残る**。
**「統制を定めた」と「統制が働いている」は別である。**
配備までの暫定手段は、`kubectl attach` の実行権限を運用者に限ることである
（クラスタの認可に依存し、本画面の許可リストとは別の統制である）。
