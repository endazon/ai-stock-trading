# 運用 Runbook: 日足 K 線の取得枠の検証口

> 運用仕様書（[`operations.md`](operations.md)）の下位にあたる手順書である。
> 同じ作法の検証口に [注文費用照会の検証口 Runbook](order-fee-probe-runbook.md) がある。
> 発注経路（`moomoo-sim`）の見分け方は [発注経路の区別と識別 Runbook](broker-execution-paths-runbook.md) を参照。

判断へ出来高（前日の出来高と、その 20 日平均に対する比）を渡すには、日足 K 線を使う。その前に、次の 2 つを実機の OpenD で確かめる必要がある。

1. **取得枠（`remainQuota`）の単位と回復周期。** 銘柄の数で減るのか、要求の回数で減るのか。いつ戻るのか。
2. **株式分割をまたいでも 20 日平均比が歪まないか。** 前復権が価格だけでなく出来高も調整するのか。

order-execution のイメージには、この 2 つを確かめるための**検証口**が同梱されている。検証口は相場の読み取り要求を**1 回ずつだけ**撃ち、結果を標準出力へ出して終わる。

- **読み取り専用**である。検証口が使えるのは、取得枠の照会と日足 K 線の取得だけである。発注・訂正・取消・口座の照会へ届く経路を持たない（発注の接続を作らず、口座も選ばない）。
- **各要求は 1 回だけ**撃つ。失敗しても撃ち直さない。
- 要求の間隔を **2.5 秒以上**あける（1 分に 24 回まで）。
- 判断へ出来高を流すことはしない（出来高は「未提供」と明示したまま）。

## この手順を実行する条件（いつ走らせるか）

- 判断へ出来高を流す実装に入る前に、取得枠の単位を確かめたいとき（1 回目）。
- 回復周期を確かめるとき。1 回目から日を置いて、2 回目以降を打つ（下の「回復周期の判定」）。
- 分割のあった別の銘柄・期間で、出来高の調整を確かめ直したいとき。

## 前提

| 項目 | 内容 |
| --- | --- |
| 必要な権限 | 名前空間 `ai-stock-trading` の Pod への `kubectl exec` |
| 必要なツール | `kubectl` |
| 対象 | **order-execution の Pod**（`deploy/order-execution-service`）。OpenD の接続先と RSA 鍵は、この Pod にだけ入っている。**OpenD の Pod には触れない**（exec・再起動・ログインのいずれもしない） |
| 構成 | 階層が `moomoo-sim` であること（[発注経路の区別と識別 Runbook](broker-execution-paths-runbook.md) の introspection で確かめる）。paper 階層では接続せずに終わる |
| 取得枠の消費 | 既定の 1 回で、**最大 3 銘柄ぶん**（AAPL・MSFT・NVDA）。枠は稼働中のサービス（バックテストの履歴源など）と共有である |
| 所要時間の目安 | 1 分（要求 12 回 × 2.5 秒） |

## 手順

1. **検証口を 1 回だけ実行する。** 稼働中の order-execution の Pod の中で、同じイメージの `dotnet` を別プロセスとして起動する（稼働中のサービスは止めない）:

   ```bash
   kubectl -n ai-stock-trading exec deploy/order-execution-service -c order-execution-service -- \
     sh -c 'exec dotnet "$SERVICE_DLL" --probe-kline-quota'
   echo "exit=$?"
   ```

   既定は、直近の日足を AAPL・MSFT で 25 本ずつ、分割の比較を NVDA の 2024-05-28〜2024-06-21（2024-06-10 に 10:1 の分割）で取る。
   変えるときは、旗の後ろにオプションを足す:

   ```bash
   kubectl -n ai-stock-trading exec deploy/order-execution-service -c order-execution-service -- \
     sh -c 'exec dotnet "$SERVICE_DLL" --probe-kline-quota --symbols AAPL,TSLA --count 25 --split-symbol AAPL --split-from 2020-08-17 --split-to 2020-09-11'
   ```

   | オプション | 意味 | 制約 |
   | --- | --- | --- |
   | `--symbols` | 直近の日足を取る銘柄（カンマ区切り） | 米国株のコード 1〜5 つ（`US.` の接頭辞は可）。重複不可 |
   | `--count` | 直近の本数 | 1〜100 |
   | `--split-symbol` / `--split-from` / `--split-to` | 分割の比較に使う銘柄と期間 | 3 つそろえて指定。日付は `yyyy-MM-dd`。from ≦ to・120 日以内・to は今日以前 |

   上以外の引数・値の欠け・重複は、使い方の誤りとして接続せずに終わる。

2. **出力を記録する**（「記録」の節）。**続けて打たない。** 撃ち直すときも 1 分以上あける。

## 出力の読み方

1 行 1 事実の `key=value` で出る。出力は次の節に分かれる（`section=` の行が区切り）。

| 節 | 内容 |
| --- | --- |
| `section=quota-before` | 取る前の取得枠（`quota[0]`）。`used=`（使った数）・`remain=`（残り）と、詳細一覧（`quota[0].detail[j]`: 銘柄・名称・要求時刻） |
| `section=recent-daily` | 銘柄ごとの前復権の日足（`kline[k]`）。`kline[k].bar[j]` の行が 1 本（`time` / `open` / `high` / `low` / `close` / `volume`（出来高）/ `turnover`（売買代金）） |
| `section=split-compare` | 分割の銘柄を無復権・前復権・後復権で取った結果。`split.row` が日付ごとの並び、`split.<区分>.vsNone` が無復権との比較 |
| `section=quota-final` | 取り終えた後の取得枠（詳細つき） |
| `section=quota-summary` | 取得ごとの枠の差（`quota.step[i]`）と、単位の読み（`quota.unit.reading=`） |

各取得（`kline[k]`）の直後に、枠を照会した行（`quota[n] label=after-kline[k]`）が続く。`delta.used=` が、その 1 回の取得で `used` がいくつ動いたかである。

`kline[k]` の行の `hasMore=yes` は、応答に続きがあったことを示す（検証口は続きを取らない）。`blank=` は、値の無い日を埋めた空白足の数である（空白足は出さない）。

| `result=` | 終了コード | 読み方 |
| --- | --- | --- |
| `ok` | 0 | すべての要求が成功した（`retType=0`） |
| `partial` | 1 | いずれかの要求が非成功だった（その行の `retMsg=` が理由）。他の段は最後まで撃っている |
| `error` | 1 | 接続失敗・返信待ちのタイムアウト等（`error[n].type` / `error[n].message`）。**以後の要求は撃っていない** |
| `usage-error` / `config-error` | 2 | 引数の誤り／構成が moomoo の SIMULATE 階層でない・RSA 鍵が無い等。**接続していない** |

出力は、構成で与えた接続先（host:port と host）と RSA 鍵のパスを `<伏せ>` に置き換えている。エラー文では、6 桁以上の数字の並びも末尾 2 桁以外を伏せている。口座番号はそもそも扱わない。

## 取得枠の単位の判定

`section=quota-summary` の行で読む。

- `quota.step[i]` は取得 1 回ぶんで、`known=` はその銘柄が**取る前から枠の詳細一覧に在った、またはこの実行で既に取った**かを示す。
- **未知の銘柄の取得は、単位が銘柄でも要求でも `+1` になる。区別は既知の銘柄の取得で行う。** 分割の比較は同じ銘柄を 3 回取るため、既定の 1 回で既知の取得が 2 回以上ある。

| `quota.unit.reading=` | 既知の銘柄の取得の差 | 意味 |
| --- | --- | --- |
| `per-security` | すべて `0` | **銘柄の数で減る。** 同じ銘柄を何度取っても枠は減らない |
| `per-request` | すべて `+1` | **要求の回数で減る。** 同じ銘柄でも取るたびに減る |
| `inconclusive` | それ以外（混在・差が 2 以上・既知の取得が無い・前後の照会が失敗） | 判定できない。行をそのまま記録する |

判断に要る取得（監視銘柄と保有銘柄の数 × 1 日の取得回数）が枠に収まるかは、この結果から見積もる。
`per-security` なら「期間内に取る銘柄の数」、`per-request` なら「期間内の要求の回数」を枠（`used + remain`）と比べる。

## 回復周期の判定

1 回の実行では分からない。**日を置いて打ち直し**、詳細一覧（`quota[0].detail[j]`）の変化から読む。

1. 1 回目の `section=quota-final` の詳細一覧（銘柄と `requestTime=`）と `used=` を記録する。
2. 1 日後・7 日後など、日を置いて 2 回目以降を打つ。**同じ銘柄だけを取る**と、枠の新たな消費を増やさずに済む（例: `--symbols AAPL` と、1 回目と同じ分割の銘柄と期間）。
3. `quota[0]`（取る前）の `used=` が 1 回目の `quota-final` より減っていれば、枠が戻っている。**詳細一覧から消えた銘柄の、1 回目の `requestTime=` から今日までの日数**が回復周期の手掛かりになる。
   消えた銘柄が無ければ、周期はまだ来ていない。

- `requestTime=` の時刻帯（OpenD の表示の時刻帯か UTC か）は確かめていない。`requestTimeStamp=`（UNIX 秒）と照らし合わせて記録する。
- 詳細一覧は、稼働中のサービスが取った銘柄も含む。

## 分割の歪みの判定

`section=split-compare` の行で読む。`split.row` は日付ごとに `none.*`（無復権）・`forward.*`（前復権）・`backward.*`（後復権）の終値と出来高を並べる。
`split.<区分>.vsNone` は、無復権と比べて終値・出来高が異なる日数（`closeDiffers=` / `volumeDiffers=`）と比の範囲である。

- `closeRatio.noneOverRehab` = 無復権の終値 ÷ その区分の終値。分割の前の日で分割比（10:1 なら 10）、後の日で 1 になる。
- `volumeRatio.rehabOverNone` = その区分の出来高 ÷ 無復権の出来高。

| 前復権（`split.forward.vsNone`）の見え方 | 読み方 | 20 日平均比への帰結 |
| --- | --- | --- |
| `closeDiffers` が分割前の日数ぶんあり、`volumeDiffers` も同じ日数で `volumeRatio` の上端が分割比 | **出来高も調整される** | 前復権の足で 20 日平均比を計算すれば、分割をまたいでも歪まない |
| `closeDiffers` はあるが `volumeDiffers=0`（`volumeRatio` が `1..1`） | **出来高は調整されない** | 分割の前後の足で出来高の桁が違う（10:1 なら前の日は約 1/10）。**20 日の窓が分割をまたぐと比が大きく歪む。**分割の前後の足を揃える必要がある |
| それ以外 | 判定できない | 行をそのまま記録する |

- 終値の比が 1 に近い小さな違い（配当の調整）は、分割とは別である。分割は、比が分割比にそろって跳ぶことで見分ける。
- 無復権の `split.row` で、分割の日の前後に出来高が分割比ほど跳んでいることも確かめる（期間が分割をまたいでいることの確認）。
- 後復権（`backward`）の要求が非成功（`retType≠0`）でも、無復権と前復権の比較で判定できる。

## 失敗したときの分岐

| 症状 | 原因の候補 | 次の手 |
| --- | --- | --- |
| `config-error`（moomoo の SIMULATE 階層の Pod でだけ動く） | 対象の Pod が paper 階層 | 階層を確かめる。paper では OpenD の接続先が入っていない |
| `config-error`（RSA 秘密鍵のファイルが無い） | 鍵のマウント漏れ | サービス本体も同じ理由で起動できないはずである。配備を確かめる（本手順では直さない） |
| `error`（OpenD への接続を確立できない） | OpenD が停止中・再ログイン待ち | **OpenD の Pod には触れない。** サービス本体のログで OpenD の状態を確かめ、復旧後に 1 回だけ打ち直す |
| `error`（TimeoutException） | OpenD が応答しない・頻度制限に掛かった可能性 | 1 分以上あけて 1 回だけ打ち直す。続けて失敗するなら打つのをやめて記録する |
| `kline[k].retMsg=` に権限の文言（No permission 等） | 市況の権限 | 記録する。米国株の日足が取れなければ、判断へ出来高を流す前提が崩れる |
| コマンドが戻らない | SDK の接続が閉じない | 3 分待っても戻らなければ Ctrl-C で抜ける（検証口は全体を 3 分で打ち切る） |

## 頻度制限への注意

- 検証口 1 回で送るのは、**枠の照会 7 回と日足の取得 5 回の合わせて 12 回**（既定）である。銘柄を N 個にすると `2 + 2N + 6` 回になる。
- 要求の間隔は 2.5 秒以上あけている。**検証口を続けて打たない。**
- 検証口は稼働中のサービスとは別に、OpenD へ相場の接続を 1 本張る（実行中だけ。終われば閉じる）。

## 記録

- 出力（標準出力の全行）と終了コードを、判断へ出来高を流す作業の issue（または検証口の issue）へ貼る。回復周期を見るときは、打った日時と各回の出力を並べて貼る。
- 出力は接続先・鍵のパスを伏せており、鍵の内容・口座番号を含まない（貼る前に念のため目視で確かめる）。

## 限界（この手順で担保できないこと）

- 取得枠の単位と回復周期の**答えそのもの**は、利用者が打った結果による（検証口は観測を出すまで）。
- 後復権が米国株で使えるかは確かめていない（非成功なら `partial` で分かる）。
- 前復権と費用モデル（借株料・配当相当額）の整合は、この手順の対象外である（バックテストの費用の問題であり、判断へ渡す出来高の条件ではない）。
- OpenD の相場の要求の頻度制限の実値は確かめていない（上の「2.5 秒以上」「続けて打たない」は安全側の目安である）。
