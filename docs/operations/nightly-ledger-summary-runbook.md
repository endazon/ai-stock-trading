# 運用 Runbook: 夜間の台帳の要約

> 運用仕様書（[`operations.md`](operations.md)）の下位にあたる手順書である。
>
> 🔴 **ログとメトリクスは、Pod の再起動で消える。** 稼働クラスタには Loki も Prometheus も無く、
> OpenTelemetry Collector の出力先は debug だけである。そのため、夜間の振り返りは**監査台帳（`audit_svc` の
> `audit_events`）を正とする**。台帳は追記専用で、再起動しても消えない。
> 例外は 13（当月の LLM 費用と月次上限に対する使用率）だけで、費用統制の台帳（`cost_control_svc`）と設定サービスの前提条件（`configuration_svc`）を読む。
> 上限の判定と同じカウンタと同じ上限の値を読むためである（上限の値はスクリプトに書かない。利用者が上限を変えると食い違う）。

## この手順を実行する条件（いつ走らせるか）

- 米国市場の引け（夏時間 05:00 JST、冬時間 06:00 JST）の後、その夜の振り返りをするとき。
- 夜間に Pod の再起動・PC のスリープ・配備があり、ログが途切れたとき。
- 「夜間に何件判断し、何件発注し、何件約定し、S1 が発動したか」を答える必要があるとき。

## 前提

- 🔴 **実行するのは利用者（人）である。** 稼働中の DB の Pod へ `kubectl exec` で入って読むため、AI エージェントの自動実行では
  稼働環境への操作として止められる（実績あり）。エージェントは実行を代行せず、利用者が実行して出力を渡す。
  エージェントは渡された出力を読んで振り返りをまとめる。
- 稼働クラスタへ `kubectl` が届くこと。
- `AST_PSQL` の利用者が `audit_svc`・`cost_control_svc`・`configuration_svc` の 3 つの DB を読めること（スクリプトが `-d` で切り替える）。
- 🔴 **読み取りだけ**を行う。SQL は読み取り専用のトランザクションの中で走り、最後に取り消して終わる。
  書き込み・スキーマの変更・一時オブジェクトの作成はしない。

## 手順

1. 夜の窓を決めて、要約を出す。

   ```bash
   # その日 20:00 JST 〜 翌日 08:00 JST（米国市場の夜を夏冬とも覆う）
   AST_PSQL="kubectl -n platform-infra exec -i deploy/postgres -- psql -U ai" \
     bash scripts/nightly-ledger-summary.sh --night 2026-09-29

   # 窓を明示する（時差つきの ISO 8601。窓は [from, to) の半開区間）
   AST_PSQL="kubectl -n platform-infra exec -i deploy/postgres -- psql -U ai" \
     bash scripts/nightly-ledger-summary.sh 2026-09-29T22:30+09:00 2026-09-30T05:00+09:00
   ```

   時差の無い時刻（例 `2026-09-29T22:30`）は受け付けない。端末と DB の時刻帯の違いで、窓が黙ってずれるためである。

2. 出力を振り返りの記録へ貼る（時刻はすべて JST で出る）。

## 出力の読み方

| 節 | 何が分かるか | 読み方の注意 |
| --- | --- | --- |
| 1. 種類別の件数 | 窓の中の、台帳のイベントの種類ごとの件数 | ここで 0 件の種類は、その夜に起きていない（か、台帳に届いていない） |
| 2. 判断（発注意図あり） | 買い／売り × 新規／決済の件数と銘柄 | 発注意図の無い判断（Hold）はここに出ない（3 を見る） |
| 3. 判断後の見送り | 見送りの理由別の件数（`LlmHold`＝LLM が見送りと判断した、など） | LLM を呼んだ**後**の見送りだけである。呼ぶ**前**の見送りは 11 を見る |
| 4. モデル利用不能による見送り | モデルが使えず判断を見送った件数 | — |
| 5. 審査 | 承認の件数と、拒否の理由別の件数 | 1 件の拒否が複数の理由を持つので、理由の件数の合計は拒否の件数より多くなり得る。🔴 保有 0・未約定なしで新規建てが必ず拒否される銘柄（損切りした当日・保有建玉数の上限・kill switch など）は、判断が LLM を呼ぶ前に見送るため、ここではなく 11 の `EntryBlockedByRiskControls` に出る（審査は変わらない。前後の夜を比べるときは 5 と 11 を足して読む） |
| 6. 発注前の見送り | 承認後に発注しなかった理由（`BrokerPositionsIndeterminate` など） | `BrokerPositionsIndeterminate` は、発注の直前に建玉を照会できなかったことを示す |
| 7. 注文 | 注文ごとの**最新**の状態の件数と一覧（約定数量・平均価格・銘柄・出どころ） | 同じ注文の記録は複数行になり得るので、最新の 1 行で数えている。出どころは `decision`（取引判断）・`S1`（ソフトウェア逆指値の決済）・`approved`（判断を経ない注文。利用者の手仕舞い・維持証拠金の自動縮小・照合後の保護レグ）・`?`（どれでも引けない）。銘柄は窓の外の記録からも引く。窓の前に発注して窓の中で部分約定した注文は、途中の記録の時刻が発注時刻のままのため、窓に入らないことがある |
| 8. S1 | 武装・損切りライン到達・発動の結果（`ClosePlaced` / `CloseRejected` / `CloseStalled` など） | 到達したのに `ClosePlaced` が無ければ、決済が出ていない |
| 9. ブローカの観測の欠け | 建玉の観測（10 分ごと）と稼働の観測（5 分ごと）が途切れた時間帯 | **照会できなかった時間帯の推定**である。Pod が止まっていた時間も欠けとして出る。照会の失敗の実測は 10 を見る（9 は 10 の記録が始まる前の夜と、Pod の停止を読み分けるために残す）。しきい値は `NIGHTLY_POSITIONS_GAP`（既定 20 分）と `NIGHTLY_AVAILABILITY_GAP`（既定 10 分）で変えられる。窓の両端も境界として数えるので、窓を夜より広く取ると、両端に長い欠けが出る。窓の途中（場中など）で走らせると、終端を現在時刻で切り、その旨の注意を 1 行出す（まだ来ていない時間を欠けとして出さない） |
| 10. 照会の失敗の区間 | 建玉照会・保有照会が失敗していた区間（発生源別）と、その終わり方・失敗の種類 | **実測**である。照会の成功⇄失敗が変わったときだけ記録されるので、区間は「失敗の記録 → 同じ発生源の次の記録」で読む。終わり方は `回復（失敗 N 回）`・`再起動の後に成功（回復の時刻は不明）`（Pod の再起動で状態が消え、再起動の後の最初の成功で閉じた）・`再起動の後も失敗`・`窓の終端まで続いた（回復の記録なし）` の 4 通り。`窓の前から` は窓の頭より前に始まった失敗である。発生源は下の表 |
| 10a. 状態の変化の件数 | 発生源 × 変化（前→後）の件数 | `Unknown→` の行は、そのサービスが起動した後の最初の観測である（再起動の回数の目安になる。照会しなかった発生源は出ない） |
| 11. LLM を呼ぶ前の見送り | 理由 × 起点（`scheduled`＝定時・`price-movement`＝価格変動）ごとの件数と銘柄 | 理由は `DailyPolicyUnconfirmed`（確定済みの日報が無い）・`CurrentPriceUnavailable`（現在値が取れない・古い）・`FxRateUnresolved`（為替が決まらない）・`FxRateStaleNoHolding`（為替が古く保有も無い）・`EntryBlockedByRiskControls`（新規建てが審査で必ず拒否される。5 の拒否から移った分）・`EntryCapacityBelowMinimumNotional`（新規建てに使える金額の上限が最小の名目額〔equity の 1%〕に届かない）・`EntryCapacityBelowOneShare`（段階残枠と日次残枠の小さい方が現在値の 1 株に届かない。従来は判断後の見送りの数量 0〔`SizingZeroQuantity`〕に出ていた分）の 7 つ。1 回の見送りにつき 1 件なので、日報が未確定のまま夜が過ぎると「銘柄数 × 巡回数」になる |
| 12. LLM の費用 | 窓の中の LLM の費用（円）を、用途 × モデル別の件数と金額で出す。最後の行（`合計`）が窓の合計 | 台帳の `LlmCostIncurred` の金額である。月次上限の対象かどうかは用途で決まり（取引判断が対象。報告書の生成・情報収集・方針の改訂は対象外）、その判別は費用統制が行う。用途が `(不明)` の行は古い形の記録で、上限の対象に数えられている |
| 13. 当月の LLM 費用と月次上限に対する使用率 | 当月の上限の対象の累計（`llm_governed_jpy`）・月次上限（`llm_limit_jpy`）・使用率（`usage`）・対象外の累計（`llm_uncapped_jpy`） | 月は費用統制と同じ **UTC の暦月**で、窓の終端（窓の途中で走らせたら現在時刻）の月である。累計はその月の頭から窓の終端までに計上された分。上限は設定サービスの前提条件の現在値で、読めなければ使用率は `不明（上限を読めない）` と出し、理由を標準エラーへ 1 行出して続ける。上限が 0 以下なら費用統制は統制しない（`上限 0 以下（費用統制は統制しない）`）。費用統制は使用率 80% で定時サイクルの間隔を延ばし、100% で取引判断を止める |
| 14. 取引判断の最中の例外 | 起点（`scheduled`＝定時・`price-movement`＝価格変動）× 例外の型名ごとの件数と銘柄 | **再試行の後の最終の失敗だけ**の件数である（定時は銘柄ごとの失敗、価格変動は再試行〔2 秒・10 秒・30 秒〕を使い切った失敗。途中の再試行は数えない）。台帳には型名しか無く、メッセージとスタックは無い（秘密情報を含み得るため）。中身はログを見る。価格変動の失敗はメッセージの退避先（`<キュー>_error`）にも残る。出力は 12 の後・13 の前に出る（13 だけ別の DB を読むため）。0 行が平常 |

10 の発生源:

| 発生源 | どの照会か | 失敗すると何が起きるか |
| --- | --- | --- |
| `ProtectiveStopGuard` | 保護逆指値ガードの巡回（30 秒ごと）の先頭の建玉照会。有効な保護記録が無い巡回では照会しない | その巡回の保護の判定を全件据え置く。失敗の種類（`Transient`・`RateLimited`・`Other`）が出る |
| `BrokerPositionSnapshot` | 建玉の定期観測（10 分ごと） | 9 の建玉の観測が欠ける |
| `BrokerAvailabilityProbe` | 稼働の定期観測（5 分ごと。moomoo では建玉照会） | 9 の稼働の観測が欠ける（段階ゲートの稼働の数えに入らない）。内蔵のペーパー構成でも probe は動くので、発注執行の起動ごとに 10a へ `Unknown→Healthy` が 1 行出る（照会の失敗ではない。起動の回数の目安として読む） |
| `SoftwareStopClose` | 損切りライン到達を受けたソフトウェア逆指値（S1）の決済の建玉照会 | S1 の決済を据え置く |
| `OrderDispatch` | 決済の発注前の突き合わせ・S1 の武装前の確かめ | 6 の `BrokerPositionsIndeterminate`（決済）・`UnattributedPosition`（S1 の新規建て）の見送りになる |
| `TradeDecisionHoldings` | 取引判断の保有照会（リスク管理の台帳） | 判断の入力の保有が「不明」になり、新規建てを見送る（3 の `HoldingsUnknownOpen`） |
| `TradeDecisionWorkingEntries` | 取引判断の未約定の新規建て注文の照会 | 同上（3 の `WorkingEntriesUnknownOpen`） |

## 台帳に無いもの（この手順では分からないこと）

- 判断の途中の例外の**本文**（メッセージ・スタック）と、**途中の再試行**の失敗（14 は最終の失敗の型名だけを数える。本文はログ、価格変動のメッセージそのものは退避先に残る）。14 の記録を出すようになる前の夜は 14 が 0 行になる。
- 10・11 の記録を出すようになる前の夜の、照会の失敗と LLM を呼ぶ前の見送り（その夜は 10・11 が 0 行になる。照会の失敗は 9 の欠けから推定する）。
- 照会の失敗の**1 回ごとの時刻**（10 は状態が変わった時刻と、回復までの失敗の回数だけを持つ）。
- 市場監視（損切りラインの判定）と報告書の保有照会の失敗（10 の発生源に入っていない）。

## 失敗したときの分岐

| 症状 | 原因の候補 | 次の手 |
| --- | --- | --- |
| `ERROR: 時刻は時差つきの ISO 8601 で与えてください` | 時差の無い時刻を与えた | `+09:00` か `Z` を付ける |
| `psql: error: connection …` / `deploy/postgres` が見つからない | クラスタに届かない・名前空間が違う | `kubectl -n platform-infra get deploy postgres` で確かめる |
| `relation "audit_events" does not exist` | 接続先の DB が `audit_svc` でない | `AST_PSQL` に `-d` を入れていないか確かめる（スクリプトが `-d audit_svc` を付ける） |
| `WARN: 月次 LLM 費用上限を設定サービス（configuration_svc の assumptions）から読めないため…` | 設定サービスの DB に届かない・前提条件の行がまだ無い（設定サービスが一度も前提条件を返していない） | 1〜12 と 13 の累計はそのまま読める。上限は画面（全体前提条件）で確かめる。DB に届かないなら `AST_PSQL` の利用者の権限を確かめる |
| `relation "cost_entries" does not exist` / 13 だけ接続に失敗する | 費用統制の DB（`cost_control_svc`）に届かない | 1〜12 は先に出ている。終了コードは 0 以外になる。`AST_PSQL` の利用者が `cost_control_svc` を読めるかを確かめる |
| 全部の節が 0 件 | 窓が違う（日付の取り違え）か、監査サービスが止まっていて台帳に届いていない | 窓を広げて 1 の件数を見る。届いていなければ監査サービスの状態を確かめる |

## 記録

- 振り返りの記録には、実行した窓（from / to）と出力をそのまま残す。
