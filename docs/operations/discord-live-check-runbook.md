# 運用 Runbook: Discord Bot の実機確認（利用者が打つコマンドと期待する応答）

> 運用仕様書（`docs/operations/`）の下位にあたる手順書である。
> 再測定手順の正本は [`docs/blocked-tasks.md`](../blocked-tasks.md) A-7a であり、本書はそれを**利用者が 1 回の窓で打つ順番**に並べ直したものである。
> **Discord での操作は利用者本人が行う**（AI は Bot を経由せずに本番の owner 操作を代行しない）。確認のうちログで見る部分は AI が引き取れる。

## この手順を実行する条件（いつ走らせるか）

- Bot の実機確認が未了のあいだ（受け入れ基準のうち、実 Discord での操作が要るもの）。
- Bot のコマンド・補完・確認ボタンに手を入れた変更を配備した後。

## 前提

| 項目 | 内容 |
| --- | --- |
| 必要な権限 | 許可リストに載った利用者本人の Discord アカウント。陰性試験には**許可リストに無い第 2 のアカウント** |
| 場所 | 通知用サーバーの通知チャンネル（Bot のコマンドはこのサーバーにだけ登録されている） |
| 所要時間の目安 | 手順 1〜5 で 15 分。手順 6 は第 2 アカウントが用意できた窓で |
| 触る統制 | 手順 3 は**報告書を確定する**（確定した方針が以後の判断に使われる）。手順 4・5 は対象が無ければ何も変えない |

### AI が読み取りのみで確かめたこと（2026-09-26）

| 項目 | 結果 |
| --- | --- |
| Gateway 接続 | notification-service の起動時に `Connecting` → `Connected` → `Ready`。途中の再接続要求にも `Resumed previous session` で復帰している |
| スラッシュコマンドの登録 | `スラッシュコマンドを登録しました（guild=…）` が出ている。登録されるのは `killswitch` `gfv` `drift` `report` `pause` `resume` `status` `stage` の 8 つ |
| Webhook による投稿 | 報告書の確定イベントを受けて `HTTP 応答: 204 POST https://discord.com/***` が出ている（送信先は秘匿されている） |
| 気になった点 | 起動時に `A Ready handler is blocking the gateway task` の警告が 1 回出る（Ready の処理でコマンド 8 件を順に登録しており約 20 秒かかる）。接続は成立しているので、本書の確認は妨げない |

## 手順

各手順の「記録すること」を、終わったら対応する issue に書く（下の「記録」）。

| # | 打つもの | 期待する応答 | 記録すること |
| --- | --- | --- | --- |
| 1 | `/status` | 稼働状態（統制・段階・当日損益・上限使用率・ポジション）が表示される。口座を照会できていないあいだは日次発注の上限が**「不明（口座を照会できていません）」**と出る（**0 と出たら不合格**）。照会できていれば `日次発注 {発注額}/{上限} 円` | 表示されたか。「稼働状態の照会に失敗しました（JsonException）」が**出ない**こと |
| 2 | `/report` を選び、`action` に `show`、`period` の欄に `daily-` まで打つ | 会話キーの候補（新しい順・最大 25 件。例 `daily-2026-09-25`）が出る。さらに打つと絞り込まれる。候補を選んで送ると `報告書 <キー>: 版 <N>` が返る | **候補が出たか・出なかったか**（出ないときは 3 秒ほど待って出るかも）。出なければ「入力補完の応答に失敗しました」の有無 |
| 3 | `/report` `action:approve` `period:<確定したい報告書>` → 出てきた**確認ボタンを素早く 2 回押す**（ダブルクリック） | 1 回目の押下で `報告書 <キー>（版 <N>）を確定しました。` が返り、**ボタンは無効化される**（以後は押せない）。2 回目の押下が無効化より先に届いた場合は `報告書 <キー>（版 <N>）は確定済みです。` が返る（窓口の版番号ガードが確定 API を呼ばずに吸収する）。どちらの場合も**通知チャンネルに届く「確定」の通知は 1 通だけ**（版番号つきの冪等確定） | 確定した会話キーと版。2 回目の押下で何が返ったか（返らなかったか）。「確定」の通知が何通届いたか |
| 4 | `/gfv` `action:clear` → 確認ボタン → **モーダル**（「何を是正したか（監査に残ります）」と「確認フレーズを入力してください」の 2 欄）に入力して送信 | ボタンとモーダルは停止の有無に関係なく出る（リスク管理を呼ぶのは送信時）。GFV 違反で止まっていなければ、リスク管理が返す拒否の文言（解除対象が無い旨）がそのまま返り、何も変わらない。止まっていれば `GFV 違反による停止を解除しました（対象 n 件）。違反記録そのものは失効しません…` | 返った文面。確認フレーズを違えて送ると拒否されることも見てよい（統制は変わらない） |
| 5 | `/drift` `action:adopt` `symbol:<銘柄>` `market:<市場>` → 確認ボタン → **モーダル**（「なぜ台帳を合わせるのか（監査に残ります）」と「確認フレーズを入力してください」の 2 欄）に入力して送信 | ボタンとモーダルは乖離の有無に関係なく出る（リスク管理を呼ぶのは送信時）。乖離が報告されていない銘柄なら、API の拒否の文言（乖離がありません）がそのまま返り、台帳は変わらない。乖離がある銘柄なら前後の数量と「操作者 <利用者名> として記録しました」。フレーズを違えると「…台帳は変わっていません」 | 返った文面。取り込んだなら操作者が利用者名になっているか（`unknown` や `client:` ではない） |
| 6 | **第 2 のアカウント**で 1〜5 を試す | どれも**拒否される**。`/report` の `period` に**候補が出ない**。`/drift` で**ボタンが出ない** | 拒否されたか |

### 手順 4・5 の確認フレーズ

手順 4・5 のモーダルで求められる**確認フレーズは kill switch の確認フレーズと同じ語**である（Bot は同じ検証を通す）。
値は Vault の `ai-stock-trading/app-secrets` のキー `discord-bot-killswitch-phrase` に利用者が登録したもの
（基盤の「秘密情報・接続設定の管理」画面で確かめられる）。**未設定なら、フレーズを何と入れても拒否される**（安全既定）。
本書には値を書かない。

### 手順 3 で選ぶ報告書（報告書の本文が検索に当たることの確認を兼ねる）

**自動生成されたドラフトを選ぶ。** 通知チャンネルに「レビュー待ち」として提示された報告書がそれである。
**手で作った会話（本文を持たない）を確定しても、本文の検索の確認にはならない**——確定した報告書は知識ベースへ保存されるが、
本文が空なら本文は送られない。

> **2026-09-26 の観測**: `daily-2026-09-26` が 2026-09-26 03:10（日本時間）に確定されたが、本文が空だったため知識ベースには
> タイトルと属性だけが保存された（report-service のログ「本文が空のため KB へ本文を送りません」）。土曜の日付の日報であり、
> 自動生成の時刻より前に確定されているため、手で作られた会話だった可能性が高い。**誰がどの経路で確定したかは通知チャンネルの
> 「確定」の通知（確定者が載る）で確かめられる。** この確定は本文の検索の確認には使えない。

## 確認（この手順が成功したと言える条件）

利用者が「終わった」と伝えれば、以下は AI が読み取りのみで確かめられる。

```bash
# 手順 3: 直近 1 時間に処理した ReportConfirmed の件数（→ 1）。
#   このログ行には会話キーが出ないため、会話キーでは絞れない。窓の中で確定したのが 1 件だけのときに有効な数え方である
kubectl -n ai-stock-trading logs deploy/notification-service --since=1h | grep -c 'Successfully processed message .*ReportConfirmed#'

# 手順 3: 2 回目の押下を窓口で吸収した記録（こちらは PeriodKey= が出る。無効化が先に効いたなら 0 件で正常）
kubectl -n ai-stock-trading logs deploy/notification-service --since=1h | grep '報告書の二重確定を窓口で吸収しました'

# 手順 3: 知識ベースへの保存が 201 で、本文が空の警告が出ていない
kubectl -n ai-stock-trading logs deploy/report-service --since=1h | grep -E '本文が空|POST http://document-service.*/documents|201'

# 手順 2: 補完が落ちていない
kubectl -n ai-stock-trading logs deploy/notification-service --since=1h | grep -E '補完の予算|報告書一覧の照会に失敗'

# 手順 6: 陰性試験が拒否として記録された
kubectl -n ai-stock-trading logs deploy/notification-service --since=1h | grep 'Discord コマンドを拒否しました'
```

本文つきの確定が 1 件できたら、AI がその本文にしか出てこない語で知識ベースを検索し、当該文書が返ることを確かめる（報告書の本文が検索に当たることの最後の確認）。

## 失敗したときの分岐

| 症状 | 原因の候補 | 次の手 |
| --- | --- | --- |
| コマンドが一覧に出ない | Bot が Ready に至っていない・別のサーバーで打っている | notification-service のログで `スラッシュコマンドを登録しました` を確かめる。通知用サーバーで打つ |
| どのコマンドも拒否される | 利用者の Discord ID が許可リストに無い・チャンネル ID が違う | 基盤の画面で `discord-bot-allowed-user-ids` / `discord-bot-channel-id` を確かめる（値は画面から入れる） |
| `/report` が「失敗しました（HTTP 401/403）…owner クライアント設定…」 | Bot の owner クライアントの資格情報・ロール割当 | 表示されたヒントのとおり。`discord-owner-auth-client-*` は画面では書けない（基盤の既定） |
| 補完の候補が出ない | 一覧 API の遅延（Discord の補完の応答期限は 3 秒） | ログに「補完の予算（2500 ms）内に返りませんでした」があれば一覧 API の遅延。出ないこと自体を記録する（優先度の判断材料になる） |
| 「確定」の通知が 2 通届いた | 冪等確定の欠陥 | その場で止め、会話キーと版を issue に書く |

## 記録

- 実 Discord の接続確認の issue（本書の trace ブロック参照）に、手順 1〜6 の「記録すること」を書く。
- 手順 3 で確定した会話キーを、報告書の本文の検索の issue にも書く（AI が検索の確認を引き取る合図になる）。

## 限界（この手順で担保できないこと）

- 手順 3 の確定は本番の統制操作である。**確認のためだけに不要な報告書を確定しない**（確定した方針が以後の判断に使われる）。
- 段階の昇格・差し戻し（`/stage promote|demote`）は測る対象ではない（利用者の承認そのものが要件であり、確認のために打たない）。
- Webhook の URL の再発行は別の手順である（同じディレクトリの Discord Webhook 再発行 Runbook）。
