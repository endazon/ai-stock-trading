## 決定

### 決定1: **権威源は監査台帳である**（判断サービスではない）

判断サービス側の状態（`FxSourceStatusTracker`）は **in-memory・プロセスごと**であり、**再起動で消える**。
**期間で引く照会の権威源にはできない。**
監査台帳は**イベント全量を JSON で 7 年保持する**（IADR-0019）——**期間の集計はここからしか復元できない。**

### 決定2: **監査台帳へ「種別 × 期間」の照会を足す。上限を持たせない**

既存の照会は**相関単位**と**直近 N 件**しか無い。

🔴 **`GetRecent(大きな limit)` で代用しない。** 期間内の件数が上限を超えると**古いものから静かに落ちる**
——**取りこぼしても赤くならない**（本プロジェクトが繰り返している失敗の型）。

- **認可は `OwnerOrService`**（ReportService からの s2s。IADR-0051 と同じ形）。**必要な 1 本だけを開ける。**
- 🔴 **認可はグループではなくエンドポイント単位に置く**——`RequireAuthorization` は**加算**であり、
  グループの `OwnerOnly` を残したまま個別に `OwnerOrService` を足すと**両方を満たす必要が生じ 403 になる**。
  **実測で踏んだ**（「開けたつもりで開いていない」形）。
- **`types` の指定漏れは 400**。空を「全件」と読むと**取引履歴（機微情報）が意図せず流れる。**

### 決定3: **期間は JST 取引日 → UTC の半開区間へ写す**

**`[from 00:00 JST, to+1 日 00:00 JST)`。**
🔴 **終端を `23:59:59` で閉じない**——**その日の最後の 1 秒が、当日にも翌日にも出なくなる。**

### 決定4: **供給不達は `null`。空（事象なし）と区別する**

`IBuyInInferenceRecordSource` と同じ向きであり、`IPeriodFillSource`（空列へ倒す）とは**逆**である。
**劣化があったのに「ありません」と書くのは、劣化を隠したのと同じ結果になる**（IADR-0196 決定3）。

### 決定5: 🔴 **出典は「台帳に証拠のある情報源」だけを載せる。無い期間は「特定できません」と書く**

**遷移でしか発行しない**（IADR-0196 決定1）ため、**静かな期間はどの源を使ったのか台帳から証明できない。**

| 台帳にある記録 | 証明できること |
| --- | --- |
| `FxRateSourceFellBack(SourceName)` | **その源を使った** |
| `FxRateSourcePrimaryRestored(SourceName)` | **第一の源へ戻して使った** |
| `FxRateStale` / `PositionClosedWithStaleFxRate` | レートを使った（**源の名前は分からない**） |
| **記録なし** | 🔴 **何も分からない**（静かに第一の源を使った／為替を一度も使わなかった、の区別が付かない） |

**あわせて「劣化なし」の文言から「第一の情報源から取得できており」を外した。**
**遷移が無いことは「第一の源を使った」ことの証拠にならない**——**証拠が支えていない主張**だった。

> **IADR-0196 決定3 と同じ規律を 1 段深く当てたものである。**
> あちらは「**照会できなかった**」を「切替なし」と書かないことを定めた。
> こちらは「**記録が無い**」を「第一の源で正常だった」と書かないことを定める。

**出典が空であることも黙って通さない**——「**記録からは特定できません**」と明記する。
そうしないと読み手は「**書き忘れ**」と「**書ける根拠が無い**」を区別できない。

> **これができるのは、クレジットが法的義務ではないからである。** ADR-0022 §利用条件（2026-08-05 裁定）は
> 日銀 API 側の義務が「**サービスを公開した場合**」の条件付きであり**私的運用では発生しない**と定めている
> （**ただし報告書への出典明記の方針は維持する**）。**義務なら「証拠が無くても書く」が要るが、
> 自己方針なら「証拠が無いと書けない」と正直に書くほうが方針の趣旨に適う。**

### 決定6: **`Detail` の JSON 設定を契約へ移し、書き手と読み手で 1 つの定義を共有する**

書き手は監査サービス、読み手は報告サービスであり**別アセンブリ**である。2 箇所に書くと——

🔴 **命名規約を片側だけ変えたとき、`JsonSerializer` は例外を投げない。**
**既定値（0 / null）で埋めた record を黙って作る**——**数量 0・金額 0 の行が報告書に載る。**

`FxSourceCredits` を契約へ置いたのと同じ理由である。**情報源の識別子（`"boj"`）も同様に契約へ寄せた**
——表示側は**イベントに載ってきた名前**で出典を引くため、**両側に別々のリテラルを置くと、
名前を変えたときに出典だけが静かに出なくなる。**

## 対象外としたもの

### 🔴 `IMarginReductionRecordSource` は結線しない（**実測で判断を変えた**）

前セッションの記録に「2 つまとめて結線するのが筋」と書いたが、**実測の結果これは誤りであった。**

- `IMaintenanceMarginSnapshotSource` の実体は `UnavailableMaintenanceMarginSnapshotSource`（**常に null**）
- **`MaintenanceMarginReductionService.Evaluate()` の呼び出し元が本番に 1 つも無い**
- ゆえに `MaintenanceMarginReductionExecuted` は**今日 1 度も発火し得ない**

ポート自身が「結線は**発火元（#331 / #342）と同時に行う**。それまでの既定は空列＝『発動なし』であり、
**発動があり得ない現状では事実として正しい**」と明記している。
**先に結線すると、発火し得ない経路の照会失敗が毎日「要確認」として出る**——正しさが下がる。

> **為替は発火している／維持率割れは発火し得ない。同じ「未結線」でも状況が違う。**

## 対照実験（変異試験・実走した実測）

**手順**: ①コミットしてから変異させる ②置換の**一致件数**を確認 ③**`git diff` の中身**で当たり所を確認
（`--numstat` では当たり所の誤りが分からない・IADR-0198 の実測）④`error CS` が 0 を確認してから判定する。

| # | 変異 | 期待 | 実測（`error CS` はすべて 0） |
| --- | --- | --- | --- |
| 1 | 期間の終端を閉じる（`<` → `<=`） | 半開区間テストが赤 | ✅ **1 件赤**（`始端は含み_終端は含まない`） |
| 2 | 種別が空のときの早期 return を潰す（`if (false)`） | 全件化テストが赤 | 🔴 **1 件も赤くならなかった**（下記） |
| 3 | 照会失敗を空の `FxSourceStatus` へ倒す | 失敗の向きテストが赤 | ✅ **3 件赤**（3 つの status すべて） |
| 4 | 出典を「証拠が無くても日銀」にする | 否定形テストが赤 | ✅ **1 件赤**（`フォールバック先しか使っていなければ_日銀の出典を出さない`） |
| 5 | 生成器から供給の呼び出しを外す | 結線テストが赤 | ✅ **1 件赤**（`為替の情報源の状態が日報の本文へ出る`） |

### 🔴 変異 2 が生き残った——そして**それが正しかった**

早期 return を `if (false)` へ潰しても**テストが 1 本も落ちなかった**。
最初は「テストが弱い」と読んだが、**実際は実装のほうが余計だった。**

**種別が空なら、下の絞り込み（`Contains`）がそのまま空を返す。** 早期 return は
**振る舞いを 1 ミリも変えない**——つまり**テストの書きようがない**。

> **これは「起こり得ないケースへの防御的実装」（禁止事項）そのものである。**
> 🔴 **守っているように見えて何も守らないコードは、読み手に「ここは守られている」と誤解させるぶん、
> 無いより悪い。**

**是正**: 両実装（EF / インメモリ）から早期 return を落とした。
**「種別の指定漏れ」を止めるのは実際にはエンドポイント側の 400 であり、そちらは検査している**
（空文字・`,,`・空白のみの 3 形）。

> **変異が生き残ったときに、まずテストを疑うのは半分しか正しくない。**
> **「そのコードが要るのか」を先に問うほうが、テストを 1 本増やすより良い結果になることがある。**

## 影響

- **良い影響**: **#381 の可視化が初めて端から端まで繋がる**（発行 → 台帳 → 期間照会 → 日報）。
  監査台帳に**期間で引く**汎用の照会ができ、他の期間集計（将来の統制記録）も同じ経路で引ける。
- **悪い影響**: 監査台帳に **s2s で開いた口が 1 つ増える**（`OwnerOrService`）。
  報告生成のたびに監査サービスへの同期照会が 1 回増える（タイムアウト 10 秒・失敗は未供給へ縮退）。

## 残余リスク

- 🔴 **静かな期間の出典が出せない**（決定5）。**遷移でしか発行しないため原理的に証明できない。**
  日次の「初回使用」記録（1 日 1 件・通貨ごと）を足せば解けるが、**新イベントの追加は本 PR の範囲を超える**
  ——**follow-up issue として起票する。**
- **`Audit:BaseUrl` 未設定の環境では従来どおり「要確認」が出る**（結線は構成による opt-in）。
- **報告期間より前に台帳から消えた記録は復元できない**（7 年保持のため実務上は問題にならない）。
- **`IMarginReductionRecordSource` は未結線のまま**（対象外・#331 と同時に行う）。
