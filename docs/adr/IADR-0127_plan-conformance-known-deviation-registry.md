# IADR-0127: 計画確定値の適合は「計画値テーブル＋既知逸脱レジストリ」で検査し、逸脱の解消を機械的に強制する

- 状態: Accepted
- 日付: 2026-08-03
- 決定者: endazon（利用者。#343 の受け入れ観点として承認）

## 起点・関連

- 関連する計画書 ID: FR-10（リスク統制）・FR-17（全体前提条件）・FR-19（取引ガード）・FR-20（段階ゲート）／ ADR-0008・ADR-0016・ADR-0018
- 関連 issue: [#343](https://github.com/endazon/ai-stock-trading/issues/343)（退行防止テスト基盤）・[#344](https://github.com/endazon/ai-stock-trading/issues/344)（親）
- 関連する実装仕様書: [作業仕様書 20260803](../specs/20260803_343_regression-test-foundation.md)・[テスト戦略](../tests/README.md)
- 先行する事故: [#306](https://github.com/endazon/ai-stock-trading/issues/306)（統制既定値が計画と乖離したまま検知されなかった）

## コンテキストと課題

計画大改定（project-planning#144）で ADR-0016 / 0018 が起案され、リスク統制の既定値が**確定単一値**へ
同期された。一方、現行実装の `TradingDefaults` と契約 enum はこれに追随しておらず、着手時点で
**11 項目の乖離**が実測で確認されている（金額系 3 値の固定額保持・連敗しきい値 3 vs 5・商品種別 2 値 vs 3 値・
発注先軸の不在・Stage 1 の呼称ほか）。

乖離そのものは各ドメイン issue（#329 / #332 / #333 / #334）が直す。問題は**その間、乖離をどう扱うか**である。
素朴な選択肢はどちらも成立しない。

- **計画値をそのままテストに書く** → 着手初日から CI が赤になり、フェーズ 1 が終わるまで全 PR がブロックされる。
- **現行実装値をテストに書く** → 実装のスナップショットを固定するだけで、計画との乖離を永久に検知しない（#306 の再発）。

さらに、仮に「暫定的に実装値で固定し、後で直す」としても、**担当 issue が値を直したときに固定値の更新を
忘れる**（テストが古い値を要求して赤くなる → 深く考えず新しい値へ書き換える）という運用が起きる。
これは統制値の変更が誰にも意識されないまま通る状態であり、資金を扱う本システムでは許容できない。

## 検討した選択肢

| 案 | 内容 | 着手初日の CI | 乖離の可視性 | 解消時の追随 |
| --- | --- | --- | --- | --- |
| A: 計画値を直接アサート | `Should().Be(計画値)` を並べる | ✕ 赤（11 件） | ○ | ○ |
| B: 実装値をスナップショット固定 | 現行値をそのまま固定 | ○ 緑 | ✕ 検知しない | ✕ 無自覚に書き換わる |
| C: 逸脱項目をテストから除外 | 乖離する項目を `Skip` する | ○ 緑 | △ 一覧が散らばる | ✕ Skip が残り続ける |
| **D: 計画値テーブル＋既知逸脱レジストリ** | 計画値を単一情報源とし、受容する逸脱を担当 issue 付きで別表に登録する | ○ 緑 | ○ 1 箇所に集約 | ○ **機械的に強制** |

## 決定

**案 D を採る。** 具体的には次の構成とする（`backend/Tests/AiStockTrading.PlanConformance.Tests`）。

**対象範囲**: 05_trading-assumptions **§5**（リスク統制・取引ガードの既定値）＋ **ADR-0008 / ADR-0016 / ADR-0018**
＋ **§1 / §4 / §6（全体前提条件の確定値。FR-17）** とする。§1（譲渡益税率）・§4（最小期待利益倍率）・§6
（月次費用上限の総額 / LLM / インフラ / データ）も §5 と同じ**利用者決定の確定値**であり、実装では
`TradingAssumptionsDefaults` にハードコードされている。サービス内のユニットテストは実装と一緒に書き換わり得るため、
**確定値である限り本レジストリの中央検査に含める**（§2 手数料・§3 為替スプレッドは計画上「要確認」であり
確定値を持たないため対象外。§6.1 の「LLM 費用上限の対象は取引判断サイクルのみ」のような**適用範囲の規則は
値ではない**ため、後述のとおり本レジストリでは扱わない）。

1. **`PlanRiskDefaults`** — 計画書の確定値テーブル。**計画側の単一情報源**であり、実装値を書き写さない。
   各行は「キー・正規化した値・出典（節 / ADR 番号）」を持つ。
2. **`ActualDefaults.Snapshot()`** — 実装側スナップショット。**すべての値を実装から機械的に導出する**
   （定数・設定フィールド・enum の列挙・型の有無をリフレクションで確認）。手で書き写さない。
3. **`KnownPlanDeviations`** — 受容する逸脱の登録簿。各行は「キー・**現行の実際値**・担当 issue 番号・理由」を持つ。
4. **検査 6 本**（`PlanConformanceTests`）:
   - 計画値と実装値が一致する（登録済み逸脱を除く）— **新規**逸脱を止める
   - 計画値の全キーが実装側スナップショットに存在する — 抽出漏れ・綴り誤りを止める
   - **登録済み逸脱は実際に逸脱している** — 実装が計画に追いついたのに登録が残っていれば失敗
   - **登録済み逸脱の現行値は実装の実際値と一致する** — 値が変わったのに登録が追随していなければ失敗
   - 登録済み逸脱はすべて担当 issue・理由・計画上の裏付けを持つ — 恒久化を防ぐ
   - 登録簿と計画表にキーの重複が無い

**値は正規化文字列で比較する。** 単位と基準を必ず含める（`"equity ratio 0.25"` / `"JPY 35000 (fixed amount)"`）。
数値だけで比べると「25% を `25m` と持つか `0.25m` と持つか」「円かドルか」「割合か固定額か」を素通しする。
これは本システムで最も危険な誤りの型であり、計画が金額系 3 値を equity 比で保持すると明記した理由でもある。

**振る舞いの規則は本レジストリで扱わない。** 「常に厳しい方が効く」「kill switch 中でも手仕舞いは止めない」
「必要証拠金の降順で縮小する」は値ではない。これらはテスト戦略の 3 点セット（境界値・プロパティベース・
否定形）で担当 issue が検証する（[docs/tests/README.md](../tests/README.md)）。

## 理由

- **検査 3・4 が本方式の核**である。#329 が `LosingStreakThreshold` を 5 へ直した瞬間、登録簿の現行値「3」が
  実際値「5」と食い違い、かつ実装が計画に一致したことも検知され、**登録簿から当該行を削除するまで CI が通らない**。
  逸脱の解消が記録へ反映されることが人手の規律ではなく機械で保証される。実測で確認済み（作業仕様書の検証節）。
- **計画値と実装値の情報源を分ける**ことで、テストが「実装が実装どおりであること」を確かめるだけの
  トートロジーに退化しない。#306 はまさにこの退化で見逃された。
- **実装側を機械的に導出する**のは、スナップショットを手書きにすると計画表と同じ紙の上の一致になり、
  検査 3・4 が働かなくなるためである。未実装の概念も「その概念が置かれるべき型の有無」を
  リフレクションで見ることで、担当 issue が型を追加した時点で自動的に値が変わる。

## 結果

- 良い影響:
  - 全面再実装の途上でも CI が green を保ちつつ、計画との乖離 11 件が 1 箇所に可視化される
  - 担当 issue の完了が登録簿へ反映されることが機械的に保証される（「直したが記録が古い」が残らない）
  - 単位・基準の取り違え（割合 / 固定額、USD / JPY）が検知対象に入る
- 悪い影響・トレードオフ:
  - 計画値テーブルは**人手で計画書から写す**。計画書が改訂されたときの追随は人の責務であり、機械化されていない
    （計画書の Markdown を機械可読にする案は、計画リポジトリ側の様式変更を要するため採らなかった）
  - 未実装概念の検知は「想定する型名」に依存する。担当 issue が別名の型を採ると、型の不在のまま検知されない。
    このため登録簿の理由欄に**想定する型名**を明記し、担当 issue の作業仕様書で追随を求める
  - 正規化文字列の表現は慣習であり、新しい項目を足す際に表現がぶれ得る。既存行に倣うこと
  - **キー名が実装のどのフィールドを指すかは人が決める**。名前が意味を正しく表していても、抽出元が
    別のフィールドだと「たまたま計画と一致している値」を見て逸脱を素通しする。実際に本 ADR の初版で
    `Stage0` の DD 許容値を運用の DD 停止ライン（`RiskLimitSettings.MaxDrawdownRatio` = 0.10）から
    抽出しており、ADR-0018 決定2 が名指しする `Stage0GateCriteria.MaxDrawdownTolerance`（= 0.15）の
    逸脱を検知できていなかった（PR #350 の AI レビューが指摘・修正済み）。
    **新しい行を足すときは「計画書が名指ししているフィールドはどれか」を計画書本文で確認する**こと
- フォローアップ:
  - #329 / #332 / #333 / #334 の各 PR は、値の修正と同時に `KnownPlanDeviations` から該当行を削除する
    （削除しなければ CI が赤になるため、忘れることはできない）
  - **§4 の最小期待利益倍率は対象範囲に含むが、行の収録を保留している**。対象範囲を §1 / §4 / §6 へ広げた
    時点の実測で、計画の確定値（**往復費用＋税の 2 倍**。2026-07-23 利用者決定。それ以前は未確定の
    `<1.5 倍>` だった）と実装（`TradingAssumptionsDefaults.MinimumExpectedProfitMultiple` = **1.5**、
    かつ基準に税を含まない）の**不一致**を発見した。既知逸脱の新規登録は担当 issue の割当を伴う監査判断で
    あるため、本 ADR の更新では登録簿へ追加せず、**計画側の是正か担当 issue 付きの逸脱登録かの裁定を待つ**。
    裁定後に `PlanRiskDefaults` へ行を追加する
  - #345（AwesomeAssertions への全置換）は本テストも対象に含める。移行でテストの意味が変わらないことの確認対象
