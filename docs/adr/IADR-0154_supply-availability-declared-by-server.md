# IADR-0154: 供給が無い指標はサーバが「供給可否」として宣言する（SC-03 空売りの現況）

## コンテキストと課題

計画（05_screens SC-03・2026-08-01／2026-08-02 追加）は、統制状態参照画面へ次の表示を求めている。

- **維持率**（本画面の最上位。「マージンコールは口座を失う唯一の経路である」）
- 空売り比率・保有ポジションの建玉方向・**借株料の累計**
- 維持率割れによる自動縮小の閾値・回復目標・**直近の発動履歴**

**しかし、これらの多くはバックエンドに供給元が無い**（`develop` 9b0f96f で実測）。

| 項目 | 供給の実測 |
| --- | --- |
| 維持率 | **無い。** `IMaintenanceMarginSnapshotSource` の既定実装は `UnavailableMaintenanceMarginSnapshotSource`（常に `null`）。PoC 項目 3 で「実弾口座でのみ照会でき SIMULATE では照会 API 自体が失敗」と実測（[blocked-tasks](../blocked-tasks.md) A-2） |
| 借株料の累計 | **無い。** 累計を保持する型・ストア・イベントがコード全体に存在しない |
| 自動縮小の発動履歴 | **無い。** 発火元（維持率）が無く、Risk 側に履歴ストアも照会 API も無い |
| 空売り比率 | **条件付き。** 分母（建玉総額）は**時価**であり、現在値の供給（`MarketData:EnableMarkToMarket`）は既定 false |
| 建玉の方向 | **有る**（台帳射影 `OpenPosition.Side`） |
| 閾値・回復目標・上限 | **有る（設定値）**。`ShortSellingLimits` |

**ここで決めるべきは「何を表示するか」ではなく「値が無いことをどう表現するか」である。**

素朴に実装すると、供給が無い指標は `0` か `—` として画面に出る。すると画面は
「維持率 0.0%」「借株料 $0」「発動履歴なし」と描き、**統制が正常に働いているように見える**。
[#403] はまさにこれで、`ControlViolationCount` の既定 0 が「統制違反なし」＝合格として読まれた。
維持率で同じことを起こせば、**口座を失う唯一の経路が「問題なし」と表示されたまま進む**。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 供給が無い項目を**画面に出さない** | 棄却 |
| B | `null` で運び、画面が `null` を「取得できていません」と描く | 棄却 |
| **C** | **サーバが指標ごとに供給可否（`MetricAvailability`）を宣言**し、画面はそれに従う | **採用** |
| D | フロントに「維持率は未供給」と定数で持たせる | 棄却 |

### A（表示しない）の棄却理由

計画が明示的に要求した表示項目であり、黙って落とすことは計画違反である。加えて
**「無い」ことが見えないのは「0」と同じ害**である——利用者は「この画面には維持率が無い」としか分からず、
**統制が働いていない**という運用上の重大事実に到達できない。

### B（`null` だけで運ぶ）の棄却理由

`null` は 2 つの別事実を区別できない。

- **供給元が無い**（＝統制がまったく働いていない。運用上の**異常**）
- **概念が成立しない**（＝信用建玉が 1 件も無い。**正常**）

打つ手がまったく違う。前者は供給元の実装（#331 / #342）を急ぐ話、後者は何もしなくてよい。
リポジトリは既に同じ区別を `MaintenanceMarginEvaluationStatus`（`NoActionRequired` / `SnapshotUntrusted`。
[IADR-0133] 決定8）で行っており、**「何もしなかった」を 1 つに潰さない**規律が確立している。

### D（フロントに定数で持つ）の棄却理由

**供給元が入った日に画面が嘘をつき続ける。** 誰かが `IMaintenanceMarginSnapshotSource` を実装しても、
フロントの定数を直さない限り「取得できていません」と表示され続ける。しかも**両側とも緑**である
（[#389] と同じ構図の逆向き）。供給可否は**サーバにしか分からない事実**であり、サーバが宣言する以外にない。

## 決定

**案 C を採る。** 読み取り専用エンドポイント `GET /risk-controls/short-selling`（OwnerOnly）を新設し、
応答が**指標ごとの供給可否を明示的に宣言**する。

### 決定1: 供給可否は 3 値の enum とし、`null` の意味を 1 つに絞らない

```csharp
public enum MetricAvailability { Available, NotSupplied, NotApplicable }
```

- `Available`（0）… 値がある
- `NotSupplied`（1）… **供給元が無い／取得できない。画面は警告として明示する**
- `NotApplicable`（2）… 概念が成立しない（建玉が 1 件も無い等）。異常ではない

`decimal?` の値は `Available` のときだけ意味を持つ。**序数は HTTP 経路で整数として往来する**
（[IADR-0086] 決定4）。既存メンバの序数は不変とし、新設は末尾へ追加する（[IADR-0134] 決定2）。

### 決定2: 判定は**サーバ側**で行い、フロントは供給可否に従うだけにする

`ShortSellingStatusService` が `IMaintenanceMarginSnapshotSource` の戻り値・現在値辞書の充足・
建玉の有無から供給可否を決める。フロントに「この指標は未供給」という知識を置かない。

**未知の供給可否は未供給へ倒す**（`availabilityRatioText` / `isNotSupplied`）。サーバが将来メンバを
追加したとき、画面が**値を持っているかのように**描かないためである（安全側フォールバック）。

### 決定3: 「値として成立しないスナップショット」も `NotSupplied` へ倒す

[IADR-0133] 決定8 と同じ向きである。壊れた建玉だけを除くと分母（建玉評価額の合計）が縮み、
**維持率が実際より良く見える**。画面でも同じ向きに倒し、「良く見える維持率」を出さない。

### 決定4: 空売り比率は**時価が揃わなければ算出しない**

ADR-0016 決定9 の分母は「建玉総額」＝時価である。取得原価で代用すると「空売り比率」という名前の
**別物**になり、上限 50% の判定を誤らせる。1 件でも現在値を欠けば `NotSupplied` とする。

### 決定5: 閾値・回復目標は**サーバ応答から取り、画面に直書きしない**

維持率閾値（0.40）・回復目標オフセット（0.05）・空売り比率上限（0.50）はすべて応答に載せる
（`Stage1GateCriteria` と同じ方針）。計画の改訂に画面が追随しない事故を防ぐ。
**「適用される閾値」と「設定上の閾値」は別の行にする**——前者は建玉の株価に依存し（自前 40% と規制要求の
厳しい方・[IADR-0133] 決定2）、スナップショットが無ければ決められない。同じ行に混ぜると、設定値が
あたかも実測の適用値であるかのように読める。

### 決定6: 「動かす」統制は 3 統制と**別の枠**（`role="region"`）に描く

計画は「本統制は『動かす』統制であり、既存の 3 統制（『止める』統制）とは性質が異なる。…
3 統制と同じ枠に並べると誤読されるため、視覚的に区別すること」と明記している。
枠線つきの `<section aria-label="維持率割れによる自動縮小（動かす統制）">` とし、テストは
**3 統制の表に自動縮小が含まれないこと**を否定形で固定する。

### 決定7: 契約フィクスチャで「供給が無いという宣言」そのものを固定する

[IADR-0146] の機構へ新エンドポイントを載せる。`risk-controls.short-selling.json` は既定構成の
実応答であり、**`NotSupplied`（＝1）が並ぶ**。ここが `0`（Available）へ黙って変われば xUnit が落ちる。
供給元が入って `Available` を返すようになった場合も落ちる——**それが正しい**。供給の有無が変わったなら、
画面（SC-03）と `docs/blocked-tasks.md` の記述を同じ PR で追随させる必要がある。

## 理由

- **「値が無い」ことが統制上の情報である。** 維持率が取れないことは、単なる表示の欠落ではなく
  「マージンコールに対する防御が働いていない」という事実である。これを 0 と同じ見た目にしてはならない。
- **供給可否はサーバにしか分からない。** フロントへ書き込むと、供給が入った日に嘘が固定される。
- **既存の規律の延長である。** [IADR-0133] 決定8（`NoActionRequired` と `SnapshotUntrusted` を潰さない）・
  `IMarginReductionRecordSource`（空列と `null` を区別する）と同じ考え方を画面へ持ち込んだだけであり、
  新しい概念を発明していない。

## 結果

- 良い影響:
  - 未供給を「正常値」に見せる経路が構造的に無くなる（変異検査で実測: 供給可否を無視して値を出す変異・
    未供給文言を `—` へ弱める変異・サーバが 0 を返す変異のいずれもテストが赤くなる）。
  - 供給元が入った瞬間に契約テストが落ち、画面と文書の追随が強制される。
- 悪い影響・トレードオフ:
  - 応答が冗長になる（指標ごとに供給可否のフィールドが増える）。**意図した費用**である。
  - 供給可否の判定が増えたぶん、サーバ側の分岐が増える。
- **残余リスク（明記）**:
  1. **`NotApplicable` を `Available` と取り違える実装が将来入り得る。** 「建玉なし」を「比率 0%」として
     返すと、上限 50% に対して余裕があるように見える。本 ADR はそれを禁じるが、機械的な検出は
     契約フィクスチャ（既定は建玉ありのケース）と単体テストに依存する。
  2. **借株料の累計は「供給元が無い」ことを実装が**ハードコード**している**（常に `NotSupplied`）。
     供給元が入ったときに `MetricAvailability` を切り替える作業が人手に残る。フィクスチャは
     この値の変化を検出するが、**切り替え忘れそのものは検出しない**（値が無いままなので緑のまま）。
  3. **空売り比率は現在値の供給（`MarketData:EnableMarkToMarket`）に依存する。** 既定 false のため、
     実運用で有効化するまで恒常的に `NotSupplied` である。
