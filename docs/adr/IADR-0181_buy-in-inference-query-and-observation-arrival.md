# IADR-0181: 強制買戻しの推定の照会 API と、観測の到達の記録（FR-21）

## 背景

**計画が実装側へ名指しで起票を指示した唯一の項目である。** ADR-0016 決定15 の 2026-08-07 確定（質問票 第 14 回 Q9）:

> **推定はリスク管理サービス、報告書は報告サービスで動き、両者を結ぶ照会 API が無い。**（…）
> **許容は恒久の免除ではない。実装側は照会 API を別 issue として起票すること。**

その起票が [#463](https://github.com/endazon/ai-stock-trading/issues/463) である。

**しかし照会 API だけでは受け入れ基準を満たせない。** issue の受け入れ基準は
「**観測の到達が記録されていない間は、台帳が空でも「取得できていません」のままである（FR-21）**」を
含み、🔴 として「供給が入ったことを理由に FR-21 を省くこと」を挙げている。

実測（2026-08-08・`develop` = `f25edda`）:

| 側 | 状態 |
| --- | --- |
| 推定（リスク管理） | 実装済み（#419・IADR-0159）。`buy_in_inferences` / `EfBuyInInferenceStore` |
| 照会 API | **無い** |
| 報告書 | `UnsuppliedBuyInInferenceRecordSource`（常に `null`）が登録されている |
| **FR-21（観測の到達の記録）** | **🔴 未実装。** `docs/blocked-tasks.md:441` が「**未起票**。『観測が届いた事実』を記録する経路が要る」と記録していた |

**FR-21 が無い限り、台帳が空のとき次の 2 つを区別できない。**

1. ブローカ建玉の観測が一度も届いていない（＝**この統制はまったく働いていない**・異常）
2. 観測した結果、強制買戻しは 1 件も無かった（＝正常）

前者を 0 件と描けば「強制買戻しは起きていない」と読める —— 計画が名指しで禁じた向きである。

## 決定

### 決定1: 観測の到達を単一行で永続化する（FR-21）

`BrokerPositionsObserved` が届いた事実（`ObservedAt`）を永続化する。計画の文言は
「**最終観測時刻の永続化**」であり、期間ごとの記録ではない。

- 新ポート `IPositionObservationArrivalStore` ＋ `EfPositionObservationArrivalStore`（単一行・
  テーブル `position_observation_arrival`）。
- **単調前進のみ。** 順序保証の無いバスで後着の古い観測が届いても巻き戻さない ——
  巻き戻すと「供給されていた」状態が後から未供給寄りへ落ち、報告済みの正当な 0 の根拠が消える。
- **記録点は `BrokerPositionsObservedHandler`。推定の有無に関わらず、推定より先に記録する。**
  これが台帳（事象が起きたときにしか書かない）との唯一かつ本質的な違いであり、
  **FR-21 が別要求として立てられた理由そのもの**である。推定が例外で落ちても「観測は届いた」事実は変わらない。
- **未記録（`null`）は未供給**（fail-safe）。既定を「観測済み」に倒すと fail-open になる。
- **並行トークンを置かない**（`PositionDriftStateRow` とは意図的に異なる）。本行の更新は
  「より新しい時刻へ前進させる」だけの単調操作であり、競合で 1 回の前進を取りこぼしても
  次の観測が同じ前進を行う。**版番号で守る対象が無い。**

### 決定2: 照会は「観測の到達」と「推定行」を**同じ応答で**返す

```
GET /risk-controls/buy-in-inferences?from=YYYY-MM-DD&to=YYYY-MM-DD
200 { "observationArrivedAt": <DateTimeOffset|null>, "inferences": [ ... ] }
```

**別々の 2 エンドポイントにしない。** 分けると、呼び出し側が推定行だけを見て 0 件と判断する経路が
作れてしまう。**1 回の応答で両方を運び、判断を分離できないようにする。**

- 認可は **`OwnerOrService`**（既存の読み取り系グループ。IADR-0051 / [IADR-0176](IADR-0176_run-once-authorization-and-cronjob-token.md) と
  同水準）。**無認証の内部エンドポイントを増やさない。**
- **`from` / `to` の省略・逆順は 400。** 隣の `/fills` は 200 空列だが、**こちらは向きが違う** ——
  黙って空列を返すと、それが「推定 0 件」として報告書に載り得る。
  **照会できなかったことは空の結果ではない。**

### 決定3: 報告側は「観測未到達」と「照会失敗」を**どちらも `null`** に倒す

| 事象 | 返り値 |
| --- | --- |
| 通信断・タイムアウト・例外・非 2xx・不正応答 | **`null`**（未供給） |
| `observationArrivedAt` が `null`（旧版応答で項目が無い場合を含む） | **`null`**（**台帳が空でも 0 件にしない**） |
| `observationArrivedAt` があり推定 0 件 | **空列**（正当な 0） |
| `observationArrivedAt` があり推定あり | 推定行 |

🔴 **同居する `HttpPeriodFillSource` は失敗を空列へ倒す。向きが逆である。**
あちらは報告書が発注判断を行わないため欠測が過大発注へ繋がらないが、こちらは
**推定経路が実在し発火し得る**ため、欠測を 0 件と描くと統制が働いていない状態が正常に見える。
**隣に逆向きの前例があるため、後から「揃える」方向の整理で壊されやすい** ——
実装コメントと本 ADR の両方に「揃えてはならない」と書き、テストで固定した。

**規約は両方向に効く。** 未供給を 0 に見せないことと、**正当な 0 を未供給に見せない**ことの
両方をテストで固定する（後者を落とすと、統制が正常に働いている状態が永久に
「取得できていません」になる）。

### 決定4: SC-03 への結線は本作業に含めない

`ShortSellingStatusService`（SC-03）も同じ理由で `NotSupplied` に固定されており、FR-21 が入れば
結線できる。しかし **issue #463 の受け入れ基準は報告サービスの経路だけを対象としている。**
含めると SC-03 側の表示規約（[IADR-0162](IADR-0162_unsupplied-metric-display-convention-all-screens.md)）の
再確認まで巻き込み、本 PR の検査対象が広がる。

**別 issue として起票した**（[#470](https://github.com/endazon/ai-stock-trading/issues/470)。`docs/blocked-tasks.md` の当該行にも「FR-21 の**記録側**は入った（表示側の SC-03 は未了）」ことを反映した）。
**現状のまま「取得できていません」と表示し続けることは安全側であり、誤りではない。**

## 検討したが採らなかった案

| 案 | 却下の理由 |
| --- | --- |
| 照会 API だけを実装し FR-21 を後回しにする | **issue が 🔴 として名指しで禁じている。** 台帳が空のときに「観測が届いていない」と「0 件だった」を区別できず、受け入れ基準を満たせない |
| 失敗時に空列（0 件）へ倒す（`HttpPeriodFillSource` に揃える） | **「強制買戻しは起きていない」という誤読が構造的に起こる。** 計画が名指しで禁じた向き |
| 観測の到達と推定行を別エンドポイントにする | 呼び出し側が推定行だけを見て 0 件と判断する経路が作れる（決定2） |
| 期間の省略・逆順を 200 空列で返す（`/fills` に揃える） | 空列が「推定 0 件」として報告書に載り得る（決定2） |
| 観測の到達に並行トークン（版番号）を置く | 単調前進のみの操作であり守る対象が無い。競合で取りこぼしても次の観測が同じ前進を行う（決定1） |
| 観測の到達を推定の**後**に記録する | 推定が例外で落ちると「観測は届いた」事実まで失われる（決定1） |
| SC-03 も同時に結線する | issue #463 の受け入れ基準の対象外。現状の「取得できていません」は安全側であり誤りではない（決定4） |

## 対照実験（実走した実測）

| 壊した箇所 | 赤くなったテスト | 読み取れること |
| --- | --- | --- |
| 報告側の失敗時の返り値を `null` → `[]` へ | **9 件** | 失敗の向きは 9 経路（非 2xx 6 種・例外・タイムアウト・不正応答）が覆っている |
| `body.ObservationArrivedAt is null` の判定を外す | **2 件**（未到達／旧版応答） | FR-21 のゲートは load-bearing。かつ**その 2 件だけが**この条件を覆っている |
| ストアの単調前進ガード（`observedAt > row.LastObservedAtUtc`）を外す | **2 件**（-60 分・-1 分。同時刻は元から書かないため赤にならない） | 巻き戻しの禁止が実装に効いている |

## 影響

- **新規テーブル 1 つ**（`position_observation_arrival`・Migration `AddPositionObservationArrival`）。
  既存テーブル・既存イベントの契約は不変。
- **新規エンドポイント 1 つ**（`OwnerOrService` の読み取り系）。
- 報告サービスは `RiskManagement:BaseUrl` **未設定なら `Unsupplied…` のまま**＝現行挙動とバイト等価。
  設定時のみ実照会へ opt-in する（`HttpPeriodFillSource` と同じ作法）。
- introspection の自己申告に `buy-in-inferences` を足した。**`noop` ではなく `unsupplied`** と申告する ——
  空列を返す no-op と違い、こちらは `null`（未供給）を返す。

## 残余リスク

- 🔴 **最終観測時刻は「その報告期間を観測が覆っていたか」を判定できない。**
  例: 初回の観測が 2026-08-20 に届いた後で 7 月分の月報を生成すると、`observationArrivedAt` は非 null の
  ため **7 月の推定 0 件が「正当な 0」として表示される** —— 実際には 7 月に観測は 1 度も届いていない。
  観測が途中で止まった期間についても同じことが起こる（最終観測時刻は過去の値のまま残る）。
  **計画 FR-21 が定めるのは単一の「最終観測時刻」であり、この粒度は計画の文言どおりである。**
  **実装で規則を発明せず、計画へ環流した**（[project-planning#292](https://github.com/endazon/project-planning/issues/292)）。
  裁定が下りたら差分を追随させる。
- **観測そのものは OpenD 常駐に依存する**（`docs/blocked-tasks.md` の A-1 / A-2）。
  本 ADR が入れたのは「届いたら記録する」経路であり、**届く経路そのものは別問題**である。
- **SC-03 は引き続き「取得できていません」を表示する**（決定4）。FR-21 の記録側は入ったため結線できる状態であり、
  [#470](https://github.com/endazon/ai-stock-trading/issues/470) で行う。**観測が流れ始めた日に、SC-03 は
  「正当な 0 を未供給に見せる」側の規約違反（FR-21 受け入れ基準の逆方向）へ黙って転じる**——
  現時点では観測が 1 件も到達していないため表示は事実として正しいが、期限のある残件である。
- **推定の根拠（`CoveringFills`）は本経路では運ばれない。** 台帳が持っていないためであり、
  根拠が無いという主張ではない（明細が要るなら監査台帳を辿る）。
