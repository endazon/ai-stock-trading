# IADR-0175: セキュリティ仕様書における「無いこと」の書き分け

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-08-07
- 決定者: 実装（Claude Code）／ 起点 [#450](https://github.com/endazon/ai-stock-trading/issues/450)
- 作業仕様書: [20260807_450_security-spec-from-measurement](../specs/20260807_450_security-spec-from-measurement.md)

## コンテキストと課題

`docs/security/security.md` は `CLAUDE.md` が必須に挙げる仕様書だが、[#348](https://github.com/endazon/ai-stock-trading/issues/348) で「MCP への公開」節を足すまで**雛形のまま**であり、表の枠だけが空欄で並んでいた。

**空欄は 3 つの異なる状態を 1 つに潰す。**

| 実際の状態 | 空欄で書いたときの読まれ方 |
| --- | --- |
| 調べた結果、**対策が存在しない**（未実装） | 「まだ書いていないだけだろう」 |
| **調べていない**（未確認） | 「対策は無いのだろう」 |
| **本リポジトリの管掌外**（インフラ・基盤） | 「抜けている」 |

**どの誤読も方向が一定でない**ところが悪い。**無い対策を「あるはず」と読まれれば危険側**であり、**ある対策を「無い」と読まれれば無駄な再実装**を招く。#348 では暫定措置として「**書かれていない ＝ 対策が無い、ではない**」という注意書きを冒頭に置いたが、これは**全体に掛かる免責であって、個々の項目がどれなのかは依然として分からない**。

**セキュリティ仕様書は「読み手が自分の判断を委ねる文書」である。** 委ねられた側が「書いていない」を都合よく解釈できる状態は、文書が無いより悪い —— **無ければ調べるが、あれば信じる**。

## 決定

### 決定1: **空欄を作らない。4 語で書き分ける**

| 表記 | 意味 | 添えるもの |
| --- | --- | --- |
| **（記述）** | 対策が**ある** | **コードの所在**（ファイル名）または IADR |
| **未実装** | 調べた結果、対策が**無い** | **担当 issue**（無ければ起票する） |
| **未確認** | **調べていない**／本リポジトリからは決められない | **何を見れば分かるか** |
| **対象外** | 本リポジトリの**管掌外** | **管掌先**（issue・基盤リポ） |

**「未実装」と「未確認」を分けるのが要である。** 前者は「無いと分かっている」、後者は「分からない」であり、**残余リスクの大きさが違う**。まとめると、調べていない項目が調べた項目の顔をする。

### 決定2: **不備もそのまま書く**

実測で見つかった不備（`RequireHttpsMetadata = false`・`ValidateAudience = false`・無認証の内部エンドポイント・監査の保持期間未実装・Vault 化未充足）を**本書に書く**。

**セキュリティ仕様書が「できていることの一覧」になると、できていないことを探す場所がどこにも無くなる。** 不備を別の場所（issue だけ）に置くと、**本書だけを読んだ人は「対策済み」と受け取る**。

### 決定3: **「対象外」は「担保されている」を意味しない、と明示する**

[IADR-0059](./IADR-0059_dedupe-retention-purge.md) はパージの対象から `audit_events` を**明示的に外している**（監査は長期保全が要求されるため）。これは正しい判断だが、**「パージ対象外」は「7 年保持が担保されている」ことを意味しない** —— 保持側の実装は別にあり、現状は**無い**。

**除外の記述は、除外した理由の側だけを語る。** 読み手は「触らない」を「守られている」と読む。**除外を書いたら、では誰が担保するのかを同じ場所に書く。**

### 決定4: **推測で埋めない。埋められないものは埋めないと書く**

**推測で埋めた仕様書は、空欄の仕様書より悪い。** 空欄は「書いていない」と分かるが、**推測は本物と見分けが付かない**。#450 が #348 の時点で「埋めるには横断調査が要る」として**あえて空欄のまま残した**判断を、本 ADR は追認する。

## 理由

- **決定1〜4 はいずれも「読み手が誤って安心すること」を防いでいる。** セキュリティ文書の失敗は「書いていないこと」ではなく「**書いてあるが実態と違うこと**」であり、その中でも**危険側の誤読**（無い対策をあると読む）が最も重い。
- **決定3 は本リポジトリで実際に起きうる読み違いの実例から来ている。** 抽象論ではない。

## 結果

- `docs/security/security.md` の 5 節が実測で埋まり、**空欄が 1 つも無くなる**。
- **不備が本書に載る** —— 見つかった 4 件は別 issue へ起票し、本書からリンクする。
- 次に本書を編集する人が、**同じ書き分けを続けられる**。

### 悪い影響（記録する）

- 🔴 **本 ADR は機械検査を持たない。** 「空欄が無いこと」も「未確認と書いた項目が本当に未確認であること」も、**人が守る規約**である。`check-doc-links.js` のような自動検査は無い。**規約は書いた瞬間から腐り始める。**
- 🔴 **本書は 2026-08-07 時点の実測であり、実装が動けば嘘になる。** とくに**認証を登録していない 5 サービス**（Notification / InformationCollection / TradeDecision / OrderExecution / Backtest）は、後から HTTP エンドポイントを足したときに記述が実態と乖離する。**それを検知する仕組みは無い。**
- **「未確認」が増えると、文書が調査の TODO 一覧に近づく。** 現時点で未確認なのは保存時暗号化・TLS 終端位置であり、いずれも**インフラ（[#24](https://github.com/endazon/ai-stock-trading/issues/24)）が入って初めて確定する**。**#24 の完了時に本書を再訪する必要がある**が、その導線も人手である。
- **本作業は可視化であって是正ではない。** 不備を書いたことは、不備が直ったことではない。
