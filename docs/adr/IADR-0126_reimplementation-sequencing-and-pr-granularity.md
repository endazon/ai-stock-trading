# IADR-0126: 全面再実装は「1 issue = 1 PR」で行い、統制コアを結線より先に完成させる

- 状態: Accepted
- 日付: 2026-08-02
- 決定者: endazon（利用者。PR 粒度は利用者指示）

## 起点・関連

- 関連する計画書 ID（FR/UC/SC/ADR）: NFR（開発プロセス）。実装対象の ID は各子 issue が持つ
- 関連 issue: [#344](https://github.com/endazon/ai-stock-trading/issues/344)（親トラッキング）と子 issue 20 件（#329〜#348）
- 関連する実装仕様書: [作業仕様書 20260802（着手準備）](../specs/20260802_344_reimplementation-preparation.md)
- 関連規約: [`.claude/rules/traceability.md`](../../.claude/rules/traceability.md) / [`docs/DEFINITION_OF_DONE.md`](../DEFINITION_OF_DONE.md)

## コンテキストと課題

計画リポジトリの大幅更新（[project-planning PR #144](https://github.com/endazon/project-planning/pull/144)）を受け、本リポジトリの実装をほぼ全面的に
作り直す。作業は 20 件の子 issue に分割済みだが、**どの単位で PR を切り、どの順で進めるか**が
決まっていない。これは体裁の問題ではなく、次の 2 つの実害に直結する。

1. **統制の空白期間**: 資金を扱うシステムであり、判断・発注の経路が統制（リスク統制・取引ガード・
   段階ゲート）より先に動くと、統制なしで発注し得る期間が生じる。
2. **退行の検出不能**: 20 件の変更を大きな単位でまとめると、退行がどの変更に由来するか特定できず、
   「テストを充実させ退行を発生させない」という #344 の最優先方針が成立しない。

加えて、既存実装の削除タイミングも論点である。各 issue の中で旧コードを削除していくと、切替前に
稼働中の統制が欠ける期間が生じる。

## 検討した選択肢

### PR 粒度

| 案 | 内容 | 退行の特定 | レビュー可能性 | 統制の空白 |
| --- | --- | --- | --- | --- |
| A: 1 issue = 1 PR | 子 issue ごとに 1 ブランチ・1 PR | ○ PR 単位で切り分く | ○ 人間がレビューできる大きさ | ○ フェーズ順で防げる |
| B: フェーズ = 1 PR | フェーズ 0〜4 の 5 本 | × 1 PR に 3〜5 機能が同居 | × 数千行規模になる | ○ |
| C: サービス = 1 PR | サービス単位で作り直す | △ | △ | × 統制と発注が同一 PR に混じる |

### 既存実装の削除タイミング

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D: 各 issue で置き換え、削除は #346 に集約 | 新実装で置き換えつつ、旧コードの削除は切替計画へ寄せる | ○ 稼働中の統制が欠けない |
| E: 各 issue で旧コードも削除 | issue ごとに完結 | × 切替前に統制が欠ける期間が生じる |
| F: 先に全削除してから作り直す | 更地から実装 | × 監査証跡・業務台帳（7 年保持）の保全前に消える危険 |

## 決定

1. **PR 粒度は「1 issue = 1 PR」とする（案 A）。** 複数 issue を 1 PR にまとめない。1 issue を複数 PR に
   割らない。PR 本文の冒頭に `Closes #<issue>` を記載する。
2. **ブランチは `<種別>/<起点ID>-<概要のケバブケース>`**（`.claude/rules/traceability.md`）とし、起点 ID が
   複数ある issue は**代表 1 件**をブランチ名に置き、コミット / PR 件名でカンマ併記する。
3. **フェーズ順を守る。** 0（基盤標準・前提検証）→ 1（統制コア）→ 2（判断・発注・情報の結線）→
   3（報告・記録・画面・連携）→ 4（切替）。**フェーズ内は並行可**。依存する先行 issue が未マージの
   間は着手しない。
4. **稼働開始のゲートはフェーズ順とは別に定める。** 実取引（`SIMULATE` を含む）の開始前に、統制
   （#329 / #330 / #332 / #333 / #334）・監査（#339）・緊急停止（#341）・費用統制（#347）が揃っていること。
5. **既存実装の削除は #346（切替計画）に集約する（案 D）。** フェーズ 1〜3 の各 issue は既存コードを
   **置き換える**形で進め、旧コードの物理削除は行わない。
6. **各 PR は着手前に作業仕様書（`docs/specs/`）を持ち、受け入れ基準を xUnit テストへ写像する。**
   機能仕様書・テスト仕様書の必須範囲は網羅裁定（[#211](https://github.com/endazon/ai-stock-trading/issues/211)）どおり FR-10 / 12 / 15 / 19 / 20 とする。
7. **ADR-0016〜0020 は `Proposed` のままだが、決定内容を正として実装してよい。** 状態が記録上
   保留なのは計画側 `/sync-impl` 未了によるものであり、決定自体は利用者裁定で確定している
   （#344「進め方の原則 4」）。各作業仕様書にこの前提を明記する。

## 理由

- **1 issue = 1 PR** は利用者の明示指示であり、かつ退行の切り分けとレビュー可能性の両方を満たす唯一の
  粒度である。フェーズ単位（案 B）は 1 PR が数千行規模になり、AI レビューも人間レビューも表面的な
  確認に退行する。
- **統制コアを先に完成させる**のは、統制が「後から足せる横断的関心事」ではないためである。発注経路が
  先に動くと、統制の入っていない経路が既定になり、後付けの統制は必ず抜け道を残す。
- **削除を #346 に集約する**のは、監査証跡・業務台帳が 7 年保持で破棄不可（#344・#346）であり、
  保全手順の確定前に消してはならないからである。置き換え中は新旧が併存するが、稼働させるのは
  一方だけなので実害はない。
- **`Proposed` の ADR を正とする**判断は記録として残す必要がある。将来の監査で「Proposed の ADR に
  基づいて実装した」ことが根拠不明に見えるのを防ぐ。

## 結果

- 良い影響:
  - 退行が PR 単位で切り分けられ、`git revert` 可能な粒度が保たれる
  - 親 issue #344 のチェックリストが PR のマージで機械的に進む（`Closes` 連動）
  - 統制なしで発注し得る期間が構造的に発生しない
- 悪い影響・トレードオフ:
  - PR 本数が 20 本になり、レビュー回数とマージ待ちが増える
  - 置き換え期間中は新旧コードが併存し、リポジトリの見通しが一時的に悪くなる（#346 で解消）
  - フェーズ順の遵守により、フェーズ 2 以降は先行 issue のマージ待ちが発生する
- フォローアップ:
  - **ローカル検証環境（.NET SDK）の回復** — 現行の実行環境には `dotnet` が無く、配布ホストへの
    ネットワークも遮断されているため `dotnet build` / `dotnet test` を実走できない。フェーズ 0 の
    #343 着手前に解消する（作業仕様書 §6）。未解消のまま進めると各 PR が DoD の
    「ビルドが成功する」「テストが green」を提出前に確認できない
  - #342（moomoo PoC・Hetzner ToS）は期限があり外部依存でリードタイムが読めないため、フェーズ 0 の
    中で**最初に着手**する
  - ADR-0016〜0020 が `Accepted` へ昇格した際、決定内容に差分があれば該当 issue の作業仕様書を追随させる
