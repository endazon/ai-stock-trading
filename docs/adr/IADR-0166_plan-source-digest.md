# IADR-0166: 計画書 → 計画値の人手転記を「節のダイジェスト」で検知する

## コンテキストと課題

`IADR-0127` の計画適合レジストリは、**計画確定値（`PlanRiskDefaults`）と実装値（`ActualDefaults`）の乖離**を機械的に検出する。しかし計画書そのものと `PlanRiskDefaults` の間は**人手転記であり、無検査**である。

```
計画書（planning submodule）  ──【人手転記・無検査】──▶  PlanRiskDefaults
                                                              │
                                                     【機械検査・IADR-0127】
                                                              ▼
実装（TradingDefaults 等）    ──【リフレクション抽出】──▶  ActualDefaults
```

[#374](https://github.com/endazon/ai-stock-trading/issues/374) の実測が、この穴を数字で示した。

| 段階 | PlanConformance |
| --- | --- |
| 1. submodule のみ更新（計画側 9 種 vs 実装側 7 種） | **Failed: 0**（緑のまま） |
| 2. 人手で `PlanRiskDefaults` を 9 種へ転記 | **Failed: 1** |
| 3. 実装追随後 | **Failed: 0** |

**submodule を更新しただけでは赤くならない。** #374 で赤が出たのは監査者が計画差分を読んだからであって、読まなければ検出されなかった。[#378](https://github.com/endazon/ai-stock-trading/issues/378) はこれを塞ぐために起票された。

`IADR-0134` 決定3 が限界として記録済みだが、**記録しただけで塞いでいない**。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A** | 計画側に**機械可読ブロック**（YAML フェンス等）を設け、実装がそれを読む | **棄却。** 計画リポへの環流と、計画側の書き方を実装都合で縛ることを要する。計画書は人間が読む散文であり、実装の都合で構造を強制するのは主従が逆である |
| **B** | 計画書の表のセルを**パターン抽出**して値を比較する | **棄却。** 計画書の書式変更で壊れる。**壊れ方が「緑のまま」になり得る**のが致命的である——抽出に失敗したセルが「差分なし」に見えると、本 IADR が塞ごうとしている穴がそのまま再現する |
| **C** | **節のダイジェスト**。計画書の該当節のハッシュを実装側に保持し、節が変わったらテストを赤にして人間へ再転記を促す（**値そのものは抽出しない**） | **採用。** 失敗モードが**過検出**（無関係な字句修正でも赤くなる）であり、検出漏れではない。実装コストも最小 |

## 決定

### 決定1: 案 C（節のダイジェスト）を採る。**値の抽出は行わない**

`PlanSourceDigests` に「計画書の節 → その節を最後に転記した時点の SHA-256」を保持する。テストは submodule の当該節を読んでハッシュし、一致しなければ赤にする。

**赤の意味は「計画側が変わった。`PlanRiskDefaults` を読み直して転記し、ダイジェストを更新せよ」であり、「値が間違っている」ではない。** 値の照合は既存の検査1（`IADR-0127`）が担う。本検査は**その手前の 1 ホップ**だけを見る。

**値を抽出しないのは意図的である。** 散文からの値抽出（案 B）は、失敗が「緑」に見える形で壊れる。ダイジェストは**壊れれば必ず赤**になる。

### 決定2: ハッシュ対象は**節単位**とし、`変更履歴` を含めない

**ファイル全体をハッシュしてはならない。** 計画書には `## 変更履歴` テーブルが改訂のたびに追記される。全体ハッシュでは**計画側のあらゆる更新で赤くなり**、「中身を読まずにダイジェストだけ更新する」運用へ堕ちる。それは検査が存在しないより悪い（緑であることの意味が失われる）。

| 出典 | ハッシュ対象 |
| --- | --- |
| `06_technical/05_trading-assumptions.md` | **`### 1.` 〜 `### 6.1` の各節**（`PlanRiskDefaults` が引用する §1 / §3 / §4 / §5 / §6 / §6.1）。`## 変更履歴` は別の `##` 節であり自動的に対象外 |
| `07_adr/ADR-0008` / `ADR-0016` / `ADR-0018` / `ADR-0022` | **`## 決定` 節**（`### 決定 N:` を含む）。`## 結果`・`## 関連`・追記履歴は対象外 |

節は「見出し行から、**同位以上の次の見出し**の直前まで」とする。

### 決定3: 正規化してからハッシュする

改行コード（CRLF/LF）と各行の**行末空白**を正規化し、末尾の空行を落とす。**これらの差異は計画の内容ではない**ため、赤にする価値がない。逆に、これ以上の正規化（全角/半角、表の整形）は**内容の変化を吸収し得る**ため行わない。

### 決定4: submodule が未取得なら **skip する**（fail-open）

`planning/` が populate されていない環境では検査を飛ばす。`check-doc-links.js` / `check-commit-messages.js` と同じ扱いである（ローカル環境差で CI を落とさない）。

**これは fail-open であり、本 IADR の弱点である。** submodule を取らない CI ジョブでは本検査が効かない。**skip したことを必ず標準出力へ notice として出す**ことで、「緑だが検査されていない」を可視化する（`check-doc-links.js` と同じ規律）。

### 決定5: **抽出候補配列の網羅性検査は追加しない**

[#378](https://github.com/endazon/ai-stock-trading/issues/378) は「併せて検討」として挙げていたが、**追加しない**と決めた。

同 issue のコメントが報告した**抽出漏れの 2 類型**は、性質が異なる。

| # | 事例 | 型 | 候補配列の網羅性検査で捕まるか |
| --- | --- | --- | --- |
| 1 | `RejectionReason.StopOrderRequired`（#374） | `ActualDefaults` の**抽出候補配列**に名前が無い | 捕まる |
| 2 | `FxOptions.*`（PR #372） | **プロジェクト参照**に無く型が見えない | **捕まらない**（候補に書いても参照が無ければ解決しない） |

**2 例目は既存の検査2（`計画確定値の全キーが実装側スナップショットに存在する`）が捕まえる。** 実際 PR #372 で落ちたのは検査2 であり、しかも**検査2 は `KnownPlanDeviations` を参照しない**ため、抽出漏れを「既知の逸脱」として登録して緑に戻すことが原理的にできない。この非対称は正しい（抽出漏れが逸脱として黙認されるのが最悪の失敗モードである）。

したがって**「計画キーに対応する実装値が実際に解決できているか」の側からの検査は既に存在する**。候補配列側の検査を足すと、1 例目にしか効かない冗長な検査が増える。

## 理由

- **本検査の価値は「気づく機会を作ること」であり、正しさを保証することではない。** 計画書の散文から値の正しさを機械的に導くことはできない（案 B の棄却理由）。ダイジェストは**人間に読み直させる**ための仕掛けである。
- **過検出は許容できるが、検出漏れは許容できない。** 統制値の乖離は資金に直結する。無関係な字句修正で 1 回赤くなる手間は、乖離を 1 回見落とす損害より小さい。
- **決定2 が本 IADR の要である。** 全体ハッシュでも「検知はできる」が、運用が形骸化して**検知しなくなる**。技術的に正しくても運用で壊れる設計を採らない。

## 結果

- 計画書の該当節が変われば、**転記を怠った時点で CI が赤**になる。
- 赤の解消には**人間が計画差分を読んで `PlanRiskDefaults` を更新し、ダイジェストを更新する**必要がある。ダイジェストだけを更新して緑に戻すことは**技術的には可能**である（本検査の限界。決定1 の「気づく機会」という位置づけの帰結）。
- **submodule を取らないジョブでは効かない**（決定4）。実効するのは submodule を取得するジョブだけである。

### 悪い影響（記録する）

- **【最重要】ベースライン確立時点で既に存在する未転記の乖離は、原理的に拾えない。** 本機構は「前回の転記時点からの**変化**」を見るのであって、「転記が正しいか」を見ない。したがって**導入時のダイジェストを取る前に、その時点の転記が正しいことを人間が確認しなければならない**。確認せずに取ると、**未転記の状態を「転記済み（緑）」として固定してしまう**。

  **これは机上の懸念ではなく、本 IADR を導入した PR #444 で実際に起きた。** ADR-0022 決定4 は 2026-08-07 に警告しきい値を **3 日 → 5 日**へ改訂していたが、`PlanRiskDefaults` は `"3 days"` のままだった。最初のベースラインはその未転記の状態を緑として固定しており、**本機構が塞ごうとしている失敗モードそのものを、導入時点で再現していた**（AI レビューが発見）。同 PR で `"5 days"` へ追随させたうえでベースラインを確定した。

  **したがって本機構の導入・対象追加の手順は「転記を確認 → ダイジェストを取る」の順でなければならない。** 逆順にすると検査が嘘をつく。

- **導入時に全項目の再照合は行っていない。** #444 で是正したのはレビューが発見した 1 件（`Fx.StaleRateWarningDays`）だけである。**他の項目に同種の未転記が残っている可能性は排除できていない。** 全項目の再照合は別途行う（フォローアップ）。
- **計画書の節構造に依存する。** `### 1.` のような見出しが改名・再編されると、節が見つからず赤になる（安全側だが、計画側の正当な整理でも赤くなる）。
- **ダイジェストの更新が「作業」になる。** 計画追随 PR は毎回ダイジェストの更新を伴う。これは意図した摩擦だが、摩擦である。

## フォローアップ

- **`PlanRiskDefaults` 全項目を計画書の現行値と再照合する（[#445](https://github.com/endazon/ai-stock-trading/issues/445)）。** 導入時に是正したのは 1 件（`Fx.StaleRateWarningDays`）だけであり、**他に未転記が残っている可能性がある**。本機構はそれを検知できない（上記「悪い影響」の最重要項）。
- 「ダイジェストだけ更新して緑に戻す」を検知する手段は無い。**レビューで見る**しかない。バックログ定期監査（[#439](https://github.com/endazon/ai-stock-trading/issues/439)）の対象に含めるかは別途判断する。
