# IADR-0146: バックエンドの実 HTTP 応答を契約フィクスチャとして固定し、フロントの型とテストをそこへ接地させる

- 状態: Accepted
- 日付: 2026-08-05
- 決定者: 実装（Claude Code）／ 起点 [#389](https://github.com/endazon/ai-stock-trading/issues/389)
- 作業仕様書: [20260805_389_frontend-backend-contract-drift](../specs/20260805_389_frontend-backend-contract-drift.md)

## 起点・関連

- 関連する計画書 ID: FR-10（リスク統制）・FR-20（段階ゲート／発注先）・SC-02・SC-03
- 関連する実装 ADR: [IADR-0130](./IADR-0130_equity-ratio-risk-limits.md)（equity 比化）・
  [IADR-0136](./IADR-0136_stage-orderable-cap-ratio.md)（総資金比化）・[IADR-0140](./IADR-0140_broker-provider-axis.md)
- 同型の問題: [#378](https://github.com/endazon/ai-stock-trading/issues/378)（機構の中に人手のホップが残る弱さ）

## コンテキストと課題

[#329] / [#333] でバックエンドのプロパティ名が `MaxOrderAmount` → `MaxOrderAmountRatio`、
`CapitalCap` → `CapitalCapRatio` へ変わったが、フロントの契約型（`frontend/src/features/risk/contracts.ts`）は
旧名のままだった。**BFF は素通しであり変換で吸収されない**ため、実サーバ相手には `undefined` を読む。

**この退行は CI を完全に緑のまま通り抜けた。** 理由は 1 つである——

```ts
// フロントのテストが使っていたモック（インライン literal）
stage: { stage: 2, mode: 1, capitalCap: 1000000 },
```

フロントのテストは**フロント自身が「こう返ってくるはずだ」と思っている形**を自分で作り、それを自分で検証していた。
バックエンドの実型とは一度も突き合わせていない。したがって:

- バックエンドが `capitalCap` → `capitalCapRatio` に変えても**フロントのテストは緑のまま**
- バックエンドのテストはフロントを知らないので**こちらも緑のまま**
- **両方緑で本番だけ壊れる**

[IADR-0127]（計画適合レジストリ）が守っていたのは「計画↔バックエンド」の境界であり、
「**バックエンド↔フロント**」の境界には同じ機構が無かった。守られていない境界は、いずれ必ず壊れる。

**決めるべきは「キー名を直すこと」ではなく、「次に誰かがバックエンドのプロパティ名を変えたときに、
機械が赤くなること」である。**

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A** | バックエンドの型から OpenAPI / JSON Schema を生成し、フロントの型をそこから生成する | 棄却 |
| **B** | **契約テスト**（バックエンドが実際に返す JSON を固定し、フロントの型・テストに食わせる） | **採用** |
| C | フロントの型とバックエンドの型のキー名一致をスクリプトで照合する | 棄却（issue も非推奨） |

### A（OpenAPI からの型生成）の棄却理由

1. **現在の実装からはスキーマが出ない。** `RiskControlEndpoints` は `Results.Ok(svc.Build())` の形で、
   **戻り値型が `IResult` に消えている**。ASP.NET Core の OpenAPI 生成はこの形から応答スキーマを推論できず、
   `.Produces<RiskStatusView>()` 等の注釈を**全エンドポイントに人手で付ける**ことが前提になる。
   これは C（人手の登録簿）と同じ弱さを別の場所に置き換えただけであり、**注釈の付け忘れが同じ穴になる**。
   実際、本 issue の 3 キーは「注釈を付け忘れたエンドポイント」があれば同じようにすり抜ける。
2. **既存の `openapi.yml` はコード由来ではない。** 本リポの CI にある OpenAPI 自動更新
   （`scripts/gen-openapi-skeleton.js`）は**通信仕様書（Markdown）から雛形を起こす**ものであり、
   バックエンドの型を情報源にしていない。「CI に既存」という issue の記述はワークフローの存在を指すが、
   それをそのまま契約の情報源に転用することはできない。
3. **生成された型は `contracts.ts` を置き換えられない。** `contracts.ts` は型宣言だけでなく、
   数値 enum → 表示ラベルの写像・安全側フォールバック・計画 ID のトレーサビリティコメントを担っている。
   生成物で置き換えると、これらの置き場を別に作ることになり、結局手書き層が残る。
4. 導入コスト（`Microsoft.AspNetCore.OpenApi` の配線 ＋ `openapi-typescript` の npm 依存 ＋ 生成物の
   コミット/差分検査ジョブ）に対して、1〜3 の理由から得られる保証が C と大差ない。

### C（キー名照合スクリプト）の棄却理由

型の対応付け（どのフロント型がどのバックエンド型に対応するか）を**人手で登録**する必要があり、
登録漏れがそのまま同じ穴になる。[#378] が指摘した「機構の中に残る人手のホップ」と同型である。
本 issue はまさに「誰も見ていない境界」が原因なのだから、新しい機構の中に「誰かが登録しないと見ない」
場所を作ってはならない。

## 決定

**案 B を採る。バックエンドの実 HTTP 応答を契約フィクスチャ（JSON）としてコミットし、
フロントの型・テストをそのフィクスチャへ接地させる。**

```
backend（実 HTTP 応答）──▶ frontend/src/features/risk/contract-fixtures/*.json ──▶ frontend（tsc / vitest）
        ① xUnit が突合                （コミット済みの正）                    ② 型付け・描画で突合
```

### 決定1: フィクスチャは**実エンドポイントの応答**から採る（DTO の手動シリアライズではない）

`RiskWorkerWebApplicationFactory`（既存・実 `Program.cs` を起動する `WebApplicationFactory`）で
`/risk-controls/settings`・`/status`・`/stage-gate`・`/settings/history` を実際に GET し、
**応答ボディそのもの**を突合対象にする。型を手でシリアライズし直すと、アプリの `JsonSerializerOptions`
（命名規則・enum の数値表現）と乖離した「テストの中だけの JSON」を検証してしまう。
フロントが読むのは**実際に配線を通って出てきた JSON** でなければ意味がない。

### 決定2: フロント側の第一の関門は**コンパイル時**（`tsc`）に置く

`contractFixtures.ts` がフィクスチャ JSON を `import` し、契約型の変数へ代入する。
TypeScript は JSON モジュールから構造を推論するため、**キー名の改名・欠落・型の変更は代入時の型エラー**になる。

これにより、**フィクスチャを再生成してバックエンド側（①）を緑に戻しても、フロント側（②）が赤いまま**になる。
「機械的にフィクスチャを更新して黙って通す」経路が塞がれ、フロントを直すまで CI は赤い。
これが本機構の要点である——①だけなら「更新して終わり」にできてしまう。

### 決定3: 画面テストのモックは**フィクスチャから作る**（インライン literal を廃する）

SC-02 / SC-03 のコンポーネントテスト・E2E のルートモックは、契約フィクスチャを基に構築し、
各テストが必要とする差分だけを上書きする。**フロントが自分で作った形を自分で検証する構造をここで断つ。**
画面が描画に使うキーが消えれば、描画結果が変わってテストが落ちる（実行時の第二の関門）。

### 決定4: 正規化は**値の形**で行い、キー名の登録簿を作らない

`DateTimeOffset` は実行のたびに変わるためフィクスチャに固定できない。正規化は
「**`T` を含む ISO 日時として解釈できる文字列**」という値の形で判定し、固定値へ置換する。
「`changedAt` と `occurredAtUtc` を正規化する」というキー名の列挙にしない——
新しい日時キーが増えたときに登録漏れでフィクスチャが不安定化し、`--update` を常用させる圧力を生むためである。
`DateOnly`（`T` を含まない）は既定値由来の定数であり正規化しない。

### 決定5: 更新は明示的なオプトイン（`UPDATE_CONTRACT_FIXTURES=1`）に限る

フィクスチャの再生成は環境変数を明示したときだけ行う。既定では**比較して落ちるだけ**である。
自動更新にすると①が常に緑になり、機構が丸ごと無効化される。

### 決定6: 否定形テストを正の確認と同数以上置く

検査器の危険な壊れ方は「赤くなるべきときに緑のまま」である（CI が緑なので誰も気付けない）。
[IADR-0143] / [IADR-0145] と同じ規律で、比較器 `ContractFixtureComparer` に対して
**キー改名・キー欠落・型変更・ネストしたキーの改名・配列要素のキー改名**を与え、
すべて不一致として検出することを固定する。フロント側は `@ts-expect-error` による**コンパイル時の否定形**を置く
（旧キーの形が契約型を満たしてしまうなら、`@ts-expect-error` が「エラーが出ていない」として `typecheck` を落とす）。

## 理由

- **境界の両側に足がある**。①はバックエンドのリポジトリ内の xUnit、②はフロントの `tsc` / `vitest` であり、
  どちらか一方だけを直しても緑にならない。「両方緑で本番だけ壊れる」という本 issue の構図が構造的に成立しなくなる。
- **人手の登録簿が無い**。対応付けは「このエンドポイントの応答＝このフィクスチャ＝この型」という 1 本の鎖であり、
  登録を忘れる場所が無い（フィクスチャが無ければ①のテストがファイル欠落で落ちる）。
- **導入コストが小さい**。新しい依存・新しい生成基盤を持ち込まない（xUnit と `tsc` の既存の力だけを使う）。
- **フィクスチャは副産物として有用**である。画面テストが「実際にサーバが返す形」を使えるようになり、
  テストの説得力そのものが上がる。

## 結果

- 良い影響:
  - バックエンドのプロパティ名を変えると `dotnet test` が落ちる（変異検査で実測）。
  - フィクスチャを更新して逃げようとすると `npm run typecheck` が落ちる。
  - 画面テストが実応答に接地し、モックの思い込みを検証する構造が無くなる。
- 悪い影響・トレードオフ:
  - **バックエンドの正当な変更でもフィクスチャの更新が要る**（`UPDATE_CONTRACT_FIXTURES=1` で再生成し、
    フロントを追随させてからコミットする）。これは意図した摩擦であり、境界を跨ぐ変更を可視化するための費用である。
  - フィクスチャは `RiskManagementService` の 4 エンドポイントに限る。他サービス（MarketMonitor・Configuration）へは
    同じ形を後から足せるが、本 issue の範囲では作らない。
- **残余リスク（明記）**:
  1. **フロントが宣言していないサーバ応答キーは検出できない**。本機構は「フロントの型がフィクスチャを満たすか」を
     見るため、サーバにだけ存在するキー（現在の `shortSell`）は素通りする。TypeScript の構造的部分型では
     未宣言キーは読めないだけで画面は壊れないため、**危険度は低いが盲点である**。
  2. **フィクスチャが表現していない状態のずれは検出できない**（例: 既定値では空の配列に入る要素の形）。
     `history` は遷移・設定変更を実際に起こして非空にしてあるが、網羅ではない。
  3. **BFF（platform 側）の変換を挟む経路は本機構の外**である。現在 `/risk-controls/*` は素通しのため
     問題にならないが、将来 BFF が形を変えるなら、その境界にも同じ形の関門が要る。
- フォローアップ:
  - [#362](https://github.com/endazon/ai-stock-trading/issues/362): SC-02 の入力 UX を割合入力へ作り直し、
    PUT の形（現在は旧名のまま＝400 で拒否）を是正する。
  - 他サービスの契約（MarketMonitor `/monitor/*`・Configuration `/assumptions`）への横展開。
