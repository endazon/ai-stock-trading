## コンテキストと課題

2026-08-07 の利用者裁定（質問票 第 13 回 Q11・Q12・Q6）が計画へ反映され、SC-01 §2 が廃止された。
実装側には次の 4 つの課題が生じた。

1. **収集間隔を「持たない」ことを、どう担保するか。** 「実装しない」は放置と区別がつかない。
   後から「利便性の改善」としてエンドポイントが足されても、誰も止められない。
2. **変動閾値の由来サービスをどうするか。** 計画の旧記述（ConfigurationService 由来）は誤りで、
   実装（MarketMonitorService）が正しかった。**裁定は実装側を追認し、計画を実装へ合わせた。**
3. **Stage 1 の最小取引件数（100 件）が定数である。** 設定にするには、値の置き場所・値域・
   楽観排他・監査ログ・段階ゲートへの反映経路をすべて決める必要がある。
4. **計上単位が設定化で壊れないか。** 件数が設定で動くようになると、
   「単位が 2〜3 倍に膨らむ」欠陥が**設定を下げたのと同じ効果**を持ち、しかも画面には現れない。

さらに、実装前の調査で計画に無い 2 つの穴が見つかった。

- **全置換 `PUT /monitor/settings` に値域検証・理由・履歴が無い。** [IADR-0155] 残余リスク 4 として
  明記されていたものであり、変動閾値が「他のリスク設定と同様に理由必須・監査ログ」となった以上、
  **API を直接叩けば理由なしで 0 を保存できる**状態は裁定と両立しない。
- **BFF が `/monitor/settings*` を登録していない。** [IADR-0091](./IADR-0091_unit-owned-bff-endpoints.md)
  が踏襲した基盤側の方針（MSP/IADR-0072 決定2）は「フロントが叩かないため登録しない」であったが、
  #340 で SC-01 §2 が叩くようになった時点でこの前提は崩れていた。
  **SC-01 §2 は本番で一度も動いていなかった可能性が高い**（BFF 未結線＝404）。

## 検討した選択肢

| 論点 | 案 | 評価 |
| --- | --- | --- |
| 収集間隔 | A: 何もしない（実装しないだけ） | 棄却 |
| | **B: 変更経路が無いことを構造テスト（ルート表・型）で固定する** | **採用** |
| 変動閾値の権威 | C: ConfigurationService へ移して計画の旧記述に合わせる | **裁定で却下済み** |
| | **D: MarketMonitorService のまま SC-02 が消費する** | **採用** |
| 最小取引件数の置き場所 | E: `StageGatePolicy`（DI singleton）を可変にする | 棄却 |
| | F: 段階別実績（`StagePerformance`）の列に持つ | 棄却 |
| | **G: `RiskManagementSettings` に置き、`StageGateService` が判定直前に重ねる** | **採用** |
| 100 未満の警告の判定 | H: 画面が `< 100` を判定する | 棄却 |
| | **I: サーバが `BelowStatisticalBasis` を宣言し、画面と Discord がそれに従う** | **採用** |
| 全置換 PUT の穴 | J: 放置（画面からは使わない） | 棄却 |
| | **K: 値域・理由・履歴を部分更新と同じ規律に揃える** | **採用** |

### A（何もしない）の棄却理由

**「実装していない」と「実装してはならない」は別である。** 裁定は後者を述べている（Q11）。
前者のままにすると、次に画面を触る者が「未実装の項目」として素直に実装してしまう。
裁定に反する実装が「機能追加」の顔をして入り込む経路を、テストで塞ぐ。

### E（`StageGatePolicy` を可変にする）の棄却理由

`StageGatePolicy` は **DI の singleton** であり、段階別の資金上限・撤退倍率という
**運用中に変わらない方針**を表す。ここへ可変の設定値を混ぜると、
「誰がいつ書き換えたか」を持たないオブジェクトが監査対象の値を抱えることになる。
楽観排他も履歴も `IRiskSettingsStore` 側にしか無い。

### F（段階別実績の列に持つ）の棄却理由

**実績と設定は別物である。** [IADR-0149] 決定3 は取引件数そのものを実績行から外し、
観測ログを唯一の供給元にした。設定値を実績行へ入れると、
「実績を差し戻しでリセットしたら設定も消えた」という事故が起き得る。

### H（画面が `< 100` を判定する）の棄却理由

判定を画面へ書き込むと、**警告を出す場所が増えるたびに同じ条件が写経される**
（SC-02・SC-03・Discord の 3 か所）。1 か所でも写し間違えれば「下げたのに警告が出ない」状態になり、
それは**裁定が「記録に残ることを担保する」と求めたものの反対側**である。
[IADR-0154]（供給可否はサーバが宣言する）と同じ論法をここにも適用する。

## 決定

### 決定1: 収集間隔は**変更経路が存在しないこと**を構造テストで固定する

`CollectionIntervalNotConfigurableTests`（MarketMonitorService / InformationCollectionService の
両 Api.Tests）が、実 `Program.cs` の配線から `EndpointDataSource` を取り出し、次を検査する。

- **ルート表に間隔を示す語（`interval` / `poll`）を含むエンドポイントが 1 本も無いこと**
- **監視設定のドメイン型・要求 DTO に間隔を表すプロパティが無いこと**（型の上でも持たない）

「実装しない」を人の記憶ではなく**赤くなる仕掛け**に置き換える。
なお **`Monitor:PollIntervalSeconds` / `Collection:PollIntervalSeconds`（起動時構成）は残す** ——
裁定は「画面から変更しない・起動時構成とする」であり、構成そのものを取り上げてはいない。

### 決定2: 変動閾値・クールダウンの権威は MarketMonitorService のままとし、SC-02 が消費する

計画の旧記述（ConfigurationService 由来）は誤りであり、**裁定が実装側を追認した**。
SC-02 は監視銘柄（`/monitor/watchlist`）と同じ由来サービスを 1 画面で扱うことになり、
「どの銘柄を、どれだけ動いたら」が 1 か所に集まる。

**BFF に 4 本（`GET /settings`・`PUT /settings/movement-threshold`・`PUT /settings/cooldown`・
`GET /settings/history`）を登録する**（[IADR-0091](./IADR-0091_unit-owned-bff-endpoints.md) の
unit-owned BFF に追加する）。「フロントが叩かないため登録しない」という前提は #340 の時点で
崩れていた。**登録しないまま画面だけ移すと、移した先でも動かない。**

### 決定3: 全置換 `PUT /monitor/settings` を部分更新と同じ規律へ揃える

値域は `MonitorSettingsBounds`（単一情報源）を通し、**理由必須・履歴記録**にする。

**画面から使わない経路だからこそ塞ぐ。** 「画面では 0 を弾くが API 直叩きでは保存できる」状態は、
統制を画面の親切心に依存させることであり、[IADR-0141] 決定1 が退けた形そのものである。
これは [IADR-0155] 残余リスク 4 の解消でもある。

### 決定4: Stage 1 の最小取引件数は `RiskManagementSettings` に置き、判定の直前に重ねる

```
RiskManagementSettings.Stage1MinimumTradeCount（既定 100）
        ↓ StageGateService が読む
policy.Stage1Criteria with { MinimumTradeCount = 設定値 }
        ↓
StageGate.AssessPromotion / AssessWithdrawal / RequestTransition
```

他のリスク設定と**同じ経路**（`IRiskSettingsStore` の単一行 JSON ＋ `Version` 楽観排他、
`ISettingsChangeLog` への理由つき記録）に載せる。`SettingsChangeType` へ
`Stage1MinimumTradeCountChanged`（**序数 8・末尾追加**）を足す（序数不変の規律・[IADR-0134] 決定2）。

**条件 1（統制違反 0 件）・条件 2（60 営業日）・打ち切り（120 営業日）は設定にしない。**
裁定が「及ばない」「変わらない」と明示している。`Stage1GateCriteria` の他 2 項目は
`Stage1GateCriteria.Default` のままであり、**設定から書き換える経路を作らない**（構造で担保する）。

### 決定5: 値域は 1〜1000。**旧行・値域外は既定 100 へ落とす**（低い側へ落とさない）

`Stage1TradeCountBounds`（`RiskLimitBounds` / `MonitorSettingsBounds` と同じ扱い）。

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| 既定 | **100** | 06_daytrading-review §4.1 条件 3 |
| 下限 | **1**（含む） | 0 以下では条件 3 が無条件に成立し、**期間だけで昇格できてしまう** |
| 上限 | **1000**（含む） | §4.3 の「200〜500 件で確信が持てる」の上を十分に取った値。これを超えると Stage 1 が事実上終わらない |
| 統計的根拠の下限 | **100** | §4.3。**これを下回る設定は警告の対象**（拒否ではない） |

設定ストアの旧行（本項目を持たない）・`null`・値域外は**既定 100 へ落とす**。
[IADR-0161] の allow-list と同じ考え方だが、**倒す先は「安全側」＝厳しい側**である
（発注先では「外部へ発注しない値」、ここでは「合格に遠い値」）。**読めない行が緩い側へ倒れてはならない。**

### 決定6: 100 未満かどうかは**サーバが宣言する**（`Stage1GateCriteria.BelowStatisticalBasis`）

画面（SC-02・SC-03）と Discord の `/stage status` は**この宣言に従う**。閾値 100 を 3 か所へ写経しない。

**警告は設定を妨げない。** 100 未満の値でも `PUT` は 200 を返し、設定は保存され、履歴に残る。
裁定の「警告は設定を妨げない／下げた事実が記録に残ることを担保する」をそのまま実装した形である。
**「妨げない」ことも退行防止テストで固定する**——警告を足した後に「ついでに拒否する」実装へ
すり替わると、裁定に反する（利用者が下げられなくなる）。

### 決定7: 計上単位は**既存実装（[IADR-0149] 決定2）をそのまま用い、テストだけを足す**

`Stage1Aggregation.CountTrades` は `DecisionId` で畳み、`CountsAsTrade` は
`MoomooSimulate` かつ `PositionEffect.Open` だけを数える。**新しい計上経路を作らない。**

足すのは次の 3 点の退行防止テストである。

1. 1 注文が 3 回に分割約定しても 1 件（累積約定数のイベントを数えない）
2. 手仕舞い（`Close`）は数えない
3. 約定しなかった注文（`FilledQuantity <= 0`）は観測として記録されない

さらに **「設定値を 1〜1000 のどこに置いても上記が変わらない」**ことを固定する。
**設定化は「合格に必要な件数」を変えるだけであり、「1 件」の定義には触れない。**

## 理由

- **「実装しない」を構造で担保しないと、裁定は次の PR で消える。** 収集間隔は
  「未実装の項目」に見えるため、善意で実装される危険が最も高い。
- **設定化しても計上単位は変わらない**という不変条件を明示的に置くことで、
  「単位を緩めて件数を稼ぐ」経路（設定を下げるより発見しにくい）を塞ぐ。
- **警告の判定をサーバへ置く**ことで、表示面が増えても条件が 1 つに保たれる。
- **画面から使わない API も塞ぐ。** 統制は「画面が親切であること」に依存してはならない。

## 結果

- 良い影響:
  - 変動閾値・クールダウンが**監視銘柄と同じ画面・同じ由来サービス**に揃う。
  - `/monitor/settings*` が BFF に載り、**SC-02 から実際に到達できる**ようになる。
  - 全置換 PUT の抜け道（理由なし・値域なし）が塞がる。
  - 最小取引件数が**理由・前後値つきの履歴**に残る。下げた事実が監査で追える。
- 悪い影響・トレードオフ:
  - `StageGateService` が `IRiskSettingsStore` へ依存する（従来は方針 singleton のみ）。
    段階ゲートの判定 1 回につき設定を 1 回読むコストが増える（単一行の読み取り）。
  - SC-02 の節が 2 つ増える。**アクセシブル名の衝突**に注意が要る（本 PR で全名称を分離した）。
- **残余リスク（明記）**:
  1. **`Stage1GateCriteria` の 3 項目のうち 1 つだけが可変になった。** 残る 2 項目を
     設定化する変更が入ると裁定に反する。テストで「他 2 項目が既定のままであること」を固定した。
  2. **値域の上限 1000 は計画が与えた値である**（裁定が明示）。下限 1 は実装の判断である
     （計画は「1〜1000」と書くのみで理由を述べていない）。
  3. **収集間隔の構造テストは語（`interval` / `poll`）の一致に依存する。**
     別の語（例: `cadence`）でエンドポイントを足されると検出できない。
     型側の検査（設定型にプロパティを足さない）と二重にしているが、完全ではない。
  4. **Discord の警告は `/stage status` にしか出ない。** 昇格コマンド（`/stage promote`）の
     応答には出ない——遷移応答（`StageTransitionResultView`）が criteria を運ばないためである。
     承認前に `/stage status` を読む運用を前提にしている。
