## コンテキストと課題

計画は本統制の**値と選択規則**を確定した——閾値＝ 40% と規制要求の厳しい方、回復目標＝**閾値 + 5 ポイント**
（閾値に連動）、対象＝**必要証拠金の降順**、量＝**回復目標に達する最小限**、そして**利用者の承認も AI も
介在させない**こと。しかし、実装するには計画が言及していない 4 点を決める必要がある。

1. **維持率の算式**。計画は「維持率」を数値としてしか語らない（分子・分母を定義していない）
2. **建玉が複数あるときの適用閾値**。閾値は株価に依存する（`max($5.00 ÷ 株価, 30%)`）ため、
   建玉ごとに異なる値が出る。口座単位の判定にどれを使うか
3. **発動条件の等号**。「割り込む**前に**発動」（§5・FR-10）と「閾値に**接近**した場合」（UC-06）を
   機械的な不等式へ落とす必要がある。計画に「閾値 + α」の α は無い
4. **回復目標へ到達できない場合**（純資産が尽きている等）の振る舞い

さらに、維持率・純資産・必要証拠金の**供給元（ブローカー照会）は現時点で存在しない**（#342 の PoC 待ち）。
決済の実発注経路（#331）も無い。したがって「どこまでを本 issue で確定するか」も決める必要がある。

## 検討した選択肢

### 論点 A: 維持率の算式

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | **純資産 ÷ 建玉評価額の合計** | ADR-0016 決定7 の規制側「実効維持率 ＝ 維持証拠金 ÷ 株価」と**分母が揃う**（比較が同じ土俵で成立する）。米国信用口座の維持率の標準的な定義でもある |
| A-2 | 純資産 ÷ 必要証拠金の合計 | 「必要証拠金の降順＝回復効率が最も高い順」は厳密に成り立つが、閾値 40% が「必要証拠金の 40% しか純資産が無い」＝**既に破綻**を意味することになり、計画の閾値と矛盾する |
| A-3 | ブローカーが返す維持率をそのまま用いる（算式を持たない） | 決済**後**の維持率を予測できない。日報が要求する「決済前後の維持率」の後者が出せず、縮小量も決められない |

### 論点 B: 建玉が複数あるときの適用閾値

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | **建玉ごとの閾値のうち最も厳しいもの**（最大値） | FR-10 の「同一の注文に複数の上限が掛かる場合は常に厳しい方が効く」を口座単位へ素直に延長したもの。建玉 1 件なら `MaintenanceMarginThresholdFor(株価)` と**完全に一致**する |
| B-2 | 評価額で加重平均する | 規制の実効要求には近いが、計画に無い式を発明することになる。**緩む向き**の近似であり統制として不適 |
| B-3 | 自前の 40% だけを使う | $12.50 未満の銘柄で規制要求（40% 超）を下回る。ADR-0016 決定7 が明示的に禁じた誤り |

### 論点 C: 発動条件

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C-1 | 維持率 < 閾値（割り込んでから） | 「割り込む**前に**発動」（§5・FR-10 の原文）に反する |
| **C-2** | **維持率 ≦ 閾値**（閾値ちょうどで発動） | 割り込む直前の 1 点で動く。**計画に無い値を 1 つも足さない**唯一の読み方 |
| C-3 | 維持率 ≦ 閾値 + α（α は余裕） | 「接近」を数値化できるが、**α が計画のどこにも無い**。5pt は回復目標側に与えられた値であり、発動側へ流用すると閾値そのものを引き上げたのと同じになる |

## 決定

### 決定 1: 維持率 ＝ **純資産（日中の実測値）÷ 建玉評価額の合計**（案 A-1）

```csharp
MaintenanceMarginSnapshot { NetEquityUsd, Positions[] }   // Positions[i].MarketValueUsd = Quantity × PriceUsd
維持率 = NetEquityUsd / Σ MarketValueUsd
```

**`NetEquityUsd` は統制上限の基準 equity（`PortfolioSnapshot.Capital`）と別物である。**
[IADR-0130](IADR-0130_equity-ratio-risk-limits.md) 決定2 の equity は「前営業日終値時点・当日中は不変」であり、
日中の含み損益で上限が動かないようにするためにそう定めた。維持率は逆に**日中に動くこと自体が判定対象**である。
同じ名前の値だからと 1 つにまとめると、日中に維持率が落ちても判定が動かない（統制が沈黙する）。
**2 つの equity は意味も更新頻度も違う**ため、型も供給元も分ける。

`RequiredMarginUsd`（必要証拠金）は**ブローカー由来の実測値**とし、実装は推定しない。対象選択に用いる唯一の
量であり（UC-06）、実装が規制式から再計算すると、ブローカーの実際の要求と食い違ったまま「回復したつもり」に
なり得る。

### 決定 2: 適用閾値は**最も厳しい建玉のもの**（案 B-1）。回復目標はそれに **+5pt**（#329 の解決メソッドを消費）

```csharp
閾値   = positions.Max(p => limits.MaintenanceMarginThresholdFor(p.PriceUsd));
回復目標 = positions.Max(p => limits.MaintenanceRecoveryTargetFor(p.PriceUsd));   // = 閾値 + 5pt
```

閾値の計算を**再実装しない**（[IADR-0131](IADR-0131_short-selling-controls-fail-closed.md) が確定した
`ShortSellingLimits` の 2 メソッドだけを通す）。オフセットが定数であるため、上の 2 式は「閾値 + 5pt」と
常に一致する（プロパティテストで固定）。

**信用買い（`MarginLong`）の規制維持率を計画が定めていない**ため、空売り側の式をそのまま適用する。
安全側（過大な要求）であり統制として害が無いが、計画側の追認が要るため環流する。

### 決定 3: 発動条件は **維持率 ≦ 閾値**（案 C-2）。「接近」に α を発明しない

閾値ちょうどの時点はまだ「割り込んで」いない。この 1 点で動くことが、計画に無い数値を足さずに
「割り込む前に発動する」を満たす唯一の読み方である。**+5 ポイントは回復目標に与えられた値であって
発動条件ではない**（発動側へ流用すると、実質的に閾値を 45% へ引き上げたことになり ADR-0016 決定7 を
無断で改変する）。

なお #329 の**新規建て拒否**（`MaintenanceMarginBreach`）は `維持率 < 閾値` である。**非対称は意図的**
——拒否は「割り込んでいる注文を通さない」判定、自動縮小は「割り込む前に動く」判定であり、目的が異なる。

### 決定 4: 縮小量は「必要証拠金の降順に、回復目標へ届く**最小の株数**まで」

```
必要な評価額の削減 X = V − NetEquity / 回復目標
必要証拠金の降順に建玉をたどり、X を満たすまで決済する。最後の 1 件は ⌈残り ÷ 株価⌉ 株だけ決済する。
```

- **建玉 1 件を丸ごと閉じない**（計画が「建玉の粒度に縛られ、必要量に対して過剰にも過少にもなる」として棄却）。
  端株が無いため、株数の**切り上げ**が「目標に届く最小限」である。
- 整列の同値は**評価額の降順 → 銘柄コード → 市場**で決定的に解く。順序が入力の並び順に依存すると
  「入力が同じなら出力も同じ」（UC-06）が壊れる。
- **到達不能（純資産 ≦ 0 など）なら全量決済する。** 目標へ届かないからと何もしないのは、
  最も危険な状態で統制が沈黙することを意味する。建玉が無くなれば維持率の概念自体が消える（`null`）。

### 決定 5: 供給が無いときは**決済しない**。ただし「報告しなければ回避できる」経路は #329 と組で塞ぐ

供給元（`IMaintenanceMarginSnapshotSource`）が `null` を返す間、本統制は 1 株も決済しない。
**フェイルクローズの向きは統制ごとに違う**——[IADR-0131](IADR-0131_short-selling-controls-fail-closed.md) 決定4 の
「維持率が確認できないなら空売りを**積み増さない**」は安全側だが、「維持率が分からないから**とりあえず決済する**」は
安全側ではない（不可逆な損失を確定させる。UC-06 の比較表「誤作動時の害＝不可逆」）。

したがって迂回（「維持率を報告しなければ縮小されない」）は**縮小側では塞げない**。塞ぐのは**積み増し側**であり、
#329 が既に実装している。両者の組で「維持率が不明な口座は、縮小されないが増えもしない」状態に閉じる。
テストは両側を 1 つの事実として固定する（T-10-190）。

### 決定 6: 縮小は統制ストアを依存に持たない（ADR-0009 の構造的担保）

`MaintenanceMarginReductionService` は kill switch / 日次損失ロックアウト / 一時停止のいずれのストアも、
`RiskEvaluator`（発注前スクリーニング）も、LLM 関連の型も依存に持たない。UC-06 は
「3 統制のいずれかが成立していても自動縮小は動く」と明記しており、**依存が無いことが規則の実装**である
（[IADR-0117](IADR-0117_owner-position-close-path.md) の手仕舞い経路と同じ規律）。

### 決定 7: 記録は 1 つのイベントに集約し、4 記録先はそれを写像する

`MaintenanceMarginReductionExecuted` が日報の表の**7 列すべて**（時刻・決済前の維持率・閾値・回復目標・
決済した建玉〔銘柄・方向・数量・必要証拠金〕・決済後の維持率）を持つ。監査ログ・Discord・日報・月報は
このイベントだけを見る。**記録先ごとに別の情報源を持たない**（同じ発動が記録先ごとに違う値で残ると、
「規則どおりに作動したか」を人が事後に検証できるという記録の目的〔04_report-templates〕が壊れる）。

日報・月報では**「なし」「0 件」と「照会できなかった」を区別する**（計画が「空欄と「なし」を区別する」と
明記した理由と同じ。照会失敗を「なし」と書くと、発動を隠したのと同じ結果になる）。

### 決定 8: 値として成立しない建玉を含むスナップショットは**全体を信頼せず**決済しない。ただし黙って止まらない

株価・数量が **0 以下**、または必要証拠金が**負**の建玉が 1 件でもあれば、`MaintenanceMarginReducer.Plan` は
`null` を返す（決済しない）。`MaintenanceMarginReductionService` はこれを
**`SnapshotUntrusted`**（健全ゆえの無動作 `NoActionRequired` とは別の状態）として返し、**警告ログを残す**。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| 8-1 | 該当建玉だけを除いて残りで評価する | **採らない。** 除くと分母（建玉評価額の合計）が縮んで**維持率が実際より良く見え**、過少縮小へ倒れる。統制として危険な向きである |
| 8-2 | 何もしない（現状の閾値算出が投げる例外のまま） | **採らない。** 定期評価ドライバ（#331）で未処理例外が上がると**評価ループごと死ぬ**・ログを埋める。結果は決定5（供給が無ければ決済しない）と同じに見えるが、**片方は設計・片方は事故**であり経路として別物である |
| 8-3 | 決済せず、拒否を無動作と区別できる形で返し、警告を残す | **採る。** 株価 0 以下は市場価格として成立せず、**フィードが壊れている証拠**である。壊れたデータで建玉を決済する方が、しないことより危険である |

**「黙って何もしない」にしないことが要点である。** 統制が実質オフラインなのに誰も気づかない状態を作らない。
記録の出し方は既存の 4 記録先（決定7）を増やさず、次の 2 つに留める——**新しいイベント種別を作らない**
（計画に無い記録種別の発明になる）／**ログだけにもしない**（呼び出し側が「健全」と「盲目」を区別できない）。

1. 戻り値の状態 `MaintenanceMarginEvaluationStatus.SnapshotUntrusted`（#331 のドライバが利用者へ届ける）
2. 警告ログ（壊れた建玉の銘柄と件数・「統制が働いていません」の明示）

なお `MaintenanceMarginThresholdFor` は非正の株価に対して**例外を投げる**（`ThrowIfNegativeOrZero`）。
入口の検査はその例外を未然に断つものであり、「弾く」と「例外で中断する」を混同しないこと
（初版のコード注釈がこれを取り違えていた。#330 のレビュー指摘）。

## 理由

- 決定1: 分母を建玉評価額に取ることで、ADR-0016 決定7 の表（株価と実効維持率の対応）がそのまま口座単位の
  判定に接続する。案 A-2 は「必要証拠金の降順＝回復効率最大」を厳密にするが、計画が与えた閾値 40% の意味を
  壊す。**規則の順序（計画が確定した対象選択）に合わせて算式を選ぶのは本末転倒**であり、算式は計画の閾値の
  定義に合わせる。案 A-1 でも必要証拠金は評価額に概ね比例するため、降順の選択は回復効率の高い順に近い。
- 決定3: 「接近」を数値化する誘惑を退けた。α を置けば必ず「いくつか」を発明することになり、
  それは ADR-0016 決定7 の閾値を実質的に書き換える。
- 決定4: 切り上げの選択は「最小限」の唯一の機械的な解である。切り捨てると目標に届かず（過少）、
  1 件丸ごとだと過剰になる。どちらも計画が名指しで棄却した失敗である。
- 決定5: 統制の縮退方向は「安全側」で決まるが、**何が安全側かは統制の作用で変わる**。止める統制は
  「止める」が安全側、動かす統制は「動かない」が安全側である（UC-06 の 2 統制比較表）。
- 決定8: 供給元が実ブローカー照会に繋がる（#331 / #342）と、低ティアのデータソースでは 0 や欠損値が
  現実に混ざる。**壊れた入力の扱いを決めていない統制は、壊れた入力が来た日に初めて挙動が決まる**。
  除外案（8-1）を退けたのは、それが「安全側に見えて実は緩む」典型だからである——1 件除くだけで
  分母が縮み、同じ口座がより健全に見え、必要な決済が起きない。

## 結果

- 良い影響:
  - 縮小量・対象・発動条件が**純関数**（`MaintenanceMarginReducer.Plan`）に閉じ、同じ入力から常に同じ
    出力が出る（UC-06 の「完全に機械的」を機械的に検証できる）
  - 閾値・回復目標の計算が #329 の 2 メソッドに一元化されたまま増えない（値の二重定義が起きない）
  - 1 回の発動が 4 記録先すべてに同じ値で残り、「知らないうちに建玉が減っていた」状態を防ぐ
  - 統制ストア・LLM への依存が無いため、3 統制が成立していても縮小が動く（ADR-0009 の不変条件）
- 悪い影響・トレードオフ:
  - **供給元が無いため、現状は 1 度も発動しない**（維持率・純資産・必要証拠金の取得経路が未実装）。
    Stage 1（SIMULATE）は維持率 50% が強制されるため 40% に到達せず、実弾での検証は Stage 3 以降になる
    （ADR-0016 決定14 の表と同じ制約）
  - 定期評価のドライバ（常駐）を置いていない。供給元と同時に置くのが正しい（#331 / #342）
  - 日報・月報のデータ供給は no-op（空列＝「なし」）である。**現時点で発動があり得ないため「なし」は
    事実として正しい**が、供給元が入った時点で照会経路の結線が要る（#331）
  - 信用買いの規制維持率を空売りの式で代用している（安全側・環流済み）
  - **壊れた値が 1 件でも混じると統制全体が止まる**（決定8）。健全な建玉ぶんも評価されないため、
    フィードの品質が悪い供給元では統制が働かない時間が生じ得る。この状態は `SnapshotUntrusted` と
    警告ログで観測できるが、**利用者へ届けるのは #331 のドライバの責務**である（本 issue の範囲外）
