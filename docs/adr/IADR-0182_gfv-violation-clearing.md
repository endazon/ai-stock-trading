# IADR-0182: GFV 違反による停止の解除（記録は消さず解除を追記する）

## 背景

計画 **[ADR-0028](../../planning/projects/ai-stock-trading/07_adr/ADR-0028_gfv-violation-clearing-and-reconciliation.md)**
（2026-08-07 Accepted・質問票 第15回 Q10/Q11・環流 project-planning#251）が空白を埋めた。

| # | 決定 | 本作業 |
| --- | --- | --- |
| 1 | **GFV 違反記録は失効させない**（期間経過で消えない） | [IADR-0165](IADR-0165_gfv-self-counting-and-settled-cash-source-ban.md) 決定4 の**追認**。変更しない |
| 2 | **停止は利用者の明示的な操作でのみ解除する。** 原因の是正の確認を伴い、**誰が・いつ・どの記録に対して**を監査ログへ | **本作業の主対象** |
| 3 | **解除の窓口は Discord Bot。** 画面（SC-02 / SC-03）からは解除できない | **本作業の主対象** |
| 4 | ブローカー表示との突合の頻度 | **対象外**（現金口座の運用開始時に定める。対象そのものが存在しない） |

実測（2026-08-08）: `IGoodFaithViolationStore` は追記専用（`Append` / `GetTally` / `GetRecordedBetween`）で
**解除の口が無く**、`BotCommandParser` にも解除コマンドが無かった。
**したがって原因を是正しても停止状態を解けなかった**（project-planning#251 が指摘した空白）。

**なお本計数が数えているのは「自らのガードの失敗回数」であり、ブローカーの GFV 件数ではない**
（ADR-0025 §理由）。ガードが正しく働けば 0 のままであり、**1 件出た時点で人が原因を調べるべき事象**である。

## 決定

### 決定1: 解除は「違反記録ごとの解除行の追記」で表す（記録を消さない・更新しない）

決定1（失効させない）があるため、**台帳から行を消す／更新するのは規約違反**である。
別テーブル `good_faith_violation_clearances` へ**解除行を追記**する。

- **主キーは解除対象の `OrderId`**（＝違反記録の計上単位）。これにより
  「**どの記録に対して**解除したか」（決定2 の要求）が構造的に表現され、**二重解除で冪等**になる。
- `GetTally()` は**解除されていない**違反記録の件数を返す。`GetRecordedBetween` は**解除の有無に
  関わらず全件**を返す ——「**数えないこと**」と「**消すこと**」は別である。

### 決定2: 解除は既存の破壊的統制操作と**同じ確認水準**に揃える

ADR-0028 §結果 が「**解除操作そのものが新たな攻撃面・誤操作面になる**」と明記している。
kill switch（[IADR-0062](IADR-0062_discord-bot-gateway-and-authorization.md) / [IADR-0097](IADR-0097_killswitch-disengage-confirmation-phrase.md)）と同型の閂を置く。

| 閂 | 内容 |
| --- | --- |
| 1 | **多層認証**（DM 拒否・サーバー・チャンネル・許可リスト・Keycloak マッピング）。**空設定は全拒否** |
| 2 | **確認ボタン**（Gateway が担う） |
| 3 | **確認フレーズ**の一致。**未設定・不一致・未入力は Risk を呼ばず拒否**する |
| 4 | **理由必須**（決定2 の「原因の是正が済んでいることの確認」の実装） |
| 5 | 認可は **OwnerOnly**（trading-owner）。s2s トークンでは 403 |

**確認フレーズは kill switch と同じ設定値を用いる。** 解除専用のフレーズを設ける根拠が計画に無く、
**設定点を増やすと設定漏れの面が増える**（閂 3 は「未設定なら拒否」であるため、増やした設定点の
漏れがそのまま拒否＝運用の詰まりになる）。

### 決定3: 対象を利用者に選ばせず、**現在解除されていない全件**を解除する

決定2 の解除は「原因を調べて是正した」ことの表明であり、**一部だけ解いて残りを止めたままにする
運用上の意味が無い**。どの記録を解除したかは記録する（決定2 の「どの記録に対して」）。

**解除対象が 0 件のとき成功に見せない**（422）。「解除した」と記録すると、
**実際には何も起きていない操作が監査上の事実になる**。

### 決定4: 監査へは「誰が・いつ・どの記録に対して」＋**残件数**を残す

新イベント `GoodFaithViolationsCleared`（`ClearedBy` / `Reason` / `ClearedOrderIds` /
`RemainingCount` / `ClearedAt`）を発行し、監査サービスが集約する（[IADR-0082](IADR-0082_stage-transitioned-bus-audit.md) と同型）。

**`RemainingCount` を載せる。** 解除の最中に新たな違反が計上され得るため 0 とは限らず、
**「解除したのに止まったまま」を監査と利用者応答の双方から説明できる**ようにする。

**要約に「解除しました」だけを書かない。** 解けたのは**停止**であって記録ではない ——
監査を読む者が「記録が消えた」と誤読すると、次に同じ原因が起きたときの調査の起点が失われる。

### 決定5: 解除の理由は**利用者に入力させる**（定型文で埋めない）

ADR-0028 §理由 は決定2 の根拠として「**解除の記録が監査ログに残ることで、後から「なぜ解除したか」を
追える**」を挙げている。**決定3 により Discord が唯一の窓口である**ため、理由を定型文で埋めると

- **全解除の理由が同一文字列になり**、「なぜ」は監査から復元できない（残るのは「解除者が
  『確認済み』と自称した」ことだけ）、
- Risk 側の理由必須チェックも常に非空の定型文では発火せず、**実質的に無効化される**。

よって確認モーダルへ**理由の入力欄（必須）**を置き、ハンドラでも空を拒否する（**Risk を呼ばない**）。
操作者と経路は理由へ添える（監査の「誰が」を理由文からも辿れるようにする）。

### 決定6: 多層認証は**スラッシュコマンドの段階**でも掛ける

`/killswitch`・`/pause`・`/stage` はいずれも slash 受信時に `DiscordCommandAuthorizer.Authorize` を呼び、
**許可外へはボタンすら出さない**。GFV 解除だけこれを欠くと、統制自体は解けない（ハンドラの閂1 が
拒否する）ものの、**破壊的操作の窓口を許可外へ露出する**点で既存水準から落ちる。
ADR-0028 §結果 が求める「既存の破壊的統制操作と同じ権限管理の下に置く」に揃える。

## 🔴 やらないこと（issue / ADR-0028 の明示）

- **未供給時の fail-closed を緩めること。** ADR-0028 が明記: 決定2 の解除は**記録が積まれた場合**の
  解除であり、**供給が無い場合の拒否を解除する手段ではない**。
  本サービスは件数にしか作用せず、`GetTally()` が `null` になる経路（ストアが判定コアへ結線されて
  いない）には触れない —— **構造的にそうなっている**（テストで固定した）。
- **画面からの解除**（決定3）。SC-02 / SC-03 に解除の口を作らない。**BFF / フロントに経路を足さない**
  ことをもって満たす（エンドポイントを OwnerOnly に置くだけでは足りない——画面も owner で叩ける）。
- **ブローカー表示との突合の頻度の実装**（決定4。現金口座は ADR-0025 決定3 により選べず、対象が存在しない）。
- **違反記録の削除・更新**（決定1）。

## 検討したが採らなかった案

| 案 | 却下の理由 |
| --- | --- |
| 失効期間を設ける（12 か月のローリング窓等） | **ADR-0028 決定1 が明示的に棄却**。本計数は「自らのガードの失敗回数」であり、**時間の経過はガードの欠陥を直さない** |
| 台帳の行を削除／更新して解除する | 決定1（失効させない）に反する。発生の証跡（FR-11）が失われる |
| 解除対象を利用者に選ばせる | 一部だけ解く運用上の意味が無い。UI の複雑さと誤操作面だけが増える（決定3） |
| 解除対象 0 件でも 200 を返す | **何も起きていない操作が監査上の事実になる**（決定3） |
| 解除専用の確認フレーズを設ける | 設定点が増え、**設定漏れ＝拒否**の面が広がる。計画に根拠も無い（決定2） |
| 解除の理由を定型文で埋める（利用者に書かせない） | **決定3 により Discord が唯一の窓口**であるため、全解除の理由が同一文字列になり ADR-0028 §理由 の「なぜ解除したか を追える」が満たせない（決定5） |
| 多層認証をハンドラ側だけに置く | 統制は解けないが、**許可外の利用者へ Danger ボタンと確認モーダルが提示される**。既存 3 コマンドの水準から落ちる（決定6） |
| 画面（SC-03）にも解除を置く | 決定3 が Discord Bot へ一元化している。SC-03 は参照専用 |
| 解除を kill switch の解除で兼ねる | 別の統制であり、GFV の停止は kill switch とは独立に成立する |

## 対照実験（実走した実測）

| 壊した箇所 | 赤くなったテスト | 読み取れること |
| --- | --- | --- |
| 解除を「解除行の追記」→「**記録の削除**」へ | **2 件**（`解除しても違反記録そのものは台帳に残る` / `同じ記録を二重に解除しても件数が狂わない`） | 決定1 の「消さない」は load-bearing であり、削除に変えると即座に検知される |
| 確認フレーズの検証を外す | **4 件**（不一致 3 パターン＋未設定） | 閂 3 は load-bearing。**Risk を呼ぶ前に**拒否している |
| 理由必須のガードを外す | **3 件**（空・空白のみ・未指定） | 決定5 の閂 4 は load-bearing |

**決定5・決定6 は監査（`adr-guardian`）の指摘で足した。** 初版は理由を定型文で埋めており、
**Discord が唯一の窓口である以上すべての解除の理由が同一文字列になる**——ADR-0028 §理由 が
決定2 の根拠に挙げた「なぜ解除したかを追える」が実質的に成立していなかった。
また `/gfv` だけ slash 段階の認証を欠いていた。

## 影響

- **新規テーブル 1 つ**（`good_faith_violation_clearances`・Migration `AddGoodFaithViolationClearances`）。
  既存テーブルは不変（**違反記録の行は一切触らない**）。
- **新規イベント 1 つ**（`GoodFaithViolationsCleared`）。`event-schemas.baseline.json` を再生成し、
  URN 固定の母集合（`EventMessageTypeNameTests`）へも登録した。
- **新規エンドポイント 1 つ**（OwnerOnly）。**読み取り系（OwnerOrService）には置かない。**
- Discord に `/gfv clear` を追加（副コマンドは `clear` の 1 つに絞る＝暗黙に別の操作が生えない）。

## 残余リスク

- **解除は「現在解除されていない全件」を対象とする**（決定3）。解除操作と新たな違反の計上が競合すると、
  直後に計上された違反は解除されずに残る。**`RemainingCount` がそれを可視化する**が、
  利用者は「解除したのに止まったまま」を一度は見ることになる。
- **確認フレーズを kill switch と共有している**（決定2）。フレーズが漏れた場合、
  kill switch と GFV 解除の双方が同時に危険に晒される。多層認証（閂 1）と OwnerOnly（閂 5）が
  残るため単独では突破できないが、**独立性は無い**。
- **ブローカー側が先に 3 回目を計上した場合を本作業は防げない**（ADR-0028 §結果 が明記。
  気づく手段はアプリの目視のままであり、決定4 の突合手順は現金口座の運用開始時に定まる）。
- **07_discord-bot-design への反映は計画側の作業である**（ADR-0028 フォローアップ 1）。
  本 ADR はコマンド名・引数・確認フローを実装側の決定として記録するにとどまる。
