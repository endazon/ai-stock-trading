## コンテキストと課題

[ADR-0016](../../planning/projects/ai-stock-trading/07_adr/ADR-0016_short-selling-staged-release.md) 決定15 は SC-03 と報告書へ「借株料の累計」の表示を求めていたが、
**その値をどう作るかを定めた記述が計画のどこにも無かった**。表示と報告だけが要求され、**入力を作る要件が欠けていた**。

ADR-0027 が 5 点（計上のタイミング・単位・期間の境界・料率変動・供給元）を確定させ、
**「実装は記録側を先行して設計してよい」**（§結果）と明記した。実装の現状は以下である（実測 2026-08-13・`develop` = `1cb19c4`）。

- **累計を保持する型・ストア・イベントがコード全体に存在しない。**
- SC-03 は `BorrowFeeAvailability: NotSupplied` を返す（IADR-0154）。**値を発明していないことは正しい**が、決定15 は未達である。

決めるべきことは 3 つある。

1. **「建玉ごと」を本リポジトリの何に写像するか**（建玉の一次識別子）。
2. **「0 として積まない」をどう担保するか**（値の検査か、型・スキーマか）。
3. **PoC 項目 9 の成立前に「供給が始まらないこと」をどう担保するか。**

## 検討した選択肢

### 論点 A: 「0 として積まない」の担保（決定4）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | 1 つの型・1 つのテーブルに `decimal? AmountUsd`（null＝未供給）で持つ | 行数は減るが、**`Sum()` が null を 0 として畳む経路が自然に書ける**。禁じられた向きが型・スキーマの上で表現可能なまま残り、**値のテストでしか守れない** |
| **A-2** | **「計上できた日」と「取得できなかった日」を別の型・別テーブルにする** | **未供給の行は金額の欄そのものを持たない**ため、「0 として積む」コードが**書けない**。IADR-0181 が観測の到達を推定台帳と分けたのと同じ構図 |
| A-3 | 未供給を記録しない（行が無い＝未供給） | **「保有していなかった日」と「料率が取れなかった日」が区別できない**。決定4 が求める「未供給の日数の併記」が成立しない |

### 論点 B: 供給開始の遮断（決定6）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | 料率の供給元（`TrdGetMarginRatio` 照会）ごと実装し、設定フラグで止める | **フラグは外れる。** 「実装は入ったが設定点が無く全構成で不活性」の逆——**設定を入れた瞬間に単位未確定の値が積まれる** |
| **B-2** | **供給元を実装しない。** 料率は引数で受けるだけにし、結線が生えたら赤くなる構造テストを置く | 単位が確定するまで**積みようがない**。IADR-0158 決定3 と同型であり、本リポジトリの既定の作法である |

## 決定

### 決定1: 計上の単位は「建玉 × 取引日」の 1 行とし、合計は**導出**でしか得られない形にする（決定1・決定2）

**主キーは (Symbol, Market, TradingDay)。** 本リポジトリの建玉は符号付き在庫の射影（`PortfolioProjection`）で
(Symbol, Market) ごとに畳まれており、**建玉の一次識別子はこの組である**。

- 銘柄別・口座全体・月次の値は**すべて日次行の合算で導出する**（`SummarizeAccount` / `SummarizePosition` / `SummarizeByPosition`）。
  **別々に積むストア・列を作らない** —— 供給元が 2 つになれば必ず食い違う（IADR-0148 決定2 / IADR-0149 決定3 と同じ規律）。
- 主キーにより**同じ日を二度計上しても金額が狂わない**（冪等）。**2 度目はイベントも出さない** ——
  出すと監査の日次内訳が同じ日について 2 行になり、内訳から累計を再現できなくなる。
- **既存行は書き換えない。** 後から別の料率で上書きすると、監査へ残した内訳と台帳が食い違う。

### 決定2: 「計上できた日」と「料率が取れなかった日」を**別の型・別テーブル・別イベント**で持つ（案 A-2）

| 事実 | 型 | テーブル | イベント |
| --- | --- | --- | --- |
| その日の借株料を計上した | `BorrowFeeAccrual`（`AmountUsd` 非 null） | `borrow_fee_accruals` | `BorrowFeeAccrued` |
| **料率が取得できなかった** | `BorrowFeeUnavailableDay`（**金額の欄が無い**） | `borrow_fee_unavailable_days` | `BorrowFeeAccrualUnavailable` |

**未供給の側は金額を表現できない。** ADR-0027 決定4 が禁じた「0 として積む」は、
値の検査ではなく**型とスキーマ**で不可能にする。

> **なぜここまでするか。** 0 を積むと「その日は費用が発生しなかった」と読め、
> **Stage 1 の「借株料は 1 円も掛かっていない」という誤読が構造的に起こる**（ADR-0027 §結果 が明示した失敗）。
> これは「値が違う」ではなく「**別の事実が同じ形で記録される**」ことによる誤読であり、後から区別できない。

### 決定3: 累計の照会は**必ず未供給の日数を伴う**（金額だけを返す集計 API を作らない）

集計の戻り値は `BorrowFeeAccrualSummary`（金額・計上日数・**未供給日数**）の 1 種類とし、
**`decimal` を単独で返す公開メソッドを置かない**（T-10-273 が公開面の戻り値型で固定する）。

issue #465 の受け入れ基準「**未供給の日がある期間の累計が、未供給の日数を伴わずに表示されない**」は、
値のテストでは守れない —— **新しい集計 API が 1 つ生えれば破れる**。型で守る。

### 決定4: 期間は必須引数とし、「全期間の合計」という入口を作らない（決定3）

**按分しないこと**は、期間で行を絞り込むだけという形で満たす（各日の計上額はその計上日が属する日・月に帰属する）。

- **生涯累計と月次合計は別の値である。** SC-03 が表示するのは建玉の生涯累計、月報が載せるのは当月分の合計であり、
  **同じ語で呼ばない**（決定3 の明示）。実装では**同じ導出の引数違い**として表す。
- 集計器は期間を必須引数に取る。**口座全体の生涯累計は計画が定義していない**ため、その入口を作らない
  （作れば「何を意味するか誰も答えられない値」が生まれる —— ADR-0027 が塞いだものそのもの）。

### 決定5: 日次の計上額を監査へ残す。要約は「0 円」と「取れなかった」を書き分ける（決定1・決定4）

ADR-0027 決定1: 「**日次の計上額は監査ログへ残す。累計だけを保持すると、後から日別の内訳を復元できない。**」

- `BorrowFeeAccrued` の要約に**計上日の料率**を出す —— 建玉時の料率で固定していないことの証跡になる。
- `BorrowFeeAccrualUnavailable` の要約に「**0 円ではありません（費用は発生しています）**」と明記する。
  **監査を読む者が「その日は費用が発生しなかった」と誤読しないため**であり、決定2 の型の分離を文面でも守る。
- 相関は銘柄で束ねる（`borrow-fee:{Symbol}:{Market}`）。建玉ごとに日次の内訳を辿れる。

### 決定6: 🔴 **供給は開始しない**（案 B-2。ADR-0027 決定6）

**`ShortFeeRate` の単位が確定しなければ累計の値そのものが定まらない。単位を取り違えると累計は 100 倍ずれる。**

| 経路 | 遮断の手段 |
| --- | --- |
| 料率の写像 | **日次の料率照会を実装しない。** 計上サービスは料率を**引数**で受けるだけで、供給元を依存に持たない |
| DI | **スケジューラも料率供給元も登録しない**（`Program.cs` にコメントで意図を明記。#331 / #342 の範囲） |
| SC-03 | `ShortSellingStatusService` に**結線しない**。`BorrowFeeAvailability` は `NotSupplied` のまま |
| 構造テスト | **T-10-275**（計上の公開面に `ShortFeeRate` が生えたら赤）・**T-10-276**（SC-03 の依存に累計ストアが現れたら赤） |

**これは「実装漏れ」ではなく意図した遮断である。** 記録側だけが入っている状態は ADR-0027 §結果 が明示した進め方である。

## 対照実験（実走した実測）

| 壊した箇所 | 赤くなったテスト |
| --- | --- |
| 未供給の日を**「0 円の計上」として積む**（決定4 が禁じた向き） | **1 件**（T-10-272 `料率が取得できなかった日は0として積まれず未供給として記録される`） |
| 料率を**建玉の最初の計上の値で固定**する（決定4 が棄却した案） | **1 件**（T-10-271 `計上日の料率で評価される`） |
| **SC-03 の集約へ累計ストアを結線**する（＝供給の開始） | **1 件**（T-10-276 `SC03の集約は累計ストアを依存に持たない`） |
| 集計から**期間の絞り込みを外す**（月次合計＝生涯累計になる） | **1 件**（T-10-274 `月をまたぐ建玉を按分せず生涯累計と月次合計が別の値として取れる`） |
| 計上の型へ **`ShortFeeRate` を写像**する（決定6 が禁じた向き） | **1 件**（T-10-275 `計上の公開面に単位未確定のShortFeeRateが現れない`） |

## 影響

- 肯定的:
  - ADR-0016 決定15 の「借株料の累計」「借株コスト」「借株コストの月次合計」に対応する**型・ストア・イベントが存在するようになった**。単位が確定した日に、供給側（日次の料率照会）だけを足せば動く。
  - **「0 として積む」がスキーマ上書けない**ため、決定4 の禁止事項が実装の寿命を通じて守られる。
  - **日次の内訳が監査に残る**ため、累計から日別へ遡れる（決定1）。
- 否定的 / トレードオフ:
  - **テーブルが 2 つに増える**（計上・未供給）。行数は増えるが、区別を失わないための代償である。
  - **記録側だけが入り、動いていない期間が続く。** `docs/blocked-tasks.md` の「実装済みだが発動しない機能」へ登録して可視化する。

## 残余リスク

- **EF ストアの広域 `catch (DbUpdateException)`** は、主キー衝突（＝別レプリカが同じ建玉・同じ日を先に書いた＝目的達成）と
  **真の書き込み失敗を区別しない**（既存ストアと同じパターンの踏襲）。倒れる向きは「**その日は計上されていない**」であり、
  集計はその日を計上日数にも**未供給日数にも数えない** —— 合計が実費より**小さく**出る側である。
  🔴 **「計上に失敗した日が未供給として残る」保証は無い**（未供給の記録は別経路のため）。供給の開始時（PoC 項目 9 成立後）に、
  計上失敗を未供給として記録し直す経路の要否を判断する。
- **金額を丸めていない。** 丸め規則は計画のどこにも無く、実装が発明すると「表示されている数字が何を意味するか誰も答えられない」
  状態（ADR-0027 が塞いだもの）へ戻る。表示・報告の丸めは供給の開始時に計画へ確認する。
- **建玉の識別子が (銘柄, 市場) である**ため、**同じ銘柄を決済して建て直した場合、日次行は同じ鍵空間に並ぶ**。
  生涯累計は「建て日以降」を期間で切って求めるため誤らないが、**建て日を与える側（SC-03 の結線・#470 系）の責務**である。
- **祝日を含む営業日暦がまだ無い**（[#407](https://github.com/endazon/ai-stock-trading/issues/407)）。ただし借株料は**暦日**で発生する
  （分母 365）ため、本 IADR の計上は営業日暦に依存しない。
