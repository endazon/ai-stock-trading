# IADR-0110: Stage 0 の最小試行数を 1 → 20 へ較正する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-07-28
- 決定者: endazon（利用者・マージ判断）/ Claude Code（起案）

## 起点・関連

- 関連する計画書 ID: FR-15（バックテスト＝Stage 0 の前提）、FR-20（段階ゲート）、
  [ADR-0008](../../planning/projects/ai-stock-trading/07_adr/ADR-0008_staged-gates-and-backtest.md)（段階ゲートとバックテスト）、

- 関連する実装仕様書: [20260728_stage0-criteria-calibration](../specs/20260728_stage0-criteria-calibration.md)
- 関連 IADR: [IADR-0044](IADR-0044_overfitting-correction.md)（DSR/PBO の実装）、

## 背景・課題

`Stage0GateCriteria.Default.MinTrials` は IADR-0045 が「較正前の暫定値」と明記したまま **1** で残っていた。
これは単なる未調整ではなく、**ADR-0008 が要求する多重検定補正を無効化する**設定である。

`DeflatedSharpeRatio.ExpectedMaxSharpe(variance, trials)` は `trials < 2` で **0 を返す**。つまり台帳に 1 件しか
記録が無いと補正項 SR0 が恒等的に消え、DSR は素の probabilistic Sharpe へ退化する。「多数の戦略候補を試すこと
自体が過剰適合を必然にする」（06_daytrading-review §3.2）という前提に対し、**探索を過少申告すれば補正を回避できる**
状態だった。

較正には本来「実データでの水準確認」も要るが、着手時に **Stooq がプログラムからの取得に対して
JavaScript proof-of-work のボット検知チャレンジ（HTTP 200・CSV ではない）を返す**ことを実測で確認した
（`stooq.com` / `stooq.pl` の双方、正直な識別用 User-Agent でも同じ）。**チャレンジの回避は行わない**方針のため、
実データ取得はこの回では成立しない。他の keyless な日足 OHLC 源は計画書の情報源一覧に無い。

## 決定

### 1. `MinTrials` を 1 → 20 とする

較正は**決定論モンテカルロ**で行った（種 20260728 固定・splitmix64 ＋ Box-Muller・標本長 252 営業日・
DSR 閾値 0.95・反復 20,000）。真のエッジ 0 の候補を探索し、台帳へ記録する件数だけを変えて偽陽性率を測る。
再生成は `STAGE0_CALIBRATION_REPORT=1` で `Stage0CalibrationReportTests` を実行する（既定スキップ・CI 対象外）。

**表 1: 探索候補数 N と偽陽性率（DSR ≥ 0.95 を真のエッジ 0 が通す割合）**

| 探索候補数 N | 記録 1 件（過少申告） | N 件を正直に記録 |
| --- | --- | --- |
| 1 | 5.06% | 5.06% |
| 2 | 9.80% | 1.93% |
| 5 | 22.76% | 0.10% |
| 10 | 40.59% | 0.06% |
| 20 | 63.94% | 0.09% |
| 50 | 92.04% | 0.08% |
| 100 | 99.38% | 0.09% |
| 200 | 100.00% | 0.08% |

正直に記録すれば補正は機能する（探索を広げても 0.1% 前後）。壊れるのは**記録しなかったとき**である。

**表 2: 200 候補を探索し一部だけ記録した場合の偽陽性率（下限が被害をどこまで抑えるか）**

| 記録試行数 | 偽陽性率 |
| --- | --- |
| 1 | 100.00% |
| 2 | 57.20% |
| 5 | 3.76% |
| 10 | 1.07% |
| **20** | **0.62%** |
| 50 | 0.39% |
| 100 | 0.19% |
| 200 | 0.08% |

**表 3: 補正項 SR0 の推定ばらつき（正直に記録・反復 5,000）**

| 記録試行数 N | SR0 平均 | 標準偏差 | 変動係数 |
| --- | --- | --- | --- |
| 2 | 0.0260 | 0.0197 | 75.9% |
| 5 | 0.0709 | 0.0254 | 35.9% |
| 10 | 0.0967 | 0.0235 | 24.3% |
| **20** | **0.1188** | **0.0193** | **16.3%** |
| 50 | 0.1432 | 0.0146 | 10.2% |
| 100 | 0.1595 | 0.0115 | 7.2% |
| 200 | 0.1747 | 0.0088 | 5.0% |

**20 を選ぶ理由**（2 つの基準の交点）:

- **被害の上限**（表 2）: 200 候補という現実的に大きい探索を下限ぎりぎりまで過少申告しても偽陽性率 0.62%＝
  単一試行を正直に記録したときの名目 5.06% より一桁低い。2 件（57.20%）・5 件（3.76%）では足りない。
- **補正の安定**（表 3）: 「補正が計算できる」（N≥2）と「補正が信頼できる」は別。変動係数は N=2 で 75.9% と
  推定が暴れるが、N=20 で 16.3% まで収まる。20 を超えても改善は逓減する（50 で 10.2%）一方、
  下限を上げるほど「候補を N 件以上記録する」運用負荷が増える。

### 2. `MinDeflatedSharpe` は 0.95 のまま据え置く

表 1 の「N=1・正直に記録」列が 5.06% であり、DSR = 0.95 が意図どおり**名目 5% 水準**として機能している
（真のエッジ 0 に対する合格率）。理論値と一致するため調整の必要が無い。

### 3. `MaxProbabilityOfOverfitting` は 0.50 のまま据え置く（厳格化を見送る）

真のエッジ 0 の性能行列（戦略 10・区間 8・分割 8・区間長 63・反復 2,000）で PBO は
**平均 0.5055 / 中央値 0.5000** に集まる。すなわち閾値 0.50 は**雑音の中心そのもの**で、この条件単独では
雑音の約半分を通す。ここまでは「厳格化すべき」に見える。

しかし対照として戦略 0 に年率 Sharpe 1.0 のエッジを注入すると、識別力が乏しいことが分かる。

| PBO 閾値 | 雑音が通る割合 | 既知エッジ（年率 SR 1.0）が通る割合 |
| --- | --- | --- |
| ≤ 0.50 | 51.15% | 65.05% |
| ≤ 0.40 | 35.00% | 50.00% |
| ≤ 0.30 | 22.80% | 37.85% |
| ≤ 0.25 | 16.20% | 28.20% |
| ≤ 0.20 | 11.70% | 22.20% |
| ≤ 0.10 | 3.85% | 8.75% |

厳格化しても**雑音と既知エッジがほぼ同じ比率で落ちる**（比は 1.27 → 2.27 にしか改善しない）。この設定での
PBO 単独の識別力は弱く、閾値を下げることは主として偽陰性を増やす。**実データで偽陰性の代償を測れるまで動かさない。**

なお PBO の識別力は CSCV の構成（区間数・分割数・区間長）とエッジの大きさに強く依存する。ここで用いた構成は
合成標本上の一例であり、実運用の構成を代表しない。

### 4. `MaxDrawdownTolerance` は較正対象にしない

0.15 は計画書（05_trading-assumptions の DD 上限・`TradingDefaults`）由来であり、実装側の自由変数ではない。
較正で動かすと計画と実装が食い違う。変更が要るなら計画側へ環流する（`/plan-feedback`）。

> **［2026-08-04 追記・値は計画側で 0.10 へ改まった。追随は [IADR-0138](IADR-0138_stage0-drawdown-tolerance-tightening.md)（#333）］**
> **本決定（較正対象にしない・変更権限は計画側にある）は維持される。改まったのは値そのものである。**
> 本決定が求めた環流は [project-planning#56](https://github.com/endazon/project-planning/issues/56) として実際に行われ、
> [ADR-0018 決定2](../../planning/projects/ai-stock-trading/07_adr/ADR-0018_risk-defaults-sync-and-stage0-dd.md)（2026-08-01）が
> **10%（`0.10`）** を確定した（同 ADR は本 IADR を「変更の権限を計画側へ明示的に戻した記録」として名指ししている）。
>
> なお本決定の当時の記述「0.15 は計画書の DD 上限由来」は**正確ではなかった**。計画 §5 の DD 上限は当時から
> **10%** であり、0.15 の出所は [ADR-0008](../../planning/projects/ai-stock-trading/07_adr/ADR-0008_staged-gates-and-backtest.md) の
> **旧レンジ「10〜15%」の上限側**である（ADR-0018 §コンテキスト）。**陳腐化したレンジからの逆算**という同一原因から
> `LosingStreakThreshold`（3 vs 確定値 5）にも同型のずれが生じており、そちらは #329 で是正済みである。

### 5. 較正ハーネスはテスト専用に置き、本番コードへ持ち込まない

`BacktestService.Domain.Tests/Calibration/` に置く。本番の実行経路には載らない（Stage 0 判定は純ドメインのまま）。
`System.Random` を使わず splitmix64 を自前実装したのは、種を固定しても系列がランタイム実装に依存し得るため
（記録した較正値を後から再現できることが根拠の前提）。

### 6. Stooq が取得不可であることを記録し、fail-safe が効くことを固定する

2026-07-28 時点で Stooq はプログラム取得に対しチャレンジ応答を返す。この応答は
`StooqDailyCsvParser` がヘッダ不一致として**解析失敗＝欠測**に落とし、バーは 0 本になる。結果として
Stage 0 は `DeflatedSharpe` / `CostRobustness` / `WalkForward` で不合格になり昇格は起きない（IADR-0105 の fail-safe）。
実際に受信した応答形を回帰テストで固定した。

**チャレンジの回避（proof-of-work の計算）は行わない。** ボット検知の回避に当たるためであり、
これは実装上の困難ではなく方針である。

## 検討した代替案

- **実データで較正する（当初計画）**: Stooq が取得不可、他の候補は資格情報を要する。資格情報の要求・投入は
  利用者判断に属するため行わない。実データでの水準確認は #208 に残置する。
- **`MinTrials` を 2 とする（構造的下限ちょうど）**: 補正は「計算できる」が推定が暴れる（変動係数 75.9%）。
  200 候補の探索を 2 件へ過少申告した場合の偽陽性率は 57.20% で、実質的に無防備。
- **`MinTrials` を 50〜100 とする**: 偽陽性率の改善は 0.62% → 0.39%/0.19% と逓減する一方、
  「候補を 50 件以上記録する」運用負荷が増える。安全側だが費用対効果で 20 を採る。
- **`MinTrials` を撤廃し DSR だけに委ねる**: DSR は台帳の件数からしか補正を計算できないため、
  過少申告に対する歯止めが無くなる（表 2 の 100% がそのまま残る）。

## 影響・トレードオフ

- **良い点**: ADR-0008 が要求する多重検定補正が、探索の過少申告に対して初めて実効的な下限を持つ。
  据え置いた 3 閾値についても「測ったうえで動かさない」根拠が残る。
- **トレードオフ**: `MinTrials=20` は**過少申告そのものを検知できない**（200 件試して 20 件だけ記録する運用は
  依然として可能で、その場合の偽陽性率は 0.62%）。下限は手続き上の歯止めであり、本質的な統制は
  「試した候補を正直に台帳へ記録する」運用規律である。これは仕組みで強制できない残余リスクとして明記する。
- **トレードオフ**: 較正は真のエッジ 0 の合成標本に基づく。「実在の戦略がこの基準を通せるか」（偽陰性の水準）は
  未測定であり、実データでの確認まで `MinTrials=20` が厳しすぎないという保証は無い。
  ただし 20 件の候補記録は探索の実務としては小さく、過度な制約になりにくい。
- Stage 0 の判定ロジック・`Shared.Contracts`・DB スキーマは不変。実弾 triple-latch（IADR-0060）にも触れない。
