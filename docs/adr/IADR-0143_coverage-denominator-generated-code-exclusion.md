# IADR-0143: カバレッジ床の分母から EF Core の自動生成コードを宣言的に除外する

- 状態: Accepted
- 日付: 2026-08-05
- 決定者: 実装（Claude Code）／ 起点 [PR #390](https://github.com/endazon/ai-stock-trading/pull/390)（[#334](https://github.com/endazon/ai-stock-trading/issues/334) の PR）
- 作業仕様書: [20260805_coverage-exclude-generated](../specs/20260805_coverage-exclude-generated.md)
- 既存決定: [作業仕様書 20260803（#343）](../specs/20260803_343_regression-test-foundation.md) §3 が
  `scripts/check-coverage.js` と `coverage-floor.json`（floor ＋ 人手 ratchet）を導入した。
  本 IADR はその枠組みを維持したまま、**分母の定義**だけを是正する。

## コンテキストと課題

`scripts/check-coverage.js` は Cobertura レポートに現れるファイルを**すべて**分母へ入れる。
そこに `dotnet ef migrations add` が生成するファイルが含まれていた。

develop 先端（`5df9049`）を Release・清掃済みで実測した内訳:

| 区分 | 被覆/行 | 率 | ファイル数 |
| --- | --- | --- | --- |
| `**/Migrations/*.Designer.cs` | 0/3,399 | 0.00% | 24 |
| `**/Migrations/*ModelSnapshot.cs` | 0/767 | 0.00% | 7 |
| （参考）手書きのマイグレーション本体 | 0/611 | 0.00% | 24 |
| その他（プロダクションコード＋テスト） | 10,794/12,625 | 85.50% | — |
| **合計** | **10,794/17,402** | **62.03%** | — |

自動生成 2 種だけで**分母の 23.9% が恒久的に 0%** である。`.Designer.cs` は `[DbContext]` 属性と
モデルスナップショットの再掲、`*ModelSnapshot.cs` はモデル全体のスナップショットであり、
**人が書くものでもテストするものでもない**。

**これは指標そのものの欠陥である。** マイグレーションを 1 つ追加するだけで数百行の 0% が分母へ積まれ、
テストを 1 行も減らしていない PR が機械的に床を割る。PR #390（#334）は実際にこれで床（62.00%）を割って
`build-and-test` が落ちた（実測 61.10%）。develop 自体も 62.03% と紙一重で、**次に誰がマイグレーションを
足しても同じことが起きる**。落ちた PR の作者にできる正しい対応が「無関係なテストを足す」か
「床を下げる」しかない指標は、退行検知として機能していない。

`check-coverage.js` に除外機構は存在しなかった（`grep -c "exclude\|除外"` が 0）。

## 検討した選択肢

1. **自動生成ファイルにテストを足す** — 棄却。`ModelSnapshot` の本体行を実行するテストは
   「EF が生成したコードが EF の生成どおりであること」を確認するだけで、退行を何も検知しない。
   生成物が変わればテストも自動的に追随してしまい、**常に緑になるテスト**にしかならない。
   さらにマイグレーションを足すたびに同じ作業が発生し、コストが恒久的に増える。
2. **床を下げる（62.00% → 61.00% 等）** — 棄却。原因（分母の汚染）が残るため、
   マイグレーション 2〜3 件ごとに同じ議論と同じ引き下げが必要になる。**床が下がり続ける運用**は、
   実コードの退行を検知するという床の目的を破壊する。今回の PR #390 のような「指標のせいで落ちた PR」を
   毎回手作業で裁定することになる。
3. **`Migrations/` 配下を丸ごと除外する** — 棄却（詳細は決定 2）。手書きの `Up`/`Down` まで一緒に消える。
4. **自動生成 2 種を宣言的に除外し、除外内訳を毎回出力し、歯止めを付ける** — 採用。

## 決定

### 決定 1: 除外パターンは `coverage-floor.json` に glob ＋ 理由の対で宣言する

```jsonc
"maxExcludedLineShare": 0.35,
"exclude": [
  { "pattern": "**/Migrations/*.Designer.cs",     "reason": "dotnet ef migrations add が生成する …" },
  { "pattern": "**/Migrations/*ModelSnapshot.cs", "reason": "dotnet ef が生成する …" }
]
```

**置き場所を `coverage-floor.json` にした理由**（別ファイル `coverage-exclude.json` を棄却した理由）:
床の数値は「**何を分母に入れて測った値か**」と不可分である。2 ファイルに分けると、床を見直す PR の差分に
除外集合が現れず、**どの分母で測った床なのかがレビューから抜け落ちる**。同じファイルにあれば、
床が動く差分と除外が動く差分が必ず同じレビューに乗る。`check-coverage.js` が既にこのファイルを
読んでいるという実装上の都合よりも、この理由の方が重い。

**glob を採り、正規表現をコードへ埋め込まない理由**: パターンは設定として人がレビューするものであり、
`**/Migrations/*.Designer.cs` は issue や CLAUDE.md で人が書く表記そのままである。コード内の正規表現に
すると「何をなぜ外したか」が設定に現れず、次に読む者が追えない（この欠陥を作らないことが本作業の主眼である）。
glob は完全一致（部分一致ではない）で評価し、`*` は `/` を跨がない。

**`reason` は必須**とし、欠けたら失敗させる（決定 3 の G3）。理由の無い除外は「とりあえず外して恒久化」への入口である。

### 決定 2: 手書きのマイグレーション本体（`Up`/`Down`）は除外しない

`Migrations/20260710095747_InitialCreate.cs` のような本体ファイルは、実測 0/611 行で**自動生成 2 種と同じく
現状 0%** である。それでも分母に残す。理由は 2 つ。

1. **人が編集し得る**。データ移行・生 SQL・条件付き DDL は本体へ手で書く。ここは資金を扱う系で最も
   壊れると痛い部分であり、「テストされていない」という事実を指標から消してはならない。
   `.Designer.cs` / `*ModelSnapshot.cs` は編集すれば `dotnet ef` が次回に上書きするのに対し、本体は残る——
   これが両者を分ける線である。
2. **実行し得る**。マイグレーション適用の結合テスト（`Category=Integration`・[IADR-0049](IADR-0049_integration-e2e-foundation.md)）で
   `Migrate()` を通せば被覆できる。既定 CI が Integration を除外しているため現状は 0% だが、
   これは**除外すべき性質**ではなく**埋めるべき穴**である（作業仕様書 §未決事項 1）。

`**/Migrations/**` のような雑なパターンへ退行すると本体が黙って一緒に消える。**この決定を実際に
守らせる仕組みは決定 6**（除外集合 ⊆ 自動生成ファイルを実ツリー × 実設定で検査）である。
決定 4 の否定形テストだけでは不十分であったことが監査で実測された。

### 決定 3: 除外内訳を必ず出力し、5 つの歯止めを置く

「silent な絞り込みを作らない」ため、`check-coverage.js` は除外を適用したら**必ず**次を出力する。

```
[check-coverage] 除外 31 ファイル・4166 行（うち被覆 0 行）。分母 17402 → 13236 行
[check-coverage]   - **/Migrations/*.Designer.cs: 24 ファイル・3399 行（被覆 0） … 理由
[check-coverage]   - **/Migrations/*ModelSnapshot.cs: 7 ファイル・767 行（被覆 0） … 理由
[check-coverage] 行カバレッジ 81.55%（10794/13236 行・レポート 51 件）/ floor 79.00%
```

歯止め:

| # | 歯止め | 挙動 | 何を止めるか |
| --- | --- | --- | --- |
| G1 | `maxExcludedLineShare`（既定 0.35） | 除外行が全体行に占める割合が上限を超えたら**失敗** | `**/*.cs` 等のパターン事故で分母を溶かす退行 |
| G2 | 空振りパターンの通知 | 1 件も一致しないパターンを CI notice で報告（**失敗はさせない**） | 誤記・対象消滅で除外が**黙って効かなくなる**こと |
| G3 | `reason` 必須 | 理由が無ければ**失敗** | 理由なき除外の恒久化 |
| **G4** | **除外集合 ⊆ 自動生成ファイル**（決定 6） | 手書きファイルが 1 件でも除外に一致したら**失敗** | 決定 2 の違反そのもの |
| **G5** | **パターンの隠蔽（shadowing）**（決定 6） | 空振りパターンを先行パターンが飲み込んでいたら**失敗** | 過度に広いパターン |

G1 の 0.35 は現状の除外率 23.9% に対する余裕であり、「マイグレーションが今の 1.5 倍に増えても通るが、
プロダクションコードを飲み込む事故は止まる」水準に置いた。

あわせて `--no-exclude` を追加し、**除外前の素の値を同じスクリプトで測れる**ようにした。
除外の効果を PR で示すのに別の道具を要求しない。

### 決定 4: テストは否定形を正の確認と同数以上置く

除外機構で最も危険な退行は「パターンが効きすぎてプロダクションコードまで分母から消える」ことである
（カバレッジが**上がる**方向に壊れるため、CI は緑のまま気付けない）。`scripts/scripts.repo.test.js` に
次を追加した（キット配布の `scripts.test.js` はバイト一致に保つ規約のため companion 側に置く）。

| 種別 | 内容 |
| --- | --- |
| 正 | `Migrations/*.Designer.cs` / `*ModelSnapshot.cs` が相対・絶対・Windows 区切りのいずれでも一致する |
| **否定形** | 手書きマイグレーション本体（`20260805044003_AddStage1ExcludedInternalPaperDays.cs` 等）が一致しない |
| **否定形** | `MigrationsRunner.cs` / `Migrations.cs` / `MigrationsHealthCheck.cs` / `DesignerLayout.cs` / `Migrations/` 配下でない `DbContextModelSnapshot.cs` / `MigrationsSupport/Helper.Designer.cs` が一致しない |
| 正 | `applyExcludes` が「残した集合」と「パターン別の内訳」の両方を返す（黙って縮めない） |
| **否定形** | 除外率が上限超で違反になる（G1） |
| **否定形** | `reason` 欠落で違反になる（G3） |
| 正 | 空振りパターンが `unmatched` として報告される（G2） |
| 契約 | 実ツリーの `exclude` が 1 件以上あり全件 `reason` を持つ（除外宣言ごと消える退行の検知） |

**この表だけでは決定 2 を守れなかった**（決定 6 で是正）。上記の否定形は `applyExcludes` に
**ハードコードしたパターン**を渡しており、`coverage-floor.json` の実設定を対象にしていなかったためである。

### 決定 6: 決定 2 は「除外集合 ⊆ 自動生成ファイル」を**実ツリー × 実設定**で検査して担保する

**発端（監査で実測された穴）**: `coverage-floor.json` の 1 つ目のパターンを
`**/Migrations/*.Designer.cs` → `**/Migrations/**` へ広げる変異を当てたところ、

- 除外が 31 ファイル・4,166 行 → **55 ファイル・4,777 行**へ拡大し、**手書きの本体 24 ファイル・611 行が
  黙って分母から外れた**（81.55% → **85.50%**）
- それでも `check-coverage.js` は **exit 0**、テストは **152 件全件緑**

つまり**決定 2 は決定文だけの存在で、機械的には何も守っていなかった**。素通りした理由は 3 つある。
`maxExcludedLineShare = 0.35` は 4,777/17,402 = 27.4% で素通り。空振りの G2 は `notice` で失敗しない。
そして否定形テストは**合成入力**を見ていて実物を見ていなかった——これは今回の一連の作業で繰り返し
現れている「**モックを検証していて実物を検査していない**」型の欠陥である（[#389](https://github.com/endazon/ai-stock-trading/issues/389) のフロント契約ずれと同型）。

**採った形: 名前ではなく中身で「自動生成か」を判定し、除外集合がその部分集合であることを要求する。**

`dotnet ef` が書く `*.Designer.cs` / `*ModelSnapshot.cs` は**全 31 件が冒頭に `// <auto-generated />` を
持ち**、手書きのマイグレーション本体は**24 件すべてが持たない**（実測で確認済み）。この marker は
Roslyn の規約であり、**パターンをどう広げても中身の判定は欺けない**。

したがって `check-coverage.js` は、`backend/` 配下のソース（`bin`/`obj` を除く 965 件）を走査し、
**除外パターンに一致した手書きファイルが 1 件でもあれば失敗する**（G4）。

「`Migrations/` 直下の本体ファイルを列挙して照合する」形も検討したが採らなかった。それは**決定 2 の
文面をなぞるだけ**で、`**/*.cs` や `**/Services/**` のような別方向の暴走を捕まえない。
中身による判定なら**除外してよいのは自動生成物だけという原則そのもの**を検査でき、
マイグレーション以外へ除外を広げたくなった将来も同じ検査がそのまま効く。

あわせて G5（隠蔽検出）を追加した。変異時に「`**/Migrations/*ModelSnapshot.cs` が空振り」という
**異常の兆候は出ていたのに `notice` のため素通りした**。空振りのうち「**先行パターンが同じファイルを
飲み込んでいる**」ケースは設定が広すぎることの決定的な証拠であり、部分実行では起こり得ないため
失敗にしてよい。

**G2（ただの空振り）を失敗にしなかった理由**: 単一プロジェクトだけを部分実行した場合、
対象が 1 件も現れないのは**正当**である（例: `dotnet test <1 プロジェクト>` の後に本スクリプトを叩く）。
これを一律に失敗させると、設定が正しいのに無関係な実行が落ち、やがて誰も出力を読まなくなる——
`notice` が読み飛ばされたのと同じ失敗を反対側から作ることになる。今回素通りを許した具体的なケースは
**隠蔽**であり、それは G5 が false positive なしに失敗させる。よって G2 は通知のまま残す。

**検査は 2 層に置く**（どちらも実設定・実ツリーが対象）。

| 層 | 場所 | 効く CI ジョブ |
| --- | --- | --- |
| 実行時ガード | `check-coverage.js`（G4 / G5。違反で **exit 1**） | `build-and-test` |
| テスト | `scripts.repo.test.js`（同じ関数を実ツリー × 実設定で呼ぶ） | `scripts-tests` |

テスト側は「違反が無いこと」を主張するため、**検査器が壊れて常に空を返しても緑になる**。これを防ぐため
**変異検査を常設のテストとして固定した**——実ツリーに対して意図的に `**/Migrations/**` を当て、
手書き本体が違反として挙がること・自動生成物は違反に数えないことを主張する。あわせて
「走査したソース数 > 500」「除外に一致した自動生成物 > 0」のメタ検査を置き、空振りでの形骸化を防ぐ。

**変異検査の実測（是正後）**: `**/Migrations/**` へ広げると `check-coverage.js` が exit 1 で
24 件の手書きファイルを名指しし、`scripts.test.js` も同じ 24 件を挙げて失敗する。復元すると
両方とも緑（159 件）に戻る。`**/*.cs` へ広げた場合は G1・G4・G5 が同時に発火する。
走査コストは全体で 0.33 秒であり、CI に足せる範囲である。

### 決定 5: 床は除外後実測 81.55% から `RATCHET_MARGIN`（2 ポイント）を引いた **0.79** とする

新しい余裕幅を発明せず、`check-coverage.js` が既に持つヒステリシス定数 `RATCHET_MARGIN = 0.02` を使う。
0.79 は `--suggest` が出す候補値と**同一の計算**（`floor((0.8155 - 0.02) * 100) / 100`）であり、
スクリプト自身の運用ルールと矛盾しない。余裕 2.55 ポイントの内訳は「不安定テストの揺れ」＋
「今後のマイグレーション本体の追加（1 件あたり約 25 行 ≒ 0.15 ポイント）」である。
引き上げは従来どおり**人手の PR** で行う（自動 ratchet はしない）。

## 測定手順の罠（この IADR に書き残す理由）

**本作業の測定で実際に誤った数値が報告された。** 同じ間違いを次の人がしないよう明文化する。

1. **CI は Release ビルドである**（`ci.yml` の `build-and-test` は `--configuration Release`）。
   Debug で測ると行数そのものが変わり、**CI と違う値が出る**（実測: Debug 63.11% vs Release 61.10%）。
2. **`bin` / `obj` / `TestResults` の残骸が混入する**（[#353](https://github.com/endazon/ai-stock-trading/issues/353) で既知）。
   `findReports` は `backend/` 配下の `coverage.cobertura.xml` を**すべて**拾うため、過去の実行で残った
   `TestResults/<guid>/` が分母・分子とも水増しする（実測: 未清掃 64.99%・レポート 255 件 / 清掃後 51 件）。

**自己診断の手がかり**: `check-coverage.js` は毎回**レポート件数**を出す。この件数が普段の値
（2026-08-05 時点で 51 件）から乖離していたら、残骸を疑うこと。

正しい手順は「`bin`/`obj`/`TestResults` を退避 → **Release** でビルド → `--collect:"XPlat Code Coverage"` で
全件実行 → `node scripts/check-coverage.js`」である（コマンドは
[作業仕様書 §測定手順](../specs/20260805_coverage-exclude-generated.md)）。

## 影響

- **CI**: 分母から 4,166 行が外れ、同じテスト資産で行カバレッジの表示値が 62.03% → 81.55% になる。
  **テストは 1 件も増減していない**。床は 0.62 → 0.79。
- **PR #390（#334）**: マイグレーション追加による機械的な床割れが解消する。
- **今後**: マイグレーション追加は本体（約 25 行）しか分母へ積まなくなる。1 件あたりの床への影響は
  約 0.15 ポイントで、揺れの範囲に収まる。
- **表示値の断絶**: 過去の PR や issue に残る「62% 台」の数値と今後の「81% 台」は**分母が違う**。
  `coverage-floor.json` の `measuredNote` に除外前後の両方を書き、比較可能にした。
- **除外の拡張には素性検査が付いて回る**（決定 6）。今後 `exclude` へ何かを足す場合、その対象は
  `// <auto-generated />` を持っていなければ CI が通らない。自動生成でないものを外したくなったときは、
  検査を緩めるのではなく**この IADR を改訂して原則そのものを議論する**こと。

## 残課題

1. 手書きマイグレーション本体（0/611 行）を、Integration テストで被覆するか、除外するか、
   nightly の Integration 分を合算するか（作業仕様書 §未決事項 1）。
2. 床の再引き上げ。81.55% に対し 2.55 ポイントの余裕がある。各ドメイン issue のテスト追加後に
   人手の PR で `--suggest` の候補へ引き上げる。
