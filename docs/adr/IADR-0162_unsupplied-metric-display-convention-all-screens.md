# IADR-0162: 「供給が無い値」の表示規約を全画面（SC-01 / SC-02 / SC-03）へ適用する

## コンテキストと課題

計画 05_screens に共通規約が新設された。

> **供給が無い値は「0」「—」で表示しない。**「取得できていません（供給元がありません）」と明示し、
> **「概念が成立しない（対象なし）」と区別する。**……**供給可否はサーバ側が宣言し、画面はそれに従う**
> （値の有無をクライアントが推測しない）。

**型は既にある。** [IADR-0154] が `MetricAvailability`（`Available` / `NotSupplied` / `NotApplicable`）を
導入済みであり、本裁定はその 3 値と 1 対 1 に対応する。よって本 ADR が決めるのは型ではなく、**規約を
全画面・全項目へ広げるときに生じる 4 つの判断**である。

1. SC-03 で **表示が求められているのに画面に存在しない項目**（強制買戻しの発生回数）をどう宣言するか
2. **推定台帳が実装済み**（#419）でありながら発生回数を供給しない、という一見矛盾する状態をどう扱うか
3. SC-02 の実額併記が **未供給を「—」で描いていた**のをどう直すか（「—」は対象なしの記号である）
4. SC-01 の **サーバが宣言する供給可否**（`isResolved`）と、**宣言する主体が存在しない項目**（収集間隔）

## 検討した選択肢

| 論点 | 案 | 評価 |
| --- | --- | --- |
| 発生回数の供給 | A: `IBuyInInferenceStore.CountInferredBetween` を SC-03 へ結線し `Available` で返す | **棄却** |
| | **B: 無条件に `NotSupplied` と宣言し、理由をコードと文書へ残す** | **採用** |
| | C: 画面から項目ごと落とす | 棄却（[IADR-0154] 案 A と同じ理由。計画が求めた表示項目を黙って落とさない） |
| 「—」の意味 | D: 未供給も対象なしも「—」で済ませる | 棄却 |
| | **E: 「—」は対象なし専用とし、未供給は必ず文言で述べる** | **採用** |
| 供給可否の所在 | F: 画面が「この項目は未供給」と定数で持つ | 棄却（[IADR-0154] 案 D。供給が入った日に画面が嘘をつき続ける） |
| | **G: サーバの宣言に従う。宣言する主体が無い項目だけ画面が明示する** | **採用** |

### A（発生回数を結線して `Available` で返す）の棄却理由

**推定台帳は「推定が起きたとき」にしか行を書かない。** 観測が届かなくても 0 行、観測が届いて何も
推定しなくても 0 行である。したがって**行数 0 は 2 つの別事実を区別できない**。

| 行数 0 の意味 | 運用上の性質 | 打つ手 |
| --- | --- | --- |
| ブローカ建玉の観測が一度も届いていない | **異常**（この統制はまったく働いていない） | 観測経路（OpenD 常駐・照会）を通す |
| 観測した結果、強制買戻しは 1 件も無かった | 正常 | 何もしなくてよい |

計画（05_screens SC-03 の供給元の表）は本項目へ **「0 件と表示してはならない」**と名指しで注記しており、
[IADR-0159] 決定3 も「供給が無い間は 0 件と表示しない」と定める。**結線は「観測が一度も無い」状態を
`Available` かつ 0 として応答へ載せる**——これは #403 とまったく同じ形の fail-open である。

### D（未供給も対象なしも「—」）の棄却理由

**打つ手が違うものを同じ見た目にしてはならない**（[IADR-0154] 案 B の棄却理由と同じ）。
SC-02 の実額併記は「25%（$750）」のように**発注規模を判断させる**ための表示である。equity が
取れていないのか該当が無いのかで、利用者が画面を信じてよいかどうかが変わる。

## 決定

### 決定1: 3 状態は**両方向**に守る——正当な 0 を未供給へ倒すことも禁じる

規約が禁じるのは「未供給を 0 に見せること」だけではない。**`Available` かつ 0 は「0」と描く**
（例: 当日の統制違反 0 件・空売り建玉が無い口座の空売り比率 0.0%・借株料 $0）。

裁定は「クライアント側で **0 かどうかから供給有無を推測しない**」と述べている。この規律は
**逆向きにも効く**——0 を見て「たぶん未供給だろう」と描けば、供給されているのに「取得できていません」と
嘘をつくことになる。件数の表示関数（`availabilityCountText`）は**供給可否だけ**を見る。

### 決定2: 強制買戻しの発生回数は**無条件に `NotSupplied`** とし、結線しない理由をコードへ残す

- `ShortSellingStatusView` へ `BuyInCountAvailability` / `BuyInCount` を追加し、
  `ShortSellingStatusService` は常に `NotSupplied` / `null` を返す。
- **`IBuyInInferenceStore` を本サービスへ注入しない。** 注入すれば「使えるのに使っていない」ように見え、
  善意の後続が結線してしまう。**結線してはならない理由**（上表）をコメントとして値の隣に置く。
- **他の指標の供給状態を条件に混ぜない**（[IADR-0154] 残余リスク4 の一般化）。維持率・現在値・建玉の有無が
  どう変わっても本項の宣言は変わらない。単体テストが**維持率と空売り比率が供給されている側**を固定する。
- 供給できる形にするには**「観測が届いた事実」を記録する経路**が要る（`blocked-tasks` へ登録）。

> **［2026-08-13 追記］本決定の「無条件に `NotSupplied`」「`IBuyInInferenceStore` を注入しない」は、
> [IADR-0186](IADR-0186_sc03-buy-in-count-supply.md) により*条件付きの結線*へ改められた。**
> 本決定が結線を禁じた理由は「**観測の到達を記録する経路が無い**」ことであり、その経路は
> [#463](https://github.com/endazon/ai-stock-trading/issues/463) / [IADR-0181](IADR-0181_buy-in-inference-query-and-observation-arrival.md) で入った
> （[#470](https://github.com/endazon/ai-stock-trading/issues/470) / IADR-0186 が SC-03 への結線を行った）。
>
> **現行の規則**: 当月が観測の届いた取引日で**覆われている場合に限り** `Available` ＋件数を返し、
> **1 日でも欠ければ `NotSupplied`** へ倒す。**本決定が塞いだ fail-open（観測ゼロを「0 件」と描く）は
> 引き続き禁止であり、IADR-0186 決定2 がそれを明示的に継承している**——変わったのは
> 「無条件に未供給」から「**被覆を条件とする供給**」への 1 点だけである。
>
> 決定2 の他の拘束（**他の指標の供給状態を条件に混ぜない**）は**不変**であり、IADR-0186 決定3 が同じ規律を守る。
>
> **したがって本決定 2 の字面（注入しない）だけを読んで結線を差し戻してはならない。**

### 決定3: 「—」は**対象なし専用**の記号とし、未供給は必ず文言で述べる

- SC-02 の実額併記は `equityAmountText(equity, ratio)` を通す。**equity が供給されていなければ
  「取得できていません（供給元がありません）」**、**入力が読めないだけなら「—」**である。
- 併記できないことを黙って隠さない、という従来の方針（[IADR-0151] 決定4）は変えない。変えたのは
  **「なぜ併記できないのか」を 2 つに分けた**点である。
- equity が 0 でも未供給ではない（実額 $0 は正当な値。決定1 の逆向きの防止）。

### 決定4: 供給可否は**サーバの宣言**に従う。宣言する主体が無い項目だけ画面が明示する

| 画面・項目 | 宣言の所在 |
| --- | --- |
| SC-03 の維持率・借株料・自動縮小履歴・空売り比率・**発生回数** | `MetricAvailability`（サーバ） |
| SC-01 §1 の全体前提条件 | **`VersionedAssumptions.IsResolved`**（＝`Version > 0`。サーバ） |
| SC-02 の equity 実額 | `/risk-controls/status` の取得可否（**取得失敗も未供給の一種**） |
| SC-01 §2 の収集間隔 | **宣言する主体が存在しない**（エンドポイントも設定ストアも無い）。画面が明示する |

最後の 1 行だけが例外である（[IADR-0155] 決定2 の踏襲）。**供給元となるエンドポイント自体が無いため、
宣言すべきサーバがいない。** 値を運ぶ経路ができた時点でサーバ宣言へ移すこと。それまでは
「画面に書いてある未供給」が 1 か所だけ存在するという**既知の例外**として扱う。

### 決定5: 維持率が Stage 1 の全期間表示できないことを**画面とコードに明記する**

ADR-0016 決定7 の 2026-08-07 追記と ADR-0019 PoC 項目 3 により、維持率は**実弾口座のヘッダを要し
moomoo SIMULATE では照会 API 自体が失敗する**。したがって Stage 1 のあいだ**一度も表示されない**。

**これは直すべきバグではない。** その旨を書かないと「そのうち直る不具合」と読まれ、利用者は統制が
無いまま待ち続ける（計画が「画面の設計として明示的に受け入れる」と書いた理由である）。
画面は未供給の警告に本文言を添え、**供給が始まれば同じコードのまま消える**（画面に定数を持たない・決定4）。

### 決定6: 「サーバが宣言していること」を契約フィクスチャで固定する

[IADR-0146] の機構へ新フィールドを載せる。`risk-controls.short-selling.json` は既定構成の実応答であり、
`buyInCountAvailability: 1`（`NotSupplied`）が並ぶ。ここが `0` へ黙って変われば xUnit が落ち、
フィクスチャを再生成すればフロントの `npm run typecheck` と契約テストが落ちる。
**片側だけでは緑にならない**ため、「サーバが宣言する」構造そのものが機械的に守られる。

## 理由

- **「値が無い」ことが統制上の情報である**（[IADR-0154] の理由をそのまま全画面へ広げた）。
- **3 状態は両方向に守らなければ意味を持たない。** 片方向だけの規律は、逆向きの嘘（正当な 0 を
  「取得できていません」と描く）を許し、やがて「どうせ未供給表示は当てにならない」と読まれて
  警告そのものが無視される。
- **「実装したから見える」と読める記述を作らない**（[IADR-0159] の結果節の明文）。推定台帳が入ったことと
  発生回数が供給されることは別である。

## 結果

- 良い影響:
  - SC-01 / SC-02 / SC-03 の未供給表示が**同じ文言**になり、利用者が「取得できていません」を
    1 つの意味で読めるようになった。
  - **正当な 0 を未供給へ倒す逆向きの誤りが、テストで固定された**（従来は片方向しか見ていなかった）。
  - 変異検査で実測: (a) 未供給を「0」で描く／(b) 未供給を「—」で描く／(c) 正当な 0 を未供給扱いにする／
    (d) クライアントが 0 から供給有無を推測する、のいずれもテストが赤くなる。
- 悪い影響・トレードオフ:
  - **画面の文言が長くなる。** 「—」1 文字で済んでいた箇所が 1 文になる。意図した費用である。
  - `MetricAvailability` を持たない値（SC-01 §1 の `isResolved`・SC-02 の取得失敗）は**画面側の分岐**で
    規約へ揃えている。型で強制されるのは SC-03 の応答だけである。
- **残余リスク（明記）**:
  1. **収集間隔だけは「画面に書いてある未供給」である**（決定4 の例外）。供給経路ができたとき、
     画面の記述を直す作業が人手に残る。
  2. **強制買戻しの発生回数は実装が `NotSupplied` をハードコードしている。** 観測記録の経路が入ったときに
     切り替える作業が人手に残る（[IADR-0154] 残余リスク2 と同型。フィクスチャは切り替え忘れを検出しない）。
  3. **SC-01 §1 は未解決でも入力値として既定値を表示し続ける。** 警告は出すが、入力欄の数値そのものを
     「未供給」に置き換えてはいない（置き換えると保存操作が成立しなくなる）。**表示している値が既定値である
     ことは文言でしか伝わらない。**
  4. **E2E（Playwright）はサンドボックスでブラウザを取得できず未実行**である（型検査のみ）。実走は CI。
  5. 計画 05_screens SC-03 の供給元の表は発生回数の現況を「推定経路が未実装である」と書いており、
     **#419 の完了で記述が古くなった**（供給が無いという結論は変わらない）。環流済み。
