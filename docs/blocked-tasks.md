# 実機確認・権限が必要で AI が完了できない作業の一覧

- 作成日: 2026-08-05
- 最終更新: 2026-08-05（**実機確認セッションの結果を反映**。develop `0143582` 時点・計画 submodule `d980a01` 時点）
- 作成者: Claude Code（監査セッション）

## この文書の目的

AI（Claude Code）と CI だけでは**原理的に完了できない**作業を洗い出す。以下の 2 種類に分ける。

- **A. 実機・実環境が要るもの** — 実口座・実ブローカー・外部サイト・本番相当のデータ量が必要
- **B. 権限・人間の判断が要るもの** — GitHub の設定権限、資金の移動、計画側の裁定

**「実装が終わっていない」だけの作業は含めない**（それらは通常の issue で追える）。ここに挙げるのは、**誰かが実物に触るまで永久に終わらない**ものだけである。

解消した項目は削除せず「**解消済み**」として日付とともに残す。**解消の過程で本文書の記述が誤っていたと判明した場合は、誤りも消さずに訂正として残す**（同じ推測を繰り返さないため）。

> ⚠️ **重要な前提**: 現時点で**実弾の発注は 1 件も行われない**。`LiveTradingGate.LiveTradingReleased = false`（定数・2026-08-05 実測で不変）が閂として効いており、解禁は 1 ファイルの変更に集約されている。本一覧の A 群が未了である限り、この閂を開けてはならない。
>
> 2026-08-05 の PoC では**実弾口座への読み取り照会**（`TrdGetMarginRatio` 等）が利用者の手で行われたが、**発注系（`PlaceOrder` / `ModifyOrder`）は実弾環境で一度も呼ばれていない**。読み取りと発注を混同しないこと。

### 参照する計画 ADR の状態について

本文書が根拠として引く **ADR-0016 / 0018 / 0019 / 0022 / 0023 はいずれも `Proposed` である**（`Accepted` ではない。submodule pin `d980a01` で実測）。ただし**裁定の内容そのものは確定している**。ADR-0022 の原文:

> **状態を `Proposed` に留めている理由**: 本 ADR の決定の内容は利用者裁定により確定している。**`Proposed` はその裁定を疑うものではない。** 保留しているのは記録としての承認だけである。…**`Proposed` は決定の効力を停止しない**。

保留の理由は、計画側で `/sync-impl` が **GitHub API 401（`Bad credentials`）で失敗**し、実装リポジトリへの読み取りアクセスが得られず**実装 IADR との突合が未了**であるためとされている。突合が済み次第 `Accepted` へ移る予定である。

**したがって本文書の期限・数値はそのまま有効**だが、「`Accepted` 済みの確定計画」と読むと状態表記と食い違う。なお**この 401 自体が B 群と同種の権限起因の詰まり**であり、計画側の記録承認を止め続けている点は留意されたい（本リポジトリからは解消できない）。

#### 🔴 A-4 の確認で判明した新たな閉塞 — 収録は「翌々営業日 8:50 頃」

**これは推測ではなく、日銀の公表・掲載予定表（`tkohyos.xlsx`）に明記された事実である。**

| 対象 | タイミング | 頻度 |
| --- | --- | --- |
| 外国為替市況（本体の **PDF 公表**） | **17:50 頃** | 毎営業日 |
| 外国為替相場状況（…日次）＝**検索サイト／API への収録** | **翌々営業日 8:50 頃** | 毎営業日 |

**ADR-0022 決定 1 の表が「公表頻度: 毎営業日」と書いているのは本体 PDF の話であり、実装が読む経路の鮮度ではない。**

平常時（8:50 以降）の「最新データの古さ」は次のように決まる。

| 取得曜日 | 最新データ | 古さ |
| --- | --- | --- |
| 水・木・金 | 2 営業日前 | 2 日 |
| **月** | 前週木 | **4 日** |
| **火** | 前週金 | **4 日** |

**平常時でも週 2 日は必ず 3 日を超える。** 3 連休明けの火曜は 5 日、8:50 の収録前に取得すればさらに 1 営業日分古くなる。

決定 4 は「二段構成であれば平常時に 3 日を超えることはまずない。3 日を超えたら『両方の源が取れていない』という異常であり、警告として意味のある値になる」としているが、**この前提が成立しない**。正常時に発火し続けると、決定 4 が 7 日・14 日を却下した理由（異常の検知が遅れる）と同種の失敗を逆方向で招く。

**FRED フォールバックはこれを救わない。** `DEXJPUS` は公表が週次であり、月曜・火曜に日銀側が 4 日前しか持たない局面で FRED がそれより新しい保証がない。決定 3 が期待した「日本の連休中も FRED 側は動いている」という冗長化は、**日本の平日に出る収録遅れ**には効かない。

- **#381 の「やること 3」と受け入れ基準は、ADR-0022 決定 4 の改定が確定するまで確定できない。とくにしきい値 3 日をそのまま実装すると、稼働直後から週 2 日の誤警告が出る。**
- 環流記録は 3 案を挙げ、**案 A（5 日へ緩める）を最小の変更**として推している（案 B = 営業日ベースは決定 3 が明確に却下したカレンダーの持ち込み、案 C = 17:50 の PDF を一次取得元にするのは PDF 解析という新たな脆さ）。
- **決定 5（絶対上限 30 日・超過で新規建て停止）は影響を受けない**（4 日は 30 日を超えない）。
- 裁定待ちとして **B-4** に登録した。
