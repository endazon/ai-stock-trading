## この文書の目的

AI（Claude Code）と CI だけでは**原理的に完了できない**作業を洗い出す。以下の 2 種類に分ける。

- **A. 実機・実環境が要るもの** — 実口座・実ブローカー・外部サイト・本番相当のデータ量が必要
- **B. 権限・人間の判断が要るもの** — GitHub の設定権限、資金の移動、計画側の裁定

**「実装が終わっていない」だけの作業は含めない**（それらは通常の issue で追える）。ここに挙げるのは、**誰かが実物に触るまで永久に終わらない**ものだけである。

解消した項目は削除せず「**解消済み**」として日付とともに残す。**解消の過程で本文書の記述が誤っていたと判明した場合は、誤りも消さずに訂正として残す**（同じ推測を繰り返さないため）。

> ⚠️ **重要な前提**: 現時点で**実弾の発注は 1 件も行われない**。`LiveTradingGate.LiveTradingReleased = false`（定数・2026-08-05 実測で不変）が閂として効いており、解禁は 1 ファイルの変更に集約されている。本一覧の A 群が未了である限り、この閂を開けてはならない。
>
> 2026-08-05 の PoC では**実弾口座への読み取り照会**（`TrdGetMarginRatio` 等）が利用者の手で行われたが、**発注系（`PlaceOrder` / `ModifyOrder`）は実弾環境で一度も呼ばれていない**。読み取りと発注を混同しないこと。

**ADR-0022 決定 1 の表が「公表頻度: 毎営業日」と書いているのは本体 PDF の話であり、実装が読む経路の鮮度ではない。**

平常時（8:50 以降）の「最新データの古さ」は次のように決まる。

| 取得曜日 | 最新データ | 古さ |
| --- | --- | --- |
| 水・木・金 | 2 営業日前 | 2 日 |
| **月** | 前週木 | **4 日** |
| **火** | 前週金 | **4 日** |

**平常時でも週 2 日は必ず 3 日を超える。** 3 連休明けの火曜は 5 日、8:50 の収録前に取得すればさらに 1 営業日分古くなる。

決定 4 は「二段構成であれば平常時に 3 日を超えることはまずない。
3 日を超えたら『両方の源が取れていない』という異常であり、警告として意味のある値になる」としているが、**この前提が成立しない**。
正常時に発火し続けると、決定 4 が 7 日・14 日を却下した理由（異常の検知が遅れる）と同種の失敗を逆方向で招く。
