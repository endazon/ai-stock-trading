# 仕様書: GFV 違反による停止の解除

> 本仕様書は実装着手前に作成する。

## 起点となる計画書（トレーサビリティ）

- 起点 issue: [#464](https://github.com/endazon/ai-stock-trading/issues/464)
- 起点 ID: **FR-19**（取引ガード）／**FR-10**／**FR-11**（監査ログ）／**UC-06**
- 起点: **ADR-0028**（2026-08-07 Accepted。質問票 第15回 Q10・Q11。環流 project-planning#251）

| # | 決定 | 本作業での扱い |
| --- | --- | --- |
| 1 | **GFV 違反記録は失効させない**（期間経過で消えない） | 実装済み（IADR-0165 決定4）を**追認**。変更しない |
| 2 | **停止は利用者の明示的な操作でのみ解除する。** 原因の是正の確認を伴い、**誰が・いつ・どの記録に対して**解除したかを監査ログへ記録する | **本作業の主対象** |
| 3 | **解除の窓口は Discord Bot。** 画面（SC-02 / SC-03）からは解除できない | **本作業の主対象** |
| 4 | ブローカー表示との突合の頻度 | **対象外**（現金口座の運用開始時に定める。対象そのものが存在しない） |

## 実装の現状（実測 2026-08-08・`develop` = `f25edda`）

- `IGoodFaithViolationStore` は **追記専用**（`Append` / `GetTally` / `GetRecordedBetween`）で、**解除の口が無い**。
- `BotCommandParser` / `BotCommandKind` に**解除コマンドが無い**（扱うのは killswitch / pause / resume / status / stage のみ）。
- **したがって、原因を是正しても停止状態を解けない**（project-planning#251 が指摘した空白）。

## 決定

### 決定1: 解除は「違反記録ごとの解除行の追記」で表す（記録を消さない・更新しない）

ADR-0028 決定1 が「失効させない」と定めているため、**台帳から行を消す／更新するのは規約違反**である。
別テーブル `good_faith_violation_clearances` に**解除行を追記**する。

- **主キーは解除対象の `OrderId`（＝違反記録の計上単位）**。これにより
  - 「**どの記録に対して**解除したか」（決定2 の要求）が構造的に表現され、
  - 同じ記録を二重に解除できない（冪等）。
- `GetTally()` は**解除されていない違反記録の件数**を返す。**違反記録そのものは残り続ける**
  （`GetRecordedBetween` は解除の有無に関わらず全件を返す＝監査の証跡は消えない）。

### 決定2: 解除は既存の破壊的統制操作と**同じ確認水準**に揃える

ADR-0028 §結果 が「**解除操作そのものが新たな攻撃面・誤操作面になる**」と明記している。
kill switch（IADR-0062 / IADR-0097）と同型にする。

| 閂 | 内容 |
| --- | --- |
| 1 | **多層認証**（DM 拒否・サーバー・チャンネル・許可リスト・Keycloak マッピング）。空設定は全拒否 |
| 2 | **確認ボタン**（Gateway が担う） |
| 3 | **確認フレーズ**の一致。未設定・不一致・未入力は Risk を呼ばず拒否する |
| 4 | **理由必須**（1 文字以上）。ADR-0028 決定2 の「原因の是正が済んでいることの確認を伴う」の実装 |
| 5 | 認可は **OwnerOnly**（trading-owner）。s2s トークンでは 403 |

### 決定3: 解除を監査ログへ「誰が・いつ・どの記録に対して」の粒度で残す

新イベント `GoodFaithViolationsCleared`（`ClearedBy` / `ClearedAt` / `ClearedOrderIds` / `Reason` / `RemainingCount`）を
発行し、監査サービスが集約する（`StageTransitioned` と同型・IADR-0082 の作法）。

**`RemainingCount` を載せる。** 解除後になお残る件数が 0 でない可能性がある
（解除操作と新たな違反の計上が競合した場合）。**「解除したのに止まったまま」を監査から説明できるようにする。**

## 🔴 やらないこと（issue / ADR-0028 の明示）

- **未供給時の fail-closed を緩めること。** ADR-0028 が明記: 決定2 の解除は**記録が積まれた場合**の解除であり、
  **供給が無い場合の拒否を解除する手段ではない。**
  実装上は構造的に満たされる（解除は件数にしか作用せず、`GetTally()` が `null` を返す経路＝
  ストアが判定コアへ結線されていない場合には触れない）。**構造テストで固定する。**
- **画面からの解除**（決定3）。SC-02 / SC-03 には解除の口を作らない。**エンドポイントを OwnerOnly に置くだけでは
  足りない**（画面も owner で叩ける）ため、**BFF / フロントに経路を足さない**ことをもって満たす。
- **ブローカー表示との突合の頻度の実装**（決定4）。
- **違反記録の削除・更新**（決定1）。

## テスト（受け入れ基準の写像）

| # | 受け入れ基準 | テスト |
| --- | --- | --- |
| 1 | 解除操作で停止が解ける | ストア（Tally が減る）＋エンドポイント |
| 2 | **否定形**: 解除しても**違反記録そのものは残る**（決定1） | `GetRecordedBetween` が解除後も全件返す |
| 3 | **否定形**: 多層認証を通らない解除要求が拒否される | ハンドラ（DM・許可外・未設定） |
| 4 | **否定形**: 確認フレーズ不一致・未設定は Risk を呼ばず拒否 | ハンドラ |
| 5 | **否定形**: 画面（SC-02 / SC-03）からは解除できない | 構造テスト（BFF ルート・フロントに経路が無い） |
| 6 | **否定形（最重要）**: **未供給**のときの拒否は解除操作では解けない | 判定コアの構造テスト |
| 7 | 監査ログに「誰が・いつ・どの記録に対して」が残る | イベント発行＋`AuditEntryFactory` |
| 8 | **否定形**: 同じ記録を二重に解除しても件数が狂わない（冪等） | ストア |

## 対照実験（緑 → 赤 → 緑）

- 解除を「行の削除」に変える → 決定1 のテスト（記録が残る）が赤。
- 確認フレーズ検証を外す → 閂 3 のテストのみ赤。
- `GetTally()` の解除除外を外す → 解除が効かないテストが赤。
