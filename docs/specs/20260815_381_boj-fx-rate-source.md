# 仕様書: 日銀 FX アダプタと順位つきフォールバック

> 本仕様書は実装着手前に作成する。

## 起点

- 起点 issue: [#381](https://github.com/endazon/ai-stock-trading/issues/381)
- 起点 ID: **FR-10**（リスク統制）/ **FR-17**
- 計画: [ADR-0022](../../planning/projects/ai-stock-trading/07_adr/ADR-0022_fx-rate-source-and-freshness.md)
  **決定1**（日銀第一・系列 `FM08'FXERD04`）・**決定2**（FRED フォールバック＋切替の可視化）・**決定3**（カレンダーを持たない）

## 🔴 なぜ今やるか — 今の警告は「常時鳴る警告」である

[IADR-0174](../adr/IADR-0174_fx-freshness-warning-and-hard-limit.md) が入れた 3 段縮退（5 日以下＝通常／
5 日超〜30 日以下＝警告つき続行／30 日超＝新規建て停止）は、**情報源が FRED 単独のままでは実効しない。**

`DEXJPUS` は系列こそ営業日次だが**公表は H.10 週次リリース**であり、最新観測の齢は**最大 12.84 日**まで
積み上がる。**5 日の警告しきい値に対して警告域へ常駐する。**

> **常時鳴る警告は無視される警告である。** 「気づくための段」は、**日銀アダプタが入って初めて意味を持つ。**

## 本 PR の範囲と、次 PR へ送るもの

**#381 の受け入れ基準は 2 つの層に分かれる。** 本 PR は**第 1 層のみ**を担当する。

| 層 | 内容 | 触る範囲 | 本 PR |
| --- | --- | --- | --- |
| **1. 情報源の二段化** | 日銀アダプタ・順位つきフォールバック・provider 集合・逸脱登録の削除・テスト | TradeDecisionService のみ | **担当する** |
| 2. 切替と警告の可視化 | 日報・監査ログ・Discord の 3 経路 | Shared.Contracts ＋ Audit ＋ Notification ＋ Report の **4 サービス** | **次 PR** |

**分割の理由**: 第 2 層は**イベント型の新設を起点に 4 サービスへ波及**する（`AuditConsumerCoverageTests` が
新イベントに対し監査ハンドラを CI で強制するため、Audit・Notification は同時に必要になる）。
第 1 層と混ぜると**「どの受け入れ基準に対する diff か」が 1 対 1 で言えなくなる**（`pr-size.yml` が
警告として挙げている形そのものである）。**#381 は本 PR では閉じない。**

> **第 1 層だけでも「常時鳴る警告」は解消する** —— 齢が 12.84 日から 2〜4 日へ下がるためである。
> **第 2 層は「劣化に気づく」ための層であり、劣化そのものを減らすのは第 1 層である。**

## 決定

### 決定1: 既存の `BojInformationSource` を再利用せず、FX 専用アダプタを新設する

**同じ日銀 API を叩く実装が既にある**（`InformationCollectionService` の `BojInformationSource`）。
しかし**再利用しない。**

| 理由 | 内容 |
| --- | --- |
| **契約が違う** | あちらは `RawInformationItem`（マクロ指標のテキスト）を返す。FX が要るのは `FxRate?`（`decimal` ＋ `AsOf`） |
| **サービスが違う** | `InformationCollectionService` と `TradeDecisionService` は別サービスであり、共有するなら `Shared.Infrastructure` への抽出になる |
| **抽出は本 issue の範囲外** | 既に動いているサービスの改修を伴い、**#381 の受け入れ基準と 1 対 1 で対応しない diff** が混ざる |

**重複するのは JSON の DTO 約 15 行である。** CLAUDE.md の禁止事項「**過剰な抽象化**」に照らし、
**2 つ目の利用者で共通化しない。** 3 つ目が現れたら `Shared.Infrastructure` へ抽出する
（この判断は [IADR-0194](../adr/IADR-0194_boj-fx-rate-source-and-ordered-fallback.md) に残す）。

### 決定2: `format=json&lang=en` を使う（CP932 を持ち込まない）

上記「食い違い」のとおり。**既存の `BojInformationSource` と同じ形にすることで、
日銀 API の応答形式についての知識が 1 つで済む。**

### 決定3: フォールバックは**順位つき**であり、既存の `CompositeInformationSource` とは別物である

情報収集側の `CompositeInformationSource` は**全ソースを合算する**（どれも等価）。
**FX が要るのは「第一が駄目なら次」という順位つきの縮退**であり、合算ではない。**新しく書く。**

- **「駄目」の定義**: `GetRateToBaseAsync` が **`null` を返した場合**（例外は各アダプタが内部で null へ縮退する）。
- **鮮度による切替はしない。** 鮮度判定は `CachingFxRateSource` が**合成の外側**で行う
  （下記「配置」）。**内側で鮮度を見ると、日銀が 3 日・FRED が 8 日のとき FRED を採ってしまう。**

### 決定4: 合成の順序は `Caching( Fallback( Boj, Fred ) )` とする

```
CachingFxRateSource            ← TTL・鮮度警告・30 日超の停止（既存のまま）
  └ FallbackFxRateSource       ← 新設。順位つき
      ├ BojFxRateSource        ← 新設。第一
      └ FredFxRateSource       ← 既存。フォールバック
```

**鮮度判定を最外に置く理由**: 3 段縮退は**採用された値**に対して効くべきである。
内側に置くと**源ごとに別々の警告が出て、どちらの値が使われたのか読めなくなる。**

### 決定5: provider 集合へ `boj` を足し、既定の推奨構成を `boj` にする

`ProviderNames = [None, Boj, Fred]`。**`ProviderNames` は計画適合検査が読む単一情報源**であり、
これを更新すると `Fx.RateSourceProviders` の実際値が `"boj, fred"` になって
**計画側の期待値と一致し、`KnownPlanDeviations` の登録行が削除を強制される**（`PlanConformanceTests` が
「登録済み逸脱は実際に逸脱している」ことを検査するため、**直したのに登録が残っていると赤になる**）。

**`boj` は API キーを要さない**（FRED と違い認証不要）。したがって **`Fx:Provider: "boj"` だけで動く。**

## やらないこと

- **第 2 層（可視化）** —— 次 PR。上記「範囲」参照。
- **CP932 デコード** —— 決定2。
- **`BojInformationSource` との共通化** —— 決定1。
- **本体 PDF の解析** —— ADR-0022 決定4 が「PDF 解析という新たな脆さを持ち込む」として明確に却下している。
- **営業日カレンダーの導入** —— ADR-0022 決定3 が禁じている。**持たないことをテストで固定する**（受け入れ基準）。

## 受け入れ基準（本 PR の分）

- [ ] `BojFxRateSource` が `db=fm08` ＋ `code=FXERD04` で仲値を取得する（`FM08'FXERD04` を渡さない）
- [ ] **当日・前営業日が `null` でも異常として扱わない**（末尾から値のある直近を採る）
- [ ] **否定形**: 中心相場（`FXERD05`）を採らないことをテストで固定する
- [ ] `FallbackFxRateSource` が**日銀 → FRED の順**で試す
- [ ] `ProviderNames` が `[none, boj, fred]` になる
- [ ] **否定形**: 営業日カレンダー（`IMarketCalendar`）を FX 経路が参照しないことをテストで固定する
- [ ] **否定形**: 30 日超で**新規建てだけが止まり、手仕舞いは止まらない**ことをテストで固定する
- [ ] `KnownPlanDeviations` から `Fx.RateSourceProviders` の行を削除し、**赤→緑の遷移を実測して報告する**
- [ ] **ミューテーションで効きを実測する**

## テスト方針

| 何を守るか | どう守るか |
| --- | --- |
| 仲値を採ること | **否定形**: `FXERD05` を渡した応答では採らない／系列コードで選ぶ |
| 収録ラグに耐えること | 末尾 3 期が `null` の応答で、その手前の値と日付を採る |
| 順位 | 日銀が値を返せば FRED を**呼ばない**（呼び出し回数で見る） |
| 縮退 | 日銀が null なら FRED を呼ぶ／両方 null なら null |
| **カレンダー非依存** | **FX 経路の型が `IMarketCalendar` を参照しないことを反射で検査する** |
| **手仕舞いは止まらない** | `TradeDecisionService` の見送りが**新規建ての経路にのみ**あることを固定する |
| 計画適合 | `Fx.RateSourceProviders` が `"boj, fred"` になり、逸脱登録が不要になる |

> **自己試験ではなく実データで確かめた部分は「実測」節に置いた。** 単体テストは合成した応答で
> 判定規則を確かめるものであり、**実 API が期待どおりに応答するかは別の問い**である
> （[IADR-0193](../adr/IADR-0193_adr-index-sync-check.md) 決定5 と同じ整理）。**実 API を叩くテストは CI に入れない**
> （外部依存で CI が落ちる。既存の `BojInformationSource` も同じ扱い）。

## 残余リスク（起案時点の見込み。実装後に更新する）

- **実 API の応答形式が変われば静かに壊れる。** CI は実 API を叩かないため、
  **壊れたことは「レートが取れない → 新規建て見送り」という安全側の縮退として現れる**（発注はしない）。
  **ただし気づくのは遅れる** —— それを縮めるのが第 2 層（可視化）である。
- **`null` の意味が区別できない**（欠測・休場・未収録が同じ `null`）。計画も「区別しない」と明記している。
- **日銀の系列が改廃されれば取得できなくなる。** FRED フォールバックが受ける。
