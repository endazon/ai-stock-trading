# 仕様書: 鮮度切れでも手仕舞いを止めない（#506）

> 本仕様書は実装着手前に作成する。

## 起点

- 起点 issue: [#506](https://github.com/endazon/ai-stock-trading/issues/506)（発見元は [#381](https://github.com/endazon/ai-stock-trading/issues/381) の受け入れ基準・[PR #507](https://github.com/endazon/ai-stock-trading/pull/507) で実測）
- 起点 ID: **FR-10**（リスク統制）・**FR-11**（監査）
- 計画: [ADR-0022](../../planning/projects/ai-stock-trading/07_adr/ADR-0022_fx-rate-source-and-freshness.md) **決定5**

## 課題 — 計画は入口と出口を分けているが、実装は同じゲートで塞いでいる

| 状態 | 計画（ADR-0022 決定5） | 実装（実測） |
| --- | --- | --- |
| 5 日超〜30 日以下 | 直近レートで続行・警告。新規建ては止めない | ✅ 一致 |
| **30 日超** | **新規建てを停止。手仕舞い・損切りは止めない** | 🔴 **手仕舞いも止まる** |

換算レートのゲートが**建玉効果（Open / Close）を決めるより前**にあり、
**建玉効果が分かるのは LLM の判断後**であるため、**出口が入口と同じゲートで塞がれている。**

> 🔴 **「止められない」より「閉じられない」ほうが危険である。**
> 新規建ての停止は安全側だが、**損失を抱えた建玉から出られないのは安全側ではない。**
> **計画が両者を分けているのはそのためである。**

**鮮度切れは `CachingFxRateSource` が「レート無し（null）」として返す**ため、
**30 日超だけでなく、レート源の未結線・取得失敗でも同じく手仕舞いが止まる。**

## 🔴 素直に直すと監査台帳が壊れる

決済を通すだけならゲートを後ろへ動かせばよい。**問題は決済意図へ載せる `FxRateToBase` である。**

`OrderIntent.FxRateToBase` は**非 nullable の `decimal`・既定 `1m`**。
既定のまま載せると **JPY 建ての約定金額が USD としてそのまま台帳へ記録され**、
`NotionalInBase = Quantity × Price × 1` となって **7 年保持の監査台帳（FR-11）の金額が約 150 倍ずれる。**

> **黙って `1m` を載せるのは、止めることより悪い。誤った金額は後から誤りだと分からない。**

## 決定

### 決定1: **案 B を採る —— 値は失わせず、判断だけを変える**

issue が挙げた 3 案のうち **B**（鮮度切れでも直近の値は返し、鮮度の判定結果を別に持たせる）を採る。

**計画の語がそう読める。** ADR-0022 決定5 は「**直近レートで続行する**」と書いており、
**値が失われるのではなく、判断が変わる**という構造を想定している。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| A: `FxRateToBase` を nullable 化 | ❌ | **契約変更が永続化（EF マイグレーション）と統制側の読み手すべてへ波及する。** 直したい範囲に対して代償が大きい |
| **B: 値＋鮮度の判定を返す** | ✅ | **計画の語に最も近い。** 波及は FX 経路に閉じる |
| C: 決済に限り最後に成功したレートを使う | ❌ | **キャッシュの保持方針の変更**が要る（現在は鮮度切れをキャッシュしない）。加えて「いつのレートか」が呼び出し側から見えなくなる |

### 決定2: **鮮度を判定するのは最外の装飾だけである。他の源は「判定しない」と表明する**

`IFxRateSource` へ `GetReadingAsync`（値＋鮮度）を足すが、**既定実装**を持たせる。

- **既定**: `GetRateToBaseAsync` の結果をそのまま返し、鮮度は **`Unknown`**。
- **`CachingFxRateSource` だけが上書き**し、実際の齢から `Fresh` / `Warning` / `Expired` を決める。

> **`Unknown` を `Fresh` と書かない。** 日銀・FRED の生アダプタは**鮮度を判定していない**のであって、
> **新鮮だと確かめたわけではない。** ここで `Fresh` と嘘をつくと、装飾を外した構成で
> **鮮度判定が消えたことに誰も気づかない**（本セッションで繰り返し出た「緑だが検査されていない」型）。

### 決定3: **`GetRateToBaseAsync` は `GetReadingAsync` から導く（二重実装しない）**

`CachingFxRateSource` の `GetRateToBaseAsync` は**自分で鮮度を判定し直さない**。
`GetReadingAsync` を呼び、**`Expired` なら `null`** を返すだけにする。

**二本立てにすると、片方だけ直して静かにずれる**（本リポジトリで繰り返している事故の型）。

### 決定4: 🔴 **決済には「実際に取得できた古いレート」を載せる。`1m` は載せない**

`Expired` のとき、決済意図の `FxRateToBase` には **`reading.Rate.Rate`（古いが実在する値）** を載せる。

**古いレートで換算した金額は不正確だが、`1m` で換算した金額は端的に誤りである。**
**前者は桁が合っている**（実勢からの乖離）。**後者は通貨を取り違えており約 150 倍ずれる。**

> 🔴 **【訂正・2026-08-15】初版は「前者は `AsOf` が台帳に残るので事後に判別できる」と書いていたが事実と異なる。**
> **`ApprovedOrderRow` は `FxRateToBase` の数値だけを持ち、`AsOf` の列が無い。**
> **結論は変わらない**が、根拠から「`AsOf` が残る」を取り下げる（残余リスクは IADR-0197 に明記した）。

### 決定5: **入口しかあり得ない場合は、LLM を呼ぶ前に見送る（費用の据え置き）**

ゲートを後ろへ動かすと、**鮮度切れでも LLM を呼ぶ**ことになり費用が出る（IADR-0107 決定2 が避けていた形）。

**保有が無ければ建玉効果は `Open` にしかならない。** したがって
**`Expired` かつ保有なしのときだけ、保有数を先に引いて即座に見送る。**

- **正常時の経路は変えない**（保有数の先読みは `Expired` のときだけ行う）。
- 先読みした保有数は**後段で再利用する**（ブローカ照会を二重に打たない）。

## やること

1. `Shared.Contracts` に `FxRateFreshness` と `FxRateReading` を新設
2. `IFxRateSource.GetReadingAsync` を既定実装つきで追加
3. `CachingFxRateSource` が鮮度を判定して `Reading` を返す（`Expired` を捨てない）
4. `IFxRateProvider` / `MarketFxRateProvider` に読み取り経路を追加
5. `TradeDecisionService`: `Expired` は**入口だけ**を止め、**決済は実レートで通す**
6. `TradeDecisionServiceTests.鮮度切れは非基準通貨の手仕舞いも止める_計画との乖離_506` を**「止めない」版へ差し替える**

## やらないこと

- **`OrderIntent.FxRateToBase` の nullable 化**（案 A。永続化へ波及する）
- **鮮度しきい値の変更**（5 日 / 30 日は計画で確定済み）
- **停止側の可視化**（#381 の残り）—— **本 PR で経路が決まるため、可視化はこの上に載せる**

## 受け入れ基準

- [x] **非基準通貨・鮮度切れで手仕舞いが発行される**
- [x] **否定形**: 同条件で**新規建ては止まる**（ゲートを丸ごと外していない）
- [x] 🔴 **否定形**: 決済へ載る `FxRateToBase` が **`1m` にならない**（実レートが載る）
- [x] **否定形**: レートが**まったく取得できない**ときは決済も出ない（値が無いのに載せない）
- [x] `Expired` かつ**保有なし**なら **LLM を呼ばずに**見送る
- [x] 警告域（5 日超〜30 日以下）では**発注が止まらない**（#381 の受け入れ基準の残り）
- [x] 既存テスト `..._計画との乖離_506` を差し替える（**残すと赤になる**）
- [x] **変異試験で効きを実測する**（**適用されたことを diff で確認してから**）

## テスト方針

| 何を守るか | どう守るか |
| --- | --- |
| 出口が塞がらないこと | 鮮度切れ＋保有あり＋Sell → **決済が出る** |
| 入口は止まること（否定形） | 鮮度切れ＋保有なし → **null**／鮮度切れ＋保有あり＋Buy → **null** |
| 🔴 台帳の金額 | 決済意図の `FxRateToBase` が **`1m` でない**・**実レートと一致** |
| 値が無いときに載せないこと | レート源が `null` → **決済も出ない** |
| 費用を増やさないこと | 鮮度切れ＋保有なしで **LLM が呼ばれない** |
| 鮮度判定の単一情報源 | `GetRateToBaseAsync` が `GetReadingAsync` と矛盾しない |

## 変異試験（実走した実測）

| # | 変異 | 落ちたテスト |
| ---: | --- | --- |
| 1 | 入口の停止を潰す | 「鮮度切れの新規建ては保有があっても止まる」 |
| 2 | 決済へ `1m` を載せる | 「実レートが載る・1m を載せない」ほか **4 件** |
| 3 | 保有なしの早期見送りを潰す | 「保有なしなら LLM を呼ばずに見送る」 |

### 🔴 **コンパイルできない変異は「殺された変異」と見分けがつかない**

変異 3 の初版は `if (false)` へ置き換えたところ**パターン変数 `held` が束縛されずビルドが壊れ**、
`dotnet test` が **exit 1** を返した ——**テストが落ちたのと同じ見え方になる。**

> **[#507](https://github.com/endazon/ai-stock-trading/pull/507)「弱い変異」／[#509](https://github.com/endazon/ai-stock-trading/pull/509)「当たらない変異」／本 PR「ビルドが壊れた変異」。**
> **3 つとも exit コードだけを見ると『効いた』と読める。**

**是正**: 変異の実行後に **`error CS` の件数を数え、0 を確かめてから**判定する。
変異 3 はコンパイルが通る形へ書き直し、**期待どおり 1 件だけが落ちる**ことを確認した。
