## 設計

### 1. 構造テスト —— **「実装していない」と「実装してはならない」を区別する**

先例は **[IADR-0164](../adr/IADR-0164_stage1-trade-count-setting-and-monitor-parameter-relocation.md) 決定1** である。あちらは「収集間隔を実行時に変更する経路が無いこと」をルート表の走査で固定した。棄却された案 A（何もしない）の理由がそのまま本作業に当てはまる。

> **「実装していない」と「実装してはならない」は別である。**
> 前者のままにすると、次に触る者が「未実装の項目」として素直に実装してしまう。

ADR-0012 が述べているのは後者である。**MCP 公開は「まだ作っていない機能」ではなく「作ってはならない機能」**であり、その区別はコード上のどこにも書かれていない。

| 論点 | 案 | 評価 |
| --- | --- | --- |
| 担保の方法 | A: 何もしない（基盤が既定非公開なので安全） | **棄却**（後述） |
| | B: `scripts/check-*.js` ＋ 専用 CI ジョブ | 棄却（後述） |
| | **C: `AiStockTrading.Architecture.Tests` の構造テスト** | **採用** |
| 検出の粒度 | D: 想定されるキー名（`mcp.exposure` 等）を列挙する | 棄却（**形が未知**。platform#445 で作り直される） |
| | **E: `mcp` の出現そのものを検出する** | **採用** |

#### A（何もしない）の棄却理由

**基盤の既定が非公開であることは、AST が公開しないことを保証しない。** 許可リスト方式は「AST が自分を登録しない限り公開されない」という意味であり、**登録する側は AST である**。ADR-0012 §結果 のフォローアップも「実装時、MCP 公開構成に本ユニットの文書コレクション・retrieval スコープが含まれないことを**確認する**」と書いている。確認を人の記憶に委ねるなら、それは担保ではない。

#### B（`scripts/` 検査）の棄却理由

検査対象が **C# ソースと deploy マニフェスト**であり、`AiStockTrading.Architecture.Tests`（`RepositoryLayout` で実ツリーを走査する既存の作法）に素直に収まる。`scripts/` 側の検査は Markdown / ワークフローを含む横断検査に使っており、**`.github/workflows/` には `mcp__github__*`（AI のツール許可リスト）が正当に存在する**ため、リポジトリ全体を対象にすると除外規則が要る。**対象を `backend/` と `deploy/` に限れば除外は 1 件（本テスト自身）で済む。**

#### E（`mcp` の出現そのものを検出する）の理由

**現在 0 件だからこそ、最も粗い検出が最も強い。** 「どういう形で書かれるか」は platform#445 の再実装まで分からない —— キー名を列挙する案 D は、**想定と違う形で書かれた瞬間に黙って素通りする**。

出現そのものを見れば、`McpExposureOptions` でも `mcp-server:` でも `"mcp": {...}` でも捕まる。誤検出の代償は「テストが落ちたので人が読む」だけであり、**本テストが求めているのはまさにそれ**である（失敗メッセージから ADR-0012 と本仕様書へ辿れるようにする）。

**空振りしないことを対照（肯定形）で固定する**: 走査したファイル数が十分に大きいこと・照合器が実際に `mcp` を検出できることを別の `[Fact]` で確認する。**「0 件でした」が「1 件も読んでいません」と区別できない形にはしない**（[IADR-0166](../adr/IADR-0166_plan-source-digest.md) と同じ規律）。

#### 走査対象は**拒否リスト**で決める（PR #451 レビューによる修正）

**当初は走査する拡張子の許可リストで書いていたが、これは誤りであった。** `Dockerfile` は `Path.GetExtension` が空文字列を返すため、**`backend/Dockerfile` と `deploy/opend/Dockerfile` の 2 件が黙って漏れていた**——**MCP サイドカーやクライアントの導入を `RUN` / `ENV` で書き得る場所**である。

**より重い問題は、それが「除外」として見えなかったことである。** 本仕様書と IADR-0171 は当初「除外は 1 件（本テスト自身）」と書いていたが、**許可リストそのものが 2 種類目の除外として働いていた**。**明示的な除外は数えられるが、許可リストの裏側にある除外は数えられない。**

拒否リストへ反転し、除外は**意図的に 1 種類（`.md`）＋本テスト自身**とした。**新しい種類のファイルは既定で走査対象になる。** あわせて、`Dockerfile` 2 件が走査対象に入っていることを**名指しの対照テスト**で固定した（回帰防止）。

### 2. `docs/security/security.md` への明文化

ADR-0012 §決定 の 3 点目（将来公開する場合の手続き）を、**実装リポジトリ側の読者が読む場所**に書く。書くのは次の 3 点である。

- 現状: **AST は MCP へ何も公開していない**（宣言そのものが存在しない）
- 禁止の範囲: **MCP という外部エージェント向け経路のみ**を閉じている —— 利用者本人による基盤チャット UI・RAG 検索・Discord からの参照（FR-08・FR-14）は**従来どおり可能**である
- 手続き: 公開するなら **ADR-0012 を Superseded する新 ADR** で、対象文書・ABAC 属性・データ越境ティア判定・無人エージェント（Client Credentials）の権限スコープを個別に定めてから行う

**2 点目を落とさないことが重要である。** 「MCP 非公開」を「AST のデータは誰も検索できない」と読み違えると、FR-08 / FR-14 の実装が萎縮する。

### 3. `docs/blocked-tasks.md` への登録

issue #348 のスコープのうち**結合確認だけが platform#445 待ち**である。**これを黙って落とすと、#348 をクローズした時点で「確認した」ことになってしまう。** A 群（実機・実環境が要るもの）へ項目を追加し、何を待っているかと、解消後に何を確認するかを書く。

## テスト方針

**この種の否定形テストは「効かない方向に壊れる」と、CI は緑のまま統制だけが消える。** 走査対象が 0 件になっても「違反 0 件」で緑になるためである。したがって

1. **走査ファイル数の下限**を別テストで固定する（現在 1100 件超）
2. **照合器そのもの**を合成文字列で検査する
3. **ミューテーション**で実際に赤くなることを実測する

の 3 点を揃える。

## 本作業で直さなかったこと

**`docs/security/security.md` は本節以外がほぼ雛形のままである。** 認証・認可・データ保護・秘密情報管理・監査ログ・脅威と対策のいずれも未記入であり、`author` / `created` も `<作成者>` `<YYYY-MM-DD>` のままである。

**本作業では MCP の節だけを足し、残りは埋めなかった。** 埋めるには実装の現状（Keycloak / ABAC の適用範囲・暗号化の実態・監査ログの保管期間）を横断調査する必要があり、**#348 とは別の作業**である。推測で埋めると、**セキュリティ仕様書が「書いてあるが実態と違う」という最も悪い状態**になる。

**したがって別 issue として起票する**（本 PR で起票し、本仕様書と PR 本文に番号を残す）。

## 残余リスク

1. **本テストは AST リポジトリ内しか見ない。** 基盤側の許可リストに AST の文書コレクションが**基盤側の PR で**追加された場合、本テストは何も言わない。**これが結合確認（platform#445 待ち）が必要な理由そのもの**である。
2. **`mcp` の出現検出は粗い。** MCP 公開を意味しない記述（例: 無関係な略語）でも落ちる。**誤検出は安全側**だが、頻発すれば除外リストが育ち、育った分だけ検査は弱くなる。
3. **`docs/` は走査対象外である。** 設計文書に MCP 公開を書いても検出しない（意図的 —— 本仕様書自身が `mcp` を多数含む）。**宣言が入るのは構成とコードであり、そこを見ている。**
4. **ADR-0012 が Superseded された後も本テストは残る。** 公開を決めた新 ADR の実装時に、本テストを**明示的に外す**必要がある（外す作業そのものがレビューの契機になるため、これは意図した設計である）。
