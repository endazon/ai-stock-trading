# 仕様書: バックログ定期監査の自動化

> 本仕様書は実装着手前に作成する。

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: **なし**（NFR。保守性・運用）
- 実装 ADR: **[IADR-0170](../adr/IADR-0170_backlog-audit-automation.md)（本作業で新設）**
- 起点 issue: [#439](https://github.com/endazon/ai-stock-trading/issues/439)
- 一次情報: [`docs/blocked-tasks.md`](../blocked-tasks.md)（A 群・B 群）／[`feedback/README.md`](../../feedback/README.md)（環流の手順）／[`docs/ai-workflow.md`](../ai-workflow.md)

## 目的・背景

2026-08-07 のバックログ監査で、**issue が増える主因は実装速度ではなく、閉じるより速く増えること**だと判明した（14 日間で 起票 111 / クローズ 86 / 純増 +25・消化率 77%）。

**実装のスループットは十分に高い。問題は分母側にあり、その一部は機械的に検出できる無駄であった。**

| 種類 | 実測 |
| --- | --- |
| クローズ漏れ | #319 / #391 / #356 が実装済みのまま open（当時の open 37 件の 8%） |
| 重複起票（計画側） | 同一主題が 3 件ずつ。**16 分間に 14 件**・3 つの命名規約が混在 |
| **環流の未起票** | `feedback/*.md` が `status: open` のまま、計画側 issue が無い |
| blocked の滞留 | A 群・B 群が 8 件前後。**AI がどれだけ働いても減らない** |

**いずれも定期的に見れば分かるが、誰も定期的に見ていなかった。**

### 本作業の着手時点での実測（`feedback/` 27 件）

**`status: open` かつ計画側 issue への参照（番号つき）が本文に無い記録が 6 件あった。**

ただし**猶予 3 日を超えているのは 1 件だけ**である（`20260708_trading-defaults-derived-values.md`・**30 日**）。残る 5 件はいずれも 0〜2 日であり、**起票までのタイムラグとして正常**である——これがしきい値を設ける理由そのものである（ゼロ日で報告すれば 6 件すべてが騒音になる）。

## 対象範囲

### 対象

| # | 追加物 | 役割 |
| --- | --- | --- |
| 1 | `scripts/check-feedback-reflux.js` | 環流記録の front matter を走査し、**未起票のまま滞留している記録**を報告する |
| 2 | `.github/workflows/backlog-audit.yml` | 週次で AI にバックログを監査させ、**単一の追跡 issue へ upsert** する |
| 3 | ラベル `blocked:env` / `blocked:decision` / `blocked:human` | **消化率の分母から外して数える**ための可視化 |

### 対象外（意図的にやらない）

- **AI による自動クローズ**（誤クローズの手戻りが放置のコストを上回る）
- **起票そのものの抑制**（AI レビュー・監査が issue を生むのは品質上正しい）
- `docs/blocked-tasks.md` の廃止（人間向けの読み物として機能している。監査は**突き合わせる**側に回る）
- 計画リポジトリ側の監査（`/triage-feedback` が担う）
- **`status: resolved` なのに計画側 issue が open のまま、という逆向きの乖離の機械検出**（後述の判断 3）

## 設計

### 1. `check-feedback-reflux.js`（機械的検査・**warn のみ**）

**CI では警告にとどめ、ブロックしない。** 環流は起票までにタイムラグがあるのが正常であり、落とすと正常な運用が止まる。

| 検出 | 条件 |
| --- | --- |
| `status` 欠落 | front matter に `status:` が無い／空（`TEMPLATE.md` は除外） |
| **未起票の滞留** | `status: open` **かつ** 本文に計画側 issue への参照が無い **かつ** `created` から **N 日超**（既定 3） |

**日数のしきい値が要である。** 起票直後は本文に issue 番号が入らない運用であるため、**ゼロ日で落とすと正常な運用を止める**。

計画側 issue の参照は、実データに現れる 2 形（`project-planning#NNN` と `project-planning/issues/NNN`）で判定する。**`project-planning/`（番号なし）は参照とみなさない** —— リポジトリへのリンクであって起票の証拠ではない。

### 2. 週次の AI 監査（`backlog-audit.yml`）

`schedule` で週 1 回起動し、`claude-code-review.yml` と同じ認証・許可リストの流儀で AI に監査させる。

- **クローズ漏れ**: 実コード・実ワークフローを読んで確認する（**タイトルからの推測で閉じない**）
- **重複**: 主題が重なる組を列挙する（先着を正とする）
- **blocked の棚卸し**: `docs/blocked-tasks.md` の A 群・B 群と open issue を突き合わせる
- **エピックの進捗**: #344 の子 issue を集計する

**この監査は issue を自動でクローズしない。** 提案の一覧を単一の追跡 issue へ upsert し、**判断は人間に残す**。

### 3. ラベル

`blocked:env`（実機/実環境）・`blocked:decision`（計画側の裁定待ち）・`blocked:human`（権限・人間の操作）。**これらを分母から外すと「AI が今日着手できる issue」が見える。**

## 実装上の判断（IADR-0170 に記録する）

| # | 判断 | 内容 |
| --- | --- | --- |
| 1 | **検査は warn に固定し、exit 1 にしない** | 環流のタイムラグは正常。落とすと「検査を外す」動機を生む |
| 2 | **しきい値は既定 3 日・環境変数で上書き可** | 0 日は正常運用を止め、長すぎると検出しない |
| 3 | **逆向きの乖離（`resolved` なのに計画側が open）は機械検査に入れない** | **計画リポジトリの issue 状態を問い合わせないと判定できない**。本スクリプトは外部依存ゼロを保つ（`check-doc-links.js` と同じ）。この観点は**週次 AI 監査の担当**とする |
| 4 | **週次 Routine（セッション由来）は本ワークフローで置き換える** | 2026-08-07 に session Routine を作ったが、**リポジトリに残らず追跡もできない**。ワークフローが正の実装であり、Routine は本作業のマージ後に削除する |

## 受け入れ基準

- [ ] `scripts/check-feedback-reflux.js` が **status 欠落**・**未起票の滞留**を検出する
- [ ] **N 日以内は検出しない**（正常運用を止めない）
- [ ] CI で **warn（exit 0）** であり、ブロックしない
- [ ] `scripts/scripts.test.js` に単体試験（正常系／`status` 欠落／N 日超／N 日以内／参照の 2 形）
- [ ] **実ツリー回帰**（現在の `feedback/` を走査して例外を投げない）
- [ ] **ミューテーション**: 日数比較を 1 段ずらすと境界のテストが赤くなる
- [ ] 週次ワークフローを追加し、`check-ai-workflow-config.js` が通る
- [x] ラベルの語彙を作り、**既存ラベルを確認できた issue へ付与する**（#397 → `blocked:env` / #342 → `blocked:env`）
- [ ] **残りの付与は初回の週次監査へ委ねる**（下記「意図的に完了させなかったこと」）

### 意図的に完了させなかったこと — ラベルの全件付与

**`blocked:*` ラベルを A 群・B 群の全 issue へ付けることは、本作業では行わなかった。**

理由は 2 つある。

1. **GitHub の issue 更新はラベル集合を置換する。** 既存ラベル（`enhancement` 等）を確認せずに付けると**既存のラベルを黙って落とす**。全 open issue のラベルを 1 件ずつ確認する必要があり、**この PR の主題（検査と監査の仕組み）とは別の作業**である。
2. **どの issue が本当に blocked かは per-issue の判断である。** `docs/blocked-tasks.md` からの機械抽出は PR 番号や解消済みの行まで拾い、**タイトルからの推測で貼るのは決定6 が禁じた形と同じ**である。

**したがって初回の週次監査に「ラベルの付け漏れを根拠つきで挙げる」ことを担当させた**（ワークフローのプロンプトに明記済み）。付与そのものは、その提案を見てから行う。

**語彙は既に存在する** —— 実際に付けた 2 件（#397 / #342）で `blocked:env` が作成済みであり、残る 2 種は初回付与時に同様に作られる。

## テスト方針

**この検査も「効かない方向に壊れる」と、CI は緑のまま滞留だけが戻る。** したがって**しきい値の境界**を両方向で固定し、**ミューテーションで効きを実測する**（#439 が明示的に要求している）。

## 残余リスク

1. **参照の検出は綴りに依存する。** 別形式（例: 短縮 URL）で起票を書くと未起票と誤判定する。
2. **`status` は人手で更新される。** 起票したのに `open` のままなら滞留として報告され続ける（**誤検出だが安全側**）。
3. **逆向きの乖離は機械検査していない**（判断 3）。週次 AI 監査に委ねるため、**その監査が動かなければ検出されない**。
4. **週次監査の質は AI の実行環境（許可リスト・トークン）に依存する。** 権限拒否で静かに劣化し得る——`check-permission-denials.js` が同ジョブで効くようにする。
