# トレーサビリティ規約の別紙（該当作業のときだけ読む）

> **本書は [`.claude/rules/traceability.md`](../.claude/rules/traceability.md)（および同ディレクトリの
> companion）の別紙である。** 規約の**本文と判断基準は規約側が持つ**。ここに置くのは、**検査器を配線する
> とき・改番するとき・クロスリポジトリ表記の細目に当たるとき・CHANGELOG を是正するとき・`docs/` の
> trace ブロックを書くときにだけ要る運用の詳細**である。
>
> 🔴 **分離の理由は読書予算である。** 規約側は毎セッション全文が読まれる（総量予算の対象。
> [`ai-workflow.md`](ai-workflow.md) §必読規約の総量予算の測り方）。**別紙は予算の対象外**であり、
> 該当作業のときだけ開けばよい。
>
> 🔴 **本書自身が「本文に ID を書かない」体制の中にある。** `docs/` 配下であるため、計画 ID・実装ADR・
> 仕様書・他リポジトリの issue 番号を**表示テキストへ書けない**（`scripts/check-trace-blocks.js` が
> 検査する）。**規約を説明するために ID の形を示す必要があるときは、インラインコードではなく
> コードフェンスに入れる** —— 検査はコードフェンスの中だけを可視本文から除く。実在の番号を引くときは
> 本書冒頭の trace ブロックへ入れ、地の文では「資料再編の計画 ADR」のように内容で呼ぶ。
>
> 🔴 **［2026-08-21 変更］本書はもはやキットとのバイト一致を前提としない。** 旧は「キット同期では
> 本書と規約本文を同時に取り込む」ことを求めていた（片側だけでも同期検査が緑になるため）。資料再編で
> **キットは bootstrap 専用となり同期検査が退役した**ため、新は本リポジトリの実情に合わせて書き換えてよい。

## trace ブロック（`docs/` 配下の非表示メタデータ）

**規約の本文は資料再編の計画 ADR 決定 4 が持つ**（本書冒頭の trace ブロックの `adrs` キーを参照）。
ここに置くのは書くときの実務だけである。**機械検査は `scripts/check-trace-blocks.js`**（CI の
`trace-blocks` ジョブ。`--self-test` あり）。

- **置き場所**: frontmatter 終端の直後・最初の H1 見出しの直前。**1 文書 1 ブロック**。frontmatter が
  無い文書ではファイル先頭に置く。**間に空行を挟まない**（挟むと配置違反になる）。
- **キーは 5 つで、この順にすべて 1 回ずつ持つ**（欠け・重複・順序違い・未知キーはいずれも error）。
  **空でも省略しない**（値の無いキーは空配列で書く）。

  ```text
  キー      入れるもの                                        値の形（例）
  ids       計画の機能要求 / ユースケース / 画面 / 非機能要件   FR-05, UC-01, SC-02, NFR（無採番可）
  adrs      計画 ADR                                          ADR-0004
  iadrs     実装ADR（他リポジトリは短縮名で修飾）              IADR-0004, MSP:IADR-0012
  specs     作業仕様書（拡張子なしのベース名）                 20260627_FR-03_hybrid-search
  issues    issue / PR 番号（本リポジトリは裸、他は修飾）      #487, planning#343
  ```

  **書式の実例は本書冒頭のブロックそのものである** —— レンダリングでは見えないので raw で開いて確かめること。
- **値域の検査**: `ids` の機能要求・ユースケース・画面と `adrs` の計画 ADR は
  [`.claude/rules/traceability.repo.md`](../.claude/rules/traceability.repo.md)「起点 ID の種別（固有）」が
  宣言するレンジ（`scripts/lib/plan-ranges.js` が読む）、`iadrs` は `.ai-context/adr/` のファイル実在で見る。
  **他プロジェクト・他リポジトリの修飾（英数字の短縮名 ＋ `:`）が付いたトークンは external とみなし、
  実在検査の対象外**にする（個別のリポジトリ名は検査器へハードコードしない。計画 ADR 決定 9）。
- **表の中で ID を示す必要がある場合**は、表の直後に隣接する trace-table ブロックへ置く（`row1` から
  連番で 1 行 1 セル分）。**trace-table だけがあって trace ブロックが無い文書は error** である。
- 🔴 **可視本文への残存が error になる。** HTML コメントの外・**コードフェンスの外**に計画 ID・実装ADR・
  修飾付き issue 参照が 1 つでもあれば落ちる。**インラインコードは除外されない**（コードフェンスだけが
  除外対象である）。裸の `#NNN`（本リポジトリの issue 言及）は対象外で、地の文に書いてよい。
  - **規約を説明する文書でも同じである。** ID の形を例示したいときはコードフェンスに入れる。
    ただし**フェンスの中でも trace ブロックのマーカー文字列そのものは書けない** —— 検査器は
    フェンスを解さずにマーカーを探すため、2 個目のブロックとして拾われる。
- **除外ルート**（母集合の規則 6 に従い、実行のたびに理由つきで標準出力へ出す）: `docs/templates/`
  （記入欄・例示の ID プレースホルダがテンプレートの目的そのもの）と `docs/blocked-tasks.md`
  （ID をキーとする作業台帳。隠すと台帳として機能しない）。
- **trace ブロックを持たない文書は許容する**（既存文書の即時移行を強制しない）。ただし**可視本文への
  残存検査は全文書に掛かる**ため、ID を本文へ書いたまま放置はできない。
- **参照グラフは `scripts/gen-knowledge-graph.js` が組み立てる**（`docs/` の trace ブロック ＋
  `.ai-context/{adr,specs}/` の frontmatter）。`--json` / `--mermaid [--scope <dir>]` / `--check`。
  **生成物はコミットしない**（都度標準出力へ書く）。

## 検査器の配線

### 計画 ID 修飾の機械検査（`check-plan-id-qualification.js`）

- `scripts/check-plan-id-qualification.js` が**空白区切りの形**（`AST` と ID が空白・TAB・
  wiki リンク括弧・バッククォート・全角括弧で離れる形）を検出する。**配布時に冒頭の置換点
  `PROJECT_PREFIXES` を書き換えること。空のままなら skip する**（他プロジェクトを参照しない
  リポジトリでは対象が無い）。`maskCode` を `check-cross-repo-refs.js` から借りているため
  **2 本セットで配布する**。
- **文脈から裸の ID を推測する形は検出しない**（偽陽性が避けられず、1 件でも出すと検査そのものが
  外されるため）。

### キット配布物の中では、他リポジトリの `ADR` / `IADR` を番号で引かない

- **配布物（`.claude/rules/traceability.md`・`scripts/` 等）には「自リポジトリ」が無く、裸の番号は
  配布先ごとに別の決定を指す。** 出典を示すなら**決定の内容を 1 行で書く**か `<PROJ>/<ID>` で修飾する。
- **機械検査は無い** —— 配布先では裸の `IADR-NNNN` が正しい参照であり、区別できない（実測。
  キットの docstring が引いた実装ADR番号は、配布先では無関係な ADR を指し、
  それを裏取りせず引き写した記述が 2 ファイルへ入った）。

### コミットメッセージ検査（`check-commit-messages.js`）の詳細

- **末尾の PR 番号**: 半角スペース + `(#123)` はスカッシュマージ既定件名として許容。
  **前提を書いていなかったため、実測した配布元では「末尾に番号を持つ PR のうち、自番号と
  一致するものが 1 件も無かった」**（起点 issue の番号だと解釈されていた）。
  `pr-title.yml` が `PR_NUMBER` を渡す構成では、`check-commit-messages.js` が一致を検査する。
- **実装ADR の実在性**: スコープの実装ADR は本リポ **`.ai-context/adr/`** に該当ファイルが実在することを
  検査する（PR コミットと PR タイトルの両方）。
- 🔴 **コミット件名の計画 ADR 実在性検査は、いま働いていない。** `check-commit-messages.js` は計画 ADR を
  **planning submodule の `projects/<name>/07_adr/` のファイル実在**で見る作りのままであり、資料再編
  （計画 ADR 決定 2）で submodule を撤去したため**恒久的に skip される**。実行時に
  `notice: planning submodule が未 populate のため計画 ADR 実在性チェックをスキップした` が出る
  —— **この notice は「違反 0 件」ではなく「検査していない」と読む。**
  - **旧**（submodule あり）: PR CI が submodule を取得しない構成だったため、実効していたのは実装ADR 検査
    だけだった。取得するジョブへ結線すれば計画 ADR まで効かせられた。
  - **新**（submodule なし）: 結線先が存在しないため、**件名の計画 ADR は書き手と PR レビューが守る**。
    **配備までの暫定手段**はこれである。なお `docs/` の trace ブロックの `adrs:` は別経路で、
    `.claude/rules/traceability.repo.md` が宣言するレンジを `scripts/lib/plan-ranges.js` 経由で
    `check-trace-blocks.js` が検査する（そちらは実効している）。**件名側を同じレンジで見るように
    直すのは未実施であり、直すなら `loadPlanAdrIds()` の取得元をレンジ宣言へ差し替える。**
- **`FR` / `UC` / `SC` の実在性**: 同様にスコープの計画レンジも実在を検査する。**この検査が無い間、
  実在しない画面 ID を騙る件名も exit 0 で受理され、スカッシュ後件名として恒久履歴へ載れた**（force push 禁止で
  事後修正できない面である）。**レンジの正はリポジトリ固有**（配布先ごとに計画プロジェクトが違う）の
  ため、キットはパーサを持たず**拡張点 `scripts/check-test-traceability.js` の `readPlanIds()` を探す**。
  - **持たない構成では skip し、skip したことを notice で出す**（黙って 0 件検査へ落ちない）。
  - **拡張点は在るが節をパースできない場合は fail** させる。追跡下の必ず読めるファイルを読めないのは
    環境差ではなく**規約側の破壊**（節の改名・書式変更）であり、黙って通すと**単一情報源が壊れたまま
    「違反 0 件」で緑になる**。
- **他リポジトリ番号の修飾を 3 つの面で見る**: **件名・本文（`%b`）・PR タイトル**。判定器は
  `check-cross-repo-refs.js` から借りる（規約の単一情報源は同スクリプト側）。**本文を見るのは、
  列挙形の修飾漏れが本文にも出るためである** —— 件名だけでは足りない。この 3 面は**裸の `#NNN` が
  本リポジトリの issue へ自動リンクする**面であり、`.md` と違って**誤リンクという実害が出る**。

### 検査対象から除外する自動コミット

- **自動コミットの著者**: `dependabot[bot]` / `renovate[bot]` / `github-actions[bot]` 等の bot 著者。
- **マージコミット**: `--no-merges` により除外。
- **自動生成・リバート**: 件名に `[skip ci]` を含むコミット、および `Revert "..."`。

除外リストは `scripts/check-commit-messages.js` の `BOT_AUTHORS` と同時に更新する。

### PR タイトル検査（`pr-title.yml`）の配線

- **`PR_NUMBER`（`github.event.pull_request.number`）を渡すこと。** 渡すと、末尾の `(#NNN)` が
  **PR 自身の番号**かどうかまで検査される。**渡さないと形状しか見られず、起点 issue の番号を
  書いた PR が素通りする**。**未設定なら従来どおり形状のみを見る** —— コミット件名モードには
  PR 番号が無く、必須にするとスカッシュ後の履歴コミットが全滅するためである。
- 検査ロジックは `check-commit-messages.js` の単一件名モード（`--title` 引数 / `PR_TITLE` 環境変数）で、
  `validateSubject` を再利用する（規約の単一情報源）。
- `pull_request` の `opened/edited/reopened/synchronize` で起動し、タイトル後編集も再検査する。
- **事前防止と事後補正の使い分け**: `pr-title.yml` は**マージ前**の予防（規約外件名を止める）。
  万一すり抜けて develop に規約外件名が入った場合は、履歴不変の原則（force push 禁止）に従い、
  CHANGELOG 生成時の `changelog-overrides.json`（`action: "remap"`）で**生成物のみ**是正する。
  前者が第一防衛線、後者が最終手段という役割分担。

### bot 作成 PR の除外は「スクリプト側・完全一致」で行う

- 🔴 **ワークフローの条件で `pull_request.user.type != 'Bot'` により弾いてはならない。** GitHub App が
  作成した PR（`claude[bot]` 等）も `user.type == 'Bot'` になるため、**AI に実装を委ねる運用（本キットが
  前提とする主要な経路）でだけ「最後の砦」が skipped になる**。実際に、人間が作った PR は success・
  GitHub App が作った PR は skipped という差が観測された（計画リポジトリ側の実測）。
- 判定は `PR_AUTHOR` 環境変数（`github.event.pull_request.user.login`）を渡し、`isBotLogin()` が
  `BOT_AUTHORS` へ**完全一致**した場合のみ除外する。コミット著者向けの `isBot()` が「著者名＋メール」への
  部分一致であるのと異なる —— PR 作成者は単一のログイン名で得られ、部分一致にすると `dependabot` を
  含む無関係なログイン名まで除外され得るためである。

### `check-cross-repo-refs.js` の置換点は配布時に必ず書き換える

冒頭の `CROSS_REPOS` / `SELF_NAMES` / `EXCLUDE_PATHSPECS` / `EXCLUDED_DIRS` / `KNOWN_OWNERS` /
`REPO_RELATIVE_PATHS` が対象である。**書き忘れは 2 つの形で検査を無力化する。**

| 置換点 | 書き忘れると | 帰結 |
| --- | --- | --- |
| `SELF_NAMES`（本リポジトリ自身を指す名前） | **正当な自リポ参照を大量に違反として上げる**（実測 22 件） | **検査そのものを外させる** |
| `KNOWN_OWNERS` | **書き換えるまで型 4（フルパス形式の owner 誤り）を検査しない。** プレースホルダのまま検査すると規約が許す正しい表記を全件違反として上げる | 同じ事故になる |

**検査していないことは実行時に notice で出す**（「検査していない」と「違反 0 件」を読み分けるため）。

## 採番衝突時の改番の追随 5 項目

改番時は以下を**すべて**追随させる。

1. ファイル名（`.ai-context/adr/IADR-xxxx_*.md`）と本文中の自番号
2. 索引（`.ai-context/adr/README.md`）・関連仕様書（`.ai-context/specs/` の `related_ids` / 本文）
   と、`docs/` 側で当該番号を引いている文書の **trace ブロック**（`iadrs:` キー。表示テキストには無い）
3. コード内コメント・テスト名の起点 ID
4. **PR タイトル**（= スカッシュ後にコミット件名として統合ブランチへ載る。ここだけが人手の追随に
   依存するため最も漏れやすい。ブランチ名は既 push なら変更不要だが、タイトルは必ず直す）
5. **計画リポジトリが引く自番号**（`projects/<name>/07_adr/*.md` の地の文）。**ここは fail-open で
   ある** —— 探さなければ何も起きない。**主たる担保は計画側の機械検査である。**

## クロスリポジトリの issue / PR 番号 —— 面ごとの壊れ方と書き方

**面によって壊れ方が違う。** 同じ違反でも、書く場所によって実害の性質が変わる（実測）。

| 面 | 裸の `#NNN` の扱い | 違反の実害 |
| --- | --- | --- |
| **issue / PR の本文・コミットメッセージ** | **本リポジトリの issue / PR へ自動リンクする** | **誤リンク**（無関係な issue を指す）。実害が出る |
| **`.md` ファイル** | **自動リンクにならない**（`.md` でリンクになるのはフルパス形式だけである） | **表記ゆれ**（機械的突合が不安定になる）。誤リンクは起きない |
| 🔴 **PR タイトル → スカッシュ後件名** | （番号の自動リンクとは別の問題）**素の `<` `>` `&` `"` を GitHub が作成時点でエスケープする** | **恒久履歴への焼き付き。** スカッシュ件名に `&lt;…&gt;` が載り、**force push 禁止のため直せない** |

- したがって、**優先して直すのは issue / PR / コミットメッセージ側**である。`.md` 側は突合の安定
  のために揃える。
- **山括弧のプレースホルダ（`<owner>` の形）を `.md` にそのまま書かない。** `.md` のファイル上は
  正しく読めるが、**issue 本文へ転記した時点で GitHub が HTML タグとみなして黙って除去する**
  （実際に起票済みの issue 本文が意味の通らない記述になった）。バッククォートで囲むか、
  山括弧を使わない書き方にする。**転記先の面ごとに壊れ方が違うことを前提に書くこと。**
  - 🔴 **PR タイトルでは「除去」ではなく「エスケープ」になり、恒久履歴へ残る**（実測）。
    実測: `git -C <submodule> grep` と書いた PR タイトルが、スカッシュ後件名へ
    `git -C &lt;submodule&gt; grep` として焼き付いた。生成物（CHANGELOG）は
    `changelog-overrides.json` の `remap` で是正できるが、**履歴は残る**。
    **`check-commit-messages.js` が件名・PR タイトルの HTML エンティティを検査し、`pr-title.yml`
    経由でマージ前に止める**（エスケープは GitHub 側で起きるため、**検査対象はエスケープ済みの
    文字列**である。素の `<` を検査しても素通りする）。
- **機械検査の 4 つの型**（長い表記の裸書き／列挙形の修飾漏れ／修飾語と番号が空白で離れる形／
  **フルパス形式の owner 誤り**）のうち、**owner 誤りだけは上の表の外にある** —— フルパス形式は
  `.md` でも自動リンクするため、owner を誤ると**表記ゆれではなく死んだリンク**になる。
- **関連番号を添える注記 `〔〕` の中も列挙として見る。** `PR planning#NNN〔裁定依頼 planning#MMM〕`
  のように**中の番号も修飾する**こと。**全角丸括弧 `（` は区切りとして扱わない** —— 日本語の地の文で
  従属節を開く記号であり、その直後の裸 `#NNN` が本リポジトリを指すのは正しいためである。
- **走査は追跡下の全ファイルである**（`*.md` に限らない）。人が読む散文は `docs/` だけでなく
  `.github/` や `deploy/` にもあり、`*.md` だけを見ていた頃はワークフロー YAML の中の違反を
  誰も見ていなかった（実測）。**置換点 `EXCLUDED_DIRS` のディレクトリの非 Markdown だけ**を外し、
  **除外件数をログに出す**（「検査していない」と「違反 0 件」を読み分けるため）。

## CHANGELOG 生成時の誤記補正・除外の運用

**原則は規約本文が持つ**（履歴は不変・生成物のみ是正・`reason` を必ず残す）。ここは `overrides` の
書き方だけを置く。宣言先は `scripts/changelog-overrides.json` の `overrides` 配列で、`hash` は
**短縮 SHA の前方一致**である。

| `action` | 用途 | 指定できる項目 |
| --- | --- | --- |
| `remap` | 誤った起点 ID・種別・要約を **CHANGELOG 上でのみ**差し替える | `type` / `scope` / `desc`（省略した項目は元コミットの値を保つ） |
| `exclude` | CHANGELOG に載せるべきでないコミット（試験的・巻き戻し前提の作業等）を生成物から除外する | —— |

- 例: 件名の起点 ID がリスク統制を指しているが実体は基盤スケルトン（P0）である場合、`scope` を
  `P0` へ補正する。**実体が大規模実装なら `type` は `feat` のまま保持し、`docs` へ remap しない**
  （実装をドキュメントとして過小計上する、新たな誤帰属を避ける）。
- 🔴 **配布時の `overrides` は空である。他リポジトリの SHA を引き継がないこと** ——
  `hash` は前方一致のため、**偶然一致した無関係なコミットを誤って差し替える**。
- `exclude` でも git 履歴には残るため、追跡可能性は失われない。
- **未知の `action`（タイプミス等）は `gen-changelog.js` が警告を出して補正を無視する**
  （黙って `remap` 扱いにしない）。許可値は `remap` / `exclude` の 2 種のみ。

CI（`changelog.yml`）は `develop` / `main` への push で `fetch-depth: 0` の全履歴から CHANGELOG を
再生成し、本補正を含む差分を PR 経由で反映する。
